# Which values of tcp_user_timeout, TCP keepalives and a liveness-probe interval let a psycopg 3 listener detect a half-open connection after a network partition or failover within a bounded time on Linux and macOS?

## Question

What settings for libpq's `tcp_user_timeout`, its TCP keepalive parameters, and an application-level liveness probe let a psycopg 3 `LISTEN` connection notice, within a known time, that its peer has silently gone away? The peer might vanish because of a network partition, a host loss or a failover. The settings must work on both Linux and macOS.

## Findings

### Why a listener needs explicit bounds

A dedicated `LISTEN` connection is idle almost all the time. A psycopg 3 listener parked in `Connection.notifies()` just waits for its socket to become readable. If the server host disappears, or a partition drops packets, without a FIN or RST reaching the client, nothing arrives and nothing fails. TCP itself gives no help by default. RFC 9293 says keep-alives "MUST default to off" and that their interval "MUST default to no less than two hours". Without tuning, a half-open listener can wait indefinitely while events pile up unseen.

Three mechanisms bound the wait. Each covers a different connection state:

1. **TCP keepalives** cover the *idle* connection, where no sent data is waiting for an acknowledgement. libpq turns `SO_KEEPALIVE` on by default (`keepalives=1`). It leaves the idle time, probe interval and probe count at the OS defaults, though:
   - Linux: 7200 s idle, 75 s interval and 9 probes, which the kernel docs describe as "~11 minutes of retries" after a two-hour wait.
   - macOS (xnu): two hours idle, 75 s interval and 8 probes.

   Either way, the defaults detect nothing useful.
2. **`TCP_USER_TIMEOUT`** covers the *busy* connection, where sent data is unacknowledged. On Linux, keepalives are not engaged while the retransmission timer is running (Cloudflare's measurements). So a liveness query sent into a dead link waits on `tcp_retries2` instead. Its default of 15 gives "a hypothetical timeout of 924.6 seconds" as a lower bound. Cloudflare observed about 940 s, and tcp(7) says 13 to 30 minutes.
3. **An application liveness probe** covers what TCP cannot see. One case is a TCP endpoint that is alive while the database behind it is not, such as a proxy that terminates TCP. Keepalives are answered by whichever host terminates the TCP connection, so they only prove that hop. The other case is a platform where a socket option is a no-op.

### What libpq actually sets on each platform

| libpq parameter | Linux | macOS (xnu) |
|---|---|---|
| `keepalives_idle` (s) | `TCP_KEEPIDLE` | `TCP_KEEPALIVE` (see note 1) |
| `keepalives_interval` (s) | `TCP_KEEPINTVL` | `TCP_KEEPINTVL` (defined in xnu's `tcp.h`; seconds) |
| `keepalives_count` | `TCP_KEEPCNT` | `TCP_KEEPCNT` (defined in xnu's `tcp.h`) |
| `tcp_user_timeout` (ms) | `TCP_USER_TIMEOUT` | silently ignored (see note 2) |

1. PostgreSQL's source maps its idle option to `TCP_KEEPALIVE` when `__darwin__` is defined. xnu documents that option as the "idle time used when SO_KEEPALIVE is enabled", in seconds.
2. xnu's `tcp.h` defines no `TCP_USER_TIMEOUT`. libpq's `setTCPUserTimeout` calls `setsockopt` only inside `#ifdef TCP_USER_TIMEOUT`, and the libpq docs say that "on other systems, it has no effect". So on macOS the parameter is accepted and does nothing, with no error.

All four parameters are ignored on Unix-domain sockets.

### How the Linux options interact

tcp(7) says that "when used with the TCP keepalive (SO_KEEPALIVE) option, TCP_USER_TIMEOUT will override keepalive to determine when to close a connection due to keepalive failure." Cloudflare's experiments show what that means in practice:

- With `TCP_KEEPCNT=3` but `TCP_USER_TIMEOUT=30s`, the socket sent six probes, not three.
- With a 5 s user timeout, a 1 s idle time and an 11 s interval, the socket was dropped at the second probe timer, about 12 s in.

Cloudflare's guidance is to set `TCP_USER_TIMEOUT` to roughly, or slightly below, `TCP_KEEPIDLE + TCP_KEEPINTVL * TCP_KEEPCNT`. That way the keepalive count keeps its meaning, and the busy and idle paths fail at about the same time.

RFC 5482 states the opposite constraint for its user-timeout option: the keep-alive timer must exceed the user timeout. Its concern is a keepalive abort cutting short a connection that a long user timeout was meant to keep alive. That is not the goal here. On Linux the user timeout governs the keepalive drop anyway, so the alignment rule is the one that matters in practice.

### Recommended values

The following profile targets about 25 s detection for an idle half-open listener, with a worst case of about one minute:

```text
keepalives=1
keepalives_idle=10
keepalives_interval=5
keepalives_count=3
tcp_user_timeout=25000      # Linux only; a no-op on macOS
connect_timeout=5           # bounds each reconnect attempt, per host
```

You can pass these as libpq conninfo keywords to psycopg, for example `psycopg.connect("host=... keepalives_idle=10 keepalives_interval=5 keepalives_count=3 tcp_user_timeout=25000 connect_timeout=5", autocommit=True)`. Note that `connect_timeout` "applies separately to each host name or IP address". With a multi-host conninfo, a reconnect attempt can therefore take up to N × 5 s.

The bounds below are derived from the sources' timer semantics. They are not end-to-end measurements of psycopg.

| Scenario | Linux | macOS |
|---|---|---|
| Idle listener, link dies silently | Probes at about 10, 15 and 20 s, then a drop at about 25 s after the last segment received. The user timeout fires at the same moment. | xnu drops when the time since the last received segment reaches `KEEPIDLE + MAXIDLE` (count × interval), so about 25 s. |
| Probe query sent into a dead link | Keepalives are suspended, and `tcp_user_timeout` drops the socket about 25 s after the unacknowledged send instead of after 924.6 s or more. Worst case from link loss is about 25 + 25 = 50 s, if the probe goes out just before the keepalive would have fired. | There is no user timeout. xnu stops retransmitting after `TCP_MAXRXTSHIFT = 12` retransmits, with backoff multipliers 1, 2, 4 … 64 and the timeout capped at 64 s. That is several minutes: about 8.5 min with a 1 s base retransmission timeout, by my estimate. See the caveat below. |
| Failover by IP takeover, or a server restart on a live host | Fast. Per RFC 9293, a reset "is sent in response to any incoming segment" for a connection that does not exist, so the next keepalive (≤ 10 s) or probe gets an RST. A restarting server closes its sockets outright. | Same. |
| Host loss, or DNS-switched endpoint with the old address black-holed | Only the timers above apply: about 25 s idle, about 50 s worst case. | About 25 s idle. A probe in flight depends on the caveat below. |

AWS's Aurora PostgreSQL fast-failover guidance is more aggressive: idle 1, interval 1, count 5, which "should notify the application within five seconds when the database stops responding". It notes the trade-off: on networks that drop keepalives, raise the count, which in turn lengthens the time to detect a real failure. A process holds a single listener connection, so even 1-second probes cost almost nothing. The real constraint is false positives. Keep `tcp_user_timeout` and `keepalives_interval × keepalives_count` well above the worst round-trip-time spikes you expect, and scale all three up for cross-region links.

**macOS caveat.** xnu's keepalive timer computes idle time from the last *received* segment. The drop check in `tcp_timer.c` (`idle_time >= TCP_CONN_KEEPIDLE + TCP_CONN_MAXIDLE`) shows no explicit test for unacknowledged data. That suggests, unlike Linux, that macOS keepalives may still drop a connection whose probe goes unanswered, but this is unverified. xnu also has a per-socket `TCP_RXT_CONNDROPTIME`, which stops retransmissions and drops the connection after the given number of seconds. libpq never sets it. In principle you could set it on libpq's socket from Python. Python doesn't expose the constant, so you would pass `0x80`, through a `socket.fromfd` duplicate, because `socket.socket(fileno=...)` doesn't duplicate the descriptor and would close it on collection. That is an untested inference. The portable guarantee on macOS is the application deadline described next.

### The liveness probe

psycopg 3.2 added `timeout` and `stop_after` to `notifies()`. A listener can therefore leave the generator periodically and check the connection:

```python
PROBE_INTERVAL = 30.0
PROBE_DEADLINE = 5.0

async def listen(conn):  # AsyncConnection, autocommit=True, LISTEN already issued
    while True:
        async for notify in conn.notifies(timeout=PROBE_INTERVAL):
            dispatch(notify)
        await asyncio.wait_for(conn.execute("SELECT 1"), PROBE_DEADLINE)
```

Choosing the values:

- **Interval.** Keepalives already bound pure TCP loss at about 25 s. The probe exists for failures TCP cannot see, and for macOS's missing user timeout. psycopg's docs warn that polling "will only detect a disconnection with an average delay of half the polling time" and generates useless traffic, so 30 to 60 s is reasonable. A failure that only the probe can see is then caught in about `PROBE_INTERVAL + PROBE_DEADLINE` in the worst case.
- **Deadline.** It must sit inside `tcp_user_timeout` so the probe fails on its own terms. When `asyncio.wait_for` cancels the probe, psycopg's async connection treats `asyncio.CancelledError` as an interruption. With a query active, it attempts a server-side cancel with a 5 s timeout, and closes the connection if that cancel times out. The effective deadline is therefore up to about `PROBE_DEADLINE + 5 s`. After a failed probe, discard the connection rather than reuse it.
- **Sync API.** The synchronous API has no client-side query deadline, and `statement_timeout` is server-side, so it cannot fire across a dead network. A sync listener depends on `tcp_user_timeout` on Linux and needs a watchdog on macOS. An asyncio listener is the simpler way to get a hard bound on both platforms.

When any of these mechanisms fires, the kernel error shows up as the socket becoming readable. A listener blocked in `notifies()` wakes, psycopg raises `OperationalError`, and `conn.broken` becomes `True`. This is the pattern psycopg's "Detecting disconnections" section relies on. The listener should then reconnect within `connect_timeout`, re-issue `LISTEN`, and run its catch-up read.

### Server-side mirror

The server needs bounds too. PostgreSQL's `tcp_keepalives_idle`, `tcp_keepalives_interval`, `tcp_keepalives_count` and `tcp_user_timeout` settings (the last is unsupported on Windows) let the server reap backends whose listener client has vanished.

`client_connection_check_interval` does not help here. It checks only "while running queries", and an idle `LISTEN` backend is not running one.

Reaping dead backends matters because a dead listener's backend can keep writing notifications into a socket nobody will read. Those notifications are lost to the client, which is why the catch-up read after reconnect is needed. If the socket's send buffer fills, the backend can also stall. The NOTIFY docs warn that a session that stops advancing blocks queue cleanup, and that `NOTIFY` fails at commit once the 8 GB queue is full.
