# What latency, WAL-retention and failover costs does a logical-decoding-based notifier add when it replaces writer-side NOTIFY for an append-only PostgreSQL event log?

## Question

When an event store stops calling `NOTIFY` in its append transactions and instead
runs a separate notifier that reads a logical replication slot, which costs does
it take on? The question covers three areas: the latency added between an append
committing and a consumer waking, the WAL and catalog retention a slot imposes,
and what happens to the slot and its wake-ups on crash and on failover to a
standby.

## Findings

### What the swap buys, and the shape of the replacement

Writer-side `NOTIFY` serialises commits. In `PreCommit_Notify`, PostgreSQL takes
`LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)` and
holds it "till after commit" so that "queue entries appear in commit order". Every
transaction that issues `NOTIFY` therefore commits one at a time. Recall.ai saw
hundreds of sessions waiting on `AccessExclusiveLock on object 0 of class 1262 of
database 0`. While `NOTIFY` was enabled, database CPU and I/O load "actually
plummeted", which is the signature of a global mutex.

A logical-decoding notifier takes that lock off the append path. The setup has
four parts:

- **The slot.** One logical replication slot, using `pgoutput`, `test_decoding`
  or `wal2json`, reads committed changes from the WAL.
- **What it decodes.** The notifier decodes either the inserted event rows,
  through a publication on the events table, or transactional
  `pg_logical_emit_message(true, prefix, content)` records that writers add to
  their append transaction. `pgoutput` delivers these when its `messages` option
  is on.
- **Order.** Decoded transactions arrive in commit order, each with its LSN.
- **Fan-out.** The notifier wakes consumers, for example with one `NOTIFY` from
  its own session or with an in-process push.

`NOTIFY` is still taken in that design, but only by the single notifier session,
so writers never queue on it. The rest of this note covers what the slot costs.

### Latency costs

1. **Decoding waits for flushed WAL.** On a primary, the logical walsender in
   `WalSndWaitForWal` waits "for the necessary WALs to be flushed to disk first,
   followed by waiting for standbys to catch up". It only decodes up to the flush
   pointer. With `synchronous_commit = on`, the writer has already flushed at
   commit, so this adds nothing. If writers commit with `synchronous_commit = off`
   to speed up appends, their WAL is flushed by the WAL writer. The documented
   maximum delay is "three times `wal_writer_delay`", and `wal_writer_delay`
   defaults to 200 ms. Combining these two documented behaviours (an inference,
   not a measured figure), an asynchronously committed append may not reach the
   notifier for up to about 600 ms by default.

2. **Changes are released only at commit, one transaction after another.** The
   output plugin callbacks "are only invoked when the transaction actually
   commits". For large transactions, "all the decoded changes have to be
   transmitted when the transaction finally commits … the transfer time may
   significantly increase the apply lag".
   - Spilling: decoded changes beyond `logical_decoding_work_mem` (default
     64 MB per replication connection) are written to local disk.
     `pg_stat_replication_slots.spill_txns`, `spill_count` and `spill_bytes`
     measure this.
   - Streaming: in-progress transactions can be streamed with `pgoutput` protocol
     version 2+ (PostgreSQL 14+), but changes "are still applied in commit order".
   - Head-of-line blocking: the slot is one commit-ordered stream, so a large
     transaction committing just before a small append holds back that append's
     wake-up.
   - Throughput: Supabase's documentation on its logical-replication-based
     Postgres Changes feature says the same thing in practice. Changes "are
     processed on a single thread to preserve their order, which means larger
     compute add-ons don't meaningfully increase … throughput."

3. **Failover-safe slots add a standby round trip to every wake-up.** On
   PostgreSQL 17+, failover slots should be paired with
   `synchronized_standby_slots` on the primary. Logical walsenders then "send
   decoded changes to plugins only after the specified replication slots confirm
   receiving WAL". The documentation states: "some latency is expected when
   sending changes to logical subscribers due to the waiting on slots named in
   `synchronized_standby_slots`". The SQL functions `pg_logical_slot_get_changes`,
   `pg_logical_slot_peek_changes` and `pg_replication_slot_advance` block in the
   same way when used on failover slots.

4. **The fan-out is an extra hop.** The notifier still has to wake consumers.
   If it does so with its own `NOTIFY`, every wake-up pays for one more commit
   plus normal `NOTIFY` delivery after decoding. That serialised cost now sits in
   one process rather than on every writer.

5. **Lag is hard to see by default.** `pg_stat_replication`'s `write_lag`,
   `flush_lag` and `replay_lag` work automatically only for physical
   replication. For logical decoding, "if [plugins] do not [emit tracking
   messages], the tracking mechanism will simply display NULL lag". A notifier
   that wants a latency service-level objective has to measure it itself, for
   example by comparing commit timestamps with wake-up times.

None of the primary sources found give end-to-end commit-to-wake-up
measurements. These are structural costs, not benchmarked ones.

### WAL and catalog retention costs

- **The slot pins WAL and catalog rows even when nothing is connected.** Slots
  "will prevent removal of required resources even when there is no connection
  using them". Neither the required WAL nor the system-catalog rows covered by the
  slot's `catalog_xmin` can be removed. "In extreme cases this could cause the
  database to shut down to prevent transaction ID wraparound." AWS warns that an
  unread slot means "data can be written and quickly fill up your DB instance's
  storage". Its Aurora guide adds that an inactive slot "prevents the vacuum from
  removing obsolete tuples".
- **Retention only moves when the client confirms.** `confirmed_flush_lsn`, and
  with it `restart_lsn`, advance only from the client's standby-status feedback.
  The psycopg2 documentation warns: "failure to constantly consume and report
  success to the server appropriately can eventually lead to 'disk full'".
  A notifier needs nothing from the WAL once it has sent a wake-up, so it can
  confirm straight away. `START_REPLICATION` resumes from whichever is later, the
  requested LSN or `confirmed_flush_lsn`.
- **Long-running transactions pin WAL even for a caught-up notifier.** The
  snapshot builder's comments explain that "every transaction remembers the last
  location we stored the snapshot to disk before its beginning. That point is
  where we can restart from." By inference, a write transaction left open on the
  append path holds `restart_lsn` back to roughly its own start, whatever the
  notifier's progress.
- **Retention can be capped, and for a notifier losing the slot is cheap.**
  - `max_slot_wal_keep_size` defaults to `-1`, which means unlimited. With a
    cap, a slot that falls too far behind moves to `wal_status = unreserved` and
    then `lost`, with `invalidation_reason = wal_removed`.
  - `idle_replication_slot_timeout` (PostgreSQL 18) invalidates slots that have
    been inactive too long. Invalidation happens at the next checkpoint, so it
    can lag the timeout.
  - For a change-data-capture pipeline, an invalidated slot means lost data. For
    a wake-up notifier over an authoritative events table, it means only lost
    wake-ups that a catch-up poll recovers. A tight cap is therefore a reasonable
    trade for this use.
- **`wal_level = logical` costs a restart but little extra WAL for
  insert-only tables.**
  - The setting "can only be set at server start".
  - The extra WAL is "particularly" large when tables use
    `REPLICA IDENTITY FULL` and see many `UPDATE` and `DELETE` statements. By
    inference, an insert-only log adds little.
  - On RDS and Aurora, logical decoding needs the static `rds.logical_replication`
    parameter and a reboot. AWS notes this "can increase WAL generation".
  - The development documentation for the release after 18 (18.6 is current)
    describes an `effective_wal_level` that rises to `logical` automatically when
    the first logical slot is created under `wal_level = replica`. PostgreSQL 18
    does not have this.
- **Each slot costs a walsender.** Each slot needs its own walsender, which reads
  the cluster's WAL stream and has its own `logical_decoding_work_mem` buffer.
  `max_replication_slots` and `max_wal_senders` both default to 10. The cost of
  slots per consumer or per process grows linearly, so the pattern is one slot
  per database, owned by one notifier.

### Crash and failover costs

- **After a crash, wake-ups repeat.** "The current position of each slot is
  persisted only at checkpoint", so after a crash the slot "might return to an
  earlier LSN" and resend changes. Clients must tolerate duplicates.
  `pg_replication_slot_advance` likewise writes positions only at the next
  checkpoint. Consumers that track their own positions already tolerate
  duplicate wake-ups.
- **Without failover slots (before PostgreSQL 17, or not configured), the slot
  disappears on promotion.** The notifier must create a new slot on the new
  primary. A new slot reaches a consistent snapshot only "once all those
  previously running transactions have committed or aborted", so creating it
  waits on any in-flight transactions. No wake-ups are produced for commits
  between the old slot's last confirmed position and the new slot's start. The
  notifier should therefore send an unconditional "resync" wake-up after it
  reconnects, and consumers must poll to catch up.
- **PostgreSQL 17 failover slots (released 2024-09-26) need a lot of
  configuration.**
  - Requirements: create the slot with `failover = true`, set
    `sync_replication_slots` on the standby, use a physical slot via
    `primary_slot_name`, turn on `hot_standby_feedback`, and put a valid `dbname`
    in `primary_conninfo`.
  - `hot_standby_feedback` "will delay cleanup of dead rows on the primary, which
    may result in undesirable table bloat".
  - Synchronisation is periodic and asynchronous. "Only persistent slots that
    have attained synced state as true on the standby before failover can be used
    … after failover". Readiness is `synced AND NOT temporary AND
    invalidation_reason IS NULL`.
  - Without `synchronized_standby_slots`, the notifier can get ahead of the
    standby, and the documentation requires "the standby server must be ahead of
    the subscriber". With it, every wake-up pays the standby round trip described
    above.
  - The notifier's liveness becomes tied to the standby's: "logical replication
    will not proceed if the slots specified in the `synchronized_standby_slots` do
    not exist or are invalidated".
  - The documentation also warns that an old primary which comes back during
    promotion may keep feeding consumers that are not redirected.
- **Patroni (PostgreSQL 11+) offers permanent logical slots instead.** The slots
  are "copied from the primary to a standby with restart, and after that their
  position advanced every loop_wait seconds". It warns that "some messages could
  be received the second time after the failover". The slots must be used only
  from the leader, because using them on replicas causes "indefinite growth of
  `pg_wal` on all other nodes".
- **Decoding on a standby (PostgreSQL 16+) moves the load but adds risk.** It
  takes decoding off the primary but adds replication lag. Slots on the standby
  are invalidated by conflicts, for example when required catalog rows are
  removed or the primary's `wal_level` drops below `logical`. Aurora PostgreSQL
  does not support logical decoding from read replicas.

### Client-library cost for a psycopg 3 library

psycopg 3 does not implement the streaming replication protocol. The maintainer's
issue "Add support for streaming replication as in psycopg2" has been open since
August 2021 with no linked work. psycopg2 does provide
`LogicalReplicationConnection` with `start_replication`, `consume_stream` and
`send_feedback`. A psycopg 3 event store would therefore need one of three
options:

- a separate notifier process built on psycopg2;
- an external tool such as `pg_recvlogical`;
- the SQL interface (`pg_logical_slot_get_changes`), which brings polling back,
  now against the slot, and blocks on failover slots until the standby confirms.

### Net assessment

For an append-only event log whose table is the source of truth, a
logical-decoding notifier does take commit serialisation off the append path. It
also delivers commit-ordered wake-ups tagged with LSNs. It is safe only when
treated as a disposable wake-up source:

- one slot per database;
- immediate confirmation after each wake-up;
- capped retention (`max_slot_wal_keep_size`, `idle_replication_slot_timeout`);
- a resync wake-up after any slot loss or failover;
- consumers that tolerate both duplicate and missing wake-ups through their
  existing position-based catch-up reads.

The costs it adds are:

- a restart to enable `wal_level = logical`;
- a replication connection and privilege;
- decoding latency behind flushes and large transactions;
- a standby round trip, if failover slots are used;
- configuration on PostgreSQL 17+ (or loss of the slot on failover before
  that);
- a Python client gap.
