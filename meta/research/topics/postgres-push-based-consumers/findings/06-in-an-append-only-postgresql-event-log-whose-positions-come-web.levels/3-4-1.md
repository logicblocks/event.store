# How can a PostgreSQL event store narrow its commit watermark to only those transactions that could still insert into the event table, instead of the cluster-wide snapshot xmin, without risking skipped events?

## Question

Event stores and outboxes that tag each row with `pg_current_xact_id()` usually read only rows whose `transaction_id < pg_snapshot_xmin(pg_current_snapshot())`. That watermark waits for every in-progress transaction in the cluster. How can it be narrowed to only the transactions that could still insert into the event table, without letting a consumer advance past an event that later commits?

## Findings

### Short answer

The scalar snapshot-xmin watermark is held back by every transaction in the cluster that has a transaction id (xid), whatever table or database it writes. There are three safe ways to narrow it, and one way to stop needing a scalar watermark at all:

1. **Filter by database.** Keep only the in-progress xids that belong to sessions or prepared transactions in the event store's own database. This is safe, needs nothing from writers, and removes delays caused by other databases only.
2. **Have appenders register a lower bound on their position.** Each appender advertises a lower bound before it calls `nextval`, and consumers read up to the lowest bound advertised. This narrows the wait to event-table writers only. The published version of this scheme has races, which can be fixed (see Option 2).
3. **Take a barrier lock on the event table.** This is exact and needs nothing from writers, but it blocks appends.
4. **Replace the scalar watermark with snapshot-pair batches, as PgQ does.** Unrelated or long-running transactions then delay nobody but themselves. The cost is that events are no longer delivered in position order.

The most obvious narrowing is unsafe: taking "in-progress transactions that hold a lock on the event table" and using their xids as the watermark. Xids are assigned at a transaction's first write to anything, so a transaction can hold an old xid before it touches the event table.

### Why the snapshot xmin covers the whole cluster

PostgreSQL assigns xids "sequentially to transactions from a global counter used by all databases within the PostgreSQL cluster. This assignment happens when a transaction first writes to the database" (transaction-id docs). `pg_current_snapshot()` returns the backend's active snapshot (`GetActiveSnapshot()` in `xid8funcs.c`). That snapshot is built in `GetSnapshotData` by a loop over every process in the proc array, with no `MyDatabaseId` test. The loop skips only:

- processes with no xid,
- the caller's own xid,
- xids at or above xmax,
- backends flagged as running logical decoding or lazy `VACUUM`.

By contrast, `ComputeXidHorizons` deliberately ignores "sessions in other databases" when it computes per-database vacuum horizons. Snapshot xmin is documented as the "lowest transaction ID that was still active". `pg_xact_status` reports prepared transactions as "in progress", and they stay in the snapshot until resolved.

In practice, any of the following holds the watermark back:

- a write transaction on another table,
- a write transaction in another database,
- an idle-in-transaction session that has written,
- an unresolved prepared transaction.

Read-only transactions do not, because they have no xid. A consumer that has itself written before computing the watermark also caps it at its own xid. The snapshot code keeps its own xid out of the in-progress list but counts it in xmin. This causes a stall, not a skip.

Practitioner sources confirm the cost:

- Sequin's write-up rejects the xmin approach because "if you have a transaction running against another table for two minutes, your cursor/query will be unable to read the last two minutes".
- Oskar Dudycz's outbox ordering article says only that queries "may be a bit delayed if our transactions last long".
- Watermill's PostgreSQL adapter uses the same `pg_snapshot_xmin(pg_current_snapshot())` filter, with primary key `(transaction_id, offset)`.

### The rule any safe narrowing must follow

A consumer may move past ordering key *k* only if it is still waiting on every transaction that could commit a row with a key at or below *k*. That requires two things:

- a transaction must become visible to the consumer's "still in flight" test **before** it obtains its ordering key, and
- keys must increase with the time they are obtained.

**Xids fail the first condition when the test is "touches the event table".** A transaction can write a business row, which assigns its xid X, and append its event much later. Suppose the consumer computes a watermark from `pg_locks` holders of `ROW EXCLUSIVE` on the event table (`INSERT` takes this lock). That transaction is not yet a holder, so the consumer moves past X. The transaction then inserts and commits an event tagged X, which is never read. `pg_current_xact_id_if_assigned()` lets an append path detect that an xid was already assigned, but it cannot undo that. An xid-keyed narrowing is only safe if every appender registers before its first write of any kind.

**Positions from a sequence can meet both conditions:**

- **Lock before allocation.** `setTargetTable` acquires the target's `RowExclusiveLock` during parse analysis. A default `nextval()` is evaluated later, during execution, and the lock is "held until the end of the transaction".
- **Sequential values.** These are guaranteed only with sequence `CACHE 1`. With a larger cache, "you should only assume that the nextval values are all distinct, not that they are generated purely sequentially". In that case `last_value` reflects "the latest value reserved by any session".
- **Allocation inside the insert.** Positions taken with a separate `nextval()` statement before the insert break the lock-before-allocation ordering.

Aborted appenders leave gaps because `nextval` is never rolled back. Bound-based schemes tolerate gaps, because they read up to a bound rather than demanding a contiguous run of positions.

### Option 1: filter the snapshot to the event store's own database

Each backend is "connected to" exactly one database (`pg_stat_activity.datid`). A transaction in another database therefore cannot insert into this database's event table. A loopback `dblink` or `postgres_fdw` write would run as a separate backend in this database and would be counted. The watermark can drop every in-progress xid that belongs to another database:

```sql
-- statement 1 (READ COMMITTED; this transaction has not written anything)
SELECT pg_current_snapshot() AS snap,
       array(SELECT backend_xid FROM pg_stat_activity
             WHERE datname = current_database() AND backend_xid IS NOT NULL) AS local_xids;
-- statement 2
SELECT coalesce(
  (SELECT x FROM pg_snapshot_xip($snap) AS x
    WHERE x::xid = ANY($local_xids)
       OR x::xid IN (SELECT transaction FROM pg_prepared_xacts
                     WHERE database = current_database())
    ORDER BY x LIMIT 1),
  pg_snapshot_xmax($snap)) AS watermark;
-- statement 3: read events WHERE transaction_id < watermark, ordered as before
```

This sketch is derived from documented behaviour. None of the sources consulted publishes it. Why it is safe:

- `pg_current_snapshot()` returns the statement's snapshot, taken before `pg_stat_activity` is read. Activity data "is collected when any such information is first requested within a transaction".
- Every running xid below xmax is in that snapshot's in-progress list.
- A same-database xid that is still running when the views are read lowers the watermark.
- A same-database xid that finished in between is visible to statement 3. Under Read Committed, each `SELECT` "sees a snapshot of the database as of the instant the query begins to run".
- Xids at or above xmax sit above the watermark anyway.
- The `xid8`-to-`xid` cast is documented. Comparing the low 32 bits is unambiguous for xids that are running at the same time.

Caveats:

- **Isolation level.** Run this under Read Committed. Under Repeatable Read, statement 3 reuses the old snapshot, so a transaction that ended between the snapshot and the view read would be both invisible and excluded, which is a skip.
- **Cached activity data.** `pg_stat_activity` is cached for the rest of the transaction. Use a fresh transaction for each poll, or call `pg_stat_clear_snapshot()`.
- **Prepared transactions.** They are not backends, so they must come from `pg_prepared_xacts`, which carries `database` and `transaction` columns. Read it after `pg_stat_activity`.
- **Permissions.** The docs say many columns are null in other users' rows. However, `pg_stat_get_activity` fills `backend_xid` in its "values available to all callers" section, so an ordinary role still sees it. Verify this on the target version.
- **Limited benefit.** Long or idle-in-transaction writers in the same database still hold the watermark back.

### Option 2: appenders register a lower bound on their position

Anthony Accomazzo's Sequin article (July 2024) describes this scheme:

- **Append side.** Each appending transaction takes a marker advisory lock `(sequence oid, 0)`. It also takes an advisory lock keyed by the sequence's current `last_value`, which is a lower bound on any position it will get. Both are taken before the insert.
- **Read side.** Readers compute the lowest key among sessions that hold both locks and read `seq <= bound`. With no registered appenders, the bound is `bigint` max.

This narrows the wait to exactly the registered appenders: unrelated transactions, including ones in the same database, never delay reads. Every writer must follow the protocol, so it belongs in the store's single append path.

Measured against the documentation, the published code has several races or limits. Each can be fixed:

1. **Exclusive try-locks drop registrations.** The code calls `perform pg_try_advisory_xact_lock(next_val)`, which returns `false` "without waiting" if the lock is taken, and `perform` discards the result. Here is how that skips an event:
   - Two appenders read the same `last_value` (10). T1 locks 10 and gets 11. T2 fails to lock silently and gets 12, unregistered.
   - T3 registers 12 and gets 13.
   - T1 commits; the reader reads up to 12, sees 11, and moves its cursor to 11.
   - T3 commits; the reader reads past 11, sees 13, and moves to 13.
   - T2 commits 12, which is never read.

   Fix: use `pg_advisory_xact_lock_shared` for the position key. A shared lock "does not conflict with other shared locks", so every appender registers.
2. **The bound is computed after the read's snapshot.** Both `seq <= max_safe_seq(...)` and the CTE form read `pg_locks` while the statement runs, but the statement's snapshot was taken when it began. An appender that is in flight at the snapshot and commits before `pg_locks` is read is neither visible nor counted, so rows above its position get read. Fix: compute the bound in an earlier statement and read rows in a later one.
3. **An empty registry means no bound.** Once fix 2 is applied, returning `bigint` max when nobody is registered lets an appender that registers between the two statements be overtaken. Fix: read the sequence `last_value` first, then scan `pg_locks`, and use `min(lowest registered key, last_value)` as the bound.
4. **Positions above 2^32 are misread.** The reader takes `min(objid)` with `classid = 0`. A `bigint` advisory key is displayed with "the high-order half in classid, low-order half in objid", so it should be rebuilt as `(classid::bigint << 32) | objid::bigint` and filtered on `objsubid = 1`.
5. **Prepared transactions are invisible.** The `l1.pid = l2.pid` join misses them, because `pid` "is null for locks held by prepared transactions".
6. **Sequence setup.**
   - The sequence must use `CACHE 1`.
   - `pg_sequences.last_value` is null before the first `nextval` or without privilege, and a lock on a null key registers nothing. Use `coalesce` or prime the sequence.
7. **Cost of reading `pg_locks`.** The view is "not a consistent snapshot", and reading it "can impact database performance if this view is accessed very frequently". Advisory locks also use slots in the shared lock table.

### Option 3: barrier lock on the event table

A consumer can take `LOCK TABLE events IN SHARE MODE` briefly. `SHARE` conflicts with `ROW EXCLUSIVE`, which `INSERT` takes at parse time and holds to commit. Once the lock is granted:

- every transaction that had inserted into the table has ended;
- any later insert, and so any later `nextval`, waits until the consumer's transaction ends.

So with `CACHE 1`, `max(position)` read under the lock is a gap-free bound. This narrows to exactly the event-table writers and needs nothing from them. The cost is heavy: each barrier waits for the slowest in-flight appender, and appenders stall while the consumer waits for and holds the lock. Bounding the wait with `lock_timeout` would at least cap it. The approach suits occasional fences, not every poll. No published store using it was found among the sources consulted.

### Option 4: snapshot-pair batches instead of a scalar watermark (PgQ)

PgQ works as follows:

- every event stores `ev_txid` (default `txid_current()`);
- a ticker inserts `pgq.tick` rows whose `tick_snapshot` defaults to `txid_current_snapshot()`;
- a batch is the set of events visible in the current tick's snapshot but not in the previous one.

`pgq.batch_event_sql` says the simple filter "has a problem with long transactions (xmin1 very low)". To avoid this it scans only the range from the previous to the current tick's xmax, and fetches xids that "were committed between snapshots" by exact `IN (...)` lookup.

As a result, a long-running transaction, or one in another database, only adds an xid to that list. It matches no events and delays nothing. A long-running appender's events arrive in a later batch. Nothing is skipped, because batch membership is decided by MVCC visibility. Events must record the top-level xid, which `pg_current_xact_id()` does: `pg_visible_in_snapshot` "will not give the correct answer for a subtransaction ID".

The cost is that a consumer's checkpoint becomes a tick (a snapshot) rather than a position. Delivery follows commit-visibility order, so a slow appender's low positions arrive after higher positions have already been delivered. Because all consumers share the same ticks, they all agree on that order. A ticker process is also required; PgQ tunes it with `queue_ticker_max_count`, `queue_ticker_max_lag` and `queue_ticker_idle_period`.

### Choosing among them

- **Consumers need strict position order.** Some waiting on in-flight appenders is unavoidable; the options differ only in how much unrelated work they also wait for:
  - Option 1 is the cheapest safe improvement when the cluster hosts other databases.
  - Option 2, with the fixes above, is the narrowest scheme that does not block.
  - Option 3 is exact, but it blocks.
- **Commit-visibility order is acceptable.** Option 4 removes the waiting on unrelated and long-running transactions altogether.

Two shortcuts should be avoided because they can skip events:

- mapping `pg_locks` holders on the event table to their xids;
- the tag-matching `pg_stat_activity` filter that Sequin itself calls brittle. It requires `state = 'active'`, which excludes `idle in transaction` appenders that have already inserted.
