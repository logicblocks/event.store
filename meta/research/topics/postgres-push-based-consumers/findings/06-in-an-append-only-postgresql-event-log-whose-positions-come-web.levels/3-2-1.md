# How do PostgreSQL event stores decouple wake-up signalling from append transactions, for example a debounced notifier that issues NOTIFY outside the append transaction, and what append throughput and consumer wake-up latency does that achieve?

## Question

How do PostgreSQL-backed event stores, and the PostgreSQL job queues that have the same wake-up problem, keep consumer wake-up signals out of the append transaction? One example is a debounced notifier that issues `NOTIFY` after the append commits. What append throughput and consumer wake-up latency do these designs achieve?

## Findings

### Why moving the signal out of the append transaction matters

PostgreSQL delivers a `NOTIFY` only if, and when, the issuing transaction commits. Notifications from different transactions arrive in commit order. Duplicate notifications (same channel, identical payload) are folded only within a single transaction, never across transactions. The documentation advises applications that use `NOTIFY` for real-time signalling to keep their transactions short.

The commit-order guarantee comes from `PreCommit_Notify` in `async.c`:

- If the transaction has pending notifications, the function forces a transaction id to be assigned.
- It then takes a heavyweight `AccessExclusiveLock` on "database 0", described as "a special lock that we hold till after commit". The lock exists so that "queue entries appear in commit order".
- The same function returns at once (`if (!pendingActions && !pendingNotifies) return;`) when the transaction has no pending notifications or LISTEN actions.

So only transactions that actually carry a `NOTIFY` pay for the lock.

Recall.ai reported what this costs at scale. Tens of thousands of concurrent writers issued `NOTIFY` in their write transactions. Their logs showed waits on `AccessExclusiveLock on object 0 of class 1262 of database 0`. One process got the lock after 1015.921 ms, with more than 300 processes queued behind it. Throughput collapsed while database CPU and I/O fell. Without `NOTIFY` the database used its full CPU and recovered quickly from load spikes. They moved the signalling into the application layer. Their July 2025 post credits a later core commit (Joel Jacobson and others) with removing the bottleneck. That patch is a separate subject.

The main lever, then, is how many committing transactions carry a `NOTIFY`, not how many notifications are sent. An append transaction that issues no `NOTIFY` never touches the lock.

### Pattern 1: NOTIFY inside every append (no decoupling)

Several PostgreSQL event stores still signal from inside the append transaction:

- **Commanded EventStore (Elixir).** An `AFTER INSERT OR UPDATE ON streams FOR EACH ROW` trigger calls `pg_notify` with the payload `stream_uuid,stream_id,first_version,last_version`. Payloads differ, so nothing is folded and every appending transaction takes the commit lock. A GenStage listener queues the notifications and never drops them.
- **Disintegrate (Rust).** An `AFTER INSERT ON event FOR EACH ROW` trigger calls `pg_notify('new_events', NEW.event_type)`. Its listener wakes either on a notification or on a poll tick (`tokio::select!`).
- **Procrastinate (Python).** A per-row trigger publishes a JSON payload containing the job id on two channels, one per queue and one for any queue. Because the payloads differ, they are never folded.
- **Python `eventsourcing` 9.5 (psycopg 3).** It runs a payload-less `NOTIFY <channel>` in the same transaction that inserts the events. It also runs `LOCK TABLE ... IN EXCLUSIVE MODE` to serialise inserts "so that readers don't pass over gaps that are filled in later".
  - Its `PostgresSubscription` runs a dedicated listener thread that waits for notifications in 0.1 s slices and sets a `threading.Event`.
  - A puller thread then reads up to 500 rows after the last position it saw. Bursts of notifications therefore collapse into one read on the consumer side.

Inference: in `eventsourcing`, appends are already serialised by the table lock, so the `NOTIFY` lock adds little extra serialisation. In stores that allow concurrent appends (Commanded, Disintegrate), the `NOTIFY` lock becomes the point where commits serialise.

### Pattern 2: NOTIFY stays in the transaction but is rate-limited

**River (Go job queue).** Release 0.5.0 (May 2024) removed River's insert trigger.

- The changelog says the trigger emitted "a large amount of notifications any time there are lots of jobs being inserted", which added overhead in high-throughput installations.
- A client-level debouncer now ensures notifications "are not emitted more often than they could be useful". When a queue is due for a notification, it "is piggy-backed onto the insert query within the transaction".
- The limiter is a per-topic gate that lets the first insert in a window through. `ShouldTrigger` returns true only when that topic's last send is older than `waitDuration`.
- The client builds the limiter with `FetchCooldown`, which defaults to 100 ms. `FetchPollInterval` (default 1 s) is "a fallback".

**pgmq.** `enable_notify_insert(queue, throttle_interval_ms DEFAULT 250)` installs a `DEFERRABLE` constraint trigger that fires `FOR EACH ROW`. The trigger updates a row in an `UNLOGGED` table, `notify_insert_throttle`, and calls `PG_NOTIFY` only if the interval has passed.

Effect: only the transaction that passes the gate takes the commit lock. Lock acquisitions are capped per queue per window: about 10 per second per River client and about 4 per second per pgmq queue at the defaults, whatever the insert rate.

Inferred caveats (neither project documents these):

- A transaction that the gate suppresses gets no notification of its own. If it commits after the notifying transaction and after the consumer has already read, its rows wait for the next signal or the poll fallback (1 s in River's defaults).
- River's limiter lives in each client process, so the cap applies per process, not globally.
- pgmq's gate is itself a write to one shared row inside every inserting transaction.

### Pattern 3: signal after commit, outside the append transaction

**River, in-process path.** For drivers without LISTEN support, River wakes local producers directly, but only after a non-transactional `Insert` or `InsertMany` has committed. The code comment says this "Should only ever be invoked *outside* a transaction. If invoked within a transaction, the producer wouldn't yet be able to access the new jobs that triggered the notification because they're not committed yet." That is the correctness rule for any signal sent outside the transaction: send it after the commit returns, never before.

**Oban (Elixir job queue).**

- Oban's first migration created a per-row `oban_notify` trigger. Migration V12 drops it.
- Current Oban sends the insert signal from the application after the insert returns. It removes duplicate queue names (`uniq: true`) but does not debounce.
- The Postgres notifier issues `pg_notify` through the application's own database connection pool (Ecto's `Repo`). A signal sent inside a caller's transaction is therefore delivered only after that transaction finishes.
- Alternative notifiers (Distributed Erlang `PG`, Phoenix PubSub) bypass PostgreSQL `NOTIFY` entirely.
- Oban's Stager is a periodic notifier fully separate from inserts. Only the leader node runs it, every 1 s with a limit of 5,000 jobs. It promotes jobs that are now due, asks which queues have available jobs, and publishes one batched `insert` notification. When the notifier is unhealthy it falls back to messaging local producers directly.

**Akka Persistence R2DBC (JVM event journal).**

- It publishes written events over Akka cluster pub-sub to running `eventsBySlices` queries, so they do not wait for the next database poll.
- It keeps polling, less often, because "delivery of published messages are not guaranteed". The defaults are a 3 s `refresh-interval`, a 100 ms `behind-current-time`, and backtracking over a 2-minute window that stays 10 s behind.
- `publish-events-dynamic` turns publishing off automatically when an exponentially weighted moving average of throughput exceeds 400, measured over a 10 s interval.
- The design admits that at high append rates polling returns full batches anyway, so push mostly helps at low rates.

**Recall.ai.** As described above, they moved signalling into the application layer.

### Pattern 4: coalescing on the consumer side

- **Graphile Worker:** `refetchDelay` waits `durationMs` on average after a fetch that returned no more than `threshold` jobs. `maxAbortThreshold` sets how many new-job notifications a pool in that delay absorbs before it fetches anyway. The thresholds are staggered across workers to avoid a thundering herd while still keeping latency low.
- **River:** `FetchCooldown` means jobs "will only be fetched *at most* this often".
- **Brandur's "notifier" pattern (from River's co-author):** one LISTEN connection per process fans out to subscribers through buffered channels using non-blocking sends. A notification is discarded when a subscriber's channel is full, which is tolerable because the signal only means "go and read".

### Throughput and latency evidence

No published benchmark was found that compares an event store using a debounced, post-commit notifier directly with in-transaction `NOTIFY`. The available figures are below.

| Source | What was measured | Result |
|---|---|---|
| River | Job processing throughput (pre-inserted jobs worked to completion, not append cost); 8-core M2 MacBook Air, 2,000 worker goroutines; debounced in-transaction design | About 46,000 jobs/s |
| Graphile Worker | Creation-to-start latency | 4.28 ms average (3.24–18.18 ms) batched; 4.47 ms (3.40–14.13 ms) unbatched |
| Graphile Worker | Throughput (i9-14900K, local database, 4 processes × 24 concurrency, 200,000 trivial jobs) | 15,600 jobs/s unbatched; about 183,000 executed and 202,000 queued per second batched |
| Recall.ai | Commit lock wait with `NOTIFY` in write transactions | 1015.921 ms, with more than 300 waiters |

Graphile Worker's page does not attribute its latency to `NOTIFY`. Its `pollInterval` defaults to 2,000 ms and is documented for future-scheduled jobs and retries, so the roughly 4 ms latency must come from a push wake-up, not polling (inference).

Default windows in these systems:

- River: 100 ms debounce, 1 s poll
- pgmq: 250 ms throttle
- Oban Stager: 1 s
- Akka: 3 s poll, publishing switched off above a throughput of 400
- `eventsourcing`: 0.1 s listener wait slices

What a decoupled notifier achieves, inferred from `PreCommit_Notify` and the systems above:

- **Append throughput.** Appends carry no `NOTIFY`, so they skip the lock entirely. The notifier's own small transactions (each still assigned a transaction id) take the lock at most once per window per notifying process. Lock traffic then depends on the window length and the number of processes, not on the append rate. Appends still serialise on whatever ordering mechanism the store uses; decoupling removes only the `NOTIFY` lock from the append path.
- **Wake-up latency, by gate type:**
  - A gate that fires on the first append of a quiet window (River-style) adds almost no latency for that append. Later appends in the same window depend on a later signal or the poll.
  - A gate that fires once at the end of the window, after the last seen append has committed, caps the added latency at the window length plus one small autocommit transaction and delivery.
  - Firing at both the start and the end of the window gives a fast first wake-up and still covers the last commit.
- **Commit visibility.** Because the signal is sent after commit, a consumer that receives it and starts a new snapshot sees those rows. It still needs its own watermark logic for concurrent commits that finish out of position order.
- **Signal loss.** A signal sent outside the transaction can be lost if the process dies between commit and notify, or if the listening connection drops. Every system above that signals outside the transaction keeps a poll running for this reason: River 1 s, Akka 3 s plus backtracking, Oban's Stager 1 s.

### Fit with psycopg 3

Psycopg recommends keeping a connection in autocommit mode to send or receive notifications in a timely way. It offers a `notifies()` generator with `timeout` and `stop_after` parameters, and says a normal blocking `Connection` is enough. A post-commit notifier therefore fits naturally (inference):

- a dedicated autocommit connection that runs `pg_notify` once the append's commit has returned, debounced in the process;
- on the consumer side, one LISTEN connection per process that turns all signals into "read after my checkpoint", with a poll as the fallback.
