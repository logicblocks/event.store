# How do PgQ-style snapshot-difference reads and xmin-horizon reads compare in query cost and index design on a large PostgreSQL events table, especially while long-running write transactions are open?

## Question

On a large, append-only PostgreSQL events table, how do two gap-safe read strategies compare? The first is PgQ's: read the events whose writing transaction became visible between two stored snapshots. The second reads only events whose transaction id is below the current snapshot's `xmin`. The comparison covers per-read query cost, the indexes and checkpoint each needs, and how each behaves while long-running write transactions are open.

## Findings

### Bottom line

Neither strategy is expensive per read if it is indexed correctly. Each does a bounded B-tree range scan whose cost grows with the batch size, not the table size. They differ in what a long-running write transaction costs:

- **xmin-horizon reads** stay cheap but **stop delivering**. No consumer gets past the oldest open transaction that holds a transaction id, anywhere in the cluster, until it ends.
- **PgQ-style snapshot-difference reads** **keep delivering** at the same cost. The price is a heavier checkpoint (a whole snapshot, not two numbers) and a delivery order that is not monotonic in transaction id or position.

PgQ's naive form would rescan everything written since the oldest open transaction on every batch. PgQ avoids this with a specific query shape, and any event-store adaptation needs to copy that shape.

### The two read models

**xmin-horizon.** Each event row stores the writer's 64-bit transaction id, using `pg_current_xact_id()` (type `xid8`). A consumer's checkpoint is the pair (last transaction id, last position). It reads `WHERE (transaction_id, id) > (:lastTxid, :lastId) AND transaction_id < pg_snapshot_xmin(pg_current_snapshot()) ORDER BY transaction_id, id`. One example is the reference event-sourcing implementation by eugene-khyst, which keeps `LAST_TRANSACTION_ID xid8` and `LAST_EVENT_ID bigint` per subscription.

This is safe because PostgreSQL defines a snapshot's `xmin` as the "lowest transaction ID that was still active". Every id below it is "either committed and visible, or rolled back and dead", so no row below the bound can appear later. Oskar Dudycz describes the same outbox design with a `LIMIT 100` page. Sequin describes it too, with the column defaulting to `pg_current_xact_id()`.

**PgQ snapshot difference.** A ticker inserts rows into `pgq.tick`, and each row's `tick_snapshot` defaults to `txid_current_snapshot()`. It ticks when a batch reaches `queue_ticker_max_count` (default 500 events) or `queue_ticker_max_lag` (default 3 seconds) has passed, and otherwise every `queue_ticker_idle_period` (default 1 minute). A batch is the pair (last tick, next tick).

`pgq.batch_event_sql` turns two snapshots into a query that returns exactly the events whose transaction is visible in the newer snapshot (sn2) but not in the older one (sn1). Each transaction therefore appears in exactly one batch: the one where it first becomes visible. Within a batch, events are ordered by `ev_id` (`order by 1`).

### Query cost on a large table

**xmin-horizon.** With a composite B-tree on (transaction id, position), the read is a single index range scan. It starts at the checkpoint tuple, stops at the `xmin` bound, and returns at most the `LIMIT`, so cost is roughly O(log N + batch). It needs no per-row function calls.

The row-value form `(a, b) > (x, y)` matters. Use The Index, Luke reports that PostgreSQL (since 8.4) supports row-value predicates and uses them for index access, keeping keyset paging flat however deep the scan goes. Dudycz's equivalent `(t = x AND p > y) OR t > x` expresses the same condition, but the row-value form is the one documented as a single index access predicate.

The eugene-khyst query also joins to an aggregate table and filters by aggregate type, with only `(TRANSACTION_ID, ID)` indexed. A subscription to one category therefore walks every event in the transaction-id range and discards non-matching rows. If consumers subscribe by category or stream, an index that leads with that column and then has (transaction id, position) keeps each subscription a single range scan. This last point is an inference from standard B-tree behaviour, not a sourced benchmark.

**PgQ.** The source's own comment states the naive filter, `ev_txid >= xmin1 AND ev_txid <= xmax2` plus the two visibility checks, and adds that "the simple solution has a problem with long transactions". The problem is that a range anchored at `xmin1` stays pinned at the oldest open transaction, so every batch would rescan every event written since it began.

PgQ's fix has two parts:

1. **Main range.** It uses `[xmax1 .. xmax2]` for the range scan. `tx_start` is `txid_snapshot_xmax(last.tick_snapshot)` and `tx_end` is `txid_snapshot_xmax(cur.tick_snapshot)`. Rows in the range are then filtered by `txid_visible_in_snapshot(ev_txid, cur)` and `NOT txid_visible_in_snapshot(ev_txid, last)`.
2. **Older transactions.** It collects the transactions that were in sn1's in-progress list and are no longer in sn2's. It walks them in descending order. Any id within 100 of the current range start lowers `tx_start` to include it, to "avoid big IN expression". The rest go into a second `UNION ALL` branch, `WHERE ev_txid IN (...)`.

So each batch costs one range scan over the transaction ids assigned between the two snapshots, a handful of index point lookups, and a sort of the batch by `ev_id`. The visibility checks are cheap. PostgreSQL's `is_visible_fxid` returns immediately for ids below `xmin` or at or above `xmax`. Inside that window it scans the in-progress list linearly, switching to binary search when the list has more than 30 entries.

The cost of this design is batch granularity. A batch is everything between two snapshots, so it cannot be cut with a `LIMIT` the way a keyset page can. A single large transaction arrives in full in whichever batch it first becomes visible. That follows from the query shape; it is not a documented PgQ limit.

### Index and checkpoint design

| Aspect | xmin-horizon | PgQ snapshot difference |
|---|---|---|
| Event-row column | `transaction_id xid8 NOT NULL` (default `pg_current_xact_id()`) | `ev_txid bigint` default `txid_current()` (deprecated predecessor of `xid8`) |
| Index | composite B-tree `(transaction_id, position)`, as in eugene-khyst's `IDX_ES_EVENT_TRANSACTION_ID_ID` | single-column B-tree on `ev_txid` per data table |
| Consumer checkpoint | two scalars | a tick id that references a stored snapshot (`xmin:xmax:xip_list`) |
| Extra machinery | none | ticker process and `pgq.tick` table (or consumers storing their own previous snapshot) |
| Table-size control | none (the log is permanent) | three data tables (`queue_ntables` default 3) rotated every `queue_rotation_period` (default 2 hours) and emptied with `TRUNCATE` |

Use `xid8`, not `xid`, for the stored id. In both PostgreSQL 13 and current master, `xid8` has a B-tree and a hash operator class, while `xid` has only a hash class. `xid8` was added in PostgreSQL 13, with `xid8` versions of all the snapshot functions; the `txid_*` functions are kept only for backward compatibility. `xid8` values "increase strictly monotonically and cannot be reused in the lifetime of a database cluster".

PgQ keeps its tables small by rotating and truncating them. An event store cannot do that because its log is permanent. So the transaction-id index of an event store adapting PgQ covers the whole log. The query still touches only the batch's range.

If an adaptation wants paging inside a batch, or wants to avoid the per-batch sort, a composite `(transaction_id, position)` index serves both strategies. That is an inference.

A snapshot checkpoint is bounded in size. PostgreSQL notes that procarray limits (MAX_BACKENDS processes plus as many prepared transactions) "guarantee nxip won't be too large". Still, it is variable-length text rather than two fixed columns.

### What a long-running write transaction does

**Which transactions count.** Only transactions holding a real transaction id appear in snapshots. A transaction gets one "when [it] first writes to the database", from "a global counter used by all databases within the PostgreSQL cluster". Read-only transactions have only virtual ids, so they hold back neither strategy.

`GetSnapshotData` adds every running top-level id to the snapshot without filtering by database. It skips only backends flagged as lazy VACUUM or logical decoding. So a write transaction left open in another database on the same cluster also lowers `xmin`. That is wider than the eugene-khyst README's "in the same database".

Sequin saw this in practice: long transactions on unrelated tables stopped cursor progress "for two minutes or more", which led them to reject the approach.

**xmin-horizon under a long transaction.** `pg_snapshot_xmin` returns the long transaction's id. Events from all later transactions are read only after it commits, which the eugene-khyst README describes as effectively pausing all event handlers.

Query cost stays low, since each poll's range scan ends at the frozen bound and returns nothing. But latency equals the age of the oldest open writer. When that writer finishes, the bound jumps, and keyset paging drains the backlog in `LIMIT`-sized pages.

The horizon follows first-write order, not commit order. The docs warn that "the order in which transactions perform their first database write might be different from the order in which the transactions started". So a transaction that read for a long time before its first write is less harmful than one that wrote early and then waited.

Two server settings bound the stall:

- `transaction_timeout` (new in PostgreSQL 17) terminates sessions whose transaction exceeds a limit. Prepared transactions are not subject to it.
- `idle_in_transaction_session_timeout` covers sessions sitting idle inside an open transaction.

Two-phase transactions remain a horizon risk that these settings do not cover. That is an inference from the procarray and timeout documentation.

**PgQ under a long transaction.** The long transaction's id stays in each tick's in-progress list, so its rows are never visible to the filter until it commits. Because the main range starts at `xmax1`, its low-numbered rows are never rescanned. Delivery of other events continues every tick.

When the long transaction commits, it leaves the next snapshot's in-progress list. It then either joins the range (if within 100 of the range start) or is fetched by index point lookups through the `IN` list.

Long transactions still affect PgQ's maintenance. Rotation is skipped while the slowest consumer's tick `xmin` is at or below `queue_switch_step2`, so tables grow while old transactions linger.

The cost of continuing to deliver is ordering. The long transaction's events have lower transaction ids and `ev_id`s than events already delivered. Delivery order is the order in which transactions became visible, and the table alone cannot reproduce it: only the retained snapshot sequence can.

### Implications for an event store

- **For a single, resumable, reproducible global order:** xmin-horizon reads with a `(transaction_id, position)` B-tree and row-value keyset paging are simpler and cheap at any table size. Operationally they need cluster-wide limits on how long write transactions may run.
- **For delivery that never stalls behind a long writer:** snapshot difference is the proven design, provided the range is anchored at the previous snapshot's `xmax`, older transactions are fetched through a separate id list as `pgq.batch_event_sql` does, and the event store accepts a snapshot-shaped checkpoint and visibility-order delivery.
- **In either case:** transactions that only read or that run on a standby add no horizon risk on the primary's write path. Reads should run in READ COMMITTED autocommit statements. `pg_current_snapshot()` returns the backend's active snapshot, so successive reads inside one REPEATABLE READ transaction would keep reusing a frozen bound. That last point is an inference from the function's implementation.
