# Does PostgreSQL's idle_session_timeout terminate a LISTEN-only session that is actively receiving notifications, given that the server treats a session waiting for a client query as idle?

## Question

If `idle_session_timeout` is enabled, will PostgreSQL disconnect a listener session that has issued `LISTEN` and then only waits for notifications, even while the server is regularly sending it `NotificationResponse` messages? Or does delivering notifications count as activity that resets the timer?

## Findings

**Yes.** Delivering notifications does not reset the timer. A session that sends no client messages after its `LISTEN` is terminated `idle_session_timeout` milliseconds after its last `ReadyForQuery`, however many notifications it receives in the meantime. The timer measures time since the client's last command. Server-to-client traffic does not count as activity.

**What the setting is.** `idle_session_timeout` was added in PostgreSQL 14 (commit 9877374, January 2021, by Li Japin with fixes by Tom Lane). The PostgreSQL 18 documentation says it will "terminate any session that has been idle (that is, waiting for a client query), but not within an open transaction, for longer than the specified amount of time":

- **Units:** a value without units is in milliseconds.
- **Default:** 0, which disables the timeout.
- **Pooler warning:** the docs say to "be wary of enforcing this timeout on connections made through connection-pooling software or other middleware". They suggest enabling it only for interactive sessions, for example per user.
- **Error code:** the termination is SQLSTATE `57P05` (`idle_session_timeout`, Class 57 — Operator Intervention) in both the PostgreSQL 14 and current error-code tables.

**Why notifications don't reset it.** The commit's changes to `postgres.c` show the whole lifecycle of the timer:

- **Starting the timer.** `PostgresMain` starts it in the not-in-transaction branch, when the backend reports itself idle (`set_ps_display("idle")`, `pgstat_report_activity(STATE_IDLE, NULL)`) as part of sending `ReadyForQuery`. It calls `enable_timeout_after(IDLE_SESSION_TIMEOUT, IdleSessionTimeout)` there.
- **Stopping the timer.** The only `disable_timeout(IDLE_SESSION_TIMEOUT, false)` call is in the main loop's step "(5) turn off the idle-in-transaction and idle-session timeouts". That step runs after the backend has read the next client message.
- **When it fires.** `ProcessInterrupts` raises `FATAL` with "terminating connection due to idle-session timeout".

Notifications reach an idle listener without leaving that wait:

- The `async.c` header says that on `PROCSIG_NOTIFY_INTERRUPT` the signal handler sets the latch, "which triggers the event to be processed immediately if this backend is idle (i.e., it is waiting for a frontend command and is not within a transaction block)".
- While the backend waits for a client command (`DoingCommandRead`), `ProcessClientReadInterrupt` calls `CHECK_FOR_INTERRUPTS()` and then `ProcessNotifyInterrupt(true)`.
- That leads to `ProcessIncomingNotify`. It opens a short internal transaction to read the notification queue, flushes the messages to the client with `pq_flush()`, and sets the process title back to "idle". It calls no timeout function at all.
- Control then goes back to the same pending client read. The backend never returns to the top of the main loop, never reaches step (5), and never sends a new `ReadyForQuery`, so the timer that started after the client's last command keeps running.
- `pg_stat_activity` keeps showing such a listener as `idle`.

**Ordering at expiry.** `ProcessClientReadInterrupt` runs `CHECK_FOR_INTERRUPTS()` before it processes pending notifications. So if the timeout has expired and a notification is also pending, the backend terminates before delivering it. All of the session's `LISTEN` registrations disappear with the backend. Notifications committed between the termination and a fresh `LISTEN` on a new connection are never delivered to this listener. That is why a consumer needs a catch-up read on reconnect rather than trusting the notification stream alone.

**What a psycopg 3 listener sees.**

- **The server's side.** The protocol documentation says that when the server disconnects on its own it "will attempt to send an error or notice message giving the reason" before closing.
- **libpq's handling.** libpq's `pqParseInput3` handles an `ErrorResponse` that arrives while the connection is idle "using the notice processor". Its comment explains: "an ERROR is very possibly the backend telling us why it is about to close the connection". So the `57P05` message reaches libpq's notice path (and any psycopg notice handler), not a query result.
- **The exception.** psycopg's `notifies()` generator waits for the socket to become readable and then calls `pgconn.consume_input()`. When `PQconsumeInput` fails, that raises `OperationalError("consuming input failed: …")` built from libpq's connection error text. From the code, the exception the listener catches is a generic connection failure. The listener should not expect `57P05` to be attached to it.

**Ways to avoid it.**

1. **Turn the timeout off for the listener.** postgresqlco.nf lists the parameter's context as `user`. For `user`-context settings, the `pg_settings` documentation says "any user is allowed to change their session-local value" with `SET`. So a dedicated listener connection can run `SET idle_session_timeout = 0` once connected, which overrides any server, database or role default. This matches the docs' advice to apply the timeout only to particular users.
2. **Send a periodic heartbeat query.** Any client message moves the backend through step (5), which stops the timer, and the next `ReadyForQuery` starts a fresh one. So a trivial query such as `SELECT 1`, sent more often than the timeout, keeps the session alive. It also doubles as the liveness check that psycopg's documentation recommends for spotting a broken connection.
   - psycopg 3.2 added `timeout` and `stop_after` to `Connection.notifies()`, so a listener can loop: wait in `notifies(timeout=…)`, run the heartbeat, then wait again.
   - psycopg 3.2.4 fixed losing notifications that arrive while the `notifies()` iterator is not running, so this loop does not drop them. That relies on not also registering `add_notify_handler()` on the same connection: psycopg 3.2.10 deprecated combining the two, because handler-received notifications are then not yielded by the generator.
3. **TCP keepalives do not help.** They act below the protocol, and the docs define idle as "waiting for a client query". Keepalives keep NAT and firewall state alive but do not reset this timer.

Since the default is 0, this only affects deployments where an operator, a role or database setting, or a managed-service parameter group has turned the timeout on. A listener that disables it for its own session, or sends heartbeats faster than the timeout, is safe either way.
