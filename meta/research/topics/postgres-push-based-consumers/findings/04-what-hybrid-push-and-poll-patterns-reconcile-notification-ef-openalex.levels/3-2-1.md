# How far can a PostgreSQL snapshot's xmin be held back by long-running or idle-in-transaction sessions unrelated to event appends, and how should an xmin-gated consumer detect, bound and report that stall?

## Question

An xmin-gated consumer reads only events whose appending transaction ID is
below the current snapshot's xmin. This guarantees that no event with a lower
position can still commit later. The cost is that any open transaction can hold
the gate back, including one that has nothing to do with the event log. How far
back can it be held? How should the consumer notice the stall, put a limit on
it, and make it visible to operators?

## Findings

### The gate is a single global low watermark

A PostgreSQL snapshot has three parts: an xmin, an xmax, and the list of
transaction IDs still in progress between them. Every transaction ID below
xmin has finished, either committed or aborted (Ports and Grittner describe
PostgreSQL's SSI implementation in these snapshot terms). If the consumer gates
on xmin alone, its delivery frontier is set by the single oldest in-progress
transaction in the cluster.

The scholarly work on MVCC garbage collection describes the same structure
from the opposite side. A version can be reclaimed only once no active
snapshot can see it, so reclamation is limited by the oldest participant.
Several papers show that one long-lived transaction holds that limit back for
everyone:

- Wu et al. treat garbage collection as one of the main design dimensions of
  MVCC engines.
- Lee et al. built a hybrid collector for SAP HANA. Its group, table and
  interval collectors exist so that long-lived snapshots do not block all
  reclamation.
- Böttcher et al. find that in HTAP workloads with long-running queries, the
  usual garbage collectors are "too coarse-grained". Their remedy is to track
  the full set of active snapshots, not just the oldest one.
- Kim et al. report that, as of 2020, the latest MySQL and PostgreSQL releases
  are still vulnerable to long-lived transactions.

For a consumer, the lesson is the same as for these collectors. A gate that
takes the minimum over every transaction is safe but coarse, and the slowest
unrelated session sets its pace.

The streaming literature calls this a low watermark. MillWheel computes a
computation's low watermark as the minimum over its inputs' oldest pending
work, so one stuck input holds back every timer downstream. Akidau et al.
define watermarks formally as a claim about how complete a stream is. They
show the trade-off between waiting for completeness and advancing on
heuristics, where advancing early means data can arrive late.

### Which sessions hold the gate, and for how long

The rest of this subsection describes PostgreSQL's own mechanics. These come
from its documented behaviour, not from the scholarly records above.

There are two separate horizons, and they behave differently:

- **The vacuum horizon** (`backend_xmin` in `pg_stat_activity`). It is held
  back by any open snapshot, including read-only ones such as a long `pg_dump`
  or an analytics query. It is also held back by replication slots and by
  `hot_standby_feedback`. Holding it back causes table bloat, which is the
  problem the garbage-collection papers address. It does not move the
  consumer's gate.
- **The snapshot xmin that gates the consumer.** It is the oldest *assigned*
  transaction ID still running. PostgreSQL assigns a transaction ID only on a
  transaction's first write, which includes row locks such as
  `SELECT … FOR UPDATE`. So a session holds the gate only if it has written
  something and has not yet committed or aborted. Common examples:
  - a web request that wrote a row and then went idle in transaction while it
    waited on an external call;
  - a migration or batch job running inside one long transaction;
  - a client library whose connection is not in autocommit mode and which
    wrote without committing;
  - a prepared (two-phase) transaction, which survives server restarts until
    someone runs `COMMIT PREPARED` or `ROLLBACK PREPARED`.

Transaction IDs and the running-transaction list are shared across the whole
cluster. A session in a different database on the same server therefore holds
the gate just as well as one in the event store's own database.

How far back the gate can be held:

- **In time, there is no limit by default.** The gate stays where it is for as
  long as the blocking transaction stays open. `statement_timeout`,
  `idle_in_transaction_session_timeout` and `transaction_timeout` (PostgreSQL
  17 and later) are all disabled by default.
- **In events, every event appended since the blocker's first write is held
  back**, whether or not those events have committed. This is because each
  later appender was assigned a higher transaction ID.
- **The only hard limit is transaction-ID wraparound.** Vacuum cannot freeze
  past the oldest running transaction ID. After roughly two billion further
  transaction IDs, PostgreSQL refuses to assign new ones, so the whole cluster
  stops accepting writes. At 1,000 writing transactions per second that point
  is about 25 days away; at 10,000 per second it is under three days. By then
  the consumer stall is the smaller problem.

One detail matters for consumers. A backend's own assigned transaction ID
counts towards its own snapshot's xmin. A consumer that writes its checkpoint
and then reads the gate in the same transaction holds back its own gate. It
should read the gate in a transaction that has not yet written.

### Detecting the stall

On its own, an empty read is ambiguous. It can mean "caught up" or "gated".
The consumer should tell these apart explicitly, with three signals:

1. **Withheld events.** Run a cheap existence check on the position index:
   are there visible, committed events beyond the consumer's frontier whose
   transaction ID is at or above the gate? If so, the consumer is stalled, not
   idle. The comparison with the watermark literature fits here. Report the
   gap between what has committed and what may be delivered, separately from
   ordinary processing lag.
2. **Gate age.** Measure the wall-clock time since the gate last moved past
   the consumer's frontier while withheld events existed. Optionally also
   measure the transaction-ID age of the gate value, using `age()` on the
   blocking session's ID, so the stall can be compared with the wraparound
   limit.
3. **Blocker identity.** Match the gate value against `backend_xid` in
   `pg_stat_activity` to get the blocker's pid, state (`idle in transaction`
   or `active`), `xact_start`, `state_change` and `application_name`. Match it
   against `transaction` in `pg_prepared_xacts` to get the gid and prepare
   time. To see other roles' sessions in full, the consumer's role needs
   monitoring privileges such as `pg_read_all_stats`.

For push-based delivery, the key point is that **releasing the gate is never
signalled**. The append notifications arrive on time, but the consumer finds
nothing deliverable. When the unrelated blocker finally finishes, it sends no
notification, because it appended nothing. A consumer that relies only on
notifications will keep holding committed events until the next append or the
next safety-net poll. So while withheld events exist, the consumer should
re-check the gate on a timer with backoff, capped at the safety-net interval,
instead of waiting for a notification.

### Bounding the stall

The library cannot shorten other workloads' transactions itself. It can offer
these options, in roughly this order of preference:

- **Isolation.** Run the event store on its own cluster. A separate database on
  a shared cluster does not help, because the gate is computed over the whole
  cluster.
- **Server-side timeouts.** Set `idle_in_transaction_session_timeout`,
  `transaction_timeout` and `statement_timeout` for the application roles that
  share the cluster. Set `max_prepared_transactions = 0` where two-phase commit
  is not used, so a forgotten prepared transaction cannot hold the gate
  indefinitely.
- **Library hygiene.** With psycopg 3, use autocommit or scoped transaction
  blocks on every library-owned connection. This stops the library's own
  appenders, checkpoint writers and listener connections from becoming the
  idle-in-transaction blocker.
- **A consumer stall policy.** Above a configured threshold, report the stall
  and keep waiting. Never step past the gate silently: that trades the
  ordering guarantee for liveness, and a blocked appender's event could then
  be skipped. Terminating the blocker with `pg_terminate_backend` should be an
  explicit, opt-in operator policy, not a default. It needs privileges and
  affects a workload the library does not own.
- **Heuristic advance (opt-in).** Where liveness matters more than strict
  order, the consumer can advance heuristically and reconcile events that
  arrive late. This mirrors the heuristic watermarks and late-data handling in
  Akidau et al. It turns the stall into out-of-order delivery, which must then
  be detected through gaps. That is an explicit semantic change, not a
  tuning setting.

The finer-grained remedy in the garbage-collection literature (Böttcher et
al.; Lee et al.) suggests a structural fix. Gate only on transactions that
could still append events, not on all of them. That needs some way to tell
appenders apart from unrelated sessions before they commit.

### Reporting

The consumer should expose one of three states: caught up, behind (normal
lag), or gated. When it is gated, it should report:

- the number of withheld events, or a capped count;
- the stall duration;
- the transaction-ID age of the gate;
- a description of the blocker (pid, application name, state and transaction
  duration, or the gid of a prepared transaction).

A health check should turn degraded once the stall passes the threshold. The
log line should name the blocker, because the fix is nearly always outside the
consumer.

### Limits of the evidence

The scholarly records establish two things in general terms:

- long-lived transactions hold back MVCC horizons, and PostgreSQL is still
  affected;
- coarse minimum-based horizons are the cause, and finer-grained tracking
  helps.

They also establish that watermark lag is the right thing to monitor when
progress is gated by a minimum over inputs. The PostgreSQL-specific mechanics
above come from the system's documented behaviour, not from these records:

- the split between `backend_xid` and `backend_xmin`;
- lazy assignment of transaction IDs;
- the cluster-wide scope of the gate;
- the timeouts and their defaults;
- the wraparound limits.

None of the records measures how long consumer gates stall in practice.
