# How do established PostgreSQL job and event libraries such as Oban, River, pg-boss or Graphile Worker combine LISTEN and NOTIFY wake-ups with a durable table and fallback polling to recover from missed notifications?

## Question

How do Oban (Elixir), River (Go), pg-boss (Node.js) and Graphile Worker (Node.js) use PostgreSQL `LISTEN`/`NOTIFY` to wake consumers while keeping the jobs table as the source of truth? And what polling, re-announcement and reconnect logic do they use so that a lost, merged or never-sent notification costs only latency, never a job?

## Findings

### The shared design: the notification is a hint, the table is the truth

All four libraries handle `NOTIFY` the same way. The notification carries no work. At most it names a queue or gives a count. When a consumer receives one, it runs the same locking fetch against the jobs table that it would run on a timer. pg-boss's notifier source says this outright: "A NOTIFY is only ever a latency hint: it wakes workers so they run their normal locking fetch sooner than the polling interval." Its worker docs describe `LISTEN`/`NOTIFY` as "an opt-in optimization on top of polling, not a replacement for it. Polling always keeps running as a safety net, so jobs are never lost if a notification is missed (for example during a brief connection drop)."

This matches how the PostgreSQL docs frame `NOTIFY`: the event "essentially means, 'I changed this table, take a look at it to see what's new'". It also explains why two `NOTIFY` behaviours are harmless here:

- **Commit-time delivery.** Notifications are only delivered if the transaction commits, so a woken consumer never sees uncommitted work.
- **Duplicate collapsing.** Identical channel-and-payload notifications within one transaction are delivered once. Since the payload is only a hint, merging them loses nothing.

Four mechanisms recur across the libraries:

1. **Notify in the inserting transaction, and only for runnable work.** No wake-up fires before commit, and no wake-up is spent on work that isn't runnable yet.
2. **A backstop poll** that runs whether or not notifications are healthy.
3. **Coalescing of wake-ups**, at the sender, the receiver or both. A busy consumer can safely ignore a wake-up because it fetches again as soon as it has capacity.
4. **Health detection and fallback to pure polling** when the listener is unavailable. In pg-boss's case this also includes an explicit catch-up fetch on reconnect.

### Oban

**Publishing.** Insert notifications used to come from a database trigger. Since v2.17 they are sent from application code, "so it's possible to disable triggers without running database migrations, and they work for *any* notifier, not just Postgres". `Oban.Engine.notify_trigger/2` builds the payload only from jobs whose state is `"available"`, with each queue listed once. It publishes on the `insert` channel when `insert_trigger: true` is set.

**The Postgres notifier connection.** The notifier holds its own `Postgrex.SimpleConnection` with `auto_reconnect: true`. Its source says "Every connection, including a reconnect after a crash, listens on all channels that have registered listeners." Listeners are tracked in a registry outside the notifier process, so they "are guaranteed to receive notifications after the notifier restarts without any monitoring or resubscribing on their part". The notifier notes that payloads "can't exceed 8kb". It also notes that it "doesn't work with connection poolers like PgBouncer when configured in transaction or statement mode". The `Oban.Notifiers.PG` notifier, which runs over Distributed Erlang, is the documented alternative.

**Consuming.** A queue's producer handles `{:notification, :insert, %{"queue" => queue}}` for its own queue by scheduling a dispatch. If a dispatch is already pending, it does nothing more. The debounce (`dispatch_cooldown`) defaults to 5 ms. Dispatch fetches jobs with `FOR UPDATE SKIP LOCKED` and schedules another dispatch when a running job finishes.

**Recovery through the Stager.** Missed notifications are recovered by the Stager, not by the producer:

- **Every tick.** The Stager runs every second by default (`interval: :timer.seconds(1)`, `limit: 5_000`). On the leader, in one transaction, it moves `scheduled` and `retryable` jobs whose `scheduled_at <= now` to `available`.
- **Global mode.** The leader then runs `check_available`, a `DISTINCT` query over queues that have any `available` job, and publishes an `insert` notification for each of those queues. Any queue that still has runnable work is re-announced about once a second, so a lost insert notification, a dropped connection or a crashed consumer costs at most about one stager interval. Only the leader queries.
- **When publishing fails.** If publishing the notification fails, the Stager falls back to local delivery.
- **Local mode.** Every node's Stager sends the insert message straight to every local producer on every tick. In effect each queue polls independently every second.

**Choosing the mode.** The mode comes from `Notifier.status/1`, which is backed by the `Sonar` process. Sonar pings on a `sonar` channel, every 5 s at first, backing off to 60 s, and treats nodes as stale after 120 s. The mapping is:

- `:clustered` → global mode.
- `:isolated` → local mode.
- `:solitary` → global mode on the leader, local mode otherwise.

v2.17.4 introduced this to replace "ad-hoc stager checks". It fixed "an infrequent and difficult to spot bug where isolated follower nodes wouldn't process jobs". The troubleshooting guide warns about the cost of degraded mode: "If every queue is polling the database every second, job staging has switched from efficient global mode to local mode."

### River

**Publishing.** `maybeNotifyInsertForQueues` calls `pg_notify` through `tx.NotifyMany()` inside the insert transaction. It only notifies for jobs inserted in the `available` state. It is also rate-limited per queue per client: `insertNotifyLimiter` is built with the `FetchCooldown` duration and calls the notify function "no more than once per waitDuration". A burst of inserts therefore sends at most one wake-up per queue per cooldown, and some inserts send none.

**Consuming.** The producer's insert handler ignores other queues and calls `fetchLimiter.Call()`. `FetchCooldown` (default 100 ms) is "the minimum amount of time to wait between fetches of new jobs". Fetch size is `MaxWorkers - numJobsActive`. If a fetch returns a full batch, "implying there may be more in the queue", the producer sets `fetchWhenSlotsAreAvailable` and fetches again as soon as a job completes.

**The backstop poll.** `FetchPollInterval` (default 1 s) is documented as follows: "Typically new jobs will be picked up ~immediately after insert via LISTEN/NOTIFY, but this provides a fallback." The poll loop's comment gives the reasons: it is "a back up in case something with listen/notify didn't work, or the fetch limiter was limited so there's still jobs to pick up, and it's also important in poll-only mode." Each poll adds random jitter of up to 10% so that producers don't fetch in lockstep. The poll runs no matter how healthy the notifier is.

**Scheduled work.** The `JobScheduler` maintenance service runs every 5 s by default. It moves `scheduled` and `retryable` jobs that are due to `available`. For queues with now-runnable jobs, it calls `NotifyInsert` inside the same transaction before commit.

**The listener and poll-only mode.**

- **Reconnect.** The notifier uses one listener connection, reconnects with exponential backoff, and re-issues `LISTEN` for every subscribed topic. It logs "Notifier healthy" or "Notifier unhealthy", and it drops notifications with "Dropping notification due to full buffer". The backstop poll covers both losses.
- **`PollOnly`.** This mode "avoids issuing LISTEN statements… The program instead polls periodically". River enters it automatically when the driver does not support a listener.
- **Connection poolers.** River's PgBouncer guide says work coordinators "use LISTEN/NOTIFY and need PgBouncer in session pooling mode, or no PgBouncer". It recommends transaction pooling for inserts and "a raw Postgres pool" for coordinators.

### Graphile Worker

**Publishing.** The current SQL migrations have `add_job` and `add_jobs` call `pg_notify` inside the inserting transaction:

```sql
perform pg_notify('jobs:insert', '{"r":' || random()::text || ',"count":' || array_length(specs, 1)::text || '}');
```

An older migration used a statement-level `AFTER INSERT` trigger with an empty payload instead. The sources don't say why the payload includes `random()`. One likely effect is that every payload is unique, so PostgreSQL's same-transaction collapsing never merges two notifications and drops a count. This is an inference, not a documented rationale.

**Consuming.** The worker pool's listen client issues `LISTEN "jobs:insert"; LISTEN "worker:migrate";`. A `jobs:insert` message nudges up to `count` idle workers. Each worker's `doNext` loop works like this:

- After finishing a job it calls `doNext()` again straight away, so a busy worker drains the table without needing notifications.
- When a fetch finds nothing, it sets a timer for `pollInterval` (default 2000 ms).
- A nudge cancels a pending timer and fetches immediately. If the worker is busy, the nudge only sets an `again` flag, so it re-fetches without sleeping.

The FAQ puts it this way: when an instance receives an event "it will pick an idle worker to ask for jobs. If there is no idle worker then it'll drop the event knowing that when one of the workers finishes they'll ask for the next job anyway."

**Recovery.** The listen client reconnects with jittered exponential backoff (`50 * e^attempts`, capped). Reconnecting does not nudge workers, so polling alone recovers notifications missed while disconnected. Polling also handles all time-based work: "We cannot use LISTEN/NOTIFY since there's nothing to generate an event when the time 'ticks over'." The FAQ suggests 30 or 60 s polling is "probably fine" when polling load is a concern.

**The optional `localQueue`.** It locks a batch of jobs and hands them to workers. In its empty (`POLLING`) mode it fetches every `pollInterval`. Notifications ("pulse") can cut short a `refetchDelay` once enough jobs have been announced. The cost is that newly added high-priority jobs "will not be detected until the local queue is exhausted".

**Connection poolers.** The FAQ notes PgBouncer "might pose an issue if it's not done in 'connection' mode".

### pg-boss

pg-boss is the clearest example of polling as the base layer, and it has the most explicit reconnect handling.

**Opting in, and how polling adapts.** By default workers poll every `pollingIntervalSeconds` (default 2, minimum 0.5). `LISTEN`/`NOTIFY` needs two opt-ins: `useListenNotify: true` on the instance and `notify: true` per queue. While the listener is up for a queue, the poll relaxes to `notifyPollingIntervalSeconds` (default 30 s) as "a slow backstop". `resolveInterval` makes this choice each loop. It returns the notify interval only while `notifier.available` is true and the queue has notify enabled. Otherwise it falls back to the normal interval, so polling speeds up again whenever the listener is down. It returns 0, an immediate re-fetch, after a full batch when burst options apply.

**Publishing.** "A NOTIFY is emitted transactionally with the insert, so it fires on commit", including inserts made in the caller's own transaction. The channel is namespaced per schema. Jobs that aren't runnable yet are not announced: "Future-dated jobs (`startAfter`, `sendAfter()`, throttling/debouncing) and jobs blocked by flow dependencies are picked up by polling once they become eligible."

**The listener connection.** It uses a dedicated, session-pinned `pg.Client`, kept outside the query pool:

- **Keepalive.** TCP keepalive is on (`notifyKeepAliveInitialDelayMs`, default 10000).
- **Heartbeat.** Every `notifyHeartbeatIntervalMs` (default 10000), a same-session heartbeat queries `pg_listening_channels()` to confirm the subscription still exists. If a heartbeat takes longer than `notifyHeartbeatTimeoutMs` (default 5000), "the listener is torn down and reconnected".
- **Backoff.** Reconnect backoff is `min(30000, 1000 * 2^min(attempt, 5))` ms.
- **Catch-up after reconnect.** Once `LISTEN` succeeds again, an `onReconnect` callback calls `forceFetchLnWorkers()`. This wakes every worker on a notify-enabled queue so that "the caller can recover missed messages". Because the callback runs after `LISTEN` is in place, work committed after that point raises a fresh notification, and work committed earlier is found by the forced fetch.

**Wake-ups during a fetch.** `worker.notify()` sets `beenNotified` and aborts the pending sleep. A notification that arrives mid-fetch makes the next loop iteration skip its delay.

**Without a listener.** When `LISTEN` is unavailable, for example through PgBouncer in transaction or statement mode, pg-boss "emits a warning of type `listen_notify_unavailable` and continues polling only".

### Cross-library comparison

| Concern | Oban | River | Graphile Worker | pg-boss |
|---|---|---|---|---|
| Where `NOTIFY` is issued | App code at insert, available jobs only | Insert transaction, available jobs only, rate-limited per queue | `add_job` and `add_jobs` SQL, count plus random payload | Insert transaction, immediately runnable jobs only |
| Receiver coalescing | 5 ms dispatch debounce | 100 ms fetch cooldown | Nudge idle workers only, or set a re-fetch flag | `beenNotified` flag |
| Backstop | Leader re-announces queues with available work every 1 s; local per-queue polling when isolated | Per-producer poll every 1 s (jittered), always on | Per-idle-worker poll every 2 s | Per-worker poll, 30 s while the listener is healthy, 2 s otherwise |
| Time-based work | Leader stager every 1 s, then notifies | Leader scheduler every 5 s, then notifies | Polling only | Polling only |
| Health detection | Sonar pings, isolated or solitary or clustered | Backoff reconnect, healthy or unhealthy logging, poll-only mode | Backoff reconnect | TCP keepalive plus `pg_listening_channels()` heartbeat with timeout |
| Catch-up on reconnect | Implicit through the 1 s re-announcement | Implicit through the 1 s poll | Implicit through polling; no nudge on reconnect | Explicit forced fetch after `LISTEN` re-succeeds |

Every library assumes notifications can be lost and builds a polling floor under them. They differ in where that floor sits:

- **Per consumer.** River, Graphile Worker and pg-boss each poll from every consumer.
- **Central re-announcement.** Oban's global mode runs one cluster-wide query per second on the leader and fans out hints. This keeps load flat as consumers are added, but it needs leader election and a working pub-sub channel.
- **Health-aware.** pg-boss is the only one that lengthens its backstop while the listener is known to be healthy and shortens it when it isn't.

### Relevance to an event store

For a psycopg 3 event-store consumer, the libraries suggest a direct translation. The table-claiming fetch becomes "read events after my checkpoint":

- **Hint-only payloads.** Keep the `NOTIFY` payload a hint, such as a category or stream name, or a position. Send it in the appending transaction so it only fires on commit.
- **A drain loop.** Read until empty, then sleep until either a notification or a backstop timer fires. Treat any wake-up received while reading as "read again without sleeping".
- **Explicit catch-up.** After the first subscription and after every reconnect, do a catch-up read once `LISTEN` has been confirmed, as pg-boss does. This closes the window between the old connection dying and the new one listening.
- **A health-aware backstop.** Choose the poll interval based on listener health. Use a long backstop while a heartbeat confirms the subscription, and drop back to a short poll when it doesn't.

Checkpoint-based reads are idempotent, so duplicate or extra wake-ups only waste a query. That makes the libraries' aggressive coalescing and "drop the event if busy" behaviour safe to copy.
