# Which dispatch designs, such as a single listening session fanning work out to a pool or partitioned channels per consumer, let competing PostgreSQL consumers avoid thundering-herd wake-ups while keeping load balanced?

## Question

When several competing consumers read work from PostgreSQL, which dispatch
designs stop one new item of work from waking every consumer, while still
spreading the work evenly? Candidate designs include a single listening session
that fans work out to a pool, and a separate channel for each consumer or
partition.

## Findings

**The problem setting.** PostgreSQL's LISTEN/NOTIFY is a broadcast: every
session listening on a channel receives every notification sent to it, and
there is no "notify one listener" option. If N competing consumers all listen
on one channel, each new event wakes all N. They then race to claim the work,
for example with `SELECT … FOR UPDATE SKIP LOCKED`, and N−1 of them come back
empty-handed. None of the scholarly records found study PostgreSQL directly.
What they do give is the queueing and systems theory behind the trade-off
between wake-up cost and load balance. Applying that theory to PostgreSQL is
inference, flagged as such below.

**Why wake-all is harmful.** Work on the thundering-herd problem treats
waking many waiters for one event as an amplifier, not just a waste of effort.
Mergendahl et al. (2022) show that thundering-herd wake-ups in
microkernel inter-process communication can be used to amplify kernel
interference and degrade response times in real-time systems. An IETF-style
document on the DNS thundering-herd problem (Sivaraman and Liu) reports
regular, synchronised spikes in queries at caching resolvers, and recommends
software mitigations that break the synchronisation. Both point to the same
cost in a database: when consumers wake in lockstep, the empty claim queries
they fire land on the server as correlated bursts.

**Design 1: one listener and a central queue (single-queue dispatch).** Here
one session listens and hands work to a pool of workers. This turns N
consumers that each wait separately into one shared queue served by k
workers, the queueing model known as M/M/k. Each notification wakes exactly
one session, and no worker sits idle while work is waiting. ZygOS (Prekas,
Kogias and Bugnion) builds on the standard queueing result that a single
shared queue gives much lower tail latency than k separate per-worker queues,
because separate queues let work pile up behind one busy worker while others
are idle. The cost of central dispatch is that the dispatcher becomes a single
point limiting throughput and availability. Sparrow (Ousterhout, Wendell,
Zaharia and Stoica) cites exactly these limits of centralised schedulers when
it argues for decentralised, randomised sampling, which its authors show gets
close to optimal. *Inference:* for an event-store consumer the dispatcher only
handles wake-up signals and claims rows, not the processing itself, so its
throughput ceiling is high. The main risk is availability. A natural layout
has two levels:

- one listening session per process, so a wake-up herd is at most the number
  of processes, not the number of workers;
- in-process fan-out to workers through a local queue.

**How the dispatcher should hand out work: late binding and pull.** Two
results argue that the central component should not push a specific item to
a specific worker. Instead, workers should say when they have capacity.

- **Join-Idle-Queue** (Lu et al., 2011): idle servers register themselves in
  an "idle queue" held by a dispatcher, and new jobs go to a known-idle server.
  This takes load-probing messages off each job's critical path.
- **Late binding** (Sparrow): a worker is committed to a task only once it is
  ready to run it.

*Inference, in PostgreSQL terms:* treat a notification purely as a hint that
work exists. Hand the hint to an idle worker, and have that worker claim a
specific row (with SKIP LOCKED) only when it is free. Then neither stale
assignments nor duplicate wake-ups can strand work.

Zhou, Tan and Shroff refine this in two papers:

- JIQ, where a worker asks for work only when completely idle, is *not*
  delay-optimal under heavy traffic, even when all servers are identical.
- A pull-based policy that sends work to any server whose queue is below a
  threshold *is* optimal, but only if the threshold grows as load approaches
  capacity.

*Inference:* at high event rates, workers should advertise capacity for more
than one item, through prefetch credits or batch claims, rather than asking
only when empty.

**Design 2: a channel per consumer or partition.** Hash each stream or
partition to a channel owned by one consumer, so each NOTIFY wakes exactly
one consumer. This removes the herd completely and keeps related work in one
place. It is the database version of per-core accept queues. Pesterev et al.
(Affinity-Accept) show that partitioning connections so they stay on one core
improves locality, but that partitions need a balancing mechanism, namely idle
cores stealing connections from busy ones. The weakness of pure partitioning
is the separate-queues problem ZygOS describes: under skewed load (a hot
stream) or when a consumer is slow or dead, work queues behind its owner
while other consumers sit idle. Both ZygOS and Affinity-Accept fix this with
**work stealing**, which recovers most of the balance of a single shared queue
while keeping the locality of partitions. *Inference:* a consumer that has
nothing in its own partition should fall back to claiming work from other
partitions, for example with an occasional SKIP LOCKED sweep. Partition
ownership should also be reassigned when a consumer fails. Stealing can break
ordering within a partition, which matters for event streams.

**Design 3: randomised targeted notification (power of d choices).** Between
waking everyone and waking a fixed owner sits randomised selection.
Mitzenmacher's "supermarket model" shows something striking. If each job
samples just two servers at random and joins the shorter queue, the expected
time spent in the system improves *exponentially* compared with picking one
server at random. Choosing among three or more servers adds only a further
constant-factor gain. Zhou et al. include power-of-d in their class of policies
that are delay-optimal under heavy traffic. *Inference:* a dispatcher, or a
notifier that can read a small table of consumer load, could notify the
less-loaded of two randomly chosen consumer channels. That gets most of the
benefit of join-shortest-queue with almost none of the coordination, though
writer transactions in PostgreSQL rarely know consumer load. So this fits best
inside a process-level dispatcher choosing among workers, not at the NOTIFY
call site.

**Synthesis.** No design is best on both wake-up count and balance on its own.
The recommended combination is:

- one listener per process, so the herd is bounded by the number of processes;
- pull-based, late-binding hand-off to workers, claiming rows with
  SKIP LOCKED;
- capacity credits that grow with load;
- if partitioned channels are used for locality, work stealing or a fallback
  sweep so that skew and failed consumers cannot strand work.

Design choices aside, the DNS and microkernel cases show that unavoidable
synchronised wake-ups (for example, every process waking on a shared channel)
should be spread out, for instance with jitter.
