# What append throughput and latency does a PostgreSQL event store achieve when appends are serialised by a transaction-level advisory lock or counter-row lock taken just before allocating positions, compared with unserialised appends that each issue NOTIFY?

## Question

An event store can make position order match commit order by serialising appends: each append takes a transaction-level advisory lock (`pg_advisory_xact_lock`) or a row lock on a counter row just before it allocates positions. Alternatively it can let appends run concurrently from a sequence, with every append transaction issuing `NOTIFY`. What append throughput and latency does each design achieve, and why?

## Findings

**Short answer.** I found no published benchmark that compares these two designs directly. The PostgreSQL source shows why the gap between them is smaller than it looks: **both designs already contain a serialised section that runs across the commit's WAL flush.** `NOTIFY` takes its own exclusive lock at pre-commit and holds it until after commit. A transaction-level advisory lock or counter-row lock is held until the same point. So the serialised design costs extra only for the work between taking the lock and committing, not for an extra flush. The design that scales with concurrency is unserialised appends that do **not** issue `NOTIFY` inside the transaction. The measured numbers below come from one counter-row-plus-`NOTIFY` event store and from production reports. They show aggregate throughput staying flat in the low thousands of events per second at batch size 100, while per-append latency rises with concurrency to hundreds of milliseconds, and up to about a second at extreme concurrency.

### Why both designs serialise at commit

- **`NOTIFY` takes a lock at commit.** In `PreCommit_Notify`, PostgreSQL calls `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)`. The source comment says: "Serialize writers by acquiring a special lock that we hold till after commit. This ensures that queue entries appear in commit order." It is a heavyweight lock "so that it'll automatically be released after either commit or abort". The comment also notes it is a lock on "database 0", so it is not scoped to any single database.
- **Locks are released only after the commit is durable.** In `xact.c`, `CommitTransaction` calls `PreCommit_Notify`, then `RecordTransactionCommit` (where the commit record is flushed, or with asynchronous commit only queued for flushing), and releases locks after that. If synchronous replication is configured, the standby wait happens inside `RecordTransactionCommit`. The comment there says the backend still shows as running and continues to hold its locks. The documentation confirms that transaction-level advisory locks "are automatically released at the end of the transaction" and that row-level locks "are released at transaction end".
- **Consequence: concurrent notifying transactions cannot share a WAL flush** (an inference from the two points above). Group commit only forms from sessions that reach their flush while an earlier flush is in progress. A second notifying transaction is blocked at pre-commit until the first has flushed and released the lock. So each `NOTIFY`-issuing append pays roughly one serial commit flush, plus a standby round trip under synchronous replication.

This gives a simple model of each design's serialised window:

- **Unserialised appends with `NOTIFY`:** writing to the notification queue, plus the commit flush, plus any synchronous-standby wait.
- **Serialised appends:** all of the above, plus the position allocation and `INSERT` work (indexes, triggers) done after the lock is granted, plus any client-to-server round trip between taking the lock and sending `COMMIT`.

Throughput is capped at about 1 divided by the length of the serialised window, in transactions per second, and that times the batch size in events per second. Unserialised appends without in-transaction `NOTIFY` avoid this cap through group commit. That cap is the real alternative to compare against. PostgreSQL's pgbench documentation describes the hot-row effect: when clients outnumber the rows they all update, "you'll mostly be measuring update contention", with "lots of transactions blocked waiting for other transactions." Laurenz Albe (Cybertec) says a counter row "will serialize all transactions that use that 'sequence'. That will deteriorate your data modification performance considerably."

### Measured numbers

**Commanded EventStore (Elixir) uses both a counter row and `NOTIFY`.**

- Each append is one statement with common table expressions (CTEs). It increments the `$all` row (`stream_id = 0`) of the `streams` table by the batch size and derives global positions from that row. The row lock is held until commit.
- A per-row trigger on `streams` calls `pg_notify`, so every append also issues `NOTIFY`.
- In its benchmark, one operation is N concurrent tasks, each appending 100 events to a new stream, and the operation ends when all N finish. The README publishes these sample figures against "a local PostgreSQL database". It gives no hardware or PostgreSQL version.

| Concurrent writers | Events per operation | Time per operation | Derived events/s |
|---|---|---|---|
| 1 | 100 | 20.3 ms | ~4,900 |
| 10 | 1,000 | 127.4 ms | ~7,800 |
| 20 | 2,000 | 376.8 ms | ~5,300 |
| 50 | 5,000 | 582.4 ms | ~8,600 |

Going from 1 to 50 concurrent writers raises aggregate throughput by less than 2x. Meanwhile the time for a round of concurrent appends grows from about 20 ms to about 580 ms. That is the pattern a serialised section produces. The benchmark does not separate the lock from other limits, such as connection-pool size, local hardware or Elixir overhead.

**Production reports on serialised counters:**

- Sequin tried row-lock serialisation of a counter. "Write throughput was much lower than we needed, and the lock durations between concurrent writes was very high (seconds)." This held even after moving the counter update to the very end of the transaction to minimise lock time. Sequin switched to a read-side approach instead.
- Oskar Dudycz (event-driven.io) found that a singleton counter table made "all the processing that's calling this function sequential". He judged "the performance hit … too big to accept" and adopted transaction ids with `pg_snapshot_xmin`.

**Production report on unserialised writers that each issue `NOTIFY`:** Recall.ai ran "tens of thousands of simultaneous writers" (July 2025).

- Commits queued on "AccessExclusiveLock on object 0 of class 1262 of database 0".
- One holder held the lock for about 1,016 ms while more than 300 processes waited about 1,000 ms each.
- Database CPU and I/O "plummeted" while throughput collapsed.
- They moved notification out of PostgreSQL into the application layer.

So `NOTIFY` alone, with no event-store lock at all, can push commit latency to around a second under heavy concurrency.

**Evidence that allocating positions later helps:** Marten's "Rich" append mode fetches sequence numbers in a separate step before the append. "Quick" mode allocates them within the append itself. Marten reports that Quick mode "appears to lead to a 40-50% time reduction" in appending and is "substantially less likely to lead to gaps". It is the default from Marten 9.

### How implementations choose lock scope and placement

- **Python `eventsourcing` library.** It runs `LOCK TABLE … IN EXCLUSIVE MODE` in every insert transaction, so that "the insert order [is] the same as the commit order". Reads continue concurrently under `ACCESS SHARE`. The lock timeout defaults to 0 (wait indefinitely). It publishes no throughput figures.
- **Message DB.** `write_message` first calls `pg_advisory_xact_lock(hash_64(category))`, before reading the stream version and inserting. This serialises writes within a category and lets different categories write in parallel. It follows (an inference) that positions are commit-ordered only within a category.
- **Lock placement.** Every client round trip inside the window is serialised too. So take the lock as late as possible and send the lock, insert and `COMMIT` in one round trip. A server-side function does this, and so does psycopg 3 pipeline mode, which sends statements "without having to read the result of the previously sent query". In pipeline mode, statements form an implicit transaction that commits at the Sync.

### Settings and changes that move the ceiling

- **Batch size.** More events per transaction spread the cost of each serialised window over more events.
- **Asynchronous commit** (`synchronous_commit = off`, which can be set per transaction). The server returns success "before the WAL records … have actually made their way to disk", which removes the flush from the window. The risk is losing acknowledged appends from up to three times `wal_writer_delay`: "data loss, not data corruption". A further inference: consumers may already have acted on events that disappear after a crash.
- **Synchronous replication** puts a standby round trip inside every lock-holding window.
- **Moving `NOTIFY` off the append path** removes the commit-ordering lock from appends. Oban recommends `insert_trigger: false`, or a notifier outside the database, "with the tradeoff that notifications from within a database transaction may be sent even if the transaction is rolled back."
- **PostgreSQL development branch.** Commit 282b1cde9 (January 2026) adds a shared channel map and "direct advancement". It gives "integer multiples" more `NOTIFY` throughput when many listeners are each interested in only a few messages, but "no improvement for the simplest case where every listener reads every message". The master branch's `PreCommit_Notify` still takes the lock it holds "till after commit". A May 2026 follow-up commit (0f24332ae) fixed listeners missing messages after that change.

### Consumer-side latency

`NOTIFY` delivers messages "in the order in which the transactions committed". With serialised appends, positions also follow commit order, so a woken consumer can read everything after its last position without waiting. With unserialised appends, a consumer has to stop at holes in the sequence. Marten's high-water mark "stops under any hole" while a transaction that could fill it is still running. So the consumer's added latency is the duration of the slowest in-flight append. Serialised appends therefore trade append throughput and latency for zero gap-wait at the consumer.
