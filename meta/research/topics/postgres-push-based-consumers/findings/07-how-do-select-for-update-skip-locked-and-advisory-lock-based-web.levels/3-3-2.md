# How should a PostgreSQL consumer group choose its virtual partition count, and how are per-partition checkpoints safely migrated when partitions are later split, merged or rehashed to a new count?

## Question

A PostgreSQL consumer group divides the event log into virtual partitions, usually by hashing the stream id. Each partition has one owner and one checkpoint, so per-stream order is kept. This note asks two things. How large should the partition count be? And when the count changes later, through a split, a merge or a full rehash, how can the per-partition checkpoints move to the new layout without skipping events or handling them twice?

## Findings

### Keep "how many partitions" separate from "how many consumers"

The most important design choice is to make the partition count independent of the member count. Once that holds, adding or removing consumers needs no checkpoint migration at all.

- **Message DB ties partitions to members, so they cannot be scaled apart.** Its category read filters with `MOD(@hash_64(cardinal_id(stream_name)), $6) = $5`, where `$6` is the consumer group size and `$5` is the member index. It checks that the member index is "less than the group size". The partition count is therefore the group size. Each member keeps its own position. Our inference from the SQL is that changing the group size gives each member a different set of streams, so the member's stored position no longer describes the work it now owns. The function offers no way to migrate.
- **Akka Projections fixes a fine-grained slice count and moves only the assignment.** A slice "is deterministically defined based on the persistence id" so as to "evenly distribute all persistence ids over the slices." The journal stores it as a `slice INT NOT NULL` column, indexed as `(slice, entity_type, db_timestamp, seq_nr)`. Projection instances take contiguous slice ranges. For example, "if using 1024 slices and running 4 Projection instances the slice ranges would be 0-255, 256-511, 512-767, 768-1023". Moving to 8 instances halves each range, and "more Projection instances can be added when needed and still reuse the offsets for the previous slice distributions."
  - This works because the timestamp offset store is keyed by slice (`PRIMARY KEY(slice, projection_name, timestamp_offset, persistence_id, seq_nr)`), not by the instance's range.
  - The one rule: "when changing the number of slices the projections with the old slice distribution must be stopped before starting new projections."
- **Axon stores one token per segment, independent of threads and nodes.** Segments are claimed by any thread on any node. `initialSegmentCount` "can only be set when a streaming processor starts for the first time". It defaults to 1 for the TrackingEventProcessor and 16 for the PooledStreamingEventProcessor. Changing the count later means explicit split and merge operations, described below.

For a PostgreSQL event store, Akka's design suggests a two-level scheme:

1. Store a fixed, fine-grained slice number on each event row when it is appended. The slice count M is a power of two, for example 256 or 1024.
2. Keep checkpoints per slice, or at least make them convertible to per-slice values.
3. Treat the "partitions" handed to members as ranges or groups of slices.

Rescaling members is then just reassigning ownership. Real checkpoint migration is only needed if M itself changes, and choosing M generously makes that very rare.

### Choosing the count

These are the main factors, combining the sources with arithmetic. The specific numbers are our synthesis, not vendor guidance.

- **Parallelism ceiling.** A partition is the unit of ownership and ordering, so no more members can be busy than there are partitions. Axon warns that a tracking processor "can only claim a single segment per thread, segments may go unprocessed if there are more segments than threads." Its pooled processor removes the one-to-one link. Kafka practice is to "over-partition a bit", sizing for "a future target throughput, say for one or two years later". The reason is that changing the count of a keyed topic breaks the deterministic key-to-partition mapping that ordering depends on. The formula there is at least `max(t/p, t/c)` partitions.
- **Balance granularity.** With P partitions over N members, the busiest member carries ⌈P/N⌉ partitions against a mean of P/N. For P=16 and N=5 that is 4 against 3.2, 25% over the mean. P=256 gives 52 against 51.2 (about 1.6%), and P=1024 gives about 0.1%. Finer granularity also lets rebalancing move small units. However, a single hot stream can never be split, so raising P beyond the number of active streams gains nothing.
- **Power-of-two counts (or a chain of moduli where each divides the next).** These make later splits and merges local:
  - PostgreSQL's own hash partitioning requires that "every modulus which occurs among the partitions of a hash-partitioned table is a factor of the next larger modulus". This "allows the number of partitions to be increased incrementally". Its example turns one modulus-8 partition into two modulus-16 partitions with remainders r and r+8, one partition at a time.
  - Axon segments use the same idea as bitmasks. A value matches a segment when "the mask applied to the given value, matches the segment id". Two segments "can be merged when their mask is identical, and the only difference in SegmentID is in the first 1-bit of their mask." Segments at different split depths can coexist.
  - Akka's 1024 slices divide evenly into 2, 4, 8 and more ranges.
- **Per-partition cost in PostgreSQL.** This is inference; the cited sources are not measuring PostgreSQL. Each partition adds a checkpoint row, a lease row or advisory lock, and lease-renewal UPDATEs that produce WAL and dead tuples. If partitions are queried one by one, each also adds a query per poll or wake-up. The costs Kafka lists for too many partitions (file handles, failover time, replication latency, producer memory) belong to the broker and do not carry over. The PostgreSQL costs are rows and round-trips. Two ways to keep them flat:
  - Give each member a contiguous slice range and read it with one range predicate (`slice BETWEEN lo AND hi`), as Akka's index allows.
  - Renew all of a member's leases in one statement.
- **A stable hash.** The partition function must give the same answer in every process and every release. Python's built-in `hash()` of `str` is unsuitable: by default "a random value is used to seed the hashes of str and bytes objects", and the values "are not predictable between repeated invocations of Python." Use an explicitly specified hash, computed in the application or in SQL. Store either the full hash or the fine-grained slice on the row, so a later regrouping changes only the mask or range, not the data.

**Practical default (synthesis):**

- Fix the slice count M as a power of two, sized well above the largest member count you can foresee. Akka uses 1024.
- Assign slices to members as ranges.
- If checkpoints have to be per partition rather than per slice, make P a power of two, at least 4 to 8 times the expected peak member count. That keeps imbalance low and leaves room to grow before any split.

### Migrating checkpoints: split

Splitting is always safe if each child inherits the parent's checkpoint.

- **Why it works.** The child's key space is a subset of the parent's. The parent had already handled every event at or below position c for all of its keys. Each key now goes to exactly one child, and that child resumes from c. Nothing is skipped, nothing is handled twice, and per-key order is kept.
- **Axon does exactly this.** `TrackerStatus.split` hands both halves the same tracking token. The split instruction writes the new half with `tokenStore.initializeSegment(newStatus[1].getTrackingToken(), ...)` and keeps the first half as the active segment. Axon requires "the given `segmentId` must be currently processed by a process owned by this processor instance". Only the current owner, with no batch in flight, may split.
- **In PostgreSQL** (synthesis):
  1. Run the split in one transaction that locks the parent's checkpoint row and checks the caller's lease token or epoch.
  2. Rewrite the parent's mask or range.
  3. Insert the sibling row with the same position.
  4. Bump the epoch, so that any late write from a stale owner fails.
- **Large changes can be done step by step.** Like the PostgreSQL modulus-8 to modulus-16 example, partitions can be split one at a time, with old and new granularities coexisting in between.

### Migrating checkpoints: merge

Merging is the hard case, because the two siblings' checkpoints c_lo and c_hi are almost never equal.

- **Taking the larger checkpoint loses data.** The lagging sibling's events in (c_lo, c_hi] would be skipped. Never do this.
- **Taking the smaller checkpoint gives duplicates.** The leading sibling's events in that interval are delivered again. This is acceptable only when handlers are idempotent.
- **A composite checkpoint keeps exactly-once behaviour (Axon's approach).** The merge stores `new MergedTrackingToken(lowerToken, upperToken)` against the merged segment. The token "keeps track of the progress of the two original 'halves', by advancing each individually, until both halves represent the same position".
  - `advancedTo` advances both halves. When they become equal it returns a single plain token, which ends the merge.
  - While the merge runs, the processor splits the merged segment back into its two halves. An event counts for a half only if that half's token actually advanced (`isLowerSegmentAdvanced()` and `isUpperSegmentAdvanced()`). So the half that was already ahead does not see its events again.
  - Splitting a token that is mid-merge gives each half its own original token back.
  - Axon's merge needs the processor to own the given segment and "be able to claim the other segment". That means "this other segment must not have any active claims".
  - In PostgreSQL (synthesis): the checkpoint row holds the lower bound min(c_lo, c_hi) plus a small set of (sub-slice or mask, position) pairs. The reader starts at the lower bound and drops an event when its sub-partition's position already covers it. It clears the set once the lower bound passes every entry.
- **A drain-to-barrier merge is simpler.** Pause both siblings, run the lagging one forward to the leading one's checkpoint, then write one merged row at that position. Every recorded checkpoint is a safe "processed-through" position, so the barrier is safe as well.

### Migrating checkpoints: arbitrary rehash

Some changes do not keep a subset relationship between old and new partitions. Examples are going from 12 to 20 partitions, changing the hash function, or switching from modulo to a consistent-hash scheme. Each new partition then draws keys from many old ones, and there are three options.

- **Global barrier.** Stop the whole group. Bring every old partition's checkpoint to a common position T. Start every new partition at T. This matches how other systems handle the problem:
  - **Kinesis.** After a reshard, reading child shards before the parents are drained "could read data for a particular hash key out of the order". Consumers should "continue to read data from the parent shards until it is exhausted" first. The KCL lease table records `parentShardId` so that "the parent shard is fully processed before processing starts on the child shards".
  - **Kafka KIP-253** (still a proposal under discussion). It makes new partitions wait until their predecessor partitions have been consumed up to set offsets, using linear hashing so that expansion stays incremental. It also adds a callback so applications can "flush state related to the keys previously received" before keys move.
- **Generalised composite checkpoint (inference).** Start each new partition at the minimum of the old checkpoints it overlaps. Deliver an event only if it is beyond the checkpoint of the old partition it came from, computed with the old hash and old count. Drop that per-old-partition vector once the new position passes all of them. This is Axon's merged token extended to N inputs.
- **Reset and replay** the projection, if the handlers can rebuild.

Consistent-hashing schemes such as jump consistent hash reduce how many keys move when buckets are added. Jump hash also requires buckets to be numbered sequentially. With a fixed slice count and an assignment table, though, reassignment already moves the minimum, so consistent hashing mainly matters if partitions map straight to members. Unlike Kinesis or Kafka, virtual partitions over one PostgreSQL global log hold no data and never "close". Only the checkpoints need reconciling.

### Safety rules common to every migration

1. **Quiesce and fence.** No owner may have an uncommitted batch on an affected partition. The migration transaction locks the affected checkpoint rows and checks or bumps their lease epoch. Akka stops the old distribution; Axon allows only the owner to split, and merges only with an unclaimed sibling.
2. **Version the topology.** Store the slice count, the partition masks or ranges, and the hash version in a group configuration row with a generation number. Members check it when they claim and fail their fenced writes if it is stale. This stops two members running different layouts at once, which would cause gaps or double handling. (Synthesis.)
3. **Make each change atomic.** Delete or rewrite the old row and insert the new rows, all with their checkpoints, in one transaction, so no reader ever sees a half-migrated layout.
