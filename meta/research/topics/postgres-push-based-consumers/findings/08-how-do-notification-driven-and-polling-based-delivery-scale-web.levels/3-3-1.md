# How should catch-up reads for hundreds of subscriptions woken by the same head-position change be concurrency-limited, staggered or merged into one shared read, and what database cost does each approach incur?

## Question

When one commit moves the event log's head position and hundreds of subscriptions are woken together, each one wants to run its own catch-up read. Should those reads be capped by a concurrency limit, spread out in time, or replaced by one shared read whose results are handed out in memory? And what does each option cost the database?

## Findings

### The baseline: one wake-up, N identical reads

In a Python asyncio consumer, the herd is easy to create. `asyncio.Event.set()` wakes every task that is waiting on the event: "All tasks waiting for event to be set will be immediately awakened". If every subscription waits on the same head-changed event and then runs `SELECT … WHERE position > :cursor ORDER BY position LIMIT :n`, one commit produces N statements at the same moment. All of them ask for the same few rows at the tail of the table.

PostgreSQL does not merge these statements on the server. It has one built-in form of scan sharing, `synchronize_seqscans`, and that only lets *sequential scans of large tables* "read the same block at about the same time and hence share the I/O workload". A head read is an index range scan with a small `LIMIT`, so this feature does not apply. Because the tail pages are almost certainly already in shared buffers, the main cost of each read is likely the fixed work every statement does: a network round trip, taking a snapshot, starting the executor and sending the rows. It is probably not disk I/O. That is an inference from how PostgreSQL works, not a measured figure. The total cost is therefore roughly N times that per-statement overhead, plus N copies of the same k new events sent over the wire.

Connection pressure is the second cost. With a psycopg 3 pool, N simultaneous checkouts grow the pool to `max_size`, and the rest of the clients are "put in a queue, and will be served a connection once one becomes available". The psycopg documentation's own advice on pool size is "probably not as large as you imagine". If each subscription instead holds its own connection, the server pays for many backends.

- Andres Freund measured this before PostgreSQL 14. With 5,000 idle connections, `GetSnapshotData()` took about half the CPU time, and throughput fell by roughly 30%.
- With 5,000 *mostly-idle* connections that sent occasional queries, one active connection's throughput dropped from about 33,457 to 9,807 TPS.
- PostgreSQL 14 improved how fast snapshots are computed "on systems with many CPUs and high session counts". The release notes say this "also improves performance when there are many idle sessions". It reduces the problem but does not remove it.
- The PostgreSQL wiki adds that once *active* connections go beyond roughly `(core_count * 2) + effective_spindle_count`, spinlock, context-switch and cache-line contention lower throughput. It also says a queued transaction will often "reach completion sooner" than one admitted to a saturated server.

So hundreds of simultaneous head reads cost far more than the small amount of data they return.

### Option 1: limit how many reads run at once

**How it works.** Every catch-up read must acquire one shared limiter before it runs, for example an `asyncio.Semaphore(L)`. When the semaphore's counter is zero, `acquire()` waits until another task releases it.

Marten's async daemon is a production example. Every agent normally "opens its own database session" to load pages of events. Marten found that on a wide store, with many projections or one agent per projection per tenant, "an unbounded daemon can drive the connection pool's high-water mark". It now applies two governors to each daemon by default:

- `MaxConcurrentEventLoadsPerDatabase` (default 4). "All of a daemon's agents share one throttle, collapsing the steady-state connection footprint to *O(databases)* with no measured throughput cost."
- `MaxConcurrentBatchWritesPerDatabase` (default 4), which caps commits separately.

Setting either value to zero or below "restores the historical unbounded behavior".

**Database cost.** The number of statements and the rows sent are the same as the baseline: N reads per head change. What changes is that peak concurrent statements and connections are capped at L, which keeps active backends under the core-count limit described above.

**Cost to the application.** The last subscription to read waits about ⌈N/L⌉ times the duration of one read. Head reads served from cache take milliseconds, so with L=4 and a few hundred subscriptions this adds tens to low hundreds of milliseconds at the tail. That figure is an inference from the mechanism.

A separate semaphore that is smaller than the pool is better than relying on the pool's queue alone. The pool then keeps spare capacity for appends and checkpoint writes, which is why Marten caps reads and writes separately.

### Option 2: spread the reads out in time, with jitter and cooldowns

**How it works.** Each subscription waits a random delay, or a minimum cooldown, before it reads. Any further head changes that arrive during the wait are folded into the same read.

Three sources show the pattern:

- **Graphile Worker** (a PostgreSQL job queue) describes the herd directly: "each time a new job comes in, each pool may request it, multiplying up the load."
  - Its `refetchDelay` makes a pool wait `durationMs` "on average" before polling again "even when new job notifications come in".
  - `maxAbortThreshold` sets how many notifications force the pool to stop waiting and read. Each pool picks a random number up to that threshold, so that "different workers will abort refetch delay at different times which a) helps avoid the thundering herd problem, and b) helps to reduce the latency".
- **Oban** puts a `dispatch_cooldown` between a producer's fetches (default 5 ms) because "a cooldown period prevents a producer from flooding with messages and thrashing the database". Each queue's throughput is then capped at about `(1000 / cooldown) * limit` jobs per second.
- **AWS's study of backoff and jitter** found that without jitter, retries arrive in "clusters of calls". With 100 contending clients, adding jitter cut call counts by "more than half". Full Jitter, `sleep = random(0, min(cap, base * 2^attempt))`, did the least total work.

**Database cost.** For a single head change, staggering does not reduce the number of reads. All N subscriptions still each need the new events. Note the contrast with a job queue: there, the herd competes for one job and only one wins. In an event store, every subscription legitimately needs every event, so jitter mainly *spreads* the reads rather than removing them.

The saving shows up under a sustained write rate. If each subscription reads at most once per window W, its read rate is capped at 1/W instead of following the commit rate, and each read returns a bigger batch. Peak concurrency falls roughly in proportion to W divided by the duration of one read.

**Cost to the application.** Average latency rises by about W/2 with uniform jitter. Notifications are also partly ignored during the window, which is why Graphile needs an abort threshold.

PostgreSQL will not do this coalescing for you. It folds duplicate notifications only within one transaction ("notifications from different transactions will never get folded into one notification"), so merging wake-ups across commits has to happen in the application. A level-triggered flag such as `asyncio.Event` merges any number of `set()` calls into one pending wake-up.

### Option 3: merge the reads into one shared head read

**How it works.** One reader per process watches the head. It reads the new events once, starting from the lowest cursor among the subscriptions it serves, and hands them out in memory. Each subscription filters by its own cursor and, if it has one, its category or stream filter.

The general technique is request coalescing. Go's `singleflight` package is the textbook example: it makes sure "only one execution is in-flight for a given key at a time", and "if a duplicate comes in, the duplicate caller waits for the original to complete and receives the same results". Here the key would be the head position being read.

This is the most common design among mature event stores:

- **EventStore (Elixir, PostgreSQL-backed, used by Commanded).** "A single process will connect to the database to listen for these notifications. It fetches the event data and broadcasts to all interested subscriptions."
  - Its `Publisher` does one `read_stream_forward` per notification over that notification's version range, decodes the events once, and broadcasts them with `PubSub.broadcast`.
  - Each subscription only reads storage itself while catching up, in batches of `max_size` (default 1,000).
  - When a broadcast event arrives whose number is ahead of the one it expects, the subscription goes back to `request_catch_up`. When its buffer reaches `max_size`, it moves to `max_capacity` until acknowledgements drain the buffer.
- **Axon EmbeddedEventStore.** It keeps a cache of recent events (default 10,000) "to prevent that each event processor needs to read from the storage engine individually". A processor that keeps up "will not need a private connection to the underlying data store".
  - A processor is removed from the shared cache once the oldest cached event is newer than its last processed event. This check runs every `cleanupDelay`, default 10 s, and the removed processor then reads storage directly.
  - The shared producer checks storage after local commits and every `fetchDelay` (default 1 s) to pick up commits from other nodes.
  - `optimizeEventConsumption` (default true) makes separate consumers "read events from the same stream as soon as they reach the head of the stream".
- **Axon processors.** The Pooled Streaming Event Processor's coordinator "will always open a single event stream and delegate the events to the segment workers", whereas the Tracking Event Processor opens a stream per segment and "will use more I/O resources". The cost is that the pooled processor's segments "will at least process as fast as the slowest segment in the set".
- **Marten composite projections.** They read "the event range *once* for all seven constituent projections", meaning "less work fetching events and … fewer network round trips through bigger batches".
- **Akka Persistence R2DBC.** It goes further and publishes newly written events to running queries over cluster messaging, so they arrive "without waiting for next query poll".
  - The events "must still be retrieved from the database, but at a lower polling frequency, because delivery of published messages are not guaranteed".
  - Publishing switches itself off automatically when the moving-average throughput passes a threshold (default 400 events per second).
  - It still adapts polling to how full its buffer is (`refresh-interval` 3 s), and reads stop `behind-current-time` (100 ms) short of the database clock.

**Database cost.** One read per head change per process, whatever N is. Each new event is read and sent once per process. One connection is busy for the tail and only the laggards hold others.

**What it costs elsewhere.**
- The shared read starts from the lowest cursor it serves. It therefore returns a superset of what any filtered subscription needs, so the filtering moves into application CPU.
- Memory goes to the shared buffer or cache.
- A slow subscriber holds the others back unless the design detects it and evicts it to individual catch-up, as Axon's cleanup and EventStore's gap detection and `max_capacity` state do.
- Correctness now depends on the handover between shared delivery and private catch-up.
- In a multi-process deployment, each process makes its own single read, so the database serves one read per process rather than one per subscription.

### What the sources suggest combining

None of the systems above uses only one option. A reasonable reading of the sources is a combination of all three:

1. **A shared tail reader for subscriptions at or near the head.** This takes per-commit load from N reads to one. It follows the Commanded and Axon designs.
2. **A small shared semaphore for subscriptions that have fallen behind.** For example a value around Marten's default of 4, kept separate from and smaller than the connection pool. It covers subscriptions that leave the shared stream, start cold, or restart together.
3. **Jitter or a cooldown on catch-up entry and on wake-ups.** This matters after a deploy or failover, when hundreds of subscriptions begin catching up at once. Wake-ups are coalesced through one level-triggered flag, so a burst of commits produces one read per window rather than one per commit.

Rough cost per head change, with N subscriptions, L the concurrency limit and k new events:

| Approach | Reads per head change | Peak concurrent statements | Rows sent | Added latency |
|---|---|---|---|---|
| Unbounded individual reads | N | N | N·k | none, but contention at high N |
| Concurrency-limited | N | L | N·k | up to ⌈N/L⌉ × read time |
| Staggered or cooldown | N, or fewer under bursts | about N·read time / W | N·k, in bigger batches | about W/2 average |
| Shared read | 1 per process | 1 per process | k per process | in-memory dispatch only |

The figures are derived from the mechanisms the sources describe. None of the sources published a benchmark comparing these options on PostgreSQL. Marten's statement that limiting concurrent reads had "no measured throughput cost" is the only empirical data point. The measurements of connection and snapshot cost explain why the unbounded design degrades as N grows.
