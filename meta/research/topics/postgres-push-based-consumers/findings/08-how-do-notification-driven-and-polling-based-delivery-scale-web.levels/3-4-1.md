# After a failover to an asynchronously replicated standby, how can an event-store consumer detect that its persisted position refers to events lost with the old primary, and how should it re-synchronise?

## Question

When a PostgreSQL primary fails and an asynchronously replicated standby is
promoted, some committed events can disappear. How can a consumer of an event
table tell that its saved checkpoint position refers to events that no longer
exist, or to positions that now hold different events? And how should it get
back in step with the new primary without silently skipping or wrongly
dropping events?

## Findings

### What is lost, and what survives

PostgreSQL ships WAL after commit, so asynchronous streaming replication
always leaves a window for loss. The documentation says that if the primary
crashes, "some transactions that were committed may not have been replicated
to the standby server, causing data loss. The amount of data loss is
proportional to the replication delay at the time of failover". That delay is
"typically under one second" when the standby keeps up. Patroni, an HA
manager, bounds the worst case in asynchronous mode to `maximum_lag_on_failover`
bytes of WAL "plus the amount that is written in the last `ttl` seconds".

Three properties of physical replication shape how a consumer can detect the
loss:

1. **The promoted standby holds a consistent prefix of the old history.** A
   standby replays WAL in order, and "once the commit record for a transaction
   is replayed on the standby, the changes made by that transaction will be
   visible". After promotion, the new primary therefore holds every
   transaction whose commit record reached it and none after that point.
   Nothing is half-applied. The lost transactions form a suffix in **commit
   (WAL) order**. That is not necessarily a suffix in event-position order,
   because positions are allocated before commit and transactions can commit
   out of order.
2. **Promotion starts a new timeline.** "Whenever an archive recovery
   completes, a new timeline is created", along with a timeline history file
   that "shows which timeline it branched off from and when". The replication
   protocol exposes the current timeline (`IDENTIFY_SYSTEM`) and the history
   file (`TIMELINE_HISTORY`), including "the WAL location where the switch
   happened".
3. **The lost suffix is eventually destroyed.** When the old primary rejoins,
   `pg_rewind` uses the timeline histories to find "the point where they
   diverged". It then makes the old primary's data directory "analogous to a
   base backup of the source", which discards the changes made after
   divergence. Lost events can only be recovered from the old primary's data
   directory before it is rewound or rebuilt.

### Why a stored position alone cannot reveal the loss

Event positions usually come from a sequence or identity column, and sequences
are not transactional. PostgreSQL's source pre-logs 32 values per WAL record
(`SEQ_LOG_VALS`: "In the event of crash we can lose (skip over) as many values
as we pre-logged"). The documentation also warns that after a crash "it is
uncertain whether the sequence will have its original or updated state". It
advises that a value used outside the database should only be used after the
`nextval` call has committed.

Across an asynchronous failover, having committed on the old primary is not
enough. The following follows from the behaviour above; no source states it
outright:

- If the WAL record that advanced the sequence was never shipped, the new
  primary can **hand out the same position numbers again** to different
  events.
- If that record was shipped, the new primary skips ahead and the lost
  positions become an ordinary-looking gap.

The same reasoning applies to a feed ordered by transaction ID. The new
primary's next `xid8` is derived from the WAL it replayed, so IDs used only by
lost transactions can be assigned again. This is also inference: no source
states it directly.

This has three consequences for a consumer:

- A stored position **greater than the new head** proves loss, but only until
  new writes pass it.
- After that, the stored position may point to a different event (reuse) or to
  a gap. A consumer that resumes "after N" skips every new event written at a
  reused position at or below N. That is silent loss for the consumer, not
  just duplication.
- Idempotency keyed on **position** would discard the new events as
  duplicates. De-duplication must be keyed on a globally unique **event ID**.

### Exposure depends on where the checkpoint and its effects live

- **Checkpoint and effects in the same cluster and the same transaction**, as
  with an in-database projection. Both roll back together to the surviving
  prefix, so the consumer stays consistent and there is nothing to detect.
  This is the strongest reason to keep checkpoints in the event-store database
  and update them inside the handler's transaction.
- **Checkpoint in the same database, effects external** (HTTP calls, email,
  message brokers, another database). The checkpoint rolls back consistently,
  so surviving events are redelivered, which is ordinary at-least-once
  duplication. But the external effects of lost events remain as orphaned
  effects, and reused positions make event-ID de-duplication mandatory.
- **Checkpoint stored outside the cluster.** The checkpoint can be ahead of the
  new history or point at reused positions. This is the case that silently
  skips events, and it needs active detection.

A consumer that reads from a hot standby keeps its session when that standby
is promoted ("Sessions will remain connected while the server changes mode").
So checking only on reconnect is not sufficient for it. Such a consumer only
ever saw what that standby had replayed, so it is only at risk if a
*different* standby is promoted.

### Detection technique 1: event-ID fingerprints

This method needs no special privileges and works on every PostgreSQL
version:

- Store the event ID next to each checkpointed position.
- Keep a short window of recently processed `(position, event_id)` pairs as
  well, not just the last one.
- On every reconnection, and periodically for long-lived sessions, check the
  window: `SELECT position, id FROM events WHERE position = ANY(:positions)`.

A row that is missing, or that carries a different ID, signals divergence.
The consumer only stores positions of events it actually processed, so a
missing row cannot be explained by normal sequence gaps (unless the store
deletes or scavenges events). A whole window is needed because the lost set is
a suffix in commit order, not position order. Suppose event 10's transaction
commits after event 11's, and only 11 reached the standby. The last
fingerprint (11) still matches, but 10 is gone.

The window must cover events processed within the maximum replication lag at
failover plus the longest writer transaction. Under Patroni the lag is bounded
by `maximum_lag_on_failover` and `ttl`.

### Detection technique 2: timeline as an epoch (the Kafka KIP-320 pattern)

Kafka had the same problem with unclean leader election, where "we may lose
committed data". KIP-320 makes consumers store the **leader epoch** alongside
the committed offset. On a leader change, the consumer asks the new leader for
the end offset of that epoch (`OffsetsForLeaderEpoch`). It detects truncation
if "there exists a leader epoch which is larger than this epoch and begins at
an offset earlier than the committed offset". It then either resets to the
divergence point automatically or raises `LogTruncationException`. KIP-320
admits that after multiple consecutive unclean elections the exact offset may
not be recoverable, "but we should be able to get close".

The PostgreSQL analogue below combines the documented functions; no source
describes it as a consumer pattern. The timeline ID plays the role of the
epoch, and the timeline switch-point LSN plays the role of the epoch end
offset.

- **At read time**, record the current timeline with the checkpoint, plus an
  upper bound on the commit LSNs of everything read. The bound is
  `pg_current_wal_insert_lsn()`, taken inside the read transaction after the
  read. Every transaction visible to the read inserted its commit record
  before then.
- **Reading the timeline:**
  - On PostgreSQL 16 and later it is available from SQL:
    `(pg_split_walfile_name(pg_walfile_name(pg_current_wal_lsn()))).timeline_id`,
    because WAL file names embed the timeline. These functions cannot run
    during recovery, which is fine for consumers that read from the primary.
  - Alternatively, use `IDENTIFY_SYSTEM` over a replication connection.
- **On reconnect, if the timeline is unchanged**, no promotion has happened.
- **If it has changed**, read the history (via `TIMELINE_HISTORY`, or
  `pg_read_file` on the history file, which is superuser-only by default) to
  find where the recorded timeline ended. If the recorded upper bound is at or
  before the switch point, everything the consumer processed survived.
  Otherwise, fall back to fingerprint checks to identify exactly which events
  were lost.
- The bound is conservative: it can raise false alarms but never misses a
  loss.
- Follow the history chain if several promotions have happened.
- `system_identifier` does **not** change on failover, because a standby comes
  from a base backup of the same cluster. It only detects pointing at an
  entirely different cluster.

The cost is privilege and operational coupling, so this works best as a cheap
"nothing lost" fast path in front of technique 1.

### Re-synchronisation

1. **Choose a policy explicitly.** Follow KIP-320: support both automatic
   rewind and raising a typed divergence error that lists the lost event IDs.
   Raise by default for consumers with external side effects. Rewind
   automatically for rebuildable projections.
2. **Find the divergence point.** This is the earliest position in the
   verification window whose fingerprint fails, or that was reused by a new
   event. Rewind the checkpoint to just below it, not to the new head, because
   lost events are not position-contiguous.
3. **Replay forward with de-duplication on event ID** against the retained
   processed-ID window. Survivors that were already handled are skipped, and
   new events at reused positions are delivered.
4. **Compensate for the lost events.**
   - In-database effects need nothing; they have already rolled back.
   - Rebuildable external projections should be rebuilt from the divergence
     point, or have compensations applied for the lost IDs.
   - Irreversible side effects, such as messages already sent, must go to an
     operator for reconciliation.
   - The lost events themselves may be salvageable from the old primary
     before `pg_rewind` runs.
5. **If no divergence point can be established** (the window has aged out, or
   several failovers have happened), replay rebuildable projections from the
   start. Otherwise halt and alarm.

### Preventing the condition instead of repairing it

**Synchronous replication.** With synchronous replication, commits wait until
the standby has the commit record on disk (`on`) or has replayed it
(`remote_apply`). Loss then requires both servers to crash, and Patroni's
`synchronous_mode` "will not promote a standby unless it is certain that the
standby contains all transactions that may have returned a successful commit
status". Small windows remain:

- If the primary restarts while commits are waiting for acknowledgement, those
  commits complete on recovery, and "some transactions may not show as
  committed on the standby, even though they show as committed on the
  primary".
- Patroni warns that a backend cancelled while waiting for replication makes
  its changes visible to other backends unreplicated, "even when using
  `synchronous_mode_strict`".
- Non-strict synchronous mode accepts unreplicated writes when no standby is
  available.

So a consumer can still, rarely, process an event that a failover later
loses. Synchronous replication shrinks the window; it does not remove it.

**Durability-gated delivery.** Deliver an event only after it is known to be
on the failover candidates:

- **Logical slots, PostgreSQL 17 and later.** With `synchronized_standby_slots`,
  logical walsenders "send decoded changes to plugins only after the specified
  replication slots confirm receiving WAL", guaranteeing that failover slots
  "do not consume changes until those changes are received and flushed to
  corresponding physical standbys".
- **Table polling.** The analogous approach, which is an inferred design
  rather than a documented feature, is to hold back each batch until
  `pg_stat_replication.flush_lsn` for every promotable standby has reached the
  batch's recorded upper-bound LSN.
  - Reading those columns requires `pg_read_all_stats`.
  - It adds roughly one replication lag to delivery latency.
  - It must cover every standby the HA manager might promote.

For comparison, KurrentDB builds this into its own cluster. A write is
acknowledged only after "a majority of nodes in the cluster" have received it.
PostgreSQL leaves the equivalent guarantee to the HA layer or the application.

### Implications for a psycopg 3 event-store library

- Give every event a globally unique ID, and de-duplicate on it, never on
  position.
- Store checkpoints in the event-store database, transactionally with
  in-database effects, together with a bounded window of recent
  `(position, event_id)` fingerprints.
- Verify the fingerprint window on every reconnect, and periodically.
- On divergence, raise a typed error that carries the lost IDs and the safe
  rewind point, and let the subscription's policy choose rewind-and-replay or
  halt.
- Optionally add the timeline check as a fast path, and offer durability
  gating for consumers with irreversible external effects.
