# How can one dedicated psycopg 3 listener connection per process fan notifications out to many in-process consumers, and how should it sit beside a psycopg_pool pool so that LISTEN state never leaks into pooled connections?

## Question

How can a Python event-store library run one dedicated psycopg 3 connection per process that LISTENs on behalf of many in-process consumers, fanning each notification out to the consumers that care about it? And how should that connection relate to a `psycopg_pool` pool used for ordinary reads and writes, so that no pooled connection ever ends up with LISTEN registrations?

## Findings

### Short answer

Open the listener as a standalone `autocommit=True` connection built from the same connection parameters and `configure` hook as the pool, but never check it out of the pool. Give it exactly one owner, either an asyncio task or a thread. That owner loops over `notifies(timeout=...)` in short time slices. Between slices it applies queued LISTEN and UNLISTEN changes and runs a liveness probe. For each notification it calls a non-blocking wake-up (for example `asyncio.Event.set()`) on every subscriber registered for that channel. Subscriptions are reference-counted per channel. On every (re)connect the owner re-issues LISTEN for every registered channel and then wakes every subscriber so each one does a catch-up read. On the pool side, the main guarantee is architectural: nothing ever issues LISTEN through a pooled connection. A `reset` callback or a `pg_listening_channels()` assertion can serve as a defensive backstop. psycopg_pool does not clear session state by itself.

### Why LISTEN must never ride on a pooled connection

- **LISTEN is session state, and the pool does not reset session state.** PostgreSQL attaches LISTEN registrations to the session. They take effect at commit and are cleared only by UNLISTEN or when the session ends. When a connection comes back, psycopg_pool does four things: it commits or rolls back any open transaction, passes the connection to an optional application-supplied `reset` callback, discards it if it is broken or past `max_lifetime`, and otherwise returns it to the pool. Nothing in that sequence issues UNLISTEN. A LISTEN run inside `with pool.connection()` and committed on exit therefore stays on that physical connection for every later borrower. PostgreSQL's own session-scrubbing command, `DISCARD ALL`, includes `UNLISTEN *` in its expansion. That shows LISTEN is exactly the kind of state a pool must scrub explicitly.
- **psycopg buffers unread notifications without limit.** Every psycopg connection installs a libpq notify callback in its constructor. If no notify handler is registered, it appends each `Notify` to a per-connection `_notifies_backlog` deque, which has no `maxlen`. The deque is set to `None` only while a `notifies()` generator is running. A pooled connection that inherited a LISTEN, and is never read with `notifies()`, therefore accumulates every notification it parses. The psycopg maintainer described this exact pattern in issue #1091, "calling LISTEN on a connection and then … not reading the notifications using `conn.notifies()`", as the way to get a leak. The reporter saw about 200 MB per hour at more than 10,000 notifications per minute. Notifications are only parsed during connection operations such as queries, so a leaked pooled connection grows a little every time a borrower uses it. Nobody consumes those notifications.
- **A leaked listener can hold back the server-side queue.** PostgreSQL keeps one notification queue (8 GB by default) that cannot be cleaned up past a listening session that sits in a long transaction. Once the queue is full, every transaction that calls NOTIFY fails at commit. A pooled connection that is listening and is then borrowed for a long transaction becomes exactly such a session. `pg_notification_queue_usage()` exposes the fill fraction.
- **A listener monopolises its connection anyway.** In both the sync and async connection classes, `notifies()` holds the connection's `lock` for the whole life of the generator, including across each `yield`. The lock is a non-reentrant `threading.Lock` for the sync class and `asyncio.Lock` for the async class. A listener borrowed from the pool would never be available for other work, would shrink the pool's capacity for as long as it lives, and would escape `max_lifetime` and `drain()` recycling, because both act only when a connection is returned.

### Building the listener connection beside the pool

Create the listener with `connection_class.connect(conninfo, **kwargs, autocommit=True)` and run the pool's `configure` callback on it. Autocommit is what the psycopg docs recommend for timely notifications, and it makes each LISTEN take effect immediately. Procrastinate, a psycopg 3 task queue, does exactly this in `_get_standalone_connection()`: it resolves the pool's conninfo and kwargs, opens a separate `autocommit=True` connection of the pool's connection class, applies the pool's `configure` callback, and does all LISTEN work on that connection rather than on a pooled one.

One caution follows from that precedent. Since psycopg_pool 3.3, `conninfo` and `kwargs` may be callables that are evaluated at every connection attempt, for example to rotate credentials. Procrastinate copes by calling the pool's private `_resolve_conninfo()` and `_resolve_kwargs()` methods. An event-store library is more robust if it owns the connection-parameter source itself and passes the same value or callable both to the pool and to its listener factory, rather than relying on private pool internals.

### The single-owner loop under psycopg's locking rules

Because `notifies()` holds the non-reentrant connection lock across yields, three rules follow (inferred from the source):

- The loop body must not run queries on the listener connection. They would wait on a lock the generator already holds.
- Other tasks or threads cannot issue LISTEN on that connection while a generator is running. They block until the generator exits.
- Slow work in the loop body delays reading the socket.

The practical shape is therefore one owner that slices time:

1. Iterate `conn.notifies(timeout=slice)`. The `timeout` and `stop_after` parameters were added in psycopg 3.2. A `None` timeout waits indefinitely.
2. When the slice ends, run any pending LISTEN and UNLISTEN commands. LISTEN does not accept bind parameters, so compose channel names with `sql.SQL("LISTEN {}").format(sql.Identifier(channel))`. Then run a liveness probe. Procrastinate runs `SELECT 1` between slices and treats `OperationalError` as the signal to reconnect.
3. Re-enter `notifies()`.

Since psycopg 3.2.4 (issue #962), notifications that arrive while the generator is not running, for example during the LISTEN or the probe, are buffered and yielded first on the next `notifies()` call. Before 3.2.4, this slicing pattern silently lost notifications. That buffering holds only when **no** `add_notify_handler()` callback is registered on the connection. Since 3.2.10, mixing the two raises a `RuntimeWarning`, and notifications that reach a handler while the generator is off are not yielded by it. The listener connection should therefore use the generator alone, and the library should require psycopg 3.2.10 or newer.

Two other ways to apply subscription changes promptly are documented in other libraries:

- **River** (Go) queues listen and unlisten operations on an interrupt channel, cancels the in-progress wait, drains every queued operation, and then waits again.
- **Procrastinate** wraps each `__anext__()` of `notifies()` in `asyncio.wait_for(..., timeout)` and treats the timeout as the end of a slice. This predates the native `timeout` parameter, and it shows cancellation-based interruption working in practice.

Neither psycopg page fetched for this note documents cancellation semantics for an interrupted `notifies()`. The native `timeout` parameter is the documented route.

### Fan-out to in-process consumers

- **Registry.** Keep a map from each channel to the set of subscribers on it. The first subscriber to a channel triggers LISTEN and the last to leave triggers UNLISTEN. River does exactly this reference counting. Each subscriber's `subscribe()` should complete only once its LISTEN has executed on the listener. Only then should it read current state from its stored position. This follows PostgreSQL's documented rule: execute and commit LISTEN first, then inspect the database, then rely on notifications. A notification for a change the first read already saw is harmless.
- **Wake-ups, not payload delivery.** For an event store, a notification only needs to mean "re-read from your position". A per-subscriber `asyncio.Event` is ideal: `set()` never blocks, repeated sets coalesce while the consumer is busy, and the consumer clears it and queries from its last position. Procrastinate's worker uses exactly this pattern: its notification callback just calls `_new_job_event.set()`, and the fetch loop waits on that event, a stop event, or a polling timer, whichever fires first. If payloads must be delivered, use bounded queues with a non-blocking put and a drop-on-full policy, and back the drop with a re-read. River fans out through a 1,000-entry buffered channel and logs and drops notifications when it is full.
- **Thread boundaries.** asyncio primitives are not thread-safe. If the listener runs on its own thread (for example with a sync `psycopg.Connection`) while consumers run on an event loop, it must wake them with `loop.call_soon_threadsafe(event.set)`. Sync consumers should use `threading.Event` instead.
- **Elixir precedent.** Postgrex's `Notifications` process is the same design. One dedicated connection process serves many subscribers, each `listen()` returns a reference, and every subscribing process gets its own messages. Oban's Postgres notifier likewise runs on a connection separate from the application's Repo pool.

### Reconnect and catch-up

Notifications sent while the listener is disconnected are gone. Postgrex warns that they "are not queued and cannot be recovered", and recommends restarting the notifications process and subscribing again rather than trusting silent auto-reconnect. On every (re)connect, the owner should:

1. Snapshot the registry and issue LISTEN for every channel in it, as River does in `listenAndWait()`.
2. Wake every subscriber so each one re-reads from its own position.

Keep a slower fallback poll in each consumer's wait as a safety net. Procrastinate waits on its event or a `fetch_job_polling_interval` timer, whichever comes first (5 seconds by default).

### Illustrative asyncio sketch

```python
class Listener:
    # One per process; the only code that ever touches self._conn.
    async def run(self) -> None:
        while not self._stopping:
            try:
                async with await psycopg.AsyncConnection.connect(
                    self._conninfo(), **self._kwargs(), autocommit=True
                ) as conn:
                    for channel in list(self._subscribers):
                        await conn.execute(listen_sql(channel))
                    self._wake_everyone()                  # catch-up after (re)connect
                    while not self._stopping:
                        async for n in conn.notifies(timeout=self._slice):
                            for event in self._subscribers.get(n.channel, ()):
                                event.set()                # never await consumer work here
                        await self._apply_pending(conn)    # LISTEN or UNLISTEN, then resolve subscribe() futures
                        await conn.execute("SELECT 1")     # liveness probe
            except psycopg.OperationalError:
                await asyncio.sleep(self._backoff())
```

### Defensive guards on the pool side

- **Prefer structure over cleanup.** Expose LISTEN only through the listener API, so that no code path can call it on a pooled connection.
- **Optional `reset` callback.** A `reset` callback receives each returned connection in idle state and must leave it idle, or the pool discards it. It could run `UNLISTEN *` followed by a commit when the pool's connections are not in autocommit mode, since UNLISTEN, like LISTEN, takes effect at commit. `DISCARD ALL` cannot run inside a transaction block. To drop notifications psycopg has already buffered on the client side, call `list(conn.notifies(timeout=0))`, which the maintainer suggested for clearing the backlog. This costs at least one extra round trip on every return.
- **Cheaper check for tests or debug builds.** Assert in the reset or `check` callback that `pg_listening_channels()` returns no rows.
- **Recovering a pool that is already contaminated.** psycopg_pool 3.3's `drain()` replaces every pooled connection. Connections currently checked out are closed when they are returned.
