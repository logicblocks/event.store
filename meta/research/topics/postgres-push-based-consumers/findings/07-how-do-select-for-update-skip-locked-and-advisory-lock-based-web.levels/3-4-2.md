# How can a psycopg 3 consumer promptly detect that the connection holding its advisory lock or open handler transaction has been lost, using libpq keepalives, TCP user timeout or server-side timeouts, and what settings balance false positives?

## Question

A consumer that claims work with a session-level advisory lock, or by holding a
row lock inside an open handler transaction, depends on one TCP connection
staying alive. How can a psycopg 3 consumer find out quickly that this
connection is gone? The candidate tools are libpq keepalives, the TCP user
timeout, and PostgreSQL's server-side timeouts. Which settings detect real
failures fast without killing healthy connections?

## Findings

### Two parties have to notice, and they use different timers

Lock ownership ends on the **server**. A session-level advisory lock "is held
until explicitly released or the session ends", and transaction-level locks
"are automatically released at the end of the transaction" (PostgreSQL
explicit-locking docs). A takeover consumer can only acquire the lock once the
**backend** decides its client is gone. The old owner learns it has lost the
lock only when the **client** side of the socket fails. These are two
independent detection clocks.

Clean failures are not the problem. When a process dies on a live host, its
kernel closes the socket, and when the server shuts down, the client sees the
socket close. The slow cases are the silent ones: a host crash, a network
partition, a NAT or firewall dropping state, or a proxy in the middle. With
default Linux settings these take a long time to detect:

- **Idle connection.** Keepalive probing starts only after `tcp_keepalive_time`
  of 7200 s. Detection then takes "approximately an additional 11 minutes (9
  probes an interval of 75 seconds apart)" (tcp(7)).
- **Connection with unacknowledged data.** Here `tcp_retries2` (default 15)
  applies, which "corresponds to a duration of approximately between 13 to 30
  minutes" (tcp(7)). Cloudflare measured 924.6 s as the lower bound.
- **Server side.** By default the server "will detect the loss of the
  connection only at the next interaction with the socket" (PostgreSQL
  `client_connection_check_interval` docs).

### The mechanisms and what each one can and cannot see

| Mechanism | Side | Detects | Blind spot | False-positive risk |
|---|---|---|---|---|
| libpq `keepalives`, `keepalives_idle`, `keepalives_interval`, `keepalives_count` | client | A silent peer while the socket has nothing unacknowledged: an idle LISTEN or lock-holding connection, or one waiting for a query result | No probes are sent while data is unacknowledged, because "the send buffer must be empty" (Cloudflare). A proxy that answers probes itself hides server loss | Low. The peer's kernel answers probes, so pauses in the application do not trigger it. Aggressive values can cut connections during transient packet loss |
| libpq `tcp_user_timeout` (PG 12+) | client | Data that stays unacknowledged, or buffered data that "may remain untransmitted (due to zero window size)" (tcp(7)) | Not available on Windows. Does nothing while no data is in flight. Never fires behind a proxy that acknowledges the data | Medium. If set below the keepalive budget, it cuts probing short. It also counts zero-window time, so it can kill a peer that is alive but has stopped reading |
| Server `tcp_keepalives_idle`, `_interval`, `_count`, `tcp_user_timeout` | server | The same as the client equivalents, from the backend's side. This is what actually ends the session and frees its locks | `tcp_keepalives_count` and `tcp_user_timeout` are not supported on Windows | Same as the client equivalents |
| `client_connection_check_interval` (PG 14+) | server | A dead client while a query is running, for example a session blocked in `pg_advisory_lock()` or in a long handler statement | Only reports a connection "if the kernel reports that the connection is closed", so it still needs keepalives to catch partitions. Runs only on Linux, macOS, illumos and BSD | Low. It polls the socket and does not judge latency |
| `idle_in_transaction_session_timeout` | server | A client that is alive but stuck, which kernel keepalives can never catch. Terminates the session | None for this case | High for handler transactions. While the Python handler works between statements, the server sees the session as idle in transaction |
| `transaction_timeout` (PG 17+) | server | Any transaction that outlives a hard cap. Terminates the session | Does not apply to prepared transactions | High if set below the longest legitimate handler |
| `idle_session_timeout` (PG 14+) | server | An idle session outside a transaction | — | Would kill a healthy holder of a session advisory lock that is merely idle. The docs warn against using it with poolers |

The interaction between keepalives and `TCP_USER_TIMEOUT` decides how these
settings should be tuned. On Linux, "when used with the TCP keepalive
(SO_KEEPALIVE) option, TCP_USER_TIMEOUT will override keepalive to determine
when to close a connection due to keepalive failure" (tcp(7)). Cloudflare
measured this and found that "with TCP_USER_TIMEOUT set, the TCP_KEEPCNT is
totally ignored". It recommends setting **TCP_USER_TIMEOUT to
`TCP_KEEPIDLE + TCP_KEEPINTVL * TCP_KEEPCNT`**. That gives one detection budget
for both an idle socket and a socket with data in flight, and the user timeout
never cuts the probe sequence short. Keepalives and the user timeout are
complementary, not alternatives. Keepalives cover the idle and waiting states.
The user timeout covers sends that hang, such as a heartbeat, a `COMMIT` or a
checkpoint write sent into a partition, which would otherwise wait out
`tcp_retries2`.

All of these TCP parameters "are ignored for connections made via a
Unix-domain socket". Local connections never have a network partition, so
process death closes the socket promptly anyway.

### Applying this in psycopg 3

- **Passing settings.** psycopg passes extra keyword arguments to
  `connect()` through as libpq connection parameters. For example,
  `keepalives=1, keepalives_idle=10, keepalives_interval=5,
  keepalives_count=3, tcp_user_timeout=25000` sets the client side. The server
  parameters `tcp_keepalives_*`, `tcp_user_timeout` and
  `client_connection_check_interval` all have **user** context
  (postgresqlco.nf). That means the consumer can set them for its own session
  through the libpq `options` parameter (for example
  `options="-c tcp_keepalives_idle=15 -c client_connection_check_interval=5000"`)
  or through `ALTER ROLE`. It does not need to change `postgresql.conf` for the
  whole cluster.
- **How a loss shows up.** A failure surfaces as `psycopg.OperationalError` on
  the next operation, and the connection's `broken` flag becomes true ("a
  broken connection is always closed"). A broken connection cannot be reused,
  so it cannot silently reconnect to a new session. As a result, a successful
  round trip on a connection that has never been reconnected is evidence that
  the same backend, and any session-level lock it holds, still exists. Since
  psycopg 3.2.4, a disconnection caused by the server raises the specific
  error, such as `IdleInTransactionSessionTimeout` or `AdminShutdown`, rather
  than a generic `OperationalError`.
- **Detecting without polling.** psycopg's docs recommend waiting for the
  operating system to signal that the socket is readable: `selectors` on
  `conn.fileno()` in sync code, or `loop.add_reader()` in asyncio. The consumer
  runs `SELECT 1` only when that happens and catches `OperationalError`. The
  docs advise against a loop of `SELECT 1` queries. When a keepalive or user
  timeout fires, the socket becomes readable with an error, so this pattern
  picks up the kernel's verdict immediately.
- **LISTEN connections.** Since psycopg 3.2, `notifies(timeout=…,
  stop_after=…)` lets the listen loop wake up periodically. Notification
  handlers registered with `add_notify_handler()` run "only during a connection
  operation, such as a query". So a periodic wake-up plus a cheap round trip
  doubles as a heartbeat.
- **Serialised connections.** psycopg serialises all queries on one connection
  ("only one cursor at time will be able to run a query on the same
  connection"). A heartbeat on the handler's own connection therefore queues
  behind the handler's statements and shares its transaction. Heartbeats belong
  on a dedicated lock-holding or LISTEN connection, or between handler
  statements. For a handler connection that is mid-statement, the server's
  `client_connection_check_interval` and the client keepalives do the
  detecting.
- **Bounding heartbeats in asyncio.** An async heartbeat can be bounded with
  `asyncio.wait_for`, but this used to be unsafe against a server that stopped
  responding. psycopg issue #1371 reported that cancelling a task blocked on
  such a server "is swallowed forever". psycopg 3.3.6 fixed this ("Don't wait
  forever for a query to terminate after interrupting it … The fix requires
  libpq 17 or newer"). `cancel_safe()` likewise needs libpq 17. On older
  versions, the client's `tcp_user_timeout` is what bounds such a hang.

### Middleboxes defeat transport-level detection

Issue #1371 also describes a structural limit. When a proxy or load balancer
"keeps the client side alive after losing its server side", "keepalive probes
are answered by the middlebox" and "tcp_user_timeout never fires because
nothing sent is left unack'd". Client keepalives only cover the hop to the
proxy. Behind a proxy, only an **application-level round trip with a
deadline** proves the server session is alive end to end.

PgBouncer adds two more effects:

- **Its own timers.** PgBouncer has its own `tcp_keepalive`, `tcp_keepidle`,
  `tcp_keepintvl`, `tcp_keepcnt` and `tcp_user_timeout` settings. By default
  these use operating-system behaviour, which on Linux is 7200, 75 and 9.
- **Lock release on disconnect.** In session mode, a server connection is
  "released back to pool after client disconnects" after running
  `server_reset_query`, which defaults to `DISCARD ALL`. `DISCARD ALL` includes
  `SELECT pg_advisory_unlock_all()` and `UNLISTEN *`. So a consumer's
  session-level lock is freed only when PgBouncer itself notices that the
  client has gone.

A session-level lock belongs to one server session. Only session pooling keeps
that session bound to a single client.

### Settings that balance prompt detection against false positives

The following is a synthesis of the sources above, not a single vendor's
prescription.

1. **The client should detect loss before the server releases the lock.** If
   the client's detection budget is shorter than the server's, the old owner
   usually learns it has lost the lock before a new owner can take it. For
   example:
   - Client: `keepalives_idle=10`, `keepalives_interval=5`,
     `keepalives_count=3`, `tcp_user_timeout=25000`, about 25 s in total.
   - Server, per session: `tcp_keepalives_idle=15`,
     `tcp_keepalives_interval=5`, `tcp_keepalives_count=5`,
     `tcp_user_timeout=40000`, about 40 s in total.

   This only narrows the window. During a partition the two clocks cannot
   coordinate, and side effects already under way are not stopped, so fencing
   is still needed.
2. **Choose the detection budget against the takeover delay you can accept.**
   For context, AWS's fast-failover guidance for Aurora uses idle 1 s, interval
   1 s and count 5, which detects loss in about 5 s. CYBERTEC gives 60 s idle,
   5 s interval and 3 probes, which detects in a little over a minute. AWS adds
   that on networks where probes are often dropped, "you can set a higher
   `tcp_keepalives_count` value". In other words, absorb packet loss with more
   probes rather than a longer interval. Kernel probes are immune to pauses in
   Python itself (the GIL, garbage collection, long handlers). That makes it
   safe to tune them much more aggressively than an application heartbeat,
   whose deadline must exceed the worst-case stall of the event loop.
3. **Keep `tcp_user_timeout` equal to idle + interval × count, on both sides.**
   A smaller value cuts probing short. It also kills peers that are alive but
   not reading once the zero-window time exceeds the timeout. A LISTEN
   connection whose notifications go undrained while a handler runs is one
   example. Drain notifications on their own connection or task.
4. **Treat server application timeouts as backstops sized from handler
   durations, not as liveness probes.** Set `idle_in_transaction_session_timeout`
   for the handler role or session comfortably above the longest legitimate
   handler. It is the only mechanism listed here that catches a client that is
   alive but stuck. Add `transaction_timeout` (PG 17) as a hard upper cap. If
   it is less than or equal to `idle_in_transaction_session_timeout` or
   `statement_timeout`, "the longer timeout is ignored". Do not apply
   `idle_session_timeout` to a session that holds a lock while idle, unless it
   sends heartbeats more often than the timeout.
5. **Turn on `client_connection_check_interval`** (for example, a few seconds)
   for consumer sessions. A backend that is executing or waiting on a lock when
   its client vanishes then exits at the next check instead of when it finally
   tries to send results.
