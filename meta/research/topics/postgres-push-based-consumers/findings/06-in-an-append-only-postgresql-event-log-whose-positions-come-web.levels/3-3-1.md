# How can a Python event-store consumer hand off from catching up by reading the event table to tailing a logical replication slot without gaps or duplicates, using the slot's exported snapshot and commit LSNs as its checkpoint?

## Question

When a consumer of an append-only PostgreSQL event table switches from reading the table directly to tailing a logical replication slot, how can it make the switch with no gaps and no duplicates? The approach in question uses the snapshot the slot exports when it is created as the boundary between the two phases, and commit LSNs as the consumer's checkpoint. Which Python clients can do this?

## Findings

### Short answer

PostgreSQL provides this handoff itself. When a logical slot is created over the streaming-replication protocol, the server returns the LSN at which the slot became consistent (`consistent_point`) and a snapshot that matches that point exactly. The documentation says the exported snapshot "will show exactly the state of the database after which all changes will be included in the change stream". You can read the database's state through that snapshot and then apply the slot's contents "without losing any changes". So:

1. Create the slot and keep its snapshot.
2. Read the event table in that snapshot.
3. Record `consistent_point` as the checkpoint.
4. Stream from the slot.

Each transaction then reaches the consumer exactly once, either in the table read or in the stream. From then on the checkpoint is the end LSN of the last transaction the consumer has durably processed. On restart, the server skips every transaction whose commit record starts before that LSN. Python is the hard part. Psycopg 3 cannot stream the replication protocol, so the streaming side needs psycopg2's replication support or another client.

### Why the exported snapshot gives an exact boundary

The slot's snapshot builder moves through START, BUILDING_SNAPSHOT, FULL_SNAPSHOT and CONSISTENT. It reaches CONSISTENT only after every transaction that was running when the slot was created has committed or aborted. Its source comment says: "Only transactions that commit after CONSISTENT state has been reached will be replayed … That ensures that we'll reach a point where no previous changes has been exported, but all the following ones will be."

The snapshot is built from commit records in the WAL. A transaction counts as committed if the builder has seen its commit record, even if the transaction has not yet left the proc array. This is why the exported snapshot lines up with the decoding start point. A snapshot taken separately and paired with a separately read WAL position, such as `pg_current_wal_lsn()`, has no such guarantee. That last point is an inference from the snapbuild.c comment, not a statement in the documentation.

Creating a slot therefore waits for transactions that are already running, including long ones. Creating a logical slot on a standby may take a noticeable time if the primary is idle.

### Handoff procedure, variant A: export and import across two connections

1. Open a replication connection (`replication=database`). It accepts replication commands and ordinary SQL, but only over the simple query protocol.
2. Run `CREATE_REPLICATION_SLOT events_consumer LOGICAL pgoutput (SNAPSHOT 'export')`. `'export'` is the default and cannot be used inside a transaction block. The single result row contains `slot_name`, `consistent_point`, `snapshot_name` and `output_plugin`.
3. Send nothing else on that connection for now. The documentation says the snapshot "is valid until a new command is executed on this connection or the replication connection is closed". The walsender comments add that the importing side checks that the exporting transaction is still open, so its xmin horizon has not advanced.
4. On an ordinary connection (psycopg 3 works here), run `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`, then `SET TRANSACTION SNAPSHOT '<snapshot_name>'`. This must come before the transaction's first query, and the transaction must be REPEATABLE READ or SERIALIZABLE. Then read the event rows the consumer has not yet processed, in position order, and deliver them.
5. When the catch-up read is done, durably record the checkpoint as `consistent_point`, then commit.
6. Issue `START_REPLICATION SLOT events_consumer LOGICAL <consistent_point> (proto_version '1', publication_names 'events_pub')`. The publication covers the event table. Leave `streaming` at its default of `off`, so only committed transactions arrive, each framed by a Begin and a Commit message.

### Handoff procedure, variant B: one connection with `SNAPSHOT 'use'`

On the replication connection, start a REPEATABLE READ, read-only transaction and make `CREATE_REPLICATION_SLOT … (SNAPSHOT 'use')` its first command. The walsender enforces each of these conditions and rejects the command inside a subtransaction. The slot's initial snapshot then becomes the current transaction's snapshot. Read the table with simple-protocol queries on the same connection, commit, then run `START_REPLICATION`.

PostgreSQL's own logical-replication table-sync worker works this way:

1. It creates a permanent slot with `CRS_USE_SNAPSHOT`, "so tell it to use the snapshot to make the final data consistent".
2. It copies the table.
3. It advances its replication origin to the LSN returned by slot creation.
4. It streams the changes made during the copy until it reaches the main apply worker's position, then hands back control.

The pgcopydb tool follows the same pattern for `clone --follow`. It creates the slot "before the initial COPY, using the same Postgres snapshot", reuses that snapshot through `SET TRANSACTION SNAPSHOT`, and fetches changes during the copy so WAL does not pile up on the source.

### Commit LSNs as the checkpoint

- **What each message carries.** A pgoutput Begin message carries the transaction's final LSN, commit timestamp and xid. A Commit message carries "the LSN of the commit" and "the end LSN of the transaction". Transactions are decoded in commit order, and rolled-back transactions are never decoded. Only commits already flushed to disk are decoded, so with `synchronous_commit = off` a commit can show up slightly later.
- **Which LSN to store.** Store the Commit message's end LSN. When decoding restarts, a transaction is skipped if the start of its commit record is before the start point: `SnapBuildXactNeedsSkip` returns `ptr < start_decoding_at`. Restarting at the stored end LSN therefore skips the last processed transaction. Storing the commit LSN instead (the start of the commit record) would not satisfy the strict `<`, so that transaction would be sent again. This is my reading of the source code. It agrees with PostgreSQL's apply worker, which records `commit_data->end_lsn` both as its replication-origin LSN and as the flush position it reports back.
- **Restarting.** `START_REPLICATION` begins at the requested LSN or the slot's `confirmed_flush_lsn`, whichever is greater. The documentation warns that this "might not catch certain kinds of client errors", so the client should check `confirmed_flush_lsn` against its own checkpoint before starting. A slot's position is persisted only at checkpoint, so after a server crash the slot can go back and resend changes. The documentation tells clients to record the last LSN they saw and either skip repeated data or ask decoding to start from that LSN.
- **Rules that rule out gaps and duplicates:**
  - Persist the end-LSN checkpoint atomically with the consumer's side effects.
  - Always restart by requesting that LSN.
  - Report a flushed position to the server (in a standby status update, or psycopg2's `send_feedback(flush_lsn=…)`) only once it is durably checkpointed. The server may discard everything before the reported position.
  - If `confirmed_flush_lsn` is ever ahead of the stored checkpoint, the slot has passed data the consumer never made durable. Treat that as a gap and re-bootstrap. (Inference.)
- **Advancing while idle.** Since PostgreSQL 15, pgoutput no longer sends empty transactions. A slot on an event table in a busy database therefore receives mostly keepalives. PostgreSQL's apply worker raises its received position from each keepalive's WAL end. When it has no pending transactions, it reports that received position as flushed, which stops the slot from holding WAL. A consumer that does the same should also persist that advanced LSN, so the `confirmed_flush_lsn` check above does not report a false gap.
- **Atomic checkpoints in the same database.** If the consumer writes its results to the same PostgreSQL database, it can write the end LSN to a checkpoint row in the same transaction. Alternatively it can use replication origins: `pg_replication_origin_session_setup` plus `pg_replication_origin_xact_setup(end_lsn, commit_ts)` per transaction. This makes progress "persist in a crash safe manner" without updating a row for every transaction. On restart, `pg_replication_origin_progress(name, true)` returns the LSN to resume from.

### Ordering consequences and failure modes

- **Positions stop being a watermark.** The catch-up phase delivers in position order inside one snapshot, and the stream then delivers in commit order. A transaction that reserved a lower `BIGSERIAL` position before the snapshot but committed after it arrives through the stream after higher positions have been delivered. This is correct and gap-free, but once the consumer has switched to the slot, position must not be used as a skip-watermark. (Inference.)
- **A crash during catch-up loses the snapshot.** The exported snapshot lives only in the open transactions, so it does not survive. You can drop and recreate the slot and repeat the catch-up, but that is only safe if catch-up processing is idempotent, for example deduplicating on event ID. Resuming "after position p" under a new snapshot can miss lower-positioned events that committed late. (Inference.)
- **WAL retention and invalidation.** A slot keeps WAL and catalog rows while the catch-up runs and whenever the consumer is down. `max_slot_wal_keep_size` or `idle_replication_slot_timeout` can invalidate it: `pg_replication_slots.wal_status = 'lost'`, with an `invalidation_reason` such as `wal_removed` or `idle_timeout`. After that the consumer must re-bootstrap.
- **Rejected alternative: Debezium's offset model.** Debezium's PostgreSQL connector reads the server's current WAL position inside its snapshot transaction and streams from that position afterwards. Its offsets are LSNs and it re-sends from the last recorded offset after a restart. That is at-least-once delivery, not the exact boundary the exported snapshot provides.

### Python client support

- **Psycopg 3 cannot stream.** The issue "Add support for streaming replication as in psycopg2" (psycopg 3 issue #71, opened August 2021) is still open, with no linked work.
  - Psycopg 3's `ClientCursor` always uses the simple query protocol, so it can probably run `CREATE_REPLICATION_SLOT` and fetch the snapshot row on a `replication=database` connection. I have not verified this.
  - It does not implement the COPY-both stream that `START_REPLICATION` needs.
- **Psycopg2 can stream.** It provides `LogicalReplicationConnection`, `start_replication(slot_name, start_lsn, options, decode, status_interval)`, `consume_stream` and `send_feedback(write_lsn, flush_lsn, apply_lsn, reply, force)`. Its `create_replication_slot` helper builds `CREATE_REPLICATION_SLOT name LOGICAL plugin` with no snapshot option, so the server's default (export) applies. The helper returns nothing, so the consumer must fetch the result row itself, or execute the command text directly with an explicit `SNAPSHOT` option.
- **A practical split:** psycopg2 (or a separate decoder process) for slot creation and streaming, psycopg 3 for the snapshot-import catch-up and the checkpoint writes.
- **The SQL-function path has no exact boundary.** `pg_create_logical_replication_slot` returns only `(slot_name, lsn)` and exports no snapshot. A consumer limited to SQL functions such as `pg_logical_slot_get_changes` therefore cannot get an exact boundary. The best it can do is create the slot first, then read the table in a later snapshot. That deliberately overlaps the two phases, and the consumer drops duplicates by event identity. The snapbuild.c comment notes that a transaction's commit record can be in the WAL before the transaction has left the proc array. So even this ordering does not formally guarantee that an ordinary snapshot taken right after slot creation includes every transaction the slot treats as already committed. (Inference.)
