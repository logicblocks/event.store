# How should an event store consumer that receives events in commit order from a logical slot checkpoint its progress, by commit LSN or by event position, so that catch-up reads from the events table and slot resumption agree without gaps or duplicates?

## Question

A consumer reads events from a PostgreSQL logical replication slot, which delivers transactions in commit order. It sometimes also catches up by reading the events table directly. Should it record its progress as a commit LSN (a position in the write-ahead log, or WAL) or as the event's position in the table? And how can the table reads and the slot resumption be made to agree, so that no event is skipped and none is handled twice?

## Findings

### Short answer

The slot can only resume from an LSN. The right LSN to store is the **end LSN of the last transaction the consumer fully processed**. PostgreSQL's own logical replication subscriber stores exactly this value. An event's position can serve as a checkpoint shared by table reads and slot resumption **only if positions are assigned in commit order**, which means appends must be serialised. In that case the consumer should store both values in one transaction:

- the position is the authority for gap-free table reads and for dropping duplicates;
- the LSN is where the slot resumes from and what the consumer confirms back to the server.

If positions come from an ordinary sequence with no serialisation, a position checkpoint cannot be reconciled with the slot. The consumer must then track the slot by LSN alone and switch between the table and the slot only at the boundary given by a slot's exported snapshot.

### What the slot's coordinates mean

The output-plugin documentation states that "concurrent transactions are decoded in commit order, and only changes belonging to a specific transaction are decoded between the `begin` and `commit` callbacks". Rolled-back transactions are never decoded. In the built-in `pgoutput` protocol:

- the Begin message carries the transaction's final LSN, its commit timestamp and its 32-bit xid;
- the Commit message carries "the LSN of the commit" (where the commit record starts) and "the end LSN of the transaction".

Debezium's resume logic is built on the consequence of commit-order delivery: "only the LSNs of transaction commits are ordered globally. The LSNs of changes are ordered only within their respective transaction." A single change's LSN, or a Begin's LSN, therefore cannot serve as a global cursor.

**How resumption works.** `START_REPLICATION SLOT … LOGICAL X/X` starts "at either WAL location XXX/XXX or the slot's `confirmed_flush_lsn`, whichever is greater". Inside the decoder, `DecodeCommit` passes the start LSN of the commit record (`buf->origptr`) to `SnapBuildXactNeedsSkip`. That function returns `ptr < builder->start_decoding_at`. So a transaction is skipped exactly when its commit record **starts** before the resume point. This has three practical consequences:

- **Storing T's end LSN** skips T on resume, and delivery continues with the next transaction. No gap and no duplicate.
- **Storing T's commit LSN** (the start of the record) is not "less than" the resume point, so the whole of T is sent again.
- **Storing any change LSN inside T**, or any lower LSN, also resends T in full.

Checkpointing too low therefore only causes duplicates. Checkpointing too high, past work that was not durably processed, loses events.

**Which LSN the client sees.** In `logical.c` the commit callback sets the message's write location to `txn->end_lsn` ("points to the end of the record"). The begin callback uses `txn->first_lsn`, and change callbacks use `change->lsn`. So the WAL start point in the XLogData header of the Commit message is already the end LSN. In psycopg2 this is exposed as `ReplicationMessage.data_start`.

**PostgreSQL's own design.** The apply worker:

1. checks that the Commit's `commit_lsn` equals the Begin's final LSN;
2. sets `origin_lsn = commit_data->end_lsn` and commits it in the same local transaction as the applied changes;
3. reports progress with `store_flush_position(commit_data->end_lsn, XactLastCommitEnd)`.

The replication-origins chapter explains why: recording the source LSN per transaction makes "replication progress … persist in a crash safe manner". An event store consumer should copy this pattern. It should write the end LSN into its checkpoint row in the same database transaction as the projection's side effects. After that transaction commits, and only then, it should send `flush_lsn`. psycopg2 documents `flush_lsn` as a position before which "the server is allowed to discard all and every data".

**The consumer's stored LSN must be the authority, not the slot's.** A slot's position "is persisted only at checkpoint, so in the case of a crash the slot might return to an earlier LSN". The documentation tells clients to "record the last LSN they saw … and skip over any repeated data or … request that decoding start from that LSN". `pg_replication_slot_advance` carries the same warning. In the other direction, `confirmed_flush_lsn` is defined so that "data corresponding to the transactions committed before this LSN is not available anymore". If the slot's `confirmed_flush_lsn` is ahead of the consumer's stored LSN, the server will silently start at the later point. The protocol documentation therefore suggests checking `confirmed_flush_lsn` before issuing `START_REPLICATION`. A consumer that finds the slot ahead of its own checkpoint has lost events. It should treat this as fatal and rebuild from the table, not carry on.

**Partially processed transactions.** One stored LSN is enough only if the consumer checkpoints whole transactions. If it checkpoints after each event, it needs a composite checkpoint, as Debezium does:

- the end LSN of the last complete transaction, plus
- the commit LSN of the transaction in progress and the last event handled within it.

On restart, the partly handled transaction is resent in full, because its commit record lies beyond the stored end LSN. Within one transaction, changes arrive in execution order, so the event's position is a safe key for skipping the prefix that was already handled. If the transaction was never located, Debezium's `WalPositionLocator` replays it "from the start of transaction".

**In-progress streaming.** The `stream_*` callbacks for large in-progress transactions send changes before the transaction commits, and that transaction may still abort. A consumer should either leave streaming off or buffer until Stream Commit, which carries the same commit and end LSNs. It should checkpoint only at commit.

### Why event positions do not line up with commit order

A sequence value becomes visible to other sessions as soon as `nextval` is called, and it is never rolled back. So if transaction 2 draws a later id but commits before transaction 1, a reader that advances to the highest id it has seen "will lose the events created by transaction #1". Sequin describes the same failure for cursor pagination over serial ids.

Marten works around it with a "high water mark": the highest sequence number up to which every event is known to be safe. Gaps hold the mark back until no live transaction could still fill them. Once a configured timeout passes, though, it skips on suspicion, and "an append that commits inside the skipped range will never be projected".

For a consumer reading the slot, this means positions arrive **out of numeric order**. A checkpoint of "highest position seen" fails both ways:

- a table catch-up of `position > checkpoint` skips a lower-numbered event that committed later;
- a duplicate filter that drops anything with `position <= checkpoint` throws that same event away when it arrives from the slot.

A transaction also cannot write its own commit LSN into the rows it inserts, because that LSN does not exist until the commit record is written (this follows from how commit works; no source states it directly). So the table cannot be queried by commit LSN.

The safe read rule on the table side is to store `pg_current_xact_id()` (`xid8`) on each event. The reader then reads `(transaction_id, id) > (last_txid, last_id)` and only rows where `transaction_id < pg_snapshot_xmin(pg_current_snapshot())`. This works because every xid below `xmin` is "either committed and visible, or rolled back and dead".

This gives a gap-free order, but it is ordered by when each transaction obtained its xid, not by commit order. The snapshot's in-progress list shows that a transaction with a higher xid can have committed while a lower one is still running. The result is a third ordering, distinct from both position and commit LSN. The Begin message does carry the xid, so slot events can be matched to xids, but sorting by xid cannot reproduce commit order. Note also a constraint of the `xmin` rule: Sequin points out that one long-running transaction on any table stalls it.

### Design 1: make positions follow commit order and store position plus LSN

Suppose every append takes a lock that serialises how global positions are handed out, and holds that lock until commit. This could be a transaction-scoped advisory lock or a row lock on a counter. In `CommitTransaction`, PostgreSQL first writes the commit record, then calls `ProcArrayEndTransaction`, which makes the transaction visible. The source requires this "be done _before_ releasing locks we hold and _after_ RecordTransactionCommit". So the next appender cannot take positions until the previous transaction is both in the WAL and visible. Position order then equals commit-LSN order and visibility order. Any reader that sees position *p* also sees every committed lower position. The only remaining gaps come from aborted transactions, and those are permanent. (This is reasoning from the source code, not a documented guarantee.)

With commit-ordered positions:

- **Checkpoint.** Store `(position, end_lsn)` in the same transaction as the side effects.
- **Table catch-up.** Read `position > checkpoint`. No `xmin` guard or high water mark is needed.
- **Slot resumption.** Start from the stored end LSN, or any earlier LSN the slot still retains. Drop events with `position <= checkpoint` as duplicates. This is now exact, because positions arrive in increasing order.
- **Switching modes.** No coordination is needed. The consumer can catch up from the table, then resume the slot at its last stored LSN and let the position filter discard the overlap. The one rule is that the slot must never be confirmed past the LSN of the last transaction whose position has been checkpointed. If it is, the WAL needed to fill the gap is released.

The cost is serialised appends; Sequin notes that batching inserts under a serialised writer improves throughput. There is also a durability argument for keeping the position as the main checkpoint: an LSN is a location in one cluster's WAL history, while a position stored in the table survives a dump and restore (this is inference).

### Design 2: unserialised positions, LSN checkpoint, hand over at an exported snapshot

While consuming the slot, the consumer checkpoints the end LSN, plus the composite described above if it needs per-event progress. The position then serves only as an idempotency key for individual events, never as a cursor.

Moving from table reads to the slot happens, for example, for a new consumer, a rebuilt projection, or a slot that was dropped or invalidated. In that case, create the slot with `CREATE_REPLICATION_SLOT … LOGICAL … (SNAPSHOT 'export')`, or with `'use'` inside the reading transaction. The command returns a `consistent_point`, "the earliest location from which streaming can start". It also returns a snapshot that "will show exactly the state of the database after which all changes will be included in the change stream". The documentation says a dump taken under it "afterwards can be updated using the slot's contents without losing any changes". `snapbuild.c` explains that only transactions committing after the consistent state "will be replayed … which is why we export a snapshot at that point".

The procedure:

1. Read the events table under `SET TRANSACTION SNAPSHOT`, in any order, because the set of visible rows is fixed.
2. Set the checkpoint to `consistent_point`.
3. Stream from there.

No duplicate filtering is needed.

Do not build this pairing by hand from `pg_current_wal_lsn()` and a fresh snapshot. A transaction's commit record is written before it leaves the procarray, the shared list of running transactions. `snapbuild.c` notes that decoded commits "can't be considered committed in a regular MVCC snapshot" until they leave it. Commit-record order and visibility order can therefore differ, and a hand-built LSN and snapshot pair can see a later commit while missing an earlier one.

The exported snapshot has limits:

- It stays valid only "until a new command is executed on this connection or the replication connection is closed". The catch-up read must finish while that connection sits idle.
- A long backfill under the snapshot holds back both vacuum and WAL removal.
- The documentation describes snapshot export only for slots created through the replication protocol, not through the SQL function `pg_create_logical_replication_slot`.

When a backfill is too large to run under one snapshot, Netflix's DBLog shows an alternative. It interleaves chunked table selects with log events using watermarks, "without stalling" log processing and without locks. For an append-only log, events would then be deduplicated by event id, not by a cursor. `pg_logical_emit_message` could put such watermarks directly into the slot stream, either transactionally or immediately (this application is inference).

### Practical rules for a psycopg-based consumer

- Checkpoint the **end LSN** of the last complete transaction, never its commit LSN, and add an in-transaction component only if progress is per event.
- Commit the checkpoint atomically with the projection's side effects. Send `flush_lsn` only after that commit.
- On start, compare the slot's `confirmed_flush_lsn` with the stored LSN. Treat "slot ahead of checkpoint" as data loss.
- Keep in-progress streaming off, or buffer until commit.
- Use Design 1 when table catch-up and slot resumption must share one cursor. Otherwise use Design 2, and switch between table and slot only at an exported-snapshot boundary.
