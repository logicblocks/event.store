# When notifications are throttled on the leading edge, what trailing catch-up read or fallback poll interval guarantees that events appended inside a suppressed window reach consumers promptly rather than waiting for the next scheduled poll?

## Question

A leading-edge throttle sends a wake-up for the first append in a window and suppresses the rest. Events appended later in that window get no wake-up of their own. What trailing catch-up read, or what fallback poll interval, makes sure those events still reach consumers quickly instead of waiting for the next scheduled poll?

## Findings

### Short answer

What happens to a suppressed event depends on who can see that its notification was suppressed.

- **Throttle on the appender side.** River's insert limiter and pgmq's trigger throttle both work this way. They drop the notification outright, so no consumer ever learns about the suppressed append. Unless something else happens, such an event waits up to one fallback poll interval P (about 1–2 s in the systems surveyed). It does not wait just the throttle window W (100–250 ms).
- **Throttle on the consumer side.** River's fetch debouncer and Oban's dispatch cooldown work this way. The consumer receives every notification and folds them into one read at the end of the window. This guarantees delivery within about W.

To get roughly W latency when the appender throttles, the consumer has to arm its own trailing read after **every** notification it receives, even a single one. The fallback poll then only has to cover rarer cases: suppressed events whose transactions commit after the trailing read, lost notifications, and listener reconnects.

### What production PostgreSQL queues actually do

| System | Where the throttle sits | Edge | Window W (default) | Fallback poll P (default) |
|---|---|---|---|---|
| River (Go) | Appender: per client process, per queue | Leading; suppressed notifications dropped | `FetchCooldown`, 100 ms | `FetchPollInterval`, 1 s plus 0–10 % jitter |
| River (Go) | Consumer: fetch debouncer | Leading plus one trailing fetch per period | `FetchCooldown`, 100 ms | same poll |
| pgmq | Appender: inside the database (insert trigger plus throttle table) | Leading; suppressed inserts not notified | `throttle_interval_ms`, 250 ms | consumer-chosen polling or `read_with_poll` |
| Oban (Elixir) | Consumer: producer dispatch | Trailing only, coalesced | `dispatch_cooldown`, about 5 ms average, jittered | Stager, 1 s |
| Graphile Worker (Node) | Consumer: local-queue refetch delay | Deferred trailing fetch, plus an early abort after enough notifications | `refetchDelay.durationMs`, 100 ms, randomised to 0.5–1.5× | `pollInterval`, 2000 ms |

**River.** River throttles in two places, and the difference between them is the answer to this question.

- **Appender side.** The client keeps an in-memory `notifylimiter.Limiter` whose wait duration is `FetchCooldown`. `ShouldTrigger(topic)` returns true only if the last notification for that queue was sent before `now - waitDuration`, and it records `now` when it does. Otherwise it returns false and nothing is sent.
- **Notify on the caller's transaction.** `maybeNotifyInsertForQueues` runs `NotifyMany` on the caller's transaction for the queues that passed the limiter. Those notifications are delivered at commit.
- **Consumer side.** Each producer wraps fetches in `chanutil.NewDebouncedChan(fetchCtx, FetchCooldown, true)`. Its documentation says repeated calls are "debounced to a single emission on C on the period's leading edge (if sendLeading is enabled), and then one fire on the trailing edge of each period for as long as Call continues to be invoked."
- **Fallback poll.** River does not count on the debouncer to catch inserts the appender suppressed. A `fetchPollLoop` calls the same debouncer every `FetchPollInterval`, and the code comment says the loop "is meant as a back up in case something with listen/notify didn't work, or the fetch limiter was limited so there's still jobs to pick up". The interval is jittered by [0, 10 %) of P, at least 10 ms, "to prevent multiple producers from synchronizing their fetches".
- **Full batches.** A fetch that returns exactly its limit sets a flag, so another fetch runs as soon as a worker slot frees up.
- **Throughput.** The documentation states that throughput is capped by `FetchCooldown`.

**pgmq.** pgmq puts the throttle inside PostgreSQL.

- `pgmq.enable_notify_insert(queue_name, throttle_interval_ms DEFAULT 250)` installs a trigger that updates an `UNLOGGED` table, `pgmq.notify_insert_throttle`. The update is conditional: it only matches when `clock_timestamp() - last_notified_at >= throttle_interval_ms`. The trigger calls `PG_NOTIFY` only if the update matched a row.
- Inserts inside the window succeed but send nothing.
- pgmq's documentation recommends notifications mainly "for queues with sporadic or low-volume traffic" and suggests running `LISTEN` alongside periodic polling or `read_with_poll()`. Recovering suppressed messages is left entirely to the consumer's polling.

**Oban.** Oban does not throttle on the appender side.

- Insert notifications are de-duplicated per queue within a single insert call, and sent only for jobs that are `available`.
- On the consumer side, `schedule_dispatch` starts a jittered `dispatch_cooldown` timer unless one is already pending. Notifications that arrive while it is pending are absorbed into that one dispatch, so every notification is covered by a read that starts after it.
- The Stager runs every second. If pubsub messages cannot get through, it switches to a "local" mode in which every node polls.
- `insert_trigger` can be turned off at very high insert rates. Jobs then wait up to the Stager interval.

**Graphile Worker.** Graphile Worker's local queue uses a different trailing scheme.

- **Starting the delay.** After a fetch that returns no more than `refetchDelay.threshold` jobs, the queue enters a delay of `(0.5 + Math.random()) × durationMs`.
- **Fetch requests during the delay.** Any `fetch()` call during the delay, including the poll timer firing, sets `refetchDelayFetchOnComplete`. A fetch then runs as soon as the delay ends.
- **Notifications during the delay.** A new-job notification only adds to a counter. Once the counter reaches a random threshold in `[0, maxAbortThreshold)` (default 5 × batch size), the delay is cut short and a fetch runs. In the source code, a notification that does not reach the threshold does not by itself cause a fetch when the delay expires. That leaves the `pollInterval` timer, which is set after every fetch, as the backstop.
- **Why.** The randomness spreads re-fetches across worker pools that all received the same notification. The cost is that a lone notification during a delay can fall back to the 2 s poll.

### Why a lodash-style trailing edge is not enough when the appender throttles

The usual leading-plus-trailing throttle, documented by lodash, fires the trailing call "only if the throttled function is invoked more than once during the wait timeout". River's debouncer follows the same rule.

When the appender suppresses notifications, the consumer only ever sees the one leading notification. So a consumer-side throttle with that rule never fires a trailing read for the suppressed appends. That is why River names the fallback poll as the safety net for limiter suppression.

Two designs give a guarantee of about W:

1. **Consumer-armed trailing catch-up (inference from the sources above).** When a notification arrives, read immediately. Also, unconditionally, schedule one more catch-up read at about the arrival time plus the appender's window W plus a small margin, and fold any further notifications into that pending read, as Oban does. This covers every append that the leading notification's window suppressed, as long as it has committed by then. It costs at most one extra read per window per consumer, which is cheap compared with the commit-time NOTIFY cost the throttle was added to avoid.
2. **Move the throttle to the consumer.** Notify on every append, or once per transaction (PostgreSQL already merges identical channel and payload pairs within a transaction). Then throttle the reads on the consumer with a leading-plus-trailing or trailing-only debouncer, as River and Oban do. This sacrifices the appender-side saving the throttle existed for.

### Remaining gaps, and how to size the fallback poll

The fallback poll is still needed, and sets the worst case, for three reasons:

- **The window is measured at insert time, but notifications arrive at commit.** River's limiter and pgmq's trigger timestamp the window when the row is inserted (`time.Now()` in the client, `clock_timestamp()` in the trigger). PostgreSQL delivers NOTIFY events "not ... until and unless the transaction is committed". A suppressed append in a transaction that commits after the consumer's trailing read gets neither a notification nor a trailing read.
- **The leading notification can vanish (inference).** If the transaction that carried the leading notification rolls back, its notification is never delivered. River's in-memory limiter keeps the timestamp anyway, so appends later in that window lose their wake-up. pgmq's throttle-row update rolls back with the transaction, so it does not have this problem. However, its conditional `UPDATE` on a single row per queue makes concurrent inserters wait for each other's commits.
- **Listener outages.** Notifications are lost while a LISTEN session is disconnected, and Oban's Stager handles pubsub failure by switching to local polling.

For sizing P, the surveyed defaults are 1 s (River `FetchPollInterval`, Oban Stager), 2 s (Graphile Worker) and 10 s (GoodJob in production, where polling is described as a fallback to LISTEN/NOTIFY). Practical rules drawn from these sources:

- **Treat P as the latency limit for residual cases only.** Once a consumer-armed trailing read handles ordinary suppression, P only governs late commits, rollbacks and outages, so it can be relaxed.
- **Jitter P across consumers.** River adds up to 10 %, to avoid synchronised polling load.
- **Restart the poll timer after every read, however it was triggered.** Graphile Worker clears its poll timer at the start of every fetch and re-arms it afterwards, so a busy consumer never polls on top of notification-driven reads.
- **Fetch again immediately after a full batch.** River and Graphile Worker both do this, so a backlog never waits for W or P.
- **Read from the checkpoint, not the payload.** Every trailing read and poll must be a catch-up from the consumer's stored position, not driven by notification payloads. In an event store, it must also stop at a safe high-water mark so that transactions committing out of position order are not skipped. Throttling does not change that requirement; it only changes when the read happens.
