# How do `SELECT ... FOR UPDATE SKIP LOCKED` and advisory-lock-based claiming distribute work among competing consumers, how do they combine with notification-driven wake-ups, and how do they preserve per-stream or per-partition ordering?

## Question

How do `SELECT ... FOR UPDATE SKIP LOCKED` and advisory-lock-based claiming distribute work among competing consumers, how do they combine with notification-driven wake-ups, and how do they preserve per-stream or per-partition ordering?

## Findings

### In brief

`FOR UPDATE SKIP LOCKED` and advisory locks both let consumers claim work. Neither one orders work. Several workers can run the same ordered claim query and each get a different item without blocking one another. SKIP LOCKED does this by skipping tuples that another transaction has locked. Advisory locks do it with integer keys that the application defines and that live in shared memory rather than on tuples. Neither keeps per-key order across workers, because the point of both is that worker B can take the next item while worker A is still busy with the previous one. Every library surveyed here that guarantees per-key order adds a second mechanism on top: while an earlier item for a key is in flight, only the head item for that key can be claimed. Notifications sit in front of the claim query as a wake-up hint. The claim query stays authoritative, and every library surveyed except Solid Queue keeps a polling fallback. Solid Queue skips notifications altogether and only polls.

### How SKIP LOCKED distributes work

The PostgreSQL docs define the behaviour: with `SKIP LOCKED`, "any selected rows that cannot be immediately locked are skipped". The docs warn that this "provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table". Only row-level locks are skipped. The table-level `ROW SHARE` lock is still taken in the ordinary way. When a locking clause sits at the top level of a query with `LIMIT`, "locking stops once enough rows have been returned to satisfy the limit". Rows skipped by `OFFSET` still get locked. At `READ COMMITTED`, an `ORDER BY` query with a locking clause can return rows out of order because sorting happens before locking. That case only arises when the query has to wait for a lock, and SKIP LOCKED avoids the wait.

Production queues use the same shape. River's `JobGetAvailable` CTE selects `state = 'available'` rows for one queue, `ORDER BY priority ASC, scheduled_at ASC, id ASC LIMIT @max_to_lock FOR UPDATE SKIP LOCKED`, and then an `UPDATE` sets `state = 'running'`, increments `attempt` and stamps `attempted_at` and `attempted_by`. Procrastinate's fetch function uses `FOR UPDATE OF jobs SKIP LOCKED`. Solid Queue polls its `ready_executions` table with `FOR UPDATE SKIP LOCKED` "to avoid blocking and waiting on locks when polling jobs".

Libraries hold the claim for one of two lifetimes:

- **Lock held for the whole handler transaction.** A crashed worker's transaction rolls back and the row can be claimed again straight away. The cost is a transaction and connection held open for as long as the handler runs.
- **Claim-and-mark**, as in River. The lock lasts only for the claim, and the state column records the claim after commit. Crash recovery then needs its own mechanism. pgmq, for example, uses a visibility timeout: if processing fails, "the visibility timeout will expire and the message becomes available again".

depesz benchmarked the two families against each other: 8 workers draining 10,000 rows took about 15.6 s with SKIP LOCKED and about 15.8 s with a `pg_try_advisory_xact_lock(123, hashtext(...))` predicate. He concluded that "the biggest benefit is that we can leave advisory locks for other purposes". Michael Paquier's 9.5 feature write-up shows the basic behaviour: one session holds a lock on row 1, and a second session's `ORDER BY id FOR UPDATE SKIP LOCKED` returns rows 2, 3 and 4. He also repeats the caveat that the result is deliberately inconsistent.

### How advisory-lock claiming distributes work

Advisory locks come in session-level and transaction-level forms (`pg_advisory_lock` and `pg_advisory_xact_lock`). Non-blocking `pg_try_*` variants return a boolean instead of waiting. Keys are either one `bigint` or two `integer`s, and the two key spaces do not overlap. Session-level locks "do not honor transaction semantics": they survive a rollback, they stack (each acquisition needs its own unlock), and they are released when the session ends. Transaction-level locks are released when the transaction ends. Advisory locks share a memory pool with ordinary locks, sized by `max_locks_per_transaction` and `max_connections`, so exhausting it stops the server granting any locks at all.

Que is the canonical advisory-lock queue. Its README says that "workers don't block each other when trying to lock jobs, as often occurs with 'SELECT FOR UPDATE'-style locking". It also notes that locks live in memory, so taking one costs no disk write, and that if a process dies its jobs "immediately become available for any other worker to pick up". Que walks jobs in `(priority, run_at, job_id)` order with a recursive CTE and calls `pg_try_advisory_lock()` on one candidate at a time. A non-recursive `SELECT` "would have the undesirable side-effect of locking multiple jobs at once".

That side-effect is a documented trap. The PostgreSQL docs mark `SELECT pg_advisory_lock(id) FROM foo WHERE id > 12345 LIMIT 100` as "danger!", because the `LIMIT` is not guaranteed to apply before the lock function runs. The result can be locks the application never expected and never releases. The fix is to apply the `LIMIT` in a subquery first. GoodJob does this with a `MATERIALIZED` CTE that selects up to 1,000 candidate ids in `priority DESC, created_at ASC` order, then calls `pg_try_advisory_lock(...)` in the outer query with `LIMIT 1`.

Session advisory locks and `LISTEN` both need a stable session, which conflicts with transaction-pooling proxies:

- Que offers a separate locking connection URL for applications whose connections "can't use advisory locks", for example when they pass through PgBouncer.
- GoodJob is incompatible with PgBouncer in transaction mode unless it runs its `:skiplocked` strategy with LISTEN/NOTIFY turned off. It offers advisory, skip-locked and hybrid claiming strategies.
- River needs "a minimum of two connections" that bypass transaction pooling, because LISTEN/NOTIFY is required both for new jobs and for leadership demotions.

Event stores usually apply advisory locks at a coarser grain: they elect one owner for a whole consumer rather than claim individual events.

- **Marten.** In `HotCold` mode Marten runs leader election "individually for each projection on each tenant database", ensuring "each projection is running on exactly one running process". By default this uses a session-scoped `pg_try_advisory_lock`, with `UseAdvisoryLockTransaction` switching it to `pg_try_advisory_xact_lock`.
- **Commanded EventStore.** The subscription state machine calls `AdvisoryLocks.try_advisory_lock(server, subscription_id, timeout)`. If the lock is lost, it disconnects, resets event tracking and purges in-flight events. The docs describe the result as "only one instance of a named subscription to a stream can connect to the database". The `AdvisoryLocks` module sends the owner a `lock_released` message so it can "attempt to reacquire the lost lock".

### Combining claiming with notification-driven wake-ups

**NOTIFY timing.** NOTIFY fits a claim loop because it is tied to commit. Notifications from a transaction "are not delivered until and unless the transaction is committed". A listener that is inside a transaction receives them only after that transaction ends. Identical channel-and-payload pairs within one transaction collapse into a single notification. Notifications are delivered "in the order in which the transactions committed". So by the time a wake-up arrives, the producer's rows are committed, and a fresh claim query at `READ COMMITTED` can see them. The payload limit is 8,000 bytes by default, so payloads are best treated as hints rather than as the data itself.

**LISTEN race.** The `LISTEN` docs describe a race when a listener starts up and give a rule to avoid it: "first execute (and commit!) that command, then in a new transaction inspect the database state as needed by the application logic, then rely on notifications to find out about subsequent changes". The first few notifications may repeat state that has already been seen, which "is usually harmless". For a consumer, that means:

1. LISTEN and commit.
2. Run the claim loop until it comes back empty.
3. Wait for a notification or a timeout.
4. Run the claim loop again.

**psycopg 3.** Psycopg 3 advises keeping the listening connection in autocommit mode "if you wish to receive or send notifications in a timely manner". Its `Connection.notifies()` generator takes `timeout` and `stop_after` arguments. A timeout lets one wait handle both a notification wake-up and the poll fallback. The alternative, `add_notify_handler`, runs handlers only "during the normal query processing". The docs say to use only one of the two methods.

**Polling fallback.** Every surveyed library still polls:

| Library | Fallback behaviour |
|---|---|
| Procrastinate | Each worker polls "every now and then, just in case". The `fetch_job_polling_interval` timer starts once a fetch returns nothing. |
| River | `FetchPollInterval` (default 1 s) is the fallback for when no job arrives via LISTEN/NOTIFY. `FetchCooldown` (default 100 ms) limits how often fetches happen, which absorbs bursts of notifications. `PollOnly` drops LISTEN entirely for environments such as transaction-pooling PgBouncer. |
| GoodJob | Falls back to `poll_interval` (10 s in production) when LISTEN/NOTIFY is disabled or unavailable. |
| Que | Jobs that are ready immediately are broadcast via LISTEN/NOTIFY, "so polling is unnecessary for them". Polling, every 5 s by default, covers scheduled and retried jobs. |
| Solid Queue | Doesn't use LISTEN. Workers poll every 0.1 s. |

**Fan-out shapes.** Most libraries broadcast:

- Procrastinate's insert trigger calls `pg_notify` on a per-queue channel and an any-queue channel, with a `{"type": "job_inserted", "job_id": ...}` payload.
- Oban publishes on an `insert` channel, which queue producers "use this as a signal to dispatch new jobs".
- Commanded EventStore's trigger on its `streams` table sends one NOTIFY per batch of appended events. The payload carries the stream uuid, stream id and first and last versions.

A broadcast wakes every listener, but SKIP LOCKED or try-advisory-lock makes the race safe. Losing workers get an empty claim rather than a duplicate, so the cost is wasted queries, which River's cooldown limits. Que instead targets one listener. Its `que_job_notify()` trigger picks a single locker from an unlogged `que_lockers` table, choosing among lockers that are listening and serve the job's queue, "weighted by their number of workers" via `NEW.id % count`. It then sends `pg_notify('que_listener_' || locker_pid, ...)`, so the notification itself hands out the work.

**Scalability caveat.** A 2025 comment on the PostgreSQL docs list reports that NOTIFY takes a global lock at commit, which serialises commits among transactions that notify at the same time. This matters for designs that notify on every append.

### Preserving per-stream or per-partition ordering

**Why claiming alone breaks order.** If two consecutive rows from one stream go to two workers, the two run at the same time and can finish in either order. Commanded's docs say that with several subscribers "the ordering of event processing is no longer guaranteed" unless events are partitioned. Concurrency limits are not ordering either. Solid Queue's per-key semaphores (`limits_concurrency`) cap how many jobs run at once, but the docs state that "queue order is not taken into account for unblocking jobs".

The surveyed systems use five patterns to restore per-key order.

1. **Head-of-key exclusion predicate (Procrastinate).** A candidate can't be fetched while another job with the same `lock` is in either of these states:
   - `doing`, or
   - `todo` with higher priority, or with equal priority and a lower id.

   The query orders by `priority DESC, id ASC` under `FOR UPDATE OF jobs SKIP LOCKED`. A partial unique index, `ON procrastinate_jobs (lock) WHERE status = 'doing'`, enforces at most one running job per lock even if two fetches race. The documented guarantee is that jobs sharing a lock "will be started in order; a job will not start before the previous one is finished", whether the previous job succeeded or failed. A higher-priority job "cannot jump ahead of a currently running job". The docs also flag a stall: if the oldest job for a lock sits in a queue nobody consumes, or is scheduled far in the future, every later job for that lock waits behind it.

2. **Lock the group row, not the item (Graphile Worker).** Named queues have rows in `_private_job_queues`. The claim restricts jobs to `job_queue_id in (select id from _private_job_queues where is_available = true for update skip locked)` and stamps `locked_by` and `locked_at` on the queue row. When fetching a batch, `select distinct on (job_queue_id, ...)` keeps only the first job per queue. Ordering is `priority asc, run_at asc`. The docs say jobs in one named queue "run one at a time". They also warn against high-cardinality queue names such as UUIDs, which "will create many dead queues that degrade performance". For an append-only event log (my synthesis), the closest equivalent is a row per stream, partition or subscription that is locked with SKIP LOCKED. Event rows are never updated, so the claim belongs on a row that represents the ordering unit.

3. **Head-of-group visibility (pgmq FIFO).** Each message carries a group id in its `x-pgmq-group` header. `read_grouped_head()` "skips groups whose head message is not visible (being processed by another worker)" and uses `FOR UPDATE SKIP LOCKED`. Two other read functions trade fairness against throughput:
   - `read_grouped` fills a batch from the oldest eligible group.
   - `read_grouped_rr` interleaves groups round-robin.

   A failed group resumes once the visibility timeout expires. A GIN index on `headers` is recommended.

4. **Per-key advisory lock.** A non-blocking transaction-level try-lock, keyed by stream, gives mutual exclusion per stream. The two-integer form can carry a namespace as well as an object id. A lock alone doesn't order anything, though: the holder must also process only the earliest unprocessed item for that key, usually by reading forward from a per-key checkpoint. Mapping arbitrary stream names onto a 32-bit or 64-bit key can produce collisions. My inference is that a collision forces two unrelated streams to run serially without breaking exclusion. The `LIMIT` trap above applies to any query that calls the lock function inside a filter.

5. **One elected owner plus partitioned dispatch (Commanded EventStore, Marten, River Pro).**
   - Commanded: one advisory-lock owner reads the log in order and fans events out to concurrent subscribers by a `partition_by` key. This guarantees that "events for each stream are processed serially (by a single subscriber) in the order they were appended". Back-pressure comes from acknowledgements: a subscriber "will not receive further published events until it has confirmed receipt of all received events".
   - Marten: the async daemon processes events "in order" through each projection, with a single process per projection.
   - River Pro sequences give a similar guarantee at the job level. Jobs within a sequence are "ordered by when they were inserted (`id ASC`)" and jobs across sequences may run in parallel. A sequence halts when a job is cancelled or discarded, unless `ContinueOnCancelled` or `ContinueOnDiscarded` is set. Retrying the offending job resumes it.

**Shared costs.** All five patterns pay with head-of-line blocking. A stuck, failed or far-scheduled head item stalls its key (Procrastinate, River sequences, pgmq visibility timeouts). Many fine-grained keys also add bookkeeping cost (Graphile's high-cardinality warning).

**Commit-order hazard.** Ordering by a sequence-assigned position is not the same as ordering by commit. Oskar Dudycz shows that sequence values are "evaluated before the transaction commit". A transaction that takes a higher position can therefore commit first, and rolled-back transactions leave gaps, so a poller that reads past a gap "may lose messages". This interacts with NOTIFY: a wake-up from a later transaction can arrive while an earlier-positioned transaction is still in flight. Two documented guards address it:

- Dudycz stores a `transaction_id xid8` column, reads only rows with `transaction_id < pg_snapshot_xmin(pg_current_snapshot())`, and orders by `(transaction_id, position)`.
- Marten tracks a "high water mark", defined as "the furthest known event sequence that the daemon 'knows' that all events with that sequence or lower can be safely processed in order".

### Synthesis for a psycopg 3, PostgreSQL-only event store

The surveyed designs converge on a consumer that works as follows:

1. Hold a dedicated autocommit connection that LISTENs, using a session-mode connection rather than one through a transaction pooler.
2. Commit the LISTEN, then catch up.
3. Wait in `notifies(timeout=...)`, using the timeout as the poll fallback.
4. Treat each notification only as a cue to re-run an ordered claim query.
5. Claim at the grain of the ordering unit (subscription, partition or stream row), using either SKIP LOCKED on that unit's row or a try-advisory-lock on its key, rather than claiming individual events.
6. Read forward only up to a visibility-safe position, so events from in-flight transactions are never skipped.
