# What batching, debouncing or statement-level trigger strategies do PostgreSQL event stores and queues use to limit the throughput cost of the commit-time global lock that NOTIFY takes when every append notifies?

## Question

When every append to a PostgreSQL-backed event store or queue issues a `NOTIFY`, each notifying transaction takes a database-wide lock at commit. What batching, debouncing, throttling or statement-level trigger strategies do real implementations use to keep that lock from capping write throughput?

## Findings

### What the lock costs, and what a mitigation has to reduce

PostgreSQL's `async.c` serializes notifying transactions in `PreCommit_Notify`. Its comment says it does so "by acquiring a special lock that we hold till after commit. This ensures that queue entries appear in commit order". The call is `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)`, a lock on "database 0". The lock is taken only when the transaction has pending notifications. It is released along with the transaction's other heavyweight locks, after commit or abort. While it is held, the transaction appends its entries to the shared queue, commits, and then (in `AtCommit_Notify`) signals listening backends. Transactions that send no notifications never take it.

Recall.ai described what this looks like in production (July 2025, updated May 2026). Hundreds of sessions were waiting on `AccessExclusiveLock on object 0 of class 1262 of database 0`. Database load spiked while CPU and I/O dropped, the usual sign of lock contention, and load tests with and without `NOTIFY` confirmed the cause.

Two consequences follow from this design. The second is an inference from the documented ordering, not something a source states.

1. **What the lock costs depends on how many transactions notify, not how many messages they send.** A transaction that sends a hundred notifications takes the lock once. Batching inside a transaction shortens the time the lock is held, because fewer queue entries are written and fewer listeners are signalled, but it does not reduce how often the lock is taken.
2. **Only skipping or moving notifications reduces how often the lock is taken.** That means time-based throttling or debouncing, so some committing transactions send nothing, or sending the signal from somewhere other than the append transaction.

PostgreSQL already collapses duplicate notifications inside a transaction: "If the same channel name is signaled multiple times with identical payload strings within the same transaction, only one instance of the notification event is delivered". Notifications with distinct payloads are always delivered separately. `async.c` switches to a hash table for duplicate detection once a transaction has `MIN_HASHABLE_NOTIFIES` (16) pending notifications. This collapsing reduces queue volume, but a transaction that sends a single notification still takes the lock.

### Strategy 1: notify per statement or per append, not per row

- **Statement-level triggers with an empty payload (older Graphile Worker).** An earlier Graphile Worker migration (`000011.sql`) installs `after insert on ... jobs for each statement`, whose function runs `perform pg_notify('jobs:insert', '')`. A bulk insert therefore produces one notification. Because the payload is constant, repeated statements in one transaction collapse into one under the duplicate rule above.
- **A statement-level table-change trigger (PgQueuer, Python).** PgQueuer creates its trigger as `AFTER INSERT OR UPDATE OR DELETE OR TRUNCATE ON <queue table> EXECUTE FUNCTION ...` with no `FOR EACH` clause. PostgreSQL defaults to `FOR EACH STATEMENT` in that case and allows `TRUNCATE` triggers only at statement level. The payload describes a table change (`channel`, `operation`, `sent_at`, `table`, `type: 'table_changed_event'`), not individual jobs.
- **Per-append notifications that carry a range (Commanded EventStore, Elixir).** This event store puts its `notify_events()` trigger on the `streams` table rather than the `events` table (`AFTER INSERT OR UPDATE ON streams FOR EACH ROW`). The payload is `stream_uuid,stream_id,first_version,last_version`. An append inserts all its events in one multi-row `INSERT` and updates two `streams` rows: the target stream and the `$all` stream (`stream_id = 0`). So a 1-event append and a 500-event append send the same small number of notifications. On the consumer side, the publisher reads the whole range with one `read_stream_forward` call of `to_version - from_version + 1` events.
- **Transition tables.** PostgreSQL's `REFERENCING NEW TABLE AS ...` gives an `AFTER` statement-level trigger "a global view of what the statement did". A trigger could use it to send one summarizing notification per statement, such as the minimum and maximum position inserted. None of the implementations examined here use transition tables for notifications.
- **The per-row pattern, for contrast (Procrastinate, Python).** Procrastinate still uses `AFTER INSERT ... FOR EACH ROW WHEN (new.status = 'todo')`. Each job sends two notifications, one on the queue channel and one on an any-queue channel, and the payload includes `job_id`. The payloads are distinct, so PostgreSQL never collapses them.

### Strategy 2: move notifications out of triggers into the application's insert call

Several projects removed their database triggers and send one notification per application-level insert call, collapsed by queue:

- **Graphile Worker 0.16.0** "Replaces job announcement trigger with calls directly in `add_job` / `add_jobs` to reduce queuing overhead". The current `add_jobs` sends one `pg_notify('jobs:insert', '{"r":<random>,"count":<n>}')` per batch. The listener reads `count` and calls `workerPool.nudge(n)`, which wakes up to n workers. Because of the random `r` field, each call's payload is distinct, so PostgreSQL never collapses two calls within one transaction (an inference from the duplicate rule).
- **Oban 2.17.0 (2023-12-08)**: "Historically, Oban used database triggers to emit a notification after a job is inserted. Now insert notifications have moved out of the database and into application code". Oban's V12 migration drops the per-row `oban_notify` trigger and its `oban_jobs_notify()` function. `Oban.Engine.notify_trigger/2` builds one payload per `insert_job` or `insert_all_jobs` call: `for job <- jobs, job.state == "available", uniq: true, do: %{queue: job.queue}`. That is one notification per insert operation, collapsed by queue. The `insert_trigger` option turns this off "if sub-second job execution isn't important or you'd like to reduce PubSub chatter". The `Oban.Stager`, which runs every second by default, then still tells queues about available jobs. Moving notifications into the application also lets Oban use a notifier other than PostgreSQL, which avoids `NOTIFY` entirely.

### Strategy 3: time-based debouncing or throttling, so most commits send nothing

This is the only strategy that reduces how many transactions take the lock.

- **River (Go), in the client.** River 0.5.0 (2024-05-03) removed its insert trigger, which "does have the side effect of emitting a large amount of notifications any time there are lots of jobs being inserted. This adds overhead, particularly to high-throughput installations". It added "a client-level debouncer [that] ensures that these notifications are not emitted more often than they could be useful". When a queue is due a notification, "the notification is piggy-backed onto the insert query within the transaction". River accepts that this slightly increases insert latency for some inserts.
  - The debouncer is `notifylimiter.NewLimiter(archetype, config.FetchCooldown)`, with `FetchCooldown` defaulting to 100 ms. `ShouldTrigger(queue)` returns true only if the queue's last notification was before `now - waitDuration`. This is a leading-edge, per-queue limit, held in each client's memory.
  - `FetchPollInterval`, 1 s by default, is the fallback that catches anything the notifications miss.
- **pgmq, in the database.** `pgmq.enable_notify_insert(queue_name, throttle_interval_ms DEFAULT 250)` installs `CONSTRAINT TRIGGER ... AFTER INSERT ... DEFERRABLE FOR EACH ROW`. The trigger function updates a per-queue row in an `UNLOGGED` table, `pgmq.notify_insert_throttle`: `SET last_notified_at = clock_timestamp() WHERE ... clock_timestamp() - last_notified_at >= throttle_interval_ms`. It calls `PG_NOTIFY('pgmq.q_<queue>.INSERT', NULL)` only if a row was updated. Setting the interval to 0 turns throttling off.
  - Two inferences from this design, not stated by pgmq. First, the throttle row is a per-queue hotspot: a transaction that wins the update holds the row lock until commit, and concurrent inserters that try the same update wait for it and then skip notifying. Second, the throttle works on the leading edge, so inserts in the rest of the window send no notification. Consumers therefore need a re-read or poll to catch those inserts.

### Strategy 4: drop NOTIFY from the write path

Recall.ai's fix was to "migrate away from `LISTEN/NOTIFY` in favor of tracking this logic at the application layer", which took under a day because only one code path used it. Oban's optional non-PostgreSQL notifiers combined with periodic staging is a structured version of the same idea.

### Upstream changes

PostgreSQL commit `282b1cde9` (Joel Jacobson, reviewed by Tom Lane) is listed in the PostgreSQL 19 release notes, which were still undated as of 2026-09-14. It adds a shared hash table recording which backends listen on which channels. A notifier then wakes only interested listeners and moves uninterested idle listeners' queue pointers forward directly. The commit message reports "very significant improvements (integer multiples) in NOTIFY throughput … when there are many listeners but only a few are interested in any specific message".

Recall.ai's updated post says this commit "eliminated the bottleneck". However, `async.c` on master still takes the `AccessExclusiveLock` on database 0 in `PreCommit_Notify`. The more defensible reading is that PostgreSQL 19 cuts the work a notifier does while serialized, rather than removing the serialization. On PostgreSQL 18 and earlier, nothing has changed.

### Implications for an event store where every append notifies

This is a synthesis of the sources above.

- **Send one notification per append transaction.** Use an empty or constant payload, either from the append code or from a statement-level trigger. This keeps the time the lock is held short and lets duplicates collapse.
- **Carry a range if consumers need hints.** As Commanded EventStore does, send a range (for example the global positions written) rather than one message per event.
- **Throttle when append concurrency is high.** If many concurrent append transactions contend for the lock, add time-based throttling, either per process like River or in the database like pgmq. That is the only lever that reduces how many transactions take the lock. It is safe only if consumers treat a notification as a wake-up hint and always catch up by reading from their last position, with a fallback poll or trailing re-read covering the suppressed windows.
