# What delivery guarantees and failure modes does `LISTEN`/`NOTIFY` have — notifications lost while no listener is connected or during reconnection, commit-time delivery and duplicate collapsing within a transaction, the 8000-byte payload limit, the notification queue's size limit and behaviour when it fills, and the global lock taken when committing a transaction that issued `NOTIFY`?

## Question

What does PostgreSQL's `LISTEN`/`NOTIFY` actually guarantee, and how does it fail? This covers notifications lost while no listener is connected or during reconnection, delivery at commit time, collapsing of duplicates within a transaction, the payload size limit, the size limit of the shared notification queue and what happens when it fills, and the global lock taken when a transaction that issued `NOTIFY` commits.

## Findings

### Summary

`LISTEN`/`NOTIFY` is a transient, at-most-once broadcast to sessions that are connected and listening when the notifying transaction commits. It is transactional on the sending side: notifications go out only if the transaction commits, and they arrive in commit order. It has no durability. Nothing is stored for disconnected sessions, nothing survives a server restart, and nothing reaches standbys. The serious operational costs are on the write path. Every transaction that issues `NOTIFY` takes one cluster-wide exclusive lock from just before its commit record is written until the transaction ends, so all notifying commits run one at a time. If the shared queue fills, typically because one listener stays inside a long transaction, every notifying transaction fails at `COMMIT` and its data writes roll back with it. For an event store, `NOTIFY` therefore works only as a "wake up and poll" hint on top of the durable event table. It cannot be the source of truth.

### Who receives a notification: lost while disconnected or reconnecting

- Delivery is limited to sessions that are listening at the moment the sender commits. In the `LISTEN` reference, a newly listening session "will receive all events committed after an instant during the transaction's commit step". In the source, a new listener sets its queue pointer to the global tail and then skips past notifications that have already committed. It can therefore miss nothing that has not yet committed, and it never receives anything that committed earlier.
- `LISTEN` itself takes effect only when its own transaction commits. If that transaction rolls back, the set of channels is unchanged. "A session's listen registrations are automatically cleared when the session ends."
- So any notification committed while a consumer is disconnected, crashed, or reconnecting is gone for that consumer. Nothing is queued for it. A PostgreSQL contributor put it plainly on the project's JDBC list: "You lose notifications during any period you don't have a connection." Client libraries that reconnect automatically document the same thing. sqlx's `PgListener` re-subscribes after a reconnect, but "as notifications are transient, any received while the connection was lost, will not be returned."
- The queue is deliberately not crash-safe. The design comment in `async.c` says notifications "are not expected to survive database crashes", so `pg_notify` data is wiped at every restart and is neither WAL-logged nor fsynced. A server crash or restart therefore drops notifications that had committed but not yet been read, even for listeners that stay connected.
- Hot standbys reject `LISTEN` and `NOTIFY`, and notifications are not replicated. A consumer cannot listen on a replica, and after a failover the promoted primary has no record of earlier notifications.
- Connection poolers can silently break subscriptions. PgBouncer's feature map lists `LISTEN` as supported in session pooling only ("Never" in transaction pooling), while `NOTIFY` works in both. A listener behind a transaction-mode pooler cannot keep a subscription.
- The documented recovery pattern is to commit `LISTEN` first, then query current state in a new transaction, then rely on notifications for later changes. "The first few received notifications might refer to updates already observed in the initial database inspection, but this is usually harmless." After a reconnect, the client must run `LISTEN` again and re-read state, as Craig Ringer's message recommends. For an event store, that means re-reading from the consumer's last stored position.
- Client-side loss in psycopg 3: before 3.2.4, notifications that arrived between `LISTEN` and the start of the `notifies()` generator were lost. From 3.2.4 they are buffered and yielded once the generator starts. From 3.2.10, if a notify handler is registered, notifications are not captured while the generator is not running, and mixing handlers with the generator is deprecated. Use one mechanism only. psycopg also recommends autocommit mode for both sending and receiving connections, because of how notifications interact with transactions.

### Commit-time delivery, ordering and duplicate collapsing

- Sending is transactional. Notifications from a transaction "are not delivered until and unless the transaction is committed", and an aborted transaction delivers none. In the source, the notifying backend writes its entries into the queue before its commit is recorded in clog (`PreCommit_Notify`). Readers stop at entries from transactions that are still in progress, deliver entries whose transaction committed, and skip entries whose transaction aborted or crashed.
- Delivery to the receiver is also deferred by transactions. A listening session that is inside a transaction does not see notifications until "just after the transaction is completed (either committed or aborted)". At the protocol level, `NotificationResponse` is currently sent only outside a transaction, although clients should be ready to accept it at any point. The backend processes incoming notifications only when it is truly idle, outside a transaction block. A consumer connection that sits idle in a transaction (for example psycopg 3 outside autocommit) receives nothing until that transaction ends.
- Ordering: apart from dropped duplicates, notifications from one transaction arrive in the order they were sent, and notifications from different transactions arrive in commit order. This follows from the single global queue, whose entries "appear in commit order".
- Duplicate collapsing: "If the same channel name is signaled multiple times with identical payload strings within the same transaction, only one instance of the notification event is delivered to listeners." Notifications with different payloads are always delivered separately. In PostgreSQL 12 and earlier, the docs only said the server "can decide to deliver a single notification only". The wording became a guarantee from PostgreSQL 13. In the implementation, a transaction with 16 or more pending notifications (`MIN_HASHABLE_NOTIFIES`) uses a hash table to remove duplicates, and duplicates are also removed when subtransaction notifications merge into the parent. Collapsing never crosses transactions: the PostgreSQL 12 docs state that notifications from different transactions "will never get folded into one notification". The source comment's advice for applications that need every notification is to put a unique string in the payload.
- A sender that also listens on the channel receives its own notifications. It can drop them by comparing the sender PID in the notification with its own backend PID.
- A transaction that ran `NOTIFY` or `LISTEN` cannot be prepared for two-phase commit.

### Payload and channel limits

- Payload: "In the default configuration it must be shorter than 8000 bytes." The limit is `NOTIFY_PAYLOAD_MAX_LENGTH = BLCKSZ - NAMEDATALEN - 128` (8192 − 64 − 128 = 8000 bytes, so at most 7999 bytes), sized so that each message fits on one queue page. It can only be changed by recompiling with a different block size. An oversized payload raises `payload string too long` when `NOTIFY` or `pg_notify()` is called, which aborts the surrounding transaction.
- Channel name: it must not be empty (`channel name cannot be empty`) and must be shorter than `NAMEDATALEN` (`channel name too long`), so at most 63 bytes by default.
- Because of these limits, and because the payload is no more durable than the notification, the usual design sends an identifier or position (for example a stream name or sequence number) rather than the event body.

### Queue size limit and behaviour when it fills

- All databases in the cluster share one disk-backed queue (`pg_notify/`, cached through SLRU buffers). Each entry is held until every listening session has read past it. The docs describe it as "quite large (8GB in a standard installation)". From PostgreSQL 17 the size is set by `max_notify_queue_pages` (default 1,048,576 pages, which is 8 GB at 8 kB pages, restart required). PostgreSQL 17 also added `notify_buffers` (default 16 blocks) to size the shared-memory cache. Neither setting exists in PostgreSQL 16, where the limit was fixed.
- The usual way the queue fills is a stalled reader: "no cleanup can take place if a session executes `LISTEN` and then enters a transaction for a very long time." From half full, the server logs `NOTIFY queue is N% full` at most once every 5 seconds and names the process with the oldest transaction, saying the queue "cannot be emptied until that process ends its current transaction." `pg_notification_queue_usage()` returns the fraction in use (0 to 1) for monitoring.
- When the queue is full: "transactions calling `NOTIFY` will fail at commit". The error is `too many notifications in the NOTIFY queue`, raised in `PreCommit_Notify`. Because it fires at `COMMIT`, the whole transaction aborts, including any data it wrote. If an event store issues `NOTIFY` from a trigger or in the same transaction as its event inserts, one stuck listener can stop all event writes across the cluster.
- A related correctness bug: VACUUM could truncate commit-status (clog) data that the notification queue still needed. Listeners then failed with `could not access status of transaction NNN`, including when issuing `LISTEN` on an otherwise quiet system. A fix that makes VACUUM freeze the transaction IDs held in queue entries was committed in November 2025 and back-patched to all supported branches (14 to 18). The commit message notes that a remaining race was handled by a follow-up commit. Long-lived listeners should therefore run a recent minor release.

### The global lock at commit

- In `PreCommit_Notify`, a transaction with pending notifications takes `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)`. This is a heavyweight lock on "database 0", visible in `pg_locks` and in lock-wait logs as `AccessExclusiveLock on object 0 of class 1262 of database 0`. The source comment explains it: "Serialize writers by acquiring a special lock that we hold till after commit. This ensures that queue entries appear in commit order, and in particular that there are never uncommitted queue entries ahead of committed ones, so an uncommitted transaction can't block delivery of deliverable notifications." Tom Lane confirmed that with notifications in use, only one notifying transaction can commit at a time. He chose a heavyweight lock so that it is released automatically on commit or abort.
- Scope and duration: the lock is shared by the whole cluster, not one database. A 2019 pgsql-general report (PostgreSQL 9.4, about 100 databases, 40 to 100 NOTIFYs per second) saw commits in one database blocked by commits in another, with up to 500 waiters and stalls of 1 to 1.5 seconds. The lock is held across the commit itself, which includes the WAL flush. A 2013 report found it was held noticeably longer once `synchronous_commit` waited for a remote synchronous standby. Transactions that do not notify do not take the lock.
- Impact in practice (vendor reports): Recall.ai traced periods of downtime in March 2025 to this lock under tens of thousands of concurrent writers. They saw hundreds of backends queued on it while CPU and I/O dropped, and moved notification logic out of the database. DBOS measured about 2.9K writes per second with notifications fired from triggers. Buffering notifications in memory and sending them in periodic batches raised this to about 60K per second, at 15 to 100 ms extra latency, with polling as the fallback for missed notifications. They attribute the ceiling to the lock serialising notifying commits and defeating group commit.
- Status of upstream fixes:
  - A January 2026 master commit by Joel Jacobson, committed by Tom Lane and targeting PostgreSQL 19, adds a shared map from channel to listeners and advances idle, uninterested listeners directly. This gives large throughput and latency gains when many listeners each care about few channels. It does not remove the commit lock or change delivery semantics, which DBOS also points out.
  - A separate pgsql-hackers patch, "Write Notifications Through WAL" (Rishu Bagga, September to November 2025), would write payloads to WAL and stop holding the global heavyweight lock from `PreCommit_Notify` to the end of the transaction. It reported roughly double the throughput under 100 concurrent clients. It remains uncommitted, listed as "Needs review" in the closed PG19-4 commitfest.

### Implications for a polling-replacement design

These properties support a hybrid design. The durable event table stays the source of truth, and consumers keep tracking their own positions. `NOTIFY` only shortens the polling interval. A periodic fallback poll covers notifications lost during disconnects, restarts, failovers or client bugs, and catches up after reconnecting and re-running `LISTEN`. Notifying commits all queue on one lock and a stalled listener can block writes, so the write path should send small, collapsible payloads, consider sending `NOTIFY` outside the hot write transaction or batching it, keep listener connections in autocommit and never idle in a transaction, and monitor `pg_notification_queue_usage()`.
