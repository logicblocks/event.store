# How does logical decoding through replication slots compare with LISTEN and NOTIFY and with table polling as a push source for event-store consumers, in delivery latency, write overhead, slot retention risk and operational complexity?

## Question

As a source of new-event signals or event data for consumers of a PostgreSQL event table, how does logical decoding through a replication slot compare with LISTEN and NOTIFY and with plain table polling? The comparison covers four things: how quickly events reach consumers, what each approach costs on the write path, the risk of a slot retaining server resources, and how hard each is to run.

## Findings

### Summary

Logical decoding is the only one of the three that is a true server push of committed data. It delivers in commit order and takes no lock on the commit path. It is also the hardest to run and the most dangerous to get wrong. It needs a privileged replication connection, a server-wide WAL setting (which needs a restart before PostgreSQL 19), and a server-side slot that keeps WAL and catalog rows until a consumer acknowledges them. Hard limits on slots and WAL senders are small and also need a restart to change. And the Python stack this library uses has a gap: psycopg 3 has no replication-protocol support. LISTEN and NOTIFY is cheap to run but only wakes consumers up, and it serialises notifying commits. Polling adds nothing to writes and carries no retention risk. Its costs are latency tied to the poll interval and the work of handling sequence gaps that logical decoding avoids altogether.

| Dimension | Logical decoding (slot) | LISTEN and NOTIFY | Table polling |
|---|---|---|---|
| What arrives | Committed row changes (or emitted messages), in commit order | A wake-up and payload of 8000 bytes or less; consumer then queries the table | Whatever the query returns |
| Latency floor | Commit plus WAL flush plus decode; streamed continuously over a replication connection | Commit plus delivery to an idle listening session, plus a follow-up query | About half the poll interval on average, plus any gap-wait |
| Write-path cost | Extra WAL from `wal_level = logical`, server-wide; decoding happens off the commit path | A heavyweight lock held until after commit, serialising notifying commits | None |
| Retention risk | WAL and catalog rows kept for a lagging or abandoned slot, up to disk-full or wraparound shutdown | Notification queue (8GB) blocked by a listener in a long transaction; when full, NOTIFY commits fail | None |
| Operations | Replication role, slot and WAL-sender limits, failover-slot setup, monitoring, client protocol support | One dedicated listening session; no privileges or configuration | Simplest; gap detection needed for correctness |

### Delivery latency

**Logical decoding.** The decoder emits only transactions that have committed and been flushed. "Concurrent transactions are decoded in commit order", and "transactions that were rolled back explicitly or implicitly never get decoded" (PostgreSQL output-plugin docs). The walsender waits until WAL "is flushed to disk so it can be safely sent to client" and then streams it continuously. So over the streaming protocol, latency is roughly commit, then flush, then decode, then send, with no poll interval. There are several caveats:

- With `synchronous_commit = off`, a commit may not be decoded straight away, because only WAL already flushed to disk is decoded.
- A large transaction is decoded at commit. Its changes spill to disk once they pass `logical_decoding_work_mem` (64MB by default). Streaming of in-progress transactions (pgoutput protocol version 2, PostgreSQL 14+) sends changes before commit. A consumer that must act only on committed events would have to buffer them until Stream Commit arrives.
- Failover slots (PostgreSQL 17+) used with `synchronized_standby_slots` send decoded changes only after the listed physical standbys confirm receiving the WAL. That adds a standby round trip to every delivery.
- The SQL interface (`pg_logical_slot_get_changes` and `pg_logical_slot_peek_changes`) runs from an ordinary connection, but it is a pull. Using it puts polling latency back, now against the slot instead of the table. The docs also say the function interface does not support synchronous replication.

Published end-to-end figures come from products, not from bare slots. Supabase reports that "Broadcast from Database" sustained 10,000 messages per second with a median latency of 46 ms, p95 of 132 ms and p99 of 159 ms. In that test, triggers insert rows into a published `realtime.messages` table, and Realtime reads the inserts from the WAL and fans them out to 80,000 concurrent users. Its "Postgres Changes" feature, which polls a logical slot and authorises each change for each subscriber, reports p95 latencies of 228 to 618 ms at 30 to 40 changes per second. Supabase attributes the limit to single-threaded processing ("to preserve their order") and per-subscriber authorisation, not to the slot itself. Its advice is to use Broadcast, which "sends each change once and fans it out", beyond about 3,000 subscribers. Both sets of figures include WebSocket fan-out, so they bound slot latency only loosely.

**LISTEN and NOTIFY.** Notifications are delivered only at commit, "in the order in which the transactions committed". A listening session that is itself inside a transaction gets the notification only after that transaction ends. For an event store, the notification is normally just a wake-up, so every delivery adds a query against the event table.

**Polling.** Latency is set by the poll interval. On top of that, a gap-safe poller must wait for sequence holes left by in-flight transactions. Marten's async daemon shows the extra machinery this takes. Its "high water mark" agent holds back when it finds a hole and asks "is any transaction still running that could have reserved it?" It skips the hole only once it is proven dead, or once a stale-gap timeout runs out. Logical decoding's commit-order delivery means a slot consumer never meets this problem for the live tail.

### Write overhead

**Logical decoding.** `wal_level = logical` "will increase the WAL volume, particularly if many tables are configured for `REPLICA IDENTITY FULL` and many `UPDATE` and `DELETE` statements are executed". The setting is server-wide, and AWS warns that enabling it "can increase WAL generation". An event table written only by `INSERT` is the favourable case: it needs no `REPLICA IDENTITY FULL`, and no updates or deletes are logged. The docs do not give a figure for that case, so it is an inference, not a measurement. Decoding runs in the walsender after commit, so the commit itself takes no lock. Morling says CDC "has no latency impact on writing transactions". Two further options keep write-side cost down:

- `pg_logical_emit_message` writes a transactional message into WAL with no table row, so there is nothing to vacuum. pgoutput delivers these messages when its `messages` option is on.
- Publications (`publication_names`) limit the decoded stream to the event table.

**LISTEN and NOTIFY.** PostgreSQL's `async.c` serialises notifying writers "by acquiring a special lock that we hold till after commit", taken on "database 0". In March 2025, Recall.ai saw this lock stall commits with "tens of thousands of simultaneous writers". Waits on "AccessExclusiveLock on object 0 of class 1262 of database 0" piled up while CPU and I/O usage fell, and they moved notification into the application. PostgreSQL 19 (in beta as of September 2026) changes NOTIFY "to only wake up backends that are listening to specified notifications"; previously most backends were woken. The current development source adds "direct advancement" of idle listeners' queue pointers. That same source still describes the commit-serialising lock. So the fix reduces wake-ups but does not appear to remove commit serialisation, even though Recall.ai's later update says the issue was fixed in core.

**Polling** adds nothing to the write path. Its cost is repeated reads, which scale with the number of consumers and the poll frequency.

### Slot retention risk

This is where logical decoding stands apart, and it is the main reason not to use it lightly:

- **Unbounded by default.** "Replication slots persist across crashes and know nothing about the state of their consumer(s). They will prevent removal of required resources even when there is no connection using them." Neither the required WAL nor the required system-catalog rows can be removed. "In extreme cases this could cause the database to shut down to prevent transaction ID wraparound." The psycopg2 docs warn that failing "to constantly consume and report success" can "lead to 'disk full' condition on the server". AWS warns that an unread slot can "quickly fill up your DB instance's storage".
- **Acknowledgement is the consumer's job.** The client must send standby status updates whose flushed LSN tells the server what it may discard. Consumers that stop acknowledging, rather than stopping altogether, keep resources pinned too.
- **At-least-once, not exactly-once.** "The current position of each slot is persisted only at checkpoint", so after a crash the slot may move back and resend changes. "Logical decoding clients are responsible for avoiding ill effects from handling the same message more than once." Consumers that track the event store's own global position can deduplicate.
- **No history.** Data committed before `confirmed_flush_lsn` "is not available anymore". A slot cannot replay from an arbitrary past position, so new subscriptions and catch-up must still read the event table. The slot can only serve the live tail.
- **Guard rails, which turn disk exhaustion into data-stream loss.** `max_slot_wal_keep_size` (PostgreSQL 13+, unlimited by default) and `idle_replication_slot_timeout` (PostgreSQL 18+, applied at checkpoint) invalidate slots that fall too far behind or sit idle too long. An invalidated slot reports `wal_status = lost` and an `invalidation_reason` (`wal_removed`, `rows_removed`, `idle_timeout`, `wal_level_insufficient`) and must be recreated. For monitoring, `safe_wal_size`, `wal_status` and `inactive_since` are the signals. Morling suggests alerting when a slot retains 10 to 20GB or more, or stays inactive for more than about 30 minutes. In clusters with several databases, an idle database's slot cannot advance while WAL grows elsewhere. Heartbeats through `pg_logical_emit_message` (PostgreSQL 14+) move it forward.
- **Temporary slots** "are not saved to disk and are automatically dropped on error or when the session has finished". This removes the abandoned-slot risk. The cost is that every reconnect must fill the gap from the table (an inference from the documented behaviour).

By comparison, NOTIFY's retention risk is the 8GB notification queue. A session that runs LISTEN and then sits in a long transaction blocks queue cleanup, and when the queue is full, "transactions calling NOTIFY will fail at commit". So the failure lands on writers, not on the database's disk. Polling has no retention risk.

### Operational complexity

- **Configuration and limits.** Up to PostgreSQL 18, `wal_level = logical` can only be set at server start. PostgreSQL 19 lets a server set to `replica` raise its `effective_wal_level` to `logical` automatically when the first logical slot is created, with no restart. `max_replication_slots` and `max_wal_senders` both default to 10 and can only be changed at server start. Only "one receiver may consume changes from a slot at any given time". A slot per subscription therefore does not work for hundreds of subscriptions. The practical shape is one slot per consuming process or elected leader, with fan-out inside the application (an inference from these limits).
- **Privileges and managed services.** Replication needs a role with the `REPLICATION` attribute, described as "a very highly privileged role". Amazon RDS also needs the static `rds.logical_replication` parameter, a reboot and the `rds_replication` role.
- **Connections.** A logical replication connection uses `replication=database` and only the simple query protocol. PgBouncer has supported replication connections only since 1.23.0 (July 2024).
- **Failover.** Logical slots carry over to a promoted standby only from PostgreSQL 17, and only with `failover = true` on the slot, `sync_replication_slots` on the standby and, for safety, `synchronized_standby_slots` on the primary. That last setting holds back decoding, and can stop it entirely if a listed slot is missing or invalidated. On earlier versions, or without this setup, a failover loses the slot, and consumers must rebuild their position from the table.
- **Client support in Python.** psycopg 3 has no streaming-replication support. Issue #71, opened in 2021, is still open. A maintainer wrote in June 2023 that it "needs complete redesign and implementation". Psycopg 3.3 only lets `START_REPLICATION` run without error, with "no further replication support" planned for that release. A proof-of-concept pull request (#1311, May 2026) was closed without being merged. Community workarounds are psycopg2's `LogicalReplicationConnection` (synchronous, with `select()`-style async reads and a required `send_feedback`), raw socket handling after entering COPY BOTH mode, and the SQL function interface, which brings back polling. NOTIFY and polling, by contrast, need nothing beyond what psycopg 3 already offers.
- **Ecosystem shape.** Mature CDC tools carry this complexity themselves: Debezium supports the built-in `pgoutput` plugin or its own `decoderbufs`, and Supabase's Postgres Changes polls its slot. This suggests slot consumption is usually done by a dedicated component, not by every application consumer.

### Implications for an event-store library

These are inferences from the sources above:

- Logical decoding is best treated as an optional live-tail source, not a replacement for table reads. A single slot consumer per process can turn the commit-ordered stream into in-process wake-ups, or deliver directly. That removes both NOTIFY's commit serialisation and the poller's gap problem for the tail. The event table stays the source of truth for catch-up, replay and recovery after slot loss.
- Requiring privileged replication roles, slot-limit tuning, failover-slot setup and WAL-retention monitoring is a heavy operational demand for a library. psycopg 3 also lacks protocol support. Together these argue for keeping NOTIFY wake-ups plus gap-aware table reads as the portable default, with slot-based delivery as an opt-in backend.
