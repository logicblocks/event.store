# During a primary failover or switchover on managed PostgreSQL such as Amazon RDS, Aurora or Cloud SQL, how does an idle LISTEN connection fail, and how long does a libpq reconnect using target_session_attrs take to reach the new primary?

## Question

When a managed PostgreSQL service (Amazon RDS, Aurora or Cloud SQL) fails over or switches over to a new primary, how does an idle LISTEN connection fail? How long does a libpq reconnect that uses `target_session_attrs` take to reach the new primary?

## Findings

### Summary

An idle LISTEN connection fails in one of two ways, depending on whether the old primary closes its sockets:

- **Planned events close it cleanly.** Switchovers, reboots with failover, maintenance and blue/green cut-overs terminate the server sessions. The listener sees an `admin_shutdown` error, or end-of-file, almost immediately.
- **Unplanned failures can leave it hanging.** If the host, Availability Zone or network fails, the listener may hear nothing. It stays blocked until a TCP keepalive or an application heartbeat with its own timeout finds the dead peer. With Linux defaults that takes more than two hours.

Reconnect time is set almost entirely by the platform, not by libpq. The platform must promote the standby and, on AWS, update DNS. The documented recovery times are:

- Aurora: about 30–60 s.
- RDS Multi-AZ DB cluster: under 35 s.
- RDS Multi-AZ instance: 60–120 s.
- Cloud SQL HA failover: about 60 s.
- Cloud SQL planned maintenance: under 1 s to under 30 s.

On top of that, the client adds three delays:

- how long it takes to detect the failure;
- up to one DNS TTL (5 s on RDS);
- its retry interval.

libpq's own work per connection attempt is small, unless it has to wait out `connect_timeout` on an address that no longer answers.

`target_session_attrs` does not make reconnecting faster. Its value is that it refuses servers that would leave a listener silently deaf. No vendor publishes reconnect timings measured specifically for libpq with `target_session_attrs`. The figures below are platform recovery times, with the client-side delays estimated from documented defaults.

### How the idle LISTEN connection fails

**Clean termination (planned switchovers and most managed failovers).** Several managed operations shut the old primary down in an orderly way:

- A manual failover of an RDS Multi-AZ DB cluster "first terminates the primary DB instance".
- An RDS blue/green switchover "drops connections to the DB instances in both environments and doesn't allow new connections".
- During Cloud SQL maintenance, "existing connections are dropped".
- A Cloud SQL HA failover closes "any existing connections to the primary instance and read replicas".

PostgreSQL's fast shutdown sends every server process SIGTERM, "which will cause them to abort their current transactions and exit promptly". A session ended this way reports SQLSTATE `57P01 admin_shutdown`. AWS documents that, through RDS Proxy during a blue/green switchover, PostgreSQL queries return `AdminShutdown: terminating connection due to administrator command`.

For an idle listener, this error and the TCP close arrive unprompted. The socket becomes readable, so a psycopg loop waiting in `notifies()` or on the connection's file descriptor wakes up straight away. psycopg reports the failure as `OperationalError` and marks the connection `broken`, which the docs define as "interrupted ... wasn't closed in a clean way". psycopg's own disconnection-detection recipe relies on this mechanism: wait for activity on the file descriptor, then let a query raise `OperationalError`. Detection here is effectively immediate.

**Silent loss (host crash, AZ loss, network partition).** Several RDS failover triggers mean the old primary may never send a FIN or RST:

- "unreachable due to loss of network connectivity";
- "busy and unresponsive";
- a failed storage volume.

The RDS Proxy documentation lists "waiting for a query response from a former writer that became unavailable without closing connections" as a failover hazard. An idle LISTEN connection has nothing in flight, so no retransmission timer is running. Only two things will notice the dead peer:

- **TCP keepalive.** libpq turns keepalives on by default (`keepalives=1`), but `keepalives_idle`, `keepalives_interval` and `keepalives_count` fall back to the OS. Linux defaults are a 2-hour idle time, then 9 probes 75 s apart, so a dead peer is found after about 2 h 11 min.
- **An application heartbeat.** A query written into a dead connection waits in TCP retransmission. Linux's `tcp_retries2` default gives "a hypothetical timeout of 924.6 seconds", about 15 minutes, as a lower bound. libpq's `tcp_user_timeout` (in milliseconds) can cut this short, and so can a client-side timeout around the heartbeat.

AWS's Aurora PostgreSQL fast-failover guidance sets keepalive idle 1 s, interval 1 s and count 5, which "should notify the application within five seconds when the database stops responding". AWS shows these as system-wide sysctls. A listener can set the same values on its own connection through libpq's `keepalives_*` parameters.

Cloud SQL moves a shared static IP address to the standby. The following is an inference, not something Cloud SQL documents: once the new host owns the address, a probe on the stale connection should be reset rather than lost. Even so, an idle listener that sends nothing still learns nothing until a keepalive or heartbeat fires.

**What does not survive.** LISTEN is per-session server state. NOTIFY delivers only to listeners "in the current database". A hot standby rejects LISTEN and NOTIFY outright, while a session that is merely read-only may still run them. As an inference from these documented rules, a promoted standby has no listener registrations and no queued notifications from the old primary. The consumer must:

- re-issue LISTEN on the new connection;
- treat the outage window as a gap to catch up from the durable log.

Notifications not yet consumed on the old primary, and any commits made before LISTEN is re-issued, are never delivered.

### How long the reconnect takes

The time from failure to a working listener on the new primary is roughly the sum of five parts:

1. **Detection:** immediate on a clean close; about 5 s with AWS's keepalive values; about 2 h with Linux defaults.
2. **Platform recovery:** see the table below.
3. **DNS convergence:** AWS only.
4. **Retry interval:** how often the reconnect loop tries again.
5. **libpq attempt cost:** small, plus any time spent waiting out `connect_timeout` on dead addresses.

Documented platform recovery times:

| Platform and event | Documented time | Endpoint behaviour |
| --- | --- | --- |
| RDS Multi-AZ DB instance failover, including reboot with failover | "typically 60–120 seconds"; longer with large transactions or lengthy recovery | DNS record repointed to the standby; connections must be re-established |
| RDS Multi-AZ DB cluster failover (two readable standbys) | "typically under 35 seconds" | DNS repointed to the promoted reader |
| Aurora failover with at least one replica | "typically ... less than 60 seconds, and often less than 30 seconds"; with no replica, a new primary "typically takes less than 10 minutes" | Cluster endpoint IP changes; DNS update "typically takes less than 30 seconds" |
| RDS blue/green switchover | Bounded by a timeout of 30–3,600 s (default 300 s); writes are cut off in both environments for the duration | Endpoints renamed; the old blue primary stays up, read-only |
| Cloud SQL HA failover | "unavailable for about sixty seconds" | Same static IP; no DNS step |
| Cloud SQL planned maintenance | Enterprise: under 30 s on average; Enterprise Plus: typically under 1 s | Same IP; connections dropped |

**DNS.** RDS DNS zones default to a 5-second TTL. AWS warns that caching beyond five seconds sends traffic to the old environment after a switchover. The Aurora cluster endpoint's IP changes on failover, so AWS says to "flush or reduce the time-to-live for any cached DNS information".

AWS's JVM-TTL warnings concern in-process caching. psycopg's async connect has resolved host names itself since version 3.1, so the Python process holds no long-lived cache of its own. Any OS-level or sidecar resolver cache still has to respect the 5-second TTL. Cloud SQL adds no DNS delay, because the IP address does not change.

**What libpq does.** libpq tries each listed host, and each address a name resolves to, in order. For each one it connects, authenticates, then applies `target_session_attrs`, rejecting servers that do not qualify and moving on. If no host qualifies, the connection fails: libpq does not keep retrying, so the consumer's reconnect loop must.

Since PostgreSQL 14, the server reports `in_hot_standby` and `default_transaction_read_only` at session start. The check can therefore be evaluated from those reported values.

`connect_timeout` "applies separately to each host name or IP address", and an unset value means "wait indefinitely". On Linux, an attempt to a black-holed old-primary address is then bounded only by SYN retries; the default retransmits until about 67 s. AWS's fast-failover example uses 2-second connect and login timeouts. Each extra host in the string adds up to one more `connect_timeout` to a failed attempt.

While the new primary is still recovering, attempts may be refused with `57P03 cannot_connect_now`. The loop should treat this as retryable.

**Choosing `read-write` rather than `primary`.** `primary` rejects only servers in hot standby. `read-write` also rejects servers where `default_transaction_read_only` is on.

After an RDS blue/green switchover, the old blue primary stays up, read-only through `default_transaction_read_only`, and it is not a hot standby. A listener that reconnects through a stale DNS entry with `target_session_attrs=primary` would therefore be accepted there. Read-only sessions may still run LISTEN, so the LISTEN would succeed, and the listener would then wait forever for notifications that writers now send to the green environment. `read-write` refuses that server.

Aurora's cluster endpoint can likewise briefly resolve to a former writer that is now read-only. AWS's Aurora guidance lists both the cluster (writer) endpoint and the reader endpoint, with `targetServerType=primary`, because the reader endpoint "might direct connections to the new primary ... for a short time after an Aurora Replica is promoted". With libpq, the same two-host string plus `target_session_attrs=read-write` can find the new primary before the writer endpoint's DNS has caught up.

**Faster-than-DNS options.**

- **AWS Advanced Python Wrapper.** It wraps psycopg and caches the Aurora cluster topology so it can bypass DNS. AWS reports it reconnects "typically around 7 seconds or less after the driver notices the failure", against "upwards of 30 seconds" when relying on DNS propagation.
- **RDS Proxy.** It keeps a stable IP address, avoids DNS propagation and local caching, and AWS says it cuts Aurora Multi-AZ failover times "by up to 66%". However, LISTEN pins a proxy session to one database connection. The documentation does not say a pinned LISTEN survives failover, and during blue/green switchovers it states that "existing connections to the proxy are dropped". A listener behind the proxy should therefore still expect to re-issue LISTEN.

### Practical reading for a psycopg listener

A listener configured as follows should be back on the new primary about one platform recovery time plus one DNS TTL after a clean failover:

- `keepalives_idle`, `keepalives_interval` and `keepalives_count` around 1/1/5;
- a bounded heartbeat, either with `tcp_user_timeout` or a client-side timeout, woken by psycopg 3.2's `notifies(timeout=...)`;
- `connect_timeout` around 2 s;
- `target_session_attrs=read-write`;
- a short, capped retry backoff.

That works out to roughly:

- 30–60 s on Aurora (about 7 s after detection with the AWS wrapper);
- under 35 s on a Multi-AZ DB cluster;
- 60–120 s on a Multi-AZ instance;
- about 60 s on Cloud SQL HA;
- a few seconds or less for Cloud SQL maintenance.

A silent failure adds the detection time, about 5 s with these settings. An unconfigured listener on a silently failed host can stay stuck for about two hours, far longer than the platform outage. In every case the reconnect must be followed by re-issuing LISTEN and catching up from the durable log.
