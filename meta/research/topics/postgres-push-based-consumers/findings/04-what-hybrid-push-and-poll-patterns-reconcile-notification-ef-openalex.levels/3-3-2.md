# When many consumers listen on one channel, how can notification fan-out be reduced so a single committed event does not trigger a redundant read from every listener, for example by sharing one dispatcher connection per process?

## Question

Suppose many consumers of a PostgreSQL-backed event log each LISTEN on the same
notification channel. How can the system avoid having one committed event wake
every listener and trigger a separate, mostly redundant, log read from each?
One example is giving each process a single shared dispatcher connection.
Which techniques reduce this fan-out, how much does each save, and what does
each cost?

## Findings

### The problem has a known shape

Take N consumers. Each holds its own PostgreSQL connection, each LISTENs on the
same channel, and each re-reads the event log when woken. One committed event
then costs N notification deliveries and N near-identical log queries. Many of
those reads are redundant: some consumers don't care about the event, and
others re-fetch rows that another consumer has just read.

The caching literature calls this structure a cache stampede: one trigger makes
many processes send the same expensive request to the backing store at the
same moment. Vattani, Chierichetti and Lowenstein describe it as a phenomenon
that "severely limits the performance of databases and web servers". An
operational analysis of DNS resolvers reports the same problem caused by
synchronised clients: a regular pattern of query spikes on caching resolvers.
The authors recommend fixing it in client software.

None of the catalogued records studies PostgreSQL LISTEN/NOTIFY directly. The
rest of this note applies the publish/subscribe and stampede literature to
LISTEN/NOTIFY. The cost figures come from counting operations in each design,
not from measurement.

### Separate selection from delivery, and do each once per process

Carzaniga, Rosenblum and Wolf split an event notification service into two
primary services:

- **Notification selection:** deciding which notifications match which
  subscriptions.
- **Notification delivery:** routing the matched notifications to consumers.

Eugster et al.'s survey of publish/subscribe describes subscribers that
register interest in an event, or a pattern of events, and are then notified
asynchronously through an intermediary.

When every consumer listens directly, PostgreSQL performs delivery N times and
each consumer performs selection itself, by reading the log. A per-process
dispatcher moves both jobs into one intermediary per process. It can do this
in four steps, each adding to the one before.

1. **One LISTEN connection per process.** The dispatcher owns the process's
   only listening connection. It keeps an in-memory registry of the process's
   consumers and what each subscribes to (all events, a category, or a
   stream). Server-side deliveries per commit fall from N to P, the number of
   processes. This also removes N − P listening connections and their
   notification queues. However, if the dispatcher still wakes every consumer
   and each still runs its own query, reads per commit stay at N. Sharing the
   connection alone reduces connections, not reads.

2. **Selective wake-up.** Appenders can put the selector that consumers
   subscribe on into the NOTIFY payload: a compact category or stream
   identifier, never the event body. The dispatcher then wakes only the
   consumers that match. This is selection at the intermediary, as in Siena.
   It also mirrors Google's Thialfi notification service, where applications
   register interest in a set of shared objects and are notified when those
   objects change. Reads per commit fall from N to k, the number of consumers
   the event matches.

   The wake-up is only a hint, so falling back to waking everyone is always
   safe. The dispatcher should do this whenever the payload is missing, can't
   be parsed, or names a selector it doesn't recognise.

3. **Shared read.** Consumers on the same selector are often at the same or
   nearby positions, which is the usual state for live, caught-up consumers.
   For them the dispatcher can run one log query starting at the lowest of
   their positions, then give each consumer the slice beyond its own position.
   Reads per commit fall to about one per distinct matching selector in each
   process. Consumers that are far behind must be left out of the shared read
   and catch up on their own. Otherwise one lagging consumer makes every
   shared read fetch its whole backlog.

4. **Single-flight coalescing.** If a read for a selector is already running
   when another notification for that selector arrives, the dispatcher marks
   the selector dirty instead of starting another read. When the current read
   returns, it runs exactly one follow-up read. This is the lock-style defence
   against a stampede: one request does the work while the others wait for
   its result. A burst of b notifications for one selector then costs at most
   two reads, not b.

   PostgreSQL already merges identical notifications on the same channel
   within a single transaction. It does not merge them across transactions, so
   coalescing bursts across commits is the dispatcher's job.

### Desynchronise what remains

Even with per-process sharing, two kinds of load stay synchronised across
processes:

- All P dispatchers wake on the same commit and read at once.
- Safety-net polls that started together, for example after a deployment,
  keep firing together.

Vattani et al.'s defence is probabilistic early expiration: each requester
randomly chooses to refresh some time before the deadline, so the refreshes
don't all land at once. They give algorithms for this randomisation that they
prove optimal. The DNS analysis likewise recommends software-side mitigations
for regular query spikes.

Applied here, a small random jitter can be added both to each dispatcher's read
after a notification and to each safety-net poll interval. This spreads the P
reads over a window instead of concentrating them in a spike. The cost is up
to one window of extra latency, so the jitter window should be small compared
with the consumers' latency budget.

### Across processes: a relay that reads once for everyone

Per-process sharing still leaves about P reads per commit. Production
change-distribution systems remove this last multiplication with a dedicated
relay tier between the system of record and its consumers:

- **LinkedIn's Databus** targets the case where derived data stores, indexes
  and caching tiers must be refreshed or invalidated whenever the primary
  store changes.
- **Facebook's Wormhole** is a publish/subscribe system that reliably
  replicates changes among services including TAO, Graph Search and Memcache.
  It runs at over 35 GB/s and about 50 million messages per second in steady
  state.

These records show that relay designs work at very large scale. They do not
measure where a relay starts to beat per-process sharing.

The rest of this subsection is analysis, not a finding from the records. In a
library that must depend on PostgreSQL alone, the closest equivalent is to
elect one reader across processes, for example by holding an advisory lock,
and have it pass results on. Passing results on through PostgreSQL costs
another NOTIFY or table write per event, so the relay saves little unless P is
large. Per-process sharing captures most of the saving without that extra
moving part.

### Channel partitioning: letting the server do the selection

Instead of sending everything on one channel, appenders can NOTIFY a channel
per category, and consumers LISTEN only on the channels they need. PostgreSQL
then performs the selection, so non-matching processes are never woken. The
cost is one NOTIFY per affected channel per transaction. It suits a small,
stable set of categories, and a per-process dispatcher can still hold all of
its process's LISTENs on one connection. Partitioning and payload-based
selective wake-up can be combined: the channel gives coarse selection on the
server, and the payload gives finer selection in the dispatcher.

### Hazards that sharing introduces

- **Shared fate.** If the dispatcher's single connection fails silently, every
  consumer in the process stops waking at once. Liveness detection and the
  safety-net poll therefore have to run in the dispatcher, on behalf of all
  its consumers, and the safety-net poll must still cover every consumer's
  position.
- **Head-of-line blocking.** One slow consumer must not hold up the dispatcher.
  Handing events over in memory needs a bounded queue per consumer. A consumer
  whose queue overflows should be dropped from the shared read and left to
  catch up by its own reads.
- **Correctness rules move to the dispatcher.** Two rules now apply to the
  dispatcher's shared read rather than to each consumer: the ordering of
  subscribing before reading, and the position-safety rules, such as gap
  handling and the visibility horizon. A mistake there affects every consumer
  in the process at once.
- **Payload limits.** PostgreSQL limits payload size, and identical
  notifications within one transaction are merged. The selector should
  therefore be compact, and a missing selector must mean "wake everyone"
  rather than "wake no one".

### Cost summary (derived by counting, not measured)

The table covers one committed event that matches k of N consumers spread
across P processes. Each row adds its technique to the rows above it.

| Design | Server deliveries | Log reads |
|---|---|---|
| Independent listeners | N | N |
| Shared connection per process | P | N |
| + selective wake-up | P (or fewer with channel partitioning) | k |
| + shared read per selector | P (or fewer) | about the number of processes hosting a matching consumer |
| + single-flight coalescing (bursts) | P (or fewer) | at most 2 per selector per process per burst |
| Cross-process relay | 1 to the relay | 1 |

Most of the saving comes from the first three steps, which cost nothing beyond
an in-process registry and a compact selector in the payload. Coalescing and
jitter take the edge off bursts and synchronised spikes. A cross-process relay
pays off only when the number of processes, not the number of consumers, is
the dominant cost.
