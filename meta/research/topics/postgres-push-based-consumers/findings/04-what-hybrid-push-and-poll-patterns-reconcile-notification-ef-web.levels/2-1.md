# How do PostgreSQL event stores make a read triggered by a notification gap-safe when global positions are reserved before commit, for example via high-water marks, transaction-id snapshots or commit-ordered sequences, and what latency does each approach add?

## Question

Suppose an event store gives each event a global position from a sequence, and that number is reserved when the row is inserted, before the transaction commits. How do PostgreSQL-backed event stores make sure that a consumer woken by a notification never skips an event that commits late? What does each technique add to delivery latency? The techniques covered are high-water marks with gap detection, transaction-ID snapshot horizons, and commit-ordered allocation.

## Findings

### Why a notification does not make a read safe

A PostgreSQL sequence (and therefore `bigserial`) hands out its value when `nextval` runs, not when the transaction commits. If the transaction aborts, the value is gone for good. The PostgreSQL documentation says plainly that sequences "cannot be used to obtain 'gapless' sequences". It also notes that an `INSERT ... ON CONFLICT` can use up a value without any abort at all. So two concurrent appenders can draw positions 11 and 12 and commit in the order 12 then 11, while a third draws 13 and rolls back.

LISTEN/NOTIFY does not fix this. A `NOTIFY` issued inside a transaction is "not delivered until and unless the transaction is committed", and messages from different transactions "are delivered in the order in which the transactions committed". The notification for position 12 can therefore reach a consumer while position 11 is still in flight.

Take a consumer that reacts by reading everything after its checkpoint and then moves the checkpoint to the highest position it saw. When 11 commits, that consumer never sees it. Protean's ADR-0025 calls this a "permanent, silent hole", and it happens at zero apparent consumer lag. Marten's async daemon had the same bug under bulk import, fixed in 9.16.1.

A notification says that *something* committed. It does not say that everything below it has committed. Every gap-safe design therefore adds a rule for which visible prefix of the log is safe to consume. That rule has to apply to notification-triggered reads as well as polled ones. There are four families of rule.

### 1. Commit-ordered allocation: make position order equal commit order

If the stretch from allocating a position to committing is serialised, a visible position implies that every lower position has either committed or never will.

- **Store-wide counter row.** Commanded's Elixir EventStore allocates positions for its `$all` stream with `UPDATE streams SET stream_version = stream_version + n WHERE stream_id = 0`. Every append updates that one row. An `UPDATE` takes a row lock that blocks other writers of that row "until the current transaction ends", so appends are serialised.
  - Because the counter is an ordinary row, an aborted append's increment is rolled back with it. This is an inference from PostgreSQL's transactional behaviour, and it means positions are also gapless.
  - Oskar Dudycz describes the equivalent singleton counter table as the "nuke option". He dismisses it because "it's locking the whole seq table making all the processing … sequential".
  - Protean rejected a global advisory lock for the same reason: it "would serialize all writes store-wide".
- **End-of-transaction advisory lock.** Kevin Grittner, writing on the pgsql-general list, gives the cheapest form: "As the very last thing before commit, take out an exclusive transactional advisory lock (pg_advisory_xact_lock) … Under cover of that lock, assign the number". This serialises only the tail of each transaction. Transaction-scoped advisory locks are released automatically at transaction end. Grittner also warns that commit order is not the same as the apparent serial order of serializable transactions.
- **Partitioned serialisation.** Message DB's `write_message` always calls `acquire_lock` before inserting. That function takes a transaction-scoped `pg_advisory_xact_lock` on a hash of the stream's *category*. Positions are therefore commit-ordered within a category, so category readers are safe. Reads across categories (an "all events" read) are not, which is the exact gap ADR-0025 exists to close.
- **Logical decoding (out of band).** "Concurrent transactions are decoded in commit order", and "Transactions that were rolled back explicitly or implicitly never get decoded." A consumer driven by the write-ahead log (WAL) therefore receives a commit-ordered stream without serialising writers. The costs are operational:
  - a replication slot holds WAL and catalog rows "as long as they are required by a replication slot";
  - after a crash the slot may replay from an earlier LSN (log sequence number);
  - each slot serves a single consumer.

**Latency:** nothing is added on the read side. A notification-triggered read can take everything visible, and with a counter row the log has no gaps to detect. The whole cost moves to writers. Every append within the lock's scope waits for the previous holder to commit, so throughput in that scope is limited by how long each transaction holds the lock. That hold includes the commit itself (an inference, not a measured figure). Locking only at the end of the transaction keeps the hold, and so the cost, small. Message DB's per-category lock keeps the cost local to each category.

### 2. Transaction-ID snapshot horizon (xmin)

Each event is stamped with `pg_current_xact_id()` in an `xid8` column. Readers then:

- read only rows whose transaction ID is below `pg_snapshot_xmin(pg_current_snapshot())`;
- order by `(transaction_id, position)`;
- resume from a tuple checkpoint.

The PostgreSQL documentation states the guarantee directly: "All transaction IDs less than xmin are either committed and visible, or rolled back and dead." The 64-bit `xid8` type "does not wrap around during the life of an installation".

Implementations that use this pattern:

- Oskar Dudycz's outbox article gives the query `WHERE ((transaction_id = last_tx AND position > last_pos) OR transaction_id > last_tx) AND transaction_id < pg_snapshot_xmin(pg_current_snapshot()) ORDER BY transaction_id, position`.
- The eugene-khyst postgresql-event-sourcing reference implementation pairs it with LISTEN/NOTIFY wake-ups and falls back to polling every 1 second.
- Emmett's PostgreSQL event store reads batches with this filter and this ordering. It bounds batches with `(transaction_id, global_position) >= (from.transactionId, from.globalPosition)` and returns the last message's `(transactionId, globalPosition)` as the next checkpoint.

Properties:

- **No gap detection needed.** Rolled-back and `ON CONFLICT` gaps don't matter, because the horizon only moves past transactions that have finished.
- **The order is neither commit order nor position order.** Xids are assigned when a transaction first writes, so "lower-numbered xids started writing before higher-numbered xids". The consumer's cursor must therefore be the `(transaction_id, position)` tuple; a single global position no longer works as the checkpoint. Oskar Dudycz notes that the ordering "respects when the transaction was started, not when the message was appended".
- **Latency is set by the oldest writing transaction in the whole cluster.** An event becomes readable only once every transaction with a lower xid has finished. Xids come from "a global counter used by all databases within the PostgreSQL cluster", so the horizon can be held back by any writing transaction anywhere, including:
  - a migration or a batch job in another database;
  - a session left idle inside a transaction;
  - a prepared two-phase transaction, which `pg_xact_status` reports as "in progress" until it is resolved.

  eugene-khyst warns that a long-running transaction "will effectively 'pause' all event handlers". Sequin rejected the approach as "a non-starter" because any long-running transaction on any table blocks reads. In a typical online-transaction (OLTP) workload the added latency is roughly the remaining duration of the slowest concurrent writing transaction, usually milliseconds, but it has no upper bound.
- **The blocker may never send a wake-up** (an inference from NOTIFY semantics). Suppose another appender holds the horizon back. Its own notification is delivered after it commits, in commit order, and that wakes the consumer to re-read. But if the blocker is an unrelated transaction, its commit sends nothing on the event channel. A notification-driven consumer stuck behind the horizon therefore needs a timed re-check.

### 3. High-water mark with gap detection

This family keeps a single global position. The consumer reads the contiguous run from checkpoint + 1, stops at the first missing position (the first gap), and moves on only once the gap is filled or judged dead.

- **Protean ADR-0025 ("settle-then-process", applied only to cross-category reads).**
  - Process the contiguous run straight away.
  - Hold at the first gap.
  - Give up on an unfilled gap after `gap_timeout_seconds`, which defaults to 5 seconds.
  - Never move the durable checkpoint past an unprocessed position.

  Positions above a genuine gap are delayed by up to the timeout, and setting it to zero turns gap safety off. Readers of a single category pay nothing, because Message DB-style category locks already order those commits.
- **Marten.** The high water mark is "the furthest known event sequence that the daemon 'knows' that all events with that sequence or lower can be safely processed in order". The documentation notes that "Most holes fill in within milliseconds". A rolled-back `SaveChangesAsync` or the loser of an optimistic-concurrency conflict "burns its sequence numbers permanently".

  Older versions skipped a stale gap after a wall-clock threshold (`StaleSequenceThreshold`, 3 seconds by default) and polled every 250 ms. Marten discussion #4953 found four ways that design skipped committed events without warning:
  - the gap detector ran several statements, each with its own READ COMMITTED snapshot, so the snapshots disagreed;
  - projection rebuilds skipped gaps unconditionally;
  - on an idle store, a fallback jumped to `HighestSequence - 32`, which could leap past thousands of uncommitted reservations;
  - the skip decision rested on elapsed time rather than evidence about transactions.

  Marten 9.16.1 (July 2026) replaced the timer with *transaction evidence*. A gap is skipped only when "no candidate transaction from before the gap was first observed remains". The daemon checks three things: write locks on `mt_events`, open transactions in `pg_stat_activity` that predate the gap, and in-progress xids in `pg_current_snapshot`. It rules out sessions that have "provably executed nothing since before the gap's sequence numbers were handed out".
  - The opt-in `SkipStaleGapsDespiteLiveTransactionsAfter` (default null) trades safety for progress.
  - Skips can be recorded in `mt_high_water_skips` when advanced tracking is enabled.
  - `QuickAppend` mode is recommended because it is "substantially less likely to lead to gaps".
- **Sequin (exact tracking of in-flight writes with advisory locks).** Each inserter takes a shared marker advisory lock plus a transaction-scoped exclusive advisory lock keyed on its own sequence value. Readers compute the safe ceiling as the minimum sequence value currently locked, joined through `pg_locks`. Writes stay "uncapped, parallel". Advisory locks share the server lock table, which is sized from `max_locks_per_transaction` and `max_connections` and typically holds "tens to hundreds of thousands" of locks.

**Latency:** usually the gap is just an append still in flight. The hold then lasts until that append commits, typically milliseconds, and its own notification wakes the consumer.

Gaps left by rollbacks or `ON CONFLICT` never produce a notification. For those, the consumer waits until its next timed re-check plus however long the gap takes to be judged dead:

- With **wall-clock timeouts** (5 s in Protean, 3 s in older Marten, 250 ms polling in Marten), latency is bounded, but an append slower than the timeout is lost.
- With **evidence-based proof** (Marten 9.16.1, Sequin), the gap is released as soon as no candidate transaction remains. Those checks only look at transactions that could actually have reserved the gap, so they are narrower than the cluster-wide xmin horizon. Unless the opt-in override is used, nothing caps how long a live candidate can hold the mark.

### 4. Gap-aware tracking tokens (record gaps instead of waiting)

Axon Framework's JDBC and JPA storage engines do not hold at a gap. A `GapAwareTrackingToken` stores the highest index seen plus the set of "sequence numbers of events that may have been inserted but have not been committed". On each fetch the engine checks whether those gaps have since filled. Gaps are dropped in three cases:

- after `gapTimeout`, which defaults to 60,000 ms;
- when they fall more than `maxGapOffset` (default 10,000) behind the index;
- through clean-up, which starts once a token carries more than `gapCleaningThreshold` (default 250) gaps.

**Latency:** none for events above a gap. Late-filling events are delivered out of global order, so handlers must tolerate reordering. An event that commits after its gap has timed out is never delivered to that tracker.

### Comparison

| Approach | Read latency added | Write-side cost | Order delivered | Residual risk |
|---|---|---|---|---|
| Commit-ordered allocation (counter row, end-of-transaction advisory lock) | None | All appends in the lock's scope are serialised | Commit order equals position order | Throughput ceiling; a per-category scope leaves cross-category reads unsafe |
| Logical decoding | Commit plus decode time | None on the write path; slot and WAL retention | Commit order | Slot management, WAL growth, one consumer per slot |
| Xid horizon (`pg_snapshot_xmin`) | Until every lower-xid writing transaction in the cluster ends | One `xid8` column | Order of first write; tuple checkpoint | Unbounded stall from long or idle transactions, or prepared transactions, anywhere in the cluster |
| High-water mark, wall-clock timeout | Milliseconds typically; up to the timeout for dead gaps | None | Position order | Loses appends slower than the timeout |
| High-water mark, evidence-based or advisory-lock ceiling | Milliseconds typically; until candidates end | Catalog queries, or advisory locks per insert | Position order | Stalls behind a live candidate unless an override is set |
| Gap-aware token | None | None | Out of order for late fills | Loses events that commit after the gap timeout |

### What this means for a notification-driven consumer

This section is synthesis drawn from the sources above.

- **Treat the notification only as a wake-up.** Apply the same safe-prefix rule on every read, whether it was triggered by a notification or by a poll, and persist only the safe checkpoint: the contiguous prefix or the horizon tuple, never the highest position seen.
- **Expect some gaps to close without any notification.** Notifications arrive after commit and in commit order, so a gap caused by an in-flight appender is closed by that appender's later notification. Three kinds of gap close silently:
  - rollbacks;
  - `ON CONFLICT` burns;
  - non-appending transactions that hold back the xmin horizon.

  A consumer holding at a gap or horizon therefore needs a short timed re-check, at about the gap-check interval, in addition to any long safety-net poll.
- **Choose by what the library can change.**
  - If cross-store append concurrency is modest, commit-ordered allocation is the simplest choice and adds no read latency.
  - If the schema and the checkpoint API can change, the xid horizon gives safety without any detection logic, but exposes consumers to cluster-wide stalls from long-running transactions.
  - If a single global position must be kept alongside parallel writers, a high-water mark with evidence-based or advisory-lock gap proof is the established route. Skipping gaps on a wall-clock timer alone is known to lose events.
