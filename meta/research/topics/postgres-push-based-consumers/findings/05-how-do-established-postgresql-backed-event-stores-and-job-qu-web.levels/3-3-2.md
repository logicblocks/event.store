# Should a Python event-store library share one psycopg 3 LISTEN connection across all in-process consumers and fan wake-ups out by channel, and how should that notifier handle subscribe, unsubscribe and backpressure?

## Question

Should a Python event-store library built on psycopg 3 run one shared, dedicated
LISTEN connection per process (or per event loop) and route wake-ups to
consumers by channel, rather than giving each consumer its own LISTEN
connection? And how should that shared notifier handle consumers subscribing,
unsubscribing, and consuming wake-ups more slowly than they arrive?

## Findings

### Short answer

Yes. psycopg 3's connection model, PostgreSQL's signalling behaviour on current
releases, and the consistent practice of mature PostgreSQL-backed queues all
point to one dedicated, autocommit LISTEN connection per process (one per event
loop for asyncio code). That connection has a single reader loop that routes
each notification by channel to a reference-counted table of subscribers.
Subscribe should be awaitable and return only once the LISTEN has run, so the
consumer can then do its catch-up read safely. Unsubscribe should remove the
subscriber at once but send UNLISTEN only when the last subscriber on a
channel leaves. For backpressure, treat a notification as a wake-up hint and
coalesce it, using a per-subscriber flag or event, so no queue builds up and
nothing needs dropping. The reader loop must never block on a subscriber.
Consumers still need periodic polling as a backstop.

### Why one dedicated, shared connection

**psycopg serialises everything on a connection, and the notifies generator
holds the lock.** psycopg connections are thread-safe, but "query execution
and results retrieval on a connection is serialized: only one cursor at time
will be able to run a query on the same connection". The source for
`AsyncConnection.notifies()` wraps its whole wait loop in `async with
self.lock:`. So while a consumer is iterating the generator, nothing else can
run a query on that connection. A user report of exactly this deadlock was
psycopg ticket 340: another coroutine's `execute()` hung while the generator
was waiting. The fix was the `timeout` and `stop_after` parameters added in
psycopg 3.2. A LISTEN connection therefore cannot double as a query
connection, so it has to be dedicated. Running one per consumer multiplies
connections for no benefit.

**Pooled connections are the wrong home for LISTEN.** LISTEN is
session-scoped. asyncpg's pool runs `UNLISTEN *` on reset and warns if
listener callbacks are still registered when a connection goes back to the
pool. PgBouncer marks LISTEN as "Never" supported in transaction pooling
(NOTIFY works). Procrastinate, the closest psycopg 3 prior art, opens a
standalone `autocommit=True` connection for listening, outside its pool.
GoodJob checks a connection out of the ActiveRecord pool and removes it from
the pool. Oban uses a dedicated `Postgrex.SimpleConnection`, and its docs warn
that LISTEN does not work behind PgBouncer in transaction or statement mode.

**On PostgreSQL 18 and earlier, every listening connection is woken by every
NOTIFY in its database.** The REL_18_STABLE `async.c` header says
`SignalBackends()` "sends a PROCSIG_NOTIFY_INTERRUPT signal to every listening
backend (we don't know which backend is listening on which channel so we must
signal them all)". Each woken backend then scans the shared queue and filters
by its own channel list. With N consumers per process each holding their own
LISTEN connection, every append's NOTIFY wakes N backends per process instead
of one. A January 2026 commit to the PostgreSQL development branch ("Optimize
LISTEN/NOTIFY via shared channel map and direct advancement", Joel Jacobson,
reviewed by Tom Lane) adds a shared hash of which backends listen on which
channels, so uninterested listeners are skipped. It reports "integer
multiples" of NOTIFY throughput gain when many listeners exist but few care
about a given message. That change is in the development branch, expected in
PostgreSQL 19, not in 18. Even after it ships, separate per-consumer
connections still cost backends and connection slots.

**Mature systems converge on this shape.** River has one `Notifier` per client
with `subscriptions map[NotificationTopic][]*Subscription` over a single
listener connection. Oban has one notifier connection per node and relays to
registered processes. GoodJob has one Notifier per process, listening on a
background thread and passing each message to its recipients. Graphile Worker
creates "a client dedicated to listening for new jobs" per worker pool and
"nudges" idle workers. Procrastinate has one listener task per worker that
sets an `asyncio.Event`.

**Limits of sharing.** psycopg connections "are not process-safe", so each
process (and in practice each asyncio event loop) needs its own notifier. The
shared connection is also a single point of failure for every consumer's
wake-ups. That is acceptable only because consumers keep polling as a backstop
(see below).

### One reader loop, routing by channel

The reader should be a single loop: one task or thread that owns the
connection, consumes notifications, and looks up `notification.channel` in a
routing table. Avoid giving each subscriber its own `notifies()` loop on the
shared connection. PgQueuer's psycopg driver shows the trap. Each
`add_listener()` call starts its own watcher task iterating
`connection.notifies(timeout=1.0, stop_after=1)`, and passes every payload to
its callback without checking the channel. Multiple watchers on one
connection therefore compete for the lock and receive notifications for
channels they did not register for.

psycopg offers two consumption styles, and its docs say to "use only one of
the two methods". Since 3.2.10, mixing them raises a `RuntimeWarning`:

- `add_notify_handler()` callbacks fire only "during a connection operation,
  such as a query". They run synchronously inside psycopg's notify callback
  (`for cb in self._notify_handlers: cb(n)`). An idle dedicated connection
  using handlers alone would therefore need a periodic query to deliver
  anything.
- The `notifies()` generator waits on the socket and yields "as soon as they
  are received". This suits a dedicated reader.

The minimum psycopg version matters. psycopg 3.2.4 added a backlog deque so
that notifications arriving while the generator is not running (for example,
while the notifier briefly leaves it to run LISTEN) are not lost. 3.2.10 fixed
a leak where that backlog grew without bound if `notifies()` was never called
again. A notifier that relies on stepping out of the generator should require
psycopg 3.2.10 or later.

### Subscribe

1. **Reference-count per channel.** River issues LISTEN only when the first
   subscriber for a topic arrives. Oban filters out channels that already have
   listeners before issuing LISTEN. Re-issuing LISTEN would be harmless
   anyway: PostgreSQL does nothing if the session already listens on the
   channel.
2. **Make subscribe return only after the LISTEN has run.** PostgreSQL's
   LISTEN docs give the rule: first execute and commit LISTEN, then inspect
   the database state in a new transaction, then rely on notifications for
   later changes. "The first few received notifications might refer to
   updates already observed ... but this is usually harmless." LISTEN "takes
   effect at transaction commit", so the notifier connection must be in
   autocommit. psycopg's docs also require autocommit for timely
   notifications. River waits for the first subscriber's LISTEN to complete
   before returning. For an event store, the order is: subscribe (LISTEN
   committed), then read from the stored checkpoint, then wait for wake-ups.
3. **Get the LISTEN past the lock.** Because the generator holds the
   connection lock, a subscribe request cannot just call `execute("LISTEN
   ...")` while the reader is waiting. River's notifier has the same problem
   in Go: "Waiting for a notification locks an underlying connection, so
   infrastructure elsewhere in the notifier must preempt it". It sends the
   operation on an interrupt channel, cancels the wait, and drains all
   pending listen and unlisten operations before waiting again. Both of the
   following patterns follow from the psycopg evidence; neither is a
   documented psycopg recipe.
   - Have subscribe requests enqueue a command and return a future. Run the
     reader as a loop over `notifies(timeout=t)`. On each exit it applies the
     queued LISTEN and UNLISTEN commands, resolves the futures, and re-enters.
     The 3.2.4+ backlog keeps notifications that arrive in between, and
     subscribe latency is bounded by `t`. PgQueuer releases the lock by
     re-entering `notifies(timeout=1.0, stop_after=1)` in a loop.
   - Alternatively, cancel the waiting task to run the command immediately,
     as River cancels its wait.
4. **On reconnect, re-LISTEN everything, then wake everyone.** River re-issues
   LISTEN for every topic in its subscription map after connecting. Oban
   documents that "every connection, including a reconnect after a crash,
   listens on all channels that have registered listeners", and that
   registrations are "durable across notifier restarts". Notifications sent
   while the connection was down are lost. Waking every subscriber after
   re-LISTEN so each does a catch-up read is the natural complement. That is
   an inference: River does not tell subscribers about reconnects and leaves
   recovery to the poll interval.

### Unsubscribe

Remove the subscriber from the routing table at once, so it gets no further
wake-ups. Send UNLISTEN only when the channel's reference count reaches zero.
River does this ("If this is the last subscription on the topic, unlisten if
we're connected") and routes the UNLISTEN through the same interrupt path as
LISTEN. A notification already in flight for a channel with no subscribers is
simply dropped at dispatch. Oban removes listeners whose process has exited,
so a crashed consumer does not leak a channel registration. The Python
equivalent is to tie a subscription's lifetime to a context manager or to the
consumer task.

### Backpressure

There are two buffers to protect.

**The server-side queue and the psycopg backlog: keep draining.** PostgreSQL
cannot clean up its notification queue (8 GB by default) "if a session
executes LISTEN and then enters a transaction for a very long time". When the
queue is full, "transactions calling NOTIFY will fail at commit", and
`pg_notification_queue_usage()` shows how full it is. A listening session also
receives notifications only between transactions. So the notifier connection
must stay in autocommit, never open a transaction, and keep reading. On the
client side, psycopg's backlog is an unbounded `deque`. In psycopg issue 1091
it grew at roughly 200 MB per hour at 10,000+ notifications per minute because
nobody drained it. If the reader stalls, memory grows.

**Fan-out to subscribers: never block the reader; coalesce rather than
queue.** The established systems differ here:

- River puts notifications into a 1,000-slot buffer with a non-blocking send.
  When the buffer is full it logs "Dropping notification due to full buffer".
  A separate goroutine calls each subscriber's function synchronously, so slow
  subscribers stall every topic.
- Oban `send`s each registered process a message, so backpressure lands in
  unbounded Erlang mailboxes.
- GoodJob calls each recipient in turn on the listening thread.
- Graphile Worker nudges only idle workers.
- Procrastinate's handler just calls `self._new_job_event.set()`. Its fetch
  loop waits on that event, a polling sleep, or stop, whichever comes first.

For an event store whose consumers read from their own checkpoint, a
notification carries no information that has to be kept. Ten notifications
while a consumer is busy mean the same as one: "read again". The bounded,
lossless design is a per-subscriber coalescing signal, such as an
`asyncio.Event`, a `threading.Event`, or a queue of size one filled with
`put_nowait` and ignoring "full". The reader sets it without blocking. The
consumer clears it before reading, so a wake-up that arrives mid-read
triggers one more pass. Memory then scales with the number of subscribers,
not the notification rate, and nothing has to be dropped. Two more points:

- Subscriber code must never run on the reader. psycopg handlers run inside
  libpq processing, and River's synchronous delivery shows how one slow
  callback delays all channels.
- Under heavy append load, a consumer-side cooldown caps query rate. River's
  `FetchCooldown` is the "minimum amount of time to wait between fetches ...
  Jobs will only be fetched at most this often".

### Failure, health and the polling backstop

Every system examined keeps polling alongside notifications:

- River has `FetchPollInterval` ("this provides a fallback") and a
  `PollOnly` mode for PgBouncer transaction pooling.
- Procrastinate has `fetch_job_polling_interval`.
- Oban's Stager switches to local polling mode when the notifier status is
  `:isolated`, "to ensure jobs keep processing when staging or database
  driven notifications fail".

GoodJob exposes `connected?` and `listening?` so callers can tell whether the
notifier is healthy. GoodJob runs `SELECT 1` every 10 seconds and River pings
after 5 seconds without notifications, to keep the dedicated connection alive
and detect when it has died. Both reconnect with backoff: GoodJob after 5
seconds, River and Graphile Worker with exponential backoff, Graphile Worker
capped at 60 seconds. A shared psycopg notifier should expose a similar health
state, so consumers can shorten their poll interval while it is down. It
should also wake all subscribers once it is listening again.
