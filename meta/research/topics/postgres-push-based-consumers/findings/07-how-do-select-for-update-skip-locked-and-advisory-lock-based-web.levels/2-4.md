# What are the failure-recovery and connection-usage trade-offs between holding a row or advisory lock for a whole handler transaction and claim-and-mark with leases or visibility timeouts for long-running event handlers?

## Question

When a PostgreSQL-backed consumer takes a unit of work (an event, a batch, or a stream partition) and runs a handler that may take a long time, it can either keep a lock alive for the whole handler — a `FOR UPDATE` row lock or a transaction-level advisory lock inside one long transaction, or a session-level advisory lock on a dedicated connection — or it can claim the work in a short transaction by writing an owner and expiry ("claim-and-mark"), then release the connection, so the claim lapses unless renewed. What does each approach cost in failure recovery (how quickly and how safely work is recovered after a crash, hang or network partition) and in connection usage?

## Findings

### Three designs, not two

Production PostgreSQL queues fall into three families, and the session-level advisory lock behaves differently enough from the in-transaction lock to be treated on its own:

1. **Lock held by the handler's transaction.** `SELECT ... FOR UPDATE SKIP LOCKED` (or `pg_advisory_xact_lock`), then run the handler and commit its writes and the acknowledgement or checkpoint in that same transaction. PostgreSQL releases row locks "at transaction end or during savepoint rollback", and transaction-level advisory locks "are automatically released at the end of the transaction, and there is no explicit unlock operation".
2. **Session-level advisory lock held on a connection.** Que, GoodJob's default `:advisory` strategy and Marten's HotCold leader election all use this. A session lock "is held until explicitly released or the session ends", and it survives rollback: "a lock acquired during a transaction that is later rolled back will still be held following the rollback".
3. **Claim-and-mark with a lease, visibility timeout or heartbeat.** pgmq's visibility timeout, Graphile Worker's `locked_at`/`locked_by`, River's running state with a rescuer, Solid Queue's claimed executions with process heartbeats, Procrastinate's `doing` status with worker heartbeats, and GoodJob's `:skiplocked` strategy. The claim is an ordinary committed row update. No lock is held while the handler runs.

### Failure recovery

**Lock held by the transaction: the database is the failure detector, and the commit is the fence.** If the worker process dies, its socket closes, the server rolls back, and the work becomes claimable again at once. Nothing has to wait for a timeout. Because the handler's database writes and the acknowledgement commit together, a worker that lost its connection cannot commit late, so its database effects are fenced automatically. This is the property Que recommends using ("It's best to destroy the job in the same transaction as any other changes you make"). River offers it as an option with `JobCompleteTx`: "A successful commit guarantees that the job will never rerun." Without it, River says there is "a small chance of failure between when a job's work function is invoked and when a River client sets it as complete."

The weak case is when the worker host disappears without closing the socket (power loss, network partition). PostgreSQL detects a dead connection "only at the next interaction with the socket". `client_connection_check_interval` polls only "while running queries", so it does not help a backend sitting idle in transaction while the client works. TCP keepalive defaults to the operating system's settings. Linux's defaults are a 2-hour idle time plus 9 probes 75 seconds apart (about 11 more minutes), so a lock can stay orphaned for over two hours unless keepalives are tuned or a server timeout ends the session. Two such timeouts exist. `idle_in_transaction_session_timeout` exists "to ensure that idle sessions do not hold locks for an unreasonable amount of time". `transaction_timeout`, added in PostgreSQL 17, terminates "any session that spans longer than the specified amount of time in a transaction". Both must be longer than the slowest legitimate handler, so for long-running handlers they cannot be tight. The recovery delay after a partition ends up roughly as long as the longest allowed handler. This is the same trade-off a lease forces, but without a heartbeat to shorten it.

A second problem follows from rollback being all-or-nothing: an attempt counter or failure record written inside the failed transaction is rolled back with everything else. Unless attempts are recorded in a separate transaction, a "poison" event that crashes the handler can be retried forever. Side effects outside the database (HTTP calls, emails) are not undone by rollback either, so delivery to external systems is still at-least-once.

**Session-level advisory lock: immediate release on process death, but lock loss is silent.** Que states that if a worker process dies, its jobs "immediately become available for any other worker to pick up". GoodJob relies on the same behaviour. The lock is tied to the session, not a transaction, so the handler can commit its work in several short transactions. That also means the fencing the commit provided in the first design is gone. Marten documents the main hazard. When "the connection holding the lock is lost — a database restart or a fail-over", the client can keep believing it is leader: "Without monitoring, `HasLock` keeps reporting true after the lock is gone, … two nodes can end up running the same projection." Marten enables connection monitoring by default for this reason. Session locks also need explicit, matched unlocks ("for each completed lock request there must be a corresponding unlock request"), and an unlock "is effective even if the calling transaction fails later". Bookkeeping errors therefore leak locks or release them too early.

**Claim-and-mark with leases: recovery is time-based, and duplicates are the price.** A claimed row stays claimed until its lease runs out, whatever happens to the worker. pgmq: "If the message is NOT deleted or archived within the visibility timeout, it will become visible again and can be read by another consumer." Its guarantee is "exactly once delivery of a message within a visibility timeout", and nothing beyond that window. Every implementation faces the same tension between timeout length and duplicate risk. River's rescuer comment is the clearest statement: rescue "can result in repeat or duplicate execution of a job that is not actually stuck but is still working… Setting a value too low will result in more duplicate executions, whereas too high of a value will result in jobs being stuck for longer than necessary before they are retried". River defaults to 1 hour and requires the rescue threshold to exceed the job timeout. Graphile Worker uses a fixed lock: a crashed worker's jobs "will remain locked for 4 hours before they can be re-attempted". It offers a manual `force_unlock_workers` with the warning "Do NOT pass any alive worker ids to this method or Bad Things may happen." AWS SQS documents the same trade-off ("setting the visibility timeout too high can delay the reappearance of unprocessed messages"). Its remedy is to start short and "implement a heartbeat mechanism to periodically extend the visibility timeout".

Heartbeats separate how fast failures are detected from how long handlers run. Procrastinate workers update a heartbeat "every 10 seconds by default". Jobs in `doing` belonging to workers with no heartbeat for 30 seconds are treated as stalled and can be retried by a periodic task. Solid Queue heartbeats every 60 seconds and treats a process as dead after 5 minutes. It then marks that process's claimed jobs as failed (`ProcessPrunedError`) rather than retrying them. Recovery policy after expiry (retry, discard, or fail to a dead-letter path) is therefore a separate design choice.

A lease can expire while its holder is still alive but stalled, for example in a long GC pause or behind a network delay. Kleppmann's analysis applies directly: "if the GC pause lasts longer than the lease expiry period, and the client doesn't realise that it has expired, it may go ahead and make some unsafe change". The fix is a fencing token — a number that increases on every acquisition and is checked by the store that accepts the writes. In PostgreSQL that means making the completion or checkpoint update conditional on the claim token the worker still holds. Event handlers that must preserve order have a further risk: if a lease on a stream or partition expires and a successor processes the next events while the original holder is still running, effects can be applied out of order. SQS FIFO avoids this by not releasing the next message in a group "until the in-flight message is either deleted or the visibility timeout expires". The underlying exposure is the same.

### Connection usage

**Lock held by the transaction** keeps one connection checked out, inside an open transaction, for the full handler duration of every in-flight unit of work. The database's connection count therefore caps handler concurrency. Behind PgBouncer in transaction mode the long transaction still works, but it pins a server connection for its whole duration, which defeats pooling. The open transaction also has an MVCC cost: "an open transaction prevents vacuuming away recently-dead tuples that may be visible only to this transaction", and psycopg's documentation warns that sessions left idle in transaction hold locks and bloat tables. In Brandur's benchmark of the Que queue, one long-lived transaction left nearly 100,000 dead rows that could not be removed. Lock acquisition slowed from under 10 ms to over 100 ms, and the backlog grew to about 60,000 jobs within an hour, because index scans had to step over dead tuples to find a lockable job. High-churn queue and checkpoint tables are the most exposed.

**Session-level advisory locks** need no open transaction, so they avoid the vacuum cost. Marten notes that the session holding its leadership lock "keeps no transaction open while it is the leader". They do require a dedicated, persistent session per lock holder. PgBouncer lists session-level advisory locks (and `LISTEN`) as "Never" supported in transaction pooling. GoodJob therefore documents itself as "not compatible with PgBouncer in _transaction_ mode", and budgets "1 connection per execution pool thread" plus "2 additional connections … for utility functionality (e.g. LISTEN/NOTIFY, cron, etc.)". Marten offers a transaction-scoped alternative as "the better fit behind PgBouncer in transaction pooling mode", but notes that "it means the leader keeps a transaction open for as long as it holds leadership". Choosing between these two lock forms means trading pooler compatibility against transaction age.

**Claim-and-mark** uses a connection only for the short claim, heartbeat and completion statements. The handler runs with no connection held, or opens its own short transactions, so a small pool can serve many long-running handlers, and the design is compatible with transaction pooling. GoodJob's `:skiplocked` mode "Claims jobs using `SELECT FOR UPDATE SKIP LOCKED` only. No advisory locks are held. Compatible with PgBouncer in transaction mode." Some connections remain for supporting work. Solid Queue sizes worker threads at "the queue database's connection pool size minus 2, as each worker uses connections for polling and heartbeat". Every heartbeat or lease renewal is also a write that creates a dead tuple, but these are short transactions that do not hold back vacuum.

### Implications for a notification-driven event-store consumer

- Wake-ups from `LISTEN` already need one dedicated session per process, since `LISTEN` is not supported under transaction pooling. That connection can also hold session-level advisory locks for partition ownership at no extra connection cost. It must be monitored for silent loss, and the consumer should stop work when the connection drops.
- For short handlers whose effects stay in the same database, holding the claim in the handler transaction and committing the checkpoint with the effects gives the strongest guarantee (exactly-once database effects, no fencing code) at the cost of one pinned connection per in-flight handler and an open transaction for the handler's duration. `idle_in_transaction_session_timeout` or `transaction_timeout` should be set just above the handler budget, together with tuned keepalives.
- For long-running handlers, or those with external side effects, claim-and-mark with a heartbeat-renewed lease keeps connections and vacuum healthy and allows fast failure detection. The handler must then be idempotent, and the checkpoint or completion write must be fenced by the claim token, because duplicate execution after an expired lease is expected behaviour, not a bug.
