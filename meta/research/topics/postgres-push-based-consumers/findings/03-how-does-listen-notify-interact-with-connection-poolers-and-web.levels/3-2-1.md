# When RDS Proxy fails over a pinned PostgreSQL session that has issued LISTEN, does the client connection receive an error, or is it silently reattached to a new backend that has none of its channel registrations?

## Question

When an Amazon RDS Proxy fails over a PostgreSQL client session that is pinned because it issued `LISTEN`, does the client get an error or a closed connection? Or does the proxy silently move the client connection to a new backend, which would have none of the session's channel registrations?

## Findings

### Short answer

AWS documentation never describes, in one place, a writer failover of a pinned PostgreSQL session. But every relevant statement it does make points one way: RDS Proxy does not move a pinned session onto a new backend. The pinned session ends, and the client sees an error or a dropped connection. It is not silently reattached. The documentation leaves one thing open: when an idle client finds out. The only explicit wording says the error comes back on "the next query". A listener that never sends queries may therefore not be told straight away, so it must not treat silence as a sign of health.

### LISTEN pins the session for the life of the client connection

RDS Proxy's list of conditions that pin a PostgreSQL session includes "Listening on a notification channel". The pinning contract is explicit: "When a connection is pinned, each later transaction uses the same underlying database connection until the session ends. Other client connections also can't reuse that database connection until the session ends. The session ends when the client connection is dropped." The concepts guide describes pinning as the fallback for when the proxy "can't be sure that it's safe to reuse a database connection outside of the current session", so "it keeps the session on the same connection until the session ends."

For PostgreSQL, the proxy also has no state-tracking and replay mechanism to fall back on. The pinning guide lists tracked statements and variables only for SQL Server, MySQL and MariaDB, and states that "for PostgreSQL setting a variable leads to session pinning." No documented path exists by which the proxy could re-run `LISTEN` on a replacement backend. A pinned session is defined as bound to one database connection until the client connection ends. When that database connection disappears, the documented model leaves only one outcome: the session ends.

### The "connections survive failover" guarantee describes multiplexed connections

The failover text is what makes silent reattachment look plausible. The RDS and Aurora concepts guides both say: "When the original DB instance becomes unavailable, RDS Proxy connects to the standby database without dropping idle application connections." They add that "most connections stay alive during failovers or other disruptions. Only connections that are in the middle of a transaction or SQL statement are canceled." The AWS Database Blog says the same: RDS Proxy "maintains idle client connections that weren't in the middle of a transaction during failovers," and "proactively terminates any client connections that were in the middle of executing a transaction on a failed database instance." The RDS Proxy FAQ promises that the proxy "automatically routes traffic to a new database instance while preserving application connections."

None of these passages mentions pinned sessions. The mechanism they describe keeps the client socket and borrows a fresh database connection for the next transaction. That only works when no session state is tied to the old database connection, which is the multiplexed case. This matters because a psycopg 3 listener blocked in `notifies()` has no transaction or statement in flight. From the proxy's point of view it is an idle connection, so a reader could wrongly apply the "idle connections are not dropped" sentence to it.

### Where AWS does address pinned sessions losing their instance, it says error and reconnect

The closest documented case is losing the instance that a pinned session runs on, behind a proxy reader endpoint. Both the RDS (Multi-AZ DB cluster) and Aurora versions of the proxy endpoints guide draw the distinction explicitly:

- "If the connection is multiplexed, RDS Proxy directs subsequent queries to a different reader DB instance without any interruption to your application."
- "If the connection is pinned, the next query on the connection returns an error. However, your application can immediately reconnect to the same proxy endpoint."
- "If the session is pinned, your application gets an error and must reconnect."

The RDS version adds: "If a reader instance is in an unavailable state, all client connections to that instance endpoint are closed."

These passages are about reader endpoints, not writer failover. But they apply the same pinning contract to the same kind of event, so the most reasonable inference is that a writer failover ends a pinned writer session the same way. This is an inference: no AWS page states it for the writer.

Blue/Green switchover through RDS Proxy is documented to be blunter still: "When the Green environment is promoted as the new writer, existing connections to the proxy are dropped. Applications must re-establish connections after the promotion is complete." During the transition, "On RDS for PostgreSQL, read and write queries will return `AdminShutdown: terminating connection due to administrator command`." In that path every client connection is dropped, pinned or not.

AWS's own client-side failover layer takes the same approach. When the AWS Advanced Python Wrapper's failover plugin does reconnect a connection to another instance, it raises `FailoverSuccessError`. It tells the application to "reconfigure session state to be the same as the original connection" because "any session state configuration of the initial connection is now lost." The reconnection is surfaced to the application, not hidden.

### Why silent reattachment would leave the listener deaf, and how to detect it

PostgreSQL ties notification registrations to the session: "LISTEN registers the current session as a listener," and "A session's listen registrations are automatically cleared when the session ends." A new backend therefore starts with no registrations. Any path that hands the client a fresh backend leaves it connected but receiving nothing. The same is true of a manual reconnect that forgets to re-issue `LISTEN`.

PostgreSQL provides two cheap checks for this. `pg_listening_channels()` "Returns the set of names of asynchronous notification channels that the current session is listening to." `pg_backend_pid()` "Returns the process ID of the server process attached to the current session." On a pinned connection the backend PID should never change. A changed PID, or a missing channel, means the registrations are gone, whatever the proxy did.

### The open point: when an idle listener learns of the failover

The documented wording ("the next query on the connection returns an error") does not say whether the proxy closes the client's TCP connection straight away or waits for the client's next request. The extra RDS sentence saying client connections "are closed" suggests an active close, at least for reader endpoints.

- **If the proxy closes the socket:** a psycopg 3 `notifies()` wait sees the connection end. The psycopg docs do not name the exception, but their own disconnection-detection example catches `psycopg.OperationalError`.
- **If the proxy only errors on the next query:** a listener parked in `notifies()` with no timeout receives nothing. That is indistinguishable from a quiet channel.

PostgreSQL's protocol says that on an unprompted disconnect, such as an administrator-commanded shutdown, "the backend will attempt to send an error or notice message giving the reason for the disconnection before it closes the connection". On this path that message travels to the proxy. Whether RDS Proxy passes it on to a pinned client is not documented.

The outage itself is not short. AWS gives "typically 60–120 seconds" for a Multi-AZ DB instance failover, and "typically under 35 second failovers" for Multi-AZ with two readable standbys. Notifications are not queued for a session that is not listening, so anything committed between losing the old backend and re-issuing `LISTEN` is missed. The listener has to catch up from stored state either way.

### Implications for a psycopg 3 listener behind RDS Proxy

1. **Treat any error or close on the listener connection as losing every `LISTEN` registration.** Reconnect through the proxy, re-issue `LISTEN`, then catch up from the consumer's stored position before relying on notifications again.
2. **Don't wait for the error to arrive on its own.** Bound each `notifies()` wait with `timeout`, and between waits run a cheap query on the same connection. That triggers the documented "next query returns an error". Making the heartbeat `SELECT pg_listening_channels()`, or comparing `pg_backend_pid()` with the value seen after `LISTEN`, also catches the hypothetical silent-reattachment case.
3. **The heartbeat is cheap on pinning.** The listener connection is already pinned for its lifetime, so the heartbeat holds no extra database connection. Pinned-but-idle client connections "continue to hold on to a database connection", which is the existing cost of a dedicated listener.
4. **Check the behaviour in your own environment.** The proxy publishes `ClientConnectionsClosed` and `DatabaseConnectionsCurrentlySessionPinned` metrics. A forced failover ("Reboot with failover") should show pinned listener connections being closed. If they are not, the listener depends entirely on the heartbeat to find out.
