# When a global event feed is ordered by transaction ID and then position rather than by sequence position alone, how can consumers still observe each stream's events in version order?

## Question

Event stores that order their global feed by `(transaction_id, position)`, reading only rows with `transaction_id < pg_snapshot_xmin(pg_current_snapshot())`, avoid skipping events whose sequence positions were allocated early but committed late. That order is not commit order, though. How can consumers still be sure of seeing each stream's events in version order?

## Findings

**Short answer.** In most cases the guarantee holds without extra work. It holds whenever the transaction that writes version N+1 gets its transaction ID (xid) *after* it has seen version N committed. It breaks only when a transaction already has an xid before it reads the stream head. There are three ways to make version order safe. Writers can be disciplined: the append is the transaction's first write, or appends run at REPEATABLE READ or SERIALIZABLE. The ordering key can be made to rise within each stream by construction. Or consumers can check per-stream versions and fill gaps by reading the stream directly.

**What the xid order actually is.** PostgreSQL gives each transaction its xid from a global counter "when a transaction first writes to the database". So "lower-numbered xids started writing before higher-numbered xids", and that order "might be different from the order in which the transactions started" (PostgreSQL docs, Transactions and Identifiers). `pg_current_xact_id()` assigns an xid early if the transaction has none yet. Inside a subtransaction it returns the top-level xid (System Information Functions). A snapshot's `xmin` is the "lowest transaction ID that was still active". Every xid below it is either committed or rolled back. Reading only below `xmin` is what lets the polling pattern avoid skipping events. The pattern is used by the postgresql-event-sourcing reference implementation, Watermill's PostgreSQL schema, Emmett, and Oskar Dudycz's outbox article. Dudycz states the trade-off directly: the order follows when each transaction started writing, not when messages were appended. The postgresql-event-sourcing README orders delivery globally by `(TRANSACTION_ID, ID)`. It says nothing about whether one aggregate's events arrive in version order. None of these sources makes a per-stream ordering guarantee.

**Why per-stream order usually holds.** Optimistic concurrency means the writer of version N+1 has to see version N first. It does this with an expected-version check, a conditional `UPDATE ... WHERE version = expected`, or a unique `(stream, version)` index. That index makes a conflicting inserter wait until the other transaction ends and then re-check (Index Uniqueness Checks). Version N must therefore be committed before the writer T2 reads it. The writer T1 of version N got its xid before writing N. If T2 gets its xid after that read, the global counter guarantees xid(T1) < xid(T2), so version N comes before N+1 in the feed. Events from one transaction share one xid and are ordered by position. Sequence values drawn in one session are successive values (CREATE SEQUENCE notes), so position order matches insertion order. Versions and positions just need to be assigned in the same row order. This reasoning follows from the documented rules above; no source examined states it as a guarantee.

**When it breaks.** At READ COMMITTED, each statement sees data committed before that statement began. Two successive statements can therefore see different data (Transaction Isolation). A transaction that already holds an xid can still read, and build on, events committed later by a transaction with a *higher* xid. Example: T2 appends to stream A and gets xid 100. T1 then gets xid 101, appends version N of stream S and commits. T2 reads S, sees N, appends N+1 and commits. Ordered by `(xid, position)`, N+1 (xid 100) comes before N (xid 101). This can happen in four ways:

- multi-stream or outbox transactions that write something before appending;
- calling `pg_current_xact_id()` before reading the stream head;
- retrying a failed append through a savepoint, which keeps the original top-level xid;
- any other write made earlier in the same transaction.

Emmett's `emt_append_to_stream` assigns `v_transaction_id := pg_current_xact_id()` as its first statement. When no expected position is supplied, it reads the stream position only after that. The function is plpgsql with default (VOLATILE) volatility, so each query in it takes a fresh snapshot at READ COMMITTED (Function Volatility Categories). By the reasoning above, that leaves a narrow window in which an append with no expected position can be ordered ahead of its predecessor. The predecessor's events do eventually arrive. They can be held back for a long time, though, if an unrelated in-flight transaction keeps `xmin` between the two xids.

**Write-side ways to make inversions impossible.**

1. *Assign the xid after the head read.* Make the append the transaction's first write. Get `pg_current_xact_id()` as part of the INSERT, after the version check, not before it. Retry a concurrency conflict in a new transaction rather than through a savepoint. This gives the guarantee only if callers never write anything earlier in the same transaction.
2. *Use REPEATABLE READ or SERIALIZABLE for appends.* The snapshot is taken at the first non-transaction-control statement (Transaction Isolation). Any xid assigned later is at least the snapshot's `xmax`, and every visible transaction has an xid below `xmax` (snapshot definitions in System Information Functions). Any version a transaction can see therefore has a lower xid than its own. If the transaction cannot see version N, its expected-version check fails. The check can fail through the unique index, or through `could not serialize access due to concurrent update` on a stream-head row. This holds for multi-stream transactions too. It needs only the version check the store already does inside the transaction, plus a retry on failure, which optimistic concurrency already requires. This is derived from the documented semantics, not stated by any source.
3. *Make the ordering key rise within each stream.* Akka Persistence R2DBC orders its event feed by a database timestamp, which is not commit order either. It inserts `GREATEST(?, (SELECT db_timestamp + '1 microsecond' ... WHERE persistence_id = ? AND seq_nr = ?))`, "to ensure that db_timestamp is always increasing for a pid". A similar idea for xid feeds would store the greater of the transaction's own xid and the predecessor's key. No PostgreSQL xid-ordered store examined does this, and whether it keeps the no-skip property has not been checked.
4. *Serialise writers.* Message DB's `write_message` takes `pg_advisory_xact_lock` on a hash of the stream's category. This avoids the problem by giving up write concurrency within a category.

**Consumer-side repair.** Akka's documentation is explicit that its query feed is ordered globally, not per entity. "It's the responsibility of the consumer to filter duplicates and make sure that events are processed in exact sequence number order for each persistence id". Its `R2dbcProjection` layer does this, and it also runs backtracking queries to catch missed events. Translated to an xid feed, a consumer would keep the last applied version per stream, often stored next to the projection's own row. When an event arrives more than one version ahead, its predecessors are already committed, because the writer had to see them. The consumer can read them straight from the stream by version range, apply them, and then drop them as duplicates when they turn up later in the feed. Waiting for them in the feed instead can take arbitrarily long, as described above. Sorting each batch by `(stream, version)` only fixes inversions that happen to land in the same batch.

**Commit-ordered sources avoid the problem.** Logical decoding delivers concurrent transactions "in commit order" (Logical Decoding Output Plugins). The writer of version N always commits before the writer of N+1 can read it. A commit-ordered feed therefore keeps per-stream version order with no writer discipline. It is a different delivery mechanism with its own costs.
