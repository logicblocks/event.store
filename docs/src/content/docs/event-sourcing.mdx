<p class="es-eyebrow">01 · An Overview</p>
## What is event-sourcing?

<p class="es-lede">
Event-sourcing is an alternative approach for data and state management that is more flexibile and 
scalabile than a traditional CRUD setup.

Instead of recording the consequences of changes, you simply record the changes themselves. They are
the source of truth, and you derive the resulting state when needed.

Especially when building distributed microservices, event-sourcing has become a necessity and _the_
standard.
</p>
<br/>


<OverviewAnimation />

<p class="es-lede">
Traditional CRUD systems store the current state, overwriting it on every change. Event-sourcing 
stores the changes themselves, as an append-only sequence of facts. The current state is derived 
from them. This small change of perspecive has big consequences.

Throughout this page we'll follow a single shopping cart, `cart-42`, as a customer adds coffee
beans, dithers over a mug, and eventually checks out.
</p>

<p class="es-eyebrow">02 · Key concepts</p>
## How it works

An **`event`** is a fact about something that has already happened. It is usually named in the past
tense, such as `item-added`, `item-removed`, or `checked-out`. 

Events are _**_immutable_**_. Once something has happened, it has happened, and so a **`stream`** of
events is _**append only**_.

To derive the current state of affairs, you **`replay`** the start (or a cached, prior moment in
time). Functional programmers will reconise this as a _**fold**_ or a _**reduce**_.

The fundamental reframe is that the event stream is the _**source of truth**_, and any state you
need is derived from it. 

<StreamFold />

{/* <br/> */}
### Commands in. Events out.

A request like "add a mug to cart 42" is a **`command`**, an instruction from one service to
another. To execute the command, the system first replays the stream to check the command makes
sense. (You can't remove an item than is no longer there, or add to a cart that's already been
checked out.) If the command succeeds, the outcome is recorded as new event.


<CartPlayground />

As you scroll back in time, notice that the state is cheap throw away and rederive. The event stream is read-only, so any number of views of the past can coexist.

### Projections and read models

Replaying a stream works well for understanding one cart. But questions like "which carts are open
right now?" or "how much coffee did we sell today?" span thousands of streams, and you don't want to
replay every one for every query.

Instead, you build **`projections`**. A projection listens to events, often across a whole
_category_ of streams, and maintains **`read model`**: a table, document, or search index shaped for
a particular question. 

You can have as many projections as you like, each optimised for its own purpose. Separating the
write side (streams) from the read side (projections) is known Command Query Responsibility
Segregation, or **`CQRS`** for short.

Also, projections are disposable. If your team identifies a new question to ask, you can write a new
projection to answer it.

<Projections />

The question "what do people remove from their carts?" was never anticipated. In a CRUD system that
information would long ago have been overwritten. Here, a new read model can replay from the very
first event, then continue to report as new events flow in.

:::note[What about really looooonng streams?] 
Replaying a stream with thousands of events on every
command can get slow. The usual solution is a **snapshot**: a cached copy of the state at some point
in time. Replays can start from there. Most streams are short-lived, so treat snapshots as an
optimisation technique once you've measured a need.
:::

### Concurrency without locks

What happens if two services try to append new events at the same time? Simultaneous events, while
rare, could lead to trouble if two systems are unaware of the others' changes.

To prevent this, event stores rely on [optimistic concurrency
control](https://en.wikipedia.org/wiki/Optimistic_concurrency_control). During a write operation,
each service must specify which version of the stream it has acted upon. If the current version no
longer matches, the append fails, and the rejected service must reprocess its command.

<Concurrency />

No service holds a lock on the data. Conflicts are rare and caught when they happen. The rejected
writer reprocesses against a fresh set of facts instead of silently overwriting it's compeitor.



<p class="es-eyebrow">03 · The benefits</p>
## Why use it?

<WhyGrid />

Events also make excellent **_integration points_**. Other services can subscribe to the events of
yours that they care about, such as `checked-out`, without accessing to your database. They operate
from their own projections.

Event-sourcing tends to pay off most in domains where **_what happened_** matters as much as **_what
is_**. Finance, logistics, ordering, bookings, compliance-heavy workflows: anywhere you've been
asked "how did it get here?" and couldn't answer.

<p class="es-eyebrow">04 · Alternatives</p>

## How it compares
Event-sourcing isn't the only technique for maintaining history or sharing changes, and is by no means a silver bullet. Here's how it compares with other common practices:

<Comparison />

|                                     | CRUD          | Audit tables      | Change data capture | Messaging / Kafka       | Event-sourcing     |
| ----------------------------------- | ------------- | ----------------- | ------------------- | ----------------------- | ------------------ |
| Source of truth                     | Current state | Current state     | Current state       | Usually a separate DB   | The events         |
| Keeps full history                  | No            | If code remembers | While retained      | While retained          | Yes, by design     |
| Captures business intent            | No            | Partly            | No, row diffs       | Yes                     | Yes                |
| Can rebuild state from history      | No            | Rarely            | Rarely              | Rarely                  | Yes                |
| New read models over past data      | No            | Hard              | Hard                | If retained forever     | Yes                |
| Familiar to most teams              | Very          | Very              | Fairly              | Fairly                  | Less so            |

Also, these approaches aren't mutually exclusive. Event-sourced systems often publish their events
to a broker for other services to consume, and plenty of successful services have a mix of some
event-driven and some CRUD, for where history matters and where it doesn't.

:::note[What do you really mean by "Event-Driven"] 
Event-based systems can go by many names, and many related techniques are often conflated. We highly recommend [this article by Martin Fowler](https://martinfowler.com/articles/201701-event-driven.html) that disentangles all this competing vocabulary.
:::

## The trade-offs

Event-sourcing's simplicity can belie 

<CardGrid>
	<Card title="Events are forever" icon="padlock">
        You can't migrate old events. When the shape of an event changes, you version it and 
        ensure your code can read both versions. Be thoughtful when naming and modeling events.
	</Card>
	<Card title="Read models lag behind" icon="clock">
		Projections are usually updated asynchronously and can be a moment behind the stream. 
        Services need to tolerate this eventual consistency or read from the stream when they can't.
	</Card>
	<Card title="A new frame of mind" icon="puzzle">
		Streams, projections, subscriptions, replays, and versioned events are new concepts for many
		teams. Debugging gets easier, but there is more to learn and more infrastructure to be aware of.
	</Card>
	<Card title="Personal data and erasure" icon="warning">
		An immutable log and the right to be forgotten are in tension. Keep personal data out of event
		payloads where you can, or encrypt it per person and delete the key ("crypto-shredding") when
		asked.
	</Card>
</CardGrid>

Event-sourcing can be overkill for small or constrained projects with no need to retain history.
However, most commercial applications eventually reach a level of complexity such the issues
arrising call for evented solutions. Transitioning a legacy, CRUD system into an evented system can
be painful, but not every domain must operate the same way. Begin where history and intent matter
most.

<p class="es-eyebrow">06 · In practice</p>

## Event-sourcing with logicblocks.event.store

**`logicblocks.event.store`** gives you the building blocks described above for Python, using
`asyncio`. 

Events are grouped into a log of categories of streams. State is derived by _**projectors**_, and open-source adapters let you record these stream in your database of choice.

Here's `cart-42` from this page:

```python
from logicblocks.event.projection import Projector
from logicblocks.event.store import EventStore, adapters, conditions
from logicblocks.event.types import NewEvent, StreamIdentifier


class CartProjector(Projector[StreamIdentifier, dict, dict]):
    def initial_state_factory(self):
        return {"items": {}, "status": "open"}

    def initial_metadata_factory(self):
        return {}

    def id_factory(self, state, source):
        return source.stream

    # One handler per event: "item-added" is handled by item_added, and so on.
    def item_added(self, state, event):
        sku = event.payload["sku"]
        state["items"][sku] = state["items"].get(sku, 0) + 1
        return state

    def item_removed(self, state, event):
        sku = event.payload["sku"]
        state["items"][sku] -= 1
        if state["items"][sku] == 0:
            del state["items"][sku]
        return state

    def checked_out(self, state, event):
        state["status"] = "checked-out"
        return state


async def main():
    store = EventStore(adapters.InMemoryEventStorageAdapter())
    cart = store.stream(category="carts", stream="cart-42")

    # publish raises an `UnmetWriteConditionError` if another event 
    # writes before this one can complete.
    await cart.publish(
        events=[
            NewEvent(name="item-added", payload={"sku": "beans"}, metadata=None),
            NewEvent(name="item-added", payload={"sku": "mug"}, metadata=None),
        ]
    )

    # Optimistic concurrency: only append if nobody else has written since we read.
    latest = await cart.latest()
    await cart.publish(
        events=[NewEvent(name="item-removed", payload={"sku": "mug"}, metadata=None)],
        condition=conditions.position_is(latest.position),
    )

    projection = await CartProjector().project(source=cart)
    print(projection.state)  # {'items': {'beans': 1}, 'status': 'open'}
```
