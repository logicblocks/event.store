# For an event store with many in-process consumers, does one static notification channel carrying the category or stream in its payload beat per-category channels with dynamic LISTEN changes, in server-side cost and in listener complexity?

## Question

When a process runs many consumers that share one listener connection, is it better to LISTEN once on a single fixed channel and carry the category or stream name in the NOTIFY payload? The alternative is one channel per category, with the listener issuing LISTEN and UNLISTEN as consumers start and stop. The question compares the two on PostgreSQL server cost and on how complex the client-side listener becomes.

## Findings

### Short answer

Yes. For one shared listener per process that fans out to many in-process consumers, a single static channel with the category in the payload costs the same or less on the server through PostgreSQL 18. It is also clearly simpler to build. PostgreSQL 19 brings the first real server-side advantage for per-category channels: a NOTIFY now wakes only the backends listening on that channel. That only helps when different processes care about largely separate sets of categories, and even then it does not make the listener simpler. The event-sourcing and job-queue projects examined here mostly use a single channel or a small fixed set of channels, and route messages in-process using a key carried in the payload.

### Server-side cost: the writer side does not depend on the channel layout

Every transaction that has issued NOTIFY takes a heavyweight lock at commit. The PostgreSQL source describes it this way: "Serialize writers by acquiring a special lock that we hold till after commit. This ensures that queue entries appear in commit order". The lock is `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)` on "database 0", and the current master source still takes it. Recall.ai found that under tens of thousands of concurrent writers this lock "effectively serializes all commits". Their article was later updated to say commit 282b1cde9 "eliminated the bottleneck". However, that commit changed how listeners are woken, and the master source still takes the commit lock. Because the lock covers every channel, splitting channels by category does nothing to relieve it.

Two more writer-side rules apply equally to both designs:

- **Duplicates within a transaction.** PostgreSQL delivers only one notification when the same channel and identical payload are sent several times in one transaction. Distinct payloads "will always be delivered as distinct notifications".
- **Payload size and the queue.** Payloads must be shorter than 8000 bytes by default. Notifications go into a shared queue of about 8 GB, and NOTIFY fails at commit if that queue fills.

So a single channel whose payload is just the category collapses duplicates exactly as well as per-category channels with empty payloads. A payload that also carries the stream name and position produces one queue entry per distinct value. Commanded's EventStore limits this by notifying from a statement-level trigger rather than once per row.

### Server-side cost: the reader side through PostgreSQL 18

In PostgreSQL 18 and earlier, the server does not track which backend listens on which channel. `SignalBackends` will "Always signal listeners in our own database, unless they're already caught up". Listeners in other databases are signalled only when they fall far behind. Each woken backend reads every queue entry for its database and filters locally with `IsListeningOn`, which is a linear scan of a plain list of channel names. A source comment notes "In practice the list is likely to be fairly short".

Consequences for these versions:

- **Wake-ups.** Per-category channels do not reduce how many listener backends are woken, or how many queue entries each one reads. Every listening connection in the database is woken for every NOTIFY, whatever its channel.
- **Matching cost.** A listener holding hundreds of category channels does a string-compare scan of that list for every queue entry. A single-channel listener does one comparison.
- **What per-category channels do save.** Notifications the client does not want are never sent over the network. In-process consumers can discard these cheaply in a dispatch table, so the saving is small.
- **LISTEN churn.** LISTEN and UNLISTEN take no locks when they run. Their effect is applied after commit to the backend-local list. Only the first LISTEN on a connection registers the backend in the shared queue. Churn is therefore cheap on the server, but each change is still a client round trip and a transaction.

### Server-side cost: the reader side from PostgreSQL 19

Commit 282b1cde9 ("Optimize LISTEN/NOTIFY via shared channel map and direct advancement", Joel Jacobson, committed by Tom Lane on 15 January 2026) is in the PostgreSQL 19 release notes as "Improve NOTIFY to only wake up backends that are listening to specified notifications". The release notes snapshot is dated 2026-09-14 and the release date is still shown as unset.

How it works:

- A shared hash table maps a (database OID, channel name) pair to the backends listening on that channel.
- `SignalBackends` looks up each channel the transaction notified, and does nothing for a channel with no listeners.
- An idle backend that is not interested and is still at the old queue head has its queue pointer advanced directly instead of being woken.
- Each backend's own lookup becomes a hash probe.

The commit message reports "very significant improvements (integer multiples) in NOTIFY throughput … when there are many listeners but only a few are interested in any specific message." Under this design LISTEN and UNLISTEN update the shared table at commit, so churn now touches shared memory instead of only backend-local state.

My inference: this gives per-category channels a real server-side advantage, but only under specific conditions. There must be many listener connections, each interested in a small subset of categories that differs from the others'. Notification volume must also be high enough that needless wake-ups matter. In a typical event-store deployment, each process hosts consumers across most categories, and "all events" consumers need everything. Most listener backends then remain interested in most notifications, and the gain shrinks towards zero.

### Listener complexity

The static-channel design is clearly simpler for a shared psycopg 3 listener:

1. **No need to interrupt the wait.** psycopg's `notifies()` generator holds `self.lock` for its whole run, so no other command can use the connection meanwhile. With dynamic channels, every consumer start or stop means leaving the generator (via `close()`, `timeout` or `stop_after`), running LISTEN or UNLISTEN, then re-entering. River's Go notifier shows the same burden. Its comment says that waiting "locks an underlying connection, so infrastructure elsewhere in the notifier must preempt it". It also adds a subscription "optimistically" and rolls it back if the LISTEN fails. Oban keeps a set of active channels and issues LISTEN or UNLISTEN only when that set changes. A static channel is listened on once per connection and never needs this machinery.
2. **No catch-up race when a consumer starts.** LISTEN takes effect at commit. The documentation advises: "First execute (and commit!) that command, then in a new transaction inspect the database state". With dynamic channels, a new consumer must wait until the listener has actually committed the LISTEN for its category before doing its catch-up read, or it can miss events. With a static channel the LISTEN committed when the connection opened. A consumer that registers in-process and then reads from its checkpoint is safe without extra coordination.
3. **Reconnecting is simpler.** "A session's listen registrations are automatically cleared when the session ends". After a reconnect, a dynamic listener must re-issue its whole current channel set, kept consistent with consumers starting and stopping at the same time. A static listener re-issues a single LISTEN.
4. **Category names are not channel names.** Channels are identifiers. Unquoted ones are folded to lower case, and identifiers longer than 63 bytes "will be truncated". `pg_notify()` instead rejects names of `NAMEDATALEN` (64) bytes or more with "channel name too long". So a long category could be silently truncated on the LISTEN side while failing on the NOTIFY side. Per-category channels therefore need a safe mapping from category to channel, such as a prefix plus a hash. They also need careful quoting, because LISTEN cannot take bind parameters and needs `psycopg.sql.Identifier`. A payload carries any string under 8000 bytes, so none of this applies.
5. **"All events" consumers come for free.** With per-category channels, a consumer of the whole log needs either a second channel, which means two NOTIFYs per write, or a LISTEN on every category, including ones not yet known. With one channel it is just another entry in the in-process dispatch table.

### Prior art

- **Commanded EventStore (Elixir).** One trigger, `event_notification AFTER INSERT OR UPDATE ON streams FOR EACH STATEMENT`, notifies channel `<schema>.events` with payload `stream_uuid,stream_id,from_version,to_version`. One listener feeds a publisher that reads the event range and broadcasts on an in-process PubSub topic per stream.
- **Oban (Elixir).** A single connection uses a small fixed set of prefix-scoped channels (`insert`, `leader`, `signal`, `sonar`). The `insert` payload is a list of `%{queue: …}` maps, and the receiving side routes by queue through a Registry.
- **River (Go).** A few fixed topics (`river_insert`, `river_leadership`, `river_control`) are multiplexed over one connection.
- **pgmq.** This is the per-entity counter-example. Each queue gets its own channel, `pgmq.q_<queue>.INSERT`, with a NULL payload and an optional throttle (250 ms by default). This suits standalone consumers that each watch one queue, not one shared listener multiplexing many consumers.

### Verdict

For a psycopg 3 event store with one shared listener per process, use one static channel, for example scoped by schema like Commanded's. Carry the category in the payload, and optionally the stream and position. Route in-process with a dictionary from category to consumers. Through PostgreSQL 18 this design is never worse on the server and is better once a listener would hold many channels. From PostgreSQL 19, consider splitting channels only after measurement shows that wake-ups across many listener connections with mostly separate interests matter. Even then, a fixed set of channels (for example hashed buckets of categories) would keep registration static and avoid the dynamic-LISTEN complexity above; this hybrid is my inference, not a pattern found in the sources. Neither design affects the commit-time NOTIFY lock, which limits write throughput.
