# How much append throughput does a PostgreSQL event store lose when it serialises the window from global position allocation to commit behind a single store-wide advisory lock or counter-row lock?

## Question

If a PostgreSQL event store holds one store-wide lock from the moment it allocates a global position until the transaction commits, so that positions become visible in commit order, how much append throughput does it give up? The lock can be a transaction-level advisory lock, a row lock on a single counter row, or a table lock.

## Findings

### Short answer

Serialising that window turns concurrent appending into a single queue. The store's ceiling becomes about **B / H events per second**, where **H** is how long each append transaction holds the lock and **B** is the number of events written per transaction. Adding writers or cores does not raise it.

H can never be shorter than a durable commit. PostgreSQL releases transaction-level advisory locks and row locks only after:

- the commit record has been flushed to disk, and
- any synchronous standby has acknowledged it.

So the loss is the gap between 1/H append transactions per second and what the same cluster would reach if concurrent appends could commit in parallel and share WAL flushes through group commit.

- **At low write rates** the loss is close to zero. Writers rarely overlap and the lock is usually free.
- **As the arrival rate of append transactions approaches 1/H**, throughput flattens at that cap. Per-append latency then grows with the number of queued writers, while CPU and I/O sit idle.

No published benchmark isolates the lock as the only variable. The evidence below is the commit mechanism in the PostgreSQL source and documentation, one published benchmark of a store that serialises through a counter row, and several practitioner and production reports.

### Why the serialised window always includes the commit flush

PostgreSQL releases transaction-level advisory locks automatically at the end of the transaction, and they have no explicit unlock. Row-level locks, such as the one an `UPDATE` takes on a counter row, are likewise "released at transaction end or during savepoint rollback". So whichever form the store-wide lock takes, it is held until the transaction finishes committing.

The commit path in `xact.c` sets the order of events:

1. `RecordTransactionCommit` flushes WAL with `XLogFlush` whenever `synchronous_commit` is above `off`.
2. It then waits for synchronous replication with `SyncRepWaitForLSN`. The source comments that "at this stage we have marked clog, but still show as running in the procarray and continue to hold locks".
3. `ProcArrayEndTransaction` runs. It must be done "_before_ releasing locks we hold and _after_ RecordTransactionCommit".
4. Only then are locks released, "at the point where any backend waiting for us will see our transaction as being fully cleaned up".

This ordering is what makes the technique correct: the next writer cannot allocate a position until its predecessor is durable and visible. It is also why H cannot drop below the commit's flush time, plus the standby round trip where synchronous replication is used. The PostgreSQL documentation states the replication cost directly: "transaction locks continue to be held until the transfer is confirmed. As a result, incautious use of synchronous replication will reduce performance … because of increased response times and higher contention". It adds that the minimum wait is the primary-to-standby round-trip time.

Releasing a session-level advisory lock before `COMMIT` would shorten the window, but it would also reopen the out-of-order commit gap the lock exists to close.

Setting `synchronous_commit = off` removes the flush wait from H. The documentation describes the flush wait as "a major component of the total transaction time" for short transactions, and asynchronous commit as "a significant boost in throughput for small transactions". The price is that the most recent commits can be lost in a crash.

### Why group commit cannot recover the loss

Without serialisation, PostgreSQL amortises flush cost across concurrent committers. With the default `commit_delay` of zero, a group is made up of the sessions that reach their flush while the previous flush is still running. A non-zero `commit_delay` lets the group leader wait so more commit records can share one sync. The documentation frames `commit_delay` as a way to amortise "the cost of each flush operation … across concurrently committing transactions".

A store-wide append lock allows at most one append transaction into its commit at a time. Append transactions therefore never share a flush with each other: each pays for its own flush, plus any standby round trip. Other kinds of transaction can still be grouped.

The resulting ceiling is plain arithmetic, not a measurement: about 1/H append transactions per second whatever the writer count. For example:

- if H is 2 ms, the store cannot exceed 500 append transactions per second;
- if H is 10 ms (slow cloud storage plus a cross-zone synchronous standby, say), the limit is 100 per second.

In queueing terms, utilisation is the arrival rate of append transactions multiplied by H. Above about 0.7, waits grow sharply, and at 1 the queue grows without bound.

### What fills the hold time in practice

From the moment the lock is acquired, H contains:

- the rest of the statement's execution: the `INSERT`, index maintenance and any triggers;
- **every client-to-server round trip between the locking statement and `COMMIT`**;
- pre-commit work, including putting `NOTIFY` messages into the notification queue;
- the WAL flush;
- any synchronous-standby wait;
- the hand-off that wakes the next waiter.

Client round trips are the part a library can control most easily.

The Python `eventsourcing` library's psycopg 3 recorder shows the shape. For recorders that keep a total order it runs, in order:

- `SET LOCAL lock_timeout = …`;
- `LOCK TABLE … IN EXCLUSIVE MODE`;
- an `executemany` of the inserts;
- `pipeline.sync()`, called explicitly "so any uniqueness constraint violation causes an IntegrityError to be raised here";
- a fetch of the new notification IDs.

All of this runs inside `conn.pipeline()` and `conn.transaction()`. Because `COMMIT` is sent after that explicit sync, the locked window includes at least one extra client round trip as well as the flush.

psycopg's pipeline mode can send several statements and their results "in a single network roundtrip". In autocommit pipeline mode the server wraps the statements "in an implicit transaction, which will be only committed when the Sync is received". So the lock, the insert and the commit can be sent together, leaving only server-side work and the flush inside H.

### Measured and reported effects

**Commanded EventStore (Elixir)** uses a store-wide counter row. Every append runs `UPDATE streams SET stream_version = stream_version + $2 WHERE stream_id = 0` on the `$all` stream inside the same CTE that inserts the events. That row lock is held until commit, so all appends are serialised.

Its README benchmark appends 100-event batches against "a local PostgreSQL database", using Erlang term serialisation:

| Writers | Average time per op | Events per op | Events/s |
|---|---|---|---|
| 1 | 20.3 ms | 100 | 4,929 (README) |
| 10 | 127.4 ms | 1,000 | ≈7,850 (derived) |
| 20 | 376.8 ms | 2,000 | ≈5,300 (derived) |
| 50 | 582.4 ms | 5,000 | 8,586 (README) |

Fifty times as many writers buys about 1.7 times the throughput. Meanwhile each writer's append latency rises from about 20 ms to about 580 ms.

At 50 writers this works out to about 11.6 ms of wall time per 100-event batch (582 ms / 50). That fits writers queuing through one critical section of roughly 12–19 ms per batch, against a 20 ms single-writer round trip that also includes client-side work outside the lock. This reading is an inference: the benchmark has no non-serialised control and does not describe its hardware.

**Sequin** generated positions from a counter row (`my_seq`). It reported that "Write throughput was much lower than we needed, and the lock durations between concurrent writes was very high (seconds)". It concluded that "writes now funnel through updates to `my_seq`, which must happen serially".

**Oskar Dudycz** tried a singleton-table gapless counter for a PostgreSQL outbox. He reports that "the performance hit … was too big to accept" for a backbone messaging mechanism, though it "could be fine for low throughput but high importance numbers".

**Laurenz Albe (Cybertec)** says of the counter-row "gapless sequence": "It will serialize all transactions that use that 'sequence'. That will deteriorate your data modification performance considerably."

**The `eventsourcing` library documentation** says its exclusive table lock "effectively serialises writing events". Readers are unaffected because `SELECT`'s ACCESS SHARE lock does not conflict with EXCLUSIVE mode. Release 9.1.5 restricted the lock to inserts "into a total order". The project publishes no throughput figures.

### Interaction with NOTIFY

PostgreSQL already runs this same serialisation pattern for `NOTIFY`, which matters for a push-based event store. In `PreCommit_Notify`, every transaction that issued `NOTIFY` takes an AccessExclusiveLock on "database 0". The source comment reads: "Serialize writers by acquiring a special lock that we hold till after commit. This ensures that queue entries appear in commit order". The lock is cluster-wide, not per-database.

Recall.ai hit this in production. A lock wait of 1,015.9 ms was logged, hundreds of processes were queued, and database CPU and I/O fell as load rose. Without `NOTIFY`, the same database used all its CPU cores. That is the failure signature of any store-wide lock held through commit: throughput plateaus, latency explodes, and resources sit idle.

It follows, as an inference from the source, that a store issuing `NOTIFY` in every append transaction already serialises its appends across the commit flush. In that case a store-wide allocation lock does not change the ceiling much. It mainly extends the locked window earlier in the transaction, to cover allocation, insert execution and any client round trips before `COMMIT`. The flip side is that the notification lock is shared with every other notifying transaction in the cluster.

### Ways to reduce the loss

- **Write more events per transaction.** The ceiling applies to transactions, so events per second scale with batch size. Commanded's figures are for 100-event batches.
- **Shrink H.** Take the lock as late as possible, in the same statement as the insert (for example inside a server-side function or CTE). Send `COMMIT` in the same round trip, via pipeline mode or a single implicit transaction. This removes client latency from H and leaves the flush.
- **Narrow the lock's scope.** Message DB's `write_message` always calls `acquire_lock`, which takes `pg_advisory_xact_lock` on a 64-bit hash of the stream's *category*, not on the whole store. Writers to different categories run in parallel, and global positions are guaranteed to commit in order only within a category.
- **Avoid serialisation altogether.** Readers can bound safe positions using transaction-ID snapshots: everything before the current snapshot's `xmin`. The eugene-khyst reference implementation describes this approach as "non-blocking" and the default, with a SHARE ROW EXCLUSIVE table lock as the serialising alternative.
- **Keep synchronous standbys and synchronous commit off the append path** where durability requirements allow. The documentation recommends setting synchronous replication at the application level for this reason.
- **Bound queueing with `lock_timeout`**, as the `eventsourcing` library does, so that a stalled holder surfaces as an error rather than an unbounded wait.
