# On PostgreSQL versions before 19, how much listener fan-out cost does a single per-process dispatcher connection avoid when it holds one LISTEN and fans notifications out to in-process consumers?

## Question

Before PostgreSQL 19, an application can give every consumer its own
`LISTEN` connection, or it can open one listener connection per process and
fan each notification out to that process's consumers in memory. How much of
the server-side and client-side fan-out cost does the second approach save,
and which costs does it leave in place?

## Findings

### Short answer

Before PostgreSQL 19, a NOTIFY wakes every listening connection in the same
database, whatever channel that connection listens on. The cost of each
NOTIFY therefore grows linearly with the total number of listening
connections in the database, not with the number that care about the
message. A per-process dispatcher cuts that number from "processes ×
consumers per process" to "processes". Every per-listener cost shrinks by the
same factor: the notifier's signal syscalls, the listener-list scan, each
woken backend's queue read, the client socket traffic, and one database
connection per consumer.

The only published measurement found is a ping-pong NOTIFY benchmark by the
author of the PostgreSQL 19 patch. In it, each extra idle listener added
roughly 4–5 µs to every round trip. Throughput fell 32% with 10 extra
listeners, 78% with 100 and 97% with 1,000. Collapsing tens or hundreds of
per-consumer listeners into a handful of per-process dispatchers recovers
most of that loss. The dispatcher does not touch the writer-side cost, the
global lock that every NOTIFY-issuing commit takes.

### What a pre-19 NOTIFY costs per listening connection

The mechanism comes from the PostgreSQL 17 source, which matches every
release from 13 to 18 in this respect:

- **Who gets signalled.** After a notifying transaction commits,
  `SignalBackends()` takes `NotifyQueueLock` in exclusive mode and walks the
  linked list of every listening backend. The source comment reads: "Always
  signal listeners in our own database, unless they're already caught up
  (unlikely, but possible)". Listeners in other databases are signalled only
  when they are `QUEUE_CLEANUP_DELAY` (4) pages behind. The test does not
  look at channels at all. Each backend keeps its channel list privately
  (`listenChannels`), so the sender cannot know who is interested. The
  sender then calls `SendProcSignal(PROCSIG_NOTIFY_INTERRUPT)`, which is one
  `kill()` per listener.
- **Where the signalling runs.** `AtCommit_Notify()`, which calls
  `SignalBackends()`, runs in `CommitTransaction` after the transaction's
  locks have been released. Signalling therefore does not lengthen the hold
  on the global NOTIFY lock. It does run inside the notifying backend's own
  commit processing, so the O(N) signalling is per-commit work for the
  writer. That latency effect is inferred from the call order in the source,
  not measured.
- **What each woken listener does.** Delivery is deferred if the listener is
  inside a transaction. When idle, it runs `ProcessIncomingNotify`, which:
  1. starts its own transaction command;
  2. registers a fresh snapshot (`GetLatestSnapshot`);
  3. reads its queue position and the queue head under a shared
     `NotifyQueueLock`;
  4. reads the queue's SLRU pages under the SLRU bank lock, copying entries
     into a local buffer;
  5. checks each entry's transaction status and filters it by channel with
     `IsListeningOn`, a linear `strcmp` over its channel list;
  6. sends matching notifications to its client, updates its shared queue
     position and commits.

  An uninterested listener does all of this only to find nothing to deliver.
- **Queue cleanup.** The queue tail advances only to the minimum position of
  all listeners. Every extra listener is one more backend that can hold
  cleanup back. The documentation warns that "no cleanup can take place if a
  session executes LISTEN and then enters a transaction for a very long
  time", and that when the queue (8 GB by default) fills, "transactions
  calling NOTIFY will fail at commit".

Older releases were worse. Before PostgreSQL 13, the listener search scanned
the whole `backend[]` array (sized by MaxBackends), and listeners in every
database were signalled. Tom Lane's PostgreSQL 13 commits threaded a linked
list through the active listeners and restricted signals to the sender's
database. He noted that this "can substantially reduce signal traffic if
listeners are spread among many databases". Within one database, the
signal-everyone behaviour stayed in place until PostgreSQL 19.

### Measured cost of extra listeners

Joel Jacobson opened the pgsql-hackers thread for the PostgreSQL 19 change
on 2025-07-12. He framed the problem as many backends listening on *distinct*
channels: "Async_Notify must signal every listening backend in the database,
as it lacks central knowledge of which backend is interested in which
channel. This results in an O(N) number of kill(pid, SIGUSR1) syscalls as
the listener count grows." His benchmark ran a NOTIFY ping-pong between two
connections while adding idle listeners:

| Extra idle listeners | Pre-patch TPS | Patched TPS |
|---|---|---|
| 0 | 9,126 | 9,152 |
| 10 | 6,233 | 9,352 |
| 100 | 2,020 | 9,320 |
| 1,000 | 238 | 8,937 |

The figures below are derived from the table by arithmetic. The base round
trip is about 110 µs. Ten idle listeners add about 51 µs (about 5 µs each).
A hundred add about 385 µs (about 3.9 µs each). A thousand add about
4.1 ms (about 4.1 µs each). The cost is close to linear, at roughly 4 µs per
listening connection per benchmark transaction. A later message in the same
thread (2025-09-30) restates the shape: 8,700 TPS falls to 6,100 TPS with
10 extra listeners, 2,000 TPS with 100, and 250 TPS with 1,000.

Several caveats apply:

- The hardware and harness live in an external repository that was not
  reviewed here, so the absolute numbers are machine-specific.
- On a shared host the woken backends also take CPU from the measured pair,
  so the slope probably reflects scheduling contention as well as syscall
  cost. That is an interpretation, not a stated result.
- Listeners that *are* interested also transmit to their clients, so the
  idle-listener figures are a floor for the cost of an interested listener.

### What the dispatcher avoids

Take P application processes, each with C consumers. With per-consumer
connections, each notifying commit signals and wakes about P × C backends.
With one dispatcher per process, it wakes P. Each item below shrinks by a
factor of C:

- **Notifier-side work:** one `kill()` per listener, plus a longer walk of
  the listener list while holding `NotifyQueueLock` exclusively. Writers
  appending to the queue need that same lock.
- **Server-side listener work:** the per-listener steps described above
  (context switch, transaction start, snapshot, lock acquisitions, SLRU page
  reads and the channel filter). Signals and wakeups are bounded by the
  notifying-commit rate times the listener count, about 100,000 backend
  wakeups per second at 500 commits per second and 200 listeners, versus
  4,000 with 8 dispatchers. The real number is lower when listeners lag:
  `SignalBackends` skips only listeners already at the queue head, and a
  woken backend drains every pending entry in a single pass.
- **Client-side work:** one socket, one NotificationResponse per message and
  one Python wakeup per process, instead of one per consumer. In psycopg 3 a
  listening connection should stay in autocommit and does not receive
  notifications while busy with other queries. A dedicated dispatcher
  connection fits that constraint naturally.
- **Connection budget:** one long-lived, session-level connection per
  process instead of one per consumer. Brandur Leach's "notifier pattern"
  (2024) gives this as the main motivation. Connections "are still somewhat
  of a precious, limited resource". A single dispatcher also lets the rest
  of the application use PgBouncer transaction pooling while only the
  listener needs a session-pooled connection.
- **Queue-cleanup risk:** fewer listening backends means fewer sessions that
  can hold back the queue tail.
- **Follow-up reads:** a dispatcher can fetch new events once and broadcast
  them, instead of every consumer re-querying after the same wakeup.
  Commanded's Elixir EventStore works this way: "One connection per node is
  used", and "a single process will connect to the database to listen for
  these notifications. It fetches the event data and broadcasts to all
  interested subscriptions."

As a rough illustration only: 8 processes with 25 consumers each give 200
listening connections. At the benchmark's slope of about 4 µs per listener,
that adds roughly 0.8 ms to each notification round trip, about 1,100 TPS in
that harness. Eight dispatchers would add about 0.03 ms, or roughly
7,000 TPS. This extrapolates one benchmark on unknown hardware. It indicates
the order of magnitude, not a prediction.

### What the dispatcher does not avoid

- **The writer-side commit lock.** `PreCommit_Notify` takes a database-wide
  `AccessExclusiveLock` "that we hold till after commit", which serialises
  all notifying commits. Recall.ai traced its production outage to this lock
  under many concurrent writers, not many listeners. Listener consolidation
  leaves it untouched.
- **Fan-out across processes.** The remaining wakeups still grow linearly
  with P. Large multi-process deployments, such as many pre-fork Python
  workers across many hosts, can still reach listener counts where the slope
  matters.
- **Routing work.** In-process routing becomes the application's job:
  filtering by category or stream, and protecting the dispatcher from slow
  consumers. The notifier pattern uses buffered channels with non-blocking
  sends for this.
- **A longer channel list.** If the dispatcher LISTENs on many channels, its
  backend's `IsListeningOn` check grows linearly per queue entry. This is
  inferred from the source and is negligible with one or a few channels.
- **Transaction discipline.** The dispatcher connection must never sit in a
  transaction, because that defers delivery and blocks queue cleanup.

### Contrast with PostgreSQL 19

Commit 282b1cd (January 2026, Joel Jacobson, reviewed by Tom Lane) adds a
shared dshash map from (database, channel) to listening backends. NOTIFY can
now wake only interested listeners, and it advances uninterested listeners
parked at the old queue head without waking them. The commit claims "very
significant improvements (integer multiples) in NOTIFY throughput … when
there are many listeners but only a few are interested in any specific
message". It also says: "There is no improvement for the simplest case where
every listener reads every message."

The PostgreSQL 19 release notes, still a draft as of September 2026,
summarise it as "Previously most backends were woken by NOTIFY."

Before 19, the dispatcher's server-side saving applies to every channel
design. From 19 on, per-category channels already avoid waking uninterested
consumers, but an event store that uses one global channel still wakes every
listener. For that design, and for the connection-count and client-side
savings, the dispatcher's benefit carries over to every version.
