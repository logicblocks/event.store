# What is the cheapest PostgreSQL query a safety-net poll can run to learn whether a consumer has unread events, and how does its cost grow with consumer count and log size?

## Question

A safety-net poll only needs a yes or no: does any committed, visible event lie beyond a consumer's last processed position, and match the consumer's filter if it has one? What is the cheapest PostgreSQL query that answers this correctly? How does the cost of running it grow as the event log gets longer and as the number of consumers polling it rises?

## Findings

**Short answer.** The cheapest correct answer is one bounded B-tree probe. It goes down the index on event position (or on filter key plus position) and stops at the first index entry that qualifies. Its cost in page visits grows logarithmically with log size. Because B-tree fanout is high, it is effectively constant in practice. If every consumer runs its own probe, the total cost grows linearly with consumer count. So the bigger saving comes from combining many consumers' polls into one probe per process, not from making the probe itself cheaper. Cheaper-looking options either move cost onto appends or give wrong answers.

**Candidate probes.**

1. *Read the sequence's high-water mark.* Reading the last value of the position sequence touches one tiny relation, so its cost does not depend on log size at all. But PostgreSQL sequences are non-transactional. The value counts positions drawn by appends that are still in flight and by appends that rolled back. Per-session caching (`CACHE` greater than 1) also pushes it ahead. This gives a one-sided test. Every committed event has a position at or below the sequence value, so "last value ≤ my position" proves there is nothing unread. The opposite result, "last value > my position", is only a hint. It stays true for good after any rollback leaves a permanent gap. And if a consumer stores the observed value as a watermark, it can miss an append that drew its position before the check but commits after it. The sequence check is therefore at most a pre-filter in front of a real probe, never a replacement for one.
2. *Head probe.* `SELECT max(position) FROM events`, or the equivalent `ORDER BY position DESC LIMIT 1`. PostgreSQL's planner turns `max` on a B-tree-indexed column into a backward index scan with `LIMIT 1`. One probe gives the newest visible position, and the process compares it in memory with every unfiltered consumer's position. This is the shape that scales best with consumer count.
3. *Existence probe.* `SELECT EXISTS (SELECT 1 FROM events WHERE position > $1)`, or for a consumer subscribed to one category or stream, `... WHERE category = $2 AND position > $1`. It goes down the index to the consumer's position and stops at the first visible match. The filtered form is only cheap if there is a composite B-tree index whose leading columns match the filter's equality columns and whose last column is position. Without that index, the scan has to filter row by row, so its cost grows with the number of non-matching events after the consumer's position. In the worst case it becomes a sequential scan of the whole log.
4. *Head row maintained by appenders.* Each append also updates a `log_head` row, or one row per category, and the poll reads that row by primary key. The read is about O(1), but every append pays for it. All appends then update one hot row, which serialises appenders on its row lock and creates a dead tuple per append. For a poll meant to be a rare safety net, this is the wrong trade: a cost on every write to save a cost on an occasional read.

**Growth with log size.** Bayer and McCreight's B-tree does retrieval, insertion and deletion in time proportional to log_k of the index size, where k is a natural number set by the storage device's page size. Comer's survey explains why the B+-tree, with keys only in linked leaves, became the standard file and database index. Graefe's survey covers the modern techniques built on that base. The arithmetic below is my own estimate, not taken from the records. An 8 KiB page holds a few hundred 8-byte position keys, so the tree is three or four levels deep even for billions of events. The pages on the rightmost root-to-leaf path are touched by every append and every probe, so they stay in shared buffers. In practice, then, a head or existence probe costs a few buffer hits whether the log has a million events or a billion.

The probe's cost depends on log size in that way, but there are two ways its cost depends on the *tail* of the log instead (this is PostgreSQL behaviour, not from the records):

- *Visibility checks.* An index-only scan can skip the heap only for pages the visibility map marks all-visible. The newest events sit on heap pages written since the last vacuum, so a probe near the tail usually fetches the heap page to check whether the tuple is visible.
- *Invisible entries.* The probe walks past index entries its snapshot cannot see: appends still in flight, and dead tuples left by rolled-back appends. That extra work grows with the number of such entries at the tail. It stays until the entries are hinted dead (marked LP_DEAD) or vacuumed away.

Neither effect depends on the length of the log. The real way a "cheap" poll grows with log size is a missing or mismatched index, which turns it into a linear scan.

**Growth with consumer count.** If each of C consumers polls on its own every T seconds, the database runs C/T probes per second. Each costs O(log N) page visits for a log of N events, plus a fixed per-statement cost: a network round trip, parse, plan and execute, and taking a snapshot. For a query this small the fixed cost dominates, so total cost grows linearly with C. Three ways to flatten that:

- *One head probe per process per tick.* Run the head probe once and compare it in memory with every consumer's position. That gives P/T probes per second for P processes, plus O(C) integer comparisons, so the database load grows with process count rather than consumer count.
- *One batched probe for filtered consumers.* A single statement that joins the consumers' positions to a lateral existence probe answers all of them in one round trip. Its cost is about F × log N page visits, where F (at most C) is the number of distinct filters.
- *Prepared statements.* These remove repeated planning.

Kafka's replicated commit log, where each consumer keeps its own offset, is the same design. Whether a consumer has unread events is a comparison between its offset and the log's end, and the end is a property of the log, read once and shared. In PostgreSQL, the rightmost leaf of the position index plays the role of that log end. (The Kafka record's abstract describes only the commit-log architecture; the offset comparison comes from Kafka's general design.)

**Concurrency at the hot leaf.** All probes and all appends meet at the same rightmost leaf page. Lehman and Yao's B-link tree adds a link pointer to each node, so readers need no read locks and can recover from a concurrent node split. Probes therefore do not block appenders at the lock level. PostgreSQL's B-tree implementation (nbtree) is derived from that design; this is background knowledge, not from the record. What remains is brief shared buffer-content locking on the hot leaf. I infer, without measurements, that this could contend with appenders only at very high probe rates. This is another reason to share one probe per process.

**Visibility must match the read path.** The probe has to apply the same visibility rule the consumer's real read uses. Suppose a consumer only reads positions that are safe under a snapshot-xmin gate, but its probe compares against the raw newest visible position. Then the probe keeps reporting unread work that the read cannot return, and the safety net degrades into a busy loop. Compare against the gated head, not the raw one.

**Recommended shape.**

- Keep a B-tree index on global position, plus a composite (filter key, position) index for each filtered subscription shape.
- Run one gated head probe per process per safety-net tick, and compare it in memory.
- Answer filtered consumers with one batched lateral existence probe.
- Use the sequence value only as an optional pre-filter, and never maintain a head row on the append path.

With this shape, cost is about constant in log size and linear in the number of processes, not consumers.

**Limits of the evidence.** The cited records support the B-tree cost model and the lock-free reader design. None of them measures PostgreSQL probe latency or the visibility-map effect, and none describes sequence semantics or the planner's `max` rewrite. Those statements rest on PostgreSQL's documented behaviour and should be checked against the PostgreSQL manual and a benchmark before the library relies on them. Scholarly searches on polling-cost scalability and on index-only-scan cost returned nothing relevant.
