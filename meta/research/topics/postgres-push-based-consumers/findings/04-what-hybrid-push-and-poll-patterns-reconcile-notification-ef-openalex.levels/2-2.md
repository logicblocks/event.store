# When event positions come from a sequence assigned before commit, how can a consumer tell transient gaps left by in-flight transactions from permanent gaps left by rollbacks, so gap-based loss detection neither stalls nor skips events?

## Question

Event positions can be drawn from a sequence before the inserting transaction commits. How can a consumer then tell a transient gap (a position held by a transaction that is still in flight) from a permanent gap (a position consumed by a rollback), so that gap-based loss detection neither stalls on holes that will never fill nor skips events that will appear later?

## Findings

**Short answer: it cannot, from positions alone.** A missing position looks the same whether its transaction is still running or has rolled back. Any rule that sees only position values must either wait on the hole or move past it. Waiting stalls forever if the hole is permanent. Moving on loses the event if the hole later fills.

The systems literature gets to "neither stall nor skip" by changing what evidence the consumer uses, not by sharpening the gap test. It offers three ways to handle gaps and a fourth that removes transient gaps altogether:

1. Read only below a **stable frontier**, worked out from authoritative knowledge of which transactions are still in flight.
2. **Resolve each hole explicitly** with a write that races the slow writer atomically.
3. Fall back on a **time-bounded heuristic** that knowingly trades stalls against skips.
4. **Serialise commits** so that position order equals commit order, which removes transient gaps.

For a store backed only by PostgreSQL, the first mechanism maps directly onto snapshot visibility. It is the strongest fit.

### Why the gap is inherently ambiguous

A position drawn from a sequence before commit follows insert order, not commit order, and it is not returned to the sequence when its transaction aborts. So the visible prefix of the log can contain holes for two different reasons: the transaction that drew the value has not committed yet, or it never will.

Rollbacks are not the only source of permanent holes. Others include:

- statements that draw a value and then fail;
- sequence values cached per session and never used;
- values pre-allocated and then lost in crash recovery.

So a loss detector that equates "gap" with "rollback" is wrong even in the cases it was designed for.

A missing row also carries no transaction identifier. The consumer cannot ask "whose hole is this?". It can only ask "could any transaction still produce rows here?".

Ports and Grittner's account of serializable snapshot isolation (SSI) in PostgreSQL describes a known anomaly with the same structure. In the batch-processing example they take from Fekete et al., a read-only report sees a batch as closed while a receipt for that batch is still in flight. The reader observes a later effect without an earlier-started one, which is exactly a consumer seeing position N while a lower position k is still uncommitted.

SSI prevents that anomaly only because the transactions conflict through a shared counter that they read and write transactionally. A sequence draw sits outside transactional isolation, so a valid serial order can place the lower-positioned writer after the reader. Running the consumer at SERIALIZABLE therefore does not close the gap on its own. This is an inference from SSI's dependency model; the paper makes no claim about sequences.

The paper's read-only optimisations are PostgreSQL's own precedent for "wait until in-flight writers resolve, then trust what you see". They include "safe snapshots" and deferrable read-only transactions, which wait until the read-write transactions running alongside them have finished.

### Mechanism 1: a stable frontier from in-flight knowledge

Spanner gives the cleanest formulation:

- Every replica tracks a safe time, and serves a read at timestamp t only if t ≤ t_safe.
- The transaction-manager part of t_safe is unbounded when no transaction is prepared but uncommitted. Otherwise it sits just below the earliest prepare timestamp among those transactions.
- A commit timestamp can never fall below its prepare timestamp, so nothing can later appear below t_safe.

The frontier is held back exactly by in-flight work and released as soon as that work resolves. No hole is ever examined.

Wang et al. describe Kafka's transactional log, which has the same shape:

- Records of open transactions are already written into the partition.
- Consumers in read-committed mode are served only up to the "last stable offset", which is the position just before the first record of a transaction that is still open.
- Commit and abort markers written into the log tell consumers which ranges to discard. A permanent gap is announced rather than inferred.
- A coordinator timeout aborts hung transactions, which bounds how long the frontier can stay pinned.

In PostgreSQL, the in-flight knowledge is the snapshot. `pg_current_snapshot()` reports an `xmin` and the list of transaction IDs still in progress. Every transaction below `xmin` has finished, either committed or aborted.

The design works like this:

1. Each append records its 64-bit transaction ID (`pg_current_xact_id()`, type `xid8`) next to the position.
2. The consumer reads only events whose transaction ID is below the snapshot's `xmin`.
3. Every row those transactions will ever contribute is already visible, so any remaining gap among them is permanent and safe to pass.

The consumer's cursor must be the pair (transaction ID, position), ordered by transaction ID first; position alone is not enough. A transaction ID is assigned at a transaction's first write, while a position is assigned at insert, so a transaction with a lower ID can hold a higher position. A position-only cursor gated on `xmin` could then step past a lower position that only becomes eligible later.

As a result, delivery order becomes (transaction ID, position) rather than raw position. That is acceptable where stream versions already guarantee order within each stream. These consequences are design inferences drawn from snapshot semantics, by analogy with the Spanner and Kafka frontiers.

The cost is the same as in Spanner and Kafka: the oldest running transaction pins the frontier. PostgreSQL transaction IDs are cluster-wide, so any long-running or idle-in-transaction session holds the frontier back, not only appenders. PostgreSQL's statement, idle-in-transaction and (from PostgreSQL 17) whole-transaction timeouts play the role of Kafka's coordinator timeout. The delay is bounded, and nothing is skipped.

### Mechanism 2: resolve each hole explicitly

CORFU's shared log has the same ambiguity at the storage layer. A sequencer hands out log positions before clients write to them. A client that crashes after taking a position leaves a hole, and readers cannot tell it from a slow write.

CORFU's answer is a *fill* operation. After waiting, a reader writes a junk value into the position. Positions are write-once, so exactly one of the original write and the fill succeeds. Either way the hole is settled for good, and a slow writer that lost the race finds out and retries. Kafka's abort markers do the same job from the writer's side.

A PostgreSQL analogue follows from how unique indexes behave. An insert whose key conflicts with an uncommitted row waits for that row's transaction to commit or abort. Suppose a consumer probes a suspect position by inserting a placeholder row with `ON CONFLICT DO NOTHING`. The probe blocks while the holder is in flight, and then one of three things happens:

- **The holder committed.** The probe does nothing, and the event is now visible.
- **The holder aborted.** The placeholder lands and marks the gap as permanent.
- **The holder had drawn the value but not yet inserted it.** The placeholder wins, the writer's insert fails, and the writer must retry with a new position. This is CORFU's write-once arbitration.

This is an inference; none of the records describe it as an established pattern. It has real costs:

- consumers write to the log table;
- it adds contention;
- writers must retry on uniqueness violations;
- the probe needs a lock timeout.

### Mechanism 3: time-bounded heuristics

"Wait T seconds, then skip the gap" is what the Dataflow model calls a heuristic watermark. Akidau et al. note that watermarks are generally heuristic, and can be either:

- too slow, which delays results (a stall); or
- too fast, which lets data arrive behind the watermark (a skip).

Their remedy is to separate the completeness signal from triggering, and to let late data update or retract results already emitted. Wang et al. likewise treat completeness under out-of-order data as a trade-off between correctness, latency and cost that users tune, not a fixed rule.

For a consumer, this means a timeout can never guarantee both "no stall" and "no skip". The best it can do is pair a skip timeout with a bounded re-check of skipped positions. Late arrivals are then delivered out of order, and each one raises an alert. A timeout is therefore a fallback or a monitoring signal, not the primary rule.

### Mechanism 4: make transient gaps impossible

CockroachDB's closed timestamps come at the problem from the other side. A leaseholder promises to accept no writes at or below a closed timestamp, and moves any writer that would land there up to a later timestamp. Readers below that frontier never wait.

On a single PostgreSQL node, the equivalent is to serialise appends so that position order equals commit order, for example with a lock held until commit around position assignment. Then any gap below the highest visible position must be permanent, and the naive gap rule becomes correct. The price is that appends from all writers are serialised, which limits throughput.

### Implication

For a store backed only by PostgreSQL, with positions drawn from a sequence before commit:

- Do not run gap-based loss detection on positions at all.
- Gate reads on the snapshot's `xmin`, with a (transaction ID, position) cursor.
- Bound stalls with transaction timeouts.
- Keep a time-based skip only as a monitored fallback with re-checks for late arrivals.

Notifications should stay pure wake-up hints. Their payload says nothing about transactions that have not yet committed, so they cannot settle a gap.
