# Has the proposed PostgreSQL patch that writes notification payloads through WAL, removing the commit-serialising NOTIFY lock, been accepted for a release, and what regressions did reviewers find?

## Question

Has the pgsql-hackers patch "Write Notifications Through WAL", which writes NOTIFY payloads into WAL so the global commit-serialising NOTIFY lock can go, been accepted into a PostgreSQL release? And what regressions or correctness problems did reviewers find in it?

## Findings

### Short answer

No. As of early October 2026 the patch has not been committed and is not in any release.

- **PostgreSQL 19 (beta).** PostgreSQL 19 is still in beta; Beta 4 was announced on 2026-09-24. Its release notes (dated "as of 2026-09-14") have one NOTIFY item: Joel Jacobson's change so that NOTIFY "only wake[s] up backends that are listening to specified notifications". They say nothing about writing notifications to WAL, removing the NOTIFY commit lock, or LISTEN on standbys.
- **Master (PostgreSQL 20 development).** `PreCommit_Notify` on master still takes the heavyweight lock. Its comment says the lock is held "till after commit" so that "queue entries appear in commit order": `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)`, the lock on "database 0". The file header still says notifications need "no WAL support or fsync'ing".
- **`async.c` history.** Commits to `async.c` up to 2026-09-23 include none that adds WAL-carried notifications.
- **The patch thread.** The last message is v9 from the author, Rishu Bagga, on 2025-11-25. A search of the pgsql-hackers archive found no later messages about the patch.
- **Commitfest status.** The commitfest app's patch search needs a login, so the entry's formal status (for example "Needs review" or "Returned with feedback") could not be checked. The public evidence shows a patch that stopped being reviewed in late 2025, not one that is heading for commit.

### Origin: from an out-of-order GUC to WAL transport

The work started in July 2025 with Bagga's proposal "Out-of-Order NOTIFY via GUC to Improve LISTEN/NOTIFY Throughput".

- **The problem.** The global lock taken in `PreCommit_Notify` "is not released until after the call to `RecordTransactionCommit`". So "each must become durable before the next can proceed": concurrent notifying transactions commit one at a time, each waiting for its own commit flush.
- **Tom Lane rejected the GUC.** He said "GUCs that change query semantics turn out to be very regrettable choices". A USERSET GUC would "break the notification order guarantees system-wide". And "queue entries appear in commit order" is "a rather fundamental assumption in async.c".
- **Tom Lane's alternative.** He then sketched the design the patch later used, borrowing ideas from two-phase commit:
  1. Write the transaction's notifications into a WAL record in `PreCommit_Notify`. He expected this to be parallelisable.
  2. Put that record's LSN in the commit record.
  3. Add a small fixed-size SLRU queue entry (xid, database OID, LSN).
  4. Listeners read the payload back out of WAL.

  He said this would also let hot-standby sessions receive NOTIFYs from the primary, "a feature many have asked for". He also warned that "step 3 would still require a global lock, to ensure that SLRU entries are made in commit order", held only for that much shorter step. **The design narrows the serialised section; it does not remove serialisation.**
- **Joel Jacobson's benchmarks.** He first argued that the lock was not the bottleneck, and that unnecessary `kill()`/SIGUSR1 wake-ups were. He later wrote "I was wrong here": which one dominates depends on the workload. With 1 listener and 1,000 notifying clients, commenting out the heavyweight lock raised throughput from 7,679 to 95,430 TPS. The wake-up half of that problem is what his separate channel-map patch fixed. Tom Lane committed it on 2026-01-15 for PostgreSQL 19, and its commit message says nothing about the commit lock. A follow-up fix to that code, "Fix NOTIFY wakeups for pre-commit LISTEN entries", landed in May 2026.

### Problems reviewers found, version by version

The first WAL-based versions (v1–v5, September 2025, in the original thread) reported about 2x TPS: roughly 30k to 63–66k at 100 clients. Reviewers found these problems:

- **Notify record written after commit (Arseniy Mukhin).** An early version wrote a separate `XLOG_ASYNC_NOTIFY_COMMIT` record after the commit record. He objected that "I don't think we can write anything about the transaction to the wal after we wrote the transaction commit record". He also noted that the global lock had been removed without anything else enforcing commit order for queue entries.
- **Assertion failure and failing tests (Matheus Alcantara).** v4 failed with `palloc` inside a critical section (`SignalBackends` called from `XactLogCommitRecord`), and isolation and regression tests failed.
- **Notifications delivered too early (Mukhin).** A transaction is not visible to new snapshots until `ProcArrayEndTransaction()`, which runs after the commit record is written. So listeners still need the `XidInMVCCSnapshot` check, or a listener "got the notification but still can't see changes notify transaction done". The patch dropped the check in v6 and restored it in v8.
- **Queue-full handling.** The patch first did not check for a full queue. A full queue inside the critical section would PANIC, where master raises an ERROR. Later versions reserve a queue slot before entering the critical section.
- **Contention (Mukhin).** Using `NotifyQueueLock` to enforce commit order blocks listeners from reading while a committer writes its commit record. Holding it while writing the payload record also loses WAL's parallel inserts. v7 fixed the second point: each backend records the current WAL insert position in `MyProc->notifyDataLsn` before writing, so no lock is needed for the payload write.
- **WAL retention, Masahiko Sawada's question.** Listeners read payloads from WAL, so the checkpointer must not recycle WAL that still holds unconsumed notifications. The resulting "WAL pinning" design added `AsyncNotifyOldestRequiredLSN()` to `RemoveOldXlogFiles`, and Mukhin found two bugs in it:
  - *Unbounded WAL growth.* One `NOTIFY ch, 'a'` followed by a 10-million-row insert made "wal grow[] without truncation", because entries already behind the queue tail were still pinning WAL.
  - *A race with the checkpointer.* It could miss a just-committed notification's LSN between scanning the per-page minimums and the per-backend LSNs.

  v8 fixed both by advancing the minimum when the queue tail advances and by swapping the order of the scans.
- **Unexplained slowdown for bare NOTIFY.** Mukhin benchmarked with 100 clients, no listeners and a 10-byte payload:

  | Workload | master (TPS) | v6 (TPS) | v7 (TPS) |
  |---|---|---|---|
  | `insert_only` | 30,982 | 34,941 | 30,933 |
  | `insert_with_notify` | 817.9 | 33,762 | 33,870 |
  | `notify_only` | 87,751 | 36,141 | 34,262 |

  - The patch made `insert_with_notify` 30–40x faster, close to insert-only throughput. This is the case that matters for NOTIFY inside an append transaction.
  - But `notify_only` (a transaction that only notifies) became about 2.5x slower: "master is 2.5 times faster than the patched version. Don't know why it happens."
  - Payload size (up to 2,000 bytes) made no difference, and runs were noisy.
  - In the messages examined, this regression was never explained or fixed.
- **Rebase and housekeeping (Sawada, November 2025).** He asked for a rebase onto HEAD, an updated design comment at the top of `async.c`, and an explanation of changed `pg_stat_slru` test output. The test change is expected: payloads no longer take SLRU pages. v9 (2025-11-25) addressed these.

v8 also added LISTEN on hot standbys, with notifications reaching standbys through replicated WAL. That widens what reviewers would need to check (replay, recovery, standby WAL retention), and the thread never examined it.

### What this means for an event store

On every released or beta PostgreSQL version, a NOTIFY inside an append transaction still takes the database-0 heavyweight lock and holds it through the commit flush. So:

- Notifying appends commit one at a time across the whole cluster.
- The 818-vs-31,000 TPS gap at 100 clients in Mukhin's benchmark shows the size of that cost on master.

The WAL design would bring notifying appends close to unserialised throughput, but:

- It is unmerged.
- Its last version has an unexplained 2.5x slowdown for bare NOTIFY.
- It has had no visible review since November 2025.
- Even Tom Lane's version keeps a short global lock to preserve commit order.

A consumer design should not count on this patch. It should treat the commit-time NOTIFY lock as a lasting constraint, for example by notifying outside the append transaction or by debouncing.
