# Does PostgreSQL guarantee that a NOTIFY committed concurrently with a session's LISTEN commit is either delivered to that session or visible to a snapshot taken after the LISTEN returns?

## Question

When one transaction appends an event and issues NOTIFY while another session is
committing its LISTEN on the same channel, can the notifying transaction fall
into a gap where the listener neither receives the notification nor sees the
event in a snapshot taken after its LISTEN completes? Or does PostgreSQL
guarantee one or the other?

## Findings

### Short answer

The guarantee holds, with conditions, but it comes from PostgreSQL's
notification implementation rather than from any published model. No scholarly
record in the OpenAlex catalogue analyses LISTEN and NOTIFY semantics. Searches
aimed directly at PostgreSQL's asynchronous notifications returned no records.
The scholarly literature does settle the snapshot half of the argument: what a
snapshot taken at a given moment can see. The delivery half rests on
PostgreSQL's own documentation and source commentary. Those are not cited here,
so the account of them below is flagged as unverified against a cited source.

The guarantee is only sound under three conditions:

- "After the LISTEN returns" must mean after the transaction that contains the
  LISTEN has **committed**.
- The later snapshot must be taken on the **same primary server**.
- "Delivered" means queued for the session by the server, not necessarily
  handed to application code yet.

### The snapshot half

Berenson et al. define Snapshot Isolation: a transaction reads from a snapshot
of the committed data as of its start. It sees the effects of every transaction
that committed before that point and of none that committed after. Ports and
Grittner describe how PostgreSQL implements this multiversion snapshot model and
builds its serializable level on it. Snapshot isolation is the basis of
PostgreSQL's REPEATABLE READ and SERIALIZABLE levels, while READ COMMITTED takes
a fresh snapshot for each statement. Kalay's survey of PostgreSQL's isolation
levels covers the same ground: what each level lets a reader see.

Two consequences matter here:

1. **Snapshots are monotone on one server.** If a writer's transaction already
   counts as committed for an earlier snapshot, it counts as committed for every
   later snapshot.
2. **Snapshot timing depends on isolation level.** Under READ COMMITTED, any
   statement issued after the LISTEN commit gets a qualifying snapshot. Under
   REPEATABLE READ or SERIALIZABLE, the snapshot is fixed at the transaction's
   first statement. A read transaction whose first query ran before the LISTEN
   committed therefore can't qualify, however late its catch-up read runs.

### The delivery half (implementation account, unverified here)

PostgreSQL's documentation says LISTEN takes effect at transaction commit. The
implementation commentary describes what happens during that commit:

- The session joins the shared listener set. From then on, the shared
  notification queue can't discard messages the session hasn't read yet.
- The session takes a fresh latest snapshot and uses it to classify queued
  messages.
- A message whose transaction is still in progress in that snapshot is held
  until the transaction resolves. It is delivered if the transaction commits and
  dropped if it aborts. So every notification from a transaction that commits
  after the registration snapshot is delivered.
- A message from a transaction that had already committed may or may not be
  delivered. That depends on where the session's queue read position starts,
  and the implementation may advance a new listener past messages that are
  already committed. Nothing is promised for these.

The commentary illustrates the hazard with a session that runs LISTEN and then
a SELECT inside the same transaction. The SELECT's snapshot predates a
concurrent writer's commit, and the writer's message can be passed over, so the
session misses both the change and the notification. The rule stated there is
that a LISTEN must be committed before the session inspects the state it is
meant to track.

### Why the two halves meet without a gap

Call the snapshot the listener takes when it registers S_L. Every notifying
transaction T falls on one side of S_L:

- **T is in progress, or hasn't started, at S_L.** The listener is already
  registered, so T's message stays in the queue and is delivered when T
  commits.
- **T is committed at S_L.** By monotonicity, T's writes are visible to every
  snapshot taken after the LISTEN commit returns, including the consumer's
  catch-up read.

On a single primary there is no third case. This split plays the role of the
monitor lock in Lampson and Redell's account of Mesa monitors. There, checking a
condition and starting to WAIT happen atomically under the monitor lock, so no
NOTIFY can slip in between. PostgreSQL has no lock that spans a LISTEN and a
read, and the registration snapshot closes that window instead.

Lampson and Redell's semantics also explain how to treat the signal itself. A
Mesa NOTIFY is a hint, so the waiter re-checks its condition in a loop, and WAIT
accepts a timeout so a missing notification can't block forever. A PostgreSQL
notification should be read the same way: as "the log may have advanced", which
triggers a re-read by position.

### Conditions and caveats

- **"Returns" must mean "commits".** A LISTEN in autocommit mode returns after
  its commit. A LISTEN issued inside an explicit transaction block returns
  before it takes effect. psycopg 3 connections are not autocommit by default,
  so a listening connection must either use autocommit or commit right after
  the LISTEN, before the catch-up read starts its snapshot.
- **Same primary only.** The visibility half assumes the catch-up read sees
  everything committed on the server where the LISTEN registered. A streaming
  replica may lag behind the primary, so a read from a replica doesn't qualify.
- **Both halves can hold at once.** A writer that committed before S_L may still
  be delivered. A writer that commits after S_L but before the catch-up read
  will be both visible and delivered. The consumer must therefore tolerate
  wake-ups for events it has already read. An idempotent read from the stored
  position handles this.
- **Delivery is to the session, not the application.** The server passes
  notifications to the client only between transactions. Whether the client
  library keeps them while the application is busy is a separate question about
  the client library.
- **The guarantee lasts only as long as the registration.** If the listening
  connection drops, the registration is lost. Recovery must repeat the whole
  sequence: commit a new LISTEN, then read with a snapshot taken after that
  commit.
- **A stalled listener can break writers.** PostgreSQL's documentation says that
  once the notification queue is full, transactions calling NOTIFY fail at
  commit. If the event append and its NOTIFY share a transaction, a listener
  that stops reading, for example one left idle in a transaction, can make
  appends fail.
- **Per-transaction only.** The guarantee is about whole transactions. It says
  nothing about whether positions assigned before commit appear in order, so it
  doesn't address sequence gaps left by in-flight transactions.

### Lineage

NOTIFY descends from the "alerters" that Stonebraker and Rowe listed among the
original POSTGRES design goals for active-database support, alongside triggers.
That design paper treats alerters as part of the rules system and doesn't set
out how registering for an alert interacts with concurrent commits. The
deliver-or-visible property is a later implementation guarantee, not part of the
original design literature.
