# Does closing, breaking out of, or cancelling a psycopg 3 notifies() generator part-way through a multi-notification batch silently drop the remaining notifications, and can a test sending several NOTIFY commands in one transaction reproduce it?

## Question

If a psycopg 3 `Connection.notifies()` or `AsyncConnection.notifies()` generator is stopped part-way through a batch of notifications that arrived together, are the notifications not yet yielded lost without any error? And can a test that sends several `NOTIFY` commands in one committed transaction reproduce that reliably?

## Findings

**Short answer.** Yes. Every psycopg 3 release up to the current 3.3.6 behaves this way. If the generator is closed while it is suspended in the middle of a batch it read from libpq, the rest of that batch is thrown away. It does not go back on the connection's backlog, and no warning, log line or exception reports it. Closing can happen through an explicit `close()` or `aclose()`, a `break` that drops the last reference to the generator, an exception raised in the loop body, or a cancelled asyncio task whose abandoned generator is later finalised. Two exits are safe because they only stop between batches: `stop_after` and `timeout`. Notifications served from the backlog are also safe (more on the backlog below). A test can reproduce the loss. It needs a second connection that commits several `NOTIFY` commands with distinct payloads in one transaction, and the listener must not run a query between that commit and entering `notifies()`.

### Why the remainder of a batch is lost

The low-level `notifies` generator in `psycopg/generators.py` waits until the socket is readable and calls `pgconn.consume_input()`. It then drains libpq in a loop (`while n := pgconn.notifies(): ns.append(n)`), calls `pgconn.notify_handler(n)` for each item, and returns the whole list. Draining is destructive. The libpq documentation says that once `PQnotifies` returns a notification, "it is considered handled and will be removed from the list of notifications". From then on the batch exists only in that Python list.

In 3.3.6, as on `master`, `Connection.notifies()` runs everything inside `with self.lock:`. It first swaps the connection's backlog out (`self._notifies_backlog, d = (None, self._notifies_backlog)`). It then loops: `pgns = self.wait(notifies(self.pgconn), timeout=remaining)` followed by `for pgn in pgns: yield Notify(...)`. Cleanup is a `finally:` clause that does only `self._notifies_backlog = d`.

Closing the generator raises `GeneratorExit` at the suspended `yield` inside `for pgn in pgns`. The `finally` puts back the old backlog deque, and the rest of `pgns` is never added to it. That remainder cannot come back by another route either:

- libpq has already removed those notifications.
- The connection's internal handler, `BaseConnection._notify_handler`, adds a notification to the backlog only when `_notifies_backlog` is not `None`. The code comment says it "is None if the `notifies()` generator is running", so nothing was copied to the backlog while the batch was being drained.

`AsyncConnection.notifies()` has the same structure, using `async with self.lock` (an `asyncio.Lock`) and `pgns = await self.wait(...)`.

The batch-local list is old. In 3.1.18 the code was already `ns = self.wait(notifies(self.pgconn))` followed by `for pgn in ns: yield n`, with the lock released before yielding. Later releases did not change it:

- 3.2 kept the lock held across yields and added `timeout` and `stop_after` (#340, #760).
- 3.2.4 added the backlog so that notifications arriving while the generator is not running are no longer lost (#962, PR #975).
- 3.2.10 stopped collecting the backlog when notify handlers are registered (#1091, #1092) and deprecated using handlers and the generator together.

### Which ways of stopping lose notifications, and which do not

- **Explicit `close()` or `aclose()` mid-batch: loses the rest.** psycopg's own documentation example calls `gen.close()` inside the `for` loop when it sees a `"stop"` payload, so any later notifications in the same batch would be dropped. The project's `test_notify` uses this pattern too, but its two notifications are sent 0.25 s apart, so the test never closes in the middle of a batch.
- **`break`: depends on whether the generator is still referenced.** The Python language reference says a generator that is "finalized (by reaching a zero reference count or by being garbage collected)" has `close()` called on it, which runs pending `finally` clauses.
  - With `for n in conn.notifies(): break` in CPython, the last reference goes away straight after the loop, so the generator is closed and the rest of the batch is lost.
  - If the generator is held in a variable, `break` leaves it suspended. Nothing is lost yet, and calling `next()` again would continue with the rest of the batch. Meanwhile it keeps holding the connection's `threading.Lock`, which is not re-entrant, so other operations on that connection have to wait for it. Any later close or garbage collection drops the remainder.
- **An exception raised in the loop body: loses the rest.** The exception propagates out of the `for` loop and the abandoned generator is then finalised. This follows from the generator semantics above, so a failing per-notification handler inside the loop loses the rest of its batch.
- **asyncio cancellation: depends on where it lands.** The low-level generator has no `yield` between `consume_input()` and returning the list. Cancellation can therefore only land in one of two places:
  - *Before anything is read.* The data stays in libpq or the socket and nothing is lost.
  - *After the batch is in `pgns`.* By then the async generator only gives control back to the consumer at its `yield`s. A cancellation hitting the consumer's own `await` leaves the generator suspended mid-batch. When it is finally closed, by explicit `aclose()` or by the event loop's async-generator finalizer, the rest of `pgns` is lost. The language reference warns that async generators that exit early "by `break`, the caller task being cancelled, or other exceptions" are cleaned up by the event loop's finalizer unless the caller calls `aclose()` explicitly.
- **`stop_after`: safe.** The generator only compares the count with `stop_after` after it has yielded a whole batch. The API documentation says: "You might actually receive more than this number if more than one notifications arrives in the same packet."
- **`timeout`: safe.** A timeout raises `_WaitTimeout` while the generator is still waiting, before anything is read from libpq, and the deadline is otherwise checked only after a whole batch.
- **Items served from the backlog: safe.** Notifications collected while the generator was not running are yielded one at a time with `d.popleft()`. On close, the unyielded ones stay in `d`, and the `finally` puts `d` back.
- **If notify handlers are registered**, they run for every item during the drain, so the handlers see the whole batch even when the generator drops the tail. Mixing handlers with the generator has been deprecated since 3.2.10 and raises a `RuntimeWarning`.

Among the notification-related issues listed in psycopg's tracker, none is about losing the tail of a batch when the generator is closed. Issue #1310 describes the related limitation that `notifies()` "holds self.lock for the entire generator lifetime", and lists "close() and reopen it whenever LISTEN/UNLISTEN is needed" as a workaround. That is exactly the restart pattern that runs into this loss.

### Reproducing it with a multi-NOTIFY transaction

PostgreSQL's rules make one committed transaction a natural source of one batch:

- Notifications are delivered only "until and unless the transaction is committed".
- Notifications from the same transaction are delivered "in the order they were sent".
- Duplicate notifications with the same channel and payload in one transaction are folded into one, so the test must use distinct payloads.

In `async.c`, a signalled listening backend reads "all of the notifications that have arrived since scanning last time" in a single pass. psycopg's own `test_stop_after_batch` relies on this. It commits `notify foo, '1'` and `notify foo, '2'` in one transaction from a second connection and asserts that `list(conn.notifies(timeout=1.0, stop_after=1))` returns both. That test is marked `@pytest.mark.timing`, i.e. timing-sensitive.

A reproduction therefore needs four conditions:

1. **Send from a separate connection.** Notifications that reach the listener while it is running a statement are moved into the backlog, which survives a close.
2. **Run no query on the listener between the commit and entering `notifies()`.** Any query moves pending notifications into the backlog (since 3.2.4) and hides the bug. psycopg's `test_first_notify_not_lost` already runs both cases through a `query_between` parameter, and the same parametrisation works here as a control.
3. **Use distinct payloads.**
4. **Assert on the full sequence.** Compare everything received with what was sent, rather than checking a count.

The sketch below was derived from the code above and has not been run. Against psycopg 3.0 to 3.3.6 it is expected to receive only `"1"`:

```python
def test_closing_notifies_mid_batch_keeps_remaining_notifications(dsn):
    with psycopg.connect(dsn, autocommit=True) as listener, \
            psycopg.connect(dsn, autocommit=True) as notifier:
        listener.execute("LISTEN events")
        with notifier.transaction():
            notifier.execute("NOTIFY events, '1'")
            notifier.execute("NOTIFY events, '2'")
            notifier.execute("NOTIFY events, '3'")

        generator = listener.notifies(timeout=2.0)
        first = next(generator)
        generator.close()
        rest = list(listener.notifies(timeout=0.5))

        assert [first.payload, *(n.payload for n in rest)] == ["1", "2", "3"]
```

Two variants make the test more convincing:

- **Batch-arrival control.** `list(listener.notifies(timeout=2.0, stop_after=1))` returning all three payloads shows that the batch arrived together. It also confirms that `stop_after` is lossless.
- **Backlog-path control.** Running `listener.execute("SELECT 1")` before creating the generator should make the original assertion pass, because the three notifications are then served from the backlog.

Remaining nondeterminism comes from packet boundaries. If the messages arrive in separate reads, the close lands between batches and the test passes falsely. That is why the batch-arrival control matters, and why the test should be treated as timing-sensitive, as psycopg treats its own.

### Implications for a notification-driven consumer

Code that ends a `notifies()` iteration early cannot assume that every notification it was sent was handed to it. These measures avoid the loss:

- Leave the generator only through `timeout` or `stop_after`, for example to change LISTEN registrations or send heartbeats, never with `break` or `close()`.
- Keep the loop body trivial and unable to raise: push each `Notify` straight onto an in-process queue.
- In asyncio, call `aclose()` explicitly, for example with `contextlib.aclosing`, and only when the generator is not mid-batch.
- Most importantly, treat each notification as a wake-up hint. After every generator restart, catch up from the event store's last processed position, so a dropped notification only delays work and never loses it.
