# Does serialising appends per category with a transaction-scoped advisory lock, as Message DB does, remove the need for gap detection in category readers, and what write throughput does it cost?

## Question

Message DB takes a transaction-scoped advisory lock on the category before every append. Does that remove the need for gap detection in readers that consume one category by global position? And how much write throughput does it cost?

## Findings

**Short answer.** Yes, for a reader that filters on exactly one category, as long as every writer takes the same lock. No, for any reader that spans categories, such as a whole-store or multi-category reader. The cost is that appends to one category are fully serialised. Each append transaction holds the lock from its first write until it ends, which includes the commit flush and any wait for a synchronous standby. So the maximum commit rate per category is roughly the inverse of that hold time. Appends to different categories still run in parallel. No published benchmark of Message DB's write throughput was found. The maintainer's own open issue asks for a "high-performance, non-locking write function", which suggests the lock is the known limit on write rate.

### What Message DB does

`write_message` first calls `acquire_lock(stream_name)`. That function derives the category from the stream name, hashes it with `hash_64`, which takes the first 64 bits of an MD5 digest, and calls `pg_advisory_xact_lock` on the result. Only then does `write_message` read the stream version, check `expected_version`, and `INSERT` the row. The `global_position` column is a `bigserial` primary key, so its sequence value is drawn during that `INSERT`, after the lock is held. The lock does two jobs:

- **Stream versions.** It keeps the per-stream `position` gapless. The maintainer explained that otherwise "using the `position` as an optimistic concurrency protection would not be guaranteed to work". A unique index on `(stream_name, position)` backs this up.
- **Consumer ordering.** It makes consumers safe. The Eventide documentation says: "The lock ID is derived from the category name of the stream being written to. The result of which is that all writes to streams in a given category are queued and processed in sequence. This ensures that write of a message to a stream does not complete after a consumer has already proceeded past its position."

The category reader is correspondingly simple. `get_category_messages` selects `WHERE category(stream_name) = $1 AND global_position >= $2 ORDER BY global_position ASC LIMIT $3`. It has no high-water mark, no gap tracking and no wait for missing positions. The README states that "Global position may have gaps", and the reader simply steps over them. Eventide consumers find new work by polling: they fetch batches back to back, and sleep for `poll_interval_milliseconds` only when a batch comes back empty.

### Why it removes gap detection for single-category readers

The guarantee rests on the order of operations inside PostgreSQL's commit:

- **Sequence values and abort gaps.** Sequence values are never handed back. PostgreSQL's documentation says aborts, crashes and even `INSERT ... ON CONFLICT` leave gaps, and that sequences "cannot be used to obtain 'gapless' sequences". Without a lock, a transaction that draws a later number can commit before one that drew an earlier number. A reader that moves past the later number then skips the earlier one for good.
- **Visibility before lock release.** In `CommitTransaction`, PostgreSQL calls `ProcArrayEndTransaction` before releasing locks through `ResourceOwnerRelease(..., RESOURCE_RELEASE_LOCKS, ...)`. `ProcArrayEndTransaction` is the point at which a commit becomes visible to new snapshots. The source comment says this "must be done _before_ releasing locks we hold". Transaction-level advisory locks are released at transaction end, like ordinary locks.

Put together, the next writer in a category cannot even draw a sequence number until the previous writer's transaction is visible or rolled back. So within one category, `global_position` order matches commit-visibility order. Any snapshot that sees position N+1 in a category also sees every committed lower position in that category. Every gap a category reader sees is therefore permanent. It is either a number used by another category, an aborted insert, or a lost sequence value. The reader can move past it at once. A wake-up-driven consumer then needs only "read everything after my last position" for that category; it never has to wait out a gap. By the same reasoning, reads from a hot standby should be safe too, because commit records reach the WAL in the same serialised order. That is an inference, not something either project documents.

### Where the guarantee stops

- **Only within one lock key.** Writes to different categories are not ordered relative to each other. A reader that spans categories can still see a later position before an earlier one commits. Message DB sidesteps this: its functions offer category, stream and last-message reads, but no whole-store read. A library that does offer a log-wide or multi-category reader still needs gap detection or another approach for that reader. One option is transaction-ID bounds, recording `pg_current_xact_id()` with each event and reading only below `pg_snapshot_xmin`, as described by Eugene Khyst and Oskar Dudycz. Another is the advisory-lock "ceiling on reads" described by Sequin.
- **Advisory means voluntary.** PostgreSQL states that "the system does not enforce their use — it is up to the application to use them correctly". A bulk import, migration or hand-written `INSERT` that skips the locking path brings the race back for that category.
- **Shared key space.** Two categories whose 64-bit hashes collide share a lock. The same applies to any other code in the database that uses an equal advisory key, such as a job library. This adds blocking but does not break the ordering guarantee.
- **Deadlock risk.** A transaction that appends to several categories takes several locks in the order it writes. Two such transactions writing in opposite orders can deadlock. PostgreSQL resolves this by aborting one of them, and it advises acquiring locks "in a consistent order".
- **Wake-ups are still needed.** The lock removes gap handling, not polling. Consumers still need either a poll interval or a push wake-up to learn that the category has new rows.

### What it costs in write throughput

- **How long the lock is held.** Per category, only one append transaction at a time can be between its first `write_message` and its end. The lock covers everything that happens in that span:
  - later writes in the same batch
  - any other statements in the transaction
  - client round trips before `COMMIT`
  - the commit itself

  With `synchronous_commit` on, the commit includes the local WAL flush. PostgreSQL's `RecordTransactionCommit` also waits for synchronous standbys while it "still show[s] as running in the procarray and continue[s] to hold locks". So synchronous replication adds a network round trip to every category's serialised section.
- **Rough ceilings.** The per-category limit is about 1 / hold time. As arithmetic only, not a measurement: a 1 ms hold allows about 1,000 append transactions per second per category, and a 5 ms hold with a synchronous standby allows about 200. Batching several messages into one transaction raises the message rate but not the transaction rate.
- **Group commit.** PostgreSQL's group commit lets sessions that reach the WAL flush at the same moment share one flush. Writers to the same category can never reach commit together, so they cannot share flushes with each other, only with writers to other categories. This too is an inference from the documented mechanism.
- **Where it bites.** Total throughput grows with the number of busy categories. It does not grow within one category. A workload where one entity type, and so one category, takes most of the writes is limited by that one category's serial rate.
- **Published evidence.** No benchmark of Message DB appends was found. The maintainer's March 2024 issue #54, "Add a high-performance, non-locking write function for purely telemetric use cases", is still open and has no description. Related evidence comes from global serialisation, which is the unpartitioned worst case:
  - Sequin reports that a serialising sequence table means "your insert throughput takes a hit. Writes now funnel through updates to `my_seq`, which must happen serially". Its main fix was to "make sure you don't touch `my_seq` until the last possible moment in your transaction", so the lock is held as briefly as possible.
  - Oskar Dudycz tried a singleton gapless-counter table for an outbox and found "the performance hit … was too big to accept".
  - Commanded EventStore appends by running `UPDATE ... streams SET stream_version = stream_version + $2 WHERE stream_id = 0` on its `$all` stream row. Under PostgreSQL's row-locking rules, a concurrent updater of that row "will wait for the first updating transaction to commit or roll back". By inference, that serialises appends across the whole store.
- **Marten as the opposite trade-off.** Marten does not serialise. Its async daemon tracks a high-water mark instead, and its documentation acknowledges an event "skipping" issue in the default Rich append mode "when a system becomes slow under heavy loads". So the cost of not serialising falls on readers.
- **Mitigations.** Each of these follows from the mechanism above:
  - Take the lock as late as possible. Message DB takes it at the start of each `write_message` call, so in a multi-message transaction it is held from the first write. Do appends last.
  - Batch several messages into each transaction.
  - Keep other work out of append transactions.
  - Use finer lock keys, accepting that each reader's filter must then match exactly one key.
  - For specific transactions, accept asynchronous commit. With `synchronous_commit` off, PostgreSQL skips the commit-time `XLogFlush`, so the flush leaves the serialised section, at the price of possibly losing the most recent commits in a crash.

For a psycopg 3 event store, the pattern means a category consumer woken by a notification can safely read "position greater than last seen" with no gap wait. That safety is paid for by serialising appends within each category. Any log-wide consumer keeps the original gap problem.
