# How should an event-store library share one dedicated LISTEN connection per process across many subscriptions, fanning out in-process wake-ups and re-subscribing every channel after reconnect, as River and Oban do?

## Question

How should an event-store library share one dedicated LISTEN connection per process across many subscriptions, fanning out in-process wake-ups and re-subscribing every channel after reconnect, as River and Oban do?

## Findings

### Why a re-subscription mechanism is needed at all

PostgreSQL ties listening to the session. "LISTEN registers the current session as a listener on the notification channel", "LISTEN takes effect at transaction commit", and "A session's listen registrations are automatically cleared when the session ends". Running LISTEN again on a channel the session already listens to does nothing, so re-issuing is safe. NOTIFY only reaches clients that have "previously executed LISTEN" on that channel, and events "are only delivered between transactions". So when a listener connection drops, the server forgets all its channels. Anything notified during the outage is gone. The Postgrex documentation says this outright: "any notifications that occur during the disconnection period are not queued and cannot be recovered". That is why every mature implementation keeps the list of what it should be listening to outside the connection, re-applies it after every reconnect, and backs notifications with a polling fallback.

### How the reference implementations are built

**River (Go).** Each client has exactly one `notifier.Notifier`, built from `driver.GetListener()` unless `PollOnly` is set. The pgx v5 driver takes the listener's connection from the pool with `Acquire()` and then `Hijack()`s it: "Assume full ownership of the conn so that it doesn't get released back to the pool or auto-closed by the pool." On close, it closes the connection outright rather than releasing it, "to guarantee no other caller will receive a partially tainted connection". Topic names are double-quoted and prefixed with the schema.

Subscriptions live in a mutex-guarded `map[NotificationTopic][]*Subscription`. LISTEN runs only for a topic's first subscriber, and UNLISTEN only when "this is the last subscription on the topic". `Listen` blocks until the server-side LISTEN has finished. If the notifier is in its wait, `Listen` sends an operation on `waitInterruptChan` and cancels the wait's context. The main loop then "Drain[s] any and all interrupt operations before continuing back into a new wait to give any new subscribers a chance to listen/unlisten."

The run loop goes connect, re-LISTEN every topic in the map, wait. On any error it closes the connection, waits with exponential backoff and starts over: "The loop below will connect/close on every iteration, but do one initial connect so the notifier fails fast in case of an obvious problem." While waiting, it pings the connection when 5 seconds pass without a notification.

Received notifications go into a 1000-slot buffered channel. A non-blocking send drops them when it is full ("Dropping notification due to full buffer"). One `deliverNotifications` goroutine then calls each subscriber's callback in turn, so a slow callback holds up the rest. The source carries a "TODO: panic recovery on delivery attempts".

River copes with this by keeping callbacks tiny. Each queue's producer subscribes separately to the insert and control topics. Its insert callback just checks the queue name in the payload (`if decoded.Queue != p.config.Queue { return }`) and calls `p.fetchLimiter.Call()`, a non-blocking trigger rate-limited by `FetchCooldown` (default 100 ms). Producers unsubscribe on shutdown. Missed or dropped notifications are covered by `FetchPollInterval` (default 1 s): "Typically new jobs will be picked up ~immediately after insert via LISTEN/NOTIFY, but this provides a fallback."

**Oban (Elixir).** `Oban.Notifiers.Postgres` runs one `Postgrex.SimpleConnection` per Oban instance with `auto_reconnect: true`. Channel names are namespaced as `"#{prefix}.oban_#{channel}"`. The list of who listens to what is kept apart from the connection, in a `Registry` with duplicate keys keyed by `{conf_name, channel}`, and the Registry removes processes that die. The notifier docs promise: "Registration is durable across notifier restarts. If the notifier is unavailable when `listen/2` is called… the registration is still recorded and the notifier picks it up when it reconnects."

The connection process issues LISTEN only for channels it is not already listening to. It issues UNLISTEN only when a channel has no registered listeners left. On reconnect, `handle_connect/1` re-LISTENs every channel found in the registry. Each notification is decoded once in `relay/3`, filtered by `ident`, and sent as `{:notification, channel, decoded}` to each registered process's mailbox. That makes fan-out asynchronous: a slow listener cannot block the others.

Oban also checks that delivery actually works. Its Sonar process sends pings on a `sonar` channel, starting at 5 s and backing off to at most 60 s. It forgets peers it has not heard from in 120 s and reports a status of `:isolated`, `:solitary` or `:clustered`. When the status is `:isolated`, the Stager switches to "local" mode: on its 1-second polling cycle it sends wake-ups straight to the in-process queue producers instead of relying on NOTIFY.

**Postgrex.Notifications** (which Oban's design follows) keeps `listeners` (ref → {channel, pid}) and `listener_channels` (channel → refs) maps and monitors every listening process. It sends LISTEN only for a channel's first listener and UNLISTEN when the last one leaves or its process goes `:DOWN`. On reconnect it re-LISTENs all channels in one round trip by joining `LISTEN "…";` statements. Its docs recommend the order "subscribe, get current state, process notifications". They also warn that unquoted channel names are case-folded.

**Other examples.** GoodJob (Ruby) checks a connection out of the pool and removes it from the pool, uses one channel, waits in `wait_for_notify` for 1 s at a time, runs `SELECT 1` every 10 s as a keepalive, and reconnects after 5 s, reporting errors after 6 in a row. Its production poll interval defaults to 10 s.

Rails Action Cable's PostgreSQL adapter shows the queueing pattern clearly, and also what is missing without reconnect handling. It uses one listener thread per process on a connection created with `new_connection` (never checked out of the pool). Subscribe and unsubscribe requests go into a `Queue` that the listener thread drains between `wait_for_notify(1)` calls. Names are quoted with `escape_identifier`, and names over 63 bytes are SHA1-hashed. But it has no reconnect or re-LISTEN logic, so a dropped connection silently ends delivery.

Procrastinate, a Python library on psycopg 3, opens a standalone `autocommit=True` `AsyncConnection` outside its pool, quotes channels with `sql.Identifier`, and on `OperationalError` restarts an outer `while True` loop that reconnects and re-LISTENs. Its worker callback only sets an `asyncio.Event`, which the fetch loop waits on alongside a 5 s polling sleep.

### What this means for psycopg 3

Two psycopg details shape the design.

- **`notifies()` holds the connection lock while it runs.** In the synchronous `Connection` source, the generator takes `with self.lock:` for its whole lifetime. Another thread that tries to run LISTEN on that connection will block until the generator exits. So the listener connection needs one owning thread or task. Subscription changes should be queued and applied between runs of `notifies(timeout=…)` (the timeout was added in 3.2), the Action Cable approach, or by interrupting the wait, the River approach. Since 3.2.4, notifications that arrive between a LISTEN and the start of the next generator "are captured and yielded by the generator once it is started", so the gaps between runs do not lose anything.
- **Handlers fire only during connection activity.** `add_notify_handler()` callbacks run "only during a connection operation, such as a query". A dedicated listener therefore has to sit in `notifies()`. It cannot rely on callbacks firing in the background.

The connection should be in autocommit mode, as the psycopg docs advise, so that LISTEN takes effect immediately and notifications arrive promptly.

### Recommended shape for an event store

The following design is synthesised from the implementations above.

1. **One listener per process per database.** Create it lazily with a lock, like Action Cable's singleton. It owns a dedicated autocommit connection opened outside the pool, the way Procrastinate and Action Cable do. Alternatively it can take ownership of a pooled connection permanently, as River's hijack and GoodJob's remove-from-pool do. Either way, the connection is closed rather than returned when the listener stops.
2. **Keep the subscription list outside the connection.** Map each channel to a set of subscriber handles. LISTEN on the first subscriber, UNLISTEN on the last, and drop subscribers automatically when they are closed or garbage-collected (as Oban's Registry and Postgrex's monitors do). This list is the only source for re-LISTEN after a reconnect.
3. **Let the owning task make every change.** `subscribe()` queues a command and waits until the LISTEN has finished, as River's `Listen` does. Only then does the subscriber run its catch-up read from its checkpoint: subscribe first, then read current state.
4. **Keep fan-out cheap and coalescing.** Decode each payload once, keep it a small hint well under the 8000-byte limit, and filter in-process, as River's queue check does. Wake each matching subscriber with a non-blocking, coalescing signal such as an `asyncio.Event` or flag, never by running its read on the listener task. Many notifications then collapse into one re-read, and a slow subscriber cannot delay the rest. Like River's drop-on-full buffer, this works only because notifications are hints and reads are idempotent.
5. **Reconnect fully.** On any error, close the connection, back off exponentially, reconnect and re-LISTEN every channel in the list in one round trip. `pg_listening_channels()`, which "Returns the set of names of asynchronous notification channels that the current session is listening to", can confirm the result. Then wake every subscriber once, because anything notified during the outage is lost. River and Oban leave this to their 1-second polls; for an event store, an explicit post-reconnect wake-up closes the gap at once.
6. **Track health and fall back to polling.** Ping when idle, as River does every 5 s and GoodJob every 10 s. Also send a periodic NOTIFY to yourself on a private channel, like Oban's Sonar, to prove end-to-end delivery. Expose the resulting status, and while it is unhealthy have subscribers poll on a short interval, as Oban's Stager does in local mode. Keep a slower background poll running in every state, the way River's `FetchPollInterval` does.
7. **Name channels carefully.** Quote identifiers (`sql.Identifier`), namespace them with the schema or a prefix (River, Oban), and hash any name over 63 bytes (Action Cable) so truncation cannot cross-wire subscriptions.
