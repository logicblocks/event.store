# How should a psycopg 3 application multiplex many subscriptions over one listening connection, and what happens to notifications across reconnection, connection poolers in transaction mode, and failover to a standby?

## Question

How should a psycopg 3 application multiplex many subscriptions over one
listening connection, and what happens to notifications across reconnection,
connection poolers in transaction mode, and failover to a standby?

## Findings

### Summary

Run one dedicated listening connection per process. It should be in autocommit
mode, live outside any `psycopg_pool` pool, and connect either directly to the
primary or through a session-mode pooler. Keep an in-process registry that maps
each channel to its interested subscribers, so each channel needs only one
`LISTEN`. Drive the connection with a loop of short `notifies(timeout=...)`
calls and apply `LISTEN` or `UNLISTEN` changes between them, because the
generator holds the connection lock while it waits.

Notifications reach only sessions that are listening at the moment the sending
transaction commits. PostgreSQL does not write them to the WAL, so they do not
survive a lost session or a failover. A transaction-mode pooler cannot carry
`LISTEN` at all. Every reconnection or failover therefore has to follow the same
steps: reconnect to a writable primary, re-issue every `LISTEN`, and only then
tell every subscriber to re-query from its stored position. A notification
tells a subscriber that new data may exist. It does not carry the data.

### PostgreSQL semantics the design must respect

- **Registration is per session.** `LISTEN` "registers the current session as
  a listener on the notification channel", and calling it again for the same
  channel does nothing. "A session's listen registrations are automatically
  cleared when the session ends" (PostgreSQL `LISTEN` docs). One `LISTEN` per
  channel on one session can therefore serve any number of in-process
  subscribers.
- **LISTEN is transactional.** "LISTEN takes effect at transaction commit". If
  the transaction rolls back, the listening set does not change. A `LISTEN` only
  protects against missed notifications once it has committed.
- **Delivery happens only between transactions.** A listening session that is
  inside a transaction receives notifications only "just after the transaction
  is completed", and "notification events are only delivered between
  transactions" (PostgreSQL `NOTIFY` docs). In the server source, a backend
  handles the notify interrupt immediately only when it is idle, and otherwise
  just before `ReadyForQuery` (`async.c`). Psycopg's docs say the same thing in
  practical terms: "you should keep the connection in autocommit mode if you
  wish to receive or send notifications in a timely manner."
- **Ordering and folding.** Notifications from one transaction arrive in the
  order they were sent. Notifications from different transactions arrive "in
  the order in which the transactions committed". Identical channel and payload
  pairs within one transaction are folded into a single notification.
- **A slow listener holds back the whole cluster.** There is one global queue,
  stored in the `pg_notify` SLRU. The queue can only be truncated up to the
  position of the slowest listening backend (`async.c`). If the queue (8GB by
  default) fills, "transactions calling NOTIFY will fail at commit". The
  listening connection must therefore never sit idle in a transaction and must
  be drained promptly. `pg_notification_queue_usage()` reports how full the
  queue is, and `pg_listening_channels()` lists the current session's channels,
  which is useful for checking registrations after a reconnect.

### psycopg 3 mechanics that shape multiplexing

- **Two ways to receive.** psycopg 3 offers the `Connection.notifies()`
  generator, which yields `Notify(channel, payload, pid)` objects, and callbacks
  registered with `add_notify_handler()`. Handlers fire only "during a
  connection operation, such as a query". On an idle listening connection a
  handler therefore never runs unless something keeps querying. The generator is
  the right tool for a dedicated listener. The docs say to use only one of the
  two methods. Since 3.2.10, using both raises a `RuntimeWarning`, and the async
  source warns that combining them "is not reliable".
- **`timeout` and `stop_after` (added in 3.2).** `notifies(timeout=...)` returns
  once the deadline passes. `stop_after=n` stops after `n` notifications, though
  "you might actually receive more" when several arrive in one packet.
- **The generator holds the connection lock for its whole run.** In both
  `Connection.notifies()` and `AsyncConnection.notifies()` the code enters
  `with self.lock` (or `async with self.lock`) before it starts waiting, and
  `Cursor.execute()` takes the same lock. A `LISTEN` issued from another thread
  or task while the generator is waiting therefore blocks until the generator
  returns. psycopg connections are thread-safe, but their operations run one at
  a time. The practical result: drive the listener with a bounded-timeout loop
  and apply queued `LISTEN` and `UNLISTEN` changes between iterations. The
  timeout sets an upper bound on how long a new subscription waits to take
  effect, and gives the loop a regular point for health checks. Based on the
  source, the wait is a client-side wait on the socket, so an empty timeout
  costs the server nothing.
- **Notifications that arrive between generator runs.**
  - Before 3.2.4, notifications that arrived while the generator was not running
    were lost. psycopg issue #962 shows this: a health-check query run between
    two `notifies()` calls lost a notification that was sent during the query.
  - Since 3.2.4, such notifications are kept in a backlog, and the next
    `notifies()` call yields them first, as the source shows.
  - 3.2.10 fixed a memory leak when the generator is never called (#1091). It
    also stopped capturing the backlog when a handler is registered.
  - The timeout-loop pattern therefore depends on psycopg 3.2.10 or later.

A minimal shape for the dispatcher loop (sync; the async form is the same with
`async for`):

```python
conn = psycopg.connect(dsn, autocommit=True)
while running:
    apply_pending_subscription_changes(conn)   # LISTEN / UNLISTEN, between waits
    for n in conn.notifies(timeout=1.0):
        registry.wake(n.channel, n.payload)    # non-blocking, coalescing
```

- **Fan-out without back-pressure on the connection.** brandur's "notifier
  pattern" (written for Go, but the idea is not Go-specific) keeps
  listen/notify connections "down to one per program", compared with "one
  connection per topic per program" in the naive version. It issues one
  `LISTEN` per topic however many components subscribe. To add a subscription,
  it interrupts the blocking wait, applies the change, and resumes. It delivers
  to each subscriber with a non-blocking send into a bounded buffer, and "the
  notification is discarded if the channel is full". For an event store this
  is safe, because each subscriber re-reads the event table from its own
  position. A coalescing wake-up signal per subscriber (an `asyncio.Event` or a
  size-1 queue) is enough. Payloads only matter for routing, for example naming
  the category or stream so that the registry wakes only the subscribers
  concerned.
- **Keep the listener out of the pool.** `psycopg_pool` "doesn't actively
  check the state of the connections held in its state". It only runs a
  `reset` callback, if one is configured, when a connection is returned. A
  pooled connection that ran `LISTEN` keeps its registration for as long as
  the server session lives. If it goes back to the pool without
  `UNLISTEN *`, it keeps collecting notifications for whichever borrower gets
  it next. A dedicated connection avoids this. Business queries and catch-up
  reads should stay on the pool.

### Across reconnection

When the session ends, its registrations go with it. The `NOTIFY` docs say
delivery goes to "all the sessions currently listening". Anything committed
while the listener was disconnected is never delivered to the new session.
After a reconnect, the notification stream has a gap that only a table query
can fill.

- **Detecting loss.** psycopg marks an interrupted connection `broken`, which
  also makes it `closed`. `notifies()` re-raises the underlying
  `OperationalError`. A half-open TCP connection (peer gone, no RST) leaves an
  idle listener waiting forever. Defences:
  - Turn on libpq TCP keepalives (`keepalives`, `keepalives_idle`,
    `keepalives_interval`, `keepalives_count`).
  - Set `tcp_user_timeout`, which controls how long "transmitted data may remain
    unacknowledged before a connection is forcibly closed".
  - Run a cheap query periodically between `notifies()` iterations. With psycopg
    3.2.4 or later, notifications that arrive during that query are kept in the
    backlog.
- **Recovery order.** Reconnect with backoff, then switch to autocommit. Issue
  `LISTEN` for every channel in the registry, and check the result with
  `pg_listening_channels()` if needed. Only after those `LISTEN`s have committed,
  wake every subscriber so that it re-queries from its persisted position. Doing
  it the other way round (query, then `LISTEN`) leaves a window in which a commit
  is neither seen by the query nor notified.
- **An accepted alternative is to restart.** The notifier article takes a "let
  it crash" approach: "If the connection becomes irreconcilably unhealthy, stop
  the program, and have it come back to a healthy state by virtue of its normal
  start up." The start-up path then does the `LISTEN`-then-catch-up sequence. It
  still has to be correct, because it runs on every start.

### Connection poolers in transaction mode

- **PgBouncer.** The PgBouncer feature table lists `LISTEN` as "Never" under
  transaction pooling and "Yes" under session pooling. It lists `NOTIFY` as
  "Yes" in both modes. In transaction mode a "server is released back to pool
  after transaction finishes". The registration therefore stays on a server
  session that PgBouncer hands to other clients, not on the listener's client
  connection. Session pooling has its own trap. The default `server_reset_query`
  is `DISCARD ALL`, which PostgreSQL defines to include `UNLISTEN *`, so a
  server connection loses its registrations when the client disconnects.
  `pool_mode` can be overridden per database and per user. A deployment can
  therefore send the listener through a session-mode PgBouncer database entry,
  or straight to PostgreSQL, while everything else uses transaction pooling.
  The notifier article recommends exactly this split.
- **Publishers are unaffected.** `NOTIFY` (or `pg_notify()` in an append
  trigger) runs inside the writer's transaction, so it works through
  transaction pooling.
- **Amazon RDS Proxy.** RDS Proxy does not fail. Instead, "Listening on a
  notification channel" pins the client to one database connection until the
  client disconnects. That is acceptable for one listener per process, but it
  should be counted when sizing the proxy.

### Failover to a standby

- **A standby cannot listen.** Hot-standby sessions get errors for `LISTEN`
  and `NOTIFY` and may only run `UNLISTEN`. This is stricter than ordinary
  read-only transactions. The listener must therefore always connect to the
  primary. With libpq multi-host connection strings, hosts "will be tried in
  order, until one succeeds", and `target_session_attrs=read-write` (or
  `primary`) skips hosts that are in hot standby. `connect_timeout` applies to
  each host separately. psycopg 3 does its own host handling: fixes in 3.1.13,
  3.1.15 and 3.1.17 corrected multiple hosts, `load_balance_hosts`, and hosts
  that resolve to several addresses. 3.2.10 reports every failed attempt in the
  raised error.
- **Notifications do not replicate.** The `async.c` design comment says:
  "Since notifications are not expected to survive database crashes, we can
  simply clean out the pg_notify data at any reboot, and there is no need for
  WAL support or fsync'ing." Without WAL records, nothing reaches a standby.
  Any notification not yet read from the old primary is lost, and the promoted
  server has no registrations for the listener. Sessions that were already on
  the standby "will remain connected while the server changes mode" and can
  write after promotion. In practice, though, the listener's connection was to
  the old primary and breaks, so the listener has to reconnect to the new one.
- **Treat failover as a reconnection.** The same steps apply: reconnect with
  `target_session_attrs=read-write`, re-issue every `LISTEN`, then trigger
  catch-up. One more risk is my inference, not stated by these sources. With
  asynchronous replication, a transaction that committed and notified on the
  old primary may be missing on the new one. A consumer may then have processed
  events that no longer exist, and the catch-up query must cope with positions
  that run ahead of the new primary's data.

### Implications for an event-store library

- One listener per process: autocommit, outside the pool, connected directly or
  through a session-mode pooler, using `target_session_attrs=read-write` with
  TCP keepalives and `tcp_user_timeout`, on psycopg 3.2.10 or later.
- A registry from channel to subscribers. A `notifies(timeout=…)` loop applies
  subscription changes and health checks between iterations.
- Non-blocking, coalescing wake-ups to subscribers. Subscribers always re-read
  the table from their own position and never trust payloads for data.
- On any connection error: back off, reconnect, re-issue `LISTEN` and check it,
  then wake every subscriber for catch-up.
- Keep a low-frequency safety poll even when notifications are healthy. Gaps
  around reconnection and failover, discarded wake-ups and folded duplicates
  all mean notifications must be treated as hints.
