# How can competing consumer processes elect and fail over a single PostgreSQL listening session, for example with advisory locks, without losing or duplicating dispatched work during the handover?

## Question

Several identical consumer processes compete to run one PostgreSQL session that
LISTENs for notifications and passes the resulting work to a pool. How can they
choose that single listener, for example with advisory locks, and hand it over
when it fails, without losing or duplicating any of the work it dispatched?

## Findings

**No scholarly record evaluates PostgreSQL advisory-lock election directly.**
The cited records do not study PostgreSQL itself. The design below combines
three things: well-established results from lock services, leases and stream
processing; the documented semantics of PostgreSQL; and how those results map
onto them. The PostgreSQL behaviour described here comes from the database's
documentation, not from the cited records.

**Electing the listener is the easy part, but a lock alone is not enough.**
Google's Chubby lock service is the standard reference for coarse-grained
leader election. It offers *advisory* locks, which only mean something to
clients that check them. Its main use was letting a group of replicas elect a
primary, as in GFS and Bigtable (Burrows). PostgreSQL's session-level advisory
locks work much the same way. Each candidate calls a non-blocking try-lock on a
fixed key using a dedicated connection. The winner issues LISTEN on that same
connection. The losers retry periodically. The connection must not go through a
transaction-pooling proxy, because both the lock and the LISTEN registration
belong to the backend session.

Chubby's experience shows the gap a lock leaves. A lock holder can fail, pause
or be cut off by a network partition. Once the lock is granted to someone else,
messages the old holder already sent can still arrive and act. Chubby addresses
this in two ways:

- **Lock-delay:** after a holder fails, the lock cannot be re-acquired for a
  bounded period. Burrows calls this imperfect but simple.
- **Sequencers:** each acquisition gets an opaque token containing a lock
  generation number. A holder attaches the token to its requests, and the
  servers it calls reject requests with stale tokens.

The same "zombie writer" problem, and the same fix, appear in MillWheel. Every
writer carries a sequencer token, the storage layer checks the token before
accepting a write, and a new owner invalidates existing tokens before it starts
work (Akidau et al.). Kafka's exactly-once design fences zombie producers with
an epoch that rises with each new producer instance. It also commits consumer
offsets in the same transaction as the outputs (Wang et al.).

**What this means for PostgreSQL advisory locks.** A session-level advisory lock
is not a lease in Gray and Cheriton's sense. A lease is a time-limited grant: if
the holder fails, the server waits for the term to expire before granting a
conflicting right. Shorter terms reduce the wait after a failure but cost more
renewal traffic (Gray and Cheriton). An advisory lock has no term. PostgreSQL
releases it only when the holder unlocks it or when the backend session ends.
This has two consequences:

1. **The database never grants the lock twice**, so split-brain cannot happen
   at the lock itself. Instead, failover is only as fast as the server's
   detection of a dead client. That is governed by TCP keepalive and
   user-timeout settings, not by a lease term.
2. **The old holder can still act after losing the lock.** Once the server has
   ended the old session, the old process may not find out until it next uses
   that connection. Until then it can keep handing already-fetched work to pool
   workers, which commit on *other* connections.

Writes made on the lock-holding connection itself cannot outlive the lock,
because they share its fate. Writes from pool workers are not protected that
way, so they need an explicit fencing token.

**A handover protocol that neither loses nor duplicates work.** These steps
apply the sequencer and epoch pattern to an event table:

1. **Fence first.** After winning the lock, the new listener increments a
   durable epoch, in a committed transaction, before doing anything else. The
   epoch can be a single leader row or a per-subscription column on the
   consumer-position rows. That number is the fencing token, the equivalent of
   Chubby's sequencer, MillWheel's token or Kafka's producer epoch.
2. **Check the token in the same transaction as the work.** Every worker
   transaction does three things in one commit: applies the side effects,
   advances the consumer position, and checks the token. It can either lock the
   epoch row with a shared row lock and compare values, or use a conditional
   update on the position row that matches the token. The new leader's epoch
   increment conflicts with these row locks, so commits are ordered relative to
   the handover:
   - a stale worker that commits before the increment is fully visible to the
     new leader;
   - a stale worker that commits after the increment matches no rows and rolls
     back.

   Either way, no work is applied twice. This is the same idea as Kafka
   committing offsets inside the producing transaction (Wang et al.) and
   MillWheel checking tokens at the storage layer.
3. **Listen before catching up.** PostgreSQL notifications are not durable. A
   notification reaches only sessions that were listening when the notifying
   transaction committed. Anything committed between the old session's death
   and the new LISTEN is therefore never announced. The new leader must:
   - commit its LISTEN;
   - then read the durable consumer positions;
   - then query the event table to catch up from those positions;
   - and only then rely on notifications.

   Treated this way, notifications are only hints that new rows exist. The
   event table and stored positions are the source of truth. This matches the
   log-centric view that consumers restart from a checkpointed position in a
   durable, ordered log (Kleppmann, Beresford and Svingen).
4. **Step down on any doubt.** A listener that sees a connection error, or a
   failed periodic heartbeat query, must stop dispatching at once. Fencing makes
   this a matter of speed rather than correctness: stale commits fail anyway.

**Side effects outside the database cannot be fenced this way.** HTTP calls,
emails and messages to other systems can still be repeated when work is retried
after a handover. The established remedy is at-least-once delivery plus
idempotent receivers. Each message carries a stable identifier, such as the
event ID plus the consumer name, and the receiver durably remembers which
identifiers it has already processed (Helland). Kleppmann and colleagues reach
the same conclusion for log consumers: restarting from a checkpoint can
reprocess events, so processing must be idempotent or deduplicated by event ID.

**The more robust design: a listener that only wakes workers.** A simpler and
sturdier option is to give the elected listener no ownership of work at all. It
only relays "something changed" signals to the pool. Each worker then claims a
stream, partition or batch inside its own processing transaction, for example
with row locks that skip already-locked rows, or with transaction-scoped
advisory locks. It commits the claim together with the position update and the
side effects. Ownership then follows PostgreSQL's transaction atomicity: a
worker whose session dies loses its claim and its uncommitted effects together.

In this design, losing or replacing the listener affects only latency. During
an election gap, workers' fallback polling still finds new rows, so a slow
failover delays delivery instead of losing or duplicating it. The fencing epoch
is then needed only if the listener itself writes on other connections. This
mirrors the per-partition single-consumer model of log-based systems, in which
one consumer processes each partition in order and recovers from its committed
offset (Kleppmann, Beresford and Svingen; Wang et al.).

**Remaining caveats:**

- **Detection time sets the failover delay.** Because advisory locks have no
  term, election speed depends on how quickly the server notices a dead client.
  Standby candidates should therefore keep their own fallback polling running.
- **Idle-session timeouts can kill the leader.** A timeout that ends idle
  sessions will also end a leader that sits idle while listening, so the leader
  should issue periodic heartbeat queries.
- **Primary-database failover resets everything.** Advisory locks and LISTEN
  registrations are not replicated. After a failover every candidate reconnects
  and runs a fresh election. With asynchronous replication the epoch and
  positions can also move backwards, so idempotent handling is still needed.
