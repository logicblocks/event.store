# What reconnect-and-catch-up pattern lets a psycopg 3 listener survive server restarts and managed failovers such as RDS Multi-AZ, Aurora or Cloud SQL HA without missing events, and how quickly do those failovers sever existing listener connections?

## Question

What reconnect-and-catch-up pattern lets a psycopg 3 listener survive server restarts and managed failovers (RDS Multi-AZ, Aurora, Cloud SQL HA) without missing events? And how quickly do those failovers cut existing listener connections?

## Findings

### Reconnecting alone cannot be lossless

A restart or failover loses notifications in ways that no reconnect logic can recover. PostgreSQL ties `LISTEN` registrations to the session: "A session's listen registrations are automatically cleared when the session ends". So a new connection hears nothing until it issues `LISTEN` again. The notification queue itself does not survive a restart. The source comment in `async.c` says: "Since notifications are not expected to survive database crashes, we can simply clean out the pg_notify data at any reboot, and there is no need for WAL support or fsync'ing". `AsyncShmemInit()` deletes the `pg_notify` directory at every start. Because the queue is not WAL-logged, standbys never receive it, and `LISTEN` and `NOTIFY` raise errors on a hot standby.

A failover or restart therefore opens three loss windows:

1. **Undelivered at the crash:** notifications committed but not yet read by the client when the old server dies.
2. **Disconnected period:** everything committed while no session is registered.
3. **Before LISTEN commits:** notifications sent between the new connection opening and its `LISTEN` taking effect.

The Elixir driver Postgrex documents the same limit for its own auto-reconnect: "any notifications that occur during the disconnection period are not queued and cannot be recovered". Its advice is to skip auto-reconnect, restart the listener, and resubscribe in three steps: "first subscribing", "then obtaining the current state of data", "then handling the incoming notifications".

For an event store, this means the append-only log is the source of truth and a notification is only a wake-up hint. Survival is a property of the catch-up read, not of the notification channel.

The managed HA options documented below keep committed data across failover:

- **RDS Multi-AZ DB cluster:** failover "completes when both reader DB instances have applied outstanding transactions from the failed writer".
- **Aurora:** writes are replicated synchronously to six storage nodes.
- **Azure zone-redundant HA:** documented as zero data loss.

A catch-up read against the new writer should therefore find every event committed before the failover.

### The reconnect-and-catch-up loop

The pattern that closes all three windows works in five steps:

1. **Connect to a writer only.** The libpq multi-host syntax plus `target_session_attrs=read-write` (or `primary`) makes libpq try each host in order and reject any server in hot standby. This matters because `LISTEN` fails on a standby, and after an Aurora failover DNS can briefly route to the wrong node. AWS's Aurora PostgreSQL fast-failover guide recommends listing both the cluster endpoint and the reader endpoint and requiring a primary. The libpq equivalent of that JDBC `targetServerType=primary` setting is `target_session_attrs`. Set `connect_timeout` too; it "applies separately to each host name or IP address", so an unreachable old IP cannot stall the loop. Open the connection with `autocommit=True`. psycopg advises autocommit "if you wish to receive or send notifications in a timely manner", and `LISTEN` "takes effect at transaction commit", so in autocommit mode it is active as soon as `execute()` returns.
2. **Issue `LISTEN` before reading anything.** This closes window 3.
3. **Catch up** from the consumer's last processed position (in memory, or a durable checkpoint after a process restart) to the current head. Use the same safe-head rules as the existing polling consumer. Gap and in-flight-transaction handling for sequence-derived positions is a separate concern.
4. **Wait in `notifies(timeout=T)`** (the `timeout` and `stop_after` parameters were added in psycopg 3.2). Each notification triggers another read from the last position; payloads are not trusted as content. When the timeout expires, send a heartbeat query and run a safety poll. That bounds latency even if a notification was lost in a way the loop did not detect.
5. **On any `psycopg.OperationalError`, discard the connection, back off with jitter, and return to step 1.** Since psycopg 3.2.4, a server-initiated disconnect raises the specific server error, such as `AdminShutdown`, "instead of a generic OperationalError". Those classes subclass `OperationalError`, so one handler covers them.

Doing `LISTEN` before the catch-up means any event committed after the catch-up snapshot already has a notification queued for this session, and any event committed before it is in the catch-up read. The overlap can only produce duplicates, never gaps. The consumer must therefore be idempotent by position, skipping anything at or below its last processed position. psycopg's own changelog warns that its buffering can yield duplicates.

The psycopg version matters for exactly this window:

- **Before 3.2.4:** notifications received between `LISTEN` and the start of the `notifies()` generator were lost. That is the catch-up interval, so on older versions only the safety poll catches those events.
- **3.2.4:** fixed this ("Don't lose notifies received whilst the notifies() iterator is not running").
- **3.2.10:** fixed a related memory leak. It also changed behaviour: if a handler is registered with `add_notify_handler()`, notifications are not captured while the generator is not running, and using both mechanisms raises a warning.

So the loop should require psycopg ≥ 3.2.10 and use only `notifies()`.

In synchronous psycopg the listener connection cannot run queries while it sits inside the generator. The catch-up and safety poll should therefore run either between generator exits or on a separate pooled connection. If they use a separate connection, it must also reach the writer. A read against a lagging asynchronous replica, such as an Aurora reader, may not yet see the event a notification announced. This is an inference from the replication model, not a documented warning.

A minimal synchronous shape follows. The host names are placeholders; `consumer.catch_up()` reads from the last processed position on a writer connection.

```python
import random, time
import psycopg

CONNINFO = (
    "host=cluster-writer.example,cluster-reader.example "
    "target_session_attrs=read-write connect_timeout=5 "
    "keepalives=1 keepalives_idle=10 keepalives_interval=5 keepalives_count=3 "
    "tcp_user_timeout=30000"
)

def run(consumer, stop):
    delay = 0.5
    while not stop.is_set():
        try:
            with psycopg.connect(CONNINFO, autocommit=True) as conn:
                conn.execute("LISTEN event_appended")
                consumer.catch_up()
                delay = 0.5
                while not stop.is_set():
                    for _ in conn.notifies(timeout=30.0):
                        consumer.catch_up()
                    conn.execute("SELECT 1")
                    consumer.catch_up()
        except psycopg.OperationalError:
            time.sleep(delay * random.uniform(0.5, 1.5))
            delay = min(delay * 2, 30.0)
```

There is a simpler alternative. Brandur Leach's "notifier" pattern (one listener connection per process) treats an unhealthy listener connection as fatal and lets the process restart; he notes "I've only seen it happen once in a year+ of use". He also recommends waiting for a confirmation that the listener has actually started listening before proceeding. Crashing is acceptable when a supervisor restarts quickly. In-process reconnection costs less when managed failovers recur, for example during maintenance windows.

### How quickly a failover cuts the listener connection

Two different things happen, and they behave very differently for a connection that only waits.

**Orderly termination: immediate.** When the old primary's processes are still running, such as during a reboot, manual failover, maintenance or scaling, PostgreSQL's fast shutdown "sends all existing server processes SIGTERM, which will cause them to abort their current transactions and exit promptly". The listener gets a fatal error on its socket, and psycopg ≥ 3.2.4 raises `AdminShutdown`. The managed services do not document which shutdown mode they use. Cloud SQL does state that "when failover occurs, any existing connections to the primary instance and read replicas are closed". AWS says the failover "changes the DNS record ... As a result, you need to re-establish any existing connections."

**Unclean loss: as slow as the client's TCP settings.** After a host crash, AZ loss or network partition, no FIN or RST ever arrives. AWS lists "Waiting for a query response from a former writer that became unavailable without closing connections" as one of the hazards RDS Proxy removes. A listener that sends nothing notices nothing until TCP gives up:

- **libpq keepalives:** enabled by default (`keepalives=1`), but the system defaults apply unless `keepalives_idle`, `keepalives_interval` and `keepalives_count` are set.
- **Linux keepalive defaults:** probing starts after 7200 s idle, with 9 probes at 75 s intervals. A silent dead peer can go undetected for about 2 h 11 min.
- **Retransmission after a write:** once the client sends something, such as a heartbeat `SELECT 1`, unacknowledged data is retransmitted per `tcp_retries2` (default 15, "approximately between 13 to 30 minutes").
- **`tcp_user_timeout` (milliseconds):** caps that wait, and on Linux it "will override keepalive to determine when to close a connection due to keepalive failure".
- **AWS's recommendation:** for Aurora PostgreSQL fast failover, AWS recommends idle 1 s, interval 1 s and count 5, which "should notify the application within five seconds". It also notes that a lossy network needs a higher count.

Pairing moderate keepalives with `tcp_user_timeout` and a periodic heartbeat query bounds detection to seconds or tens of seconds.

Once the connection is cut, reconnects fail until the new writer accepts connections. The documented windows are:

| Service | Documented outage | How clients reach the new writer |
| --- | --- | --- |
| RDS Multi-AZ DB instance | "typically 60–120 seconds"; large transactions or lengthy recovery can extend it | DNS record changed to the standby |
| RDS Multi-AZ DB cluster | "typically under 35 seconds" | DNS record changed to a reader |
| Aurora PostgreSQL with a replica | "typically restored in less than 60 seconds, and often less than 30 seconds"; with no replica, recreating the primary "typically takes less than 10 minutes" | Cluster endpoint; DNS update "typically takes less than 30 seconds"; reader endpoint TTL 1 s |
| Cloud SQL for PostgreSQL HA | "about sixty seconds"; health heartbeat every second, failover after multiple misses | Shared static IP, no DNS change |
| Cloud SQL planned maintenance | Enterprise edition "less than 30 seconds on average"; Enterprise Plus "typically ... less than 1 second"; connections are dropped | Same IP |
| Azure Database for PostgreSQL, zone-redundant HA | Forced failover "typically completes within 60-120 seconds" | Same server name |

These windows set how the backoff should be tuned:

- **Backoff cap:** keep the retry cap at a few seconds up to about 30 s, so the listener reconnects soon after the window closes.
- **DNS TTL:** AWS's TTL guidance is written for the JVM's DNS cache. psycopg (3.1+) resolves hosts on each async connect attempt, but any OS or sidecar resolver cache must still respect the endpoints' low TTLs.
- **Faster discovery on Aurora:** the AWS Advanced Python Wrapper supports psycopg. It keeps "a cache of the Aurora cluster topology" to bypass DNS delay, refreshing every 2 s by default with a 300 s overall failover timeout. After a `FailoverSuccessError` the application must "reuse and reconfigure the original connection". For a listener, that means issuing `LISTEN` again and catching up.

### Proxies hide the cut but not the lost state

RDS Proxy keeps idle client connections open through a failover: "Only connections that are in the middle of a transaction or SQL statement are canceled". However, "Listening on a notification channel" pins the session to one backend, and that backend's registrations end with the old server. The AWS pages reviewed do not say whether a pinned, listening client is disconnected or silently re-attached.

The defensive inference is that the heartbeat should check session identity as well as liveness. For example, `SELECT pg_backend_pid(), array(SELECT pg_listening_channels())` returns "the set of names of asynchronous notification channels that the current session is listening to". If the channel list comes back empty or the backend PID has changed, the listener should issue `LISTEN` again and catch up. A listener that has silently stopped receiving otherwise looks exactly like a quiet system.

Citus's guidance on Postgres failover makes the same general point: "a PostgreSQL connection is stateful", and all session state disappears on failover. With libpq `target_session_attrs=read-write` and pg_auto_failover, its tests showed reconnection costing "less than 2s of impact".
