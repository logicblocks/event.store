# How do synchronous_commit settings and synchronous standby replication change how long a NOTIFY-issuing commit holds the global notification lock, and so the ceiling on notifying commits per second?

## Question

PostgreSQL serialises NOTIFY-issuing transactions behind one global heavyweight lock. This note asks how `synchronous_commit` and synchronous standby replication change how long each notifying commit holds that lock. Because notifying commits run strictly one after another, that hold time sets the upper limit on notifying commits per second.

## Findings

### Short answer

A notifying transaction takes the global notification lock in `PreCommit_Notify` and holds it through the whole of `RecordTransactionCommit`. The lock is released only after the transaction is marked finished in the process array. `RecordTransactionCommit` is where `synchronous_commit` takes effect: it covers the local WAL flush and, when synchronous standbys are configured, the wait for standby acknowledgement. So a synchronous setting holds the lock for at least one durable WAL flush. Synchronous replication then adds at least one primary-to-standby round trip, plus the standby's write, flush or replay work depending on the mode. Because only one notifying commit can be inside that window at a time, the ceiling is roughly the inverse of the mean hold time. On one published benchmark a commit-time fsync under the lock cut an insert-plus-NOTIFY workload from about 31,000 TPS to about 818 TPS. `synchronous_commit = off` removes both waits from the window. A transaction that writes no WAL before its commit record also escapes both waits, whatever the setting. A pure NOTIFY transaction is such a case.

### Where the lock sits in the commit path

The lock is a heavyweight `AccessExclusiveLock` taken with `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)`. The `async.c` source says why: "Serialize writers by acquiring a special lock that we hold till after commit. This ensures that queue entries appear in commit order, and in particular that there are never uncommitted queue entries ahead of committed ones." It is a heavyweight lock "so that it'll automatically be released after either commit or abort". The lock is tagged with database OID 0, so it is shared across the whole cluster, not per database. The Recall.ai incident log shows this: waiters queued on "AccessExclusiveLock on object 0 of class 1262 of database 0". Before taking the lock, `PreCommit_Notify` forces an XID to be assigned, so every notifying transaction writes a commit record.

`CommitTransaction` in `xact.c` then runs these steps in order:

1. `PreCommit_Notify()` takes the lock and appends entries to the `pg_notify` SLRU queue.
2. `RecordTransactionCommit()` writes the commit record, then either flushes WAL or takes the async path, then waits for synchronous replication.
3. `ProcArrayEndTransaction()` runs.
4. `ResourceOwnerRelease(..., RESOURCE_RELEASE_LOCKS, ...)` releases the lock.
5. `AtCommit_Notify()` signals listeners. This runs after the lock is released.

So the hold window covers the queue append, the commit record insert, any WAL flush, any synchronous-replication wait, the clog update and the process-array update. The source comment above the synchronous-replication wait says so directly: "Note that at this stage we have marked clog, but still show as running in the procarray and continue to hold locks." The official synchronous-replication documentation makes the same general point: "Waiting doesn't utilize system resources, but transaction locks continue to be held until the transfer is confirmed."

This design is unchanged in the `REL_17_STABLE`, `REL_19_STABLE` and `master` branches of the PostgreSQL source. All three take the lock in `PreCommit_Notify` with the "hold till after commit" comment. The notification queue is still a non-WAL-logged SLRU ("there is no need for WAL support or fsync'ing").

### What each setting puts inside the window

`RecordTransactionCommit` flushes WAL synchronously only when `(wrote_xlog && markXidCommitted && synchronous_commit > SYNCHRONOUS_COMMIT_OFF) || forceSyncCommit || nrels > 0`. Otherwise it calls `XLogSetAsyncXactLSN` and does not wait. It then calls `SyncRepWaitForLSN` only `if (wrote_xlog && markXidCommitted)`. That function returns at once unless `SyncRepRequested()` holds, which means `max_wal_senders > 0 && synchronous_commit > SYNCHRONOUS_COMMIT_LOCAL_FLUSH`, and synchronous standby names are defined. For a typical event-append transaction (it wrote WAL and has an XID), the window therefore contains:

| `synchronous_commit` | No synchronous standbys | With synchronous standbys |
|---|---|---|
| `off` | No flush, no replication wait. Only CPU and shared-memory work. | Same; no replication wait. |
| `local` | Local WAL flush (fsync). | Local WAL flush only. |
| `on` (default) | Local WAL flush. | Local flush, then wait until standbys report the commit record flushed to durable storage. |
| `remote_write` | Local WAL flush (same as `on`). | Local flush, then wait until standbys report it written to their file systems. |
| `remote_apply` | Local WAL flush (same as `on`). | Local flush, then wait until standbys have replayed it. The docs warn this "will cause much larger commit delays than previous settings since it waits for WAL replay." |

The documentation says the "minimum wait time is the round-trip time between primary and standby". So with synchronous standbys, each notifying commit holds the lock for at least one fsync plus one network round trip, plus the standby-side work. The setting is decided per transaction ("the behavior for any one transaction is determined by the setting in effect when it commits"). `SET LOCAL synchronous_commit TO OFF` therefore changes only the window of the transaction that sets it.

The `wrote_xlog` test matters a great deal. `wrote_xlog = (XactLastRecEnd != 0)` is evaluated before the commit record is written. The source comment says the flush may be asynchronous "if synchronous_commit=off, or if the current transaction has not performed any WAL-logged operation". A transaction whose only action is NOTIFY gets an XID but has written no WAL (the queue is not WAL-logged). It therefore commits on the asynchronous path and skips the synchronous-replication wait, even with `synchronous_commit = on` and synchronous standbys configured. A transaction that appends events and also calls NOTIFY pays the full flush and replication wait while holding the lock.

### Measured effect on the ceiling

The clearest measurement comes from the pgsql-hackers thread "[PATCH] Write Notifications Through WAL". Arseniy Mukhin ran `pgbench -c 100 -j 10 -T 100` on unpatched master with no listeners and recorded:

- `insert_only` (one-row insert per transaction): about 30,982 TPS.
- `insert_with_notify` (the same insert plus `NOTIFY`): about 818 TPS.
- `notify_only` (just `NOTIFY`): about 87,751 TPS.

The roughly 38-fold drop from adding NOTIFY to a WAL-writing transaction matches the code path above. The thread's own diagnosis, from Rishu Bagga: "The global lock is not released until after the call to RecordTransactionCommit and the reset [sic] of CommitTransaction. So if there are multiple transactions sending notifications, each must become durable before the next can proceed." The run's `synchronous_commit` and fsync settings were not reported; the default is `on`.

The following is inferred, not measured. Group commit normally lets many concurrent commits share one WAL flush, which is how `insert_only` reaches about 31k TPS. The notification lock lets only one notifying transaction into its flush at a time, so notifying commits cannot share flushes with each other. 818 TPS is about 1.2 ms per notifying commit, which is consistent with one serial fsync per commit. The `notify_only` figure, which involves no flush, shows how high the ceiling goes when the window holds only CPU work. Rishu Bagga's separate notify-only benchmark on an Apple M2 laptop reached about 186,000 TPS with the lock.

The ceiling model that follows (an inference) is: maximum notifying commits per second ≈ 1 / mean lock hold time, summed across every notifier in the cluster. Under load, queueing adds per-commit latency on top of that: with N concurrent notifiers, each waits roughly N × hold time. For example, adding 1 ms of synchronous-replication round trip and standby flush to a 1.2 ms local flush would cut the ceiling from about 800 to about 450 commits per second. `remote_apply` would cut it further. These are illustrative calculations, not measurements. No source found here benchmarked insert-plus-NOTIFY under synchronous replication or with `synchronous_commit = off`.

Practitioner reports agree on the direction. Rishu Bagga says the serial durability wait "becomes especially expensive in environments where compute and storage are separated, such as certain cloud-based variants of Postgres." Recall.ai saw lock waits above one second on the global lock, with "hundreds" of blocked processes, while CPU, disk I/O and network traffic fell. That is the signature of a serial convoy. They removed LISTEN/NOTIFY from their write path. Joel Jacobson also found that the lock alone, with no durability wait, can dominate at high concurrency: 7,679 TPS with the lock against 95,430 TPS without it, for 1,000 concurrent senders and one listener.

### Failure amplification under synchronous replication

The documentation warns that with synchronous standbys, "transaction commits may never be completed if any one of the synchronous standbys should crash." A notifying commit stuck in that wait keeps the cluster-wide notification lock. So every other NOTIFY-issuing transaction in any database on the cluster queues behind it in `PreCommit_Notify` (wait event type `Lock`, event `object`). This includes transactions that set `synchronous_commit` to `local` or `off`, because they are waiting to acquire the lock, not to commit. Transactions that do not notify are unaffected by the lock itself. Cancelling the stuck backend makes it give up the wait with the warning "The transaction has already committed locally, but might not have been replicated to the standby", and its locks are then released.

For diagnosis, the backend holding the lock shows `IO` / `WalSync` or `WalWrite` when it is flush-bound, or `IPC` / `SyncRep` when it is replication-bound. The waiters show `Lock` / `object`, and `log_lock_waits` reports them as "object 0 of class 1262 of database 0".

### Options for an event store

These follow from the code and documentation above. The trade-offs are inferences unless a source is named.

- **Per-transaction `SET LOCAL synchronous_commit TO OFF` on append transactions.** This removes both the flush and the replication wait from the window, so the ceiling approaches the CPU-bound figures. The cost is durability: "the most recent transactions may be lost if the database should crash", for up to three times `wal_writer_delay`. Readers and listeners see the commit before it is durable, so a consumer could act on events that later disappear in a crash. That is a serious risk for an event store. `local` keeps the local flush but drops the replication wait, which brings a similar risk across a failover.
- **Issue NOTIFY in a separate WAL-free transaction after the append commits.** The code says such a transaction takes the asynchronous path whatever `synchronous_commit` is, so its lock window contains no fsync and no replication wait. The append keeps full durability. The cost is that the wake-up is no longer atomic with the append: a crash between the two commits loses the wake-up, so safety-net polling must cover it. No published benchmark of exactly this pattern was found; `notify_only` is the closest evidence.
- **Fewer notifying commits.** Coalescing or debouncing on the sender side divides the serial cost across many appends.
- **`commit_delay` is unlikely to help.** This is an inference. The delay targets group commit, but notifiers cannot share a flush while serialised, so a notifying flush leader that waits `commit_delay` would mostly lengthen its own hold time.
- **Future change.** The "Write Notifications Through WAL" patch, following a design sketched by Tom Lane, writes notification data to WAL before commit. Per the thread, versions 7 to 9 take the queue lock only around writing the commit record, which shrinks the window. The `insert_with_notify` result rose from about 818 to about 33,870 TPS. The patch was at version 9 in November 2025 and is not in `REL_19_STABLE` or `master`. Every released version up to and including 19 behaves as described above.
