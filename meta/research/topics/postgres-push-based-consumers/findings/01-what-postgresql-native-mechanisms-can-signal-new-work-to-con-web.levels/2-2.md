# What reconnect and catch-up sequence lets a psycopg 3 consumer combine LISTEN with a fallback poll so that notifications lost to disconnects, server restarts or listener lag never cause missed events?

## Question

What order of connect, `LISTEN`, catch-up read, wait, liveness check and reconnect lets a psycopg 3 consumer use PostgreSQL notifications for low latency while a fallback poll makes sure no event is missed, even when notifications are lost to dropped connections, server restarts or a slow listener?

## Findings

### The governing principle: notifications are hints, the stored position is the truth

PostgreSQL's notification semantics make one design rule unavoidable. A notification can only wake a consumer up. It can never be the record of what the consumer still has to process. That record has to be a durable checkpoint, the last position the consumer processed, and every wake-up has to lead to a re-read of the log from that checkpoint. The primary sources show why notifications cannot carry correctness:

- **Only current listeners get a notification.** `NOTIFY` delivers to sessions that "previously executed `LISTEN`", and a session gets "all events committed after an instant during the transaction's commit step" of its own `LISTEN`. Anything committed while a consumer is disconnected never reaches it. Registrations are "automatically cleared when the session ends", so every new connection has to `LISTEN` again.
- **Notifications do not survive a restart.** The source of PostgreSQL's `async.c` says: "Since notifications are not expected to survive database crashes, we can simply clean out the pg_notify data at any reboot, and there is no need for WAL support or fsync'ing." After a crash or restart, any queued notification that had not been delivered is gone.
- **Standbys do not support it.** `LISTEN` and `NOTIFY` raise errors on a hot standby. After a failover, the listener must reconnect to the new primary, not to a replica.
- **A lagging or idle-in-transaction listener causes trouble on both sides.** A listening session that is inside a transaction does not get notifications delivered "until just after the transaction is completed". If it stays in a transaction for a long time, "no cleanup can take place" in the queue. The queue is capped by `max_notify_queue_pages` (default 1048576 pages, about 8 GB, settable only at server start). When the queue fills, "transactions calling `NOTIFY` will fail at commit". So a stuck listener can break the writers' append path, not just delay the consumer.
- **Duplicates collapse, and order follows commit order.** Identical channel and payload pairs within one transaction collapse to a single notification. Notifications from different transactions arrive "in the order in which the transactions committed".

Every established PostgreSQL-backed queue examined treats LISTEN as an accelerator on top of a poll, never as a replacement for it:

- **Procrastinate (built on psycopg 3):** its worker "polls the database regardless" of `listen_notify`. With notifications enabled, `fetch_job_polling_interval` (default 5 s) "acts as a fallback mechanism".
- **River:** `FetchPollInterval` exists because "this provides a fallback". Its poll loop is "meant as a back up in case something with listen/notify didn't work".
- **Oban:** its stager switches from notifier-driven ("global") mode to local polling (1 s default) whenever the notifier reports itself `:isolated`.
- **Graphile Worker:** it polls (2 s default), and it deliberately drops a notification when no worker is idle, "knowing that when one of the workers finishes they'll ask for the next job anyway".

### The sequence

The sequence below combines PostgreSQL's documented `LISTEN` rule with the patterns these libraries use. Each step names its source; the parts marked as inference are this note's own reasoning.

1. **Open a dedicated, non-pooled listener connection in autocommit mode.**
   - psycopg says to keep the connection in `autocommit` "if you wish to receive or send notifications in a timely manner". Procrastinate uses a standalone connection for listening and its pool for everything else. River and Graphile Worker also keep a single long-lived listener client.
   - Set libpq's TCP liveness parameters on this connection: `keepalives_idle`, `keepalives_interval`, `keepalives_count`, and `tcp_user_timeout` (where the OS supports it). Without them, a half-open TCP connection can leave a blocking wait hanging forever.
   - Set `target_session_attrs=read-write` (or `primary`) with a multi-host connection string. libpq then tries hosts in order and accepts only a server that is "not in hot standby mode", which keeps the listener off standbys where `LISTEN` fails. `connect_timeout` applies to each host separately.

2. **Issue `LISTEN` for every channel before reading anything.** The PostgreSQL manual gives the rule: "first execute (and commit!) that command, then in a new transaction inspect the database state ... then rely on notifications to find out about subsequent changes". In autocommit mode the `LISTEN` commits immediately.
   - Doing it the other way round (read first, then `LISTEN`) leaves a window. Events committed between the read and the `LISTEN` produce no notification for this session and wait for the next poll.
   - On reconnect, re-`LISTEN` on every channel. Oban: "Every connection, including a reconnect after a crash, listens on all channels that have registered listeners". River's `listenAndWait` re-issues `LISTEN` for every subscribed topic.

3. **Catch up from the durable checkpoint, then start waiting.** Read events after the stored checkpoint in batches until a batch comes back short or empty, advancing the checkpoint as you go. Use a pooled connection for this, configured with `check=ConnectionPool.check_connection`, because the pool "doesn't actively check the state of the connections held in its state". The catch-up after reconnect is what recovers everything lost during an outage, restart or failover.
   - Notifications that arrive during catch-up may refer to events already read. The manual calls this "usually harmless", and it is harmless when every wake-up just re-reads from the checkpoint.
   - **psycopg version behaviour.** Whether notifications that arrive before the generator is running are kept depends on the psycopg version:
     - Before 3.2.4, notifications "received between calling `LISTEN` and starting the generator were lost".
     - From 3.2.4 they are captured and yielded once the generator starts, but this introduced a memory leak (#1091) if the generator is not used regularly.
     - From 3.2.10 the leak is fixed, but "if a handler is registered then notifications are not captured when the generator is not running".
   - **What to do about it.** Use either the `notifies()` generator or `add_notify_handler`, never both; since 3.2.10 mixing them triggers a runtime warning. Either way, rely on the fallback poll, not on buffering, to cover the gap between the last catch-up read and the start of the wait.

4. **Wait for a notification or for the poll interval, whichever comes first, then repeat the catch-up.**
   - psycopg 3.2 added `notifies(timeout=..., stop_after=...)`, so one call gives "wake on notification, else poll after N seconds". Procrastinate's worker does the same with `wait_any(new_job_event.wait(), sleep(fetch_job_polling_interval), stop_event.wait())` and then fetches.
   - Coalesce: one catch-up pass covers any number of pending notifications. A burst of N notifications should cause one read, not N. `stop_after` may return more than requested if they "arrive in the same packet".
   - If receiving and processing run in separate tasks with a flag or event between them, clear the flag *before* the read, not after. Procrastinate clears it in a `finally` after fetching. A notification that arrives during a long read is then still noticed, and the poll interval is not the only thing catching it. (This is an inference from the race, not a documented requirement.)

5. **Probe liveness whenever the wait times out.**
   - Procrastinate's `_loop_notify` runs `connection.execute("SELECT 1")` each time its notify wait times out and treats `psycopg.OperationalError` as a dead connection.
   - psycopg's documentation suggests the same `SELECT 1` probe for detecting disconnection. River pings its listener every 5 seconds.
   - Since 3.2.4, psycopg raises the specific server error (for example `AdminShutdown` when the server shuts down) instead of a generic `OperationalError`. The reconnect handler must catch the parent class that covers these.
   - The probe catches clean closes and server-initiated terminations. A half-open connection may make the probe itself hang, and only the TCP-level timeouts from step 1 bound that.

6. **On failure, back off, keep polling, then go back to step 1.**
   - Close the broken connection and reconnect with exponential backoff and jitter. Graphile Worker computes `jitter * min(MAX_DELAY, 50 * e^attempts)` (about 136 ms, 370 ms, 1 s, 2.7 s, …) and resets the counter once `LISTEN` succeeds. River also uses exponential backoff.
   - While the listener is down, keep catching up at the poll interval over the pool, as Oban's stager does in local mode and River does in poll-only mode. Consumers then still make progress, only with higher latency.
   - Never go back to waiting without first redoing steps 2 and 3. Re-`LISTEN` must come before the catch-up.

### Handling listener lag specifically

Keep receiving notifications and processing events separate. The listener connection should do nothing but wait and probe, and it must never open a transaction, or it delays its own deliveries and blocks queue cleanup for every writer. Watch `pg_notification_queue_usage()` on the server. PostgreSQL logs warnings that name the blocking session once the queue is half full. On the client, a consumer that falls behind loses nothing, because it re-reads from its checkpoint: a backlog of notifications collapses into one catch-up pass. Graphile Worker relies on exactly this when it drops notifications while all workers are busy.

### Illustrative synthesis (async psycopg 3)

```python
async def consume(conninfo, channel, pool, checkpoint, poll_interval=5.0):
    attempt = 0
    while True:
        try:
            async with await psycopg.AsyncConnection.connect(
                conninfo, autocommit=True, target_session_attrs="read-write",
                keepalives_idle=10, keepalives_interval=5, keepalives_count=3,
                tcp_user_timeout=30_000,
            ) as listener:
                await listener.execute(sql.SQL("LISTEN {}").format(sql.Identifier(channel)))
                attempt = 0
                await catch_up(pool, checkpoint)            # only after LISTEN committed
                while True:
                    async for _ in listener.notifies(timeout=poll_interval, stop_after=1):
                        pass                                # wake-up hint only
                    await catch_up(pool, checkpoint)        # on notify or timeout
                    await listener.execute("SELECT 1")      # liveness probe
        except psycopg.OperationalError:
            attempt += 1
            with contextlib.suppress(psycopg.Error):
                await catch_up(pool, checkpoint)            # keep polling while down
            await asyncio.sleep(backoff_with_jitter(attempt))
```

This sketch assumes psycopg 3.2.10 or later with no notify handler registered, so notifications that arrive between generator runs are captured. It also assumes `catch_up` reads strictly from the durable checkpoint.

### Residual gap this sequence does not close

This sequence makes sure a consumer always re-reads after any possible loss. Whether that re-read sees every event depends on the catch-up query itself. Notifications arrive in commit order, but log positions are assigned at insert time, so a plain "position greater than checkpoint" read can skip a lower position whose transaction commits later. That gap-safety problem is separate, and the read in steps 3 and 4 must use whatever gap-safe rule the event store adopts for it.
