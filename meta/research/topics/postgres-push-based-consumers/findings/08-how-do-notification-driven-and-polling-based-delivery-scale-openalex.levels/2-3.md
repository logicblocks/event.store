# What adaptive polling policies, such as empty-poll backoff with jitter or notification-triggered draining with a long fallback interval, minimise event delivery latency for a fixed database query budget, and how have they been evaluated?

## Question

Which adaptive polling policies give the lowest event delivery latency for a fixed budget of database queries? Candidates include backing off after empty polls (with or without random jitter) and draining on notification with a long fallback poll. How has the research literature evaluated these policies?

## Findings

None of the scholarly records evaluates these policies against a PostgreSQL event table specifically. Three older bodies of research do study the same latency-versus-query-cost trade-off, and their models carry over closely:

- scheduling polls of web pages and feeds under a fixed polling budget
- adaptive push-pull dissemination of changing web data
- hybrid interrupt-and-polling designs in operating-system network and storage stacks

Together they support three conclusions:

- Under a fixed budget, adaptive polling only beats fixed-interval polling when event arrival rates vary over time.
- Notification-triggered draining is a well-evaluated pattern for getting low latency at low load and bounded cost at high load.
- A fallback poll alongside push is justified mainly by resilience to lost notifications, not by latency.

Randomised jitter is not evaluated in any record found.

### Polling under a fixed budget: the delay models

Cho and García-Molina (ACM TODS) state the general problem: local copies of sources that change independently must be kept fresh, the sources "do not notify the copies … of new changes", and every poll costs time and resources.

- **Model.** They define two metrics, freshness and age, and model source changes as a Poisson process.
- **Evaluation.** Refresh policies are assessed both analytically and experimentally against real web change data.
- **Results.** They report large freshness gains over existing policies, by orders of magnitude in some cases. The counter-intuitive result: for a fixed total number of polls, polling each source in proportion to its change rate does worse on freshness than polling all sources uniformly. Polls spent on fast-changing sources buy little.

Sia, Cho and Cho (IEEE TKDE) is the closest analogue to an event consumer.

- **Problem.** An RSS aggregator must monitor many sources so it retrieves new postings quickly while using as few resources as possible. The metric is *delay*, the time from posting to retrieval, rather than staleness. The authors argue this makes the problem different from search-engine index refresh.
- **Policy.** It is built on the posting patterns of sources, whose rates vary over time.
- **Evaluation.** It was evaluated on a collection of real RSS feeds and delivered alerts faster than the best prior approach for the same retrieval resources.

A short derivation from this delay model (my own reasoning, not a quoted result) clarifies when adaptive polling helps:

- **One stream.** Each event that arrives during a polling interval of length T waits T/2 on average. With a fixed number of polls and a constant arrival rate, total delay is minimised by equal intervals, because delay is convex in interval length. **For a steady event stream, a fixed-interval poller is already optimal for its budget.** Adaptive policies can only win by moving queries from quiet periods to busy ones.
- **Time-varying rate.** Minimising expected delay ∫ λ(t) / (2 r(t)) dt, subject to a fixed total number of polls ∫ r(t) dt = N, gives r(t) ∝ √λ(t). The polling rate should follow the *square root* of the event rate, not the rate itself. This matches Cho and García-Molina's finding that proportional allocation over-spends on busy sources.
- **Many streams.** The same rule applies when many streams or subscriptions share one budget.

Seen this way, exponential backoff on empty polls is a crude, reactive estimator of the arrival rate. It has a built-in cost. The first event after a quiet spell waits up to the backoff cap, so **the cap is the worst-case delay** and should be set from the latency requirement, not from cost alone. The interval should also drop back to its minimum as soon as a poll returns rows. Sia et al.'s approach of scheduling from learned posting patterns is the principled alternative to purely reactive backoff.

Cho and García-Molina's companion paper (ACM TOIT) builds estimators for change frequency from poll histories. A web poll only shows *whether* a page changed since the last visit, so naive estimators are biased. Their estimators are much more accurate, analytically and experimentally. An event-table poll is easier to learn from: it returns the new rows themselves, so a consumer sees exact counts and commit times and can estimate its arrival rate directly (my inference).

### Adaptive time-to-refresh and push-pull hybrids

Srinivasan, Liang and Ramamritham (IEEE RTSS) present adaptive approaches for keeping data gathered from web sources temporally coherent. Sources must be queried continually, but contact with servers must be kept to a minimum. Their method chooses when to poll next from the observed dynamics of the data and the user's tolerance for staleness. It is the scholarly ancestor of empty-poll backoff: lengthen the interval while nothing changes, shorten it when changes appear, and keep it within bounds.

Bhide, Deolasee, Katkar, Panchbudhe, Ramamritham and Shenoy (IEEE Transactions on Computers; earlier version by Deolasee et al. at WWW) compare the two canonical approaches:

- **Pull.** Clients poll according to how fast the data changes and how fresh they need it.
- **Push.** Servers keep per-client state and push only the changes each client cares about.

The two have complementary properties in four respects:

- how fresh the data stays (temporal coherency)
- communication overhead
- server-side state
- loss of freshness when a server fails

The paper combines them into two schemes:

- **Push-and-Pull (PaP).** The client pulls on an adaptive schedule and the server pushes the changes the client would otherwise miss.
- **Push-or-Pull (PoP).** The server chooses push or pull per client according to its load and the client's requirements.

The evaluation shows adaptive dissemination is needed to meet varied freshness requirements, stay resilient to failures, and use server and network resources efficiently.

Mapped onto PostgreSQL, notification-triggered draining with a long fallback poll is a Push-and-Pull hybrid:

- **NOTIFY is the push.** It gives low latency, but notifications are lost when the listening session disconnects, which is the failure case Bhide et al. single out.
- **The fallback poll is the pull.** It bounds how stale a consumer can get.

The fallback interval sets two numbers at once: the idle query floor (one query per consumer per interval) and the worst-case delay for an event whose notification was lost.

### Notification as a doorbell: interrupt-triggered polling

Mogul and Ramakrishnan (ACM TOCS) is the canonical evaluation of the drain pattern.

- **Problem.** Interrupt-driven systems "provide low overhead and good latency at low offered load, but degrade significantly at higher arrival rates" into receive livelock, where the system does nothing but handle interrupts.
- **Fix.** Use interrupts under light load and polling under heavy load. An interrupt acts only as a wake-up. The handler then turns off further interrupts, polls the queue in bounded quotas until it is empty, and turns interrupts back on.
- **Evaluation.** Kernel measurements showed this removes livelock without degrading other aspects of performance.

The direct translation for a database consumer:

1. Treat a NOTIFY as a doorbell, not as data.
2. On wake, query in bounded batches until the queue is drained, ignoring further notifications in the meantime; they coalesce.
3. Then go back to waiting.

Query count then grows with the number of batches rather than the number of events. At low load each event costs about one wake-up and one query. A batch shorter than the batch limit already shows the queue is drained, so no confirming empty query is needed (my inference). The bounded batch quota is the counterpart of Mogul and Ramakrishnan's polling quota: it stops a busy stream from starving other work.

The networking work that followed refines when to switch between interrupts and polling:

- **Dovrolis, Thayer and Ramanathan (ACM SIGOPS OSR).** Interrupts beat polling on per-packet latency but carry high overhead on modern processors. They reduce that overhead with a hybrid interrupt-polling scheme.
- **Chang, Muppala, Zou and Li (IEEE LCN).** Hybrid interrupt-polling and interrupt coalescing are the two common defences against livelock. The adaptive schemes proposed so far rely on local knowledge, are all heuristic, and had not been systematically compared, so the authors analyse their capabilities.
- **AlQahtani (ISCIT).** Proposes a hybrid that switches between enabling and disabling interrupts and polling.
- **Salah, Elbadawi and Haidari, and Salah and Qahtan (both Computer Communications).** The first compares interrupt-handling schemes in gigabit networks; the second implements and experimentally evaluates a hybrid scheme. Their records carry no abstracts, so their results are not reported here.

The typical evaluation in this line of work combines analytical or queueing models with measurements of throughput, latency and remaining CPU capacity as offered load rises. That method transfers directly to measuring consumer latency and database load as event rate rises.

Storage stacks give a weaker but related parallel at microsecond scale. For ultra-low-latency SSDs, the trade-off between classic polling, hybrid polling and interrupts is studied by:

- Koh et al. (IEEE IISWC)
- Lee, Shin and Jeong (Journal of Systems Architecture)
- Harris and Altiparmak (HotStorage)

Hybrid polling, as generally understood, sleeps for part of the expected wait before polling. Harris and Altiparmak measured interrupt, classic polling and hybrid polling with a power meter on a real device under several workloads. Contrary to common belief, they found polling can be *more* energy-efficient than interrupts. The general point: whether waking on a signal or busy polling is cheaper depends on the workload and must be measured, not assumed.

### What remains unevaluated: jitter

None of the records evaluates random jitter on poll timing or measures what happens when many pollers share a database in lock-step. Under the delay model above, a random poll phase does not change one consumer's expected delay or query count. Jitter's value is therefore on the server side: it spreads queries from many identical consumers so they do not arrive in bursts. That effect is not measured here. The only scholarly basis found for backoff is the bounded, data-driven adaptive time-to-refresh approach.

### Implications for a psycopg 3 consumer

These points follow from the evidence above:

- **Default policy.** Wait for a notification with a timeout equal to the fallback interval. On any wake-up, from either a notification or the timeout, drain in bounded batches until a batch comes back short, then wait again. This is the interrupt-then-poll pattern combined with Push-and-Pull's pull safety net.
- **Sizing the fallback interval.** Set it from the tolerable worst-case delay for a lost notification and the acceptable idle-query cost per consumer, not from typical latency, which the notification path handles.
- **Without notifications** (for example, behind a transaction-pooling proxy):
  - Use bounded backoff on empty polls, dropping back to the minimum interval on any non-empty poll.
  - Set the cap to the acceptable worst-case delay.
  - For many subscriptions sharing a budget, allocate polls in proportion to the square root of each one's observed event rate.
  - For a steady stream, a fixed interval is already optimal.
- **Evaluating a policy.** Follow the published designs and measure two things on traces of real, bursty event arrivals: delivery delay (from commit to consumer read) and queries per unit time.
