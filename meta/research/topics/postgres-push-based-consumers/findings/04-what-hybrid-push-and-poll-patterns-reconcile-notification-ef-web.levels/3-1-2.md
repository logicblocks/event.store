# How can an event store prove a high-water-mark gap is dead from pg_stat_activity, pg_locks and pg_current_snapshot evidence without stalling on unrelated long-running transactions elsewhere in the cluster?

## Question

An event store that assigns global positions from a PostgreSQL sequence before
commit will see holes below its highest committed position. Some holes are
transient: an appender has drawn a number and has not committed yet. Others are
permanent: the appender rolled back. How can a consumer use live server evidence
from `pg_stat_activity`, `pg_locks` and `pg_current_snapshot()` to prove that a
hole is permanent and move past it, while scoping that evidence so that
unrelated long-running transactions, especially in other databases on the same
cluster, do not hold the high-water mark back?

## Findings

### Short answer

You cannot tell a dead gap from a live one by looking at the hole. You can only
ask whether any transaction that could have reserved the missing numbers is
still running. Once no candidate reserver is alive, a fresh read decides it: a
row that is still missing is permanently dead. Marten's async daemon is a
production implementation of this rule. Its docs say: "is any transaction still
running that could have reserved it? While the answer is yes, the mark holds.
Once no such transaction remains, the gap is proven dead and the daemon skips
the entire dead span in one step" ([Marten docs](https://martendb.io/events/projections/async-daemon.html)).

Whether the proof stalls on unrelated work depends on how narrowly the evidence
defines a "candidate reserver". The cluster-wide snapshot `xmin` is the widest
definition and stalls on everything. The narrowest is a relation lock in
`pg_locks` that only appenders take.

### Why a reserver must exist and be findable

- **Numbers burn outside transactions.** `nextval` values are "not reclaimed for
  re-use if the calling transaction later aborts". A gap can also appear
  without an abort: `INSERT ... ON CONFLICT` calls `nextval` before it detects
  the conflict. PostgreSQL sequences therefore "cannot be used to obtain
  'gapless' sequences" ([PostgreSQL sequence functions](https://www.postgresql.org/docs/current/functions-sequence.html)).
  The burned number's transaction may still commit; it just commits without the
  row. A gap is therefore not dead until its reserver has *ended*. That
  reserver's commit or abort status alone does not settle it.
- **Allocation order is only safe with `CACHE 1`.** With `CACHE 1`, which is the
  default, "it is safe to assume that `nextval` values are generated
  sequentially". With a larger cache, sessions pre-reserve blocks and values
  "might be generated out of sequence" ([CREATE SEQUENCE](https://www.postgresql.org/docs/current/sql-createsequence.html)).
  The proof depends on this. With `CACHE 1`, any missing position below a
  position the reader has seen committed was allocated *before* the reader's
  snapshot. Its reserver had already started by then, and at the moment of the
  read it was either finished or still running. Transactions that start later
  cannot fill the hole. With a cache larger than one, a session can hand out a
  pre-reserved low number in a *later* transaction, and no evidence taken at
  observation time can rule that out.

### Why the obvious snapshot signal stalls cluster-wide

`pg_current_snapshot()`'s `xmin` is the "lowest transaction ID that was still
active" ([PostgreSQL info functions](https://www.postgresql.org/docs/current/functions-info.html)).
In normal (non-recovery) operation, `GetSnapshotData` builds the snapshot's
in-progress (`xip`) list by looping over every backend in the proc array, with
no database filter. It skips only backends doing lazy vacuum or logical
decoding ([procarray.c](https://raw.githubusercontent.com/postgres/postgres/master/src/backend/storage/ipc/procarray.c)).
By contrast, the *vacuum* horizon in `ComputeXidHorizons` does ignore sessions
in other databases for non-shared data. So snapshot `xmin` and `xip` are
cluster-wide, and a long transaction in any database on the server appears in
them.

Both practitioner write-ups of the `xid8` watermark approach hit this. One
stores `pg_current_xact_id()` per row and reads only rows below
`pg_snapshot_xmin(pg_current_snapshot())`. Oskar Dudycz acknowledges that
long-running transactions delay processing
([event-driven.io](https://event-driven.io/en/ordering_in_postgres_outbox/)).
Sequin rejected the approach because "_any_ long-running transaction in your
system will set a ceiling … if you have a transaction running against another
table for two minutes, your cursor/query will be unable to read the last two
minutes" ([Sequin](https://blog.sequinstream.com/postgres-sequences-can-commit-out-of-order/)).
Gating gaps on snapshot `xmin` therefore cannot avoid the stall the question
describes.

### The evidence ladder: from cluster-wide to relation-scoped

Each signal trades scope against blind spots:

| Signal | Scope | Catches | Blind spots |
|---|---|---|---|
| `pg_snapshot_xip(pg_current_snapshot())` limited to xids below the `xmax` recorded when the gap was first seen | Whole cluster | Any reserver that already had an xid, including prepared transactions and sessions hidden by role redaction | Reservers without an xid yet; stalls on unrelated *writers* in other databases |
| `pg_stat_activity` with `datname = current_database()` and `xact_start <=` first sighting | One database | Any older transaction in the event store's database, including reservers that have called `nextval` but not yet inserted | Every unrelated old transaction in the same database stalls it; other roles' rows are redacted without `pg_read_all_stats`; prepared transactions are not sessions |
| `pg_locks` `RowExclusiveLock` on the events table, joined to `pg_stat_activity` | One relation | Appenders that have already inserted | Reservers that have called `nextval` but not yet inserted; the join on `pid` drops prepared transactions, whose `pid` is null |
| `pg_locks` `RowExclusiveLock` on the global-position *sequence* | One relation | Every transaction that has called `nextval` on it | `CACHE` above 1; inference, not documented practice (see below) |
| Writer-registered advisory locks (Sequin) | Defined by the application | Appenders that registered | Race between reading `last_value` and calling `nextval`; 32-bit `objid` |

Supporting facts from primary sources:

- Every transaction holds an exclusive lock on its virtual transaction ID for its
  whole life. Once it has an xid, it also holds one on that xid "until it
  ends". `pg_locks.pid` is "null if the lock is held by a prepared transaction".
  `pg_locks` reads fast-path locks backend by backend "without freezing the
  state of the entire lock manager"
  ([pg_locks](https://www.postgresql.org/docs/current/view-pg-locks.html)).
- `INSERT` takes `ROW EXCLUSIVE` on its target table, and "once acquired, a lock
  is normally held until the end of the transaction"
  ([explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html)).
- In `pg_stat_activity`, "ordinary users can only see all the information about
  their own sessions … In rows about other sessions, many columns will be null",
  unless the reader is a superuser or has `pg_read_all_stats`. Activity data
  "is collected when any such information is first requested within a
  transaction, and the same information will be displayed throughout the
  transaction". A polling probe must therefore run each check in a fresh
  transaction or call `pg_stat_clear_snapshot()`
  ([monitoring stats](https://www.postgresql.org/docs/current/monitoring-stats.html)).
- A prepared transaction "is no longer associated with the current session" but
  "continues to hold whatever locks it held". Prepared transactions are listed,
  with their `database`, in `pg_prepared_xacts`
  ([PREPARE TRANSACTION](https://www.postgresql.org/docs/current/sql-prepare-transaction.html),
  [pg_prepared_xacts](https://www.postgresql.org/docs/current/view-pg-prepared-xacts.html)).

### A worked implementation: Marten's gap-liveness probe

Marten (JasperFx) splits the work between an observation step and a liveness
probe.

**Observation.** When the mark gets stuck, the detector records three values
([HighWaterDetector.cs](https://raw.githubusercontent.com/JasperFx/marten/master/src/Marten/Events/Daemon/HighWater/HighWaterDetector.cs)):

- `Since`: the first-sighting time, taken from server `transaction_timestamp()`.
  The detector deliberately avoids event timestamps, which the client writes.
- `Xmax`: `pg_snapshot_xmax(pg_current_snapshot())` at that moment.
- An *allocation fence*: "the latest server time at which the highest ALLOCATED
  sequence number was still at or below the stuck mark", built by sampling the
  sequence's `last_value`. Every number inside the gap was therefore allocated
  after the fence.

**Grace period.** Nothing is probed until the gap is older than
`StaleSequenceThreshold`. That defaults to 3 s, against high-water polling every
250 ms under load and every 1 s when quiet
([JasperFx DaemonSettings](https://raw.githubusercontent.com/JasperFx/jasperfx/main/src/JasperFx.Events/Daemon/DaemonSettings.cs)).

**Probe.** One SQL statement computes three "live reserver" counts
([GapLivenessProbe.cs](https://raw.githubusercontent.com/JasperFx/marten/master/src/Marten/Events/Daemon/HighWater/GapLivenessProbe.cs)):

1. `old_lock_holders`: granted `RowExclusiveLock`s on `mt_events*` tables in
   the current database, held by sessions with `xact_start <= first_observed`.
2. `older_transactions`: any `client backend` in the current database whose
   transaction started at or before the first sighting.
3. `older_write_xids`: xids in `pg_snapshot_xip(pg_current_snapshot())` below
   the recorded `xmax`. These are mapped to 32-bit `backend_xid` with
   `mod(xid, 4294967296)` so excluded sessions can be removed.

**Exclusions.** Two kinds of session are removed from all three counts:

- *Quiescent* sessions: idle in transaction with `state_change` before the
  allocation fence. Such a session "has executed no statement since — it cannot
  have called nextval for any gap sequence".
- The daemon's own leadership advisory-lock connections, which never write
  (`backend_xid is null`).

The code comments explain how this fails safe. Without `pg_read_all_stats`,
`state` and `state_change` are redacted, and "a redacted NULL never matches,
degrading to 'not excluded', which errs toward holding". The class doc gives
the reason for three signals: a reserver "which called nextval but has not yet
issued its first INSERT (no lock, possibly no xid yet)" must still be caught.

**Decision.** `IndicatesLiveReserver` is true if any count is non-zero, and then
the mark holds. When all three are zero the gap is proven dead. The mark then
advances to the highest *committed* sequence, "never the reserved last_value"
(issue #4953). Skipped spans are recorded in `mt_high_water_skips`.

**Escape hatch.** `SkipStaleGapsDespiteLiveTransactionsAfter` is off by default:
"Null (the default) never knowingly skips past a live appender". When set, the
daemon skips on "a _suspicion_ of deadness, so an append that commits inside the
skipped range will never be projected". The docs recommend PostgreSQL's
`idle_in_transaction_session_timeout` as "usually the better backstop, since it
removes the cause rather than working around it"
([Marten docs](https://martendb.io/events/projections/async-daemon.html)).

**Scope.** The table-lock and activity signals are limited to the current
database. The `xip` signal is not filtered by database, so an *active* writer
that started before the sighting in another database still holds the gap.
Quiescent idle-in-transaction sessions in any database are excluded, because
the quiescent CTE has no database filter. The `xip` signal is what still sees
prepared transactions and cross-role sessions that `pg_stat_activity` hides.
Marten accepts some cross-database stalling in exchange for working without
elevated privileges.

### Narrowing further: the sequence's own lock (inference)

This subsection is an inference from PostgreSQL's source, not a documented or
field-proven technique. In `sequence.c`, `nextval` first calls
`lock_and_open_sequence`, which takes `RowExclusiveLock` on the sequence under
`TopTransactionResourceOwner`. That holds the lock until the top-level
transaction ends, even if the `nextval` ran inside a savepoint that rolled back.
The call happens *before* any cached value is returned and before an xid is
assigned. An xid is only forced when the fetch is WAL-logged, once every 32
values ([sequence.c](https://raw.githubusercontent.com/postgres/postgres/master/src/backend/commands/sequence.c)).

Together with `CACHE 1`, this suggests a tighter proof:

1. Read the events, and let the read's snapshot reveal a hole below a committed
   position.
2. In a later statement, record the set of `virtualtransaction` values that hold
   a granted lock on the global-position sequence's OID, excluding your own
   backend. Include rows with a null `pid` so prepared transactions count.
   Any reserver still running at the read either appears in this set or has
   ended since. Its lock predates its number, and the number predates the read.
   The fast-path inconsistency in `pg_locks` only affects locks taken or released
   during the scan, so it cannot hide such a reserver.
3. Poll in fresh transactions until none of those virtual transaction IDs still
   holds the lock. Then re-read: positions still missing are dead.

This would cover reservers that have not inserted yet without the broad
same-database `xact_start` signal. It would need no `pg_read_all_stats`, and it
would never wait on other databases. It would stall only on transactions that
genuinely drew numbers from the event store's sequence. Marten's probe does not
use this: it filters `relkind in ('r','p')`, which is tables only, and its doc
comment treats a pre-`INSERT` reserver as having "no lock". The approach should
therefore be tested before anyone relies on it.

Sequin's advisory-lock design pursues the same goal differently. Writers call
`pg_try_advisory_xact_lock_shared(seq_oid, 0)` and lock the next value.
Readers compute a safe ceiling as the minimum advisory `objid` held by
registered sessions. Sequin itself notes that `last_value` is read before
`nextval`, so the locked value is not guaranteed to match
([Sequin](https://blog.sequinstream.com/postgres-sequences-can-commit-out-of-order/)).

### Practical rules for a psycopg 3 event store

These rules synthesise the sources above:

- **Sequence setup.** Keep the global-position sequence at `CACHE 1`. Advance
  the mark only to the highest committed position, never to `last_value`.
- **Observation record.** Record the first sighting with server time and
  `pg_snapshot_xmax(pg_current_snapshot())` in the same transaction as the read
  that revealed the gap. Keep an allocation fence by sampling `last_value`.
- **Probe hygiene.** Wait a short grace period first; Marten uses 3 s, while
  holes "fill in within milliseconds" in the common case. Run each probe in a
  fresh transaction, because `pg_stat_activity` caches per transaction.
  Exclude the consumer's own connections, such as listener, leader-lock and
  probe connections.
- **Avoiding cross-database stalls.** Prefer relation-scoped `pg_locks`
  evidence on the events table and, if validated, on the sequence. Limit
  activity evidence to `current_database()`. Grant `pg_read_all_stats` so
  `xact_start` and `state_change` are visible. Use the cluster-wide `xip` list
  only as a backstop for what the other signals cannot see. Alternatively,
  replace that backstop with `pg_prepared_xacts` filtered by database, or set
  `max_prepared_transactions = 0`.
- **Residual stalls.** Stalls caused by a genuine appender that stays open cannot
  be proven away. Bound them operationally with
  `idle_in_transaction_session_timeout`. If anything, use a
  skip-despite-live cap that is opt-in, logged, and records the skipped ranges.
- **Primary only.** `pg_locks` and `pg_stat_activity` describe sessions on the
  server being queried. Proof evidence must therefore come from the primary,
  where appenders run, not from a standby. This last point is an inference from
  the per-server nature of these views.
