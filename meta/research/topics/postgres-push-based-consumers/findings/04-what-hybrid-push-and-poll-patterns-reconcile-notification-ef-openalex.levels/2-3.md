# At what event arrival rates does a notification-driven consumer degrade in a way analogous to receive livelock, and what signal should switch it to continuous batched polling and back again?

## Question

As event arrival rates rise, when does a consumer that waits for PostgreSQL notifications stop being efficient and start degrading in a way that resembles receive livelock in interrupt-driven kernels? What observable signal should move it into continuous batched polling, and what signal should move it back to waiting for notifications?

## Findings

**Evidence base.** OpenAlex returns truncated abstracts for these records. Where this note describes a paper's mechanisms beyond the abstract excerpt, it is describing that paper's published design. Applying those designs to a PostgreSQL event-log consumer is this note's own analysis. None of the sources measures PostgreSQL itself.

### The kernel precedent

Mogul and Ramakrishnan define the problem this question borrows. Interrupt-driven systems "can provide low overhead and good latency at low offered load, but degrade significantly at higher arrival rates". Under receive livelock, "the system spends all of its time processing interrupts, to the exclusion of other necessary tasks", and in extreme cases nothing reaches the application at all.

The important point is that livelock is not just saturation. A saturated system should plateau at its maximum loss-free rate. A livelocked one collapses beyond it, because the high-priority notification path keeps pre-empting the lower-priority work that would finish each item. Work already spent on earlier stages is then thrown away.

The paper's fix is a hybrid:

- Interrupts are used only to start polling.
- Polling continues, with a per-poll quota and round-robin across sources, until there is no more work. Interrupts are then turned back on.
- Input is temporarily disabled when a full downstream queue, or a CPU-usage limit, shows that other tasks need to run.
- Work that will be discarded is dropped early, and admitted work is processed to completion.

The result is interrupts under light load and polling under heavy load. The switch is driven by the state of the queue, not by a fixed rate.

Three other systems show the same idea of adapting batch size to load:

- **IX** processes bounded batches to completion. Its batches grow only when work is actually backed up, so low load keeps per-item latency and high load gets amortisation.
- **SEDA** builds services from event-driven stages joined by explicit queues. Dynamic resource controllers, including one that tunes how many events a handler takes per call, keep each stage "within their operating regime" so it is not overcommitted when demand exceeds capacity.
- **Pan Qing** adds feedback-control logic to a kernel's event-driven protocol processing. The record notes that most earlier overload fixes "combine polling and interrupt processing together".

Salah, Elbadawi and Haidari compare interrupt-handling schemes analytically at gigabit rates. Their record has no abstract, so this note does not reproduce their crossover results.

### Mapping it onto a PostgreSQL consumer

Treat a NOTIFY reaching a listening connection as the interrupt, and a read of events after the consumer's cursor plus handler execution as packet processing. The costs per event are:

- `c_w`: waking up and handling a notification.
- `c_q`: the fixed cost of one read query (round trip, planning, execution, transaction).
- `c_e`: the marginal cost per event (decode, handle, checkpoint share).

If every notification triggers its own read and each read returns about one event, the consumer's capacity is about **λ₁ = 1 / (c_w + c_q + c_e)**. With batches of B events, capacity rises to about **λ_B = 1 / (c_q/B + c_e)**.

There is no universal threshold rate. The crossover is wherever the arrival rate λ approaches λ₁ for that deployment. As an unmeasured illustration, a read dominated by a 1 ms round trip puts λ₁ below about 1,000 events per second per consumer. Below λ₁, notification-driven waiting is strictly better: it costs nothing when idle and adds only notification latency plus one read. Near λ₁, notifications start arriving while a read is still running, and reads start returning more than one event. Above the batched capacity λ_B, no mode keeps up and lag grows. The aim then, as in the kernel case, is to plateau rather than collapse.

A consumer over a durable log cannot lose deliveries the way a kernel drops packets, because the log is the buffer. The livelock analogue therefore shows up as wasted work and growing lag, not as zero delivery. It arises in three designs:

1. **One read per notification.** Each notification triggers a read even when an earlier read already covered its event. Read rate stays equal to λ while useful rows per read fall, so the consumer spends its capacity on redundant queries. This is the direct analogue of interrupt overhead squeezing out useful processing.
2. **Payload-driven processing.** If the notification payload carries the event and is handled one at a time, the consumer can never batch. Its ceiling is about 1 / (c_w + c_e), and backlog piles up in the connection's notification buffer.
3. **Fan-out on the server.** With N consumers on one channel, per-notification reads put about N·λ queries per second on the database. Batched polling puts about N·λ/B. At high λ, the server spends its capacity answering redundant reads, which competes with the commits that produce the events.

### Signals for switching

Following the kernel design, the most robust signal is the **result of the last read**, not a calibrated arrival-rate threshold. It is self-calibrating: it needs no knowledge of the machine-specific λ₁, which a rate threshold must be tuned to per deployment.

**Switch to continuous batched polling** when either of these is true:

- A read returns a full batch (rows equal the batch limit), which shows there is a backlog.
- More notifications arrived while the read was running. This is a cheap proxy for λ × read duration ≥ 1.

While polling:

- Read again straight away without waiting.
- Drain and discard pending notifications rather than acting on each one (coalescing).
- Cap every batch (the quota).
- Between batches, yield round-robin to other subscriptions and to housekeeping such as lease heartbeats and checkpoint flushes. This is the analogue of Mogul's CPU-usage limit.
- When the downstream handler queue is full, stop reading instead of reading and buffering. The log absorbs the backpressure, which fits the principle of dropping early.

**Switch back to notification-driven waiting** when a read returns a short or empty batch and no notification arrived while it ran. This mirrors re-enabling interrupts once the queue is empty. Two refinements reduce flapping near the crossover:

- Require short batches on several consecutive reads.
- Wait a short "linger" period before re-arming. This is the consumer equivalent of interrupt coalescing, and it trades a little latency for fewer mode changes.

Re-arming must also avoid the lost-wakeup race between the final empty read and the next wait. That ordering is a separate question.

A feedback controller in the style of SEDA or Pan Qing can sit on top of this. It would grow the batch limit while full batches persist and shrink it when per-event latency goals are missed, keeping the consumer in its operating range without hand-tuned rate thresholds.
