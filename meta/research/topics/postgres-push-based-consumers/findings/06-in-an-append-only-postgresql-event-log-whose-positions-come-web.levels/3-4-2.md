# Does pg_current_snapshot on a hot standby replica reflect the primary's in-progress transactions, and can a PostgreSQL event-store consumer safely compute snapshot-xmin watermarks against a read replica?

## Question

When a PostgreSQL event-store consumer runs `pg_current_snapshot()` on a hot standby, does the result describe the transactions still running on the primary? Can the consumer then use `pg_snapshot_xmin(...)` as a "everything below this transaction id is finished" watermark, reading events from the replica rather than the primary?

## Findings

**Short answer.** Partly. On a standby, the snapshot's `xmin` and `xmax` do track the primary's in-progress transactions, but only as of the WAL the standby has replayed, so they lag the primary. The in-progress list (`xip`) is always empty on a standby. An xmin-only watermark is safe against a replica if three conditions hold:

- The watermark is computed on the same replica that serves the event read.
- The consumer never relies on `xip`-based tests.
- The consumer accepts that the watermark trails the primary.

LISTEN and NOTIFY do not work on a standby, so a push-based consumer has to listen on the primary and then wait for the replica to catch up.

### How a standby builds snapshots

A hot standby has no entries for the primary's writing backends in its own process array. It emulates them instead. The transam README says recovery maintains "a list of XIDs belonging to transactions that are being replayed, so that each transaction that has recorded WAL records for database writes exist in the array until it commits." In `procarray.c` this list is called KnownAssignedXids: XIDs "known to be running on the primary (or more precisely, were running as of the current point in the WAL stream)."

The list starts from running-transactions ("running-xacts") WAL records written by `LogStandbySnapshot`. After that the standby must "move shared nextXid forwards as we see new xids" and "keep track of uncommitted known assigned xids". It extends the list from the last observed xid onwards as new xids appear. Per the README, transactions that write no WAL, such as read-only ones, "have no effect on MVCC in recovery." That doesn't matter here, because any transaction that appends events writes WAL.

In `GetSnapshotData`, the snapshot's `xmax` is "always latestCompletedXid + 1" and `xmin` starts at `xmax`. In recovery, `xmin` is then lowered to the oldest entry in KnownAssignedXids. So the snapshot boundaries reflect the primary's running transactions as replayed. The docs describe standby data as "eventually consistent" with "a measurable delay between primary and standby."

### The in-progress list is always empty on a standby

The recovery branch of `GetSnapshotData` stores every known xid in the snapshot's subtransaction array. Its comment reads: "A simpler way is to just store all xids in the subxip array because this is by far the bigger array. We just leave the xip array empty." The top-level count stays 0, so the snapshot ends with `snapshot->xcnt = count` equal to zero.

The server's own visibility checks handle this. `XidInMVCCSnapshot` has a `takenDuringRecovery` branch that searches `subxip` ("The xip array is empty"). `pg_current_snapshot()` does not handle it: it copies only `cur->xcnt` and `cur->xip` into the SQL-level `pg_snapshot`.

On a standby, therefore:

- `pg_current_snapshot()` returns a correct `xmin` and `xmax` with an empty in-progress list.
- `pg_snapshot_xip()` returns no rows.
- `pg_visible_in_snapshot(x, snap)` returns true for every `x` below `xmax`, because the check falls through to "not found in xip, therefore visible". That includes transactions still running on the primary.

None of this is documented. The function docs don't mention standbys, and the PostgreSQL wiki even suggests `txid_current_snapshot()` as a diagnostic on a standby. It is a conclusion from reading the current master source.

The practical rule is to use only `xmin`, and possibly `xmax`, on a replica. Never use `xip` membership, `pg_visible_in_snapshot`, or an "xmin to xmax minus xip" refinement to advance past a long-running transaction there. Doing so would treat in-progress primary transactions as finished, and their events would be skipped when they later commit.

### Why an xmin-only watermark is safe on one replica

The documented invariant for a snapshot's `xmin` is: "All transaction IDs less than xmin are either committed and visible, or rolled back and dead." The standby's own MVCC correctness depends on this holding for snapshots taken there. `xmin` is the oldest xid the standby still considers running, and the docs say "once the commit record for a transaction is replayed on the standby, the changes made by that transaction will be visible to any new snapshots taken on the standby." Together these mean that every appending transaction below the replica's `xmin` has had its commit or abort replayed. Its event rows are therefore visible to a read on that replica.

Two further points support using the replica's values directly:

- **Comparable 64-bit transaction ids.** `pg_current_snapshot()` widens xids to full 64-bit `xid8` values relative to the next transaction id, and the standby advances that from replayed WAL. The resulting values can be compared with `xid8` values the primary stored using `pg_current_xact_id()`.
- **No regression on one replica.** Replay only moves forward: `pg_last_wal_replay_lsn()` "will increase monotonically" while recovery runs. A later watermark query on the same replica therefore never sees less than an earlier one.

### Replica-specific constraints

- **Transaction-id functions.** `pg_current_xact_id()` calls `PreventCommandDuringRecovery`, so it fails on a replica. `pg_current_xact_id_if_assigned()` returns NULL there, because standby transactions "may never be assigned a transaction ID." Appends must stay on the primary, and consumer code must not call these on the replica.
- **Don't mix nodes.** The watermark is only valid for the node that computed it. Combining a primary-computed `xmin` with an event read from a lagging replica can skip events: the replica may not yet have replayed transactions below the primary's `xmin`. Compute the watermark and read the events on the same replica, ideally in one statement or one REPEATABLE READ transaction. If a consumer moves to a replica that is further behind, that replica's lower `xmin` should be treated as "nothing new yet", not as a rewind.
- **Visibility order differs between nodes.** On pgsql-hackers, Jeff Davis notes that PostgreSQL's process-array-based visibility means "some snapshots on the primary are impossible on the replica." Andrey Borodin published a reproducer in which the primary returns "(T1 invisible, T2 visible)" while a standby returns "(T1 visible, T2 invisible)". This "Long Fork" anomaly is still unfixed; commit-sequence-number snapshot work was ongoing as of September 2026. An xmin watermark doesn't depend on commit order, so it stays safe on each node. Event ordering seen through a replica can still differ from the primary's commit order.
- **Extra watermark hold-backs.** The replica's `xmin` trails the primary by replay lag. A primary transaction that dies without writing an abort record stays in KnownAssignedXids, which is pruned only by running-xacts records. The background writer logs those every `LOG_SNAPSHOT_INTERVAL_MS` (15000 ms), and only when there has been activity. Checkpoints also log them. So the replica watermark can stall for up to about 15 seconds after such a failure. Long-running and prepared primary transactions hold it back just as they do on the primary.
- **Subtransactions and query cancellation.** If a transaction has more than 64 subtransactions, standby snapshots are marked "suboverflowed" and need `pg_subtrans` lookups. Such transactions can also delay a standby from accepting read-only connections at startup. Recovery conflicts can cancel standby queries once `max_standby_streaming_delay` is exceeded. Short consumer queries rarely hit that limit, and `hot_standby_feedback` reduces the risk at the cost of bloat on the primary.

### Wake-up path for a replica-reading consumer

LISTEN and NOTIFY are on the docs' list of commands that error on a hot standby. A push-based consumer must therefore LISTEN on the primary. Notifications are delivered only once the notifying transaction commits, "in the order in which the transactions committed." When one arrives, the replica may not yet have replayed that commit, so an immediate replica read can come back empty.

There are three ways to close that gap:

1. **`synchronous_commit = remote_apply` on appending sessions,** with the replica listed in `synchronous_standby_names`. Commits then wait until the standby has "applied it, so that it has become visible to queries on the standby(s)." The docs warn of "much larger commit delays".
2. **Poll the replica's replay position.** After a notification, read `pg_current_wal_insert_lsn()` on the primary. That LSN is at or past the notifying commit. Then poll `pg_last_wal_replay_lsn()` on the replica until it reaches that LSN.
3. **`WAIT FOR LSN 'lsn'` (PostgreSQL 19, beta 4 as of 24 September 2026).** In `standby_replay` mode it is documented as giving read-your-writes consistency on an async replica, "provided that the target LSN is at or after the end of the relevant write transaction's COMMIT record." It must run as a top-level command before the reading transaction takes a snapshot. It supports `TIMEOUT` and `NO_THROW`.
