# Does RDS Proxy forward asynchronous NotificationResponse messages to a pinned PostgreSQL client connection promptly and without loss, and are pinned listener connections ever closed before the 24-hour maximum lifetime?

## Question

When a PostgreSQL client issues `LISTEN` through Amazon RDS Proxy, the proxy pins the session to one database connection. Does the proxy then pass the server's unsolicited `NotificationResponse` messages on to the client promptly and reliably? And can such a pinned listener connection be closed before the proxy's fixed 24-hour client-connection lifetime runs out?

## Findings

**Short answer.** AWS treats `LISTEN` as something to preserve, not reject: listening on a notification channel is one of the documented triggers that pin a PostgreSQL session to one backend for the rest of the session. AWS does not document how the proxy forwards asynchronous `NotificationResponse` messages. It gives no latency figure, no buffering behaviour and no delivery guarantee for them, so "promptly and without loss" is a reasonable expectation inside an unbroken session but not a documented promise. The second half has a clear answer: yes, pinned listener connections can be closed well before 24 hours. The documented causes are the idle client timeout (30 minutes by default, 8 hours at most), database restarts that close the pinned backend, and the fixed 24-hour cap itself. Whenever a session ends, its `LISTEN` registrations go with it, and nothing committed during the gap is ever delivered. A listener behind RDS Proxy must therefore treat notifications as wake-up hints and catch up from durable storage after every reconnect.

### What AWS documents about LISTEN and pinning

The RDS and Aurora user guides list "Listening on a notification channel" among the PostgreSQL conditions that cause pinning. The same list covers `SET`, session-level prepared statements, temporary tables, cursors, session-level advisory locks and `nextval`/`setval`. Once a session is pinned, "each later transaction uses the same underlying database connection until the session ends", other clients cannot reuse that database connection, and "the session ends when the client connection is dropped". AWS's best-practice guide calls pinning "an exclusive 1:1 association between a client-proxy connection and a proxy-database connection".

The proxy also reads the protocol rather than passing raw bytes through: AWS says it handles traffic "first by understanding the database protocol", and the engine family "determines which database network protocol the proxy recognizes when it interprets network traffic to and from the database". So the backend that holds a listener's registrations stays bound to that one client for the whole session, and its notifications have only one place to go. Pinning exists for exactly this purpose: so that state the proxy cannot move between backends, including channel registrations, keeps working.

Two documented PostgreSQL limitations also matter to a listener:

- RDS Proxy "doesn't currently support canceling a query from a client by issuing a `CancelRequest`". A listener cannot rely on a protocol-level cancel to break out of a blocking wait. It needs a client-side mechanism instead, such as psycopg 3's `notifies()` `timeout` or `stop_after` parameters, or closing the generator.
- Session pinning filters are not supported for PostgreSQL, so the pin cannot be configured away.

### Forwarding promptness and loss: what is and is not established

The PostgreSQL protocol defines `NotificationResponse` as an asynchronous message. The backend sends it whenever a `NOTIFY` commits on a channel the session listens to. At present it can only be sent outside a transaction, though possibly just before `ReadyForQuery`, and "frontends must be prepared to deal with these messages at any time, even when not engaged in a query". To forward one, a proxy must relay a message the server sends on its own initiative while no client request is outstanding.

None of the AWS pages on pinning, connections, limitations, troubleshooting, monitoring or best practices describes how RDS Proxy handles such server-initiated messages. Neither does the AWS Database Blog post on PostgreSQL extended-query multiplexing. There is no statement on latency, ordering, buffering or loss for notifications. The only latency figure AWS publishes is that the extra network hop through RDS Proxy typically adds latency "in the low single-digit milliseconds", stated for query traffic. Applying it to notifications is a plausible but undocumented extrapolation.

On loss, the PostgreSQL side is well defined, and it shows where loss realistically happens:

- Notifications are queued on the server until every listening session has processed them. The queue holds 8 GB in a standard installation, and when it fills, `NOTIFY` fails at commit rather than discarding entries. If the listening session is inside a transaction, delivery waits until that transaction ends.
- A session's "listen registrations are automatically cleared when the session ends", and a `NOTIFY` reaches only "the sessions currently listening on that notification channel".

So inside one unbroken pinned session, a notification is lost only if the proxy itself discards bytes from a 1:1 relay, and AWS documents no mechanism that would do that. (That is an inference from the architecture, not something AWS states.) The real loss window is any break in the session. When the client connection or the pinned backend ends, the registrations vanish, and every notification committed before the new connection's `LISTEN` takes effect is never queued for it. `LISTEN` itself only takes effect at transaction commit.

### Pinned listener connections are closed before 24 hours

RDS Proxy documents several ways a pinned listener connection can end early.

1. **Idle client timeout.** `IdleClientTimeout` defaults to 1,800 seconds (30 minutes) and can be set from 1 second up to 28,800 seconds (8 hours). The user guide defines a client connection as idle "when the application doesn't submit a new request within the specified time after the previous request completed". The API reference puts it as "no activity". The best-practice guide says that for the timeout to apply, the connection "must be truly idle without sending any queries (even simple health checks such as `SELECT 1;`)".

   Taken together, these say that client requests reset the timer. A listener that only waits on `notifies()` sends no requests, so it is exposed to closure after at most 8 hours, and after 30 minutes by default. Whether server-to-client notification traffic also resets the timer is not documented, and the user-guide wording counts only requests the application submits. AWS explicitly lists "you deliberately want to prevent certain connections from timing out in the proxy layer" as a legitimate reason to keep client-side liveness checks.

2. **Database restart.** In AWS's own words: "pinned back-end connections might be closed due to a database restart". A pinned backend cannot be swapped transparently, because the state that justified the pin, here the `LISTEN` registrations, lives only on that backend.

3. **The fixed 24-hour cap.** "RDS Proxy enforces a maximum life of client connections of 24 hours. This value is not configurable." The proxy "closes the connection after 24 hours even if it doesn't qualify as idle", "regardless of the activity on the connection". AWS advises setting client-side maximum connection lifetimes below 24 hours "to avoid unexpected client connection drops".

4. **Failover: documented for other connection types, not for pinned ones.** AWS says that during a failover the proxy connects to the standby "without dropping idle application connections", and that "only connections that are in the middle of a transaction or SQL statement are canceled". It does not say what happens to a pinned session whose backend was on the failed instance. A pinned listener might be dropped, or it might be silently reattached to a backend with no registrations. That is a separate open question, and it cannot be assumed either way.

The documentation names no other trigger for closing client connections, but it does not promise there are none. The RDS Proxy event catalogue has no event for dropped client connections. The aggregate CloudWatch metrics `ClientConnectionsClosed` and `DatabaseConnectionsCurrentlySessionPinned` are the only proxy-side signals.

### Implications for a psycopg 3 listener behind RDS Proxy

- **Heartbeat.** Wake periodically, for example by looping `notifies(timeout=...)`, and issue a trivial query on the listener connection, at an interval comfortably shorter than the proxy's `IdleClientTimeout`. This is the documented way to keep a connection from being treated as idle. Psycopg's documentation also advises keeping the listening connection in autocommit so that notifications arrive in a timely manner.
- **Planned recycling.** Replace the listener before 24 hours on your own schedule. Open the new connection and commit its `LISTEN` before closing the old one, so the two overlap rather than leaving a gap. Then run a catch-up read from the store's durable position.
- **Every disconnect is a gap.** Whatever the cause (idle timeout, 24-hour cap, database restart, failover), re-issue `LISTEN` and catch up from storage. Never assume notifications were buffered across the break. PostgREST's listener is an established example of this pattern: it retries forever with exponential backoff, capped at 32 seconds between attempts, and reloads its cached state on recovery.
- **Budget for dedicated backends.** Each listener holds its own backend for its lifetime. Pinned connections are not available for reuse and do not count as idle in the pool, so one shared listener per process keeps the cost bounded.
