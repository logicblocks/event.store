# What keepalive, timeout and health-check settings let a long-lived session-mode LISTEN connection through PgBouncer or a managed pooler detect a silently dead link quickly, without being closed as idle by client-side or proxy-side timeouts?

## Question

A consumer that waits for `NOTIFY` holds one connection open for a long time and sends almost nothing on it. When that connection runs through PgBouncer in session mode, or through a managed pooler, which settings at the client, the pooler and the PostgreSQL server let the consumer find out quickly that the link has silently died? And which idle timeouts must be avoided or outpaced so that a healthy but quiet listener is not closed?

## Findings

### A pooled LISTEN connection is two TCP legs, and each needs its own detection

Through a pooler, a listener has two TCP connections: one from the application to the pooler, and one from the pooler to PostgreSQL. In session mode PgBouncer "assigns a server connection to [the client] for the whole duration it stays connected". `LISTEN` is supported in session pooling and "Never" in transaction pooling (PgBouncer features page).

Detection at the TCP layer is per leg. The application's libpq keepalive probes are answered by the pooler's kernel, so they show only that the pooler host is reachable. They say nothing about the pooler-to-PostgreSQL leg. That leg is covered by PgBouncer's own socket options and by PostgreSQL's server-side keepalives. PgBouncer's source applies one `tune_socket()` routine, which sets keepalive and `TCP_USER_TIMEOUT`, to both accepted client sockets (`sbuf_accept`) and outbound server sockets (`sbuf_connect`). It skips Unix-domain sockets. So one set of `tcp_*` values in `pgbouncer.ini` covers both of PgBouncer's legs.

When PgBouncer's server connection dies, `disconnect_server` unlinks it and disconnects the linked client with an error message. A dead server leg therefore surfaces to psycopg as a closed connection, but only once PgBouncer notices it. The reverse also holds. When the client disconnects, PgBouncer releases the server back to the pool. In session mode it runs `server_reset_query` (default `DISCARD ALL`) on release, and `DISCARD ALL` includes `UNLISTEN *`. So LISTEN state does not leak to the next client. However, the backend stays registered as a listener for as long as PgBouncer takes to detect a silently dead client. PostgreSQL's docs warn that the 8 GB notification queue cannot be cleaned up past a listening session that stops progressing, and they log warnings once it is half full. That makes fast detection of a dead client on PgBouncer's side a server-health concern as well as a consumer concern.

Only one check runs end to end: a query sent through the listener's own connection. Its reply must cross both legs.

### What will and will not close a quiet session-mode listener

**PgBouncer.** PgBouncer's janitor code limits its idle timers to connections that are not in use:

- `client_idle_timeout` (default 0, disabled) skips any client that has a linked server (`if (client->link) continue;`). A session-mode client that has issued `LISTEN` is linked, so this timer never closes it. The docs say the setting should be "larger than the client-side connection lifetime settings, and only used for network problems".
- `server_idle_timeout` (default 600 s) and `server_lifetime` (default 3600 s) are enforced only on the used, tested and idle server lists. They never touch the active list that a linked session server sits on. This matches the documented wording: `server_lifetime` closes an "unused (not currently linked to any client connection) server connection".
- `server_check_query` and `server_check_delay` run only when a released server is handed to a new client. PgBouncer has no in-session health check for a linked listener's server leg.
- `idle_transaction_timeout` (default 0) applies only when the client sits idle inside a transaction. Leaving it on for the listener's user is a useful guard, because a listener stuck in a transaction neither receives notifications nor lets the queue be cleaned. The listener must run in autocommit.
- `pool_mode` can be set per database entry and per user. A dedicated listener alias or user can therefore get `session` while application traffic stays on `transaction`. `client_idle_timeout`, `query_timeout`, `idle_transaction_timeout` and `transaction_timeout` can also be overridden per user.

**PostgreSQL server.** `idle_session_timeout` (PostgreSQL 14+) terminates any session "idle … but not within an open transaction". A quiet listener is exactly that. The docs advise against enforcing it on connections from pooling middleware and suggest scoping it to particular users. For the listener's role, set it to 0, or else keep the probe interval below it. `idle_in_transaction_session_timeout` and `transaction_timeout` touch the listener only if it opens a transaction.

**Managed poolers.**

- **AWS RDS Proxy.** RDS Proxy pins a session when it detects "Listening on a notification channel". The client then keeps a dedicated database connection until it disconnects. The "Idle client connection timeout" defaults to 1,800 s. A connection counts as idle "when the application doesn't submit a new request within the specified time after completing the previous request." By that definition, notifications arriving from the server are not application requests. A notify-only listener should therefore expect to be closed after the timeout unless it sends a query more often than that.
- **Azure Database for PostgreSQL flexible server.** The built-in PgBouncer is version 1.25.2 on port 6432, with `pool_mode` defaulting to `transaction`. Only a short parameter list is exposed (`pool_mode`, `server_idle_timeout` 600, `query_wait_timeout` 120, pool sizes and so on), and it includes no keepalive settings. Azure also notes that PgBouncer restarts with the VM on scaling, HA failover or restart, after which connections must be re-established. The documented list offers no per-database `pool_mode`. A listener therefore either needs the whole server's pooler in session mode, or connects directly on port 5432 and relies on client-side and server-side keepalives.
- **Google Cloud SQL managed connection pooling.** It offers transaction mode (the default) and session mode. `LISTEN` is unsupported in transaction mode. Its options mirror PgBouncer's: `client_connection_idle_timeout` (default 0), `server_connection_idle_timeout` (600 s), `server_lifetime` (3,600 s) and `query_wait_timeout` (120 s). The docs do not say whether the client idle timer exempts session-linked clients the way PgBouncer does. If it is set to a non-zero value, keep the probe interval below it.
- **Neon.** Neon's pooled endpoint is PgBouncer in transaction mode, its settings are not user-configurable, and LISTEN/NOTIFY is listed as unsupported. A listener must use the direct, unpooled endpoint.
- **Supabase.** The shared Supavisor pooler's session mode (port 5432) supports session features including LISTEN. The dedicated pooler runs in transaction mode only. Supavisor has a tenant `client_idle_timeout` (0 in the client-handler defaults). In its client handler, the idle timer is armed only on the busy-to-idle transition after a query completes, so server-originated traffic does not reset it, but a periodic client query does. The handler also has a separate periodic heartbeat that writes a protocol message to the client socket and terminates the client if the write fails.

**Network middleboxes on either leg.** These drop state silently on quiet flows:

- An AWS NAT gateway times out a flow after 350 s idle and answers later packets with RST. AWS recommends TCP keepalive "with a value less than 350 seconds".
- An AWS Network Load Balancer defaults to 350 s idle for TCP (configurable from 60 to 6,000 s), and "TCP keepalive packets [can] restart the idle timeout". Its TLS listeners are fixed at 350 s.
- Azure Standard Load Balancer defaults to 4 minutes, configurable from 4 to 100 minutes.

The keepalive idle time on every leg that crosses such a device therefore needs to sit well under 240 s to be safe on Azure, and under 350 s on AWS.

### Keepalive and TCP_USER_TIMEOUT: what each one bounds

Linux's defaults (`tcp_keepalive_time` 7200 s, `tcp_keepalive_intvl` 75 s, `tcp_keepalive_probes` 9) mean an idle dead peer is noticed only after about 2 h 11 min. PgBouncer's docs restate these defaults for its own `tcp_keepalive = 1`, whose `tcp_keepidle`, `tcp_keepintvl` and `tcp_keepcnt` are "not set" by default. With no keepalive at all, an idle established socket has no timer and "will remain in that state forever, even if the communication is broken" (Cloudflare).

Keepalive covers only the idle case. Once there is unacknowledged data, such as a probe query or a notification being written, keepalive stops and retransmission falls under `tcp_retries2`, which defaults to roughly 13 to 30 minutes. `TCP_USER_TIMEOUT` bounds that case: it is the maximum time "transmitted data may remain unacknowledged". When combined with `SO_KEEPALIVE`, Linux also uses it to "override keepalive to determine when to close a connection due to keepalive failure" (tcp(7)). Cloudflare's guidance is to enable keepalive and set `TCP_USER_TIMEOUT = TCP_KEEPIDLE + TCP_KEEPINTVL × TCP_KEEPCNT`. Too small a value aborts early, and too large a value makes the keepalive count irrelevant.

The same four knobs exist at every hop:

| Leg | Keepalive idle, interval, count | Unacked-data bound |
|---|---|---|
| App to pooler (libpq conninfo) | `keepalives=1` (default), `keepalives_idle`, `keepalives_interval`, `keepalives_count` | `tcp_user_timeout` (ms) |
| PgBouncer, both of its legs | `tcp_keepalive`, `tcp_keepidle`, `tcp_keepintvl`, `tcp_keepcnt` | `tcp_user_timeout` (ms, "only supported on Linux") |
| PostgreSQL to its client (the pooler) | `tcp_keepalives_idle`, `tcp_keepalives_interval`, `tcp_keepalives_count` | `tcp_user_timeout` (ms) |

Platform notes:

- libpq and PostgreSQL apply each option only where the matching socket option exists. `TCP_USER_TIMEOUT` is absent on Windows and has no effect where unsupported, so a macOS listener has no kernel bound on the unacked-data case.
- PostgreSQL's `client_connection_check_interval` detects a vanished client only while a query is running. It does not help an idle listener.

### An application-level liveness probe on the listener connection

TCP keepalives on the client leg cannot see a pooler that is alive while its server leg is dead. Pooler idle timers such as RDS Proxy's, Supavisor's and possibly Cloud SQL's count only client requests. Both gaps call for a periodic query issued on the listener connection itself, such as `SELECT 1` in autocommit. The probe:

- crosses both legs, so a reply proves the whole path, and a dead server leg makes PgBouncer close the client;
- resets request-based idle timers at the pooler and PostgreSQL's `idle_session_timeout`;
- refreshes NAT and load-balancer flow state on both legs, including the pooler-to-server leg where the application cannot set keepalives.

In psycopg 3.2+, `Connection.notifies(timeout=…, stop_after=…)` returns control after a bounded wait. A listener loop can therefore wake on a schedule, run the probe on the same connection, and resume listening without a second thread touching the connection. The probe needs its own deadline, because a probe written into a dead link becomes unacknowledged data:

- On Linux, the client-side `tcp_user_timeout` provides that deadline.
- Elsewhere, or as defence in depth, the application should enforce a deadline itself. One way is to wrap the async probe in a timeout and discard the connection when it expires.

On failure, psycopg reports `Connection.broken`, which distinguishes an interrupted connection from a cleanly closed one. That is the trigger for the reconnect-and-catch-up path.

### A configuration that satisfies both goals

The values below illustrate the constraints rather than prescribe them. Each one is chosen to stay under the shortest idle timeout on the path while bounding detection to about a minute.

- **Client (psycopg conninfo):** `keepalives=1 keepalives_idle=30 keepalives_interval=10 keepalives_count=3 tcp_user_timeout=60000`. A dead idle client leg is found in about 60 s, and keepalives every 30 s keep NAT and load-balancer state warm.
- **PgBouncer:** the same `tcp_keepidle=30`, `tcp_keepintvl=10`, `tcp_keepcnt=3`, `tcp_user_timeout=60000`, with `pool_mode=session` on a dedicated listener database entry or user. Set `idle_transaction_timeout` for that user. `client_idle_timeout`, `server_idle_timeout` and `server_lifetime` can be left at their defaults, because they do not touch linked session connections.
- **PostgreSQL:** server `tcp_keepalives_*` and `tcp_user_timeout` set similarly, so that a vanished pooler host or direct client is detected and its listener slot freed. `idle_session_timeout = 0` for the listener role.
- **Liveness probe:** every 30 to 60 s via `notifies(timeout=…)`, with a deadline of a few seconds. The interval must stay below every request-based idle timer in use: RDS Proxy's 1,800 s default, any Supavisor or Cloud SQL client idle timeout, and any `idle_session_timeout`.

### Caveats

- The PgBouncer timer exemptions are read from the current janitor source and agree with the documented `server_lifetime` wording. They are not re-tested here across older PgBouncer versions.
- The managed-pooler documentation does not state whether server-originated notifications reset client idle timers, nor how promptly those poolers forward `NotificationResponse` to a pinned or session client. The guidance to probe more often than the idle timeout follows from their request-based definitions of idleness.
