# How should a psycopg 3 consumer structure one long-lived listener connection that combines waiting with a timeout, heartbeat checks and reconnect-then-catch-up, and which failure modes such as idle_session_timeout, TCP keepalives and poolers must it guard against?

## Question

How should a consumer built on psycopg 3 structure a single long-lived LISTEN connection so that it waits for notifications with a bounded timeout, checks that the connection is still healthy, and after any disconnect reconnects and catches up from the durable log? And which failure modes must it defend against: server-side session timeouts such as `idle_session_timeout`, silent TCP loss and keepalive tuning, connection poolers and proxies, and failover?

## Findings

### Summary

The design the sources support has five rules:

1. Use one dedicated connection in autocommit mode that does not come from a pool.
2. Issue `LISTEN` first, then do a catch-up read from the consumer's stored position, then wait.
3. Wait with `Connection.notifies(timeout=...)`, which needs psycopg 3.2 or later. A version of 3.2.10 or later is safer.
4. When the wait times out with no notification, run a cheap heartbeat query and also run the catch-up read, so that a timeout doubles as a safety-net poll.
5. When an `OperationalError` is raised, close the connection, back off exponentially, and start again from rule 2.

TCP keepalives and `tcp_user_timeout` make a silently dead path fail quickly. The heartbeat interval must stay below every idle timeout on the path (`idle_session_timeout`, pooler and proxy idle-client limits, load-balancer idle timeouts). The connection must avoid transaction-mode poolers completely, because `LISTEN` cannot work through them.

### The psycopg 3 primitives and their constraints

**Autocommit is required.** psycopg's documentation says to keep the connection in autocommit mode "if you wish to receive or send notifications in a timely manner." The reason is in PostgreSQL itself. Notifications "are only delivered between transactions". If a listening session is inside a transaction when a notification arrives, delivery waits "until just after the transaction is completed". A long transaction also has a cost for the whole server: "no cleanup can take place if a session executes `LISTEN` and then enters a transaction for a very long time." The notification queue is 8GB, and once it is full, "transactions calling `NOTIFY` will fail at commit." A listener that leaves a transaction open can therefore break writers that call NOTIFY, not only itself.

**Bounded waiting.** `Connection.notifies(*, timeout=None, stop_after=None)` and its asyncio counterpart gained `timeout` and `stop_after` in psycopg 3.2. When the timeout expires, the generator ends without raising. With `stop_after=n` it ends after n notifications, although it "might actually receive more than this number if more than one notifications arrives in the same packet." In the source code, a timeout of 0 still polls at least once.

**The generator holds the connection lock.** The method runs its whole loop inside `with self.lock`. While the generator is waiting, no other thread or task can run a query on that connection. A heartbeat therefore cannot run alongside the wait on the same connection. The loop has to leave the generator, either by timeout or by `stop_after`, run its heartbeat, and then start a new generator. Two cautions about leaving early:

- Closing a generator that is waiting can only be done from another thread or task.
- Breaking out of the loop early leaves the generator suspended while it still holds the lock, until it is garbage-collected.

So the cleanest pattern is to iterate a bounded generator until it finishes.

**Version floor.** That exit-and-re-enter pattern was unsafe in early 3.x releases. Issue #962 reports this exact sequence: `notifies(timeout=5)`, then a health-check query, then `notifies(timeout=5)` again. Notifications sent during the health check were lost. The fix landed in 3.2.4 ("Don't lose notifies received whilst the `notifies()` iterator is not running"). Version 3.2.4 also delivers notifications that arrive between `LISTEN` and the start of the generator.

The 3.2.4 buffer caused a memory leak when the generator was never called. That leak was fixed in 3.2.10 (ticket #1091). Version 3.2.10 also changed the rules for mixing the two delivery methods: if a handler is registered, notifications that arrive while the generator is not running go only to the handler. Using both the generator and handlers on one connection is deprecated and now raises a runtime warning.

The practical rules are:
- Require psycopg 3.2.10 or later.
- Use the generator only.
- Do not register `add_notify_handler` on the listener connection. Handlers fire only while the connection is running a query, so they suit a poll-with-handler design but not a blocking wait.

**Typed disconnect errors.** Since 3.2.4, psycopg raises the server's actual error when a server error disconnects the client, rather than a generic `OperationalError`. Examples are `AdminShutdown` (57P01) and `IdleSessionTimeout` (57P05). Every class-57 error inherits from `OperationalError`, so one `except psycopg.OperationalError` handler covers all of them and can still log the specific cause.

### How two production libraries structure the loop

**Procrastinate** is a Python task queue built on psycopg 3.
- **Connection:** its listener uses a standalone `AsyncConnection` opened with `autocommit=True`, built from the pool's conninfo and settings but not taken from the pool.
- **Wait:** it issues `LISTEN` on each channel, then loops on `connection.notifies()` with a 30-second timeout that does not raise (`LISTEN_TIMEOUT = 30.0`).
- **Heartbeat:** after each wait ends it runs `SELECT 1`.
- **Reconnect:** `psycopg.OperationalError` breaks the inner loop, and an outer `while True` opens a fresh connection and re-issues `LISTEN`.
- **Safety net:** the worker treats a notification only as a wake-up. A notification sets an `asyncio.Event`, and the worker waits for whichever comes first: that event, a 5-second `fetch_job_polling_interval` sleep, or a stop event. It fetches once at startup, before waiting. Polling therefore covers notifications missed during a reconnect.

**River** is a Go job queue, and its notifier has the same structure.
- **Wait and heartbeat:** a goroutine blocks in `WaitForNotification` while a `select` loop pings the connection every 5 seconds ("Ping the conn to see if it's still alive"). Either a wait error or a ping error ends the cycle. Its code comments say this was added so that "dead or flaky connections are now actively detected".
- **Reconnect:** after an exponential-backoff sleep it reconnects and re-issues `LISTEN` for every current subscription.
- **Catch-up:** the notifier does not catch up itself. Subscribers are expected to re-poll.

### Reconnect-then-catch-up ordering

PostgreSQL clears "a session's listen registrations ... automatically ... when the session ends". Nothing published while the consumer is disconnected is kept for it. Recovery must therefore come from the durable log, not from notifications.

`LISTEN` "takes effect at transaction commit", which in autocommit mode means as soon as the statement completes. That gives the correct order on every connect and reconnect:

1. Connect.
2. Run `LISTEN` (committed).
3. Read the log from the consumer's last processed position.
4. Wait.

The order matters. If the catch-up read ran before `LISTEN`, an append committed between the two would be invisible to both, and would wait until the next timeout poll. With `LISTEN` first, such an append is either seen by the read or produces a notification. Since 3.2.4, psycopg buffers that notification even though it arrives before the generator starts. The worst case is then a redundant read that finds nothing new.

The catch-up read should key on the stored position and read everything after it, so that a burst of notifications collapses into one read. Making it gap-safe when positions are reserved before commit is a separate question. If the read runs on the listener connection, it must be a single autocommit statement or a very short transaction. Otherwise it delays delivery and blocks cleanup of the notification queue, as described above. A separate pooled connection for catch-up reads avoids that coupling.

Reconnect attempts should back off exponentially with a cap. River does this, and so does psycopg's own pool, which retries "using an exponential backoff ... until a maximum of `reconnect_timeout`". This avoids hammering a server that is restarting or failing over.

If the consumer also issues NOTIFY, its own notifications will come back to it. PostgreSQL suggests comparing the notifying backend's PID, which `Notify.pid` carries, with the session's own PID to skip them.

### Why a heartbeat is needed, and what it can and cannot detect

The wait returns only when the socket becomes readable or the timeout expires.

- **Server-initiated closures** make the socket readable, and psycopg raises. Examples are `idle_session_timeout`, administrator termination and server shutdown, and each sends a FATAL error before the server closes the connection.
- **A silently dead path** produces nothing. Causes include a middlebox dropping its connection state, a network partition, or a host disappearing during failover. Each timeout looks like a quiet period, and the consumer believes it is idle.

psycopg's "Detecting disconnections" section advises against a constant `SELECT 1` loop. It recommends waiting for operating-system readiness on the file descriptor and probing only when there is activity. That catches server-side closures cheaply. It cannot, on its own, catch a path that has gone silent, because no bytes ever arrive. That is why Procrastinate and River both probe on a timer as well.

Sending data matters because of how Linux handles retransmission. Without `tcp_user_timeout`, the kernel keeps retransmitting unacknowledged data for `tcp_retries2` (default 15), "approximately between 13 to 30 minutes". `tcp_user_timeout` caps how long data may stay unacknowledged before the connection is "forcibly closed". On Linux, when keepalives are enabled, it "will override keepalive to determine when to close a connection due to keepalive failure."

There is also a further point, which goes beyond what the sources state. TCP keepalives check only the hop to the nearest TCP peer. When a pooler or proxy sits in front of PostgreSQL, only a SQL-level heartbeat tests the whole client-to-backend path.

Received notifications should not be assumed to reset server idle timers. PostgreSQL defines idle as "waiting for a client query", so a listener that only receives notifications may still count as idle. The heartbeat should therefore be time-based: it runs whenever the listener has not issued a query within the interval, not only after a timeout with no notifications.

### Failure modes to guard against

- **`idle_session_timeout` (PostgreSQL 14+).** It terminates any session "idle (that is, waiting for a client query), but not within an open transaction" for longer than the setting. A waiting listener matches that definition. The documentation warns: "Be wary of enforcing this timeout on connections made through connection-pooling software or other middleware". It suggests limiting the setting to particular users. Two guards are available: exempt the listener's role, or keep the heartbeat interval below the timeout. Expect `IdleSessionTimeout` and handle it as a normal reconnect.
- **`idle_in_transaction_session_timeout` and `transaction_timeout`.** These terminate sessions held in a transaction. They matter only if the listener breaks the autocommit rule, and in that case notification delivery and queue cleanup break too. `statement_timeout` does not affect the wait, because no statement is running, but it does apply to heartbeat and catch-up queries.
- **Silent TCP loss and middlebox idle timeouts.** libpq enables client keepalives by default. However, `keepalives_idle=0` means "the system default", which on Linux is 7200 seconds. That is far longer than common middlebox timeouts:
  - An AWS Network Load Balancer stops tracking a TCP flow after 350 seconds idle by default. The next send gets an RST. The docs say "clients or targets can use TCP keepalive packets to restart the idle timeout".
  - Azure Standard Load Balancer defaults to a 4-minute idle timeout, after which the session "isn't guaranteed to be maintained".

  The listener should therefore set these libpq parameters, all of which psycopg passes through:
  - `keepalives_idle` below the smallest idle timeout on the path, such as tens of seconds.
  - Small `keepalives_interval` and `keepalives_count` values.
  - `tcp_user_timeout`, so that both keepalive probes and heartbeat queries fail within a known time.
  - `connect_timeout`, so that a reconnect attempt cannot hang. It applies to each host separately.
- **Orphaned listeners on the server.** Server-side `tcp_keepalives_*` and `tcp_user_timeout` let the server reclaim backends whose client vanished. RDS defaults are 300 seconds idle, a 30-second interval and a count of 2. `client_connection_check_interval` (PostgreSQL 14+) polls the socket only while a query is running, so it does not help an idle listener.
- **Transaction-mode poolers.** PgBouncer's feature matrix marks LISTEN as "Never" in transaction pooling, although NOTIFY works there. Neon's pooled endpoint runs PgBouncer with `pool_mode=transaction`, lists LISTEN/NOTIFY as unsupported, and directs listeners to the direct hostname (the one without `-pooler`). Session pooling works, but the listener permanently occupies one server connection. It is also exposed to PgBouncer's `client_idle_timeout`, which is off by default and documented as "potentially dangerous". A library should accept a separate listener conninfo so that deployments can route publishes and reads through a pooler and send LISTEN direct.
- **Proxies that pin sessions.** On Amazon RDS Proxy, "Listening on a notification channel" pins the client session to one database connection until the client disconnects. This works, but the listener gets no multiplexing benefit. RDS Proxy also disconnects client connections that stay inactive beyond `IdleClientTimeout`, so the heartbeat interval must be shorter than that limit.
- **Client-side pools.** Procrastinate deliberately keeps its listener out of psycopg_pool. A pool's `max_idle`, `max_lifetime` and `check` behaviour exists to recycle connections, which suits short borrows and does not suit a session that has to persist. One further point is my own reasoning rather than anything the sources state. A pooled connection returned with active `LISTEN` registrations would carry that session state to the next borrower, unless a `reset` callback runs `UNLISTEN *`.
- **Failover onto a standby.** Hot-standby sessions cannot run `LISTEN` or `NOTIFY`; both raise errors. A reconnect after failover must therefore reach the primary. libpq's multi-host conninfo with `target_session_attrs=read-write` or `primary` tries each host until one is acceptable. Sessions on a standby that gets promoted "remain connected while the server changes mode".

### Reference loop shape

The following synchronous sketch puts the pieces together. It is a synthesis of the sources above, not code from any one of them. It needs psycopg 3.2.10 or later.

```python
import time
import psycopg
from psycopg import sql

CONNECT_KWARGS = dict(
    autocommit=True, connect_timeout=10,
    keepalives=1, keepalives_idle=30, keepalives_interval=10,
    keepalives_count=3, tcp_user_timeout=60_000,
)

def listen_forever(listener_conninfo, channel, catch_up, interval=30.0):
    backoff = 0.5
    while True:
        try:
            with psycopg.connect(listener_conninfo, **CONNECT_KWARGS) as conn:
                conn.execute(sql.SQL("LISTEN {}").format(sql.Identifier(channel)))
                backoff = 0.5
                catch_up()                     # read log after stored position
                last_query = time.monotonic()
                while True:
                    for _ in conn.notifies(timeout=interval, stop_after=1):
                        pass                   # a hint only; exhaust, don't break
                    if time.monotonic() - last_query >= interval:
                        conn.execute("SELECT 1")   # heartbeat, resets idle timers
                        last_query = time.monotonic()
                    catch_up()                 # wake-up or safety-net poll
        except psycopg.OperationalError:      # incl. IdleSessionTimeout, AdminShutdown
            time.sleep(backoff)
            backoff = min(backoff * 2, 30.0)
```

The asyncio version has the same shape with `AsyncConnection` and `async for`. To stop the consumer, cancel the task while it waits or set a stop flag that is checked after each bounded wait. The `interval` value must stay below these limits:
- `idle_session_timeout`
- any pooler or proxy idle-client timeout
- the latency budget for recovering missed notifications, since every timeout also runs a catch-up read
