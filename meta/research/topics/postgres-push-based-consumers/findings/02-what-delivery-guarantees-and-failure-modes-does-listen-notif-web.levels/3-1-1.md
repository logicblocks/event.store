# For a consumer that tracks a checkpoint in an append-only event log instead of claiming rows, how should wake-up coalescing, debounce windows and backstop poll intervals be tuned to bound end-to-end latency without issuing redundant reads?

## Question

A consumer reads an append-only event log from a stored checkpoint, rather than claiming rows from a job table. It is woken by PostgreSQL `LISTEN`/`NOTIFY` and backed by periodic polling. How should it coalesce wake-ups, size any debounce or cooldown window, and set the backstop poll interval so that end-to-end latency stays bounded without issuing redundant reads?

## Findings

### Why a checkpoint consumer can coalesce freely

A checkpoint consumer's read is cumulative: "fetch events with position greater than my checkpoint, up to a safe horizon, in order, one page at a time". One read after ten commits returns the same events as ten reads, one after each commit. Ten wake-ups therefore carry no more information than one. A notification is a level-triggered hint that the log may have grown, not a unit of work.

PostgreSQL does not do this coalescing for the consumer. Within one transaction it delivers only one copy of an identical channel-and-payload pair, but "notifications from different transactions will never get folded into one notification". Notifications from different transactions arrive in commit order. They are also delivered only between transactions, and psycopg's documentation tells listeners to stay in autocommit mode to receive them promptly. A listener facing R committing appends per second therefore receives about R notifications per second, and coalescing them is the client's job. Oban's Postgres notifier also de-duplicates before publishing and notes that each notification costs a separate query.

The Elixir EventStore, used by Commanded, shows the opposite, edge-triggered design. An after-update trigger issues one `NOTIFY` per batch of inserted events, carrying the stream id and the from and to versions. A GenStage publisher with `max_demand: 1` reads exactly that range for every notification and broadcasts it to the stream's subscribers. The number of reads grows with the number of commits. A subscriber that falls behind buffers up to `max_size` events (default 1,000), then switches to catch-up mode and reads from storage. The design has one useful property: a single read serves every subscriber of the stream. For a consumer that already keeps a checkpoint, a small or empty payload plus a cumulative read is simpler, and cheaper under bursty load.

### Coalescing: fire on the leading edge, then once on the trailing edge

The established PostgreSQL job queues use the same pattern. River sends every wake-up source through one `fetchLimiter`: insert notifications, ticks of the backstop poll timer, and "fetch again" requests. The limiter is a `DebouncedChan` built with `sendLeading = true` and the `FetchCooldown` period. Its doc comment says it signals at once on the first call, then merges calls made during the cooldown into a single emission at the end of each period, for as long as calls keep arriving. `FetchCooldown` defaults to 100 ms (minimum 1 ms). River describes it as "the minimum amount of time to wait between fetches of new jobs" and warns that "Throughput is limited by this value." Oban's equivalent, `dispatch_cooldown`, defaults to 5 ms (minimum 1 ms), giving per-queue throughput of roughly `(1000 / cooldown) * limit` jobs per second.

Applied to a checkpoint consumer, this throttle gives two bounds at once. The following is inferred from the mechanism:

- **Latency.** An event that arrives while the consumer is idle is read with no added delay. Under sustained traffic an event waits at most one cooldown C for the trailing fire.
- **Read rate.** The consumer makes at most about 1/C notification-driven reads per second, whatever the append rate.

A pure trailing debounce, which waits for W ms of quiet before reading, has the wrong shape. It adds W to every wake-up, including the first one after an idle period. Under a steady stream with gaps shorter than W it never fires at all unless it also has a maximum wait. The "debounce window" for this kind of consumer should therefore be a throttle cooldown, not a quiet-period timer.

Coalescing can also happen at the socket. psycopg 3.2 added `timeout` and `stop_after` parameters to `Connection.notifies()`. After the first notification wakes the consumer, it can drain whatever else is already buffered, using a zero or very short timeout, and set a single dirty flag instead of scheduling one read per notification. `stop_after` may return more notifications than requested when several arrive in one packet; that is harmless if each one only sets the flag. The flag should be cleared before the read starts, not after. A notification that arrives during the read then causes exactly one more read instead of being lost; this is the trailing-edge fire in another form (inference).

**Choosing C.** C trades latency for efficiency. Established libraries range from 5 ms (Oban) to 100 ms (River). For a checkpoint consumer, a read is one indexed range scan. Values near the low end keep latency tight. Raising C matters only when many consumers or processes make the total cost of notification-driven reads significant (inference).

### Draining backlogs without waiting for notifications

A read that returns a full page means more events are probably waiting. River records this case in its comment: "if we fetched the maximum number of jobs on the last attempt, get a little more aggressive triggering the fetch limiter". It still sends the re-fetch through the limiter, so draining a backlog is paced at one fetch per cooldown.

An event-store consumer catching up from its checkpoint should instead read the next page immediately while pages come back full, and go back to waiting only after a short page. The cooldown should pace only notification-driven reads. Unlike job claiming, paging forward from a private checkpoint does not compete with other workers for rows (inference).

Graphile Worker shows the opposite tuning, aimed at large fleets. When a fetch returns fewer jobs than a threshold, its local queue waits a random 0.5 to 1.5 times `refetchDelay.durationMs` (about 100 ms by default) before asking again. It counts new-job notifications during the delay and ends the delay early once a randomly chosen count, capped by `maxAbortThreshold`, has arrived. Its docs say the feature exists because at very high scale "Worker's polling can cause significant load on the database when there are too few jobs in the database to keep all worker pools busy." This is a lever for many-instance deployments; a single in-process consumer rarely needs it.

### The backstop poll: what it bounds and how to keep it from being redundant

Every library examined keeps a periodic poll even when `LISTEN` works:

- **River:** `FetchPollInterval` defaults to 1 s and is described as a fallback. Each interval is randomised to between P and P + max(P/10, 10 ms).
- **Graphile Worker:** `pollInterval` defaults to 2000 ms.
- **Oban:** the stager runs every 1,000 ms. Insert notifications exist so that jobs run immediately rather than "waiting up to the stager's interval".

The backstop sets the worst-case latency for any event whose notification never arrives. That happens when the listener is disconnected or reconnecting, or when notifications are unavailable altogether. Oban notes, for example, that its Postgres notifier does not work behind PgBouncer in transaction or statement pooling mode.

For a checkpoint consumer, the safe read horizon is a second reason the backstop matters:

1. **Positions can commit out of order.** Identity and sequence positions are allocated before commit, so a transaction that commits later can expose a lower position after a reader has already moved past it. Readers therefore avoid reading past any transaction that is still in flight.
2. **The xmin guard blocks on any open transaction.** One published approach stores `pg_current_xact_id()` with each event and reads only rows where `transaction_id < pg_snapshot_xmin(pg_current_snapshot())`. PostgreSQL defines xmin as the "lowest transaction ID that was still active". That covers any transaction holding a transaction id, not only event appenders.
3. **A notification can arrive before its events are readable.** Transaction T's notification can wake the consumer while an older transaction still holds xmin back, so the read finds nothing new from T.
4. **Whether a later notification frees T depends on the blocker.** If the older transaction is itself an appender, its own commit notification triggers the read that releases both. If it is unrelated, such as a write to another table or a long batch job, it sends nothing on the event channel when it ends. T's events then wait for the next backstop poll.

Marten's async daemon, which tracks a high-water mark over gaps in the event sequence, faces the same problem and tunes for it:

- **Adaptive polling.** Its high-water agent polls every 250 ms (`FastPollingTime`) under high activity and every 1 s (`SlowPollingTime`) under low activity.
- **Stale gaps.** It treats a stuck gap as stale after 3 s (`StaleSequenceThreshold`).
- **Live transactions.** Its current docs describe holding the mark while a live transaction could still fill the gap, with a setting that skips such gaps after a bounded time anyway.

The backstop interval P therefore bounds two cases: a lost notification, and a horizon held back by something that will never notify.

Ways to stop the backstop from causing redundant reads (the first point is inferred from River's code):

- **Reset the backstop after every read.** Treat it as an idle timer and reset it whatever triggered the read. Under steady traffic it never fires; when idle it costs one cheap, empty read per consumer per P. River resets its poll timer only when the timer itself fires, so the timer runs independently of notification-driven fetches. Because each tick goes through the same limiter, a tick during a cooldown merges with the pending trailing fire, so River pays at most one extra fetch per P.
- **Jitter P.** River adds up to 10%, and Graphile Worker randomises its refetch delay between 50% and 150%. This stops many consumers or processes from polling in step.
- **Size P for the degraded case, not the normal one.** The 1 to 2 s defaults in River, Oban and Graphile Worker reflect that notifications handle the common case. Shorten P if horizon stalls caused by unrelated transactions are common; each shortening costs one more empty indexed read per consumer per interval when idle.
- **Read immediately after every (re)connect.** Issue `LISTEN` first, then read from the checkpoint unconditionally. Anything committed while the listener was down is then read straight away rather than at the next backstop tick.

### One listener per process, and ignoring your own notifications

Giving every consumer its own `LISTEN` connection multiplies both connections and notification traffic. Production event stores centralise detection instead. Marten's daemon uses one high-water agent whose mark decides how far projections may read. The Elixir EventStore runs one listener and one publisher per event store, reading once and broadcasting to subscribers.

For a Python library, one `LISTEN` connection per process can pass a dirty-flag signal to each consumer's own throttle. Each consumer still coalesces independently, but each process carries only one stream of notifications. Where a single session both appends and listens, the PostgreSQL docs suggest comparing the notifying backend's PID with your own and ignoring matches. This avoids "reading a database table to find the same updates that that session just wrote out".

### How often to persist the checkpoint

Restarts also cause redundant reads: a consumer resumes from its last persisted checkpoint and re-reads everything it processed after that point. The Elixir EventStore offers two settings for this:

- `checkpoint_threshold` (default: write after every acknowledgement) limits checkpoint writes to at most one per N events.
- `checkpoint_after` (in milliseconds) forces a write after a period of inactivity, so a quiet subscription does not keep a stale checkpoint.

A larger N means fewer checkpoint writes but more re-reading and redelivery after a crash, so handlers must be idempotent.

### Putting the numbers together

This model is inferred from the mechanisms above. Let d be the notification transit time, C the cooldown, t_r the read time, and P the backstop interval with jitter fraction j:

- **Normal case:** end-to-end latency is at most d + C + t_r. The first event after an idle period sees about d + t_r.
- **Degraded case** (lost notification, reconnect, or horizon stall): latency is at most P(1 + j) + t_r, plus however long the horizon stays held back.
- **Read rate per consumer:** at most about 1/C under load, plus paging reads while catching up; about 1/P when idle. With an idle-reset backstop, there are no extra backstop reads under load.

Starting points drawn from library defaults: C between 5 and 100 ms, P of about 1 s with about 10% jitter, and a page size large enough that steady-state reads return short pages.
