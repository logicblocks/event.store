# What PostgreSQL-native mechanisms can signal new work to consumers — `LISTEN`/`NOTIFY`, `pg_notify()`, row- versus statement-level trigger-driven notification, and advisory-lock or other wake-up primitives — and how does each work internally, from the notifying transaction's commit to delivery on a listening connection?

## Question

Which mechanisms built into PostgreSQL can tell a consumer that new work exists?
The candidates are asynchronous notifications (`LISTEN`, `NOTIFY`, `pg_notify()`),
notifications fired from row-level or statement-level triggers, advisory locks,
and any other wake-up primitive. For each one, what happens inside the server
between the notifying transaction's commit and the moment a listening client
connection receives the signal?

## Findings

### Overview

PostgreSQL has one purpose-built primitive for signalling between sessions:
**asynchronous notifications** (`LISTEN`, `NOTIFY` and the function
`pg_notify()`). Trigger-driven notification is not a separate mechanism. It is a
way of calling `pg_notify()` automatically from a write, and the choice between
row-level and statement-level triggers changes how many notifications a
transaction queues, not when listeners receive them. **Advisory locks**, like
the server's other heavyweight locks, give you a blocking wait that wakes when
the holder releases the lock. That makes them a mutual-exclusion tool rather
than a signalling channel: a waiter gets no payload, and while it waits its
connection is busy running a statement. **Logical decoding** is the only durable
push stream: changes, plus optional custom messages from
`pg_logical_emit_message()`, are read out of the WAL and streamed through the
replication protocol. psycopg 3 does not support that protocol.

### `LISTEN`, `NOTIFY` and `pg_notify()`: guaranteed semantics

- **Delivery happens at commit.** "If a `NOTIFY` is executed inside a
  transaction, the notify events are not delivered until and unless the
  transaction is committed." `LISTEN` also "takes effect at transaction commit",
  and a rolled-back `LISTEN` changes nothing.
- **Ordering.** Notifications from one transaction arrive in the order they were
  sent. Notifications "from different transactions are delivered in the order in
  which the transactions committed."
- **Deduplication.** Within one transaction, repeated notifications on the same
  channel with an identical payload are delivered once. Different payloads are
  always delivered separately. Notifications "from different transactions will
  never get folded into one notification."
- **Payload.** In the default build the payload must be shorter than 8000 bytes.
  In the source, `NOTIFY_PAYLOAD_MAX_LENGTH` is `BLCKSZ - NAMEDATALEN - 128`, so
  that each message fits on one queue page. The `NOTIFY` command only accepts a
  string literal. `pg_notify(text, text)` is the documented alternative for
  channel names and payloads that are not constants.
- **What the client receives:** the channel name, the server PID of the
  notifying session, and the payload. A session that listens on a channel it
  also notifies gets its own notifications back. It can filter them by
  comparing the PID with its own.
- **Scope and restrictions.** Notifications are local to one database: each
  queued message carries the sender's database OID. A transaction that has
  executed `LISTEN` or `NOTIFY` cannot be prepared for two-phase commit.
- **No durability or replay.** Listen registrations are dropped when the session
  ends. The queue directory `pg_notify/` is wiped at server start ("During start
  or reboot, clean out the pg_notify directory"). A listener only receives
  notifications that commit after its own `LISTEN` has committed. The result is
  at-most-once delivery, and only to sessions connected at the time.
- **Start-up race.** A new listener "will receive all events committed after an
  instant during the transaction's commit step", which is slightly later than
  anything that transaction could have seen in its queries. The documented
  pattern is to commit `LISTEN` first, then read the current state in a new
  transaction, then rely on notifications. The first few notifications may then
  repeat changes already seen, which is harmless.

### Internals: from `NOTIFY` to the wire

The design is described in the header of `src/backend/commands/async.c`.

1. **Inside the notifying transaction.** `Async_Notify()` adds the notification
   to a list held in the backend's own memory, which "will not be processed
   until transaction end". Duplicates are dropped as they arrive: by linear scan
   until the (sub)transaction has `MIN_HASHABLE_NOTIFIES` (16) entries, and by
   hash table after that. When a subtransaction commits, its entries are merged
   into the parent's list, with duplicates removed. When it aborts, its entries
   are discarded.
2. **`PreCommit_Notify()`, before the commit is recorded in clog.** The backend
   takes a heavyweight lock on "database 0", the object shown in lock logs as
   `AccessExclusiveLock on object 0 of class 1262 of database 0` and in
   `pg_stat_activity` as wait event `Lock: object`. It holds the lock "till after
   commit". The purpose is "that queue entries appear in commit order, and in
   particular that there are never uncommitted queue entries ahead of committed
   ones". With the lock held, the backend appends its entries, each tagged with
   database OID, transaction ID, channel and payload, to the head of a single
   cluster-wide SLRU queue. The queue lives on disk under `pg_notify/`, with the
   pages in use cached in shared memory. If the queue is full, the backend
   raises `too many notifications in the NOTIFY queue`. Because this happens
   before the commit is recorded, the transaction can still roll back, which is
   why the documentation says a `NOTIFY` transaction "will fail at commit". If a
   transaction writes entries and then aborts, readers skip those entries
   because the transaction ID never committed.
3. **Commit runs with the lock held.** Writing the commit record and flushing
   the WAL both happen while the lock is held. As a result, every committing
   transaction that has a pending notification is serialised against every
   other one across the whole cluster, in all databases. In a 2019
   pgsql-general report, COMMITs in one database blocked behind a single holder
   of this lock while commits in other databases queued behind it, with up to
   500 waiters. Recall.ai described outages in 2025 with "tens of thousands of
   simultaneous writers": CPU and I/O dropped while hundreds of processes queued
   on the lock. DBOS adds that because the lock is held through `fsync()`,
   these commits cannot share a WAL flush through group commit. They report
   going from 2.9K to 60K writes per second by buffering notifications in
   memory and sending them in periodic batched transactions, with polling as a
   fallback. In a July 2025 pgsql-hackers thread on optional out-of-order
   `NOTIFY`, Joel Jacobson argued that the dominant cost in benchmarks with both
   `LISTEN` and `NOTIFY` was wake-up syscalls, and that the lock would be the
   next bottleneck. The PostgreSQL 19 release notes contain no change to the
   commit lock, so it is still present in 19.
4. **`AtCommit_Notify()` and `SignalBackends()`, after commit.** The backend
   applies any pending `LISTEN` or `UNLISTEN` changes, then releases
   `NotifyQueueLock` and wakes listeners with
   `SendProcSignal(pid, PROCSIG_NOTIFY_INTERRUPT, …)`. Who gets woken depends on
   the version:
   - **PostgreSQL 18 and earlier.** The backend signals *every* listening
     backend in its own database that has not already caught up, whatever
     channel it listens on. It also signals listeners in other databases that
     are at least `QUEUE_CLEANUP_DELAY` pages behind, so that their queue
     pointers move forward and the global tail can advance.
   - **PostgreSQL 19, in beta (Beta 4 released 24 September 2026).** Commit
     `282b1cde9` (Joel Jacobson, January 2026) adds a shared hash table that maps
     each (database OID, channel name) pair to the backends listening on it.
     Only listeners on the affected channels are signalled, plus idle listeners
     that have fallen far behind. A listener with no interest in the new
     messages that is sitting at the old queue head has its pointer moved past
     them without being woken. The commit reports "integer multiples" more
     `NOTIFY` throughput, and lower latency, when there are many listeners and
     few are interested in each message. It reports no gain when every listener
     reads every message. A May 2026 follow-up fixed a race in which a listener
     whose `LISTEN` had not yet committed could be advanced past messages meant
     for it.
5. **On the listening backend.** The signal handler sets the process latch. If
   the backend is idle, meaning it is waiting for a client command and not
   inside a transaction block, it handles the notifications straight away.
   Otherwise the handler only sets a flag, and the work happens "just before we
   next go idle". `asyncQueueReadAllNotifications()` takes a snapshot and scans
   forward from the backend's queue position. For each entry it tests
   `XidInMVCCSnapshot` *before* `TransactionIdDidCommit`, "else we might return a
   message from a transaction that is not yet visible to snapshots". When it
   reaches an entry from a transaction still in progress, it stops and backs up
   so the entry is read again next time. It then filters entries by database
   OID and by its own channel list (a linear list search in PostgreSQL 18; a
   per-backend hash table in 19). A useful consequence: by the time a client
   receives a notification, the notifying transaction's writes are visible to
   any snapshot taken afterwards, so a consumer can query for the new rows as
   soon as it wakes.
6. **On the wire and in the client.** Each notification is sent as a protocol
   `NotificationResponse` message. "At present, NotificationResponse can only be
   sent outside a transaction", and it can arrive just before `ReadyForQuery`.
   The protocol documentation still advises clients to accept it at any point.
   A listener that keeps a transaction open therefore receives nothing until the
   transaction ends. In libpq the client waits on `PQsocket()` with `select()`,
   then calls `PQconsumeInput()` and `PQnotifies()`. This uses no CPU while
   idle; `PQnotifies()` itself never reads from the socket. psycopg 3 recommends
   autocommit mode on any connection that sends or receives notifications. It
   offers two ways to receive them:
   - The `Connection.notifies()` or `AsyncConnection.notifies()` generator. The
     `timeout` and `stop_after` parameters were added in 3.2, and `stop_after`
     can be exceeded when several notifications arrive in one packet. Since
     3.2.4 the generator also captures notifications that arrive between uses,
     with a documented memory leak if it is not consumed regularly.
   - `add_notify_handler()` callbacks. These only fire "during a connection
     operation, such as a query". Since 3.2.10, using both styles on one
     connection raises a warning.
7. **Queue maintenance.** The queue tail is the smallest position held by any
   listener. Sending backends try to advance it and truncate old segments once
   every `QUEUE_CLEANUP_DELAY` pages. A new listener starts at the furthest
   position held by any other listener in its database, because everything
   before that is "surely committed". A listener that sits in a long-running
   transaction stops cleanup entirely. The server logs warnings that name the
   blocking session once the queue is half full, and `NOTIFY` commits fail once
   it is full. The queue size is set by `max_notify_queue_pages`, which is
   documented from PostgreSQL 17, defaults to 1048576 pages (8 GB with 8 kB
   pages) and can only be set at server start. Current usage is reported by
   `pg_notification_queue_usage()`. The LWLock wait events `NotifyQueue`,
   `NotifyQueueTail`, `NotifySLRU` and `NotifyBuffer` show contention inside the
   queue.

### Trigger-driven notification: row-level versus statement-level

A trigger function calls `pg_notify()`. The notification joins the
transaction's pending list and goes through the commit path described above. So
trigger timing decides how many entries are queued and what they contain, never
when listeners see them. Any trigger like this also means *every* transaction
that writes to the table takes the commit-time lock. A FOSDEM PGDay 2026 talk
(Jimmy Angelakos) is built around how "a simple trigger could bring our
database to a crawl".

- **`FOR EACH ROW`** runs "once for every row that the operation modifies".
  Row-level `AFTER` triggers are queued and fire at the end of the statement,
  before any statement-level `AFTER` triggers. A payload that differs per row,
  such as a row ID or position, queues one entry per row, and every listener
  receives each one. A payload that is constant, or set per stream or
  category, collapses to one notification per distinct value per transaction
  because of the deduplication rule. A `WHEN` condition on an `AFTER` row
  trigger avoids queuing the trigger event at all for rows that do not match.
- **`FOR EACH STATEMENT`** runs once per statement "regardless of how many rows
  it modifies". It also runs when a statement modifies zero rows, so it fires
  spurious notifications unless the function checks for this. On an `AFTER`
  trigger on a plain table, `REFERENCING NEW TABLE AS …` (or `OLD TABLE`)
  exposes the whole set of changed rows. One notification can then summarise
  the statement, for example the highest new position or the distinct stream
  names, and can be skipped when the set is empty. Restrictions: transition
  tables cannot be combined with an `UPDATE OF column` list or used on
  constraint triggers, and row-level triggers with transition relations cannot
  be defined on partitions or inheritance children. `TRUNCATE` triggers exist
  only at statement level.
- **Deferred constraint triggers** (`DEFERRABLE INITIALLY DEFERRED`, which must
  be `AFTER ROW`) fire at the end of the transaction rather than the end of the
  statement. They are still row-level, and the notification is still sent at
  commit.

### Advisory locks and other wake-up primitives

- **Advisory locks.** `pg_advisory_lock()` and `pg_advisory_xact_lock()` (and
  their shared variants) obtain the lock "waiting if necessary". The
  `pg_try_…` variants never wait. A waiter sleeps in the heavyweight lock
  manager (wait event `Lock: advisory`). `ProcSleep` "returns after the lock has
  been granted, or if a deadlock is detected", and the deadlock check runs after
  `deadlock_timeout`. When the holder releases the lock, `ProcLockWakeup` scans
  the wait queue and wakes every waiter that is no longer blocked, by setting
  its latch through `ProcWakeup`. A transaction-level lock is released when its
  transaction ends. A session-level lock ignores rollback and is held until it
  is explicitly unlocked or the session ends. Session-level locks are
  re-entrant, and each acquisition needs a matching unlock. All of these locks
  share a lock table sized by `max_locks_per_transaction` × `max_connections`,
  and `lock_timeout` applies to them.

  As a way to signal new work, an advisory lock has clear limits:
  - A wake-up carries no payload. It only grants a lock, one waiter at a time
    for an exclusive lock.
  - The waiting connection is running a statement. Because notifications are
    only delivered to idle sessions, that connection cannot receive
    notifications while it waits.
  - Each wake-up means re-acquiring a lock.

  The documented uses are mutual exclusion and coordination: application-defined
  locks that "block each other in the expected way". For consumers that makes
  advisory locks a complement to `LISTEN`, for example a
  `pg_try_advisory_lock()` that guarantees a single active consumer per
  subscription, rather than a replacement for it. This assessment is an
  inference from the documented behaviour; the sources do not state it.
- **Logical decoding and replication slots.** Logical decoding turns WAL into a
  stream of changes in the order "they were made on the origin server". A slot
  "will emit each change just once in normal operation", and slots survive
  crashes. Through the streaming replication protocol, the walsender pushes
  changes to the client. The SQL functions, such as
  `pg_logical_slot_get_changes()`, are a pull interface.
  `pg_logical_emit_message(transactional, prefix, content [, flush])` writes a
  custom message into the WAL, either as part of the current transaction or
  immediately. This gives a durable equivalent of `NOTIFY` that a decoder can
  pick out by its prefix. The costs: a slot keeps WAL and catalog rows from
  being removed even when no consumer is connected, and "in extreme cases this
  could cause the database to shut down to prevent transaction ID wraparound".
  psycopg 3 has no replication-protocol support. Issue #71 ("Add support for
  streaming replication as in psycopg2") has been open since August 2021, so a
  psycopg 3 consumer cannot use the push interface directly.
- **The `WAIT` command, new in PostgreSQL 19.** It lets a *standby* wait until a
  given LSN has been written, flushed or replayed. It supports read-your-writes
  on replicas and is not a general way to signal new work.

### Comparison

| Mechanism | Payload | Survives disconnect or restart | Cost on the writer | Wake-up target | psycopg 3 |
|---|---|---|---|---|---|
| `LISTEN` and `NOTIFY` (`pg_notify()`) | text under 8000 bytes | No (at-most-once) | Cluster-wide commit lock held through the WAL flush | PG 18 and earlier: all listeners in the database; PG 19: listeners on the channel | `notifies()` generator or handlers |
| Row-level trigger plus `pg_notify()` | per row, deduplicated within a transaction | No | Commit lock on every writing transaction, plus one entry per distinct payload | as above | as above |
| Statement-level trigger plus `pg_notify()` | per statement; transition tables allow a summary | No | Commit lock on every writing transaction; fires even when zero rows change | as above | as above |
| Advisory lock wait | none | n/a | Holding and releasing a lock | waiters whose request can now be granted | ordinary SQL (blocking statement) |
| Logical decoding (slot plus `pg_logical_emit_message()`) | full changes or custom messages | Yes (slot persists) | WAL volume; retained WAL and catalog rows | the slot's consumer | not supported |
