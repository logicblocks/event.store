# How can an event-store consumer that reads by global sequence number combine LISTEN and NOTIFY wake-ups with gap detection so that events committed out of sequence order are never skipped?

## Question

A consumer reads events by global sequence number and gets woken by LISTEN and NOTIFY. How can it also detect gaps in the sequence so that it never skips an event whose transaction commits after an event with a higher number?

## Findings

### Why the problem exists, and why NOTIFY does not solve it

PostgreSQL hands out sequence values when `nextval` runs, not when the transaction commits. A value is never given back if the transaction aborts. The documentation says this means "transaction aborts or database crashes can result in gaps", that gaps can appear even without an abort (for example `INSERT ... ON CONFLICT` calls `nextval` before it detects the conflict), and that sequences "cannot be used to obtain 'gapless' sequences". Two concurrent appenders can therefore commit in the opposite order to the numbers they took. If transaction #2 starts after #1 but commits first, a processor can read #2's events, record #2's position as its checkpoint, "and thus lose the events created by transaction #1" (eugene-khyst). A reader that finds a hole also cannot tell whether a rollback or a slow, still-running transaction caused it. Oskar Dudycz puts it this way: "If we optimistically assume that the gaps were caused by rollbacks, we may lose messages."

LISTEN and NOTIFY have three properties that matter here:

- NOTIFY events are delivered only "until and unless the transaction is committed". An aborted append never sends a notification.
- Messages "from different transactions are delivered in the order in which the transactions committed". A notification can therefore carry a *lower* position than one that arrived before it.
- A session receives "all events committed after an instant during the transaction's commit step" of its LISTEN. The documented rule is to commit LISTEN first, then inspect database state in a new transaction, then rely on notifications. The first few notifications may repeat what the initial read already saw, which is "usually harmless".

So a notification tells the consumer that something committed. It cannot tell the consumer that everything below a given position has committed. The safety guarantee has to come from the read query and the checkpoint rule. The notification only decides when the next read happens.

### Four ways to make the read safe

**1. Make commit order equal sequence order by serialising appends.** If appends cannot interleave, a plain `position > checkpoint` read is safe, and a notification payload can carry the position.
- The Python `eventsourcing` library's PostgreSQL recorder takes an `EXCLUSIVE` table lock when it inserts events. The library says this "avoids a potential issue where insert order and commit order are not the same" and prevents readers "tailing the application notification log" from missing notifications. A `POSTGRES_LOCK_TIMEOUT` setting is optional and defaults to no timeout.
- Commanded's Elixir EventStore gets the same effect a different way. Each append runs `UPDATE streams SET stream_version = stream_version + n WHERE stream_id = 0` and links the new events to the `$all` stream from the version that update returns. The row lock on the `$all` counter row is held until commit, which serialises global numbering.
- Sequin describes a variant that uses a counter table. It also suggests assigning the number at the end of the transaction so the lock is held for less time.

The cost is that all appends are serialised.

**2. Filter by the transaction-snapshot horizon (xid8).** Each event row stores `pg_current_xact_id()`, a 64-bit `xid8` that "does not wrap around during the life of an installation". The reader only reads rows whose transaction ID is below `pg_snapshot_xmin(pg_current_snapshot())`. PostgreSQL defines snapshot `xmin` as the "lowest transaction ID that was still active", and says all IDs below it "are either committed and visible, or rolled back and dead". The reference query, from eugene-khyst, is:

```sql
WHERE (e.TRANSACTION_ID, e.ID) > (:lastProcessedTransactionId::xid8, :lastProcessedEventId)
  AND e.TRANSACTION_ID < pg_snapshot_xmin(pg_current_snapshot())
ORDER BY e.TRANSACTION_ID ASC, e.ID ASC
```

Oskar Dudycz uses the same query. The checkpoint stores both the last transaction ID and the last event ID. This is what makes the scheme safe. Transaction IDs are assigned at a transaction's first write, which is not necessarily when it calls `nextval`. So a transaction with a lower xid can hold a higher position than one with a higher xid that is still running. Ordering and checkpointing by position alone, even with the xmin filter, could still skip the lower position (this follows from the documented semantics of `pg_current_xact_id`). The ordering therefore changes from position order to the order of "when their transaction *started*" (Dudycz). The main drawback is that "any long-running transaction in your system will set a ceiling" (Sequin), including unrelated ones. Events are delayed, never lost.

**3. Detect gaps by position and resolve them by time or by transaction evidence.** This keeps position ordering.
- Axon Framework's `GapAwareTrackingToken` stores the highest index seen "and additionally stores a set of possible gaps". Each fetch re-queries the gap positions as well as the range after the index.
- In Axon's JDBC engine, gaps more than `maxGapOffset` (default 10,000) behind the head are dropped. Gaps around events older than `gapTimeout` (default 60 s) stop being tracked. Clean-up runs once a token holds `gapCleaningThreshold` (default 250) gaps. An `extendedGapCheckEnabled` query also catches holes larger than one batch.
- Marten's async daemon keeps a contiguous "high water mark", "the point below which the daemon knows every event is committed and safely ordered". It stops at any hole. Current documentation says it skips a hole only when no running transaction could have reserved those numbers: it "rules out any session that has provably executed nothing since before the gap's sequence numbers were handed out". There is a time-based escape hatch, `SkipStaleGapsDespiteLiveTransactionsAfter`, which knowingly gives up the guarantee.
- Marten also cuts down on gaps at the source. Failed appends write "tombstone" rows into the sequence numbers they reserved, and its `QuickAppend` mode is "substantially less likely to lead to gaps".

A purely time-based timeout like Axon's can skip a transaction that is live but slower than the timeout.

**4. Writers announce their reserved range.** This is Sequin's recommended scheme. Each writer takes a shared advisory lock (`classid = 1`) to mark itself as an appender, plus an exclusive advisory lock whose `objid` is the next sequence value. The reader's safe ceiling is `min(objid)` over these locks in `pg_locks`. When no writer holds a lock, it reads everything. Appends stay concurrent, ordering stays by position, and the reader is not held back by unrelated long transactions.

### Wiring the wake-ups to the safe read

These sources point to one loop that works whichever strategy is chosen:

1. Commit `LISTEN` on a dedicated connection, then run a catch-up read from the stored checkpoint (the PostgreSQL rule above).
2. Treat every notification as a coalescible hint and run the same safe read until it returns nothing. Never move the checkpoint to a position taken from a notification payload. Under strategies 2 to 4 the payload can name events the read is not yet allowed to return.
3. When a read is held back, arm a short re-check timer, because the event that unblocks the reader may never send a notification. A read is held back when a hole is waiting (strategy 3), rows exist above the xmin horizon (strategy 2), or a writer's lock is lowering the ceiling (strategy 4). The unblocking event may never notify because aborted transactions do not notify, gap timeouts are measured in time, and the long transaction holding back `xmin` may not append events at all.
4. Keep a slow fallback poll for notifications that are missed or lost.

The eugene-khyst project offers LISTEN and NOTIFY "instead of polling" as a mutually exclusive mode. In that design a held-back read waits for the next append's notification. That delays events but does not lose them. The re-check timer in step 3 closes that latency hole.
