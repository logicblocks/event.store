# Which notification strategies, such as batched notifier transactions, statement-level triggers or a dedicated notifier process, most reduce commit serialisation from the NOTIFY lock on an event store's append path under concurrent writers?

## Question

When many writers append to a PostgreSQL-backed event store at once, and each append signals consumers with `NOTIFY`, the commit-time NOTIFY lock serialises those commits. Which ways of issuing notifications do the most to reduce that serialisation: batching notifications into separate notifier transactions, using statement-level triggers instead of row-level ones, or running a dedicated notifier process?

## Findings

### Where the serialisation comes from

The cause is a lock in PostgreSQL's `async.c`. `PreCommit_Notify()` returns straight away if a transaction has no pending LISTEN actions and no pending notifications. Otherwise, inside an `if (pendingNotifies)` block, it assigns the transaction an XID and calls `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)`. The source comment explains why: "Serialize writers by acquiring a special lock that we hold till after commit. This ensures that queue entries appear in commit order, and in particular that there are never uncommitted queue entries ahead of committed ones." The file header says that "all writers serialize on a cluster-wide heavyweight lock". It is a lock on a shared object (database 0), so notifying transactions in every database on the instance compete for it. Recall.ai's logs show it as "AccessExclusiveLock on object 0 of class 1262 of database 0".

`CommitTransaction()` in `xact.c` sets how long the lock is held. It runs `PreCommit_Notify()`, then `RecordTransactionCommit()`, then `ProcArrayEndTransaction()`, then the release of heavyweight locks, and only then `AtCommit_Notify()`, which signals listeners. `RecordTransactionCommit()` is where `XLogFlush` runs when `synchronous_commit` is on, and where `SyncRepWaitForLSN` waits for synchronous standbys. So the lock covers the notifier's queue insertion, its commit record, its WAL flush and any wait for a replica. DBOS notes that this rules out group commit: "stream writes need to commit sequentially". Their first implementation topped out at about 2.9K stream writes per second without CPU, memory or IOPS ever becoming the limit. That works out to roughly 0.35 ms per serialised commit. Recall.ai's production symptoms looked the same: hundreds of sessions queued behind one lock holder, database load rising, and CPU, disk and network all falling.

Two consequences decide which strategies work:

1. **The unit of serialisation is the notifying transaction, not the notification.** A transaction that issues one NOTIFY or a thousand takes the lock once. A transaction that issues none never takes it.
2. **Hold time is the in-lock work plus the commit's durability wait.** A strategy can therefore help in one of two ways: reduce how many transactions on the append path carry a notification, or shorten how long each one holds the lock.

### Statement-level triggers and other "fewer NOTIFYs per transaction" techniques

The PostgreSQL docs recommend putting `NOTIFY` in a statement trigger so that applications cannot forget to send it. `FOR EACH STATEMENT` is the default when `CREATE TRIGGER` names neither level. PgQueuer, a Python queue, follows this pattern: it renders `AFTER INSERT OR UPDATE OR DELETE OR TRUNCATE` with no row clause, so its trigger runs at statement level. Commanded's Elixir EventStore gets a similar effect differently. Its `FOR EACH ROW` trigger sits on the `streams` table rather than the events table, so each append sends one notification per stream row touched, with the payload `stream_uuid,stream_id,first_version,last_version`, however many events were written.

PostgreSQL already sends "only one instance" of identical channel-and-payload notifications from one transaction. A row-level trigger with a constant payload therefore collapses to the same single queue entry as a statement-level one. These techniques do reduce queue volume and the insertion work done while the lock is held. That matters most for row-level triggers that put a distinct value, such as the event position, in every payload, because that defeats deduplication.

What they cannot do is reduce lock acquisitions. Every appending transaction still has a pending notification, so every append commit still takes the lock for its whole commit. Under concurrent single-batch appends, the usual event-store pattern, the gain is close to zero. One extra caution: a statement-level trigger also fires for statements that change zero rows, so an unguarded trigger can make no-op statements take the lock too.

### Throttled in-transaction notification

Throttling keeps NOTIFY inside the writer's transaction but skips it most of the time. Transactions that skip it never take the lock.

- **River (Go)** calls `insertNotifyLimiter.ShouldTrigger(queue)`, an in-memory limiter set to `FetchCooldown` (100 ms by default). It collects the queues that pass into one `NotifyMany` call inside the insert transaction.
- **pgmq** keeps throttle state in an unlogged table. Its trigger runs `UPDATE ... SET last_notified_at = clock_timestamp() WHERE ... clock_timestamp() - last_notified_at >= throttle_interval_ms` (default 250 ms in `enable_notify_insert`) and calls `pg_notify` only if a row was updated.

This caps notifying commits at about one per interval for each limiter scope: per process per queue for River, per queue across the whole database for pgmq. It has two costs:

- **Lost wake-ups.** An append that commits inside the window is never announced, so consumers need a fallback poll. River documents its `FetchPollInterval` fallback and a `PollOnly` mode.
- **A possible new hot spot (my inference, not documented by pgmq).** With a shared throttle row, a concurrent writer whose `UPDATE` reaches the row while the notifying transaction still holds its row lock must wait for that transaction to commit. That transaction is the one holding the NOTIFY lock, so in bursts the throttle can swap NOTIFY-lock waits for row-lock waits. An in-process limiter like River's avoids this, but its cap grows with the number of writer processes.

### Batched notifier transactions in the writer process

DBOS took NOTIFY out of the write transactions altogether. They start from the point that "notifications aren't themselves a source of truth"; they only tell a reader to check a table. So they buffer notifications in memory and periodically flush them "in a single batch transaction". After that, "the global lock only needs to be taken when the buffer is flushed, not for each individual stream write". Throughput went from about 2.9K to about 60K writes per second (roughly 20x) at 15–100 ms latency. At the peak, Postgres CPU was fully used, so the lock had stopped being the limit.

The flush happens after the data commits, so a consumer that wakes up always finds the data committed. A crash can lose buffered notifications, which DBOS covers with an infrequent fallback poll. With this design, notifying transactions scale with the number of processes multiplied by the flush rate, not with the number of appends.

### Dedicated notifier or detector process

A further step leaves the append path with no notification work at all. One session detects newly committed events and wakes everyone else.

- **Marten (.NET).** Marten's async daemon does this without LISTEN/NOTIFY. A single elected leader runs a "high water mark" agent that polls for the highest event sequence that is safe to process, and it handles sequence gaps from uncommitted or rolled-back appends.
- **NOTIFY variant.** One notifier session polls the log head and issues one NOTIFY per batch of new positions to listeners in other processes. Only that session ever takes the lock, so writers never contend for it.
- **Logical decoding variant.** The notifier can read committed changes from a replication slot instead of polling. The PostgreSQL docs warn that slots "will prevent removal of required resources even when there is no connection using them", so an abandoned slot retains WAL indefinitely.

The costs are detection latency (the poll interval or decoding lag), a single point of failure that needs leader election, and the gap-detection logic Marten documents. Oban, as a related precedent, ships non-Postgres notifiers (Erlang distribution and Phoenix PubSub). Its docs say the Postgres notifier is the only one that is transactionally consistent, but "it is not as scalable as other notifiers".

### Shortening each hold

`XLogFlush` and `SyncRepWaitForLSN` both run inside the lock window. The docs allow `SET LOCAL synchronous_commit TO OFF` for a single transaction, and in that mode "there is no waiting". So a notify-only flush transaction from either of the previous two strategies could be committed asynchronously and hold the lock only for the in-lock work. Its data was already committed durably by the writers. None of the sources benchmarks this; it follows from the commit sequence in the source code. The same setting is not appropriate for writer transactions that carry event data, because it opens a window in which acknowledged commits can be lost. Small, constant payloads also keep the in-lock queue insertion short.

### Upstream changes

- **Shared channel map and direct advancement (commit `282b1cde`, 15 January 2026).** Authored by Joel Jacobson and reviewed by Tom Lane, this commit adds a shared map of which processes listen to which channels. It skips waking listeners that are not interested, and directly advances their queue position instead. It gives "integer multiples" of throughput when many listeners each care about only a few messages, but "no improvement for the simplest case where every listener reads every message".
  - Current `async.c` still takes the lock and holds it "till after commit".
  - Recall.ai's May 2026 update says this commit "eliminated the bottleneck". DBOS says the Postgres 19 patch "addresses a narrower scenario" and leaves the core problem in place.
  - A plausible way to reconcile these: Recall.ai had very many listeners on distinct channels, and the waiting may have been made worse by woken listeners competing for `NotifyQueueLock`. In 2019 Martijn van Oosterhout found that most of the time in a similar case went to listening backends holding the queue lock.
  - For an event store whose consumers mostly listen on the same few channels, this commit does not remove the serialisation between writers.
- **Writing notifications through WAL (Rishu Bagga, from September 2025).** This patch puts notification payloads in WAL and writes compact queue entries, which removes the global lock held from `PreCommit_Notify` to the end of the transaction. Results: 60–70K TPS against about 30K on `pgbench -c 100`, and 30–40x on a reviewer's insert-with-notify benchmark. At its last recorded activity (v9, November 2025) it was marked "Needs review" in the PG19-4 commitfest, and it is not in the current source. Tom Lane has explained that the lock guarantees "no other would-be notifier can insert any messages in between ours", and other parts of the design depend on that.

### Ranking for an event store's append path

From most to least reduction in writer commit serialisation:

1. **Dedicated notifier or detector process.** No writer transaction ever takes the lock. The cost is detection latency and running a leader.
2. **Batched notifier transactions in each writer process (DBOS).** The lock is taken once per flush interval per process, with a measured 20x gain. The cost is tens of milliseconds of added latency.
3. **Throttled in-transaction notification (River, pgmq).** One notifying commit per window per scope. The notifications that are sent still commit atomically with their data. Appends inside the window get no wake-up, and a database-side throttle row can become a new contention point.
4. **Statement-level or summary-row triggers.** Little benefit for concurrent appends: every append still takes the lock. They mainly cut queue volume and in-lock insertion work.

Strategies 1–3 all lose or delay some notifications, so consumers need a fallback poll whichever one is chosen; both DBOS and River pair push with periodic polling.

For a psycopg 3 library, the pattern most directly supported by these sources has four parts:

- The append transaction commits without any NOTIFY.
- A post-commit hook marks the affected channel as dirty in an in-process coalescer.
- A background task on its own connection sends `pg_notify` for all dirty channels in one transaction every few tens of milliseconds, optionally committed with `synchronous_commit` off.
- Consumers treat notifications as hints and keep a slower safety poll.
