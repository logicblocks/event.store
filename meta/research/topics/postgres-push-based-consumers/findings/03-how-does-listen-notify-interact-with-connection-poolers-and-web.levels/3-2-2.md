# Can the AWS Advanced Python Wrapper failover plugin manage a psycopg 3 connection that is blocked waiting in notifies(), and how does it surface a completed failover to such a listener?

## Question

When a psycopg 3 connection opened through the AWS Advanced Python Wrapper is
parked in `Connection.notifies()` as a dedicated `LISTEN` connection, does the
wrapper's failover machinery (the `failover` / `failover_v2` plugins, plus the
host-monitoring plugins that feed them) notice and handle a writer failure on
that connection? And once the wrapper has failed over, how does a listener
learn about it?

## Findings

### Short answer

No — not while it is blocked. `notifies()` never goes through the wrapper's
plugin pipeline, so neither failover nor Enhanced Failure Monitoring (EFM)
watches a connection that is waiting for notifications. A blocked listener sees
one of two things. Either psycopg raises its own raw `OperationalError` when
the server closes the socket, or the listener stays blocked until TCP
keepalives or a `notifies(timeout=...)` deadline fire.

The wrapper reports a failover only on the listener's **next call that goes
through the pipeline**, such as `execute`, `cursor`, `commit` or `rollback`.
That call:

- makes the wrapper classify the dead connection as a network error;
- makes the wrapper swap a new physical connection into the same wrapper
  object;
- raises `FailoverSuccessError`. It raises `TransactionResolutionUnknownError`
  instead if the connection was in a transaction, and `FailoverFailedError` if
  no new connection could be made.

The new connection has no `LISTEN` registrations and no notify handlers. The
listener must register both again and catch up from durable storage.

None of this is documented by the wrapper project. The project's issue tracker
has no issues about `LISTEN`, `NOTIFY` or `notifies()`. The conclusions below
come from reading the wrapper's source code (version 3.1.0, released
2026-08-24, main branch) and psycopg 3's source code.

### Why notifies() bypasses the plugin pipeline

`AwsWrapperConnection` defines a fixed set of methods that it routes through
its plugin manager:

- `commit`, `rollback`, `close` and `cursor`;
- the `autocommit` and `read_only` properties;
- the two-phase-commit (`tpc_*`) methods;
- a psycopg-specific `execute()`, which creates a wrapper cursor so that the
  plugin chain still runs.

Any other attribute is passed straight to the underlying driver connection:

```python
def __getattr__(self, name: str) -> Any:
    if name == "_plugin_service" or name.startswith("__"):
        raise AttributeError(name)
    return getattr(self.target_connection, name)
```

Here `target_connection` is `self._plugin_service.current_connection`. The
wrapper does not define `notifies`, so `conn.notifies()` finds the bound method
of whichever `psycopg.Connection` is current at that moment and calls it
directly. `add_notify_handler` is resolved the same way.

The failover plugins and the host-monitoring plugins (v1 and v2) only run for
the methods they subscribe to:

- `connect`;
- the internal host-list and connection-changed events;
- the driver dialect's *network-bound methods*.

For psycopg, the network-bound methods are:

- `Connection.commit`, `rollback`, `close` and `cursor`;
- the autocommit and read-only getters and setters;
- `Cursor.close`, `callproc`, `execute`, `fetchone`, `fetchmany` and `fetchall`.

`notifies` is not in this set. Nothing in the psycopg driver dialect mentions
notifications at all.

The asyncio wrapper added in 3.1.0 (`AsyncAwsWrapperConnection`, backed by
psycopg's `AsyncConnection`) has the same design. Its `__getattr__` "proxies
unknown attributes to the underlying connection", and it has no notification
handling of its own.

### What a blocked listener actually sees during a failover

psycopg's `notifies()` holds the connection lock for its whole life. It loops
on `self.wait(notifies(self.pgconn), timeout=remaining)`, and the inner
generator waits until the socket is readable and then calls
`pgconn.consume_input()`. There are two cases:

- **The old writer closes the socket.** This is the usual case when the
  instance is rebooted or demoted. `PQconsumeInput` fails, and psycopg raises
  `psycopg.OperationalError("consuming input failed: ...")` directly from the
  generator. The wrapper never sees this exception. No failover starts, and no
  `FailoverSuccessError` is raised from `notifies()` itself. The psycopg
  connection is left in libpq status `BAD`, so `conn.closed` (passed straight
  through) returns `True`.
- **The host disappears without closing the socket.** The listener stays
  blocked. EFM is no help here: its monitoring context is started only around
  a call that goes through the pipeline. Its probes start
  `failure_detection_time_ms` (default 30 000 ms) after that call is sent,
  repeat every 5 000 ms, and give up after 3 failures. A listener waiting in
  `notifies()` is never inside such a call. The only bounds are:
  - libpq TCP keepalives — the psycopg dialect passes `keepalives`,
    `keepalives_idle`, `keepalives_interval` and `keepalives_count` through to
    libpq;
  - a `timeout` argument to `notifies()`, after which the application regains
    control.

### How the completed failover then surfaces

Suppose the listener now calls a method that goes through the pipeline, for
example `conn.execute("LISTEN events")` or `conn.execute("SELECT 1")`.
`execute` calls `cursor()`, and psycopg's `_check_connection_ok()` raises
`OperationalError("the connection is closed")` on a `BAD` connection.

The psycopg exception handler in the wrapper counts this as a network error.
Its message list is "connection failed", "consuming input failed",
"connection socket closed" and "the connection is closed". It also matches
SQLSTATE classes `08`, `53`, `57P01` to `57P03`, `58`, `99`, `F0` and `XX`.

The `failover_v2` plugin, which is in the default plugin chain, then:

1. invalidates (closes) the current connection;
2. marks the host unavailable;
3. picks a new connection using the cluster topology;
4. raises one of:
   - `FailoverSuccessError` — failed over successfully outside a transaction;
   - `TransactionResolutionUnknownError` — failed over successfully during a
     transaction;
   - `FailoverFailedError` — no new connection within `failover_timeout_sec`
     (default 300 s; the project's "aggressive" example uses 30 s).

The failover documentation says that the wrapper "internally establishes a
ready-to-use connection inside the original Connection object before throwing
an exception". It tells applications to reuse and reconfigure that object,
recreate their cursors, and repeat the query that failed. Discarding the
object throws away the fast failover. The statement that triggered the failover
did **not** run, so a `LISTEN` sent this way has to be sent again.

### What the new connection does not have

The wrapper transfers a small amount of session state on a switch:

- The documentation lists `autocommit` and `read_only`.
- The psycopg dialect's `transfer_session_state` also copies
  `isolation_level`.

Everything else about the backend session is lost:

- **`LISTEN` registrations.** These belong to the server session, which no
  longer exists.
- **Callbacks registered with `conn.add_notify_handler(...)`.** Through
  `__getattr__` these were attached to the *old* `psycopg.Connection` object.
  The new physical connection has none.
- **Any `notifies()` generator obtained before the failover.** It stays bound
  to the old, dead connection. A fresh call to `conn.notifies()` resolves to
  the new connection.

There is a hook for this: `SessionStateTransferHandlers.set_transfer_session_state_on_switch_func`.
It sets a process-wide callback that is called as
`func(session_state, new_connection)`, and returning `True` skips the default
transfer. In principle it could issue `LISTEN` on the new connection during the
switch. However:

- it applies to every wrapper connection in the process;
- it receives only the driver connection, not the wrapper;
- nothing in the project's documentation covers using it for `LISTEN`.

The safer choice is to register again explicitly after catching
`FailoverSuccessError`.

### Interference from other connections in the same process

`aurora_connection_tracker` is also in the default chain. It records every
driver connection it opens in a set shared by all connections in the process,
keyed by instance endpoint. When any connection detects that the writer has
changed, the plugin closes every tracked connection to the old writer. It does
this from a daemon thread, calling `invalidate()` if available and `close()`
otherwise.

psycopg's `close()` does not take the connection lock. It sets `_closed` and
calls `pgconn.finish()`. So the listener's socket may be closed by another
thread while `notifies()` is waiting on it. Neither project documents whether
this reliably and promptly wakes the waiting thread, so do not rely on it.

### Practical consequences for an event-store listener

- **Keep the listener on the writer.** `failover_mode` defaults to
  `strict_writer` except when connecting through an Aurora reader endpoint,
  where it is `reader_or_writer`. PostgreSQL rejects `LISTEN` and `NOTIFY` on a
  hot standby, so a listener moved to a reader cannot register.
- **Plain RDS instances are not covered.** The wrapper documents failover and
  EFM as incompatible with plain (non-cluster) RDS databases. Only Aurora and
  RDS Multi-AZ DB clusters are covered.
- **Use a heartbeat and a recovery loop.** Treat the wrapper as a fast way to
  reconnect, not as something that watches the listener. A pattern consistent
  with the code above:
  1. Loop on `conn.notifies(timeout=heartbeat)`.
  2. Between windows, run a cheap query through the wrapper, which is covered
     by EFM and failover.
  3. If either step raises (a raw `psycopg.OperationalError` from
     `notifies()`, or a wrapper error from the heartbeat), call a method that
     goes through the pipeline until it raises `FailoverSuccessError` or
     `FailoverFailedError`.
  4. After a successful failover, on the same wrapper object: issue `LISTEN`
     again, register handlers again, run a catch-up read from the consumer's
     durable position, then call `notifies()` again.
- **Catch-up is mandatory.** Notifications committed on the old writer but not
  delivered, and any sent before `LISTEN` is registered again, are gone.
  `NOTIFY` has no replay.
