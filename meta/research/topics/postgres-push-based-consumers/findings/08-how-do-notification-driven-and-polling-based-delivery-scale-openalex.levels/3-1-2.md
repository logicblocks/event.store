# What runtime overhead and delivery latency did evaluations of PostgreSQL-integrated publish and subscribe prototypes, such as the Hermes integration by Vargas, Bacon and Moody, measure for in-database change event detection?

## Question

When researchers built prototypes that put publish and subscribe inside PostgreSQL, so that the database itself detects data changes and publishes them as events, what runtime overhead on the database and what end-to-end delivery latency did they measure? The best-known example is Vargas, Bacon and Moody's integration of PostgreSQL with the Hermes middleware.

## Findings

**Short answer: the scholarly catalogue records show no measured overhead or latency figures for the PostgreSQL and Hermes prototype.** The records show the prototype's architecture and its line of publications. None of the available abstracts reports a number for trigger or rule overhead on writes, for publication throughput, or for the delay between a commit and a subscriber receiving the event. Any such figures are only in the full papers or the dissertation, and not in their catalogue entries. This note does not give numbers that the records do not contain.

**What the prototype is.** Vargas, Bacon and Moody's "Integrating databases with publish/subscribe" (IEEE ICDCS Workshops, 2005) describes how they combined *active databases* with publish and subscribe. They used PostgreSQL as the database and Hermes as the event middleware. Their design differs from a continuous-query model:

- **The database defines the events.** Each database manager defines and advertises a set of *change events*. Subscribers do not register arbitrary queries for the database to re-evaluate.
- **Events can span several tables.** An advertised event can cover a number of physical relations. Each one corresponds to a virtual relation of a *security view*, so event definitions double as access-control boundaries.
- **Clients subscribe to advertised events.** They subscribe to the events they are interested in and can narrow their subscriptions further. The abstract is cut off at this point in the catalogue record.

Because the database is "active", change detection runs inside the database engine through its trigger and rule machinery. The cost of detecting an event therefore falls on the transaction that makes the write, not on a separate reader. The available abstract text presents the paper as an architecture paper and does not mention an evaluation.

**The Hermes side.** Hermes (Pietzuch and Bacon, ICDCS Workshops, 2002) is a distributed event-based middleware with a type- and attribute-based publish and subscribe model. It is built around event types and supports features from object-oriented languages, such as type hierarchies and subscriptions to a supertype. It routes events over a scalable overlay network. In the integrated system, events detected in the database are handed to this external routing layer for delivery. Delivery latency therefore depends on both the in-database detection path and the routing path through the broker overlay. The Hermes record also gives no numbers for that combined path.

**Follow-on work.** The research continued in two later outputs:

- **"Event-Driven Database Information Sharing"** (Vargas, Bacon and Moody), published in the Lecture Notes in Computer Science series, the proceedings of the British National Conference on Databases (BNCOD) 2008.
- **Vargas's dissertation, "Integrating databases and publish/subscribe".**

Neither catalogue record includes an abstract. If the group published measurements of change-detection overhead or delivery latency, these two are the most likely places. Neither can be confirmed or quoted from the records available.

**Related work on database-integrated publish and subscribe.** Two neighbouring designs appear in the catalogue. Neither is PostgreSQL-based, and neither record reports latency or overhead measurements.

- **NonStop SQL/MX** (Hanlon, Klein, Van der Linden and Zeller, ICDE 2004). This project, started in 1998, turned a commercial RDBMS into an active database by building transactional queuing into relational tables through simple SQL extensions, with clearly defined query and transactional semantics. The authors describe it as the first commercially available RDBMS with streams. All data flowing through the system is kept in tables.
- **TIBCO's transactional publish and subscribe** (Chan, ACM SIGMOD Record, 1998). This is the industrial counterpart: publish and subscribe as push technology, tied to transactional guarantees.

Both show that tying event publication to database transactions is an established design. Neither record supplies the cost data the question asks for.

**Implication for replacing polling (inference, not a measured result).** The detect-in-database, publish-to-broker pattern puts change-detection work on every committing write, and adds a hand-off from the database to the delivery mechanism. A PostgreSQL event store moving from fixed-interval polling to push delivery would have the same structure: a trigger or the writing transaction issues a notification, and a listener wakes the consumers. This literature gives no published overhead or latency figures to use as a baseline. The cost of in-database detection would need to be measured directly, for example as insert throughput and commit latency with and without the detection step, and as commit-to-delivery latency under load.
