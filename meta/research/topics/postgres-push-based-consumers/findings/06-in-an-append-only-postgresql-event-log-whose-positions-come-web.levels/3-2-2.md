# Is there a PostgreSQL proposal or patch that stops NOTIFY holding its commit-ordering lock across the WAL flush, and what concurrent-commit throughput gains did its benchmarks report?

## Question

Has anyone proposed or written a PostgreSQL patch that stops a NOTIFY-issuing transaction from holding the lock that keeps commits in order while its commit record is flushed to WAL? If so, what concurrent-commit throughput gains did the benchmarks for that work report, and what is the patch's status?

## Findings

### The lock and why it spans the WAL flush

When a transaction that issued NOTIFY commits, `PreCommit_Notify()` in `src/backend/commands/async.c` takes a heavyweight lock. The call is `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)`, a lock on "database 0". The source comment explains why:

> "Serialize writers by acquiring a special lock that we hold till after commit. This ensures that queue entries appear in commit order, and in particular that there are never uncommitted queue entries ahead of committed ones, so an uncommitted transaction can't block delivery of deliverable notifications."

It is a heavyweight lock so that it is "automatically ... released after either commit or abort".

`CommitTransaction()` in `xact.c` runs these steps in order:

1. `PreCommit_Notify()` takes the lock.
2. `RecordTransactionCommit()` runs. Its comment reads "This is where we durably commit." It calls `XLogFlush` on the commit record whenever `synchronous_commit` is above `off`.
3. `RecordTransactionCommit()` then calls `SyncRepWaitForLSN` if synchronous replication is configured. The comment there says that at that point the backend has "marked clog, but still show[s] as running in the procarray and continue[s] to hold locks."
4. `ProcArrayEndTransaction()` runs.
5. The resource owner releases the locks.
6. `AtCommit_Notify()` signals the listeners.

So the lock is held across the commit record's WAL flush and any synchronous-replica wait. Every transaction that issues NOTIFY therefore commits one at a time.

The rest of this paragraph is inference, not something the sources state. On storage where flushes are slow, throughput is capped at roughly one notifying commit per flush. Group commit cannot batch those flushes.

Recall.ai's write-up of a production incident (Recall.ai engineering blog, July 2025) described the effect. The lock "effectively serializes all commits". Under load, database CPU and I/O "actually plummet".

### Proposal 1: an out-of-order NOTIFY setting (rejected)

On 18 July 2025 Rishu Bagga posted "Proposal: Out-of-Order NOTIFY via GUC to Improve LISTEN/NOTIFY Throughput" to pgsql-hackers. It named "the global lock taken in `PreCommit_Notify`, which serializes all notifications" as a main bottleneck. It proposed a setting, `publish_out_of_order_notifications` (off by default), that would skip the lock. The cost was possible out-of-order delivery, and possible notifications from transactions that rolled back.

The benchmark was NOTIFY-only, run with pgbench (8 connections, 2,000 transactions each) on an 8-core MacBook Air M2:

| `publish_out_of_order_notifications` | TPS (five runs) | Latency |
|---|---|---|
| off | 158,190–190,288 | 0.042–0.051 ms |
| on | 298,982–353,834 | 0.023–0.027 ms |

That is about a 2x gain.

Tom Lane rejected the approach on two grounds:

- Settings that change query semantics are a regrettable choice, and this one would break ordering for everyone even if only one session set it.
- async.c depends on "queue entries appear[ing] in commit order".

Joel Jacobson ran benchmarks in the same thread on a 16-core M3 Max. The results depended on the workload:

| Workload | Master (TPS) | Out-of-order patch (TPS) | Change |
|---|---|---|---|
| NOTIFY only | about 160k | about 340k | about +125% |
| LISTEN plus NOTIFY | about 73k | about 83k | about +14% |

He first concluded that waking listeners with `kill()` system calls was the real cost.

On 30 July 2025 he reported a second benchmark: one listening session and 1,000 notifying pgbench connections (`-c 1000 -j 8 -T 60`). The results were:

- "tps = 7679 (with heavyweight lock; in commit order)"
- "tps = 95430 (without heavyweight lock; not in commit order)"

That is about a 12x gain. He concluded that PostgreSQL would benefit from reducing `kill()` calls, and also from "finding ways to avoid the heavyweight lock while preserving commit order".

### Proposal 2: Tom Lane's WAL-transport design

Tom Lane proposed an alternative design on 18 July 2025:

1. In `PreCommit_Notify()`, write all of the transaction's notification payloads as a WAL record and remember its LSN. Existing parallel WAL insertion means this step can run in parallel.
2. Include that LSN in the transaction's commit record.
3. While writing the commit record, add a small fixed-size entry to the notify SLRU queue: the transaction id, the database OID and the payload LSN.
4. Signal listeners as before.
5. Listeners read the queue and fetch the payloads from WAL.

A global lock is still needed so that queue entries are made in commit order. However, "that lock only needs to be held for the duration of step 3, which is much shorter than what happens now." As a side benefit, WAL replay on a hot standby could produce the queue entries, so NOTIFY would also work on replicas.

### The patch: "[PATCH] Write Notifications Through WAL"

Rishu Bagga implemented Tom Lane's design: a first version on 4 September 2025, then v5 to v9 under the subject "[PATCH] Write Notifications Through WAL". The v5 message (25 September 2025) states its aim: "eliminating the need for a global lock to be held from PreCommit_Notify to the end of transaction". Its write path is:

1. Write the payloads to WAL in `PreCommit_Notify` and store the LSN in `MyProc`.
2. Take `NotifyQueueLock` exclusively.
3. Write a compact queue entry that references the LSN.
4. Commit, putting the payload LSN in the commit record.
5. Release `NotifyQueueLock`.

The heavyweight lock on "database 0" is replaced by a short hold on that lightweight lock.

Changes made during review:

- **Payload WAL writes moved out from under the lock.** Arseniy Mukhin objected that holding the lock while writing payload data to WAL stopped those writes running in parallel. v7 moved them outside the exclusive lock.
- **The lock now sits around the commit-record insertion.** The queue write and its locking moved into `RecordTransactionCommit()`, around `XactLogCommitRecord()`. `XactLogCommitRecord()` inserts the commit record and runs before the commit's `XLogFlush`. The thread summaries reviewed do not state outright that the flush happens after the lock is released. The commit-record placement and the patch's stated aim both point that way, but this reading has not been checked against the patch code.
- **Listeners still check snapshot visibility.** Reviewers required that listeners keep the `XidInMVCCSnapshot` check, which waits until a notifying transaction is visible to their snapshot.
- **WAL is pinned until notifications are consumed.** The patch keeps WAL that holds unconsumed notifications from being removed.
- **Standby support.** v8 (3 November 2025) let a standby listen for and receive notifications from the primary.

Reported benchmarks:

- **Initial patch (4 September 2025).** `pgbench -c 100 -j 8 -T 100`, each transaction doing `INSERT` then `NOTIFY`: 63,445–66,372 TPS with the patch, against 29,191–30,908 TPS without it (about 2x).
- **v5 (25 September 2025).** `pgbench -c 100 -T 100 -j 8`: "With patch: TPS = 60k - 70k / Without patch: TPS = ~30k".
- **Independent run of v6 and v7 (Arseniy Mukhin, 17 October 2025).** `pgbench -n -c 100 -j 10 -T 100` with no listeners and 10-byte payloads:

| Workload | Master | v6 | v7 |
|---|---|---|---|
| insert_only | 30,981.6 | 34,940.9 | 30,933.0 |
| insert_with_notify | 817.9 | 33,761.7 | 33,870.5 |
| notify_only | 87,750.5 | 36,141.2 | 34,261.9 |

All figures are TPS. In the INSERT-plus-NOTIFY workload, which is closest to an event-store append, the patch gave a "stable 30-40x boost". That brought it up to the INSERT-only baseline, so the notify cost almost disappears. NOTIFY-only transactions, which write no other WAL, lost about 2.5x, and the reviewer could not explain why. Payloads of 2,000 bytes behaved like 10-byte ones.

The gap between the two master results for INSERT plus NOTIFY (about 30k TPS against 818 TPS) suggests, though the sources do not say so, that the cost of the serialised hold depends on how slow WAL flushes are on the test machine. Fast-flush hardware hides most of the cost; flush-bound storage exposes all of it.

### Status as of October 2026

The last message in the thread is v9 (25 November 2025). It rebased the patch, updated the async.c header comment and the `pg_stat_slru` test expectations, and answered review comments from Masahiko Sawada. A search of the mailing-list archives finds no later messages on the thread. The patch has not been committed:

- `async.c` on master still calls `LockSharedObject(...)` with the "hold till after commit" comment.
- The `async.c` header still says there is "no need for WAL support or fsync'ing".
- The PostgreSQL 19 release notes (Beta 4, September 2026) have one NOTIFY item: "Improve NOTIFY to only wake up backends that are listening to specified notifications (Joel Jacobson)" (commit 282b1cde9). That change addresses waking listeners, not the commit-order lock.

Recall.ai's later update to its post says commit 282b1cde9 "has eliminated the bottleneck in the postgres core". This should be read narrowly. That commit fixed the wake-up storm, and the lock held through commit is still in master. In PostgreSQL 19 a pgsql-hackers thread on documenting LISTEN and NOTIFY performance pitfalls was still open (July 2026). Bruce Momjian asked whether a wiki page would be easier to keep current.

### Implications for an event store

On every released PostgreSQL version up to and including 19, an append transaction that issues NOTIFY:

- commits one at a time with every other NOTIFY-ing commit;
- waits for its own WAL flush, and any synchronous-replica acknowledgement, while holding the lock.

The benchmarks give a sense of the cost. Unpatched master ran INSERT plus NOTIFY at 818 TPS where INSERT alone ran at 31k. Removing the lock from the commit flush gave about 2x on fast-flush hardware and 30–40x on flush-bound hardware.

Until a WAL-transport patch is committed, the practical options are:

- move NOTIFY out of the append transaction;
- shorten the flush, for example with asynchronous commit on the notifying transaction (inference: this shortens the hold because `XLogFlush` is skipped when `synchronous_commit` is off).
