# What sustained append rate per category does a transaction-scoped advisory lock allow on current PostgreSQL under synchronous commit and under synchronous replication, measured against unserialised inserts with pgbench?

## Question

If an event store serialises appends per category with `pg_advisory_xact_lock`, as Message DB does, what is the most appends per second a single category can sustain on current PostgreSQL? The question asks for this with durable local commit (`synchronous_commit = on`, no standby) and with synchronous replication. It also asks how that rate compares with unserialised inserts measured the same way with pgbench.

## Findings

### Short answer

None of the sources cited here publishes a pgbench comparison of exactly this shape. That includes PostgreSQL's documentation, Message DB's repository (whose own write benchmark cannot measure it, as explained below) and the practitioner sources. PostgreSQL's source code and documentation do fix the shape of the answer, though. A transaction-scoped advisory lock is released only after the commit record has been flushed to local disk. With synchronous replication, it is also held until the standby has acknowledged. So one category can commit at most one append per lock-hold time:

- **Ceiling per category ≈ 1 / (work done under the lock + local WAL flush + any synchronous-replication wait).**

Unserialised inserts do not have this ceiling. Group commit lets one WAL flush cover many concurrent commits, so total throughput grows with the number of clients. Serialised commits in the same category cannot share a flush, because the next writer cannot start its insert until the previous commit's flush has returned. Commits in different categories can still share flushes.

Using published device and network latencies, the estimated ceilings below are calculated, not measured:

| Commit path inside the lock window | Published latency | Per-category ceiling (flush/ack only, before statement work) |
|---|---|---|
| Local flush, battery-backed RAID cache | 0.04 ms fsync (23,000 fsync/s measured) | ~20,000+/s, so in practice statement work and CPU set the limit |
| Local flush, enterprise NVMe with power-loss protection | 0.14 ms (7,380 fsync/s) | ~7,000/s |
| Local flush, AWS EBS io2 Block Express | average under 500 µs per 16 KiB I/O | about 2,000/s or a little more |
| Local flush, consumer SATA or NVMe SSD | 0.49 ms to 9.3 ms (108 to 2,031 fsync/s) | ~100 to ~2,000/s |
| Local flush, 7200 or 5400 RPM disk | 18 ms to 66 ms (15 to 56 fsync/s) | ~15 to ~55/s |
| Synchronous replication across availability zones (`on`) | local flush plus a round trip of up to about 2 ms plus the standby's flush | roughly 300 to 500/s |
| Synchronous replication with `remote_apply` | adds standby WAL replay, described as "much larger commit delays" | lower again, depends on the workload |

With unserialised inserts on the same hardware, throughput is not tied to a single flush time. The clearest published contrast comes from the group-commit work in PostgreSQL 9.2. On a laptop 7200 RPM disk whose raw `fdatasync()` took about 8 ms, which allows about 125 serial commits per second, the author reported "towards 14,000 write transactions per second" with many concurrent clients. On that disk, a single serialised category would have been limited to roughly 1% of the unserialised insert throughput.

### Why the lock-hold window includes the flush and the replication wait

- **Message DB takes the lock first.** `message_store.acquire_lock` computes `hash_64(category)` and calls `pg_advisory_xact_lock` on it. `write_message` calls `acquire_lock` before it reads the stream version, checks the expected version and inserts. So the lock covers the whole append, and then the commit.
- **Transaction-level advisory locks have no unlock.** PostgreSQL's documentation says they "are automatically released at the end of the transaction, and there is no explicit unlock operation."
- **Locks are released after the durable commit.** In `CommitTransaction` in `xact.c` on the current master branch, `RecordTransactionCommit` runs first ("This is where we durably commit"). Then `ProcArrayEndTransaction` runs, which "must be done _before_ releasing locks we hold and _after_ RecordTransactionCommit". Only after that does `ResourceOwnerRelease` release the locks.
- **The replication wait happens while locks are still held.** `RecordTransactionCommit` calls `XLogFlush` and then `SyncRepWaitForLSN`. The code comment says: "at this stage we have marked clog, but still show as running in the procarray and continue to hold locks."
- **The documentation says the same.** The synchronous-replication docs state that "transaction locks continue to be held until the transfer is confirmed", so "incautious use of synchronous replication will reduce performance … because of increased response times and higher contention."

Every non-`off` setting of `synchronous_commit` waits for the local WAL flush. `remote_write` also waits for the standby to write the commit record to its operating system. `on` also waits for the standby to flush it to durable storage. `remote_apply` also waits for the standby to replay it, which "will cause much larger commit delays". The documentation gives the round-trip time between primary and standby as the minimum extra wait.

### What sync replication costs on managed services

All the main managed high-availability setups put a cross-zone acknowledgement inside the lock window:

- **Azure Database for PostgreSQL:** high availability always commits synchronously to the standby. A commit waits until the standby "durably stores the WAL" but not until it applies it. Microsoft calls the cost "a small increase in commit latency". Azure aims for "round-trip latency of less than approximately 2 milliseconds" between zones.
- **Amazon RDS Multi-AZ DB instance deployments:** these "can have increased write and commit latency compared to a Single-AZ deployment" because of synchronous replication.
- **Amazon RDS Multi-AZ DB clusters:** these need an acknowledgement from at least one of two readers. AWS describes them as having "lower write latency" than Multi-AZ instance deployments.

None of these vendors publishes a commit latency in milliseconds. The 300 to 500/s cross-zone figure in the table assumes a 1 to 2 ms round trip plus sub-millisecond flushes on both servers.

### Factors that lower the per-category rate further

- **Adding clients only adds waiting.** Once one category is saturated, more concurrent writers do not raise its throughput. In a closed-loop pgbench run, mean latency grows roughly as clients × lock-hold time. For example, 32 clients sharing a 3 ms hold would see about 96 ms per append. This follows from the serial queue; it is not a measured figure.
- **`commit_delay` works against serialised categories.** It "increases latency by up to the `commit_delay` for each WAL flush" when at least `commit_siblings` other transactions are active. That delay falls inside every category's lock window. A server tuned for total throughput with `commit_delay`, recommended at about half the measured flush time, therefore lowers the ceiling for each category.
- **Client round trips while the lock is held.** Message DB does the whole append inside one server-side function. If the caller wraps it in an explicit `BEGIN … COMMIT`, at least one client-to-server round trip passes between `write_message` returning and `COMMIT` arriving. A psycopg 3 append written as separate lock, version-check, insert and commit statements would hold the lock for one round trip per statement. Taking the lock as late as possible, and committing in the same round trip, keeps the window close to the flush time.
- **Large or batched appends.** Sequin reported that serialising writes through a sequence table gave "Write throughput … much lower than we needed, and the lock durations between concurrent writes was very high (seconds)". They traced this to large insert batches. That was a row lock rather than an advisory lock, but it serialises in the same way.
- **The lock manager is rarely the limit.** Advisory locks cannot use PostgreSQL's fast-path locking, which is reserved for weak relation locks. They go through the shared lock table, which is partitioned by a hash of the lock tag. At the per-category rates above, the flush time sets the limit long before lock-table contention does.

### Levers that change the ceiling, and what they cost

- **`synchronous_commit` can be set per transaction** with `SET LOCAL`. With `local`, the append waits only for the local flush, which removes the replication wait from the lock window but gives up the replication guarantee for that append. With `off`, the flush wait is removed as well, at the risk of losing acknowledged appends after a crash (at most three times `wal_writer_delay`).
- **Batching several events into one append transaction** spreads one flush, and one lock-hold window, over many events.
- **Finer lock keys** raise total throughput but weaken the ordering guarantee. Examples are locking per stream, or on a hash bucket within a category.
- **Not serialising at all**, and filtering readers by transaction ID with `pg_snapshot_xmin` instead, keeps appends non-blocking. Practitioners describe the serialisation option as a "nuke option" with a "performance hit [that] was too big to accept".

### Message DB's own benchmark cannot show this cost

Message DB's `benchmark.sh` runs `EXPLAIN ANALYZE SELECT benchmark_write(stream, cycles)`. `benchmark_write` loops over `write_message` inside one PL/pgSQL call, which is one transaction. The transaction re-acquires a lock it already holds and commits once. So the benchmark measures how fast statements run under the lock, not how often commits can pass through it. It says nothing about the flush-bound or replication-bound ceilings above.

### How to measure it with pgbench

A comparison that would answer the question directly for a given deployment uses two custom scripts, run with `-f`:

```sql
-- unserialised.sql
\set cat random(1, 4)
BEGIN;
INSERT INTO events (category, payload) VALUES (:cat, '{}');
END;

-- serialised.sql
\set cat random(1, 4)
BEGIN;
SELECT pg_advisory_xact_lock(:cat);
INSERT INTO events (category, payload) VALUES (:cat, '{}');
END;
```

Run each script with `-M prepared -c <clients> -j <threads> -T 300 -r`:

- **Vary the number of categories** (set the upper bound of `random` to 1, 4, 16 and 64) and the number of clients (1, 8, 32 and 64).
- **Repeat for each commit setting:** `synchronous_commit` at `off`, `local` and `on` with no standby, then `remote_write`, `on` and `remote_apply` with `synchronous_standby_names` set.
- **Read `-r`'s per-command latencies.** The `pg_advisory_xact_lock` line shows the time spent queueing for the lock. The `END` line shows flush plus replication-acknowledgement time.
- **Run `pg_test_fsync` on the primary and the standby** to get the flush term, and measure the round trip between them.
- **Run each test for minutes**, following pgbench's own advice to "never believe any test that runs for only a few seconds".

If the model above holds, the serialised run with one category should level off at about 1 / (lock-wait-free statement latency + `END` latency), whatever the number of clients. The unserialised run should keep scaling with clients until CPU or WAL insertion becomes the limit.
