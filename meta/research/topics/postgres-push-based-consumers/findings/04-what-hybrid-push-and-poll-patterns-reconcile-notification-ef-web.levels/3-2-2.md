# Does a periodic self-NOTIFY round-trip on the listener connection catch failures that a SELECT 1 heartbeat misses, such as a stalled notification queue or a proxy that answers queries but no longer forwards notifications?

## Question

Does a periodic self-NOTIFY round-trip on the listener connection catch failures that a SELECT 1 heartbeat misses, such as a stalled notification queue or a proxy that answers queries but no longer forwards notifications?

## Findings

### Short answer

Partly. A self-NOTIFY round-trip catches a real set of failures that `SELECT 1` cannot see. These include:

- a full notification queue;
- a listener session stuck inside a transaction;
- a backend that has lost its `LISTEN` registration;
- stalls on the notify lock or the commit path;
- a connection that has landed on a hot standby.

It is weaker than it looks on the proxy case, which is one of the two failures the question names. PostgreSQL hands a session's own notifications back as part of that command's response, not as an unprompted message on an idle connection. So the probe never tests whether a proxy forwards notifications that arrive while the client is idle. Under transaction pooling it can also return a false "healthy".

A stronger check sends the probe from a different connection, ideally the append path's own pool, and waits for it on the listener. Oban and PgQueuer both ship this kind of check in production. Even this probe only proves the path works now. It does not prove that no notification was missed, so a catch-up read is still needed.

### What each probe actually exercises

A `SELECT 1` (or pg-listen's `SELECT pg_backend_pid()`, run every 30 s by its "paranoid checking" option) proves only one thing. Something at the far end of the socket still parses queries and replies. pg-listen reconnects and re-issues `LISTEN` for every channel only when that query throws. Npgsql's application-level keepalive works the same way: "periodic ping roundtrips", recommended "when waiting for PostgreSQL notifications". None of these touch the notification machinery.

A `NOTIFY` on the listener connection goes through much more of the machinery. PostgreSQL's `async.c` shows the steps:

1. **It is a write transaction.** `PreCommit_Notify` makes sure the transaction has an XID, because each queue entry carries its XID. Readers use it to check whether the writing transaction is still in progress.
2. **It takes the global notify lock.** It acquires `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)` and holds it "till after commit", so that queue entries appear in commit order.
3. **It writes to the shared queue.** If the queue is full, the commit fails with `too many notifications in the NOTIFY queue`.
4. **It reads its own entry back.** In `SignalBackends`, when the target is the sender itself (`pid == MyProcPid`), the code sets `notifyInterruptPending = true` instead of sending a signal. Then, "after we are out of the transaction altogether and about to go idle", the backend scans the queue for messages for its own client, "which might be notifies from other backends, or self-notifies from our own".
5. **The client receives it.** The `Notify` message carries the sender's PID. psycopg exposes this as `Notify.pid` and the connection's own PID as `conn.info.backend_pid`, so a probe can recognise its own echo, as the NOTIFY docs suggest.

### Failures a self-NOTIFY catches that SELECT 1 misses

- **A listener session stuck in a transaction.** PostgreSQL holds notifications for a session that is inside a transaction "until just after the transaction is completed". It also holds a NOTIFY issued inside a transaction until commit. A self-probe sent from such a session never comes back.

  This failure is easy to cause in psycopg 3. By default "even a simple `SELECT` will start a transaction", and the session then stays *idle in transaction*. So a `SELECT 1` heartbeat on a connection without autocommit can create this exact failure while still reporting success. psycopg's docs say a connection used for notifications should be in autocommit mode. The NOTIFY docs also warn that a listening session sitting in a long transaction stops queue cleanup for the whole cluster.

- **Notifications cannot be queued.** When the shared queue (8 GB by default) fills, "transactions calling `NOTIFY` will fail at commit". The probe surfaces that error at once, while `SELECT 1` keeps passing. Queue growth is a slow stall, though: delivery to healthy listeners continues until the queue is full. It is better caught early by making the heartbeat query `SELECT pg_notification_queue_usage()` instead of `SELECT 1`. That function returns the fraction of the queue in use. The server also logs warnings from half full onwards (`NOTIFY queue is %.0f%% full`) and names the oldest session holding up cleanup.

- **A lost `LISTEN` registration on the backend that serves the probe.** Examples include a client library or wrapper that reconnects transparently without re-listening, or a session reset by `DISCARD ALL`. In each case `SELECT 1` succeeds on the new or reset session, but the probe's echo never arrives because no one is listening.

  RDS Proxy is a managed example of this risk. AWS documents that "Listening on a notification channel" pins a session to one database connection. It also says the proxy "connects to the standby database without dropping idle application connections" during failover, and that only connections "in the middle of a transaction or SQL statement are canceled". The docs do not say whether a session pinned by `LISTEN` is closed or silently re-attached. If it is re-attached, the registration is gone. A self-NOTIFY would expose that; `SELECT 1` would not.

- **Write-path and lock stalls.** Because the probe commits under the global notify lock, its round-trip time measures contention with other notifying commits. My inference is that it would also hang whenever commits hang, for example while waiting for an unavailable synchronous standby. That would be a false alarm about the listener itself, but a correct alarm that appends issuing NOTIFY are stuck.

- **Landing on a hot standby.** `LISTEN` and `NOTIFY` are both rejected during hot standby, whereas `SELECT 1` succeeds there.

### Failures a self-NOTIFY on the same connection still misses

- **A proxy that answers queries but does not forward unsolicited messages.** This is the main weakness. The protocol docs say a NotificationResponse is sent only outside a transaction and "might occur just before ReadyForQuery". The backend sends self-notifies as it is "about to go idle". Together these mean the echo normally reaches the client inside the probe's own request–response exchange.

  A proxy, or a client loop, that relays only replies to requests would therefore pass the probe. Meanwhile it would drop the real case: notifications pushed by other backends while the listener connection sits idle. The probe also skips the signal another backend uses to wake the listener, because the sender only sets a flag on itself.

- **Transaction-mode poolers.** PgBouncer lists `LISTEN` as "Never" supported in transaction pooling, and Neon's pooled endpoints exclude it as well. A self-probe does not reliably detect this setup:
  - In transaction mode, PgBouncer does not run `server_reset_query`, so the `LISTEN` stays registered on whichever server backend ran it.
  - By default PgBouncer reuses server connections "in LIFO … manner".
  - On a quiet pool, the probe's `NOTIFY` is therefore likely to land on that same backend and echo back. Notifications arriving while the client is detached are still lost.
  - The probe passes or fails depending on which backend the pool hands out.

  This is an inference from the documented behaviour, not a tested result.

- **Problems on the writer side.** Examples: writers connected to a different server or database, writers that stopped issuing `NOTIFY`, or writers using a different channel name after an upgrade. A probe that never uses the writers' code path cannot see any of these.

- **Notifications already missed.** A successful probe shows the path works now. It says nothing about notifications dropped before the probe ran, so reconnects still need a catch-up read.

### What production libraries do

- **Oban (Elixir)** runs a "sonar" check. It broadcasts `%{node: …, ping: true}` on a `sonar` channel every 5 s, backing off to 60 s. It records which nodes it has heard from and drops entries older than 120 s. From this it classifies the notifier as `:isolated` (hears nothing), `:solitary` (hears only itself) or `:clustered`.

  Its Postgres notifier sends `pg_notify` through the main Repo connection pool and listens on a dedicated connection. So even its "self" ping crosses connections, exercising the writer path and idle-time delivery to the listener. The docs say the notifier is isolated "behind a connection pooler".

  When it is isolated, Oban logs "notifier can't receive messages from any nodes, functionality degraded". Its job stager switches to local mode, which "polls for jobs for every queue", on a 1 s interval until a working notifier restores global mode.

- **PgQueuer (Python, asyncpg and psycopg)** has `listener_healthy()`, documented as "Round-trip a NOTIFY/LISTEN probe". It sends a `health_check_event` with a unique id on the queue's channel and waits up to 10 s for that id to come back. A periodic task repeats this every 10 s. A timeout raises `FailingListenerError`, which shuts the worker down if `shutdown_on_listener_failure` is set. Otherwise polling continues on the dequeue timeout.

### Cost and design guidance for a psycopg 3 event store

- **Each probe is a full notifying commit.** It assigns an XID, takes the global notify lock and writes a commit record.
- **Before PostgreSQL 19, every probe wakes every listener in the database.** `SignalBackends` signals every listener in the database regardless of channel. PostgreSQL 19 changed `NOTIFY` "to only wake up backends that are listening to specified notifications". On 19 and later, a private per-listener channel (for example, one named after a process UUID) wakes only the prober.
- **The load is small.** N processes each probing every T seconds add N/T notifying commits per second. At intervals of a few seconds this is negligible beside append traffic.
- **Recommended combination:**
  - Run the listener connection in autocommit.
  - Make the cheap heartbeat `SELECT pg_notification_queue_usage()`, with an alert threshold, rather than `SELECT 1`.
  - Send a periodic canary `NOTIFY` with a nonce payload from the append-side pool, not the listener connection. Wait for it on the listener with `conn.notifies(timeout=…)` (the `timeout` and `stop_after` parameters were added in psycopg 3.2).
  - If the canary does not arrive, treat the listener as suspect: reconnect, re-`LISTEN`, catch up from the last processed position, and rely on safety-net polling in the meantime.
- **psycopg version details.** Since 3.2.4, notifications that arrive before the `notifies()` generator starts are captured and yielded once it starts, provided no notify handler is registered. Since 3.2.10, mixing handlers and the generator is deprecated.
- **When to use a same-connection self-NOTIFY.** It is only worth adding as a cheap extra check when the deployment cannot send from a second connection. It is not a substitute for the cross-connection canary.
