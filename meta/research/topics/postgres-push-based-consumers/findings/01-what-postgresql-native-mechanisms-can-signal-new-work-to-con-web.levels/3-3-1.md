# How much does committing a notify-only flush transaction with synchronous_commit off shorten the NOTIFY lock's hold time and raise notification throughput under many concurrent writers?

## Question

Suppose event writers append without issuing `NOTIFY`, and a separate "flush" transaction issues only the `NOTIFY` (or `pg_notify()`) calls. How much does committing that flush transaction with `synchronous_commit = off` shorten the time it holds PostgreSQL's global NOTIFY lock, and how much does that raise notification throughput when many writers run concurrently?

## Findings

### What the lock covers

`PreCommit_Notify()` in `async.c` first forces an XID onto the transaction with `GetCurrentTransactionId()`. It then takes `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)`, a heavyweight lock on "database 0". Every notifying transaction in the cluster takes this same lock, and the source says it is held "till after commit" so that queue entries appear in commit order. In logs it shows up as `AccessExclusiveLock on object 0 of class 1262 of database 0`.

`CommitTransaction()` in `xact.c` runs these steps in order:

1. `PreCommit_Notify()` takes the lock and appends to the `pg_notify` queue.
2. `RecordTransactionCommit()` writes the commit record and, if required, flushes it and waits for synchronous standbys.
3. `ProcArrayEndTransaction()` makes the transaction visible as committed.
4. `AtCommit_Notify()` calls `SignalBackends()` to signal listeners.
5. `ResourceOwnerRelease(... LOCKS ...)` finally releases the lock.

So the lock covers four things: the queue write, any commit-time WAL flush, any synchronous-replication wait, and the signalling of listeners. The queue itself is not WAL-logged. `async.c` says notifications are not expected to survive a crash, so "there is no need for WAL support or fsync'ing".

A notifier blocks in `PreCommit_Notify()` before it reaches `RecordTransactionCommit()`. Notifying transactions therefore cannot share one group-commit flush: each WAL flush happens alone inside the lock. `commit_delay`, which adds a wait before a WAL flush, would also lengthen the hold for any notifier that flushes.

### For a truly notify-only transaction, `synchronous_commit = off` changes almost nothing

`RecordTransactionCommit()` decides whether to wait for the flush:

```c
wrote_xlog = (XactLastRecEnd != 0);
...
if ((wrote_xlog && markXidCommitted &&
     synchronous_commit > SYNCHRONOUS_COMMIT_OFF) ||
    forceSyncCommit || nrels > 0)
    XLogFlush(XactLastRecEnd);
else
    XLogSetAsyncXactLSN(XactLastRecEnd);
...
if (wrote_xlog && markXidCommitted)
    SyncRepWaitForLSN(XactLastRecEnd, true);
```

`wrote_xlog` is computed before the commit record is inserted, and the source comment says async flush is allowed "if the current transaction has not performed any WAL-logged operation". A transaction that only queues notifications has an XID but has written no WAL record before commit, because the notify queue is not WAL-logged. It therefore already:

- takes the asynchronous branch (`XLogSetAsyncXactLSN`, no fsync wait);
- skips `SyncRepWaitForLSN`;

and it does both whatever `synchronous_commit` is set to. For such a transaction, `SET LOCAL synchronous_commit = off` shortens the lock hold by essentially zero.

The pgsql-hackers benchmarks agree with this. NOTIFY-only pgbench transactions on unpatched master reached about 154,000–190,000 TPS with 8 clients on Apple M2 and M3 laptops. That implies a serialised section of only a few microseconds, which is not possible if each commit waited for a WAL flush. The remaining hold time is the queue append, the commit-record insertion and the signalling of listeners.

### When the setting does matter

The setting changes the hold time only if the flush transaction writes WAL before commit. Any WAL record a backend inserts sets `XactLastRecEnd`, according to `xlog.c` ("It is updated for all inserts"). That makes `wrote_xlog` true. There are three ways this happens:

- **Deliberate bookkeeping.** The flusher updates a "last notified position" row or inserts a marker or outbox row.
- **Hint-bit full-page images.** Reading just-committed event rows (for example, `SELECT max(position)`) sets hint bits on those tuples. With data checksums on, or `wal_log_hints = on`, the first hint-bit change to a page after a checkpoint is written to WAL as a full-page image. `initdb` enables data checksums by default from PostgreSQL 18.
- **Heap pruning.** The `xact.c` comment notes that pruning can write WAL during a transaction.

In any of these cases, with `synchronous_commit` at `on` (the default), the notifier holds the cluster-wide lock across a full local WAL flush. With synchronous standbys configured, and `synchronous_commit` above `local`, it also holds the lock until the standby acknowledges (`SyncRepRequested()` is `max_wal_senders > 0 && synchronous_commit > SYNCHRONOUS_COMMIT_LOCAL_FLUSH`).

Setting `synchronous_commit = off` for that transaction removes both waits. The hold then drops from "queue append + flush latency (+ standby round trip) + signalling" to "queue append + commit-record insertion + signalling", which is microseconds. One proposer on pgsql-hackers described the synchronous case: "each must become durable before the next can proceed". He added that this is "especially expensive in environments where compute and storage are separated".

The following throughput ceilings are derived arithmetic, not measurements. Because the lock admits one notifying commit at a time and no group commit happens among them, the ceiling is about 1 / hold time:

| Storage | Flush latency | Approximate ceiling (notifying commits/s) |
|---|---|---|
| EBS gp3 | "single-digit millisecond" | about 110 to 1,000 |
| EBS io2 Block Express | average under 500 µs | about 2,000 |
| Same, with a synchronous standby | flush plus network round trip | lower |
| No flush inside the lock | none | tens to hundreds of thousands (laptop benchmarks above) |

For a flusher that writes WAL, async commit can therefore raise the ceiling by one to three orders of magnitude. For one that writes none, the gain is nil.

An unpatched-master benchmark of `INSERT` + `NOTIFY` per transaction (100 clients) reached about 30,000 TPS. Its storage and durability settings were not stated, so the absolute figure is no guide to production disks.

The setting is safe for this transaction. The docs say `off` creates "no risk of database inconsistency". The loss window is up to three times `wal_writer_delay` (200 ms by default). A lost notify-only commit costs nothing that a crash would not already lose. Two conditions apply:

- If the flusher keeps a bookkeeping row, that row can roll back after a crash, so re-notifying must be harmless.
- Event writers keep their own synchronous commit. Turning off `synchronous_commit` on the writers' append transactions instead would give up event durability.

### Under many concurrent writers, contention dominates, not fsync

Asynchronous commit does nothing about lock queueing itself. In one benchmark (1,000 clients, one listener, NOTIFY-only transactions, no fsync inside the lock) unpatched master managed 7,679 TPS, against 95,430 TPS with the heavyweight lock commented out. That is a 12x gap. The developer found the bottleneck moves between the heavyweight lock and the `kill()` signalling syscalls depending on the workload.

Signalling counts as hold time because `SignalBackends()` runs before the lock is released. PostgreSQL commit 282b1cde (Joel Jacobson, committed by Tom Lane on 15 January 2026, for PostgreSQL 19) adds a shared channel-to-listener map. With it, only interested listeners are signalled, and idle uninterested ones are advanced directly. The commit reports "integer multiples" more throughput when many listeners are uninterested, no gain when every listener reads every message, and no change to the lock.

The Recall.ai incident report describes the same failure in production. With tens of thousands of concurrent writers issuing `NOTIFY` inside their write transactions, hundreds of sessions queued on the lock, lock waits exceeded a second, and CPU and I/O fell while throughput collapsed.

So under many concurrent writers, the larger gain comes from issuing far fewer notifying transactions, not from making each one async. Each `NOTIFY` should coalesce many appends, ideally from a single notifier, so that the lock is rarely contended. `synchronous_commit = off` on that notifier is a cheap guard: it keeps incidental or deliberate WAL writes from dragging a flush, and possibly a standby round trip, into the lock.

### Upstream direction

Tom Lane has outlined a redesign. Notification payloads would be written into WAL in parallel, and only a small fixed-size SLRU entry would be written under the global lock. He says the lock would then be held "much shorter than what happens now". A prototype of this design doubled `INSERT` + `NOTIFY` throughput at 100 clients, from about 30,000 to about 64,000 TPS. Current master source still takes the "database 0" lock in `PreCommit_Notify()`, holds it until after commit, and describes the queue as having no WAL support.
