# How can a consumer reading a PostgreSQL event table by position avoid skipping rows from transactions that commit out of sequence order, and what do snapshot-based or commit-ordering techniques cost in write throughput and read latency?

## Question

A consumer reads an event table in order of a position column, usually filled from a sequence, and remembers the highest position it has handled. How can it avoid permanently skipping a row whose transaction got a lower position but committed after a higher-positioned row was already read? And what do the fixes cost in append throughput and delivery latency?

## Findings

### Why rows get skipped, and why stronger isolation alone does not help

A sequence hands out a position when the row is inserted. The row only becomes visible when its transaction commits. Suppose transaction T1 takes position 10 and T2 takes position 11. If T2 commits first, a consumer can read row 11, move its cursor to 11, and never come back for row 10 once T1 commits. Push delivery does not change this. A notification fires when its transaction commits, so a wake-up from T2 can arrive while T1 is still running. Any notification-driven consumer still needs one of the techniques below.

Fekete, O'Neil and O'Neil describe a close relative of this problem. Under snapshot isolation, a read-only transaction can see a state that no serial execution could produce. Their example is a batch-processing report: it sees a batch as closed but misses a receipt from a concurrent transaction that read the old batch number and committed later. This overturns the common assumption that read-only transactions are always safe under snapshot isolation. Ports and Grittner's account of PostgreSQL's SERIALIZABLE level, which uses Serializable Snapshot Isolation (SSI), uses this batch-processing case as a motivating example. SSI detects the dangerous pattern and aborts one of the transactions. The paper also adds read-only optimisations: a `READ ONLY DEFERRABLE` transaction waits for a "safe" snapshot and then runs without SSI tracking. The authors report SSI throughput close to plain snapshot isolation and well above lock-based serialisability on read-heavy workloads.

The following inference is drawn from those papers, not stated in them. SSI only protects positions that come from transactional data the writers read, such as a batch or epoch counter. PostgreSQL sequences are deliberately non-transactional. The serial order "T2, consumer, T1" fully explains what the consumer saw, so there is no dependency cycle for SSI to detect. Raising the isolation level therefore does not stop sequence-ordered gaps. The fix has to come from how positions are allocated or how the reader decides which positions are safe to pass.

### Technique 1: make position order match commit order

Writers take a single exclusive lock, such as a transaction-scoped advisory lock or a lock on a counter row, before they allocate positions. The lock is held until commit. PostgreSQL marks the transaction visible before it releases the lock, so any snapshot that sees position N also sees every position below N. The reader can trust positions immediately, which keeps read latency to a minimum.

The cost falls on writers. Every appending transaction passes through one critical section that includes the commit's write-ahead log flush. Append throughput is therefore capped at roughly one transaction per critical-section time, however many cores or connections exist. As an illustration (arithmetic, not a measurement), a 1 ms commit flush caps appends at about 1,000 transactions per second. Two things soften this:

- Taking the lock as late as possible, by allocating positions just before commit, shrinks the critical section to about the commit itself.
- Writing many events per transaction spreads the cost across more events.

CORFU shows the opposite design choice. It is a shared log that reaches about 1 million 4 KB operations per second on 16 to 32 machines because the component that hands out positions does no I/O, so "there is no single I/O bottleneck". A commit-serialising lock puts the I/O back inside the ordering step.

### Technique 2: transaction-ID (snapshot) watermark

Each row stores its writer's 64-bit transaction ID (`pg_current_xact_id()`, type `xid8`). The reader uses the oldest still-running transaction ID in its current snapshot (`pg_snapshot_xmin(pg_current_snapshot())`) as a watermark. Every transaction with a lower ID has already committed or aborted, so the set of rows with IDs below the watermark can never grow. A cursor kept in transaction-ID terms gives stable, gap-free batches: each read takes rows from the previous watermark up to the current one, ordered by position inside the batch.

- **Write cost:** small. Each row gets one 8-byte column, usually indexed, and writers never wait on each other.
- **Read cost:** latency. A row can only be delivered once every transaction with a lower ID has finished. One long-running or idle-in-transaction session that holds a transaction ID, even one that never touches the event table, delays delivery of everything after it.

Transaction IDs are handed out at a transaction's first write, not at commit. Per-stream order across batches is only exact when the event insert is the transaction's first write, or when ordering is otherwise constrained.

Elnikety, Zwaenepoel and Pedone's generalized snapshot isolation is the theory behind this trade. They show that reading an older snapshot instead of the latest one keeps snapshot isolation's main properties: read-only transactions never block or abort, and they never cause updates to block or abort. The watermark consumer deliberately reads a slightly stale but stable view. It pays in freshness, not in writer contention.

### Technique 3: gap detection with a timeout, or hole filling

The reader stops at a missing position and waits. After a timeout it assumes the position belonged to a rolled-back transaction and moves on. Writers pay nothing. Readers pay two costs:

- Every permanent gap costs one full timeout of delivery delay. Rollbacks, failed inserts and sequence values cached and lost in a crash all leave permanent gaps.
- Correctness depends on the timeout being longer than the slowest in-flight append. If it is not, rows are still skipped.

CORFU handles this more safely. Each position can be written only once, and a reader that finds a hole can "fill" it with a junk entry. A late writer's append then fails and retries at a new position, so a stuck position becomes a delay rather than a lost row. A possible PostgreSQL equivalent, which is inference and was not evaluated in any source found, is to have the reader insert a placeholder row at the gap's primary key:

- If an uncommitted row already holds that key, the unique index makes the reader wait until that transaction finishes. It then either gets a duplicate-key error (the row is now visible) or succeeds (the gap is permanently closed).
- If no transaction holds the key, the insert succeeds immediately and the gap is closed.

### Technique 4: read the commit-ordered log instead of the table

PostgreSQL's write-ahead log records commits in commit order. A change-data-capture (CDC) consumer that decodes the log avoids out-of-order visibility entirely. DBLog, Netflix's CDC framework for MySQL and PostgreSQL, captures committed changes from the transaction log. It writes marker rows into a dedicated watermark table so those markers appear in the log. This lets DBLog merge table reads into the change stream without table locks.

The costs are operational rather than contention:

- A replication slot keeps write-ahead log on disk until the consumer catches up.
- Decoding runs as a single stream per slot.
- The consumer's position becomes a log sequence number (LSN) instead of a table column.

The DBLog record reports no throughput or latency figures.

### Cost summary and evidence gaps

| Technique | Write-throughput cost | Read-latency cost |
|---|---|---|
| Commit-serialising lock | High: appends serialise through the commit flush | Minimal |
| Transaction-ID watermark | Negligible: one extra column, no contention | Bounded by the longest concurrent transaction holding an ID |
| Gap timeout | None | One timeout per permanent gap; skips if the timeout is too short |
| Log decoding (CDC) | Slot and log retention, not lock contention | Commit-to-decode delay |
| SSI with an epoch counter | Tracking overhead close to snapshot isolation, plus aborts and retries | At least one epoch, plus any wait for a safe snapshot |

None of the scholarly records found measures write throughput or read latency for these techniques on a PostgreSQL event table. The cost directions above follow from the mechanisms. The only measured anchors are adjacent ones: CORFU's throughput with I/O-free sequencing, and Ports and Grittner's comparison of SSI with snapshot isolation.

For a psycopg-based consumer woken by notifications, the transaction-ID watermark is the only technique here that adds no writer contention and keeps table-based reads. Its main risk is delivery stalls caused by long transactions anywhere in the database.
