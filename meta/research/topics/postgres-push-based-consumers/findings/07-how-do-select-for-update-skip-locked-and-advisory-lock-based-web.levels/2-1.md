# How do PostgreSQL event stores compute a safe high-water mark so that consumers woken by commit-time notifications never skip events from transactions that commit out of position order?

## Question

When an event store assigns each event a global position and notifies consumers as each append commits, how does it work out the highest position a consumer can safely read up to and checkpoint? The danger is a transaction that drew a lower position but commits after a higher one. A consumer that has already moved its checkpoint past that lower position would skip the event for good.

## Findings

### Why the problem exists

There are two separate orderings, and they can disagree.

- **Position order.** Global positions usually come from a sequence (`bigserial`) at insert time, not at commit. PostgreSQL says `nextval` values are "not reclaimed for re-use if the calling transaction later aborts". It also says that "transaction aborts or database crashes can result in gaps", that gaps can appear without an abort (for example with `INSERT ... ON CONFLICT`), and that sequences "cannot be used to obtain 'gapless' sequences".
- **Notification order.** `NOTIFY` follows commits. Notifications are "not delivered until and unless the transaction is committed", and "messages from different transactions are delivered in the order in which the transactions committed".

Here is how a naive consumer skips an event:

1. Transaction A draws position 10. Transaction B draws position 11.
2. B commits first. Its notification wakes the consumer.
3. The consumer reads `position > checkpoint`, sees 11, and moves its checkpoint to 11.
4. A commits. Event 10 is now behind the checkpoint and is lost.

From the reader's side, a hole at 10 looks the same whether A is still running or rolled back. Oskar Dudycz puts it this way: "If we optimistically assume that the gaps were caused by rollbacks, we may lose messages." The eugene-khyst reference implementation describes the same failure: a subscription processor reads transaction #2's events, updates its checkpoint, and loses transaction #1's.

So the safe high-water mark (HWM) is the highest position P where every event at or below P is either visible now or can never appear. The PostgreSQL event stores and queues examined use five ways to establish it.

### 1. Make position order equal commit order by serialising writers

If appends are serialised so that each one draws its positions while holding a lock that is released only at commit, then position order equals commit order. A plain `position > checkpoint` read is then safe.

- **Commanded EventStore (Elixir).** Every append runs `UPDATE streams SET stream_version = stream_version + $2 WHERE stream_id = 0`. Stream 0 is the all-stream. The append then derives each event's global number from the version it read before the update plus the event's index. That row lock is held until commit, so all appends are serialised globally.
- **Message DB (Eventide).** `write_message` first calls `acquire_lock`. That function hashes the stream's *category* and takes `pg_advisory_xact_lock` on the hash, which lasts until the transaction ends. Only then does it insert into `messages`, where `global_position` is a `bigserial`. Within one category, positions are therefore drawn in commit order.
  - The guarantee is per category. This is an inference from the code, not a documented claim: a reader that spans categories by global position could still meet out-of-order commits.

The cost is throughput. Sequin's write-up of the row-lock version notes that one writer "will need to wait until Pid 1 commits before it can lock the row". There is a useful side effect for push delivery (an inference from the NOTIFY ordering guarantee): when writes are serialised, notifications arrive in commit order, which is also position order. A position carried in the notification payload is then itself a safe HWM.

### 2. Transaction-ID visibility horizon (`xid8` plus `pg_snapshot_xmin`)

This is the most common design among newer PostgreSQL event stores. Each event row stores its writer's transaction ID from `pg_current_xact_id()`, which is of type `xid8`. Readers only return rows whose transaction is older than the oldest transaction still running.

The PostgreSQL documentation explains why this works. A snapshot's `xmin` is the "lowest transaction ID that was still active. All transaction IDs less than `xmin` are either committed and visible, or rolled back and dead". So every row below that horizon is final. `xid8` is 64-bit and "does not wrap around during the life of an installation", which makes it safe to persist in a checkpoint.

Implementations:

- **Emmett (`emmett-postgresql`).** It reads with `(transaction_id, global_position) > (...)` and `transaction_id < pg_snapshot_xmin(pg_current_snapshot())`, ordered by `transaction_id, global_position`.
- **eugene-khyst `postgresql-event-sourcing`.** It uses the same predicate: `(e.TRANSACTION_ID, e.ID) > (:lastProcessedTransactionId::xid8, :lastProcessedEventId)` together with `e.TRANSACTION_ID < pg_snapshot_xmin(pg_current_snapshot())`.
  - The checkpoint row stores both `LAST_TRANSACTION_ID` and `LAST_EVENT_ID`, and is claimed with `FOR UPDATE SKIP LOCKED`.
  - A trigger on the event table issues `NOTIFY` so that consumers wake on new events. The JDBC driver still polls for notifications with a timeout, so a timed fallback stays in place.

Properties and caveats:

- **The checkpoint is a pair, `(transaction_id, position)`, not a position.** Delivery follows transaction-ID assignment order, which is neither commit order nor position order. Dudycz notes that it "respects transaction start order, not append order".
- **Long transactions block delivery.** Dudycz says publication is delayed "until all older transactions complete". Sequin says "any long-running transaction in your system will set a ceiling", even one that never touches the event table.
  - `pg_current_snapshot` reports which transaction IDs are in progress across the server, not just for one table.
  - `pg_xact_status` reports prepared transactions as `in progress`. This implies, without being stated, that a forgotten prepared transaction would hold the horizon indefinitely.
- **The notification can arrive before the horizon allows the read** (inference). The wake-up from B's commit may find B's rows still held back behind an older transaction. If that older transaction is another append, its own commit will notify. If it is unrelated, its end produces no notification. A consumer that finds committed rows held back must therefore schedule its own re-check.

### 3. Snapshot-difference batching (PgQ)

PgQ, Skype's queue extension, uses snapshots directly instead of a single cut-off:

- A ticker periodically writes tick rows, and each tick carries a snapshot. Tick creation is controlled by `queue_ticker_max_count`, `queue_ticker_max_lag` and `queue_ticker_idle_period`.
- A batch is everything between two ticks. The batch SQL selects events whose `ev_txid` is "visible in the current snapshot but invisible in the previous snapshot", using `txid_visible_in_snapshot(ev.ev_txid, cur.tick_snapshot) AND NOT txid_visible_in_snapshot(ev.ev_txid, last.tick_snapshot)`.
- To keep the scan small, it limits the range to "[xmax1..xmax2]". It picks up transactions that were still running at the previous tick by listing `txid_snapshot_xip(batch.last_snapshot)` explicitly.

The effect (an inference from the SQL): each committed transaction lands in exactly one batch, and one long-running transaction does not hold back everything committed after it. The price is that the consumer's position is a snapshot (xmin, xmax and the in-progress list) rather than a single number, and events are delivered in visibility order, not position order. The modern equivalents of these functions are `pg_visible_in_snapshot(xid8, pg_snapshot)` and `pg_snapshot_xip`.

### 4. Gap detection with waiting, liveness checks and timeouts

Stores that keep sequence positions without transaction IDs treat a hole as "maybe still in flight" and wait before deciding it is permanent.

**Marten (.NET).** The async daemon's HWM is "the furthest known event sequence that the daemon 'knows' that all events with that sequence or lower can be safely processed in order".

- It reads the highest *committed* `seq_id` from `mt_events`, deliberately "never mt_events_sequence.last_value, which includes numbers reserved by transactions still in flight". It then walks forward to find where `next_seq - seq_id > 1`.
- `StaleSequenceThreshold` (default 3 seconds) controls when a stuck gap is considered for skipping. Recent versions also ask whether "any transaction [is] still running that could have reserved it".
  - A liveness probe checks `pg_locks` for row-exclusive locks on the events table, open client transactions, and in-progress write transaction IDs.
  - It ignores the daemon's own advisory-lock sessions.
  - It applies an "allocation fence": the latest server time at which the sequence's reserved `last_value` was still at or below the stuck mark. Every number in the gap was allocated after that time, so a session idle since before it cannot hold one.
- Proven-dead spans are skipped in one step and recorded in `mt_high_water_skips`. The clock for a stuck gap is stored in `mt_event_progression`, so it survives restarts.
- `SkipStaleGapsDespiteLiveTransactionsAfter` sets an upper limit; its default of null "never knowingly skips past a live appender". `AdvanceHighWaterMarkToLatestAsync` is a manual override.
- The daemon looks for a new HWM every 250 ms when busy and every 1 s when quiet.

**Axon Framework (JDBC storage engine).** `GapAwareTrackingToken` does not stop at a gap. It stores the highest sequence seen (`index`) plus the set of lower sequence numbers "that have not been seen yet". On each fetch it checks whether a gap has been filled, and delivers late events when they appear.

| Builder setting | Default | Meaning |
| --- | --- | --- |
| `gapTimeout` | 60 s | after this time a gap "may be considered timed out" |
| `maxGapOffset` | 10,000 | maximum distance in sequence numbers between a gap and the highest index |
| `gapCleaningThreshold` | 250 | number of gaps in a token before a clean-up is attempted |

This trades a stall for out-of-order delivery. Nothing committed within the timeout is skipped.

**Prooph PDO event store (PHP).** `GapDetection` exists because "projections skip events due to newer events becoming visible before old ones".

- It sees a gap when `streamPosition + 1 ≠ eventPosition`.
- It retries after 0, 5, 50 and 500 ms, then accepts the gap.
- An optional detection window turns retries off for old events during replays, because "during replays only gaps caused by transaction rollbacks are possible".

The weakness of all timeout-based schemes is that a transaction slower than the threshold is skipped. Marten's liveness probe is a way to replace that guess with proof. Since a rolled-back transaction never notifies, a gap left by a rollback cannot be resolved by a notification, so these schemes rely on timers.

### 5. Advisory-lock fencing of in-flight positions (Sequin)

Sequin describes a middle ground that neither serialises writers nor waits on unrelated long transactions.

- Each writing transaction first takes `pg_try_advisory_xact_lock_shared(1, 0)`. This tags the session as an appender to the table.
- It then takes `pg_try_advisory_xact_lock((select last_value + 1 from seq))`. This lock records the lowest position the transaction could draw.
- Readers compute the minimum such lock key across the tagged sessions with a self-join on `pg_locks` (`l2.classid = 1`, `l1.classid = 0`, `locktype = 'advisory'`). Positions below that minimum are final.

The article calls it complex: it needs two locks per transaction "due to integer argument limits", and it depends on writers following the protocol. Only appenders to the table hold the ceiling back, which is better than an `xmin` horizon.

### What this means for a notification-driven consumer

These points are synthesis from the sources above:

- **A notification only says "re-read now".** It is not a cursor. Under any scheme except serialised writers, payload positions arrive in commit order, so they are not monotonic in position.
- **On each wake-up,** read from the checkpoint up to an HWM computed by one of the methods above, and only persist checkpoints at or below that HWM.
- **Re-checking cannot be fully event-driven.** Rollbacks, unrelated long transactions and finished in-flight appends that drew no new notification all leave nothing to wake on. Whenever a read finds rows held back, a gap, or committed rows above the horizon, the consumer needs a short timed re-check. Every implementation above that combines NOTIFY with a safe HWM also keeps a polling or timeout path.
- **The trade-offs:**
  - Serialised writers give the simplest consumer and a payload that is safe to trust, at the cost of write concurrency.
  - The `xid8` horizon gives correctness without coordinating writers, at the cost of composite checkpoints and stalls behind any long transaction.
  - Gap detection keeps plain positions but either waits or delivers late events out of order.
