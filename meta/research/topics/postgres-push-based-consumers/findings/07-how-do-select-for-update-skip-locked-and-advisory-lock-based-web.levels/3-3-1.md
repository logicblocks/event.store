# How do lease-based partition claims fence a stale or paused owner so that its late checkpoint writes and handler side effects cannot overwrite progress made by the consumer that took over the partition?

## Question

When consumers claim partitions with time-bounded leases, an owner can pause (GC, VM freeze, network stall) past its lease expiry, the partition can be taken over, and the old owner can then wake up and carry on as if it still owned the partition. What mechanism stops that stale owner's late checkpoint writes and handler side effects from overwriting or regressing the progress of the new owner? How does that mechanism map onto a PostgreSQL-backed consumer group?

## Findings

### A lease lets another consumer take over, but it does not stop the old owner writing

Expiry is what lets another consumer take over from an owner that has stopped responding. Expiry alone does not stop the old owner from making changes. Kleppmann's analysis of lock services puts it directly: "if the GC pause lasts longer than the lease expiry period, and the client doesn't realise that it has expired, it may go ahead and make some unsafe change." He cites HBase GC pauses lasting several minutes and a GitHub incident in which packets were delayed for about 90 seconds. A delayed write can reach storage after its lease has gone. The fix he describes is a **fencing token**: "a number that increases … every time a client acquires the lock". The storage that receives writes must "take an active role in checking tokens, and rejecting any writes on which the token has gone backwards". Under this design safety comes from comparing tokens, not from timing assumptions. Clocks and timeouts then only decide when a takeover may happen.

Google's Chubby paper describes the same mechanism under a different name. A lock holder can request a **sequencer**, "an opaque byte-string" containing the lock name, the lock mode and the lock generation number, and passes it to the servers it calls. "The recipient server is expected to test whether the sequencer is still valid and has the appropriate mode; if not, it should reject the request." Some servers cannot check sequencers. For those, Chubby offers a weaker fallback called **lock-delay**: when a holder fails, the lock cannot be reclaimed for a bounded period (up to one minute). The paper calls this "imperfect", because it narrows the window for delayed or reordered requests but does not close it.

Both sources reach the same conclusion. A stale owner can only be fenced by the resource it writes to. Every write must carry an ownership epoch, and the resource must reject any epoch that has been superseded.

### How established partitioned-consumer systems fence the checkpoint

- **AWS Kinesis Client Library (KCL).** Each shard's lease row in DynamoDB stores `leaseOwner`, `checkpoint` and `leaseCounter`, and "leaseCounter increases if the lease ownership is transferred to another worker". In the KCL source, `takeLease`, `renewLease` and `updateLease` are all DynamoDB conditional writes that expect the `leaseCounter` value the worker last saw, and all three increment it. Each acquisition also gets a UUID concurrency token. The renewer refuses an update when the token differs from the one it holds ("refusing to update lease … because concurrency tokens don't match") or when it no longer holds the lease. The checkpointer turns that refusal into a `ShutdownException`: "Can't update checkpoint - instance doesn't hold the lease for this shard". The checkpoint lives in the lease record, so a checkpoint write is a compare-and-set against the ownership counter. A takeover increments the counter, and any later checkpoint from the old owner then fails.
- **Apache Kafka consumer groups.** Under KIP-848, offset commits are validated against the member epoch and rejected with `STALE_MEMBER_EPOCH` or `FENCED_MEMBER_EPOCH`. A member that misses heartbeats for the session timeout is removed from the group. Partitions are revoked from the old owner before being assigned to a new one. A fenced member must "immediately abandon all its partitions and rejoin the group … with a member epoch equals to zero".
  - KIP-447 describes this note's exact scenario: client A pauses for GC, is timed out of the group, B receives A's partition, and A resumes and tries to commit. The fix is to send the group `generation.id` and `member.id` with transactional offset commits: "If one of the field is not matching correctly on server side, the client will be fenced immediately."
  - KIP-98 fences zombie producers the same way. A new instance with the same `transactional.id` "bumps up the epoch … so that any previous zombie instance of the producer is fenced off", and the old instance gets `ProducerFencedException`.
  - Together these mean Kafka commits the checkpoint and the handler's output records in one transaction, and the epoch fences both.
- **Azure Event Hubs event processor.** Ownership claims go through a checkpoint store that "guarantees that only one of the instances succeeds in claiming ownership of a partition". Ownership records carry an owner id, a last-modified time and an optional etag. However, the documented abstract `update_checkpoint` takes only the partition, sequence number and offset, with no owner or etag. So the interface contract does not fence checkpoint writes by ownership. The documentation relies instead on "at least once" delivery and tells users to make downstream systems idempotent.
- **Marten (a PostgreSQL event store, .NET).** Projection progress is updated with an optimistic compare-and-set on the previous position: `update … set last_seq_id = ?, … where name = ? and last_seq_id = ?`. If no rows are affected, it throws `ProgressionProgressOutOfOrderException`, meaning "the stored progression is not the floor this range was built from". Leadership comes from a session-scoped `pg_try_advisory_lock` that Marten monitors so it "notices when the connection holding the lock is lost". The compare-and-set fences overlapping ranges without a separate token: whichever owner commits a range first wins, and the other fails. It does not stop the stale owner's first commit, but it does prevent progress being lost or regressed.

### Mapping the pattern onto PostgreSQL

Put the checkpoint in the lease row, as KCL does, and add a monotonically increasing epoch that changes on every change of ownership. The following is a sketch built from the sources above, not a quoted implementation:

```sql
-- claim, or take over an expired lease: one statement, database clock only
UPDATE consumer_partition_leases
   SET owner_id    = %(me)s,
       lease_epoch = lease_epoch + 1,
       expires_at  = clock_timestamp() + %(ttl)s
 WHERE consumer_group = %(group)s AND partition = %(partition)s
   AND expires_at < clock_timestamp()
RETURNING lease_epoch, checkpoint;

-- the fence, inside the same transaction as the handler's writes
UPDATE consumer_partition_leases
   SET checkpoint = %(position)s,
       expires_at = clock_timestamp() + %(ttl)s
 WHERE consumer_group = %(group)s AND partition = %(partition)s
   AND lease_epoch = %(epoch)s
   AND checkpoint  < %(position)s;
-- zero affected rows: ROLLBACK, drop the partition, stop handling it
```

PostgreSQL's row-level concurrency rules make this safe. Under READ COMMITTED, an `UPDATE` that finds its target row already updated by a concurrent transaction waits for that transaction to commit or roll back. If it commits, "the search condition of the command (the WHERE clause) is re-evaluated to see if the updated version of the row still matches". That gives two cases:

- **The takeover commits first.** The stale owner's fencing `UPDATE` re-evaluates `lease_epoch = $epoch` against the new row version, matches nothing, and the transaction rolls back. The handler's database writes roll back with it.
- **The stale owner's fencing `UPDATE` locks the row first.** The takeover blocks until the stale transaction ends, then re-evaluates against the committed row and `RETURNING` hands it the advanced checkpoint. Progress has passed to the new owner rather than been overwritten. This holds even if the stale owner pauses between the fence and `COMMIT`, because the row lock keeps the new owner waiting.

Under REPEATABLE READ the stale transaction instead fails with "could not serialize access due to concurrent update", which also fences it. Either way, both writers are serialised on one row and only the current epoch can move the checkpoint.

These rules follow from the sources:

1. **Put the fence and the effects in one transaction.** The fence only protects work that commits or rolls back with it: read-model rows, outbox rows and the checkpoint together. This is the same design as Kafka's transactional offset commits.
2. **Lock the lease row; do not just read it.** A plain `SELECT` check at the start of the transaction is a check-then-act race under READ COMMITTED, because a takeover can commit between the check and the commit. (This follows from the isolation rules above.) The fence must take a row lock, either as a conditional `UPDATE` or as `SELECT … FOR NO KEY UPDATE` or `FOR SHARE` on the lease row; PostgreSQL holds these locks until the transaction ends.
   - Locking **early** holds the lease row for the whole handler transaction. A paused owner whose connection is still open then blocks the takeover. Bound this with `idle_in_transaction_session_timeout` or `transaction_timeout`, which terminate the session and release its locks, and give the taker a `lock_timeout`.
   - Locking **late**, as the last statement before `COMMIT`, keeps blocking short, but the fenced owner wastes its work.
3. **Fence on an epoch, not an owner id.** If a worker loses a lease and later wins it back, a check on owner id alone would accept a late write from its earlier tenure. This is why KCL issues a per-acquisition concurrency token and a counter, Kafka uses member and producer epochs, and Chubby uses a lock generation number.
4. **Use only the database clock, and use `clock_timestamp()`.** `now()` and `CURRENT_TIMESTAMP` return the transaction's *start* time and "do not change during the transaction". An expiry check written with `now()` inside a long handler transaction would test the lease against a stale time. `clock_timestamp()` returns the actual current time. Expiry only decides when a takeover is allowed; the epoch comparison is what provides safety.
5. **Optionally require the checkpoint to move forward.** The `checkpoint < $position` guard, or a Marten-style compare-and-set on the previous position, stops any path from moving the checkpoint backwards.

**If the claim is a session-level advisory lock rather than a lease row:** PostgreSQL holds the lock "until explicitly released or the session ends", and it is not released on rollback. This gives an implicit fence only if every handler write goes through the same session that holds the lock. If that session is terminated, its open transaction aborts and the lock is released in the same step, so a late write cannot commit through it. A paused owner whose connection is still open keeps the lock, so it delays the takeover but does not cause two owners. The hazard is a process that loses its lock-holding connection and keeps writing through another pooled connection. Nothing fences that, so an advisory-lock design still needs an epoch check on the checkpoint write. (This paragraph is an inference from the PostgreSQL advisory-lock rules and Marten's connection monitoring.)

### Side effects outside the database

Fencing only protects resources that check the token. Kleppmann asks for fencing "on all resource accesses under the lock", and Chubby relies on lock-delay for servers that cannot check sequencers. An HTTP call or broker publish made before a fenced commit fails cannot be undone. The sources point to four mitigations:

- **Transactional outbox.** Write outgoing messages to an outbox table in the same fenced transaction, so they exist only if the stale owner's commit wins. The relay "might publish a message more than once", so receivers must be idempotent.
- **Forward the epoch** to downstream resources that can reject superseded epochs, as Chubby does with sequencers.
- **Idempotency keyed on event identity or position,** as Azure recommends for at-least-once processing.
- **A grace delay after expiry before the new owner starts** (Chubby's lock-delay). This narrows the window but, like an owner checking its own lease before each effect, cannot close it: the owner can pause just after the check.
