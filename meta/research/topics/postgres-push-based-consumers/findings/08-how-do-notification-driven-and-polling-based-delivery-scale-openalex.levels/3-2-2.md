# How do work-stealing and partition-rebalancing schemes keep per-stream event ordering intact when idle consumers claim work from partitions owned by other consumers?

## Question

When competing consumers share a backlog and an idle consumer takes work that
another consumer owns, either by stealing it or through a rebalance, how do
published schemes stop that transfer from reordering events within a single
stream?

## Findings

### The tension: stealing assumes independent work, ordering is a dependency chain

Classical work stealing, as analysed by Blumofe and Leiserson, has processors
that need work steal computational threads from other processors. Its
guarantees hold for "fully strict" computations, whose dependencies are well
structured, and a thread is stealable only when its dependencies allow it to
run. Per-stream event ordering is the most restrictive dependency structure
there is: event *n+1* of a stream depends on event *n*. Inside one stream,
nothing is safe to steal in parallel with its predecessor. Order-preserving
schemes therefore all make the same structural move. **The unit that gets
stolen or rebalanced is the ordering domain itself: a whole stream, key or
partition, never individual events.** Load balancing works across ordering
domains and never inside one.

### Key grouping: one owner per key, rebalanced as whole keys

Stream-processing research formalises this as *key grouping*. Rivetti et al.
(DEBS) describe it as partitioning a stream into disjoint sub-streams by key,
so that each operator instance receives all the tuples for a given key. That
guarantee is what preserves per-key order and per-key state. Its known cost is
imbalance. Hash-based assignment overloads some instances when key frequencies
are skewed, and the work aims at near-optimal balance by choosing a better
key-to-instance mapping while keeping the one-owner-per-key guarantee. Gedik et
al. (IEEE TPDS) address the dynamic version of the problem. Auto-parallelisation
replicates regions of the data-flow graph and applies data partitioning, and
the number of parallel channels is adjusted at run time as workload and
resources change. For partitioned stateful operators, changing the channel
count means moving key ranges, and their state, between channels. Schneider et
al. (PACT) show that this kind of automatic data parallelism can be made safe
even for stateful and user-defined operators: when the compiler builds parallel
regions, it preserves first-in-first-out semantics, so the parallelised
application observes the same order as the sequential one.

The consistent lesson is that rebalancing preserves order when it reassigns
*whole* keys or partitions. Rebalancing then affects where a stream is
processed, never the sequence in which its events are processed.

### Key splitting: better balance bought by giving up per-key order

The alternative is to split a hot key across several workers. Partial Key
Grouping (Nasir et al., ICDE and arXiv) adapts the "power of two choices" to
streams. Each key may go to one of two workers, chosen by local load
estimates, which balances load much better than key grouping and scales better
than shuffle grouping. Adaptive key partitioning (Liu et al.) similarly applies
key splitting selectively to frequent keys. Splitting a key means two
consumers hold events of the same key at the same time, so neither sees a
total order. Splitting is sound only when the downstream computation can merge
partial results (associative or commutative aggregation). It is not sound for
event-sourced projections, which must apply a stream's events in sequence.
Consistent Grouping (Nasir et al., arXiv) takes a middle path suited to
ordered consumers. It is built on small units of work assigned to processing
instances according to their capacity. Fine granularity, rather than key
splitting, then provides balance on heterogeneous clusters while each unit
keeps a single owner.

### Making the handover itself order-safe

Coarse-grained transfer alone is not enough. The transfer also needs a
barrier, so that the old and new owners never process the same stream at the
same time and the new owner resumes exactly where the old one stopped. Three
recurring mechanisms appear in the records:

1. **Checkpointed position plus replay.** SEEP (Castro Fernandez et al.)
   integrates scale-out and fault tolerance through explicit operator state
   management. Operator state is externalised and checkpointed, and when an
   operator is scaled out, the checkpointed state is partitioned across new
   instances and unprocessed upstream tuples are replayed. Ordering survives
   because the new owner starts from a consistent checkpoint and replays the
   tail in its original order.
2. **Explicit handover protocols for live reconfiguration.** Rhino (Del Monte
   et al.) names the three problems of on-the-fly reconfiguration of stateful
   queries as network overhead for state migration, consistency, and overhead
   on data processing. It addresses them with a library that coordinates
   ownership transfer and state migration so that the new instance resumes
   consistently, without a global stop.
3. **Atomic progress commits and fencing of stale owners.** The Kafka Streams
   paper (Wang et al., SIGMOD) aims for strong correctness under unexpected
   failures and out-of-order data. In Kafka's consumer-group model, partitions
   are reassigned whole during a rebalance. Consumed positions, state changes
   and outputs are committed together transactionally, and a previous owner
   that has lost its assignment is fenced so that it cannot commit. The new
   owner therefore resumes at the last committed offset, and a "zombie" owner
   cannot interleave late writes.

### Implications for PostgreSQL event-table consumers

None of the records studies PostgreSQL consumers directly, but their
invariants carry over.

- **Make the ordering domain the unit of claim.** Idle consumers should claim
  whole streams, or hash partitions of streams, never individual events.
  Claiming partitions through row locks taken with `SKIP LOCKED`, or through
  advisory locks keyed by partition, gives each partition a single owner. Lock
  release when the owner's session ends gives the lease behaviour that
  checkpoint-and-replay schemes need.
- **Commit position and effects together.** Store the consumer's position for
  a partition in the same transaction as its side effects. The next claimant
  then resumes exactly after the last committed event, which is the
  equivalent of Kafka's atomic offset commit or SEEP's checkpoint.
- **Fence stale owners.** If ownership can lapse while a slow consumer is
  still running, for example when a lease expires rather than a session
  ending, have each owner check an epoch or ownership token in its commit.
  This is the equivalent of Kafka's zombie fencing.
- **Balance through granularity, not splitting.** Hash streams into many more
  partitions than consumers, in the style of Consistent Grouping's small
  units. Idle consumers then have something to claim, and skew evens out. The
  limit from key-grouping research remains: one hot stream can never be
  processed faster than a single consumer can process it, because
  parallelising inside a stream is exactly what key splitting does at the cost
  of order.
