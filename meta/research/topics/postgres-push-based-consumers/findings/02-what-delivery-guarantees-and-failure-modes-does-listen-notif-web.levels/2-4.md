# Can PostgreSQL logical decoding or logical replication slots give an event store durable, resumable push delivery that avoids the NOTIFY commit lock, and what operational risks do slots carry?

## Question

Can a logical replication slot, read through PostgreSQL's logical decoding, serve as a durable push channel for an append-only event store? That means consumers survive disconnects and restarts without missing events, and writers avoid the global lock that `NOTIFY` takes at commit. What operational risks come with slots?

## Findings

### Short answer

Mostly yes, with three qualifications. A logical replication slot is a cursor over the write-ahead log (WAL) that lives on the server and survives crashes. A consumer streaming from it receives every committed change, in commit order, and continues from its last confirmed position after a disconnect. Writers do nothing extra at commit, so the `NOTIFY` lock never comes into play.

The qualifications:

- **At-least-once, not exactly-once.** A crash can replay changes, so consumers must handle duplicates.
- **Retention cost.** A slot keeps WAL and catalog rows until its consumer confirms progress. An abandoned or stalled slot is a real way to fill the disk.
- **Setup and HA cost.** Slots need server-level configuration and the `REPLICATION` privilege, and they only survive failover from PostgreSQL 17 onwards.

For a library built on psycopg 3 there is a further practical blocker. psycopg 3 does not implement the streaming replication protocol (see "Configuration, privileges and client support" below).

### Why slots sidestep the NOTIFY commit lock

`PreCommit_Notify` in PostgreSQL's `async.c` still takes `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)` on the master branch. The source comment explains why: "Serialize writers by acquiring a special lock that we hold till after commit. This ensures that queue entries appear in commit order". Recall.ai described this lock serialising all committing writers under heavy concurrency, so that throughput collapsed even though CPU and I/O usage fell. The PostgreSQL 19 beta release notes improve `NOTIFY` so that it wakes only backends listening on the relevant channels. The commit-time lock in the source is unchanged.

Logical decoding works differently. It is "implemented by decoding the contents of the write-ahead log" for each slot after the WAL has been written. An append transaction writes only its normal WAL and takes no extra lock. It follows (an inference from how decoding works, not a benchmark) that moving wake-ups from `NOTIFY` to a slot takes the serialisation point off the write path entirely. Two costs remain:

- **Extra WAL.** `wal_level = logical` "increases WAL volume, particularly if many tables use `REPLICA IDENTITY FULL` and frequent `UPDATE`/`DELETE` statements are executed". For an insert-only events table the increase should be modest (inference).
- **Synchronous mode.** A slot consumer can be put back on the commit path by running logical decoding as a synchronous standby. The docs warn this can deadlock when a transaction holds exclusive locks on catalog tables, and that it only works when a single database is in use. Push delivery should stay asynchronous.

### Delivery semantics a consumer can rely on

- **Commit order, committed data only.** "Concurrent transactions are decoded in commit order". Rolled-back transactions "never get decoded", and changes reach the output plugin only when the transaction commits. This matters for event stores. Sequence-assigned positions are fixed before commit, so transactions can commit out of position order, and position-based pollers can skip events that were still in flight. A slot stream never delivers a later commit ahead of an earlier one. The catch is that event positions in the stream are not monotonic, so a consumer cannot checkpoint by "highest position seen" (inference).
- **Once in normal operation, replays after a crash.** "A logical slot will emit each change just once in normal operation". However, "the current position of each slot is persisted only at checkpoint, so in the case of a crash the slot might return to an earlier LSN, which will then cause recent changes to be sent again". The docs make clients responsible for duplicates: record the last LSN seen and skip repeats, or ask decoding to start from that LSN. Replication origins exist for this purpose.
- **Resumption and acknowledgement.** `START_REPLICATION SLOT ... LOGICAL` streams from whichever is greater: the requested LSN or the slot's `confirmed_flush_lsn`. The consumer advances that position with the flushed LSN in its standby status updates. Data committed before `confirmed_flush_lsn` "is not available anymore" from the slot. A consumer must therefore acknowledge only after it has durably handled the event. An early acknowledgement cannot be undone through the slot, although the rows are still in the events table.
- **One reader per slot.** "Only one receiver may consume changes from a slot at any given time", and a slot "knows nothing about the state of the receiver(s)". Independent consumers each need their own slot, or a single dispatcher reads one slot and fans events out.
- **Large transactions arrive in one burst.** Decoded changes are buffered until commit. Above `logical_decoding_work_mem` they spill to disk, unless the plugin streams in-progress transactions (pgoutput protocol version 2+, PostgreSQL 14+). A bulk import arrives all at once when it commits.
- **A slot does not replay history.** It covers only changes after it was created. A new consumer, or one whose slot was lost, must catch up from the events table. When a slot is created through the replication protocol it exports a snapshot that "will show exactly the state of the database after which all changes will be included in the change stream". That snapshot gives a consistent handover point between reading the table and reading the stream.
- **Slot creation can block.** A new slot reaches a consistent state only after the transactions running when it started have finished. Creating slots on demand, for example each time a consumer starts, can therefore stall behind a long-running transaction.
- **Messages without a table.** `pg_logical_emit_message(transactional, prefix, content)` writes an arbitrary message into the WAL. If `transactional` is true, the message is decoded as part of its transaction. pgoutput forwards these messages when its `messages` option is enabled. They can serve as an in-transaction "doorbell" or as heartbeats. pgoutput itself requires at least one publication.

### Operational risks of slots

1. **Unbounded WAL retention.** Slots "persist across crashes and know nothing about the state of their consumer(s). They will prevent removal of required resources even when there is no connection using them." The standby documentation warns that slots can retain so many segments "that they fill up the space allocated for `pg_wal`". The psycopg2 docs say that failing to keep consuming and reporting progress "can eventually lead to 'disk full' condition on the server". AWS warns that an unread slot can "quickly fill up your DB instance's storage".
2. **Vacuum and wraparound.** A slot's `catalog_xmin` stops `VACUUM` from removing catalog rows it still needs. "In extreme cases this could cause the database to shut down to prevent transaction ID wraparound."
3. **Idle streams still pin WAL.** If the published table is quiet while other activity generates WAL, a consumer that only acknowledges when it receives events never moves its slot forward. Gunnar Morling recommends periodic heartbeats via `pg_logical_emit_message()` for this. The protocol also lets a client confirm progress without having received data.
4. **Safety valves turn disk-full into a lost slot.**
   - `max_slot_wal_keep_size` is unlimited by default (`-1`). Once a slot falls further behind than the cap, its `wal_status` goes from `unreserved` to `lost`, with `invalidation_reason = wal_removed`.
   - `idle_replication_slot_timeout` (PostgreSQL 18, disabled by default) invalidates slots left inactive too long, with `invalidation_reason = idle_timeout`.
   - Morling's guidance is that losing a slot is "inconvenient but preferable to disk exhaustion". Suggested alerts: disk above 60–70%, a slot inactive for more than 30 minutes, or a slot retaining more than 10–20 GB.

   An invalidated slot cannot be used again. It must be dropped and recreated, and the consumer must catch up from the table. Because the events table is the source of truth in an event store, this is recoverable. That argues for treating the slot as a speed-up rather than the system of record.
5. **Failover.** Logical slots can be synchronised to standbys only from PostgreSQL 17 ("Enable the failover of logical slots"). This requires:
   - a slot created with `failover = true`
   - a physical slot between primary and standby
   - `hot_standby_feedback` on the standby
   - `sync_replication_slots` on the standby
   - ideally, the standby's physical slot listed in `synchronized_standby_slots`

   Logical walsenders then hold back changes until the listed standbys confirm them, and "logical replication will not proceed" if one of those slots is missing or invalidated. The docs also warn that if the old primary comes back during promotion, consumers may keep reading from it and end up inconsistent. On earlier versions a promotion loses the slot, so consumers must recreate it and recover from the table.
6. **Configuration and capacity.**
   - **`wal_level`.** Changing `wal_level` requires a restart up to PostgreSQL 18. In PostgreSQL 19, which was in beta as of September 2026, a server set to `replica` switches to `logical` automatically when the first logical slot is created; the new `effective_wal_level` setting reports the level actually in force.
   - **Connection limits.** `max_replication_slots` and `max_wal_senders` both default to 10. `max_wal_senders` should sit slightly above the expected number of clients, because an abruptly disconnected client can leave an orphaned walsender behind until a timeout.
   - **Decoding cost.** Every streaming consumer occupies a walsender, and each slot decodes the WAL for itself (inference). Decoding cost therefore grows with the number of slots.
7. **Privileges and managed services.** The replication role needs the `REPLICATION` attribute (or superuser) and a `pg_hba.conf` entry that allows replication connections. On Amazon RDS, `rds.logical_replication` is a static parameter that needs a reboot, plus the `rds_replication` role. AWS notes it increases WAL generation.

### Configuration, privileges and client support

psycopg 3 issue #71, "Add support for streaming replication as in psycopg2", has been open since August 2021. psycopg2 provides `LogicalReplicationConnection` with `consume_stream` and `send_feedback(flush_lsn=...)`. The SQL functions `pg_logical_slot_get_changes` and `pg_logical_slot_peek_changes` work over an ordinary connection, but they pull rather than push, which brings polling back. Replication connections also accept only the simple query protocol. A psycopg 3 library therefore needs a separate replication-capable client (psycopg2, `pg_recvlogical`, or a sidecar) to receive pushed changes.

Practitioner accounts agree: logical replication "was built for change data capture" and gives stronger durability and ordering than `NOTIFY`. However, "replication slots and the replication protocol are less familiar to most developers" and need "specific strategies … to ensure that you don't miss messages during restarts" (Sequin). Oskar Dudycz's push-based outbox prototype on Npgsql reports at-least-once delivery and one consumer per slot, and is explicitly not yet used in production.

### Two viable designs for an event store

- **Slot as the durable channel.** One permanent slot per consumer group, or one dispatcher that fans out. The consumer acknowledges the flushed LSN only after durably recording its own checkpoint (an LSN), and handlers are idempotent. New or invalidated consumers catch up from the events table using the slot's exported snapshot. Operate it with `max_slot_wal_keep_size`, heartbeats, slot-lag alerts and, on PostgreSQL 17+, failover slots. This gives commit-ordered, gap-free delivery without the `NOTIFY` lock, at the cost of every risk listed above.
- **Slot as a doorbell.** Each listener uses a *temporary* slot, which "should not be permanently stored to disk", is "only meant for use by the current session" and is "released upon any error". A dead consumer therefore cannot pin WAL. Decoded commits only wake the consumer, which then reads the events table from its own checkpoint, and every reconnect starts with a table catch-up. This keeps the lock avoidance and drops the retention risk. The durability comes from the table rather than the slot. It still needs the `REPLICATION` privilege, one walsender per listener and logical WAL, and creating the slot on each reconnect can block behind long transactions.
