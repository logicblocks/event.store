# How does `LISTEN`/`NOTIFY` interact with connection poolers and connection limits — PgBouncer session versus transaction mode, other poolers and managed proxies (such as RDS Proxy pinning, Supavisor and PgCat), and the cost of a dedicated session connection per listener — and how does psycopg 3 expose asynchronous notifications and support keeping a long-lived listener connection healthy (keepalives, idle timeouts, reconnection)?

## Question

How does PostgreSQL's `LISTEN`/`NOTIFY` behave behind connection poolers and managed proxies (PgBouncer session versus transaction pooling, RDS Proxy, Supavisor, PgCat and similar), what does it cost to hold a dedicated session connection for each listener, and what does psycopg 3 offer for receiving asynchronous notifications and for keeping a long-lived listener connection healthy through keepalives, idle timeouts and reconnection?

## Findings

### The root asymmetry: `LISTEN` is session state, `NOTIFY` is transactional

Every pooler behaviour below follows from how PostgreSQL scopes the two commands.

- `LISTEN` "registers the current session as a listener", and "a session's listen registrations are automatically cleared when the session ends". It "takes effect at transaction commit", and a rolled-back `LISTEN` changes nothing. A single session can listen on any number of channels.
- Notifications reach a client only between transactions. If a listening session receives a notification "while it is within a transaction, the notification event will not be delivered to its connected client until just after the transaction is completed". A `NOTIFY` sent inside a transaction is delivered only if that transaction commits.
- A listener that sits inside a long-running transaction stops the shared notification queue from being cleaned up. The queue is 8 GB in a standard installation, the log warns once it is half full, and when it fills, "transactions calling `NOTIFY` will fail at commit". A listener must therefore never sit idle inside a transaction.
- On a hot standby, `LISTEN` and `NOTIFY` both raise errors (only `UNLISTEN` is allowed). A listener has to connect to the primary.
- PostgreSQL's documented way to avoid missing updates is to run and commit `LISTEN` first, then inspect database state in a new transaction, then rely on notifications for later changes.

So `NOTIFY` (or `pg_notify` called from a trigger in the writing transaction) works through any pooler that keeps the transaction on one backend. `LISTEN` needs the same backend for as long as the subscription lasts. PgBouncer's compatibility table says exactly this: under transaction pooling, `NOTIFY` is "Yes" and `LISTEN` is "Never".

### PgBouncer

- **Modes.** In session pooling, the server connection "is released back to pool after client disconnects", and session pooling "supports all PostgreSQL features". Session is PgBouncer's default `pool_mode`. Transaction pooling releases the server connection when each transaction finishes. It breaks session features: `LISTEN`, `SET`/`RESET`, SQL-level `PREPARE`/`DEALLOCATE` and session-level advisory locks are all "Never". Protocol-level prepared statements work if `max_prepared_statements` is set. `server_reset_query` (default `DISCARD ALL`) is not used in transaction mode, "because in that mode, clients must not use any session-based features."
- **How it fails.** PgBouncer gives no error when `LISTEN` goes through a transaction pool. A practitioner guide describes the result: the registration stays on a backend the client no longer holds, so notifications go "to a backend connection your client no longer holds, or to whichever client happens to hold that connection next". Tests with a single client often pass, and the problem only appears under concurrent load. The publish path also works, which hides the problem further.
- **Workarounds.** `pool_mode` can be overridden per database and per user in the `[databases]` and `[users]` sections. A common pattern is a second database alias in session mode, used only by listener connections, while all other traffic stays on the transaction-mode alias. The other option is to connect listeners directly to PostgreSQL.
- **Limits that apply to a session-mode listener.**
  - Each listener holds one server connection for as long as it is connected. That connection counts against `default_pool_size`, which defaults to 20 per user and database pair, and against `max_db_connections`, which defaults to unlimited.
  - `server_lifetime` (default 3600 s) only closes *unused* server connections, so it never recycles a held session.
  - `client_idle_timeout` (default 0, disabled) closes clients that are idle too long. If it is turned on, a quiet listener could be closed; the docs do not say whether server-pushed notifications count as activity.
  - `tcp_keepalive` is on by default with OS defaults. `tcp_keepidle`, `tcp_keepintvl`, `tcp_keepcnt` and `tcp_user_timeout` are available for tuning.
- **Native support in transaction mode.** Issue #655, opened in November 2021, asks PgBouncer to keep one upstream listener and fan notifications out to subscribers. It is still open.

### Amazon RDS Proxy

- "Listening on a notification channel" is one of the PostgreSQL conditions that cause **pinning**. A pinned client uses the same database connection for every later transaction "until the session ends". No other client can reuse that connection, and "the session ends when the client connection is dropped". Pinned connections are also not counted as idle for `MaxIdleConnectionsPercent`. A listener behind RDS Proxy therefore gets no multiplexing benefit and acts like a direct connection with an extra network hop. Other PostgreSQL pinning triggers include `SET`, session-level advisory locks, `nextval` and `setval`, and `DISCARD ALL` used as a pool reset query.
- **Timeouts.**
  - `IdleClientTimeout` defaults to 30 minutes and can be set from 1 minute to 8 hours.
  - The proxy counts a client as idle when it "doesn't submit a new request". AWS notes that even `SELECT 1` health checks reset this timer. This implies that a listener which only receives notifications could be closed after the idle timeout unless it sends periodic queries. That reading is inferred from the definition; AWS does not say how server-pushed messages are treated.
  - RDS Proxy also enforces "a maximum connection lifetime of 24 hours, regardless of whether the connection is idle".
- **Guidance.** AWS names two legitimate reasons for client-side liveness checks: deliberately keeping specific connections from timing out, and detecting connections the proxy dropped (for example, pinned connections closed by a database restart, or the 24-hour limit). It recommends ordering timeouts as `client timeout < proxy timeout < database timeout`.

### Supavisor (Supabase)

- Supavisor has three pool modes. Transaction mode holds a connection for one transaction. Session mode "assigns a connection to a client for the duration of the client connection". Native mode proxies the client "as if it was directly connected".
- On Supabase, port 5432 is session mode and port 6543 is transaction mode. Session mode on port 6543 was deprecated on 28 February 2025, so session features need port 5432.
- Supabase lists `LISTEN`/`NOTIFY` as unsupported in transaction mode: session-level `listen` and `notify` commands "are lost between transactions". Its paid-plan dedicated pooler is PgBouncer in transaction mode only.
- For persistent backends such as VMs and long-running containers, Supabase recommends the direct connection.
- Session mode on the shared pooler gives each client an exclusive backend. Supabase's FAQ warns that in session mode the first clients to take the direct connections "could keep them, even if they are no longer executing queries".

### PgCat

PgCat describes its session pooling as "Identical to PgBouncer" and its transaction pooling as like PgBouncer's, with better handling of bad clients. Its transaction-mode limitations list prepared statements, `SET` and advisory locks; the README does not mention `LISTEN`. It is inferred, not documented, that `LISTEN` works in PgCat session mode and is unsafe in transaction mode for the same reason as in PgBouncer.

### PgDog (a pooler with transaction-mode pub/sub)

PgDog is the one pooler found that supports `LISTEN`/`NOTIFY` in transaction mode.

- It is disabled by default and enabled with `pub_sub_channel_size`.
- On `LISTEN`, PgDog registers with PostgreSQL on a dedicated server connection, with one registration per channel however many clients subscribe. It fans notifications out to clients through an in-process broadcast channel.
- `NOTIFY` is queued and forwarded over a dedicated connection. Inside a transaction it is buffered until commit and discarded on rollback.
- The documented trade-offs: clients get an acknowledgement immediately but forwarding can lag behind a backlog; `NOTIFY` delivery is "at most once" and can be lost if a connection breaks; PgDog reconnects immediately after failures.
- Its author describes the point of this design: PostgreSQL "only has to send a message as many times as there are instances of PgDog".

### Other managed poolers

- **Google Cloud SQL Managed Connection Pooling.** It defaults to transaction mode, where `LISTEN` is unsupported. Session mode "uses a dedicated server connection that maintains a session state". `client_connection_idle_timeout` defaults to 0 and `server_connection_idle_timeout` defaults to 600 s.
- **Neon.** Its pooled endpoint is PgBouncer with `pool_mode=transaction` and `max_client_conn=10000`. `LISTEN`/`NOTIFY` are not supported on it, and Neon points users who need them to direct connections.

### The cost of one dedicated session connection per listener

- Every listener that bypasses transaction pooling is a real PostgreSQL backend. It counts against `max_connections` (typically 100 by default), and some server resources, including shared memory, are sized from that setting. A pooler's high client limit therefore does not help listeners: they are charged against the database's own connection budget.
- Andres Freund's 2020 analysis found that each connection costs "a few MiB", and under 2 MiB with `huge_pages`. The larger problem was CPU: on pre-14 PostgreSQL, idle connections slowed active work through `GetSnapshotData()`, and 5,000 idle connections cut one active connection's throughput by more than half. PostgreSQL 14's snapshot-scalability work, as reported by pganalyze, raised throughput from about 15,000 to nearly 35,000 TPS with 10,000 idle connections plus one active query.
- **Design implication.** One session can listen on many channels. The cheaper pattern is therefore one listener connection per process or service, fanned out in-process, rather than one per consumer. Behind RDS Proxy, each pinned listener also takes a slot from the proxy's pool permanently.

### psycopg 3: receiving notifications

- **Basics.**
  - The connection should be in autocommit mode "if you wish to receive or send notifications in a timely manner". This also keeps the listener from sitting idle in a transaction, since psycopg otherwise opens a transaction implicitly.
  - A plain blocking `Connection` works fine; an `AsyncConnection` is not required.
  - Notifications arrive as `Notify` objects with `channel`, `payload` and `pid`.
- **Two mechanisms; use only one.** Using both on one connection raises a `RuntimeWarning` since 3.2.10.
  - The `notifies()` generator, or an async generator on `AsyncConnection`, is intended for connections dedicated to notifications.
  - `add_notify_handler()` callbacks fire only "during a connection operation, such as a query". They do not run a background reader.
- **`notifies(timeout=..., stop_after=...)`** has been available since 3.2.
  - Before 3.2, maintainer Daniele Varrazzo wrote that the generator "proved harder to use than expected": during the loop, "the connection cannot be used to run queries", including `LISTEN`/`UNLISTEN`, and stopping it required `gen.close()` from another task or thread. Issue #340 reported that `AsyncConnection.execute()` hung while the generator was active.
  - The implementation still holds the connection lock for as long as the generator runs. The intended pattern is a loop that calls `notifies(timeout=N)` and, between calls, changes channel registrations or runs health checks.
- **Fixes along the way.**
  - 3.2.4 stopped losing notifications that arrive while the generator is not running. They are now kept in a backlog and delivered on the next call (#962), and handlers are called while the generator runs (#972).
  - 3.2.10 fixed a leak introduced by that change. The backlog grew without bound when `notifies()` was never called; the reporter saw about 200 MB per hour at more than 10,000 events per minute (#1091). This matters for any connection that has `LISTEN` registrations but no consumer.
- **Mechanics.** psycopg follows libpq's recommended approach: wait for the socket to be readable with no CPU use, call `PQconsumeInput`, then drain `PQnotifies`. If `PQconsumeInput` fails, psycopg raises `OperationalError("consuming input failed: ...")`. A server-closed or reset connection therefore shows up as an exception from the `notifies()` loop.

### psycopg 3: keeping a long-lived listener healthy

- **Detecting a lost connection.**
  - psycopg's documented pattern registers `conn.fileno()` with `selectors`, or with `loop.add_reader` under asyncio. When the socket becomes readable, it runs `SELECT 1` and treats `OperationalError` as "we lost our database".
  - `Connection.closed` and `Connection.broken` (closed uncleanly) expose the connection's state.
  - Socket readiness only helps if the network actually delivers a FIN or RST. A path that silently drops packets may never make the socket readable, so a `notifies()` call with no timeout could wait forever. This is inferred from the mechanism and is why TCP keepalives and a bounded `timeout` both matter.
- **TCP keepalives.**
  - Client side: psycopg passes libpq parameters through the conninfo string or keyword arguments. `keepalives` defaults to on, but with system defaults. `keepalives_idle`, `keepalives_interval` and `keepalives_count` tune probing, and `tcp_user_timeout` limits how long transmitted data may stay unacknowledged.
  - Server side: `tcp_keepalives_idle`, `tcp_keepalives_interval`, `tcp_keepalives_count` and `tcp_user_timeout` are the equivalents. `client_connection_check_interval` only applies while a query is running, so it does not help an idle listener.
  - Middleboxes enforce their own idle limits. An AWS NAT gateway times out connections idle for 350 s or more and answers further traffic with an RST. AWS recommends traffic or TCP keepalives under 350 s.
- **Server-side idle timeouts.**
  - `idle_session_timeout` (default 0) terminates sessions that are idle outside a transaction, which describes a listener waiting for notifications. The PostgreSQL docs warn against applying it to pooler connections.
  - `idle_in_transaction_session_timeout` and `transaction_timeout` do not affect an autocommit listener.
- **Connecting and reconnecting.**
  - psycopg enforces its own connect timeout: 130 s when `connect_timeout` is unset or zero or less, and at least 2 s. It tries each host and address in turn, and since 3.2.8 it reports every attempt's error.
  - `target_session_attrs=read-write` or `primary` makes a reconnection after failover land on the primary, which matters because `LISTEN` fails on a standby.
  - psycopg does not reconnect a standalone `Connection` automatically. The application has to catch `OperationalError`, reconnect with backoff, issue and commit `LISTEN` again, and then re-read durable state. The old session's registrations disappeared when it ended, and any `NOTIFY` sent while no session was listening is gone.
- **`psycopg_pool`.**
  - It offers `check` callbacks (with `ConnectionPool.check_connection`, added in 3.2) run on every checkout, plus `max_lifetime` (3600 s), `max_idle` (600 s) and `reconnect_timeout` (300 s, exponential backoff, then a `reconnect_failed` callback).
  - It only manages connections that are borrowed and returned. On return the pool ends any open transaction and calls an optional `reset` callback for "application-specific cleanup"; the docs do not describe a `DISCARD` or `UNLISTEN`.
  - Holding a pooled connection permanently as a listener bypasses `max_lifetime` recycling and permanently shrinks the pool. Returning a connection that ran `LISTEN` would leave its registration in place, an inference from session semantics.
  - A dedicated `Connection` outside the pool, with its own supervision loop, fits the listener role better.

### Implications for a psycopg 3 event store

- **Writers** can keep using transaction-pooled connections and issue `NOTIFY` inside the append transaction.
- **Each consuming process** should open one autocommit listener connection that bypasses transaction pooling: a direct connection, a session-mode alias in PgBouncer, port 5432 on Supavisor, or session mode on Cloud SQL. It should connect with `target_session_attrs=primary` and keepalive settings shorter than any middlebox idle limit, and loop on `notifies(timeout=...)` so it can periodically change registrations and run health checks.
- **Behind RDS Proxy**, the listener should also send a lightweight query more often than `IdleClientTimeout` and expect a forced reconnection at least every 24 hours.
- **Notifications are lossy across reconnects.** Treat them as wake-up hints and back them with a catch-up read from each consumer's stored position.
