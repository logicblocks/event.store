# In psycopg 3 async code, does wrapping a heartbeat query in asyncio.timeout reliably abandon a half-open connection where TCP_USER_TIMEOUT is unavailable, as on macOS, or can psycopg's cancel attempt or close call block?

## Question
If a psycopg 3 `AsyncConnection` becomes half-open, will a heartbeat query (for example `SELECT 1`) wrapped in `asyncio.timeout(...)` reliably give up and let the consumer reconnect? This matters most where the kernel cannot do it, as on macOS, which lacks `TCP_USER_TIMEOUT`. Half-open means the peer is gone but no FIN or RST ever arrives. The question also asks whether psycopg's query-cancellation step or `close()` can block that escape.

## Findings

**Short answer: it depends on the versions.** With psycopg 3.3.6 or newer and libpq 17 or newer, the escape is reliable but late. `asyncio.timeout` raises `TimeoutError` up to about 10 seconds after its deadline, and the connection is left closed and marked broken.

With psycopg before 3.3.6, a single `asyncio.timeout` is not reliable at all. The task can hang indefinitely on a half-open socket. With libpq older than 17, even current psycopg cannot bound the cancel step. `close()` itself does not block.

**Why the kernel cannot be relied on.** libpq's `tcp_user_timeout` "is only supported on systems where `TCP_USER_TIMEOUT` is available; on other systems, it has no effect". Keepalive tuning also depends on platform socket options. A hang reported against psycopg also occurred behind a load balancer or proxy that keeps the client socket ESTABLISHED and keeps ACKing. In that setup "keepalive probes are answered by the middlebox, so they detect nothing, and `tcp_user_timeout` never fires because nothing sent is left unack[nowledged]". An application-level deadline is therefore needed on Linux too. macOS only removes one more kernel backstop.

**How `asyncio.timeout` works.** On expiry it cancels the current task. It turns the resulting `CancelledError` into `TimeoutError` only when that error propagates out of the block. Python's documentation warns that `Task.cancel()` "does not guarantee that the Task will be cancelled": the coroutine can clean up first, and that delays the exit. A single timeout issues a single cancellation. The deadline is only as good as the cancellation handling of the code inside the block.

**What psycopg does on cancellation.** `AsyncConnection.wait()` catches `asyncio.CancelledError`, `KeyboardInterrupt` and (from 3.3.6) `SystemExit`. If the transaction status is `ACTIVE`, it does two things before re-raising:

- It awaits `_try_cancel(timeout=5.0)`, which sends a server-side cancel request.
- It re-enters the wait on the original query, to consume the outcome.

libpq reports `PQTRANS_ACTIVE` "only when a query has been sent to the server and not yet completed", which is exactly the state of a stuck heartbeat. This behaviour was added in 3.1.9 (#543) so that cancelled tasks do not leave queries running or connections stuck "ACTIVE".

**psycopg before 3.3.6: not reliable.** In the 3.2.0 source the second `wait_async` call has no deadline. Issue #1371 (July 2026) reproduced the result:

- **Setup:** macOS, Python 3.11, psycopg 3.3.4 with libpq 17.9 and 18.0, and an in-process proxy that strands connections while still ACKing.
- **Symptom:** the cancelled task sat in `cancelling=1, cancelled=False` indefinitely.
- **Scope:** both `asyncio.timeout()` and `asyncio.wait_for()` were ineffective.
- **Production impact:** Procrastinate workers hung for seven hours during managed-database failovers.

The reporter also found that a *second* `task.cancel()` does break out, because the re-wait sits inside the `except` block. A single `asyncio.timeout` cannot do that, but an outer watchdog that cancels again can.

**psycopg 3.3.6 or newer with libpq 17 or newer: bounded.** PR #1411 shipped in 3.3.6 on 18 September 2026. It gives the post-cancel re-wait a 5-second timeout. On expiry psycopg logs "query not terminated after cancellation: closing connection", calls `pgconn.finish()`, and re-raises the `CancelledError`, so the timeout raises `TimeoutError` as intended.

The cancel itself uses libpq 17's non-blocking `PQcancelCreate`, `PQcancelStart` and `PQcancelPoll` API, run through psycopg's own non-blocking waiter with a deadline. libpq states that `connect_timeout` is ignored by `PQcancelPoll` and that bounding it is the application's responsibility. psycopg supplies the 5 s, raises `CancellationTimeout`, and `_try_cancel` logs and swallows that error.

The worst case is therefore about 5 s for the cancel plus 5 s for the re-wait. The project's regression test freezes a proxy, applies a 0.5 s `wait_for`, and asserts that the connection ends up `broken` after both 5 s timeouts.

**libpq older than 17: still unbounded.** The release note says plainly: "The fix requires libpq 17 or newer." With older libpq, `cancel_safe()` falls back to `await asyncio.to_thread(self.cancel)`, which is the deprecated `PQcancel`. psycopg documents it as "blocking even on async connections", and says its `timeout` parameter "has no effect for libpq older than version 17". The PR's rationale: "PQcancelSafe() can be interrupted, PQcancel() couldn't."

The event loop stays responsive because the cancel runs on a worker thread, and asyncio cancellation cannot stop that thread. But the heartbeat task waits as long as `PQcancel` takes to open a fresh connection and send its request, plus up to 5 s. If packets to the server are silently dropped, nothing in psycopg bounds that connect.

The binary wheels bundle "the libpq version ... available on the runners" (the #1371 reporter's binary build had libpq 18.0). The pure-Python implementation loads the system libpq. A library can check `psycopg.pq.version()` at startup and refuse or warn below 17.

**`close()` does not block on a half-open socket.** `AsyncConnection.close()` awaits nothing on the network: it marks the connection closed and calls `pgconn.finish()` (libpq's `PQfinish`). psycopg sets every connection to `nonblocking = 1` when it connects. In that mode libpq's send routine `pqSendSome` returns "1 when not all data could be sent because the socket would block" instead of calling `pqWait`. Any goodbye bytes `PQfinish` writes therefore cannot park on a dead socket. I did not inspect `PQfinish`'s own source, so this conclusion rests on that nonblocking send path. Calling `close()` after 3.3.6 has already finished the connection returns immediately, because `closed` is true.

The `async with conn:` exit path is different: on error it awaits `rollback()` before closing. `rollback()` returns immediately if the connection is closed or its status is `IDLE`. A half-open connection left inside an open transaction would instead attempt a `ROLLBACK` round trip with no deadline. Heartbeat and LISTEN connections should therefore run in autocommit mode and be closed explicitly.

Separately, 3.1.12 fixed a "possible hanging if a connection is closed while querying" (#608). That suggests closing from another task is meant to unblock a waiting query, but this note did not verify it for half-open sockets.

**Waiting in `notifies()` behaves differently.** If a deadline fires while the consumer is awaiting `notifies()` rather than a query, the status is not `ACTIVE`. psycopg then skips the cancel and re-wait, and `CancelledError` propagates at once. The connection, however, stays open with unknown health. `notifies(timeout=...)` (added in 3.2) is the cleaner way to wake periodically and then run the deadline-wrapped heartbeat.

If pooled connections are involved, cancellation handling has had its own fixes:

- psycopg_pool 3.3.2 now propagates cancellation raised in a connection check (#1401).
- Issue #1345 reports a residual race in pool 3.3.1 where `getconn()` loses a cancellation.

That argues for keeping the LISTEN connection out of the pool.

**Practical consequence for the event store.** Require psycopg 3.3.6 or newer and libpq 17 or newer. Under those versions:

1. Wrap the heartbeat in `asyncio.timeout(d)`.
2. Budget roughly `d + 10` seconds for the escape.
3. On `TimeoutError`, call `close()`, which returns at once.
4. Reconnect with `connect_timeout` set, re-issue `LISTEN`, then do a catch-up read.

On older stacks, a single `asyncio.timeout` is not a dependable liveness bound.
