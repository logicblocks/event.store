# How do managed migration and blue-green upgrade services, such as AWS RDS blue-green deployments and AWS Database Migration Service, treat transaction-id counters and sequences at cutover, and what hooks let an event store fence its ordering there?

## Question

Take a PostgreSQL event store that allocates positions from a `BIGSERIAL` sequence. Its consumers may also order or gate reads by transaction ids, for example an `xid8` column filled from `pg_current_xact_id()` and compared with `pg_snapshot_xmin(pg_current_snapshot())`. What happens to the sequence and to the transaction-id counter when the database moves through Amazon RDS or Aurora Blue/Green Deployments, AWS Database Migration Service (DMS), or a similar managed service? And which hooks, in the service or in the database, let the event store put a safe ordering fence at the cutover?

## Findings

### Summary

The managed services handle sequences in different ways, and you have to check each one. None of them documents anything about the transaction-id counter.

- **RDS Blue/Green with physical replication** (minor-version or no-version changes): the green instance is a physical replica. Sequence and transaction-id state therefore carry over through the WAL.
- **RDS Blue/Green with logical replication** (major-version upgrades), and **all Aurora PostgreSQL blue/green deployments**: sequences are not replicated. RDS raises green's sequences to blue's values during the switchover itself. The transaction-id counter on green is never reconciled, and AWS says nothing about it.
- **AWS DMS**: does not migrate sequences during ongoing replication. AWS tells the operator to set `NEXTVAL` on the target after replication stops.
- **Google Cloud DMS**: warns only that sequence state "might vary" from the source.

So positions can be made safe. Transaction-id-based watermarks cannot be carried across a logical-replication or DMS cutover. The event store has to treat that cutover as an era boundary. Every one of these services drains writes before it reopens them, so a fence can be built from:

- the service's events,
- the read-only state that the switchover enforces, and
- a fence position recorded once writes have stopped.

### RDS Blue/Green Deployments: two replication modes

RDS for PostgreSQL "primarily uses physical replication for blue/green deployments". It switches to logical replication only when a major-version upgrade is requested and the source is on 16.1+, 15.4+, 14.9+, 13.12+, 12.16+ or 11.21+. Minor-version upgrades, and deployments with no upgrade, use physical replication. The green primary is created "by restoring from a DB snapshot". It is read-only by default, and with physical replication writes to green cannot be enabled at all.

**Physical mode.** Green replays blue's WAL, so the two share one transaction-id space and one sequence state. AWS lists no sequence-sync step for this mode: the sequence limitation appears only under logical replication. One side effect follows from PostgreSQL itself (inferred, not documented by AWS). The PostgreSQL documentation says each sequence "caches a block of values (typically 32) in memory before generating a new WAL record". It also says crashes "can result in gaps". So after promotion, a sequence on green can resume up to one cached block ahead. Positions can jump forward but never go backwards. Gap-detecting consumers have to accept that gap as permanent and skip past it.

**Logical mode.** AWS's limitations table states: "NEXTVAL operations on sequence objects aren't synchronized between the blue environment and the green environment. During switchover, Amazon RDS increments sequence values in the green environment to match those in the blue environment." Very large numbers of sequences can make the switchover time out. The step is visible as events:

| Event | Message |
|---|---|
| RDS-EVENT-0307 | sequence sync initiated |
| RDS-EVENT-0308 | sequence sync completed |
| RDS-EVENT-0310 | sequence sync cancelled because sequences failed to sync |

Aurora PostgreSQL blue/green documents only logical-replication limitations, including this same sequence-increment rule. Aurora builds green by cloning blue's storage volume. So on Aurora, even a deployment with no version change moves the data through logical replication.

### Transaction-id counters in logical mode

Neither the RDS nor the Aurora documentation says anything about transaction ids. The pg_upgrade documentation also does not say what happens to the xid counter or epoch. PostgreSQL scopes `xid8`'s guarantee to one installation: the type "does not wrap around during the life of an installation".

The following follows from PostgreSQL mechanics and is not stated by AWS:

1. Green starts as a physical copy of blue (a snapshot or clone), so its counter starts at blue's value at copy time.
2. After that, green assigns ids only to its own apply transactions, while blue keeps assigning ids to every write transaction. Blue's count includes aborted transactions and writes that are never replicated.
3. Logical replication ships stored column values. So `xid8` values recorded on blue arrive on green unchanged, in blue's numbering.
4. After switchover, new appends on green get ids from green's counter. Nothing guarantees that counter is above the highest blue-era id already in the table.

That has two consequences for consumers:

- **Skips.** A consumer that orders or checkpoints by `(xid8, position)` can see new events sort below events it has already processed, and skip them.
- **Stalls.** A consumer that only reads rows whose id is below `pg_snapshot_xmin` (or that uses `pg_visible_in_snapshot`) will treat blue-era ids above green's counter as not yet committed. It stalls until green's counter passes them.

### The switchover as a write fence

RDS's switchover sequence:

1. Runs guardrails: replication health, replica lag, no active writes on green, no long-running writes or DDL on blue, and no unsupported PostgreSQL changes.
2. "Stops new write operations on the primary DB instance in both environments".
3. Drops all connections and refuses new ones.
4. Waits for green to catch up.
5. Renames the instances and endpoints.
6. Reopens connections, then writes on the new production primary only.

If the timeout (30–3600 s, default 300 s) is exceeded, every change is rolled back. After the switchover, the old blue (renamed `-old1`) "only allows read operations" until `default_transaction_read_only` is changed. During the switchover, green's writer has `default_transaction_read_only` set to `on`. AWS explicitly warns: if an application overrides it at session level, writes can reach green during the switchover and are lost if the switchover rolls back.

Through RDS Proxy, PostgreSQL clients get `AdminShutdown: terminating connection due to administrator command`. Long-lived `LISTEN` sessions therefore end at the cutover and have to reconnect.

Other things that break across the switchover:

- **Logical-slot positions.** AWS states that DMS tasks "can't resume because the checkpoint from the blue environment is invalid in the green environment". Blue also may not be a logical publisher, and a guardrail requires dropping self-managed replication slots. A consumer driven by logical decoding must create a new slot on green and re-anchor itself.
- **PITR history.** The new production instance cannot be restored to any time before green was created.

### AWS Database Migration Service

DMS reads PostgreSQL changes through a logical replication slot, using `test_decoding` or `pglogical`. Its checkpoints are source LSNs, for example `checkpoint:V1#1#000004AF/B00000D0#…`. On the target it "supports basic schema migration, including the creation of tables and primary keys", and it does not propagate objects "not directly related to table data".

The PostgreSQL-target page is explicit about sequences: "If your tables use sequences, then update the value of `NEXTVAL` for each sequence in the target database after you stop the replication from the source database. AWS DMS copies data from your source database, but doesn't migrate sequences to the target during the ongoing replication."

DMS's homogeneous data migrations use `pg_dump`/`pg_restore` for the schema, then native publication and subscription. That puts them under PostgreSQL's own restriction: "Sequence data is not replicated … If, however, some kind of switchover or failover to the subscriber database is intended, then the sequences would need to be updated to the latest values". PostgreSQL 19 adds `CREATE PUBLICATION … FOR ALL SEQUENCES` and `ALTER SUBSCRIPTION … REFRESH SEQUENCES`. These copy sequence values on demand rather than continuously, so they still have to be run after writes stop.

On the target, DMS commits in its own transactions:

- **Transactional mode** is the default. It "preserves transactional integrity" and batches changes according to `MinTransactionSize` (default 1000) and `CommitTimeout` (default 1 s).
- **Batch-optimised apply** (`BatchApplyEnabled`) allows "temporary lapses in transactional integrity".

So transaction ids on the target have no relation to the source's. Consumers should not tail a DMS target before cutover.

### Other managed services

Google Cloud Database Migration Service for PostgreSQL warns only that "`SEQUENCE` states (for example, `last_value`) on the new Cloud SQL destination might vary from the source", and that the destination stays writable during migration.

### Hooks for fencing

**Service-side signals.**

- RDS publishes blue/green events through EventBridge and SNS:
  - RDS-EVENT-0247 or 0250: switchover started.
  - RDS-EVENT-0307, 0308, 0310: sequence sync initiated, completed, or failed.
  - RDS-EVENT-0248 or 0251: switchover completed, with renames.
  - RDS-EVENT-0249 or 0252: switchover cancelled.
- The `BlueGreenDeployment` status moves through `SWITCHOVER_IN_PROGRESS` to `SWITCHOVER_COMPLETED` or `SWITCHOVER_FAILED`. AWS itself suggests scripts that react when the status becomes `SWITCHOVER_IN_PROGRESS`.
- DMS can stop a task at a source commit time or a replication-server time (a CDC stop point).
- With `TaskRecoveryTableEnabled`, DMS continuously writes its applied source checkpoint to an `awsdms_txn_state` table on the target.
- DMS emits SNS events and offers data validation. AWS notes that CDC latency has no SLA.

**Database-side behaviour to rely on.**

- The switchover drains writes and enforces `default_transaction_read_only`.
- An appender must never override that setting.
- An appender should treat read-only errors and `AdminShutdown` as signals to stop appending and reconnect.

**A fence protocol (a design inference from the above, not something a vendor documents).**

1. Stop appends, or let the switchover stop them.
2. Make sure the position sequence is at least the highest stored position. RDS does this in logical mode. For DMS, Google Cloud DMS and native logical replication, run `setval` against the maximum position yourself.
3. Record the fence: an era number plus the highest position, in an event-store-owned table, written before appends reopen.
4. In consumers, store the era with every checkpoint, and do not compare transaction ids across eras. Everything at or below the fence position was committed before writes stopped, so read that range by position alone. Use transaction-id watermarks only for positions above the fence, measured against the new cluster's counter.
5. Re-create any logical slot after the fence, and re-anchor it at the fence position.

Physical-mode blue/green needs only gap tolerance, not an era change.
