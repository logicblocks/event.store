# How should a psycopg 3 consumer detect a silently dead LISTEN connection, using TCP keepalives, timeouts or heartbeat queries, and resubscribe without missing new events?

## Question

How should a consumer built on psycopg 3 notice that its dedicated `LISTEN` connection has died without any error reaching it? Which tools work, and how do they combine: libpq TCP keepalives, `tcp_user_timeout`, `notifies()` timeouts, and application heartbeat queries? Once a failure is detected, how should the consumer reconnect and re-subscribe so that no event committed during the outage is missed?

## Findings

### Why a listener can go deaf without an error

A psycopg 3 listener spends nearly all its time blocked in `Connection.notifies()`. In psycopg's source, the generator behind it waits for the socket to become readable. Only then does it call `PGconn.consume_input()`. If that call fails, it raises `OperationalError("consuming input failed: ...")`, and the connection is then reported as `closed` (and `broken` if it was not closed cleanly). This works when the failure produces a packet. A server shutdown sends a FIN, a crashed peer kernel sends a RST, and either one wakes the socket at once.

A silent failure produces no packet. Examples are host power loss, a network partition, or a NAT, firewall or load balancer dropping its idle flow state. The socket never becomes readable, so `notifies()` without a timeout waits forever, and every event committed in that time goes unnoticed. TCP sends nothing on an idle connection unless keepalives are enabled. Even then, the Linux defaults are 7200 s idle, 75 s between probes and 9 probes, so the kernel takes about 2 h 11 min to declare the peer dead. libpq turns keepalives on by default (`keepalives=1`), but the idle, interval and count values default to the system settings. Out of the box, a listener can therefore be deaf for more than two hours.

There is a second, separate trap. Once the client has written to a dead peer (a heartbeat query, say, or a `LISTEN` command), keepalives stop. Unacknowledged data switches TCP to retransmission rules. With Linux's `tcp_retries2 = 15`, Cloudflare measured a lower bound of 924.6 s and observed about 15.7 minutes before the socket errors. A heartbeat query sent over a half-open connection can therefore hang for about a quarter of an hour unless something else bounds it.

### Layer 1: transport detection with libpq keepalives and `tcp_user_timeout`

psycopg passes keyword arguments to `connect()` straight through to the libpq connection string, so all of libpq's TCP controls are available:

- `keepalives`, `keepalives_idle`, `keepalives_interval`, `keepalives_count` set when probes start, how often they repeat, and how many may be lost before libpq's socket is declared dead. An idle dead connection is detected in about idle + interval × count seconds; for example, 10 + 5 × 3 ≈ 25 s.
- `tcp_user_timeout` (milliseconds) limits how long sent data may stay unacknowledged before the kernel closes the connection with `ETIMEDOUT`. On Linux it also overrides keepalive when deciding to close after keepalive failure. This makes it the fix for the stuck-heartbeat trap above.
- `connect_timeout` bounds each reconnect attempt per host. Without it, connecting to an unreachable host can wait indefinitely.

Cloudflare's advice is to enable keepalives and set `TCP_USER_TIMEOUT` to `TCP_KEEPIDLE + TCP_KEEPINTVL * TCP_KEEPCNT`. If the user timeout is much larger than that, it defeats `TCP_KEEPCNT`. libpq ignores all of these settings on Unix-domain sockets, and ignores each one on platforms without the matching socket option. `TCP_USER_TIMEOUT` is a Linux socket option (Linux 2.6.37 and later), and the server-side equivalent is documented as unavailable on Windows.

When the kernel gives up, the socket reports a pending error. `notifies()` wakes, `consume_input()` fails, and psycopg raises `OperationalError`. That error is the consumer's signal to reconnect. Keepalives have a second benefit, noted in AWS's RDS guidance: they stop firewalls and routers from dropping idle sessions in the first place. Detection then rarely needs to fire.

Keepalives have one limit that matters here. They only show that something at the far end of this TCP hop is still acknowledging packets. If a proxy or a load balancer that terminates TCP sits between client and server, keepalives test only the client-to-proxy hop. They say nothing about whether the backend session is alive or still registered as a listener (this point is reasoning about how TCP works, not a claim from the sources). Covering the whole path needs an application-level check.

### Layer 2: an application heartbeat on the listening connection

psycopg's own docs advise against polling with `SELECT 1` to detect disconnection. They call it wasteful and say it detects loss only "with an average delay of half the polling time". Instead they suggest a thread or asyncio task that watches `conn.fileno()` with `selectors` or `loop.add_reader()` and runs a check when the OS reports activity. That watcher only wakes when the OS learns something, though, so it is only as good as the keepalives underneath it.

Established listener implementations add a heartbeat anyway:

- **River** (Go) pings its listener connection after 5 s without a notification. On error it reconnects with exponential backoff and re-issues `LISTEN` for every subscribed topic. A comment in River's code records a bug where the ping used an already-cancelled context, which made it "a no-op that always returned context.Canceled". After the fix, "dead or flaky connections are now actively detected, which may trigger reconnections that were previously silently swallowed". A heartbeat can quietly become a no-op, so it needs a test of its own.
- **pg-listen** (Node) has a "paranoid checking" option that runs `SELECT pg_backend_pid()` every 30 s by default. When the check fails it reconnects (500 ms retry interval, 3000 ms timeout) and re-issues `LISTEN` on every subscribed channel.
- **Oban** (Elixir) sends periodic pings on a `sonar` notification channel, every 5 s at minimum and up to 60 s. From what it receives, it marks itself `isolated`, `solitary` or `clustered`, and drops peers not heard from in 120 s. When the notifier is `isolated`, Oban's job stager switches to local polling every 1 s.

psycopg 3.2 and later support this pattern on a single connection. `notifies(timeout=..., stop_after=...)` was added in 3.2. Before that, the generator had no timeout, the connection could not run queries while the loop was active, and stopping it from inside the loop was awkward (Daniele Varrazzo's 2023 proposal says as much). The timeout is one overall deadline, so the generator returns on schedule even while notifications keep arriving, and the same connection can then run the heartbeat. Two later fixes matter here:

- **3.2.4:** notifications that arrive while the iterator is not running are kept and delivered by the next `notifies()` call (ticket #962), so a heartbeat between calls loses nothing.
- **3.2.10:** using `add_notify_handler()` and `notifies()` on the same connection is deprecated and raises a runtime warning.

A heartbeat can take two forms:

- **Round-trip query** (`SELECT 1` or `SELECT pg_backend_pid()`). This proves the socket and the backend respond.
- **Self-NOTIFY.** The listener sends `NOTIFY` on a heartbeat channel it also listens on, and expects the notification back before a deadline. PostgreSQL says a session gets back its own notifications, identifiable by comparing the sender PID with its own. This tests the whole delivery path, including the `LISTEN` registration itself. It is the single-node version of Oban's sonar.

The heartbeat itself needs a time limit:

- `statement_timeout` is enforced by the server, so it cannot help when the server is unreachable.
- On Linux, `tcp_user_timeout` bounds the heartbeat at the transport level.
- With asyncio, an application deadline such as `asyncio.timeout` around the heartbeat works, after which the connection should be discarded.
- When psycopg's wait routine is interrupted during an active query, it tries a server cancel with a 5-second limit. Interrupting a heartbeat therefore costs up to that long before control returns.

### Server-side settings that interact with the listener

- **Autocommit is required.** psycopg's docs say to keep notification connections in `autocommit` mode. PostgreSQL holds notifications back from a session that is inside a transaction until that transaction ends. `LISTEN` also only takes effect at commit. In psycopg's default non-autocommit mode, a heartbeat `SELECT` would open a transaction and hold back delivery.
- **`idle_session_timeout`** ends any session that waits for a client query outside a transaction for longer than the limit. A listener blocked in `notifies()` is exactly such a session. Either keep the heartbeat interval below the limit or exempt the listener's role.
- **Server keepalives** (`tcp_keepalives_idle`, `tcp_keepalives_interval`, `tcp_keepalives_count`, `tcp_user_timeout`) let the server clean up the backend of a client that vanished silently. The docs say that without them the server notices a lost connection "only at the next interaction with the socket". `client_connection_check_interval` applies only "while running queries", so it does nothing for an idle listener's backend. AWS RDS sets server defaults of 300 s, 30 s and 2 probes, which detects a dead peer in a few minutes.

### Re-subscribing without missing events

A `LISTEN` registration is cleared when its session ends. Notifications sent while no session is listening are not kept for that consumer. So re-subscribing cannot bring back events from the outage; they have to be recovered from the durable event log. PostgreSQL's `LISTEN` docs give the rule for the race this creates. A new listener receives "all events committed after an instant during the transaction's commit step", which is slightly later than anything that transaction's own queries could have seen. The prescribed order is: "first execute (and commit!) that command, then in a new transaction inspect the database state as needed by the application logic, then rely on notifications to find out about subsequent changes". The docs add that the first few notifications may refer to changes already seen, "but this is usually harmless".

For a psycopg 3 consumer, that gives this procedure:

1. Treat any `OperationalError` from `notifies()` or the heartbeat, or `conn.broken` being true, as fatal for the connection. Close it and do not reuse it.
2. Reconnect with backoff, as River and pg-listen do, with `connect_timeout` set.
3. On the new `autocommit=True` connection, issue `LISTEN` for every channel before anything else. In autocommit mode each `LISTEN` commits immediately.
4. Only after that, run a catch-up read of the event log from the consumer's durable checkpoint, as a new transaction (a separate statement or another connection), and process what it returns.
5. Resume `notifies(timeout=heartbeat)`. Treat each notification as a hint to "read from the checkpoint", never as the event itself, so duplicate or stale hints cost only an empty read.
6. Keep a low-frequency fallback poll as a safety net for anything the heartbeat misses, as Oban does when isolated.

Follow the same order at cold start. One limit applies to an event store specifically. "Read after checkpoint" has no gaps only if log positions become visible in order. Positions allocated from a sequence can commit out of order, which is a separate problem this procedure does not solve.

Below is a minimal synchronous sketch of the loop. The settings are illustrative values derived from Cloudflare's formula, not recommendations from any source. `catch_up` reads from the checkpoint over a different connection, because `notifies()` holds the listener connection's lock while it is iterating.

```python
from psycopg import OperationalError, connect, sql

def listen_forever(dsn, channels, catch_up, backoff, heartbeat=15.0):
    while True:
        try:
            with connect(
                dsn, autocommit=True, connect_timeout=10,
                keepalives=1, keepalives_idle=10, keepalives_interval=5,
                keepalives_count=3, tcp_user_timeout=25000,
            ) as conn:
                for channel in channels:
                    conn.execute(sql.SQL("LISTEN {}").format(sql.Identifier(channel)))
                catch_up()
                while True:
                    for _ in conn.notifies(timeout=heartbeat):
                        catch_up()
                    conn.execute("SELECT 1")
                    catch_up()
        except OperationalError:
            backoff()
```

The `catch_up()` after each heartbeat doubles as the fallback poll. The detection time is then bounded by the heartbeat interval plus `tcp_user_timeout` (where that option exists) or the keepalive budget, rather than by the OS defaults of hours or minutes.
