# In an append-only PostgreSQL event log whose positions come from a `BIGSERIAL` sequence, how can a consumer woken by a notification avoid skipping events that concurrent transactions commit out of position order — transaction-id or snapshot-based high-water marks (`pg_current_xact_id`, `pg_snapshot_xmin`), gap detection with timeouts, or serialised appends — and how does notification order relate to commit order?

## Question

When positions in an append-only PostgreSQL event table come from a `BIGSERIAL` sequence, concurrent append transactions can commit in a different order from the positions they were given. How can a consumer that is woken by `LISTEN`/`NOTIFY` read the log without permanently skipping events? The options are transaction-id or snapshot-based high-water marks (`pg_current_xact_id`, `pg_snapshot_xmin`), gap detection with timeouts, and serialised appends. And what does PostgreSQL guarantee about the order of notifications compared with the order of commits?

## Findings

### Why positions become visible out of order

A `BIGSERIAL` default calls `nextval` when the row is inserted, not when the transaction commits. Changes to sequence state are not transactional. Other sessions see them at once, and a value is "not reclaimed for re-use if the calling transaction later aborts". Aborts, crashes, and even `INSERT ... ON CONFLICT` therefore leave permanent gaps, and PostgreSQL states that sequences "cannot be used to obtain 'gapless' sequences". The row itself only becomes visible when its transaction commits.

Here is how that loses events. Transaction T1 takes positions 11–12 and transaction T2 takes position 13, but T2 commits first. A reader that runs `WHERE position > 10` between the two commits sees 13 and not 11–12. If it then sets its checkpoint to 13, it never sees 11–12. Oskar Dudycz, Eugene Khyst's reference implementation, Sequin and Precision Nutrition all describe this failure, and Precision Nutrition hit it in production. Precision Nutrition also found about 0.6% of ids permanently missing. So an "expect `last + 1`" check cannot tell a transient gap (an append still in flight) from a permanent one (a rolled-back append).

### How notification order relates to commit order

The PostgreSQL 18 `NOTIFY` documentation guarantees four things:

- Notifications are delivered only "until and unless the transaction is committed".
- Notifications from one transaction arrive in the order they were sent. The one exception is that repeated notifications with the same channel and payload in one transaction are collapsed into one.
- "Messages from different transactions are delivered in the order in which the transactions committed".
- A listening session that is inside a transaction gets nothing until that transaction ends.

The source code (`src/backend/commands/async.c`) shows how this is enforced. `PreCommit_Notify` adds entries to a cluster-wide queue while holding a special lock "that we hold till after commit. This ensures that queue entries appear in commit order, and in particular that there are never uncommitted queue entries ahead of committed ones". Listening backends check `XidInMVCCSnapshot` before `TransactionIdDidCommit`, and they stop at any entry whose transaction is still in progress. So by the time a client receives a notification, the transaction that sent it has committed and its rows are visible.

This has four consequences for a consumer:

- **Notification order is commit order, not position order.** In the example above, T2's notification (position 13) arrives before T1's (11–12). Positions carried in payloads are not monotonic. A consumer that sets its checkpoint from payloads skips events exactly as a naive poller does.
- **Aborted appends send nothing.** A gap left by a rollback never triggers a wake-up, so any approach that waits on gaps also needs a timer.
- **Commit order has a cost.** The lock (taken on "database 0") serialises the commit step of every transaction that sent a notification, across the whole cluster. Recall.ai traced outages under many concurrent writers to this lock (July 2025). Since then, PostgreSQL commit `282b1cde` (Joel Jacobson, reviewed by Tom Lane) made listener wake-ups cheaper with a shared channel map, but the comment about the commit-order lock is still in `async.c` on master. Two 2025 pgsql-hackers proposals targeted the lock:
  - Rishu Bagga's patch (September 2025) would write notification data through WAL, "eliminating the need for a global lock to be held from PreCommit_Notify to the end of transaction". It still holds the queue lock through commit, so "it is impossible for a listener to come across a notification that is not yet committed".
  - Another patch would add an opt-in out-of-order delivery setting. A reviewer noted that it no longer preserved commit order.

  Neither changes the documented guarantee.
- **The notification is a doorbell, not a cursor.** It only says "re-run your read query". The read query is what decides correctness. It should also run on reconnect, because only "the sessions currently listening on that notification channel are notified". The `LISTEN` documentation recommends a fixed order: run `LISTEN` and commit, then inspect the database state in a new transaction, then rely on notifications. It adds that the first few notifications "might refer to updates already observed", which is harmless.

### Approach 1: transaction-id high-water mark (`pg_current_xact_id`, `pg_snapshot_xmin`)

Each event row records the 64-bit id (`xid8`) of the transaction that wrote it. The consumer reads only events from transactions older than the oldest transaction still running. Dudycz and Khyst both publish this pattern. Rendered for an event table:

```sql
ALTER TABLE events ADD COLUMN transaction_id xid8 NOT NULL DEFAULT pg_current_xact_id();
CREATE INDEX ON events (transaction_id, position);

SELECT position, ...
FROM events
WHERE (transaction_id, position) > (%(last_transaction_id)s::xid8, %(last_position)s)
  AND transaction_id < pg_snapshot_xmin(pg_current_snapshot())
ORDER BY transaction_id, position
LIMIT %(batch_size)s;
```

**Why it is correct.** The documentation defines the snapshot's `xmin` as the "lowest transaction ID that was still active. All transaction IDs less than `xmin` are either committed and visible, or rolled back and dead." A transaction gets its id when it first writes, from a counter shared by every database in the cluster. The `xid8` form "does not wrap around during the life of an installation". Any event that is not yet visible belongs to a transaction whose id is at least `xmin`, and any transaction that starts writing later gets a higher id. So once the cursor has passed `(x, p)` with `x < xmin`, no row can ever appear behind it. Gaps in `position` stop mattering, because the consumer waits on transactions, not on position numbers.

**Ordering changes, and so does the checkpoint.** Events come out in the order their transactions first wrote, which is neither commit order nor position order. The documentation also warns that first-write order can differ from start order. Dudycz notes this "may create problems if forgotten". The resume token becomes the pair `(transaction_id, position)`, so a single `BIGSERIAL` value is no longer enough to resume from.

**Liveness cost.** An event can be delivered only after every transaction with a lower id has finished. The PostgreSQL source (`GetSnapshotData` in `procarray.c`) includes running transactions from all processes with no filter by database, and skips sessions that have no transaction id ("If the transaction has no XID assigned, we can skip it"). So the watermark is held back by any writing transaction anywhere in the cluster, not only in the event store's database. Khyst's README says "in the same database"; the source code indicates the whole cluster. Read-only transactions do not hold it back. These do:

- long batch writes;
- sessions left idle in a transaction after writing;
- prepared two-phase transactions, which `pg_xact_status` reports as "in progress".

Any of these pauses every consumer; Khyst calls it a long-running transaction "effectively 'pause' all event handlers". Sequin advises against the approach for this reason.

**Interaction with notifications (my inference from the documented behaviour).** T2's notification can arrive while an older appender T1, or an unrelated older write transaction T0, is still open. The read query then returns nothing for T2. When T1 commits it sends its own notification, but T0 never will. A consumer that only sleeps until the next notification can therefore stall with committed events waiting. Whenever events exist at or above the watermark, the consumer must re-check on a short timer, for example with `EXISTS (... WHERE transaction_id >= pg_snapshot_xmin(pg_current_snapshot()))`.

**Using the full snapshot.** The snapshot also exposes `xmax`, the list of in-progress ids (`pg_snapshot_xip`) and `pg_visible_in_snapshot`. With these, committed transactions above `xmin` could be delivered early. But events from still-open lower ids would then arrive behind the cursor, so the checkpoint would have to carry the set of open transaction ids. That is the same bookkeeping as the gap-tracking tokens below.

### Approach 2: gap detection with timeouts

**Axon.** Axon's `GapAwareTrackingToken` keeps the global sequence number plus "a set of possible gaps", which it describes as "sequence numbers of events that may have been inserted but have not been committed". It re-checks those gaps on each batch. The JDBC storage engine defaults are `gapTimeout` 60,000 ms, `maxGapOffset` 10,000 and `gapCleaningThreshold` 250. Once a gap expires or falls more than the offset behind, a late commit into it is never delivered.

**Marten.** Marten's async daemon keeps a "high water mark", described as the "furthest known event sequence that the daemon 'knows' that all events with that sequence or lower can be safely processed in order". It advances only through contiguous positions. Marten long relied on a 3-second wall-clock threshold for giving up on a gap. A GitHub discussion opened on 14 July 2026 (#4953) showed the daemon silently moving past committed events under concurrent appends. Four causes were identified:

- gap checks made of several SQL statements each took a separate snapshot under READ COMMITTED;
- catch-up and rebuild paths skipped gaps without checking whether they were stale;
- when idle, the mark could jump to reserved positions based only on the wall-clock threshold;
- the 3-second threshold "couldn't distinguish slow appends from rolled-back transactions".

Marten 9.16.1 (18 July 2026) made gap detection a single statement. It now skips a gap only when no live transaction could still hold the missing positions. Its evidence comes from a granted `RowExclusiveLock` on `mt_events` in `pg_locks`, from `pg_snapshot_xip(pg_current_snapshot())`, and from `pg_stat_activity.xact_start`. Otherwise "the daemon holds: a slow append gets waited out". Users who want a cap can opt in to `SkipStaleGapsDespiteLiveTransactionsAfter`, Marten recommends `idle_in_transaction_session_timeout` as a backstop, and every skip is now logged and recorded in `mt_high_water_skips`.

**Lesson.** Timeouts alone trade lost events for lower latency. Gap detection only becomes safe when it asks PostgreSQL which transactions are still running, which is the same information the transaction-id watermark uses. In exchange, the consumer keeps a single integer position. The evidence also has to be gathered within one snapshot.

**Sequin's variant.** Writers hold a shared advisory "marker" lock plus an exclusive advisory lock keyed on the sequence value they are about to use. Readers stop below the smallest such value visible in `pg_locks`. This keeps integer positions and concurrent writers, at the cost of complexity.

**With notifications,** a gap left by an abort never triggers a wake-up, so expiring gaps always needs a timer.

### Approach 3: serialised appends

The append transaction takes an exclusive lock before it allocates positions, and holds it until the transaction ends. The lock can be any of these:

- `pg_advisory_xact_lock`: transaction-level advisory locks "are automatically released at the end of the transaction";
- an `UPDATE` on a single counter row;
- `LOCK TABLE ... IN EXCLUSIVE MODE`, which conflicts with the `ROW EXCLUSIVE` lock that `INSERT` takes.

The next appender cannot allocate until the previous transaction has finished, so allocation order equals commit order. Whenever a reader sees position *p*, every lower position is either visible or permanently gone. The consumer can safely checkpoint at the highest position it sees and skip gaps immediately.

**Prior art:**

- **Commanded EventStore (Elixir).** Every append runs `UPDATE streams SET stream_version = stream_version + $2 WHERE stream_id = 0 RETURNING stream_version - $2`. That row lock serialises all appends, and global positions are computed from the returned starting value rather than from a sequence. Because the counter update rolls back on abort, positions have no gaps. A trigger (`AFTER INSERT OR UPDATE ON streams`) calls `pg_notify` with a payload of the form `stream_uuid,stream_id,first_version,last_version`.
- **Message DB.** `write_message` first calls `acquire_lock`, which takes `pg_advisory_xact_lock(hash_64(category))`, and then inserts into a table whose `global_position` is `bigserial`. Ordering is therefore guaranteed only within a category. Category consumers are safe; readers across categories are not.
- **Precision Nutrition.** Their fix was a counter table (`UPDATE stream_ids SET id = id + n RETURNING ...`) feeding a separate `events_stream` table. They warn that if a trigger does this, concurrent inserts make other writers' transactions wait until they complete.

**Cost.** Throughput is limited by how long the lock is held, from acquiring it through the commit flush. Dudycz rejected manual sequencing as performance-prohibitive, and Sequin cites reduced write throughput. Taking the lock as the last step before the insert and keeping append transactions short reduces the cost. Precision Nutrition also warns of deadlock risk with pessimistic locking.

**Interaction with notifications (my inference).** If each append sends `NOTIFY` in the same transaction, serialised appends make notification order, commit order and position order the same. Payload positions then arrive in increasing order, and the consumer can spot a missed notification from a jump. Commits of notifying transactions are already serialised by the `NOTIFY` queue lock. So a global append lock adds serialisation over the rest of the append transaction, not over the whole commit path from scratch.

### Comparison for a notification-driven consumer

| Approach | Never skips? | Resume token | Concurrent appends | Main risk | What wakes the consumer |
|---|---|---|---|---|---|
| Transaction-id watermark | Yes, by construction | `(xid8, position)` | Unrestricted | Any long-running writing transaction anywhere in the cluster stalls delivery | Notification, plus a timed re-check while events sit above the watermark |
| Gap detection, timeout only | No: a commit after the timeout is lost | Integer, plus a set of gaps | Unrestricted | Silent loss (Axon defaults, Marten before 9.16.1) | Notification, plus a timer to expire gaps |
| Gap detection, checks for running transactions | Yes, if all checks use one snapshot | Integer, optionally with a set of gaps | Unrestricted | Complexity; stalls behind live transactions, like the watermark | Notification, plus a timer |
| Serialised appends | Yes | Integer (no gaps with a counter row) | One appender at a time, or per category | Throughput limited by lock hold time | Notification alone; payload positions arrive in order |

Whichever approach is used, the notification only prompts the consumer to re-run its read query, and the query also runs on reconnect. A consumer's listening session must stay outside a transaction, because PostgreSQL holds notifications back from a session until its transaction ends.
