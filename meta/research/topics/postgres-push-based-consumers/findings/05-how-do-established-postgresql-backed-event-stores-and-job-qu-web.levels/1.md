# How do established PostgreSQL-backed event stores and job queues — such as Marten's async daemon, Message DB, River, Oban, Graphile Worker, GoodJob, pg-boss, Solid Queue and pgmq — deliver new work to consumers, and what design choices, problems and lessons have their maintainers published?

## Question

How do mature PostgreSQL-backed event stores and job queues (Marten's async daemon, Message DB with Eventide, River, Oban, Graphile Worker, GoodJob, pg-boss, Solid Queue and pgmq) get new work to their consumers? Which design choices, problems and lessons have their maintainers written up?

## Findings

### Summary

None of the nine systems uses a notification to carry the work itself. They fall into three groups:

1. **Notification-accelerated polling.** River, Oban, Graphile Worker and GoodJob use PostgreSQL `LISTEN`/`NOTIFY` by default. pg-boss and pgmq offer it as an opt-in. In all of them a notification is only a wake-up hint carrying at most a queue name. The consumer then re-reads the table, usually with `FOR UPDATE SKIP LOCKED`. A periodic poll keeps running underneath as the guarantee that nothing is missed.
2. **Pure polling.** Solid Queue, Message DB with its Eventide consumers, and Marten's async daemon do not use `LISTEN`/`NOTIFY` for delivery. Marten's creator wrote in 2016 that `NOTIFY`/`LISTEN` "was not adequate by itself". The project later closed a request for listen and notify support as "wontfix".
3. **Server-side long-poll.** pgmq's `read_with_poll` loops inside the database with `pg_sleep` until a message arrives or a timeout expires.

Six lessons recur across these projects:

- Keep polling as the guarantee of correctness.
- Debounce notifications both where they are sent and where they are received.
- Move insert notifications out of per-row triggers and into application code.
- Give the listener a dedicated session connection, and provide a poll-only mode for PgBouncer transaction pooling.
- Detect when notifications fail silently.
- For event stores that read by global sequence, notifications do not solve the hard problem: events can become visible out of sequence order while transactions are still in flight.

### Comparison

| System | Wake-up path | Who emits the notification | Fallback poll (default) | Notable published lesson |
|---|---|---|---|---|
| River (Go) | `LISTEN`/`NOTIFY` | Application, debounced per queue, attached to the insert inside the transaction (trigger removed in 0.5.0) | `FetchPollInterval` 1 s; `FetchCooldown` 100 ms | One `NOTIFY` per inserted job was too much overhead at high throughput; `PollOnly` mode added for PgBouncer |
| Oban (Elixir) | Pluggable notifier: Postgres `LISTEN`/`NOTIFY` or Erlang `PG` | Application since 2.17.0 (trigger removed); de-duplicated, sent after commit | Stager interval 1 s; producer `dispatch_cooldown` 5 ms | Detect a broken notifier and switch to "local" polling on every node |
| Graphile Worker (Node) | `LISTEN`/`NOTIFY` on by default | Database side when a job is added | `pollInterval` 2 s, used for future-dated jobs and retries | Polling is still required because nothing emits an event when the clock reaches a scheduled time; events are dropped if no worker is idle |
| GoodJob (Ruby) | `LISTEN`/`NOTIFY` on the `good_job` channel | Application sends `NOTIFY good_job` with a JSON payload | `poll_interval` 10 s in production | Dedicated connection with keepalive and reconnect; `:skiplocked` plus polling for PgBouncer |
| pg-boss (Node) | Polling by default; opt-in `useListenNotify` | Sent in the same transaction as the insert, so it fires on commit; only for immediately available jobs | `pollingIntervalSeconds` 2 s, or `notifyPollingIntervalSeconds` 30 s while listening | Notification is "an opt-in optimization on top of polling, not a replacement for it" |
| pgmq (extension) | Long-poll `read_with_poll`; opt-in insert trigger with `NOTIFY` | `AFTER INSERT` trigger, throttled per queue (default 250 ms) | Client's choice; `read_with_poll` checks every 100 ms internally | Throttled trigger; notifications for mixed-case queue names silently never fired until 1.13.1 |
| Solid Queue (Ruby) | Polling only | None | Workers 0.1 s, dispatchers 1 s | Keep the polled table tiny and use a covering index; about 1,300 polls a second at 110 µs average at 37signals |
| Message DB with Eventide | Polling only | None | Eventide consumer sleeps only when a batch comes back empty | Global position "may have gaps"; writes take an advisory lock on the category |
| Marten async daemon (.NET) | Polling with high-water-mark gap detection | None | `FastPollingTime` 250 ms, `SlowPollingTime` 1 s (per issue report) | Events in flight versus sequence order; events were skipped under concurrent appends until 9.16.1 |

### River

River's `Config` documentation says that new jobs "will be picked up ~immediately after insert via LISTEN/NOTIFY". `FetchPollInterval` (default `1 * time.Second`) "provides a fallback". `FetchCooldown` (default `100 * time.Millisecond`) is "the minimum amount of time to wait between fetches of new jobs". A client-side `insertNotifyLimiter`, built from `FetchCooldown`, debounces outgoing insert notifications.

The 0.5.0 changelog records an important change of direction. "The initial design for River utilized a trigger on job insert that issued notifications (`NOTIFY`) so that listening clients could quickly pick up the work if they were idle." That design "does have the side effect of emitting a large amount of notifications any time there are lots of jobs being inserted", which adds overhead "particularly to high-throughput installations". Notifications are now emitted at the application level. "A client-level debouncer ensures that these notifications are not emitted more often than they could be useful". When a queue is due a notification, it "is piggy-backed onto the insert query within the transaction".

River 0.3.0 added `Config.PollOnly`, which avoids `LISTEN` entirely. A resigning leader or a new job "will be noticed less quickly", but River can then run on "systems without listen/notify support, like PgBouncer operating in transaction pooling mode". River's PgBouncer guide says `LISTEN`/`NOTIFY` is "required for both listening for new jobs and listening for leadership demotions". It recommends transaction pooling for inserts and workers, with a raw Postgres pool for the work coordinators.

Later changelog entries extend the same idea:

- 0.23.0 notifies producers in the same process immediately when the driver cannot listen.
- 0.40.0 adds a table-backed "pseudo listen/notify" for SQLite.
- 0.48.0 (2026-09-30) automatically polls for job cancellations and queue pause or resume changes when `LISTEN`/`NOTIFY` is unavailable.

### Oban

In Oban, delivery goes through a pluggable `Oban.Notifier` with `insert`, `leader`, `signal` and `sonar` channels. The Postgres notifier delivers notifications "only after a transaction completes" and de-duplicates them. Payloads cannot exceed 8 kB. The notifier "doesn't work with connection poolers like PgBouncer when configured in transaction or statement mode". For that case Oban recommends `Oban.Notifiers.PG`, which uses distributed Erlang.

Oban 2.17.0 (2023-12-08) removed the database trigger. Historically Oban "used database triggers to emit a notification after a job is inserted". Insert notifications now live in application code, "so it's possible to disable triggers without running database migrations", and they "work for any notifier, not just Postgres". The `insert_trigger` option, default `true`, can be turned off "if sub-second job execution isn't important or you'd like to reduce PubSub chatter".

Scheduled and retryable jobs go through the Stager:

- It runs every 1,000 ms and stages at most 5,000 jobs per run.
- When notifications work, "only the leader node stages jobs and notifies queues".
- When they do not, "staging switches to a less efficient 'local' mode in which all nodes poll for jobs to run".

Oban 2.17.4 added `Notifier.status/1`, backed by a Sonar process, which reports `isolated`, `solitary` or `clustered`. The Stager uses it to choose global or local mode. This fixed a bug where "isolated follower nodes wouldn't process jobs".

On the consumer side, each queue's producer waits on average `dispatch_cooldown` (5 ms) before fetching again. This smooths out bursts of notifications.

### Graphile Worker

Graphile Worker advertises "typically under 3ms from task schedule to execution" because it "uses `LISTEN`/`NOTIFY` to be informed of jobs as they're inserted". It finds jobs with `SKIP LOCKED`.

Its FAQ explains why polling must stay: "We cannot use `LISTEN`/`NOTIFY` since there's nothing to generate an event when the time 'ticks over'." `pollInterval` (default 2,000 ms) exists "for jobs scheduled in the future/retries". The FAQ suggests 30 to 60 seconds is acceptable if load is a concern.

Dispatch within an instance is deliberately lossy. "Each instance will `LISTEN` for events and when it receives one it will pick an idle worker to ask for jobs. If there is no idle worker then it'll drop the event", because busy workers ask for the next job when they finish anyway.

The newer `localQueue` locks a batch of jobs ahead of time to cut database round-trips. The documented trade-offs are higher latency and late detection of new high-priority jobs. A `refetchDelay` setting holds back re-fetching after a fetch returns few jobs. In the source, incoming notification "pulses" are counted and can end that delay early.

### GoodJob

GoodJob sends `NOTIFY good_job` with a JSON payload from application code. It listens on a dedicated connection that is checked out of the pool and run in a background thread. The relevant constants are:

| Constant | Value |
|---|---|
| `WAIT_INTERVAL` | 1 s blocking wait for a notification |
| `RECONNECT_INTERVAL` | 5 s |
| `KEEPALIVE_INTERVAL` | 10 s (no-op query) |
| `CONNECTION_ERRORS_REPORTING_THRESHOLD` | 6 consecutive errors before reporting |

`poll_interval` defaults to 10 s in production as a fallback and is disabled by default in development. The README notes that "LISTEN/NOTIFY is enabled in both production and development, so polling is not strictly necessary."

GoodJob "is not compatible with PgBouncer in transaction mode", because both its advisory locks and `LISTEN`/`NOTIFY` "require full database connections". The `:skiplocked` lock strategy together with disabled `LISTEN`/`NOTIFY` makes it compatible. The README budgets "2 additional connections" for utility work such as `LISTEN`/`NOTIFY` and cron.

### pg-boss

pg-boss polls by default every `pollingIntervalSeconds` (default 2 s, minimum 0.5 s). A request to support `LISTEN`/`NOTIFY` (issue #24) has been open since March 2017. A 2026 suggestion to replace fixed polling with deadline-based sleeping, citing the CPU and connection cost of polling, was closed as not planned.

Recent documentation adds an opt-in `useListenNotify` instance option plus a per-queue `notify: true` flag:

- The notification is "emitted transactionally with the insert, so it fires on commit".
- Only "immediately-available jobs emit a notification". Future-dated jobs and those blocked by flow dependencies are found by polling.
- While a queue is listening, polling slows to `notifyPollingIntervalSeconds` (default 30 s) but "always keeps running as a safety net".
- One dedicated, session-pinned connection is used. Heartbeat and keepalive settings tune it.
- If the listener cannot be established, pg-boss emits a `listen_notify_unavailable` warning and carries on with polling only.

### Solid Queue

Solid Queue has no `LISTEN`/`NOTIFY` path. Workers poll `solid_queue_ready_executions` every 0.1 s and dispatchers poll scheduled executions every 1 s. Dispatchers move due jobs in batches of 500.

The 37signals announcement (Rosa Gutiérrez, December 2023) describes the design choice. Jobs that are scheduled, in progress, failed or blocked are isolated so that "the table that workers poll" stays "as small as possible". A covering index keeps the polling queries "very fast, non-blocking". In production, "with around 5.6 million jobs executed daily, we perform around 1,300 polling queries per second, with an average query time of 110 µs and examination of 0.02 rows per query".

Users running PostgreSQL have reported CPU spikes from the ready-executions polling query (issue #508). The maintainers' reasoning there is not visible.

### pgmq

pgmq offers `read_with_poll(queue, vt, qty, max_poll_seconds DEFAULT 5, poll_interval_ms DEFAULT 100)`. This is a PL/pgSQL loop that re-runs the read and calls `pg_sleep` until it finds rows or times out. The trade-off is that a database backend is held for the whole wait.

Since 1.7.0, `enable_notify_insert(queue, throttle_interval_ms DEFAULT 250)` installs an `AFTER INSERT` trigger. The trigger updates a per-queue row in `pgmq.notify_insert_throttle` and calls `PG_NOTIFY('pgmq.q_<queue>.INSERT', NULL)` only when the throttle window has passed. Throttling arrived in 1.8.0.

One cautionary bug: for queues with mixed-case names, the trigger rebuilt a lower-cased name, so "the throttle UPDATE touched nothing ... and the PG_NOTIFY it guards was never reached". Notifications never fired, and consumers fell back silently to whatever polling they had. The fix shipped in 1.13.1 in September 2026. A further inference, not stated by the maintainers: every insert that clears the throttle updates the same row, so concurrent inserters to one queue may contend on that row lock.

### Message DB with Eventide

Message DB's consumer interface is `get_category_messages(category, position, batch_size DEFAULT 1000, …, consumer_group_member, consumer_group_size, condition)`. The documentation warns that "Global position may have gaps". Eventide consumers poll this function through the `poll` library. Following the library's empty-result rule, a consumer sleeps for `poll_interval_milliseconds` only when a batch comes back nil or empty, and loops immediately otherwise. Read position is saved to a position store every 100 messages by default (`position_update_interval`).

`write_message` always calls `acquire_lock`, which takes `pg_advisory_xact_lock(hash_64(category))`. Every write therefore takes a transaction-scoped lock on the whole category before inserting. The maintainers' rationale was not found. A reasonable inference is that this serialises commits within a category, so a category reader that advances by global position cannot pass a lower-positioned message that is still in flight. The cost is write concurrency within a category.

### Marten async daemon

In 2016, Marten's creator explained the daemon's design:

- It polls the events table.
- It uses a `SEQUENCE`-backed `bigint` key because sequential GUIDs could not be ordered reliably "under a heavy parallel load".
- It queries only events older than a threshold ("3 seconds is the default") "to avoid missing events still in flight".
- It "pauses a little bit, and tries again" when it sees gaps in the sequence.

The current documentation describes a high water mark: the furthest sequence below which all events can safely be processed in order. Gaps are skipped only when no live transaction could still fill them. Skips are recorded in `mt_high_water_skips`. An optional `SkipStaleGapsDespiteLiveTransactionsAfter` cap trades possible event loss for liveness. Leader election uses advisory locks.

Problems Marten has published:

- **Skipping when appends are slow.** The performance guide warns of event "skipping" when appending transactions "become slower than the `StaleSequenceThreshold` (the default is only 3 seconds)". It recommends Quick append mode.
- **Events skipped under concurrent appends (2026).** A maintainer discussion records this failure: sequence numbers are reserved before rows become visible. The gap detector ran three statements, each with its own READ COMMITTED snapshot. It "could only see gaps that sit between two visible rows", so the high water mark could silently pass an invisible committed event. Version 9.16.1 (July 2026) fixed this with single-snapshot gap queries and by checking `pg_locks` and `pg_stat_activity` for in-flight appends before skipping. It also now logs every skip at Warning.
- **Over-polling (2021).** A report found the daemon polling up to three times in 10 ms, despite expected `FastPollingTime` and `SlowPollingTime` defaults of 250 ms and 1 s.

### Lessons across the projects

1. **A notification is a hint. Correctness comes from re-reading the table.** Every system that uses `NOTIFY` keeps a periodic poll. Polling is needed in any case for work that becomes eligible because time has passed, such as scheduled jobs and retries (Graphile Worker, Oban's Stager, pg-boss). Notifications carry at most a queue name.
2. **Notifications per row do not scale, so debounce.** River and Oban both replaced insert triggers with application-level notifications that are debounced or de-duplicated. pgmq kept its trigger but added a time-based throttle. Consumers coalesce bursts with cooldowns: River's 100 ms `FetchCooldown`, Oban's 5 ms `dispatch_cooldown`, Graphile Worker dropping events when every worker is busy, and its refetch delay. A separate incident report from Recall.ai (not one of these projects) explains another reason to minimise transactions that issue `NOTIFY`. Committing such a transaction takes an `AccessExclusiveLock` on the database object that "effectively serializes all commits". The post notes that a later PostgreSQL core commit addressed the bottleneck.
3. **The listener needs its own session connection, and a poll-only mode is required.** Every system that listens documents that PgBouncer in transaction or statement mode breaks `LISTEN`. Each also ships an escape hatch: River `PollOnly`, GoodJob `:skiplocked` with listening disabled, Oban's Erlang `PG` notifier, and pg-boss falling back automatically. Connection upkeep (keepalive, reconnect, heartbeat) is part of the published design for GoodJob and pg-boss.
4. **Detect silent notification failure.** Oban added a Sonar health check and switches to local polling when a node is isolated, because isolated followers had stopped processing jobs. pgmq's mixed-case bug shows that notifications can fail without any error while a fallback poll hides it.
5. **Cheap polling is a valid design.** Solid Queue shows that a small polled table with a covering index sustains about 1,300 polls a second at sub-millisecond cost. Eventide's "sleep only when empty" loop gives back-to-back reads under load.
6. **Ordering by sequence is the hard problem for event stores.** For an event store whose consumers advance by global sequence, a notification says only that *something* committed. It does not say that every lower sequence number is visible. Marten addresses this with high-water-mark gap detection backed by transaction evidence. Message DB serialises writes per category instead. Push delivery would sit on top of one of these mechanisms, not replace it.

### Implications for a psycopg 3 event-store consumer (synthesis)

This is synthesis, not something a maintainer published. The prior art supports keeping the existing position-based poll as the guarantee of correctness. On top of it, a dedicated `LISTEN` connection would cut short the poll's sleep when a notification arrives, with the cut-off debounced. The notification itself would be sent from application code inside the append transaction, throttled per category or per store rather than per event. The idle poll can then be lengthened while listening is healthy and shortened again when the listener is down. The consumer should still guard against events that become visible out of sequence order, using either a gap or high-water-mark check or category-level write serialisation.
