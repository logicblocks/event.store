# How should notification channels and payloads be designed for an event store, such as one global channel versus per-category or per-stream channels and empty payloads versus payloads carrying positions, to balance deduplication, filtering and gap detection?

## Question

An event store backed only by PostgreSQL can signal new events with `NOTIFY`.
It has to decide how many channels to use (one global channel, one per category,
or one per stream) and what each notification carries (nothing, routing keys
such as category or stream, or global positions). Which combination gives the
best balance of deduplication, filtering and gap detection, given how
PostgreSQL actually implements `LISTEN` and `NOTIFY`?

## Findings

### What PostgreSQL already decides

Several properties of the server set the limits for any channel or payload
design:

- **Folding happens only within a transaction.** "If the same channel name is
  signaled multiple times with identical payload strings within the same
  transaction, only one instance of the notification event is delivered."
  Notifications with distinct payloads are always delivered separately, and
  "notifications from different transactions will never get folded into one
  notification". Duplicate elimination switches from a linear scan to a hash
  table once a transaction has 16 pending notifications
  (`MIN_HASHABLE_NOTIFIES`). So a constant payload costs one notification per
  transaction per channel, however many rows the transaction writes. A payload
  that varies per row costs one notification per row.
- **Delivery follows commit order.** Messages from different transactions "are
  delivered in the order in which the transactions committed". To guarantee
  this, `PreCommit_Notify` takes a special heavyweight lock and holds it until
  after commit, which serialises every transaction that has issued a `NOTIFY`.
  Nothing is delivered from a transaction that does not commit.
- **Payloads are small hints.** In the default configuration a payload must be
  shorter than 8000 bytes (`NOTIFY_PAYLOAD_MAX_LENGTH = BLCKSZ - NAMEDATALEN -
  128`). The documentation advises that larger data belongs "in a database
  table and send the key of the record". Every entry takes space in a shared
  queue capped by `max_notify_queue_pages` (default 1048576 pages, about 8 GB).
  When that queue is full, notifying transactions fail at commit.
- **Channels are identifiers.** PostgreSQL uses at most 63 bytes of an
  identifier and silently truncates longer names. Unquoted identifiers are
  folded to lower case. River checks its longest topic name for exactly this
  reason, because "Schemas are prefixed to notification topic names and
  Postgres enforces a maximum topic length of 63 characters." One inference
  from the identifier rules: `pg_notify(text, text)` takes the channel as a
  string value, so a mixed-case channel name will not match an unquoted
  `LISTEN` of the same name. Lower-case channel names avoid the problem.
- **Wake-ups depend on the server version.** Up to PostgreSQL 18,
  `SignalBackends()` "sends a PROCSIG_NOTIFY_INTERRUPT signal to every listening
  backend (we don't know which backend is listening on which channel so we
  must signal them all)". Each woken backend then scans the queue and checks
  every entry against its own channels. Those channels are held in "a simple
  list of channel names" and searched linearly, on the assumption that "the
  list is likely to be fairly short". PostgreSQL 19, still pre-release in its
  release notes as of September 2026, adds a "global channel table
  (implemented as a dynamic shared hash table…) that maps channel names to the
  set of backends listening on each channel" and only wakes "backends that are
  listening to specified notifications". Backends that are not interested have
  their queue pointers advanced directly. Each backend also gets a hash-based
  local channel table.
- **Sessions hear their own notifications.** The notifying session receives
  its own notifications, and the docs suggest comparing the sender PID in the
  notification with your own session's PID to skip "one's own work bouncing
  back". psycopg 3 exposes `channel`, `payload` and `pid` on each `Notify`.

### Channel topology

| Topology | Used by | Strengths | Costs |
|---|---|---|---|
| One global channel | Commanded EventStore (`<schema>.events`), GoodJob (`good_job`), Graphile Worker (`jobs:insert`), River (`river_insert`, schema-prefixed) | One `LISTEN` per process. Fits a single listener per process with in-process fan-out. Constant payloads fold well | Every listener receives every notification. Filtering moves into the payload or into the follow-up read |
| Per category or per queue | Procrastinate (`procrastinate_queue_v1#<queue>`), pgmq (`pgmq.q_<queue>.INSERT`) | Consumers only receive relevant notifications. On PostgreSQL 19 only the relevant backends are woken | Up to PostgreSQL 18 every listening backend is still signalled. Writers emit more notifications. Category names must fit in 63 bytes along with the prefix |
| Per stream | None of the surveyed systems | Exact targeting | Unbounded channel count. Dynamic `LISTEN` and `UNLISTEN` churn. Linear channel-list search before PostgreSQL 19. Stream ids plus a prefix risk the 63-byte limit |

Commanded EventStore is the closest analogue to an event-sourcing library, and
it answers per-stream subscription without per-stream channels. Its writer
uses one channel per schema (`channel := TG_TABLE_SCHEMA || '.events'`). "A
single process will connect to the database to listen for these
notifications. It fetches the event data and broadcasts to all interested
subscriptions". It uses one connection per node, and routing to individual
streams happens in-process through PubSub keyed by `stream_uuid`. River and
the notifier pattern described on brandur.org take the same approach: hold
one connection per process and "allow other components in the same program to
use it to subscribe to any number of topics". Oban also multiplexes several
channels (`<prefix>.oban_<channel>`) over one connection.

Per-queue channels work when the number of channels is small and fixed, which
holds for job queues. They also have a cost. Procrastinate serves both
queue-scoped and unscoped workers, so its row trigger sends every job twice,
once to `procrastinate_queue_v1#<queue>` and once to
`procrastinate_any_queue_v1`. Workers listen on the per-queue channels when
they are configured with queues, and on the any-queue channel otherwise. An
event store that wants both global (`$all`) consumers and category consumers
pays the same doubling if it uses per-category channels.

### Payload content

There are three payload options.

1. **Empty or constant payloads (a pure wake-up).** pgmq sends a `NULL`
   payload from a deferrable row-level constraint trigger. It also throttles to
   at most one notification per queue every `throttle_interval_ms` (default
   250 ms), tracked in a `notify_insert_throttle` table. The payload is
   identical every time, so in-transaction folding reduces a multi-row append to
   one notification per transaction. Queue use is minimal. The consumer learns
   only "something changed" and must always query from its own checkpoint. It
   cannot filter, skip duplicate wake-ups or detect gaps from the notification.
   Procrastinate puts a `job_id` in its payload but its worker still uses
   `job_inserted` purely as a wake-up: it sets an `asyncio.Event` and keeps a
   5-second `fetch_job_polling_interval` fallback.
2. **Routing keys.** GoodJob sends JSON containing `queue_name`, `count` and
   optionally `scheduled_at`, and groups bulk enqueues by queue and scheduled
   time so that they produce fewer notifications. River sends
   `{"queue": "<name>"}` and debounces per queue with a limiter that calls the
   notify function "no more than once per waitDuration" (`FetchCooldown`,
   default 100 ms). Graphile Worker reads a `count` from the payload and wakes
   that many idle workers, defaulting to one. With routing keys, a single
   channel can still be filtered on the client side. Folding still works when
   one transaction writes many events with the same key.
3. **Positions or position ranges.** Commanded's payload is
   `stream_uuid,stream_id,first_version,last_version` (for example
   `stream-12345,1,1,5`). It is fired by an `AFTER INSERT OR UPDATE ON streams
   FOR EACH ROW` trigger, so the granularity is one notification per stream
   per append, not one per event. The publisher reads exactly that range
   (`read_stream_forward(conn, stream_id, from_stream_version, count)`). The
   subscription state machine uses the range for both deduplication and gap
   detection. A batch whose first event is below `last_received + 1` is
   ignored as already seen. A batch whose first event is above it triggers
   `request_catch_up`, which replays the missing events from storage.

Positions are the only option that support deduplication (dropping
notifications at or below the checkpoint), coalescing (taking the maximum
position from a burst of pending notifications) and gap detection, all
without a query. A position is a bigint of at most about 20 characters, far
below the 8000-byte limit.

### Positional payloads are only as safe as position ordering

Commanded's gap check works because its positions are assigned in commit
order. Each append runs
`UPDATE streams SET stream_version = stream_version + $2 WHERE stream_id = 0`
on the `$all` row and takes its `$all` positions from the returned value. That
row lock is held until commit, so appends are serialised and `$all` positions
rise in commit order (this follows from PostgreSQL row-locking semantics). The
same `streams` trigger fires for the `$all` row, so each append produces one
notification for its stream and one for `$all`. Combined with commit-ordered
delivery, the `$all` ranges then arrive contiguously.

Sequence-assigned positions behave differently. `nextval` "is not reclaimed for
re-use if the calling transaction later aborts", and sequences "cannot be used
to obtain 'gapless' sequences". Positions are also reserved before commit, so
two concurrent appends can commit in the opposite order to their positions.
The eugene-khyst reference implementation describes the resulting loss. When
"transaction #2 started after transaction #1 but committed first", a reader
that advances past #2's events will "lose the events created by transaction
#1". Its answer is to restrict reads to transactions older than
`pg_snapshot_xmin(pg_current_snapshot())`, with polling kept as a backup.

In a store like this, a Commanded-style rule applied to payload positions is
unsafe in both directions:

- A notification at position 11 that arrives while the checkpoint is 9 does not
  prove that position 10 was lost. Position 10 may belong to a transaction that
  is still in flight, or to one that aborted and will never appear.
- The more dangerous case is dropping notifications at or below the checkpoint.
  Suppose the consumer reads up to 11 naïvely and then receives position 10 from
  the late committer. Dropping it as a duplicate loses event 10 for good.

Deduplication by payload position is safe only if the checkpoint itself is
advanced by a gap-safe read, one that never moves past a position held by an
in-flight transaction. In that design, the payload position works as a lower
bound on the store's high-water mark. It tells the consumer whether a read is
worth issuing. It does not tell the consumer what to read.

### Emission granularity

Folding is per transaction and per payload, so where `NOTIFY` is issued decides
how many notifications are sent:

- A row-level trigger with a constant payload folds to one notification per
  transaction per channel.
- A row-level trigger whose payload carries each row's position does not fold,
  and sends one notification per event.
- A statement-level `AFTER INSERT … REFERENCING NEW TABLE AS … FOR EACH
  STATEMENT` trigger can send a single notification per statement carrying
  `max(position)` or a min and max range. Such a trigger "executes once for any
  given operation… an operation that modifies zero rows will still result in
  the execution" of it, so it must skip empty statements.
- Constraint triggers can be deferred to the end of the transaction but "must be
  AFTER ROW triggers", which is the form pgmq uses.
- The library can also issue `pg_notify` itself, once per append transaction,
  with the batch's high-water position.

Fewer and smaller notifications also mean less work while holding the global
commit-time notify lock.

### Recommended design for this event store

1. **Channels.** Use one global channel per schema, with a lower-case name that
   fits in 63 bytes including the prefix (for example `<schema>_events`). Route
   to stream, category and consumer-group subscribers inside the process, from
   a single listener connection, as Commanded does. Do not use per-stream
   channels. Add a small, fixed set of per-category channels only if consumers
   are mostly category-scoped and the deployment runs PostgreSQL 19 or later.
   Only then does the server stop waking uninterested listeners. Budget for
   sending each append to both the global and the category channel.
2. **Payloads.** Carry the append's highest global position, and optionally its
   category, as compact text (for example `"<position>"` or
   `"<category>:<position>"`). Never carry event data. This lets a consumer:
   - ignore wake-ups at or below a gap-safe checkpoint;
   - collapse a burst of pending notifications into one read up to the maximum
     position;
   - filter by category on a shared channel;
   - notice that it is behind.
3. **Gap detection.** Detect gaps from payload positions only if positions are
   commit-ordered, which needs serialised appends like Commanded's `$all` row
   update or a table lock. With sequence-reserved positions, treat the payload
   as a hint. The read itself has to be gap-safe, using a high-water mark or
   transaction-id snapshot, and an apparent gap should prompt a read rather
   than an alarm.
4. **Emission.** Issue one notification per append transaction, either from
   the library or from a statement-level trigger, rather than per event. Where
   no positional information is needed, use a constant payload so that
   in-transaction folding applies.
5. **Consumer hygiene.** Ignore notifications whose `pid` matches the
   consumer's own session. Keep notifications strictly as hints over the
   durable log. Every surveyed system (Procrastinate, River's `PollOnly` mode,
   pgmq, eugene-khyst) keeps polling as a fallback.
