# How should a psycopg 3 consumer run a dedicated LISTEN connection, including reconnection, keepalive, health detection and catch-up polling after missed notifications?

## Question

How should a Python consumer built on psycopg 3 host its LISTEN connection,
covering reconnection, TCP keepalive, detecting when the connection or the
notification path has failed, and catch-up reads that cover notifications it
missed?

## Findings

### 1. Why the listener needs a dedicated, autocommit connection that does no other work

Several psycopg and PostgreSQL behaviours together mean the LISTEN connection
should be a standalone connection with nothing else running on it:

- **Transactions hold notifications back.** PostgreSQL delivers a notification
  to a listening session only *between* transactions. A session that is inside
  a transaction gets nothing until that transaction ends. `LISTEN` itself takes
  effect only at commit. The psycopg docs therefore say the connection should
  be kept in `autocommit` mode "if you wish to receive or send notifications in
  a timely manner". The NOTIFY docs add a second reason. A session that has run
  `LISTEN` and then stays in a long transaction stops the shared notification
  queue (8 GB in a standard install) from being cleaned up. PostgreSQL logs a
  warning naming that session once the queue is half full. If the queue fills,
  NOTIFY-issuing transactions fail at commit. So an idle-in-transaction listener
  can end up breaking appends, not just slowing delivery.
- **The generator holds the connection lock.** In psycopg's source,
  `notifies()` runs its whole loop under `with self.lock:`. Psycopg issue #340
  shows that `execute()` on the same `AsyncConnection` hangs while another
  coroutine is iterating `notifies()`. pgqueuer, a Python queue, works around
  this by calling `notifies(timeout=1.0, stop_after=1)` so the lock is released
  after every batch. The simpler fix is not to share the connection at all.
  Procrastinate, a psycopg-3-based job queue, opens a separate connection for
  listening (`_get_standalone_connection`, `autocommit=True`) rather than
  borrowing one from its pool. Catch-up reads and other queries then run on
  normal pooled connections.
- **LISTEN registrations belong to the session.** PostgreSQL clears them
  automatically when the session ends. A pooled connection is a poor home for
  them. If it is returned to the pool it either carries live registrations or
  gets reset, and if the pool drops a broken connection the registrations
  disappear without any signal. Every reconnect must re-issue every `LISTEN`.
- **Channel names cannot be bound parameters.** Psycopg's server-side binding
  does not work for utility statements such as `SET` and `NOTIFY`, and the docs
  suggest `pg_notify()` for sending. `LISTEN` also takes its channel as an
  identifier, so the listener should build the statement on the client with
  `sql.SQL("LISTEN {}").format(sql.Identifier(channel))`.
- **The listener must reach a primary.** `LISTEN` and `NOTIFY` raise errors in
  hot standby, and notifications exist only on the server where the NOTIFY
  committed. A listener connected through a multi-host conninfo should set
  `target_session_attrs=read-write` (or `primary`) so that a reconnect after
  failover finds the new primary. Notifications that were in flight on the old
  primary are lost, so the catch-up read in section 5 is required.

### 2. Receive loop: `notifies(timeout=...)` plus a liveness check

Since psycopg 3.2, `Connection.notifies(*, timeout=None, stop_after=None)`
yields `Notify` objects (`channel`, `payload`, `pid`) as they arrive. It stops
when `timeout` seconds have passed (the deadline is computed once at the start,
so it ends on time even on a busy channel) or after `stop_after` notifications.
Without a timeout the generator blocks indefinitely and never gives control
back for health checks. Bounded generator runs inside an outer loop are the
standard shape.

The minimum psycopg version matters:

- Before 3.2.4, notifications that arrived between `LISTEN` and the start of the
  generator, or between two generator runs, were lost (issue #962). The issue's
  reproduction is exactly the "loop on `notifies(timeout=5)`, health-check in
  between" pattern.
- 3.2.4 added a backlog so those notifications are yielded on the next run.
  That backlog leaked memory on long-lived connections (around 200 MB per hour
  at 10,000+ events per minute, per issue #1091).
- 3.2.10 fixed the leak. It also deprecated using notify handlers and the
  generator on the same connection, which now emits a runtime warning. If a
  handler is registered, notifications are no longer captured while the
  generator is not running.

A consumer should therefore require psycopg 3.2.10 or later and use only the
generator on its listener connection. `add_notify_handler()` callbacks fire
only during other connection operations, so they are a poor fit for an
otherwise-idle listener.

Procrastinate's `_loop_notify` is a compact, production-proven version of the
loop. It iterates `connection.notifies()` under a 30-second timeout
(`LISTEN_TIMEOUT = 30.0`), and every time the timeout expires it runs
`SELECT 1`. A `psycopg.OperationalError` from either step means "connection is
dead, we need to reconnect": it breaks out to an outer `while True` loop, which
opens a new standalone connection and re-issues every `LISTEN`. River (Go) has
the same structure. Its notifier pings the connection when no notification has
arrived within a 5-second ping interval, reconnects with exponential backoff,
logs "Notifier unhealthy", and re-runs `LISTEN` for every active topic after
reconnecting.

River also had a bug worth learning from. Its ping once used an
already-cancelled context, so it "always returned context.Canceled" and dead
connections went unnoticed. A health check has to actually reach the server.

The psycopg docs also describe an event-driven alternative to timed pings:
register `conn.fileno()` with `selectors` (sync) or `loop.add_reader` (asyncio),
and run `SELECT 1` only when the socket becomes readable or a 60-second wait
expires. Either way, the round-trip query is what confirms the connection.

### 3. Failure detection: what notices which failure

Failures fall into four groups, and each needs a different mechanism:

- **Clean server-side termination.** This covers restarts,
  `pg_terminate_backend`, and `idle_session_timeout`. The server sends an error
  and closes the socket, so the blocked generator wakes and raises. Since
  3.2.4, psycopg raises the specific server error (for example `AdminShutdown`
  57P01 or `IdleSessionTimeout` 57P05) instead of a generic `OperationalError`.
  Every SQLSTATE class 08 (connection exception) and class 57 (operator
  intervention) error maps to `OperationalError`, so a single
  `except psycopg.OperationalError` catches them all.
- **`idle_session_timeout`.** This setting terminates sessions that are idle
  and not in a transaction, and a waiting listener is exactly that. The
  PostgreSQL docs suggest applying the setting only to particular users, so
  either the listener's role should have it disabled, or the periodic
  `SELECT 1` must run more often than the timeout.
- **Silent network failure (a half-open TCP connection).** No bytes arrive, so
  nothing wakes the generator. An idle listener also sends nothing, so
  `tcp_user_timeout` cannot fire either. With Linux defaults
  (`tcp_keepalive_time` 7200 s, `tcp_keepalive_intvl` 75 s,
  `tcp_keepalive_probes` 9), libpq's keepalives (enabled by default) take over
  two hours to declare the peer dead. The fix is to set client-side conninfo
  parameters explicitly:
  - `keepalives_idle`, `keepalives_interval` and `keepalives_count` (for
    example idle 15–30 s, interval 5–10 s, count 3) bound detection while idle.
  - `tcp_user_timeout` (milliseconds) bounds how long sent data, such as the
    health-check `SELECT 1`, can go unacknowledged before the kernel closes the
    socket. According to the Linux `tcp(7)` man page, `TCP_USER_TIMEOUT` "will
    override keepalive to determine when to close a connection due to keepalive
    failure".
  - These options do not apply to Unix-domain sockets, and are ignored on
    platforms without the matching socket option.
  - Wrapping the health query in a client-side deadline (for example
    `asyncio.wait_for`) adds a further layer. On timeout, discard the
    connection; psycopg 3.3.6 fixed a case where it waited forever for an
    interrupted query on an unresponsive server.
  - On the server side, `tcp_keepalives_idle`, `tcp_keepalives_interval` and
    `tcp_keepalives_count` let PostgreSQL detect clients that have vanished.
    The PostgreSQL docs note that reliable, bounded detection of lost TCP
    connections may require tuning these.
- **The connection is healthy but notifications are not flowing.** Examples
  are a LISTEN registration missing after a code path bypassed re-listen, a
  publisher that stopped notifying, or a pooler in the path. `SELECT 1` cannot
  see this. Oban's Sonar handles it by periodically sending a notification on a
  `sonar` channel and recording which nodes it hears from. It pings every 5 s
  after a status change, backs off to 60 s, and treats a node as stale after
  120 s. The notifier then reports `:isolated` (hearing nothing), `:solitary`
  (hearing only itself) or `:clustered`. When it is `:isolated`, Oban's stager
  switches to `:local` mode and signals local queues directly on its 1-second
  staging interval, so jobs are still picked up without pub/sub.
  - A psycopg consumer can copy this by issuing `SELECT pg_notify('<heartbeat
    channel>', ...)` on a schedule and checking that it arrives before a
    deadline. Comparing `Notify.pid` with `conn.info.backend_pid` identifies
    self-sent notifications.
  - Each heartbeat is a committed NOTIFY on the shared queue, so a modest
    interval keeps its cost negligible next to append traffic.

### 4. Reconnection

The outer loop should:

1. Connect with an explicit `connect_timeout`. If none is set, psycopg defaults
   to 130 s and enforces a 2 s minimum. The timeout applies to each host in a
   multi-host list.
2. Set `autocommit=True` and the keepalive and `target_session_attrs`
   parameters above.
3. Re-issue `LISTEN` for every channel. Because each statement autocommits,
   every registration is in effect once `execute()` returns.
4. Reset the backoff counter, mark the listener healthy, and trigger a
   catch-up read.
5. On any `OperationalError` (or health-check timeout), mark it unhealthy,
   close the connection, and sleep with capped exponential backoff and jitter
   before retrying.

psycopg_pool uses the same model for its own reconnects: exponential backoff
up to `reconnect_timeout`, then a `reconnect_failed` callback where the
application can alert or shut down. A listener should expose the same kind of
hook, because a listener that is down for a long time silently degrades
consumers to pure polling. Procrastinate's outer loop reconnects immediately
with no backoff, which risks a tight loop while the database is unavailable.
River's exponential backoff is the better model.

### 5. Catch-up polling: treat notifications as wake-up hints

The LISTEN documentation describes the race-free startup order:

1. Run and commit `LISTEN`.
2. In a new transaction, read the current state.
3. Rely on notifications for later changes.

The docs say the first few notifications "might refer to updates already
observed … but this is usually harmless". For an event-store consumer this
order should run on *every* (re)connect, not only at startup. Registrations
are dropped when the session ends, so anything committed while the listener was
disconnected, or during a failover, produced no notification it can still
receive. Only a read from the consumer's last stored position recovers it.

Two design rules follow:

- **Notifications only wake the consumer; the log is the source of truth.**
  The listener should not process payloads. It sets a wake-up signal (an
  `asyncio.Event`, or a `threading.Event` for a sync listener thread), and the
  consumer reads forward from its stored position on its own pooled
  connection. Procrastinate does exactly this: a `job_inserted` notification
  sets `_new_job_event`. The consumer should clear the event *before* starting
  each read pass, so a notification that arrives mid-read causes another pass
  instead of being absorbed. Within one transaction, NOTIFYs with an identical
  channel and payload collapse into one. Hints therefore do not map one-to-one
  to events, which is fine for a wake-up model.
- **Keep a fallback poll even when the listener is healthy.** Procrastinate's
  worker waits on whichever finishes first: the notification event, a
  `fetch_job_polling_interval` sleep (default 5 s), or a stop event. The
  interval puts an upper bound on latency for any notification lost in ways
  the listener cannot detect. When the listener is unhealthy, consumers should
  tighten to their normal polling interval, as Oban's stager does when
  isolated.

### 6. Reference shape (asyncio)

```python
async def run_listener(conninfo, channels, wake, health):
    attempt = 0
    while True:
        try:
            async with await psycopg.AsyncConnection.connect(
                conninfo, autocommit=True, connect_timeout=10,
                keepalives=1, keepalives_idle=15, keepalives_interval=5,
                keepalives_count=3, tcp_user_timeout=30_000,
                target_session_attrs="read-write",
            ) as conn:
                for channel in channels:
                    await conn.execute(
                        sql.SQL("LISTEN {}").format(sql.Identifier(channel)))
                attempt = 0
                health.mark_healthy()
                wake.set()                      # catch-up after (re)LISTEN
                while True:
                    async for _ in conn.notifies(timeout=10.0):
                        wake.set()
                    await asyncio.wait_for(conn.execute("SELECT 1"), 5.0)
        except (psycopg.OperationalError, TimeoutError):
            health.mark_unhealthy()
            await asyncio.sleep(min(30.0, 0.5 * 2 ** attempt) * random.uniform(0.5, 1.0))
            attempt += 1
```

The consumer side loops: wait for `wake` or the poll interval, clear `wake`,
then read from its checkpoint until caught up. A sync implementation has the
same structure, with `psycopg.Connection`, `for n in conn.notifies(timeout=...)`
in a dedicated thread, and a `threading.Event`. With psycopg 3.2.10 or later and
no notify handlers registered, a notification that arrives during the
`SELECT 1` is held in the backlog and yielded on the next `notifies()` run. If
it were dropped, the catch-up read and fallback poll would still recover the
event.
