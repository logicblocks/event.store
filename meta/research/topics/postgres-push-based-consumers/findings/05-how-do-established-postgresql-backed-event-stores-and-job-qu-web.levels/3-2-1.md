# What latency and lost-wake-up trade-offs arise from sending NOTIFY in a separate short transaction after an append commits, rather than inside the append transaction itself?

## Question

If an event store sends NOTIFY in its own short transaction after the append transaction has committed, instead of inside the append transaction, what does that change for append latency, wake-up latency and the risk of consumers missing a wake-up?

## Findings

**Summary.** Moving NOTIFY out of the append transaction trades atomicity for a shorter serialised section. Appends no longer queue on PostgreSQL's global notification lock while their commit flushes WAL or waits for synchronous replication. In exchange, the wake-up arrives about one client-to-server round trip later. A new way to lose a wake-up also appears: anything that goes wrong between the append's commit and the NOTIFY's commit loses it. Consumers need a fallback poll in either design, because listeners can miss notifications anyway. So the extra producer-side loss risk costs, at worst, one poll interval of latency. No events are lost, because they are durably committed and consumers read them from the table.

### What the commit path does in each case

NOTIFY inside a transaction is transactional. PostgreSQL delivers the events "until and unless the transaction is committed". It also guarantees that "messages from different transactions are delivered in the order in which the transactions committed". To provide that ordering, `PreCommit_Notify` in `async.c` serialises writers "by acquiring a special lock that we hold till after commit". The comment explains that "queue entries appear in commit order, and in particular that there are never uncommitted queue entries ahead of committed ones". This is a heavyweight lock, released with the transaction's other locks.

`xact.c` shows what that lock spans. `CommitTransaction` calls `PreCommit_Notify` before `RecordTransactionCommit`, and it releases locks only afterwards. `RecordTransactionCommit` performs the synchronous `XLogFlush` and, when required, `SyncRepWaitForLSN`. An appending transaction that notifies therefore holds the global lock through its own WAL flush and any synchronous-replication round trip. Every other notifying commit waits behind it. Recall.ai saw this lock in production as "AccessExclusiveLock on object 0 of class 1262 of database 0". With tens of thousands of concurrent writers, processes waited more than a second for it, and database CPU, I/O and throughput collapsed.

A separate NOTIFY-only transaction behaves differently. NOTIFY forces an XID to be assigned, with the comment "Make sure that we have an XID assigned to the current transaction". The transaction therefore writes a commit record. But `RecordTransactionCommit` flushes synchronously only when `wrote_xlog && markXidCommitted && synchronous_commit > off`. `wrote_xlog` is computed from WAL written *before* the commit record, and the synchronous-replication wait has the same condition ("we only want to wait if this backend assigned an xid and wrote WAL"). A transaction that only calls `pg_notify` writes no other WAL. It should therefore take the asynchronous-commit path, and it holds the notification lock only while queueing its entry and inserting its commit record, not through an fsync or a standby acknowledgement. This conclusion comes from reading the current source, not from a published benchmark. Each such transaction also costs one extra XID and a small commit record.

PostgreSQL 19 does not change this. Its only NOTIFY release-note item (beta 4, September 2026) is "Improve NOTIFY to only wake up backends that are listening to specified notifications". That item is commit 282b1cde ("Optimize LISTEN/NOTIFY via shared channel map and direct advancement"), and it targets wake-ups, not the commit-time lock. The `async.c` on the master branch still contains the lock that is held until after commit.

### Latency trade-offs

- **Append latency improves under concurrency.** With NOTIFY inside the transaction, every appending commit queues on the global lock, which is held across other transactions' flushes, including notifying transactions in unrelated parts of the application. A slow synchronous standby slows every notifying commit. With a separate transaction, the append commits without touching the lock. The NOTIFY transaction still contends for it, but only briefly, unless other writers in the cluster still notify inside their own transactions.
- **Wake-up latency gets slightly worse.** Inside the transaction, listeners are signalled from `AtCommit_Notify` immediately after the commit, before the appending client has even received its commit reply. A post-commit NOTIFY adds at least one client-to-server round trip (`SELECT pg_notify(...)` on an autocommit connection), plus any wait for the lock. The extra delay is tiny compared with any polling interval.
- **Pipelining has a trap.** psycopg's docs warn that "even in autocommit, the server wraps the statements sent in pipeline mode in an implicit transaction, which will be only committed when the Sync is received". If an INSERT and a `pg_notify` share one Sync group, NOTIFY is back inside the append's transaction. Any attempt to hide the extra round trip with pipelining needs a sync point between the append's commit and the NOTIFY.
- **Debouncing can reach further.** Inside a transaction, PostgreSQL merges duplicate notifications only within that one transaction. A post-commit notifier can merge across many appends, for example one NOTIFY per category per window, at the cost of up to one window of extra delay. River debounces inside the insert transaction instead. Its `maybeNotifyInsertForQueues` calls `tx.NotifyMany` on the inserting transaction, rate-limited per queue by `FetchCooldown`, which defaults to 100 ms.

### Lost-wake-up trade-offs

- **In-transaction NOTIFY is atomic and never early.** The notification exists only if the append commits. On the reading side, `async.c` holds back entries from a transaction "still in progress" by testing `XidInMVCCSnapshot` "before we test TransactionIdDidCommit, else we might return a message from a transaction that is not yet visible to snapshots". A consumer that queries after a wake-up will see the append. Oban's Postgres notifier documents this as the property it alone offers: notifications "will not be sent if the transaction is rolled back … this is the only notifier which provides that guarantee".
- **Post-commit NOTIFY is a dual write.** It has the classic outbox failure mode: "if a service sends a message after committing the transaction there's no guarantee that it won't crash before sending the message". For an event store, the loss window covers a process crash or kill, a dropped connection after the commit reply, and an error in the NOTIFY transaction itself. The events stay committed, so a missed wake-up only delays them. The next fallback poll finds them, or the next wake-up caused by a later append on the same channel does. The worst case is an append that is the last one before a quiet period: its events wait a full poll interval.
- **Listeners need a fallback poll regardless.** Notifications are also lost when a listener disconnects. In psycopg before 3.2.4, "notification received between calling LISTEN and starting the generator were lost". River's `FetchPollInterval` (default 1 s) exists because "Typically new jobs will be picked up ~immediately after insert via LISTEN/NOTIFY, but this provides a fallback". GoodJob polls every 10 s in production "in case of a LISTEN/NOTIFY blip". Given this, the extra loss window of the post-commit design adds rare, bounded delays rather than a new type of failure.
- **Send strictly after the commit reply.** If the notification can go out before the append is visible, for example from another connection or a non-transactional bus while the append is still open, a consumer can wake, read nothing, and go back to sleep. That is a lost wake-up created by the design. Oban's PG notifier "scales much better than Oban.Notifiers.Postgres but lacks its transactional guarantees", which is the same trade-off described by a maintainer. Sending in the wrong order produces early wake-ups. A wake-up sent for an append that later rolls back is spurious but harmless.
- **Failure isolation reverses.** With NOTIFY inside the transaction, notification problems can fail appends. "If this queue becomes full, transactions calling NOTIFY will fail at commit", and the queue fills when a listening session sits in a long transaction. Also, "a transaction that has executed NOTIFY cannot be prepared for two-phase commit". With a separate transaction, these failures affect only the wake-up. The library must then log, not raise, NOTIFY errors after commit. A caller that sees an exception after a successful commit could retry and append twice. This point is inferred from the semantics above, not documented by a maintainer.
- **Ordering is weaker but rarely matters.** Separate NOTIFY transactions from concurrent appenders can reach the queue in a different order from their appends' commits. This matters only if a payload is treated as a high-water mark. Wake-ups without a payload, or with only a hint, are unaffected. Neither design changes the out-of-order sequence-number gaps that a global-position reader must handle, because sequence values are allocated before commit.

### Practice among maintainers

River and Oban's Postgres notifier keep NOTIFY inside the insert transaction for atomicity, and both rely on a fallback poll. Recall.ai moved off LISTEN/NOTIFY entirely, "in favor of tracking this logic at the application layer". In the Hacker News discussion of that post, commenters proposed a single relay process that follows WAL or logical replication and issues NOTIFY, an outbox-style relay "whose only job is to listen to the wal … and then NOTIFY", so that NOTIFY does not burden other transactions.

For a psycopg 3 event store whose consumers already poll as a safety net, the post-commit NOTIFY is a reasonable low-risk choice. Use an autocommit `pg_notify` on the same connection after the commit returns, with errors logged and not raised. It keeps the global lock out of the append's flush and replication wait. The cost is about one round trip of wake-up delay and an occasional delay of one poll interval after a crash.
