# How can a notification-driven PostgreSQL consumer be woken promptly when the transaction holding back pg_snapshot_xmin, or an unfilled sequence gap, resolves without itself issuing a NOTIFY, without reverting to fixed-interval polling?

## Question

Suppose a consumer is woken by commit-time `NOTIFY` but has to stop at a safe horizon. That horizon is either the transaction-ID horizon `pg_snapshot_xmin(pg_current_snapshot())` or the first unfilled gap in a sequence-assigned global position. How can the consumer learn promptly that the blocking transaction or gap has resolved when nothing sends a notification at that moment? And how can it do so without falling back to a fixed polling interval?

## Findings

### Which stalls actually lack a wake-up signal

`NOTIFY` events are "not delivered until and unless the transaction is committed". Messages from different transactions "are delivered in the order in which the transactions committed". If an aborted transaction had executed `NOTIFY`, the notification has no effect. So when the blocker is itself an appender that commits, its own commit-time notification already wakes the consumer, and no extra mechanism is needed. Three cases produce no signal at all:

1. **The blocking appender rolls back.** Its notification is discarded with the rest of the transaction.
2. **The xmin is held by a transaction that never appends.** `pg_snapshot_xmin` is the "lowest transaction ID that was still active". Only transactions with an assigned ID count, and an ID is normally assigned only once a transaction "changes the state of the database". The snapshot is also cluster-wide. In the server source, `GetSnapshotData` adds every running backend's XID to the snapshot and lowers `xmin` from it without any database check. Database scoping applies only to the separate vacuum-horizon computation. So a writing transaction in *another database* on the same server can hold back an event store's horizon. Practitioner write-ups of the transaction-ID horizon technique already warn that reads "may be a bit delayed if our transactions last long".
3. **A sequence gap is never filled.** The value from `nextval` "is not reclaimed for re-use if the calling transaction later aborts". `INSERT ... ON CONFLICT` can use up values without any abort, and crashes can also leave gaps. No transaction will ever fill such a gap, so nothing will ever signal. Marten's documentation notes that "most holes fill in within milliseconds — they are simply appends that have drawn a sequence number and not yet committed". The remaining gaps are permanent.

The useful options are: wait on the blocker inside the server; classify the blocker and compute a single deadline; or remove the consumer's dependence on the horizon altogether.

### 1. Block inside the server until the blocker ends

PostgreSQL already has an event-driven primitive for "wait until transaction X ends". Each transaction holds an exclusive lock on its own transaction ID until it ends. "When a process finds it necessary to wait specifically for another transaction to end, it does so by attempting to acquire share lock on the other transaction's ID ... That will succeed only when the other transaction terminates". The snapshot functions themselves only *report* status: `pg_xact_status` returns `in progress`, `committed` or `aborted`, and nothing there waits. Two documented SQL routes do lead to this kind of wait:

- **Advisory locks, if appenders cooperate.** Transaction-level advisory locks "are automatically released at the end of the transaction", whether it commits or rolls back. A shared lock "does not conflict with other shared locks on the same resource, only with exclusive locks", and the lock functions wait "if necessary".
  - *A design built from these facts (inference, not an established pattern):*
    - At the start of each append, the appender takes `pg_advisory_xact_lock(pg_current_xact_id()::text::bigint)`. Marten uses the same `::text::bigint` cast to turn `pg_snapshot_xmax` into an integer.
    - A stalled consumer takes the blocking XID, from `pg_snapshot_xmin` or from `pg_snapshot_xip`, and calls `pg_advisory_lock_shared(k)` followed by `pg_advisory_unlock_shared(k)`.
    - That call blocks inside the server until the appender commits *or aborts*, and then returns at once. This closes case 1 without any polling.
    - If the call returns immediately, no appender holds the key, which shows the blocker is not a cooperating appender (case 2).
  - Each transaction gets its own key, so appenders never queue behind a waiting consumer. Shared locks also let any number of consumers wait at the same time.
  - Use `lock_timeout` or `statement_timeout` to bound the wait.
  - Run the wait on a connection other than the `LISTEN` connection. A session in a transaction does not deliver notifications "until just after the transaction is completed", and psycopg recommends autocommit for timely notifications.
  - Advisory keys share one namespace across the database, so the keys can collide with other uses of advisory locks.
- **Unique-index waits for a known gap position.** "If a conflicting row has been inserted by an as-yet-uncommitted transaction, the would-be inserter must wait to see if that transaction commits." In principle, a consumer that sees a gap at position N could probe-insert N inside a transaction and then roll it back. The probe waits for whichever transaction is inserting N. *Inference:* this is clumsier than advisory locks. The probe succeeds immediately when N has been drawn but not yet inserted, or will never be inserted, so it cannot tell "not yet" from "never". It also needs insert rights and briefly delays the real appender.

### 2. Classify the blocker and arm one deadline instead of an interval

Lock-waiting cannot cover a transaction that does not cooperate (case 2) or a gap with no owner (case 3). For these, the consumer can classify the stall once and then set a single, computed wake-up:

- **Classify the blocker.**
  - `pg_stat_activity` exposes `backend_xid`, `xact_start`, `state` and `state_change`, which connect a blocking XID to its session.
  - Marten's `GapLivenessProbe` treats a gap as possibly live while any of these hold:
    - a transaction that began before the gap was observed holds `RowExclusiveLock` on the events table;
    - any client transaction in the database started at or before the observation;
    - an in-progress XID below the recorded `xmax` remains in `pg_snapshot_xip`.
  - It rules out sessions that are `idle in transaction` and whose `state_change` predates an "allocation fence", because they cannot have called `nextval` since. It also rules out its own leadership-lock connections.
  - Gaps it proves dead are skipped "in one step" and recorded in `mt_high_water_skips`.
  - `SkipStaleGapsDespiteLiveTransactionsAfter` lets an operator cap the wait. Its default is `null`, which never knowingly skips past live appenders.
- **Bound how long any blocker can last.**
  - `idle_in_transaction_session_timeout` terminates idle-in-transaction sessions.
  - `transaction_timeout` (added in PostgreSQL 17) terminates "any session that spans longer than the specified amount of time in a transaction".
  - The documentation advises against setting either one in `postgresql.conf`, so set them per role or per database for the roles that write events.
  - *Inference:* if every writer role has `transaction_timeout = T`, a blocker found in `pg_stat_activity` must end by `xact_start + T`. The consumer can then wait for notifications with psycopg 3.2's `notifies(timeout=...)` set to that deadline, re-check once with `pg_xact_status`, and skip a gap that has been proven dead. Re-checks happen only while a stall exists and are tied to a deadline the server enforces. An idle consumer stays purely notification-driven.

### 3. Remove the dependence on the horizon

The stall exists because the checkpoint is a *position* that has to advance contiguously. Two designs avoid it:

- **Snapshot-difference batches (PgQ).**
  - Each PgQ tick stores `tick_snapshot` (default `txid_current_snapshot()`).
  - A batch between snapshots sn1 and sn2 holds the events whose txid is "NOT txid_visible_in_snapshot(ev_txid, sn1) AND txid_visible_in_snapshot(ev_txid, sn2)".
  - A long-running or aborted transaction therefore never holds back later commits. When it does commit, its events simply fall into the next batch.
  - PgQ's batch SQL keeps scans small during long transactions by range-scanning `[xmax1..xmax2]` and finding older XIDs with an `IN (..)` list.
  - PgQ itself is time-driven, not push-driven. The `pgqd` daemon runs the ticker every `ticker_period` (default 1 second). Queues tick at most `queue_ticker_max_lag` (default 3 seconds) after an event, and at `queue_ticker_idle_period` (default 1 minute) when there are no events. The ticker functions issue no `NOTIFY`.
  - *Inference:* an event store could run the snapshot-difference read on every `NOTIFY` wake-up. Every event it needs to deliver comes from a committed appender that sent its own notification, so notifications alone are enough and there is never a stall to resolve.
  - The cost is that, across batches, delivery follows visibility (commit) order rather than global position, and the checkpoint has to persist a snapshot.
  - *Inference:* per-stream order still holds when appends use optimistic concurrency. A writer of version n+1 must have seen version n committed, or else conflicted on it.
- **Logical decoding.**
  - "Concurrent transactions are decoded in commit order", and "transactions that were rolled back explicitly or implicitly never get decoded". So none of the three stall cases arises, and the change stream is pushed over the replication protocol.
  - Costs:
    - a slot keeps WAL and catalog rows even while no client is connected;
    - it needs `wal_level=logical`;
    - for a psycopg 3 library, streaming replication support is still an open request ("Replication support", issue #71, opened August 2021), so a different client would be needed.

### Synthesis

No server mechanism notifies anyone when an arbitrary transaction ends or when a sequence value is lost. A consumer that keeps position-ordered, horizon-gated reads can avoid fixed-interval polling by layering the options:

1. Commit-time `NOTIFY` for appenders that commit.
2. A server-side lock wait on a per-transaction advisory key, which also wakes on abort.
3. A liveness classification plus one deadline bounded by `transaction_timeout` or `idle_in_transaction_session_timeout`, for blockers that do not cooperate and for dead gaps.

The alternative is to stop gating on the horizon at all, using snapshot-difference or commit-order consumption. That makes the stall disappear, but it gives up delivery in global-position order.
