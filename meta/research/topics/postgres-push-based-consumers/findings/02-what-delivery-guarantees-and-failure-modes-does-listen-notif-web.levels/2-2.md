# How much throughput does a write path lose when NOTIFY is issued in the same transaction as the data write, compared with batching notifications in a separate transaction, across different levels of commit concurrency?

## Question

How much write throughput is lost when `NOTIFY` is issued inside the same transaction as the data write, compared with batching notifications into a separate transaction, and how does that loss change as the number of concurrently committing transactions grows?

## Findings

### Why the cost exists: a cluster-wide lock held across the commit

When a transaction that has issued `NOTIFY` commits, `PreCommit_Notify()` in `src/backend/commands/async.c` takes a heavyweight lock, `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)`. It is a lock on "database 0", which makes it instance-wide rather than per database. The source comment says the lock serialises writers "that we hold till after commit" so that "queue entries appear in commit order". In current master this lock is still present (async.c on GitHub master, checked October 2026).

The order of calls in `CommitTransaction()` in `xact.c` shows what the lock is held across:

1. `PreCommit_Notify()` takes the lock and appends the transaction's notifications to the queue.
2. `RecordTransactionCommit()` writes the commit record and, for a transaction that wrote WAL under `synchronous_commit` on, calls `XLogFlush`.
3. `AtCommit_Notify()` calls `SignalBackends()` to wake listeners.
4. Only after that are locks released.

So each notifying commit holds the lock through its own WAL flush and through listener signalling. DBOS describes the effect directly: the lock is held "for the entire duration of its commit, including the flush to disk". That stops notifying transactions from sharing a group-commit fsync. Transactions that do not notify never take this lock and are not serialised by it. Notifying transactions, though, are serialised against each other across the whole instance.

The result is a throughput ceiling for notifying commits of roughly one commit per (flush latency plus signalling time). That ceiling does not depend on how many clients are committing. Insert-only throughput, by contrast, keeps rising with concurrency because group commit amortises fsyncs. The relative loss therefore grows with concurrency. (This framing is an inference from the code paths and the measurements below. No source states it as a formula.)

### Measured losses at different concurrency levels

| Concurrency | Workload | Same-transaction NOTIFY on master | Comparison | Source |
|---|---|---|---|---|
| 8 connections, laptop (M2) | NOTIFY-only, no listener | ~158k–190k TPS | ~299k–354k TPS with the commit lock skipped (about 2x) | Bagga, pgsql-hackers, 2025-07-18 |
| 8 connections, laptop (M3 Max) | LISTEN plus NOTIFY | ~73k TPS | ~83k TPS with lock skipped (about 14%); `kill()` signalling dominated | Jacobson, as summarised on hackorum.dev |
| 100 connections | `INSERT` plus `NOTIFY` in one transaction | 817.9 TPS | 30,981.6 TPS for the same `INSERT` without `NOTIFY` (about 38x loss) | Mukhin, pgsql-hackers, October 2025 |
| 100 connections | `INSERT` plus `NOTIFY` in one transaction | ~29k–31k TPS | ~63k–66k TPS with the experimental WAL-transport patch (about 2x) | Bagga, pgsql-hackers, 2025-09-04 and 2025-09-25 |
| 1000 connections, 1 listener | NOTIFY transaction | 7,679 TPS | 95,430 TPS with the heavyweight lock commented out (about 12x) | Jacobson, pgsql-hackers, 2025-07-30 |
| Tens of thousands of writers (production) | Update endpoint issuing NOTIFY | Outage: one lock holder with 300+ queued waiters, waits of ~1 s, CPU and I/O falling | Moved notification logic to the application layer | Recall.ai, July 2025 |

Arseniy Mukhin's run is the closest match to an event-store append. It used `pgbench -n -c 100 -j 10 -T 100` with three scripts: insert-only, insert plus notify, and notify-only. Adding a 10-byte-payload `NOTIFY` to the insert transaction cut master throughput from about 31k to about 818 TPS. That is roughly one commit every 1.2 ms, which matches fully serialised fsyncs. Rishu Bagga's 100-connection insert-plus-notify run reached about 30k TPS on master, and neither poster gave hardware or `synchronous_commit` settings. So the size of the loss depends heavily on the environment, and the two runs cannot be reconciled from the thread.

The pattern fits the mechanism. Where a WAL flush is nearly free (laptops, or `fsync` that does not reach stable storage), the loss is modest. On durable storage under high concurrency it can reach one or two orders of magnitude. Bagga argued in the same thread that cloud deployments with compute separated from storage make it worse, because flushes are slower there.

In the same benchmark, notify-only transactions ran at 87,750 TPS on master, far faster than insert-plus-notify. `RecordTransactionCommit()` explains why. It flushes synchronously only when the transaction already wrote WAL (`wrote_xlog`). A transaction that only issues `NOTIFY` writes none, so it commits asynchronously and holds the lock only briefly. This is the mechanism behind the separate-transaction pattern.

### Batching notifications in a separate transaction

DBOS measured both designs for a Postgres-backed stream:

- **Same transaction.** A row trigger that issued a notification on every write peaked at about 2.9K writes per second. At that point CPU, memory and IOPS showed no strain, which points to a lock bottleneck.
- **Separate batched transaction.** Notifications were buffered in application memory and flushed periodically in one batch transaction. Throughput reached about 60K writes per second, roughly 20x higher, with 15–100 ms delivery latency, and Postgres CPU became the limit.

The trade-offs DBOS reports:

- **Latency.** Wake-ups are delayed by up to the flush interval.
- **Atomicity.** A crash can lose buffered notifications. Readers therefore poll the database at a low frequency as a fallback.

The concurrency numbers behind DBOS's figures were not published.

In mechanism terms, batching changes the cost model. The number of commit-lock acquisitions per second becomes one per flush interval, independent of writer count. A notify-only batch transaction does not wait for an fsync while holding the lock. Data writes get group commit back. Notifications with the same channel and payload in one transaction also collapse into one, according to the `NOTIFY` documentation. A batch of payloadless wake-ups on one channel is therefore delivered as a single notification.

### Changes in PostgreSQL core

Commit `282b1cd` ("Optimize LISTEN/NOTIFY via shared channel map and direct advancement") was written by Joel Jacobson and committed by Tom Lane on 2026-01-15. It adds a shared hash table of which processes listen on which channels. A notifier then signals only interested listeners, and it advances idle listeners' queue pointers without waking them. Signalling runs before the commit lock is released, so this shortens lock hold time in workloads with many listeners. Recall.ai's May 2026 update credits this commit with eliminating their bottleneck.

DBOS's author has said the change "does not remove the global lock". The current async.c confirms that the lock is still taken in `PreCommit_Notify()`, so the hold across the commit's WAL flush remains. The published insert-plus-notify measurements above predate this commit.

Proposals to remove the serialisation have not been merged:

- An out-of-order `NOTIFY` setting was rejected on semantic grounds. Tom Lane objected that it breaks commit-order delivery and that writers would still serialise on `NotifyQueueLock`.
- A patch that carries notification data through WAL and records its LSN in the commit record restored insert-plus-notify to about 34k TPS in Mukhin's test. It slowed notify-only transactions by about 2.5x and was last reported as still under review in the PostgreSQL 19 commitfests.

### Implications for an event-store write path

These follow from the evidence above:

- **Low commit concurrency (a single writer or a few).** Same-transaction `NOTIFY` costs little, because commits are already serialised on their own flushes. It also gives atomic "notify if and only if committed" semantics. No source measured this case with data writes, so treat it as likely rather than confirmed.
- **Tens to thousands of concurrent appenders.** Same-transaction `NOTIFY` caps appends at roughly the serial-fsync rate. Measured losses ranged from about 2x to about 38x, and production collapse was reported at very large scale.
- **Recommended pattern.** Issue a payloadless `NOTIFY` after commit from a separate transaction, debounced or batched, and treat it as a wake-up hint. Consumers read from their own stored positions and keep a slow fallback poll. This matches the pattern that recovered about 20x throughput in DBOS's measurements, at the cost of tens of milliseconds of latency and the need for that fallback.
