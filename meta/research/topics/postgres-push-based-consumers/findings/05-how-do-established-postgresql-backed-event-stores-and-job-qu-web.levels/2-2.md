# What does issuing NOTIFY inside high-throughput append transactions cost in commit throughput on current PostgreSQL versions, and how much do per-channel debouncing schemes like River's and pgmq's reduce that cost?

## Question

What does putting `NOTIFY` (or `pg_notify`) inside high-throughput append transactions cost in commit throughput on current PostgreSQL versions? How much do per-channel debouncing schemes, such as River's client-side insert-notification limiter and pgmq's throttled insert trigger, reduce that cost?

## Findings

### Where the cost comes from: a cluster-wide lock held across commit

Running `NOTIFY` costs almost nothing. The notification sits in backend-local memory and nothing happens until commit. If the same channel and payload are signalled more than once in one transaction, only one notification is delivered. Distinct payloads are always delivered separately. The current source builds a hash table for duplicate detection once a transaction has 16 pending notifications (`MIN_HASHABLE_NOTIFIES`). PostgreSQL 13's release notes list a general LISTEN/NOTIFY performance improvement. A July 2026 pgsql-hackers proposal to document NOTIFY's risks still lists "O(N²) duplicate checking", but it does not say which versions or cases that applies to.

The real cost lands at commit. In `PreCommit_Notify`, any transaction with pending notifications takes a heavyweight `AccessExclusiveLock` through `LockSharedObject(DatabaseRelationId, InvalidOid, 0, ...)`. The source comment says the backend holds this lock "till after commit". That keeps queue entries in commit order, so "there are never uncommitted queue entries ahead of committed ones". The lock is on "database 0", which is a shared object. So it serialises notifying commits across every database in the cluster, not just one. The July 2026 documentation proposal says the same. The lock sits inside an `if (pendingNotifies)` block, so transactions that issue no `NOTIFY` never take it.

While a notifying backend holds the lock, it does all of the following:

- writes its entries into the SLRU-backed notification queue (under `NotifyQueueLock`)
- finishes the transaction commit
- runs `AtCommit_Notify` "after committing to clog", which calls `SignalBackends()`

The lock is released only at end-of-transaction resource-owner cleanup. So notifying commits run strictly one at a time, and each one's critical section covers queue insertion, the commit itself and signalling of listeners.

### What it costs, in measured numbers

- **Notifying inserts versus plain inserts (pre-PostgreSQL 19 master).** Arseniy Mukhin posted a pgbench run (October 2025) with `pgbench -n -c 100 -j 10 -T 100`:
  - `insert_only` (`BEGIN; INSERT ...; COMMIT;`): 30,981 TPS
  - `insert_with_notify` (the same transaction plus one `NOTIFY` with a 10-byte payload): 817 TPS
  - `notify_only` (no insert): 87,750 TPS

  Adding one `NOTIFY` to a single-row insert transaction cut commit throughput about 38-fold. No hardware or configuration was given, and the author offered no explanation.

  My inference, not stated in the thread: a transaction that has written data must flush its commit record to WAL synchronously, and it does that while holding the lock. Notifying writers therefore pay their WAL flushes one after another instead of sharing group commits. A NOTIFY-only transaction writes no data and holds the lock only briefly. If that is right, the bad case is exactly an event-store append: every append writes WAL, normally with `synchronous_commit` on.
- **A second, smaller measurement.** The opening message of the "Write Notifications Through WAL" thread (Rishu Bagga, September 2025) reports about 30k TPS on master and 60k–70k with the patch. That run used `pgbench -c 100 -j 8` and a custom notifying-transaction script. The script and configuration differ from Mukhin's, so the size of the penalty depends heavily on the environment. The direction does not.
- **Listener count multiplies the time under the lock.** Before PostgreSQL 19, `SignalBackends()` sent a signal to every listening backend in the database, whatever channel it listened on, and it did so inside the critical section. Joel Jacobson's July 2025 ping-pong benchmark fell from 9,126 TPS with no extra listeners to 6,233 (10 listeners), 2,020 (100) and 238 (1,000 idle listeners on unrelated channels).
- **Production symptom.** Recall.ai (July 2025) had "tens of thousands of simultaneous writers". They logged lock waits such as "acquired AccessExclusiveLock on object 0 of class 1262 of database 0 after 1015.921 ms". As load rose, throughput, CPU and I/O all fell, which is the signature of lock serialisation rather than resource exhaustion. They moved the notification logic to the application layer.

  The post was later updated to say that commit 282b1cde "eliminated the bottleneck". That commit keeps the lock (see below). Whether it fixes what Recall.ai saw depends on how much of their lock-hold time was signalling, and the post does not say.

### What has changed in current versions

- **PostgreSQL 18 and earlier**, the current stable docs line: the database-0 lock is held across commit, and every listener in the database is signalled.
- **PostgreSQL 19**, at beta 4 as of 14 September 2026: commit 282b1cde, by Joel Jacobson and committed by Tom Lane on 15 January 2026, adds a shared channel map and "direct advancement".
  - Only backends listening on the notified channel are signalled.
  - Idle, uninterested listeners have their queue pointers moved forward without being woken.
  - The commit message reports "very significant improvements (integer multiples)" in NOTIFY throughput when many listeners are on other channels, and no slowdown when every listener wants every message. In the patch thread, the 1,000-listener case stayed near 9,000 TPS.
  - The release note reads: "Improve NOTIFY to only wake up backends that are listening to specified notifications."

  The design keeps, and explicitly relies on, the heavyweight lock: "This is possible because all NOTIFY writers are serialized by a heavyweight lock". PostgreSQL 19 therefore cuts the signalling part of the critical section, but notifying commits are still serialised, flush included. The current master `async.c` header still describes the database-0 lock.
- **Not in any release:** the "Write Notifications Through WAL" patch. It writes notification payloads into WAL and stores only an LSN in the queue, so the lock no longer has to be held to end of transaction. In Mukhin's run it lifted `insert_with_notify` from 817 to about 33,800 TPS, close to the insert-only baseline. It also cut `notify_only` from 87,750 to about 34,000 TPS, which nobody could explain. The patch was at v9 in November 2025, and it is not in the PostgreSQL 19 release notes.
- **Documentation.** A July 2026 pgsql-hackers proposal by Nikolay Samokhvalov would document the global commit lock, recommend `log_lock_waits` for diagnosis, and point to logical decoding as an alternative. Bruce Momjian replied that, with PostgreSQL 19's changes, a wiki page might suit better than the official docs.

### River: a client-side, per-queue limiter

- **Background.** River 0.5.0 (May 2024) dropped its trigger-based `NOTIFY` on every job insert. The changelog says the trigger emitted "a large amount of notifications any time there are lots of jobs being inserted". Now "a client-level debouncer ensures that these notifications are not emitted more often than they could be useful". The notification "piggy-backs" on the insert transaction.
- **Mechanism.**
  - `notifylimiter.Limiter` keeps a `lastSentByTopic` map in memory. `ShouldTrigger(topic)` returns true only if the configured wait has passed since that topic last fired.
  - The client builds the limiter with `config.FetchCooldown`, which defaults to 100 ms. That is the same interval that caps how often producers fetch.
  - After an insert, `maybeNotifyInsertForQueues` de-duplicates the affected queues and calls `ShouldTrigger(queue)` for each. It then sends a single `NotifyMany` call inside the same transaction, with a `{"queue": ...}` payload per queue that was due.
  - `FetchPollInterval` (default 1 s) stays as a periodic fallback fetch.
- **Effect on commit cost.** Only transactions that actually carry a `NOTIFY` take the lock. Each client process sends at most one notifying insert transaction per queue per 100 ms, so at most 10 lock-taking commits per second per process per hot queue. Every other insert commits without touching the lock. With P inserting processes and Q hot queues, the cap is about 10·P·Q per second. Compared with a serialised ceiling of hundreds of notifying commits per second, as in the benchmark above, the lock is uncontended most of the time.
- **Trade-offs, read from the code.**
  - The limiter's state is per process, so the cap grows with the number of processes. It is not a database-wide bound.
  - A send is recorded when `ShouldTrigger` returns true, before the transaction commits. If that transaction rolls back, the queue's notifications stay suppressed for the rest of the window.
  - Jobs inserted while notifications are suppressed may wait for the next notification or for the 1 s poll.
  - River has published no commit-throughput measurements for the change. The changelog says only that the extra insert latency "should be small".

### pgmq: a database-side, per-queue throttle

- **Background.** pgmq 1.7.0 added `enable_notify_insert`, a trigger that runs `NOTIFY` on insert. pgmq 1.8.0 (PR #445, merged November 2025) added throttling.
- **Mechanism.**
  - `enable_notify_insert(queue_name, throttle_interval_ms DEFAULT 250)` installs `AFTER INSERT DEFERRABLE FOR EACH ROW` constraint triggers.
  - Throttle state lives in an UNLOGGED table, `pgmq.notify_insert_throttle`, with columns `queue_name`, `throttle_interval_ms` and `last_notified_at`.
  - For each inserted row, the trigger runs `UPDATE ... SET last_notified_at = clock_timestamp() WHERE queue_name = ... AND (throttle_interval_ms = 0 OR clock_timestamp() - last_notified_at >= interval)`.
  - Only if a row was updated does it call `pg_notify('pgmq.q_' || queue || '.' || TG_OP, NULL)`.
  - The PR's review discussion focused on write amplification, which is why the table is unlogged. It contains no benchmarks.
- **Effect on commit cost.** The throttle state is shared in the database, so the cap is per queue across all producers: at most one notifying commit per 250 ms per queue, about 4 per second, however many processes are sending. That is a tighter bound than River's per-process one.

  With `throttle_interval_ms = 0`, every row calls `pg_notify`. Identical channel and NULL payload are folded within the transaction, but every sending transaction still takes the commit lock.
- **Trade-offs, my inference from the SQL.**
  - Every inserted row runs an extra `UPDATE` against one hot row per queue.
  - When the window has expired, the first sender's `UPDATE` locks that row until its transaction commits. A concurrent sender whose snapshot still shows the old row version blocks on that lock, then re-checks and skips. So for that brief window, concurrent senders to the same queue queue up behind the notifying transaction, whose own commit holds the NOTIFY lock.
  - Long sending transactions widen that window.
  - The timestamp is taken at `UPDATE` time, not at commit.

### How much debouncing helps

Neither maintainer has published commit-throughput measurements for their scheme, so the reduction cannot be given as a measured number. What the mechanism shows is that only transactions carrying a pending notification pay the serialisation cost. Debouncing cuts how many transactions those are: from every append to one per channel per interval (per process, for River). At 100 ms or 250 ms, that means single-digit to low tens of lock acquisitions per second per channel. The serialised ceiling in the benchmark above was hundreds per second, so most of the 817-versus-30,981 TPS gap should disappear.

What remains:

- The notifying commits are still serialised and still pay their WAL flush under the lock.
- On PostgreSQL 18 and earlier, each notifying commit still pays signalling cost proportional to the number of listeners in the database.
- pgmq adds row-lock waits on its throttle row.
- Consumers get wake-up latency of up to the debounce interval, or up to the poll fallback when a suppressed notification was the last one.

For an append-only event store, the evidence points the same way on every version up to 19. Never issue a `NOTIFY` per row or per append. Debounce per channel, such as per category or per stream group. Use constant payloads so in-transaction folding works. Keep a polling fallback for wake-ups the debouncer suppresses.
