# Which ordering of subscribing, reading the log and waiting removes the lost-wakeup race between a consumer's final empty read and its next wait for a notification?

## Question

A push-driven consumer reads the event log from its cursor until a read comes
back empty, then blocks waiting for a notification. If a producer commits an
event and sends its notification in the gap between that empty read and the
start of the wait, the consumer can sleep through the event until a safety-net
poll fires. In what order must the consumer subscribe, read and wait, and what
must it do with notifications that are already pending, for that window to
close?

## Findings

### The race is the classic lost wake-up

This is the lost wake-up problem from operating-system synchronisation. A
process checks a condition, finds it false, and goes to sleep. A waker makes
the condition true and signals between the check and the sleep, so the signal
reaches nobody. Luo Yigui's article on the Linux kernel describes the problem
on SMP systems and the kernel idiom that solves it. The sleeper first
publishes its intent to sleep by setting its task state, then checks the
condition, and only then calls the scheduler. A wake-up that lands between the
check and the call resets the task to runnable, so the call returns at once
instead of sleeping. The general lesson is that the "I am waiting" registration
must come before the check, never after it.

The classic literature gives three ways to close the window. Only two of them
suit a PostgreSQL consumer.

**1. Make check-and-wait atomic under a shared lock.** In Hoare's monitors, a
condition is tested and waited on inside the monitor. WAIT gives up the
monitor atomically as the process suspends. The signaller has to enter the
same monitor to change the state, so it cannot slip into the gap. Signals are
not remembered, though: a signal sent when no process is waiting is simply
lost. That is safe only because the lock rules out the gap. Buhr, Fortier and
Coffin's taxonomy of monitors sorts the variants by signalling semantics, and
the point holds for all of them: the condition variable keeps no memory, so the
mutual exclusion around check and wait is what makes it correct. PostgreSQL
has no lock that spans both the consumer's read and the producer's
commit-plus-notify, short of serialising every writer behind an advisory lock.
So this route does not carry over to an event store with many writers.

**2. Use a signal that is remembered until consumed.** Dijkstra's semaphores,
which structure the THE multiprogramming system, count V operations. A V
issued before the matching P is not lost, because the later P finds the count
already raised and goes straight through. PostgreSQL's LISTEN and NOTIFY behave
like this once a subscription is in place. A notification committed while the
session is listening is queued for that session until the client reads it. A
wait that starts after the notification arrived therefore returns at once.
The only real hazard is a notification committed before the subscription
exists, because it is never queued for that session.

**3. Wait on a value rather than on an occurrence.** Reed and Kanodia's
eventcounts replace "wait for the next signal" with `await(E, v)`, which
returns as soon as the counter `E` has reached `v`. A process reads the
counter, does its work, then awaits `read value + 1`. If the counter moves on
while the process is working, the await is already satisfied and returns at
once. The race disappears without mutual exclusion, and the authors note that
this also makes the mechanism easier to implement in distributed systems. For
an event store, the consumer's cursor and the log's committed high-water
position play the roles of `v` and `E`. Waiting on "head position greater than
cursor" is immune to ordering mistakes in a way that waiting on "a
notification arrived" is not.

### The ordering that closes the window

Chandy and Lamport's distributed-snapshot algorithm states the rule in its most
general form. A process records its own state and starts recording messages on
its incoming channels at the same instant. Every message is then reflected
either in the recorded state or in the recorded channel contents. If recording
starts after the state is captured, messages sent in between end up in
neither. If it starts before, a message can end up in both. For a consumer,
the read of the log is the state capture and the notification subscription is
the channel recording. That gives one correct sequence:

1. **Subscribe first.** Issue LISTEN on the notification connection and make
   sure it has taken effect before reading anything. LISTEN registers when its
   transaction commits, which in autocommit mode means when the command
   completes. If the catch-up read runs on a different connection, it has to
   start after the LISTEN has been acknowledged, so that the read's snapshot
   is later than the subscription.
2. **Clear pending hints, then read.** At the top of each cycle, drain any
   notifications already queued without blocking. Then read from the cursor
   until a read comes back empty, advancing the cursor as you go. Draining has
   to happen before the read, never after it. This is the same rule as the
   kernel's "set state before checking": a hint cleared after the read could be
   the only record of an event the read's snapshot missed.
3. **Wait with a timeout.** Block until a notification arrives or the
   safety-net interval runs out, then go back to step 2. Anything committed
   after the drain is still queued, so the wait returns at once even if it
   arrived during the read. Lampson and Redell's Mesa monitors are the
   precedent for the timeout. Mesa treats a notification as a hint, attaches
   timeouts to WAIT, and requires the waiter to re-check its condition in a
   loop after every wake-up, whatever caused it.

The two wrong orderings show why this one is needed:

- **Read, then subscribe, then wait.** An event committed between the read's
  snapshot and the LISTEN raises no notification for this session and is not
  in the read. The consumer sleeps until the safety-net poll.
- **Subscribe, read, then drain, then wait.** Draining after the read throws
  away exactly the hints the read could not see, which reopens the window the
  subscription had closed.

### Consequences of the ordering

- **Spurious wake-ups are the price, and they are harmless.** Subscribing
  before reading means some notifications refer to events the read has
  already returned. Chandy and Lamport's "in both" case shows up as an extra
  read that comes back empty. The consumer must treat every notification as a
  hint and not a work item, which is the Mesa discipline.
- **Every reconnect is a fresh subscription.** A LISTEN lasts only as long as
  its session. After a dropped connection the consumer must LISTEN again and
  then do a full catch-up read before it waits. Skipping the read leaves the
  events committed during the outage covered by nothing but the timeout.
- **Payloads can make the wait value-based.** If notifications carry the
  committed position, the consumer can skip a re-read when every pending
  payload is at or below its cursor, which brings it closer to the eventcount
  model. When positions come from a sequence assigned before commit, a payload
  below the cursor can mean a gap has just been filled, not that the event is
  stale. Using payloads to suppress reads therefore needs the transient-gap
  handling that is being researched separately.
- **The client library is part of the subscription.** The argument assumes
  notifications that reach the client stay buffered until the consumer drains
  them, including ones that arrive while the read query is running. If a
  driver only dispatches notifications to whoever is listening at that moment,
  the ordering has to be enforced at the driver layer as well.

None of these records covers PostgreSQL directly. The mapping above relies on
PostgreSQL's documented session-scoped, queue-until-read LISTEN semantics, and
that should be confirmed against the PostgreSQL documentation and the driver's
behaviour.
