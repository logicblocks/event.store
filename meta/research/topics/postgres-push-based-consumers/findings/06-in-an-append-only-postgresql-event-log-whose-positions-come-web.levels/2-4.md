# How can a PostgreSQL event-store consumer detect that its snapshot-xmin watermark is held back by a long-running, idle-in-transaction, or prepared transaction elsewhere in the cluster, and which server settings bound that delay?

## Question

Some event-store consumers deliver only events whose recorded transaction ID is
below `pg_snapshot_xmin(pg_current_snapshot())`. How can such a consumer tell
that this watermark is being held back by a long-running, idle-in-transaction,
or prepared transaction elsewhere in the cluster? And which PostgreSQL server
settings put an upper bound on how long it can be held back?

## Findings

### What lowers the watermark, and what does not

The PostgreSQL docs define a snapshot's `xmin` as the "lowest transaction ID
that was still active". The source code is more precise. `GetSnapshotData` in
`procarray.c` loops over every entry in the process array. It applies no
database filter. It skips any process that has no transaction ID assigned. It
also skips processes flagged as running lazy `VACUUM` or logical decoding. For
every other process, it lowers `xmin` to that process's *xid*, not to the
process's own `xmin` horizon. The calling backend's own xid also counts toward
`xmin`, although it is left out of the in-progress list. Prepared transactions
appear in the process array as dummy entries (`pid == 0`), so their xids count
too. This has five consequences for an event-store consumer.

1. **The watermark is cluster-wide.** Xids are "assigned sequentially to
   transactions from a global counter used by all databases within the
   PostgreSQL cluster". A writing transaction in an unrelated database on the
   same server holds back the event store's watermark exactly as an
   event-store writer would.
2. **Only transactions with an assigned xid count.** An xid is assigned "when a
   transaction first writes to the database". A long-running read-only
   transaction (a report, a dump, or a psycopg session that ran only `SELECT`
   and was never committed) sets `backend_xmin`, which holds back VACUUM. It
   has no `backend_xid`, though, so it does not hold back the watermark.
   Calling `pg_current_xact_id()` forces an xid to be assigned. The docs
   recommend `pg_current_xact_id_if_assigned()` "if the transaction might
   otherwise be read-only". So a consumer should read its watermark in a
   transaction that has not written anything and has not called
   `pg_current_xact_id()`.
3. **Prepared transactions always count.** `PrepareTransaction` calls
   `GetCurrentFullTransactionId()`, which assigns an xid if the transaction does
   not have one yet. After `PREPARE TRANSACTION`, the transaction is detached
   from its session and its state is stored on disk. It survives a crash.
   `pg_xact_status()` reports it as `in progress`. It holds the watermark
   until some session issues `COMMIT PREPARED` or `ROLLBACK PREPARED`.
4. **An `idle in transaction (aborted)` session does not hold the
   watermark.** When an error occurs inside a transaction block, PostgreSQL
   runs `AbortTransaction()` straight away and moves to a "failed xact,
   awaiting ROLLBACK" state. `AbortTransaction()` calls
   `ProcArrayEndTransaction`, which takes the xid out of the process array. The
   session still shows as idle-in-transaction until the client issues
   `ROLLBACK`, but its xid no longer lowers anyone's snapshot `xmin`.
5. **Replication slots and standbys hold back VACUUM, not the watermark.** A
   slot's `xmin` and `catalog_xmin` mean "VACUUM cannot remove tuples deleted
   by any later transaction". `hot_standby_feedback` likewise "can cause
   database bloat on the primary". The code applies these limits to the VACUUM
   horizons computed in `ComputeXidHorizons`. Snapshot `xmin` is built only from
   running xids, and none of these carries one.

So general-purpose "xmin horizon" checks flag more culprits than actually
matter here. For example, Cybertec's VACUUM troubleshooting queries rank
sessions by `greatest(age(backend_xmin), age(backend_xid))` and also list slots
and standby feedback. For the watermark, only two kinds of holder matter:

- sessions in `pg_stat_activity` with a non-null `backend_xid`
- rows in `pg_prepared_xacts`

### Detecting a stalled watermark

The defining symptom is a **watermark that stops advancing while committed,
visible events pile up at or above it**. These are rows the consumer can
already read but must not deliver yet. The consumer can track this cheaply on
every wake-up:

- Record the watermark and the wall-clock time it last moved.
- Optionally count visible rows whose transaction ID is at or above the
  watermark.
- Measure the lag in transactions, without assigning itself an xid, using
  `pg_snapshot_xmax(s)` minus `pg_snapshot_xmin(s)` (after casting `xid8` to a
  numeric type), or `age(pg_snapshot_xmin(s)::xid)`. `age()` "returns the
  number of transactions between the supplied transaction id and the current
  transaction counter".
- Read `pg_snapshot_xip(s)` to get the full list of in-progress top-level
  transactions.

Oskar Dudycz's description of this outbox technique notes only that "our
queries may be a bit delayed if our transactions last long". It does not
describe how to detect the delay, so the consumer has to build that monitoring
itself.

To **attribute** a stall, match the watermark xid against both holder
sources. `xid8` values "can be converted to xid by casting":

```sql
WITH w AS (SELECT pg_snapshot_xmin(pg_current_snapshot())::xid AS xmin)
SELECT 'session' AS holder, a.pid, a.datname, a.usename, a.backend_type,
       a.state, now() - a.xact_start AS open_for, age(a.backend_xid) AS xid_age
FROM pg_stat_activity a JOIN w ON a.backend_xid = w.xmin
UNION ALL
SELECT 'prepared', NULL, p.database, p.owner, NULL,
       'prepared', now() - p.prepared, age(p.transaction)
FROM pg_prepared_xacts p JOIN w ON p.transaction = w.xmin;
```

How to read the result:

- `state = 'idle in transaction'` means a client is holding a write transaction
  open.
- `active` means a long-running statement inside a writing transaction.
- A row only in `pg_prepared_xacts` means an orphaned two-phase commit. Its
  `database`, `owner` and `prepared` columns show where it came from and how
  old it is. Prepared transactions have no backend, so they never appear in
  `pg_stat_activity`.
- No match at all usually means the holder ended between the two reads. Check
  again before raising an alert.

`pg_locks` gives a second way in. It is "a global view of all locks in the
database cluster". Every transaction with a permanent xid holds an exclusive
lock on that xid until it ends. `pid` is null when a prepared transaction holds
the lock, and `virtualtransaction` joins to `pg_prepared_xacts` as `'-1/' ||
transaction`. A `RowExclusiveLock` on the event table also shows whether the
holder is an event-store writer or an unrelated workload.

That distinction is for diagnosis only. It does not make it safe to skip past
the holder. An xid is fixed at a transaction's first write anywhere, so a
transaction that wrote elsewhere first could still insert an event later
carrying its old, low xid. If the consumer had moved past that xid, it would
never see the event. This is an inference from the documented assignment rule;
no source states it.

**Privileges.** Ordinary roles "can only see all the information about their
own sessions". In rows about other sessions, "many columns will be null".
Superusers and roles with the built-in `pg_read_all_stats` privilege see
everything. In `pgstatfuncs.c`, the unprivileged branch still fills in
`backend_xid` and `backend_xmin`, but it nulls `state`, `query` (replaced by
`<insufficient privilege>`), `xact_start` and the other timing columns. An
unprivileged consumer can therefore see which pid, database and role holds the
watermark, but not that session's state or how long it has been open. To get
the full picture, grant `pg_read_all_stats` to the diagnostic role.

Reading `pg_prepared_xacts` briefly locks the transaction manager's internal
data structures, and the docs warn there "could be some impact on database
performance if this view is frequently accessed". Run attribution queries only
once a stall has been detected, not on every notification.

### Settings that bound the delay

Each kind of holder is bounded, or not, by a different setting:

| Holder | Setting that bounds it | Notes |
|---|---|---|
| Session idle inside an open transaction | `idle_in_transaction_session_timeout` | Ends the session after the configured idle time. Default `0` (off). |
| One long statement | `statement_timeout` | Applies to each statement separately. Default `0` (off). |
| Whole transaction, active or idle | `transaction_timeout` (PostgreSQL 17+) | Ends the session. Default `0` (off). Does not apply to prepared transactions. |
| Prepared transaction | None. Set `max_prepared_transactions = 0` to disable the feature | The default is `0`. Changing it requires a server restart. |
| Session whose client has died | TCP keepalive settings | Only bounds detection of the dead client over TCP. |
| Replication slot or standby feedback | Not applicable | Holds back VACUUM only, not the watermark. |

More detail on each setting:

- **`idle_in_transaction_session_timeout`** ends any session that has been idle
  "within an open transaction for longer than the specified amount of time".
  The docs give lock holding and blocked VACUUM as the reasons to use it. This
  matters for psycopg 3 clients. Psycopg starts a transaction on the first
  statement by default and warns that a long-running program "will remain
  *idle in transaction*" unless it commits or uses autocommit. That only
  affects the watermark once the session has written something.
- **`statement_timeout`** aborts any single statement that runs longer than the
  limit. Because it applies to each statement separately, a transaction made of
  many short statements with short gaps between them is not bounded by it.
- **`transaction_timeout`** was added in PostgreSQL 17. It ends any session
  "that spans longer than the specified amount of time in a transaction". It
  covers both explicit transactions and single-statement implicit ones. If it
  is shorter than or equal to `idle_in_transaction_session_timeout` or
  `statement_timeout`, "the longer timeout is ignored". It is the only setting
  that bounds the whole lifetime of an ordinary writing transaction. Its docs
  note: "Prepared transactions are not subject to this timeout."
- **Prepared transactions have no timeout.** The only server-side guarantee is
  `max_prepared_transactions = 0`, which "disables the prepared-transaction
  feature". It is the default and can only be changed at server start. The
  `PREPARE TRANSACTION` docs say to leave it at zero unless an external
  transaction manager closes prepared transactions promptly. Otherwise a
  forgotten one blocks VACUUM and can, in extreme cases, force a shutdown to
  prevent xid wraparound. A forgotten one also holds the event watermark
  indefinitely, including across restarts.
- **Dead clients.** An idle backend notices that its client has gone only at
  "the next interaction with the socket".
  `client_connection_check_interval` checks the connection only "while running
  queries". For a dead TCP client stuck idle in transaction, detection depends
  on `tcp_keepalives_idle`, `tcp_keepalives_interval`, `tcp_keepalives_count`
  and `tcp_user_timeout`, or the operating-system defaults. These settings are
  ignored on Unix-domain sockets. `idle_in_transaction_session_timeout` bounds
  this case anyway.
- **Settings that do not bound the watermark.** `hot_standby_feedback`, slot
  `xmin` and `max_slot_wal_keep_size` act on VACUUM or WAL retention, not on
  running xids. `old_snapshot_threshold` was removed in PostgreSQL 17. It only
  "allowed vacuum to remove rows that potentially could be still visible to
  running transactions" and never ended a running transaction.

**Scope of these bounds.** The docs advise against setting `statement_timeout`
or `transaction_timeout` in `postgresql.conf` "because it would affect all
sessions". The usual alternative is `ALTER ROLE ... SET` or
`ALTER DATABASE ... SET`. Those values apply only "when starting a fresh
database session", and a session can override user-settable parameters with
`SET`.

Because the watermark is cluster-wide, a bound only holds if it covers every
role that writes to *any* database on the cluster. That includes other
applications and administrators, not just the event store's own writers.

In practice, the worst-case delay is:

- the largest effective `transaction_timeout` among those writing roles, where
  every role is covered;
- otherwise, a looser combination of `statement_timeout` and
  `idle_in_transaction_session_timeout`;
- unbounded wherever a writing role has no timeout, or prepared transactions
  are enabled.

A useful operating rule is to alert when the watermark has stalled for longer
than the configured `transaction_timeout`. Under a correct configuration that
should never happen. When it does, it almost always points to a role the
timeouts do not cover, or to an orphaned prepared transaction.
