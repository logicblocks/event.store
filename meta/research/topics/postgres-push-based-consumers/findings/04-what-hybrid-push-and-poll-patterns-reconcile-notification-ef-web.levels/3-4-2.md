# How should an event store version its notification channel names and payload formats so that writers and consumers running different library versions can coexist during rolling upgrades?

## Question

During a rolling upgrade, some processes that append events and some that consume them run an older library version while others run a newer one. How should a PostgreSQL event store name its LISTEN/NOTIFY channels and shape its payloads, and how should it roll out changes to either, so that mixed-version fleets keep working?

## Findings

### Two separate things to version, and they fail differently

PostgreSQL delivers a notification only "to each client application that has previously executed `LISTEN channel` for the specified channel name". The payload is an opaque string that "must be shorter than 8000 bytes" by default. That leaves two separate things to version, and they fail in different ways:

- **The channel name decides whether a listener hears anything.** If writers and listeners disagree about it, nothing errors. Listeners on the old name just stop waking up.
- **The payload decides whether a listener understands what it hears.** A mismatch here is loud or quiet depending on the reader. Commanded EventStore shows the brittle case. Its `notify_events` trigger sends `stream_uuid,stream_id,first_version,last_version` as a comma-separated string on channel `{schema}.events`. `Notification.new/1` parses that string by splitting it from the right into exactly four parts, and it carries no version marker. So adding, removing or reordering a field would make older listeners misread it or crash with a match error.

The biggest factor in upgrade safety lies outside both of these. If a notification is only a wake-up hint over a durable log, and consumers also poll as a safety net, then a missed or unreadable notification costs latency, not correctness. Procrastinate's documentation says workers poll the database "in case they don't receive notifications from the LISTEN/NOTIFY mechanism". River shows a channel rename that relies on this. Its v2 migration's trigger sent `pg_notify('river_insert', json_build_object('queue', NEW.queue))`. Release 0.5.0 moved insert notifications into client code and prefixed every topic with `{schema_name}.`. Migration 004 dropped the `river_notify` trigger, and the changelog calls that migration "backward compatible with any River installation running the v3 migration".

The changelog describes no period in which both channels were active. From the channel names alone, it looks like old and new clients stop waking each other during the overlap, and periodic fetching covers the gap. A consumer that relies on push only, with no polling, would stall silently through the same change.

### How existing PostgreSQL libraries handle it

| Library | Channel naming | Payload | How versions are marked | What happens during a mixed-version window |
|---|---|---|---|---|
| Procrastinate 3.x | `procrastinate_queue_v1#<queue>`, `procrastinate_any_queue_v1` | JSON `{type, job_id}` with `type` of `job_inserted` or `abort_job_requested` | `_v1` suffix on the channel and trigger-function names | Pre-migration adds the v1 triggers and keeps the old trigger (old channels with no suffix, payload = task name). The post-migration drops the old trigger and functions. |
| Que 2.x | `que_listener_<pid>` (one channel per locker process) | JSON with `message_type: 'job_available'`, queue, priority, id, run_at | `job_schema_version` column on both jobs and lockers | The trigger notifies only lockers whose `job_schema_version` matches the job's. Que 1 and Que 2 workers run side by side until the Que 1 jobs have drained. |
| Graphile Worker | `jobs:insert`, plus a control channel `worker:migrate` | JSON `{count}`; `{migrationNumber, breaking}` | Migrations table with a `breaking` flag | When a breaking migration is announced, workers shut down gracefully with exit code 57. At startup they refuse to run against a newer breaking schema, and only warn about newer non-breaking ones. |
| Oban | `{prefix}.oban_{channel}` | JSON; above 512 bytes, gzip plus base64 with a `Z:` prefix | Marker inside the payload (a prefix) | The decoder accepts `Z:`-prefixed, `H4sI`-prefixed (base64 gzip) and plain JSON payloads. |
| River | `river_insert` (trigger) became `{schema}.`-prefixed topics sent by client code | JSON `{queue}` | None | Channel renamed at 0.5.0. Polling covers the gap. |
| Commanded EventStore | `{schema}.events` | Comma-separated values, parsed by position | None | No way to evolve the payload. |

Together these show two workable patterns:

1. **Version in the channel name.** Procrastinate puts the version in the name, so a listener only hears formats it understands.
2. **Version inside the payload.** Que, Procrastinate and Graphile use a self-describing JSON object with a type field, and Oban adds a format prefix. The reader dispatches on that marker.

They also show two ways to handle changes that cannot be made compatible:

- **Announce and stop.** Graphile records breaking migrations, announces them on a control channel, and old processes exit rather than carry on unsafely.
- **Route by version.** Que gives each worker a version, and the trigger only notifies workers that can handle the job.

### Recommended design for an event store

**1. Keep the payload small and advisory.** The less a payload carries, the less often it needs to change. Something like `{"v":1,"category":...,"position":...}` is enough. Consumers must always re-read the durable log from their checkpoint, never from the payload.

**2. Mark the payload version inside the payload, and read it tolerantly.** Use a JSON object with a discriminator field (`type` in Procrastinate, `message_type` in Que) or a format prefix (as Oban does). Only add fields. Readers should:

- ignore keys they do not know, following Fowler's Tolerant Reader advice to "only take the elements you need, ignore anything you don't";
- treat a payload they cannot parse, or a version they do not know, as an unfiltered wake-up rather than an error. Graphile's `tryParseJson` returns `null` instead of throwing.

With tolerant readers, adding an optional field is "full" compatible in Confluent's schema-evolution terms, so producers and consumers "can be upgraded independently". Removing a field, or changing what one means, is not.

**3. Version the channel name only for breaking changes, and add the version from day one.** A name like `{schema}_events_v1`, plus a category if you use per-category channels, means a later breaking change becomes a new channel instead of a reinterpretation of the old one.

Adding a schema prefix later, as River did, is itself a channel rename and needs the same handling. Keep in mind how PostgreSQL treats names:

- Identifiers keep at most 63 bytes, and LISTEN truncates longer names. `pg_notify` instead rejects names that are too long with "channel name too long". A long generated name can therefore end up different on the listening and notifying sides.
- Unquoted identifiers are folded to lower case, but `pg_notify`'s text argument is not. Use lower-case channel names and quote them the same way everywhere.

**4. Roll out breaking changes in three steps: expand, migrate, contract.** This follows Fowler's Parallel Change pattern: support old and new, move every client over, then remove the old. For channels and payloads, the expand step can take one of two forms:

- **Writers publish to both.** During the window, writers emit both the old and the new channel or format, as Procrastinate's pre-migration does by keeping the old trigger next to the new `_v1` ones. This is Confluent's "upgrade producers first" order.
  - Cost: each commit sends two notifications. PostgreSQL only merges duplicates with the same channel and payload within one transaction, so notifications on different channels are never merged.
- **Consumers listen to both.** Upgraded consumers LISTEN on both the old and new channels. psycopg's `Notify` object carries `channel`, so one dispatcher can choose a parser per channel. Writers switch over only after every consumer is upgraded. This matches Confluent's "upgrade all consumers before you start producing new events".

The contract step comes only after the last old-version process is gone. Procrastinate warns that keeping the service running requires stopping "at every version that provides migrations". A library should therefore support at least the current and previous notification formats in each release (N and N-1), and say so in its upgrade notes.

**5. Decide who sends the notification, because that decides what you version against.** When a trigger sends NOTIFY (Procrastinate, Que, Commanded, early River), the format follows the schema version. A migration switches every writer at once, whatever library version each process runs, so the question becomes whether running consumers can read the post-migration format. Pre and post migrations around a blue-green deploy handle that.

When library code sends NOTIFY (River from 0.5, Graphile's migrate notice), the format follows each writer's library version. A mixed fleet then sends mixed formats, so writers must publish to both channels or readers must accept several formats.

**6. Have a way out for changes that cannot be made compatible.** Store a protocol or schema version in the database and check it when a consumer starts. Announce breaking changes on a control channel so that out-of-date consumers stop loudly, as Graphile Worker's `worker:migrate` handling does. The alternative is to route by version, as Que's `job_schema_version` matching does. Either way, an old consumer fails visibly instead of waiting forever on a channel nobody writes to.
