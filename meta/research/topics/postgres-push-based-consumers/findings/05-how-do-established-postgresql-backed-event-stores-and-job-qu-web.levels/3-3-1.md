# How do cloud network paths and managed PostgreSQL services such as Amazon RDS, Aurora, Cloud SQL and Azure Database for PostgreSQL treat long-idle LISTEN connections during idle timeouts, maintenance and failover?

## Question

A consumer that waits for PostgreSQL `NOTIFY` wake-ups keeps one connection open, often for hours, with no traffic between notifications. How do the network components between a cloud workload and its database (NAT gateways, load balancers, stateful firewalls and connection tracking) treat such an idle connection? And how do the managed services (Amazon RDS for PostgreSQL, Aurora PostgreSQL, Google Cloud SQL for PostgreSQL and Azure Database for PostgreSQL flexible server) handle that connection during maintenance, failover and their pooling and serverless features?

## Findings

### Why a LISTEN connection is especially exposed

PostgreSQL ties LISTEN registrations to the session: "A session's listen registrations are automatically cleared when the session ends." Any drop, whether it comes from a middlebox timeout, maintenance or failover, removes the registrations. Notifications sent between the drop and a fresh `LISTEN` on a new session are never delivered to that consumer. Hot standby servers reject `LISTEN` and `NOTIFY` outright, although `UNLISTEN` is allowed. So a listener must always be connected to the current primary.

A waiting listener sends nothing. Data flows from server to client only when a notification is published, so in quiet periods the TCP flow is fully idle in both directions. The defaults do little to change this. libpq turns client keepalives on by default (`keepalives=1`), but `keepalives_idle`, `keepalives_interval` and `keepalives_count` default to "the system default". On Linux those defaults are `tcp_keepalive_time` 7200 s, `tcp_keepalive_intvl` 75 s and `tcp_keepalive_probes` 9, which is roughly two hours before the first probe and about 11 more minutes before the connection is killed. The PostgreSQL server-side parameters `tcp_keepalives_idle`, `tcp_keepalives_interval` and `tcp_keepalives_count` also default to 0, meaning the operating system's default. `tcp_user_timeout`, on both client and server, only limits how long "transmitted data may remain unacknowledged". A client that only waits has no unacknowledged data, so this setting alone cannot detect a dead idle listener. Without keepalives, Linux gives up on unacknowledged data only after `tcp_retries2` (default 15 retransmissions, about 13 to 30 minutes). `client_connection_check_interval` (default 0) applies only "while running queries", so it does nothing for an idle listener. `idle_session_timeout` defaults to 0 (disabled). If an operator enables it, it would end an idle listening session, and the PostgreSQL documentation warns against applying it to connections made through poolers or middleware.

As a result, every documented cloud middlebox idle timeout (4 to 20 minutes, listed below) is far shorter than the default keepalive start of about 2 hours. A listener on default settings can sit on a dead flow for over two hours before anything tells it so.

### Network-path idle timeouts

| Component | Default idle timeout | Behaviour on expiry (as documented) |
| --- | --- | --- |
| AWS NAT gateway | 350 s (fixed) | "the connection times out… a NAT gateway returns an RST packet to any resources behind the NAT gateway that attempt to continue the connection (it does not send a FIN packet)". Fix: send traffic or "enable TCP keepalive on the instance with a value less than 350 seconds". |
| AWS Network Load Balancer, TCP | 350 s, configurable 60 to 6000 s | Connection "no longer tracked"; later data gets a TCP RST. "Clients or targets can use TCP keepalive packets to restart the idle timeout." TLS listeners: fixed 350 s. |
| AWS EC2 ENI connection tracking (security groups) | 350 s on Nitro v6 instance types; 432,000 s (5 days) on others; range 60 to 432,000 s | AWS's networking blog describes expiry as a silent drop. The EC2 documentation says long-lived connections such as "database connection pools" should set `TcpEstablishedTimeout` and send keepalives "at intervals of less than 5 minutes". The AWS blog advises starting keepalives at 240 s or less when the timeout is 350 s. NAT gateways, NLBs, PrivateLink endpoints and Lambda Hyperplane ENIs are always tracked. |
| Google Cloud NGFW / VPC firewall connection tracking | 10 min | "connection tracking table entries are removed after a flow has been idle for 10 minutes"; tracking state stays active "if at least one packet is sent every 10 minutes". The docs do not say exactly what happens to packets after expiry. They tell applications to set `SO_KEEPALIVE` and give a Linux example of 60 s idle, 60 s interval, 5 probes. |
| Google Cloud NAT | 1200 s (20 min), TCP established; configurable | "the Cloud NAT mappings are removed"; increase only if you run connections "without a keepalive mechanism". |
| Azure Load Balancer (Standard) | 4 min; 4 to 100 min for load-balancing and inbound NAT rules, 4 to 120 min for outbound rules | Beyond the timeout the session "isn't guaranteed to be maintained"; an optional TCP reset can be enabled. |
| Azure NAT Gateway | 4 min; 4 to 120 min | The idle connection "is silently dropped"; an RST is sent "only when it detects traffic on the dropped connection flow", from either side. Microsoft advises against raising the timeout (SNAT exhaustion) and recommends TCP keepalives. Timer values are "subject to change". |

Not every path crosses every component. An app in the same VPC or VNet as its database usually avoids NAT, but stateful security-group or firewall tracking still applies. A NAT, load balancer or outbound-rule hop appears when the database is reached through a public endpoint, across networks, through a self-managed pooler behind an NLB, or from platforms whose egress is NATed.

These documents imply a direction problem for listeners (this is inference, not stated by any vendor). After a silent drop, the next notification is server-to-client data on a flow the middlebox no longer knows. Per the AWS and Azure NAT documentation, the RST goes to the side that sent the traffic, which is the database. The waiting client may never learn the flow has gone, because it sends nothing until its own keepalive fires, by default after about 2 hours. Notifications published in the meantime are lost to it. Client-side keepalives below the shortest timeout on the path solve both halves: the probes refresh the middlebox state, and if the flow has already gone, a probe triggers the RST or probe failure that tells the client. The strictest documented default is Azure's 4 minutes, then AWS's 350 s, Google Cloud's 10 minutes and Cloud NAT's 20 minutes. An idle threshold of about 60 to 120 s (Google's example uses 60 s) stays under all of them at default settings.

### Amazon RDS for PostgreSQL

- **Multi-AZ DB instance failover** typically takes 60 to 120 s. The DNS record moves to the standby, "As a result, you need to re-establish any existing connections". Failover triggers include OS patching "in an offline operation" during the maintenance window, an unhealthy or unreachable primary, instance modifications and reboot-with-failover.
- **Multi-AZ DB cluster** (the two-reader cluster) failover is "typically under 35 seconds". Its DNS also changes, so connections must again be re-established.
- **Maintenance.** OS updates on Multi-AZ are applied to the standby first, then a short failover follows that "typically lasts less than a minute". Engine version upgrades modify primary and standby "at the same time", causing downtime until the upgrade completes. Required OS or database patching takes a Single-AZ instance offline briefly.
- **Blue/Green switchover** "Drops connections to the DB instances in both environments". AWS asks clients to keep DNS cache TTL at or below 5 s, which is the RDS default. If RDS Proxy fronts the database, "existing connections to the proxy are dropped" when green is promoted.
- **RDS Proxy.** For PostgreSQL, "Listening on a notification channel" is a pinning condition. A pinned client keeps a dedicated database connection until the session ends, which defeats multiplexing. The proxy also closes client connections that are idle longer than `IdleClientTimeout` (default 1,800 s, i.e. 30 minutes) and enforces a fixed, non-configurable 24-hour maximum client connection life. A silent listener behind the proxy is therefore cut after 30 minutes by default and after 24 hours at the latest, unless it sends requests. AWS says the proxy preserves application connections during Aurora failover, but it does not document whether a pinned session's server-side state, including its LISTEN registrations, survives. That state lives on the old writer, so it should be treated as lost.

### Aurora PostgreSQL

- **Failover**: "service is typically restored in less than 60 seconds, and often less than 30 seconds". During the gap reads and writes fail with an exception. With no replicas, Aurora recreates the primary, which "typically takes less than 10 minutes". The cluster endpoint follows the writer, and DNS updates "typically take less than 30 seconds".
- **Fast-failover guidance**: AWS recommends very aggressive keepalives (`tcp_keepalives_idle = 1`, `tcp_keepalives_interval = 1`, `tcp_keepalives_count = 5`) so the application is notified "within five seconds when the database stops responding". It also recommends low DNS cache TTLs, connecting with both the writer and reader endpoints listed, and checking `SHOW transaction_read_only` after connecting, because a connection made during DNS propagation can land on a reader. For a listener this check matters: a hot standby rejects `LISTEN`, so a listener that reconnects to a stale DNS answer gets an error rather than a working subscription. AWS also publishes the AWS Advanced Python Wrapper, which supports psycopg. It caches cluster topology to bypass "the delays caused by DNS resolution", and its host-monitoring plugin aborts connections to unhealthy hosts.
- **Zero-downtime patching (ZDP)** for minor upgrades and patches tries to preserve client connections across an engine restart. AWS lists cases where "connections will be dropped for ZDP to complete", including long-running transactions, DDL, temporary tables or table locks, WITH HOLD cursors, TLS 1.1, and the line "All sessions are listening on notification channels." That wording is ambiguous, but it puts listening sessions on the list of things that disrupt connection preservation. ZDP is not used for reader upgrades or OS patches, and its throughput dip lasts "a few seconds or at most, approximately one minute".
- **Aurora Serverless v2 auto-pause** (minimum 0 ACUs): an instance does not pause while "any user-initiated connections are open… regardless of whether the connections aren't running any SQL statements". A permanently open LISTEN connection therefore stops the cluster from ever scaling to zero. An attached RDS Proxy has the same effect. Resume after a pause takes about 15 s, or 30 s or more after more than 24 hours paused.

### Google Cloud SQL for PostgreSQL

- **Maintenance**: "The database stops accepting new connections, and existing connections are dropped." Enterprise edition instances lose connectivity "for less than 30 seconds on average"; Enterprise Plus "typically lose connectivity for less than 1 second". Google recommends connection and query retry with exponential back-off. With a pooler, "connections between the pooler and the database are dropped during maintenance, the connections between the application and the pooler are preserved". For a listener this means the client's connection to the pooler can survive while the server-side session holding the LISTEN registration is gone. That is inference; the Cloud SQL docs do not discuss LISTEN under pooling during maintenance.
- **HA failover**: "any existing connections to the primary instance and read replicas are closed". Expect about 60 s of unavailability. Clients reconnect to the same IP address and connection string.
- **Managed Connection Pooling** defaults to transaction mode, in which `LISTEN` and session-level advisory locks are not supported. A session mode exists.
- Cloud SQL's connection-management guidance focuses on pool idle timeouts and maximum lifetimes (its samples default to 10-minute idle and 30-minute lifetime). Its Cloud Run page warns generically that "Connections to underlying databases may be dropped, either by the database server itself, or by the platform infrastructure". Neither page gives keepalive guidance; that comes from the Compute Engine and VPC documentation's 10-minute tracking limit.

### Azure Database for PostgreSQL flexible server

- **HA failover** (zone-redundant or same-zone) completes "within 60-120 seconds" with zero data loss. The service updates the DNS record so clients reconnect to the same hostname, and it can take longer than 120 s under heavy WAL replay. In a forced failover, application downtime runs until the DNS record points at the promoted standby.
- **Planned maintenance**: "Monthly maintenance is impactful and involves some downtime". It typically runs at least 30 days apart, but critical updates can arrive at shorter notice. On HA servers it is applied to the standby first, then the service "drains primary server connections and triggers a failover". Without HA, minor-version patching "restarts the database server". Either way, existing connections end.
- **Built-in PgBouncer** runs on port 6432 with `pgbouncer.pool_mode` defaulting to `transaction`. PgBouncer's own feature map marks LISTEN as "Never" supported in transaction pooling (it works in session pooling). PgBouncer restarts with the VM on failover, scaling or restart, "You then need to re-establish the existing connections."

### What this means for a LISTEN-based consumer

These implications are synthesised from the sources above rather than stated by any one of them:

1. **Disconnection is routine, not exceptional.** Every service documents connection-dropping events that recur during normal operation: monthly or quarterly maintenance, failovers of 30 to 120 s, Blue/Green switchovers, and proxy idle and lifetime limits. Because LISTEN state dies with the session, every reconnect must re-issue `LISTEN` and then run a catch-up read for anything committed while deaf.
2. **Keepalives below about 2 minutes are the minimum.** Set them explicitly through libpq connection parameters, so they apply to any libpq-based driver. This keeps the flow alive through AWS (350 s), Azure (4 min), Google Cloud (10 min) and Cloud NAT (20 min) defaults and bounds dead-peer detection. An application-level heartbeat on the listening connection, such as a trivial query, adds outbound data, which lets `tcp_user_timeout` bound detection and also exercises the server.
3. **Connect the listener directly to the primary.** Do not route it through transaction-mode poolers (RDS Proxy pins it; Cloud SQL managed pooling and Azure's built-in PgBouncer reject or break `LISTEN`). After reconnecting, confirm the server is writable, because standbys reject `LISTEN` and DNS can briefly point at a reader during failover.
4. **Cost and scale-to-zero.** One always-open listener per process keeps Aurora Serverless v2 from auto-pausing, and behind RDS Proxy each listener holds a pinned database connection. Both argue for one shared listener connection per process rather than one per consumer.
