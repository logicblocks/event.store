# How should one shared psycopg 3 listener connection per process fan out notifications to many in-process consumers, given that notifies() holds the connection lock and changing LISTEN registrations requires leaving the generator?

## Question

A process wants a single dedicated psycopg 3 connection that receives
PostgreSQL notifications and hands them to many in-process consumers. Two
psycopg facts get in the way. First, `Connection.notifies()` holds the
connection's lock for as long as it is iterating. Second, issuing `LISTEN` or
`UNLISTEN` (or any query) on that connection means leaving the generator
first. What loop structure, dispatch mechanism and subscription protocol make
this work safely and with low latency?

## Findings

### What the constraint actually is

The psycopg source settles the mechanics. Both `Connection.notifies()` and
`AsyncConnection.notifies()` wrap their whole body in `with self.lock` (or
`async with self.lock`). They yield each `Notify` from inside that critical
section. In `psycopg._acompat`, `Lock` is `threading.Lock` and `ALock` is
`asyncio.Lock`, and neither is reentrant. This has two consequences.

- **Your loop body runs while the lock is held.** If the loop body calls
  `conn.execute(...)` on the same connection, it blocks on a lock its own
  suspended generator owns. In sync code that is a self-deadlock; in async
  code it is an await that never completes. Python's documentation says plain
  `Lock` "handles this case the same as the previous, blocking until the lock
  can be acquired". Every unit of work done between yields also delays the
  next read from the socket.
- **Other threads or tasks wait until the generator returns.** psycopg
  connections are thread-safe, but "query execution and results retrieval on
  a connection is serialized". A `LISTEN` from another task therefore waits
  for the generator to finish. The maintainer's position on the issue tracker
  is blunt: "Yes, you are not supposed to run queries while you are
  listening". To issue a new `LISTEN`, stop the generator, run the statement,
  then call `notifies()` again. In a 2023 mailing-list post he also described
  this as making the generator "harder to use than expected". His example was
  that during the loop "the connection cannot be used to run queries (and some
  would be pretty useful, such as LISTEN/UNLISTEN to change the channels to
  listen at)".

psycopg 3.2 added two clean exits through `timeout` and `stop_after` (PR #673,
merged January 2024). In the source, both are checked only **after** a whole
received batch has been yielded. `stop_after` "might actually receive more
than this number if more than one notifications arrives in the same packet".
Leaving through `timeout` or `stop_after` therefore never cuts a batch short.
The `timeout` is a local wait on the socket. It sends nothing to the server,
so a short timeout costs only event-loop or thread wake-ups.

Re-entering the generator is safe from 3.2.4 onwards. A notification can
arrive while the generator is not running, for example during the `LISTEN`
statement itself or a heartbeat `SELECT 1`. Such notifications are now stored
in an internal `_notifies_backlog` deque and yielded first on the next call
(issue #962, fixed by PR #975: "Notifications are now captured whilst the
`notifies()` generator is not listening and returned first"). **Before 3.2.4,
notifications arriving during a query between generator runs were lost.**
That is exactly the gap a "leave, LISTEN, re-enter" loop creates. 3.2.10 fixed
a backlog memory leak (#1091) and changed the rule: if a handler is registered
through `add_notify_handler()`, the backlog is not filled. Mixing generator
and handlers on one connection is now deprecated and raises a
`RuntimeWarning`. So the listener connection should use the generator only,
with no handlers, on psycopg 3.2.10 or later.

### Why notify handlers are not the answer on a dedicated listener

`add_notify_handler()` looks like an event-emitter alternative. But the
psycopg docs say that with handlers "notifications will not be received
immediately, but only during a connection operation, such as a query". The
low-level generators call the handler only when draining input during `_fetch`
or `notifies`. On an idle listener connection, nothing triggers it.

In 2022 the maintainer suggested `select()` on the socket followed by
`select 1` to pump handlers, and admitted this is not ideal. The reporter
replied that a query per wake-up adds overhead that is unsuitable when
notifications must arrive quickly. Contrast asyncpg: its
`Connection.add_listener()` dispatches callbacks (coroutine functions allowed
since 0.24.0) from the protocol layer, so subscriptions can change without
pausing a receive loop. psycopg has no such idle-time push path, and that is
why the loop pattern below is needed.

### A hazard: closing the generator mid-batch (inferred from source)

The low-level `notifies(pgconn)` generator calls `consume_input()` and then
collects **every** pending notification into a local list. The high-level
generator yields that list one item at a time. During iteration the backlog is
set to `None`, and with no handlers registered the per-notification callback
does nothing.

Reading the code, this follows: if the generator is closed after yielding
only part of a batch, the rest of the list is discarded. That covers
`gen.close()`, `await gen.aclose()`, `break` out of a sync `for`, or
cancellation that finalises the async generator. The workaround posted on
issue #340 (`notify = await anext(conn.notifies(stop_after=1))` followed by
`aclose()`) has this exposure whenever several notifications arrive in one
read, such as several `NOTIFY` commands committed in one transaction.

This conclusion comes from reading the code, not from a reported bug. The safe
rule is to let the generator **end by itself** through `timeout` or
`stop_after` and never close it early. A related point: an abandoned async
generator keeps holding `self.lock` until it is finalised. Litestar's fallback
of cancelling the listener task, and any `break` out of an `async for` over
`notifies()`, therefore deserve care. `contextlib.aclosing` at least makes the
release prompt.

### The pattern that has emerged: a single-owner listener loop

Several independent Python libraries built on psycopg 3 use the same shape.

1. **One dedicated autocommit connection per process, owned by one task or
   thread.** oban-py's `PostgresNotifier` "maintains a dedicated connection
   for receiving notifications and dispatches them to registered callbacks".
   Procrastinate opens a standalone `autocommit=True` connection outside its
   pool for `listen_notify`. psycopg's docs say to keep autocommit on to
   receive notifications "in a timely manner".
2. **An alternating loop: apply pending registrations, then run the generator
   until it ends by itself.** oban-py's main loop calls `_process_pending()`,
   which runs queued `LISTEN` or `UNLISTEN` commands, and then
   `_process_notifications()`, which iterates
   `conn.notifies(timeout=notify_timeout)` with a default timeout of 0.1 s.
   Litestar's psycopg channels backend is equivalent but stop-start: on each
   subscribe it takes its own `asyncio.Lock`, sets a stop flag, and awaits the
   listener task. The task exits at its next 0.1 s `notifies(timeout=...)`
   boundary, and is cancelled after 5 s as a fallback. The backend then runs
   `LISTEN` and restarts the task. In both designs the timeout sets the worst
   case for how long a registration change or a shutdown waits. Since 3.2.4,
   notifications arriving while `LISTEN` executes go to the backlog and are
   not lost.
3. **Subscriptions go through a queue, not directly to the connection.**
   oban-py's `listen()` adds the channel to `_pending_listen`, records a
   `{token: callback}` entry in a per-channel subscription map and returns a
   token. With `wait=True` it awaits an `asyncio.Event` that `_process_pending`
   sets only **after** the `LISTEN` statement has run. `unlisten(token)`
   removes the callback and queues `UNLISTEN` only when the channel's last
   subscriber leaves. On reconnect, `_connect` re-queues every channel in
   `_subscriptions` for `LISTEN`. Only the owner task ever runs statements on
   the connection, apart from a heartbeat.
4. **Dispatch must not block, because it runs with the lock held.** Litestar
   calls `put_nowait` into one `asyncio.Queue` and filters against the
   subscribed set in `stream_events`. oban-py runs sync callbacks inline and
   starts async callbacks with `asyncio.create_task`, so a slow consumer
   cannot hold the lock. Procrastinate does `await on_notification(...)`
   inside the loop, but its worker callback only calls
   `self._new_job_event.set()`. The worker then waits on that event, a 5 s
   polling fallback, or its stop event.
5. **The heartbeat shares the connection.** Procrastinate runs `SELECT 1`
   after each 30 s `LISTEN_TIMEOUT` generator run and reconnects on
   `OperationalError`. oban-py sends `SELECT 1` every 30 s from a separate
   task. That task waits for the connection lock and gets it because
   `asyncio.Lock` is documented as fair: "the coroutine that proceeds will be
   the first coroutine that started waiting on the lock".

There is also a counter-example. pgqueuer's `PsycopgDriver.add_listener` runs
`LISTEN` and then starts **one watcher task per channel** on the same
connection, each iterating `notifies(timeout=1.0, stop_after=1)`. Its
docstring says this "releases the connection lock after each" batch. But
`notifies()` yields every notification on the connection whatever its channel,
and the quoted watcher calls its own callback without checking
`note.channel`. With two or more channels on one connection, a notification
would go to whichever watcher held the lock at the time (inferred from the
code). One loop per connection, demultiplexing by channel, avoids this.

### The sync (threaded) variant

Lock fairness is a real difference between the two flavours. For
`threading.Lock`, "which one of the waiting threads proceeds is not defined".
A listener thread that loops `notifies(timeout=T)` takes the lock back almost
at once, so a second thread calling `execute()` on that connection may be
starved. The sound sync design (a synthesis, not taken from a single source)
has these parts:

- The listener thread is the only user of the connection.
- Subscription changes reach it through a `queue.Queue` of commands, which it
  drains between generator runs.
- Each command carries a `threading.Event` that is set once its `LISTEN` has
  run.
- Fan-out uses `queue.Queue.put_nowait` or a `threading.Event` per consumer.
- The heartbeat is a statement the owner runs itself after a timed-out
  generator run, as Procrastinate does.

### Fitting this to an event-store consumer

For a library whose consumers treat a notification as a hint ("new events
exist; re-read from your checkpoint"), the sources suggest the following.
These points are synthesis.

- **Coalesce per consumer instead of queueing every notification.** A
  per-consumer `asyncio.Event` (or `threading.Event`) works like
  Procrastinate's `_new_job_event`. It caps memory, lets a slow consumer miss
  nothing that matters, and keeps dispatch O(1) under the lock. Keep a
  periodic fallback poll for missed wake-ups, as Procrastinate does every 5 s.
- **Prefer a static channel set where possible.** If channels are fixed at
  startup, for example one per log table or a small set of categories with the
  stream or category in the payload, the generator only has to exit for
  heartbeats and shutdown. All filtering then happens in process, and the
  leave-and-re-enter latency (bounded by the timeout) never affects a
  subscription.
- **Order subscribe before catch-up.** A consumer should register in process
  and **wait until the `LISTEN` is confirmed** before its initial catch-up
  read, as oban-py's `wait=True` event allows. If the read comes first, events
  committed between the read and the `LISTEN` produce no wake-up and wait
  until the fallback poll. Reconnect should re-`LISTEN` everything and then
  wake every consumer to catch up, because notifications sent while
  disconnected are gone.
- **Pin psycopg 3.2.10 or later, register no notify handlers on the listener
  connection, and never close the generator early.** Let `timeout` (short,
  such as 0.1 s, if registrations change often) end each run.
