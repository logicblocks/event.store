# How should a pull-based PostgreSQL consumer record its position atomically with its side effects, and how do the resulting delivery guarantees compare with Kafka offset commits and transactional stream processing?

## Question

A consumer that pulls events from a PostgreSQL event table by position has to
record how far it has got. How should it store that position so the position
and the consumer's side effects commit or fail together? And how do the
delivery guarantees that result compare with Kafka's consumer offset commits,
Kafka transactions, and checkpoint-based stream processors such as Apache
Flink and Google's MillWheel?

## Findings

### Effects, not delivery, are what can be made "exactly once"

The end-to-end argument of Saltzer, Reed and Clark lists duplicate message
suppression, delivery acknowledgement and crash recovery as functions that only
the endpoints can provide completely. Lower-layer mechanisms for them are
justified only as performance optimisations. Every system compared here
follows that pattern. The transport delivers at least once, and the "exactly
once" guarantee comes from the receiving end, which applies each event's
effect once. It does so by committing the effect together with a record that
the event was consumed, or by making the effect idempotent. Desai's synthesis
of event-driven reliability makes the same point for business-critical events:
transactional semantics alone are not enough, and must be combined with
idempotency and stage-aware retries.

For a pull-based PostgreSQL consumer, the question is therefore where the
"consumed" record lives relative to the side effect. There are four answers,
and their guarantees differ sharply.

### 1. Same-transaction checkpoint (effectively once, for effects inside PostgreSQL)

When the side effects are writes to the same PostgreSQL database (projections,
read models, aggregates, outbox rows), the consumer can read a batch, apply
it, and advance its position in one local transaction:

```sql
BEGIN;
SELECT position FROM subscriber_positions
  WHERE subscriber_id = $1 FOR UPDATE;          -- also fences rival instances
-- read events with position > saved position, apply projection writes ...
UPDATE subscriber_positions SET position = $last_applied
  WHERE subscriber_id = $1;
COMMIT;
```

Either the projection writes and the new position both become durable, or
neither does. After a crash the consumer resumes from the last committed
position, and none of the replayed events' effects had persisted. This is the
strongest guarantee available, and it costs the least. The event log, the
position table and the side-effect target share one transaction manager, so
no coordinator, two-phase commit or transaction-marker machinery is needed.
The row lock on the position (or an equivalent conditional
`UPDATE ... WHERE position = $expected`) also stops a stale or zombie consumer
instance from committing over a newer one. This is the PostgreSQL counterpart
of the fencing that Kafka and MillWheel build explicitly (see below).

MillWheel is the published system closest to this design. Akidau et al.
describe per-key exactly-once processing. Each incoming record carries a
unique ID. The framework checks the ID against stored deduplication data, runs
the user code, and then commits the state changes, the pending output records
("strong productions") and the record's ID in a single atomic write to the
backing store. Only after that write does it acknowledge the sender, which
retries until acknowledged. Delivery is at least once and effects are exactly
once. A PostgreSQL consumer that commits its position with its projection
writes does the same thing. Because positions in an ordered log are monotonic,
one position value replaces MillWheel's per-record ID set. MillWheel also
offers "weak productions", which skip the checkpoint before sending output and
accept duplicates when downstream processing is idempotent. That is the same
trade a PostgreSQL consumer makes when it moves external effects out of the
checkpoint transaction.

### 2. Separate checkpoint (at-least-once or at-most-once)

If the position is committed in a different transaction from the effects, the
order of the two commits decides the guarantee:

- **Effect first, then position:** at least once. A crash between the two
  commits replays the events, so effects must be idempotent, for example keyed
  on the event's ID or on (stream, position).
- **Position first, then effect:** at most once. A crash between the two
  commits silently loses the effect.

This is the window Andersson studies for Kafka. Failures between external side
effects and Kafka offset commits can lead to duplicate or lost outputs. The
thesis compares coordination strategies for getting exactly-once *effects*
when Kafka feeds external sinks, among them idempotent sink writes. A
PostgreSQL consumer whose effects leave the database (HTTP calls, email, other
brokers) is in exactly this position, and the same strategies apply.

### 3. Outbox (turning external effects into in-database effects)

When effects must reach external systems, the consumer can write an *intent*
row to an outbox table in the same transaction that advances its position.
This brings the external effect back inside case 1. A separate relay then
delivers outbox rows at least once, carrying a stable idempotency key that the
external system can deduplicate on. Pratinav and Mishra describe the outbox
pattern as the mechanism that guarantees atomicity between database state
changes and event emission. Here it is used on the consuming side rather than
the producing side. The trade-offs are an extra hop of latency and a relay
process to run. In exchange, the consumer's checkpoint never covers an
external call that may or may not have happened.

### 4. Inbox or deduplication table (when positions are not monotonic)

When work is not consumed strictly in position order, a single position value
cannot represent progress. Examples include competing consumers claiming rows
with `FOR UPDATE SKIP LOCKED`, or one handler fed from several sources. The
MillWheel-style alternative is a table of processed event IDs, inserted in the
same transaction as the effects, with a unique constraint turning duplicates
into no-ops. This costs one index insert per event and needs a retention
policy, but it keeps effectively-once effects without ordered consumption.

### Comparison with Kafka offset commits

- **Plain consumer offset commits.** A Kafka consumer commits offsets to the
  broker separately from whatever its handler did. Auto-commit or
  commit-before-processing gives at-most-once. Commit-after-processing gives
  at-least-once. This corresponds to case 2. Kafka has no transaction that
  spans the offset commit and an external database write, so the
  PostgreSQL same-transaction checkpoint is strictly stronger for effects
  inside the database. The usual Kafka workaround, storing offsets in the
  sink database alongside the outputs and seeking to them on restart, is case
  1 rebuilt by hand.
- **Kafka transactions (exactly-once semantics).** Wang et al. describe how
  Kafka Streams gets exactly-once results for read-process-write loops. Output
  records, state-store changelog records and consumer offsets are committed in
  one Kafka transaction, and downstream consumers reading with read-committed
  isolation see only committed output. Producer epochs fence zombie instances.
  The paper presents this as one point in a tunable trade-off between
  correctness, latency and cost. Commit frequency limits how soon downstream
  readers see results, because output only becomes visible at transaction
  commit. The guarantee stops at the edge of Kafka. Andersson notes that
  Kafka's transactional messaging and idempotent producers give exactly-once
  only within the Kafka ecosystem, and that extending it to databases, REST
  APIs and object storage remains a basic challenge. A PostgreSQL consumer
  with a same-transaction checkpoint gets the same kind of guarantee, bounded
  by the database instead of the broker. A single-node ACID transaction
  replaces Kafka's coordinator, transaction markers and epoch fencing.

### Comparison with transactional stream processing

- **Apache Flink.** Carbone et al. describe Flink's consistent distributed
  snapshots. Source read positions are snapshotted together with operator
  state, so after a failure the whole dataflow rolls back to the last
  completed snapshot and replays input from the recorded positions. The
  exactly-once guarantee covers Flink-managed state. Output to external
  systems needs idempotent writes, or a transactional commit tied to
  checkpoint completion, to extend it. Externally visible latency is then
  bounded by the checkpoint interval. The structure is the same as case 1
  (position and state committed together), but done asynchronously across a
  distributed job. A single PostgreSQL consumer gets the same result
  synchronously and more cheaply from one local transaction.
- **MillWheel.** Its exactly-once guarantee comes from per-key atomic
  checkpoints, as described under case 1, rather than global snapshots. It
  shows that effectively-once processing does not need a global barrier, only
  an atomic write that bundles the effect with the progress marker.

### Summary of guarantees

| Design | Where progress is recorded | Effects inside the store | External effects | Coordination needed |
|---|---|---|---|---|
| PostgreSQL same-transaction checkpoint | Position row, same transaction | Effectively once | At least once (idempotency or outbox needed) | Row lock or conditional update |
| PostgreSQL separate checkpoint, after effects | Position row, later transaction | At least once | At least once | None |
| PostgreSQL separate checkpoint, before effects | Position row, earlier transaction | At most once | At most once | None |
| Kafka consumer, commit after processing | Broker offsets topic | At least once | At least once | None |
| Kafka transactions (Streams EOS) | Offsets inside a Kafka transaction | Exactly once within Kafka | At least once | Transaction coordinator, producer epochs |
| Flink checkpoints | Source positions in a global snapshot | Exactly once for managed state | Needs idempotent or transactional sinks | Barrier-aligned snapshots |
| MillWheel | Record IDs and state in a per-key atomic write | Exactly once per key | Weak productions need idempotence | Per-key single writer |

### Caveats for a PostgreSQL event-table consumer

- **An atomic checkpoint only protects what was read.** If position-based
  reads can skip rows from transactions that commit out of sequence order, an
  atomic checkpoint makes the skip permanent. The recorded position must be a
  safe watermark, below any still-in-flight writer, not merely the highest
  position seen.
- **Keep external I/O out of the checkpoint transaction.** Holding the
  position row lock across network calls lengthens transactions and blocks
  failover. Use the outbox (case 3), or commit effects-then-position with
  idempotency keys (case 2).
- **Notifications stay hints.** With the position as the sole record of
  progress, a push trigger such as `LISTEN`/`NOTIFY` only decides *when* the
  consumer pulls next. A lost or coalesced notification costs latency, never
  correctness, as long as the consumer also polls on a fallback interval.
- **Evidence gap.** None of the sources retrieved for this note reports
  measurements of what a same-transaction checkpoint costs in PostgreSQL
  throughput or latency as batch size varies. The closest comparative
  evaluation is Andersson's, of exactly-once strategies for Kafka with
  external sinks.
