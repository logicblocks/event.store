# How do notification-driven and polling-based delivery scale as listeners, channels, subscriptions and event throughput grow — measured notification latency and throughput, commit-time contention, thundering-herd wake-ups and fan-out cost — and what does published research on push versus pull delivery and adaptive polling say about the latency-versus-load trade-off?

## Question

As a PostgreSQL-backed system adds listeners, channels, subscriptions and write throughput, how do LISTEN/NOTIFY-driven delivery and polling-based delivery behave? The question covers measured notification latency and throughput, contention at commit time, thundering-herd wake-ups and fan-out cost. It also asks what published research on push versus pull delivery, and on adaptive polling, says about trading latency against load.

## Findings

### Summary

The two mechanisms hit their limits along different axes, and both sets of limits are well characterised.

- **LISTEN/NOTIFY costs fall in two places.** The first is the write path. Every transaction that issues NOTIFY takes a cluster-wide lock and holds it until its commit is durable. The second is the number of listening backends. Before PostgreSQL 19, every NOTIFY signalled every listener in the database, whichever channel it was listening on.
- **Polling costs fall elsewhere.** It creates idle read load that grows with subscriptions multiplied by poll frequency. It also sets a latency floor equal to the poll interval.

Research on push versus pull covers web data dissemination, feed materialisation, operating-system network stacks, storage I/O and message brokers. It reaches the same conclusion in each field:

- Push gives the best latency and wastes the least work at low load.
- Pull handles overload better, gives natural backpressure and allows batching.
- The best-performing designs are hybrids that adapt to load. A push signal triggers a pull, and the system switches to steady polling when arrivals near saturation.

### How PostgreSQL's notification path spends its costs

The PostgreSQL documentation defines the contract that causes these costs:

- Notifications are delivered only when the sending transaction commits.
- Messages from different transactions are guaranteed to arrive in commit order.
- Identical channel-and-payload pairs within one transaction are folded into a single notification.
- All notifications pass through one shared queue, 8GB in a standard installation. When the queue is full, transactions that call NOTIFY fail at commit.
- A session that runs LISTEN and then stays in a long transaction stops the queue from being cleaned up. The docs advise keeping transactions short.

To guarantee commit order, `PreCommit_Notify` takes an `AccessExclusiveLock` on "object 0 of class 1262 of database 0". This is a single lock for the whole cluster, and it is held until the commit has been flushed to disk. Three sources confirm the hold duration: Recall.ai's incident write-up, DBOS's analysis, and the pgsql-hackers patch that tries to shorten it.

Before PostgreSQL 19, the backend had no central record of which listener cared about which channel. `SignalBackends()` therefore sent `PROCSIG_NOTIFY_INTERRUPT` (a `kill(pid, SIGUSR1)`) to every registered listener in the same database. Each woken backend then read the queue pages, threw away entries it did not want, and moved its read position forward.

PostgreSQL 13 had already removed several older costs:

- Signals go only to listeners in the same database.
- The notifier, not every listener, advances the queue tail, once every four pages.
- Duplicate detection within a transaction used a linear scan, which is O(N²). It now switches to a hash table once a transaction queues more than 16 distinct notifications.

### Commit-time contention as notifying writers grow

- **Production failure (Recall.ai, March 2025).** Recall.ai had tens of thousands of concurrent writers on an endpoint that issued NOTIFY. With `log_lock_waits` enabled, the logs showed one process holding the lock and 256 or more waiting for it, each for about 1 second. Database CPU, disk I/O and network traffic all fell as throughput collapsed. That pattern means work was being serialised, not that resources were exhausted. Recall.ai moved the logic into the application layer in under a day.
- **Benchmark ceiling and workaround (DBOS, July 2026).** DBOS fired a NOTIFY from a trigger on every stream write. Throughput peaked at 2.9K writes per second, with no visible CPU, memory or IOPS saturation. They then buffered notifications in memory and flushed them in periodic batch transactions, which reached 60K writes per second (20x) with Postgres CPU fully used. Delivery latency was 15–100 ms, and a low-frequency fallback poll recovered notifications lost in crashes. The trade-off is that notifications are no longer atomic with the write. This is acceptable only because the table remains the source of truth.
- **Developer measurements (Joel Jacobson, pgsql-hackers, July 2025).**
  - With 1,000 concurrent notifiers and one listener, keeping the commit-order lock gave 7,679 TPS. An experimental out-of-order variant without the lock gave 95,430 TPS, about 12.4x more.
  - A week earlier, on a single machine with local storage, the same change gave a larger gain for NOTIFY alone (about 160K to 340K TPS) than for combined LISTEN and NOTIFY (about 73K to 83K TPS).
  - Jacobson first concluded that the lock was not the bottleneck, then retracted that ("much more complex than I initially thought"). Which cost dominates depends on the workload.
- **Inference (not measured directly):** because the lock covers the commit flush, notifying transactions commit roughly one durable flush at a time. Storage with millisecond-scale fsync latency would therefore cap them in the low thousands per second, which matches DBOS's 2.9K/s figure.
- **The commit lock is still present in PostgreSQL 19.** The patch committed for PostgreSQL 19 deals with wake-ups only, and its design depends on the heavyweight lock to identify exactly which queue entries belong to the committing transaction.
  - A separate patch by Rishu Bagga writes notification payloads to WAL and keeps the lock only briefly. It measured about 30K TPS rising to 60–70K TPS with 100 clients.
  - Reviewers raised open correctness questions about it, such as whether listeners could see a notification before they can see the transaction's data.
  - At the January 2026 commitfest, the last one for PostgreSQL 19, the patch was listed as "Needs review" and flagged as needing a rebase. It is not in PostgreSQL 19.
  - Recall.ai's article has an update saying the bottleneck was eliminated in core and crediting Jacobson. That update is best read as referring to the wake-up work.
- **Documentation proposal.** Nikolay Samokhvalov proposed documentation warnings about the global lock (which affects every database in the cluster), duplicate checking, `log_lock_waits` diagnosis and logical decoding as an alternative. The proposal was not committed. Bruce Momjian pointed to the PostgreSQL 19 wake-up improvement in reply.

### Listener count, channel count and thundering-herd wake-ups

Jacobson's "ping-pong" benchmark has two connections notifying each other while extra idle listeners sit on unrelated channels. On the master branch, round trips per second fell steeply as idle listeners were added:

| Idle listeners | Round trips per second (master) |
|---|---|
| 0 | 9,126 |
| 10 | 6,233 |
| 100 | 2,020 |
| 1,000 | 238 |

The cause was one `kill()` syscall, plus the wake-up and queue scan that follow, per listener per NOTIFY.

A later run on an Apple M3 Max compared master with the patched build:

| Idle listeners | Master TPS | Master max latency | Patched TPS | Patched max latency |
|---|---|---|---|---|
| 0 | 32,123.7 | 893 µs | 31,832.6 | about 1 ms |
| 1,000 | 202.5 | 6,212 µs | 25,720.6 | about 1 ms |

At 1,000 idle listeners the patched build had about 127x the throughput and about 6x lower worst-case latency.

The patch was committed on 2026-01-15 for PostgreSQL 19. It adds two things:

- A shared hash map from (database OID, channel) to the backends listening on that channel, so only interested backends are signalled.
- "Direct advance": an uninterested listener sitting at the old queue head has its read pointer moved past the new entries without being woken.

The commit message claims "integer multiples" more throughput and lower latency when many listeners exist but few care about a given message. It reports no improvement, and no measurable loss, when every listener reads every message. The PostgreSQL 19 release notes list the change ("previously most backends were woken by NOTIFY"). The release was at Beta 4 on 24 September 2026.

**Channels per listener.** Heikki Linnakangas reviewed an intermediate version of the patch with listeners subscribed to 10,000 extra channels. That version cut the notify rate from 3,296/s to 1,274/s, because each listener's linear-list check of its channels ran while holding the queue's SLRU lock. On master, 67.6% of deliveries landed in the 0.1–1 ms latency bucket. With the regressing version, 99.7% landed in the 1–10 ms bucket. His fix was to move the check outside the lock, and he suggested replacing the list with a hash table. Two points follow:

- A listener's channel count is a cost dimension in its own right.
- On an unloaded master, a typical delivery takes well under a millisecond.

**What remains after PostgreSQL 19 (inference from the commit message).** Fan-out to listeners that are interested still costs one wake-up and one queue read per listener per notification. If N consumers listen on the same channel, a NOTIFY still wakes all N, even when only one of them can claim the work. This is the classic thundering herd, and PostgreSQL 19 does not remove it.

### Fan-out at the application tier

Production libraries make the number of database listeners independent of the number of subscriptions:

- **Brandur Leach's "notifier" pattern (2024).** One connection per process holds every LISTEN and fans notifications out in-process. It uses buffered channels with non-blocking sends, deliberately dropping notifications for slow subscribers so the notifier never blocks. Everything else can use PgBouncer in transaction-pooling mode.
- **Graphile Worker.** Each process LISTENs and, on each event, asks one idle worker to fetch jobs. If no worker is idle, it drops the event, because busy workers fetch the next job when they finish. This avoids the herd entirely.
  - With prefetching into a local queue and batched completion writes, Graphile Worker reports about 183,000 jobs per second executed, with 4.16 ms average (13.84 ms maximum) latency from enqueue to start, on an i9-14900K.
  - Without batching, the figure is about 15,600 jobs per second. Batching cuts queries per second and WAL churn.
  - Its fallback poll defaults to 2 seconds. The docs say 30–60 seconds is "probably fine" when polling causes performance problems.

The listener count that pre-19 PostgreSQL charges for then grows with the number of processes, not the number of subscriptions.

### Polling: idle load, latency floor and adaptive forms

**Cost of fixed-interval polling (simple arithmetic).** A fixed-interval poller sends 1/interval queries per subscription whether or not anything has changed. Its mean delay is about half the interval plus query time, and its worst case is the full interval.

Production systems tune or adapt around this:

- **Solid Queue (Rails).** Polls with `FOR UPDATE SKIP LOCKED`, every 0.1 s for workers and 1 s for dispatchers by default. It recommends running in a separate database.
- **Akka Persistence R2DBC `eventsBySlices`.** This is an event-sourcing projection query.
  - It waits the refresh interval (3 s by default) only when the last query returned nothing or at most 10% of its buffer. Otherwise it queries again immediately, so it runs at full speed while there is a backlog.
  - For latency below a few hundred milliseconds, the docs recommend not shortening the interval. Instead they recommend "publish-events", which pushes events across the cluster to running queries at the cost of more CPU and network. Because published events are not guaranteed to arrive, polling continues at a lower rate.
  - A dynamic mode turns publishing off when the exponentially weighted throughput goes above a threshold (default 400).
  - Backtracking queries look back over a 2-minute window to catch events that became visible out of order.
- **pgmq `read_with_poll`.** Moves the long poll into the database. It checks every 100 ms for up to 5 s by default, at the cost of holding a connection for the whole wait.
- **Amazon SQS.** Recommends long polling (waits of up to 20 s) to cut empty and falsely empty receives, each of which is a billed request.
- **Kafka.** Its design notes that naive pull busy-waits and fixes this with blocking "long poll" fetch requests.

### What published research says about push vs pull and adaptive polling

**Web data dissemination: Bhide, Deolasee, Katkar, Panchbudhe, Ramamritham and Shenoy, "Adaptive Push-Pull" (WWW10 2001; IEEE Transactions on Computers 2002).**
- Push keeps clients fully coherent with low message overhead, because only changes of interest are sent. It costs per-client server state and connections, and loses that state when the server fails.
- Pull is stateless and resilient but needs two messages per poll. It achieved only 70–80% fidelity under stringent coherency requirements, even with adaptive time-to-refresh.
- Their PaP hybrid (pull primarily, push what the pull would miss) reached 98–100% fidelity.
- Their PoP hybrid assigns each client to push or pull according to server resources, and degrades gracefully instead of failing abruptly.

**Feed materialisation: Silberstein, Terrace, Cooper and Ramakrishnan, "Feeding Frenzy" (SIGMOD 2010).**
- The lowest system load comes from deciding push or pull separately for each producer–consumer pair, based on the ratio of the producer's event rate to the consumer's read rate.
- Events from high-rate producers are pulled at read time. Events from low-rate producers are pushed, meaning materialised, in advance.

**Broadcast dissemination: Acharya, Franklin and Zdonik, "Balancing Push and Pull for Data Broadcast" (SIGMOD 1997), via a secondary summary.** A pull back-channel improves on pure broadcast push, but it can saturate the server as load grows. The paper proposes techniques to delay that point.

**RSS feeds: Liu, Ramasubramanian and Sirer (IMC 2005).** In a 45-day trace and a crawl of about 100,000 feeds:
- 58% of automated clients kept the default hourly poll.
- Clients polled independently, "imposing a high load on the servers of popular feeds".
- Fetching only the changes would save about 93% of bandwidth.

The authors recommend that publishers state poll rates, and point to asynchronous update notification as the direction to take.

**Network stacks: Mogul and Ramakrishnan, "Eliminating Receive Livelock in an Interrupt-Driven Kernel" (USENIX 1996; ACM TOCS 1997).**
- Interrupt-driven systems "provide low overhead and good latency at low offered load, but degrade significantly at higher arrival rates".
- An unmodified kernel livelocked at about 6,000 packets per second.
- Their fix is a hybrid: an interrupt only starts polling, polling handles bounded batches (quotas of 10–20 packets), and interrupts are re-enabled only when polling has drained the work. In their words: "interrupts to avoid latency" at low load, "polling to ensure progress and fairness" at high load.

**Linux NAPI.** Linux's NAPI subsystem builds this hybrid into the kernel:
- Interrupts stay masked while polling.
- `napi_defer_hard_irqs` counts the consecutive empty polls allowed before falling back to interrupts.
- The docs describe busy polling as trading "CPU cycles for lower latency".

**Storage I/O: Yang, Minturn and Hady, "When Poll Is Better than Interrupt" (FAST 2012).** With ultra-low-latency devices, spinning on completion beats interrupts. Polling wins when the expected wait is very short.

**Interrupt coalescing: Tai, Smolyar, Wei and Tsafrir, "Calibrated Interrupts" (OSDI 2021).**
- They frame the choice as firing an interrupt immediately for latency versus delaying it to spread its cost over more completions.
- Adaptive coalescing heuristics can behave badly without knowing which requests are latency-sensitive.
- Marking latency-sensitive requests gave up to 35% more throughput, 30% less CPU and 37% lower latency.

The PostgreSQL parallel is batching NOTIFY, as DBOS does, versus notifying on every commit.

**Message brokers: Kafka's design rationale.**
- Push "has difficulty dealing with diverse consumers", because the consumer "tends to be overwhelmed when its rate of consumption falls below the rate of production".
- Pull lets a consumer "fall behind and catch up", and gives "optimal batching without introducing unnecessary latency".
- The weakness of naive pull, busy-waiting, is fixed with long polls.

**Standards: IETF RFC 6202 on HTTP long polling.**
- Under load, long polling "has a natural tendency to gracefully degrade in performance at a cost of message latency", delivering queued messages in batches.
- Its costs are holding a connection and request per client, and a maximum latency of three network transits.

**Common conclusions.** Together, these sources make three points:
1. Push minimises latency and wasted work when events are sparse, but it costs per-subscriber state and behaves worst under overload.
2. Pull is stateless, sets its own pace and batches well under load, but wastes queries and adds latency when traffic is low.
3. The most efficient designs adapt to load. A push signal triggers pull-based draining. The push-or-pull choice is made per producer–consumer pair based on relative rates. Polling takes over, or pushes stop, while there is a backlog. Push resumes only after several consecutive empty polls.

### Implications for replacing fixed-interval polling in a psycopg 3 event store

The following is synthesis from the evidence above, not a measured result:

- **Use a notification only as a wake-up hint.** The consumer re-reads the events table from its last position. Keep a slow fallback poll, as DBOS, Graphile Worker and Akka all do, because notifications can be lost and the PostgreSQL 19 delivery path is best-effort from the consumer's point of view.
- **Hold one listening connection per process** and fan out in-process. Wake one consumer per subscription group, not every consumer. This avoids both the pre-19 per-listener signalling cost and the same-channel herd that PostgreSQL 19 keeps.
- **Fold notifications.** A channel per stream or category with a constant or position-only payload lets PostgreSQL's per-transaction de-duplication fold repeats. Consumers drain in batches, re-query at once while batches come back full, and back off when empty.
- **Account for the commit lock.** On every release up to and including PostgreSQL 19, NOTIFY inside a write transaction serialises all notifying commits across the cluster. Under high concurrent write throughput, either send NOTIFY from a separate batched transaction, giving up atomicity with the write (DBOS's approach), or leave high-rate streams to polling. This is the per-pair rate rule from Feeding Frenzy and the load-dependent switch from NAPI and Akka.
