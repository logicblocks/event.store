# Which adaptive polling policies, such as immediate re-query on a full batch, exponential backoff with jitter when empty, or ignoring notifications under sustained backlog, best bound latency and idle load across hundreds of subscriptions?

## Question

Which adaptive polling policies best bound end-to-end latency and idle database load when hundreds of subscriptions consume a PostgreSQL event table? The candidates are re-querying immediately after a full batch, exponential backoff with jitter when a query comes back empty, and ignoring notifications while a subscription is already behind.

## Findings

### Summary

No source found here publishes a measured, side-by-side comparison of these policies for hundreds of database-backed subscriptions. Graphile Worker's maintainers say outright that they "don't know the best value" for their own notification-suppression threshold. Even so, mature PostgreSQL-backed consumers (Akka Persistence R2DBC, Marten or JasperFx.Events, River, Graphile Worker, Oban, Solid Queue, Eventide, GoodJob and Elixir EventStore) have arrived at the same composite policy. It mirrors the interrupt-or-poll hybrid from operating-systems research (Mogul and Ramakrishnan, and Linux NAPI). The policy has four parts, and each bounds a different term.

1. **Drain while full.** Re-query immediately whenever the last batch was full or nearly full. During a backlog, latency then depends on processing throughput, not on a polling interval.
2. **Wait on a notification when idle, with a bounded timeout.** The timeout is a capped interval with jitter. The notification gives low latency. The cap limits the worst case when a notification is missed, and also sets the idle query rate.
3. **Treat notifications as edge-triggered hints, and suppress or coalesce them under load.** Use a minimum gap between fetches (a cooldown), a refetch delay, or a throughput-based switch. Notifications cannot then multiply the query rate.
4. **Share the "is there anything new?" check across subscriptions.** Use one head-position watcher or one listener and reader per process, not one poller per subscription. This is the only part that removes the dependence of idle load on the number of subscriptions N.

### 1. Immediate re-query on a full batch

Several systems use the size of the last result to decide how long to wait before the next query:

- **Akka Persistence R2DBC** has a three-band rule for live `eventsBySlices` queries. When the previous query returned at least 90% of `buffer-size` (default 1000), "the next query will be emitted immediately". When it returned nothing or no more than 10%, the next query waits the full `refresh-interval` (default 3 s). Between those two bands it waits half the interval.
- **Solid Queue's dispatcher** returns a delay of `batch.zero? ? polling_interval : 0.seconds`. It re-polls at once after any non-empty batch (batches default to 500) and otherwise waits `polling_interval`, which defaults to 1 s for dispatchers and 0.1 s for workers.
- **Eventide's** poll loop sleeps only when its block returns an empty result. Otherwise it breaks out and returns immediately. The interval is a cycle period: it sleeps `interval_milliseconds - elapsed_milliseconds`. The consumer subscription's default interval is 100 ms, which can be overridden with `POLL_INTERVAL_MILLISECONDS`.
- **Marten's high-water agent** (now in JasperFx.Events) uses `FastPollingTime` (default 250 ms) when the high-water mark has changed and `SlowPollingTime` (default 1 s) when it is caught up.
- **River**: when a fetch returns the maximum number of jobs requested, the producer sets `fetchWhenSlotsAreAvailable`. The code comment says a full result is "implying there may be more in the queue". The next fetch then fires as soon as a worker slot frees up.

The important constraint is **back-pressure**. Immediate re-query is only safe if it is limited by the consumer's capacity:

- River limits each fetch to `MaxWorkers` minus the number of active jobs, and skips the fetch entirely when no slots are free.
- Solid Queue's worker returns `polling_interval` while its pool is idle. When the pool is busy it returns 10 minutes and relies on an `on_idle` wake-up instead.
- Elixir EventStore stops sending a subscriber events until it has acknowledged earlier ones, up to `buffer_size` in flight. On overflow it switches to a catch-up mode that reads from storage.

For an event-store subscription, "re-query immediately" should mean re-querying as soon as the handler has capacity, not in a tight loop.

### 2. Backoff with jitter when empty

Marc Brooker's AWS analysis compared capped exponential backoff with and without jitter for contending clients. Without jitter, backoff still leaves "clusters of calls". With jitter, calls spread into an approximately constant rate. "Full Jitter", `sleep = random(0, min(cap, base * 2 ** attempt))`, gave the best balance of total work and completion time. Equal Jitter needed similar work but took much longer to complete, and Decorrelated Jitter was close to Full Jitter.

That study modelled contention during retries, not steady idle polling. The lesson that carries over to hundreds of subscriptions is to **de-synchronise** them, so that pollers started together (for example, after a deploy) do not query in lock-step. Some systems add jitter while keeping the mean interval fixed, which keeps load predictable:

- Oban's `dispatch_cooldown` is "the average number of milliseconds" between fetches, randomised between roughly 0 and 2x the setting (default 5 ms, minimum 1 ms).
- Graphile Worker's `refetchDelay.durationMs` is likewise a wait "on average".

Unlike Full Jitter, mean-preserving jitter does not halve the mean interval, and therefore does not double the idle query rate. This is an inference from the formulas, not a measured result.

Whether to back off exponentially or step between two fixed intervals depends on what the idle interval is for:

- **Polling is the only signal.** The cap sets both the worst-case latency and the idle rate. Without a shared check, the idle rate is about N divided by the mean interval. For example, 300 subscriptions polling every 1 s issue about 300 queries per second while idle. Backing off to a 30 s cap cuts that to about 10 queries per second, but makes worst-case latency about 30 s.
- **Notifications are the primary signal.** The timer only needs to cover a missed notification, so it can be long. River's `FetchPollInterval` (default 1 s) is "a fallback". GoodJob's production `poll_interval` of 10 s exists "in case of a LISTEN/NOTIFY blip". Marten uses a simple two-step fast and slow scheme rather than an exponential ramp.

In psycopg 3, the idle wait can be the notification wait itself. Since version 3.2, `Connection.notifies(timeout=..., stop_after=...)` blocks until a notification arrives or the timeout expires. That gives the long-poll behaviour Amazon SQS documents for `ReceiveMessage` wait times: fewer empty responses, with results returned as soon as messages are available. A notification therefore cuts the jittered sleep short, and the timeout is the fallback poll. psycopg warns that the generator and `add_notify_handler` should not both be used on one connection.

### 3. Ignoring notifications under backlog or high throughput

The idea of switching notifications off during heavy load comes from interrupt-driven kernels:

- **Mogul and Ramakrishnan** (USENIX 1996) avoided receive livelock by "using interrupts only to initiate polling". They disabled input while work was pending and re-enabled interrupts "when no work is pending, to avoid polling overhead and to keep latency low".
- **Linux NAPI** follows the same pattern. Drivers keep interrupts masked while polling, and unmask them only after `napi_complete_done()` once a poll does less work than its budget. `napi_defer_hard_irqs` sets how many consecutive empty polls happen before interrupts are re-armed, trading CPU for latency.

Mapped to a subscription: a notification moves an idle subscription into "draining" mode. While batches come back full, further notifications are redundant and can be reduced to a dirty flag. The subscription goes back to waiting on notifications only after a short or empty batch. Optionally it can wait for a few consecutive empty polls first, as `napi_defer_hard_irqs` does, which avoids repeatedly switching between modes.

The PostgreSQL-backed systems implement versions of this:

- **River**: insert notifications call a fetch limiter, so fetches happen "*at most*" once per `FetchCooldown` (default 100 ms) however many notifications arrive.
- **Graphile Worker**: when a fetch returns fewer jobs than `refetchDelay.threshold`, the pool waits `durationMs` and "(mostly) ignore[s] 'new job' notifications". It abandons the delay only after a random number of notifications, up to `maxAbortThreshold` (default 5 × `localQueue.size`). The randomness exists because "different workers will abort refetch delay at different times", which helps avoid the thundering herd and cuts latency when every worker is delayed. The idle load becomes roughly `(1000/durationMs) * INSTANCE_COUNT` queries per second, independent of how many notifications arrive.
- **Akka Persistence R2DBC**: events are published inside the cluster for low latency, and this fast path is switched off automatically when the exponentially weighted moving average of throughput exceeds `throughput-threshold` (default 400 events per second). Polling continues regardless, because published delivery is not guaranteed.
- **Oban**: documents that its insert-trigger notifications become a bottleneck at thousands of inserts per second, and that they can be disabled safely.

PostgreSQL also coalesces notifications to some extent. Repeated `NOTIFY` calls on the same channel with identical payloads in one transaction are delivered once, but distinct payloads are always delivered separately. So a payload that carries a sequence number prevents coalescing, while a constant or empty "something changed" payload allows it. "Ignoring" should still mean reading notifications off the connection and discarding them. The notification queue is 8 GB by default, a long-running transaction in a listening session blocks its cleanup, and if the queue fills, transactions calling `NOTIFY` fail at commit.

### 4. Bounding load across hundreds of subscriptions

Job queues are competing consumers. Graphile notes that each new job can make every pool query for it, "multiplying up the load". Event-store subscriptions are fan-out instead: every subscription that wakes genuinely has work. The risk is therefore not wasted queries but N reads per burst of events, plus N idle polls per interval. Two designs remove N from the idle term:

- **A single head watcher.** Marten and JasperFx.Events run one high-water agent per database. It polls the safe sequence mark (250 ms when active, 1 s when caught up) and publishes it to every projection shard through a tracker. The shards do not each poll. The agent also handles gaps from uncommitted sequence reservations: it holds back, then skips gaps older than `StaleSequenceThreshold` (default 3 s).
- **A single listener and reader.** Elixir EventStore uses "a single process" per node to listen for notifications. It "fetches the event data and broadcasts to all interested subscriptions". A subscription that falls behind its buffer switches to reading from storage until it catches up.

With either design, idle load is one cheap query per watcher interval, whatever the value of N. Peak load from notifications is limited by the cooldown on the shared watcher, not by N divided by the cooldown.

### Synthesis for an event-store consumer library

This policy is assembled from the sources above, not taken from any single measured study.

- Run one listening connection and one head watcher per process. The watcher waits on `notifies(timeout=T)`, where T is a capped interval with mean-preserving jitter: about 1 s when notifications are trusted, longer if the fallback can tolerate it. A notification triggers a head check that is throttled by a cooldown, in the range River and Oban use (milliseconds to about 100 ms).
- Wake only the subscriptions whose position is behind the new head.
- Each woken subscription drains: it re-queries immediately while batches are at least about 90% full, as Akka does, within its handler's capacity. After a short batch it waits a brief interval, and after an empty batch it goes back to sleep until the watcher wakes it.
- While any subscription is draining, extra notifications only set a flag.
- Latency is then bounded by:
  - notification delivery plus cooldown plus query time, when idle;
  - backlog divided by throughput, when behind;
  - T, when a notification is missed.
- Idle load is about 1/T queries per second for the whole process, rather than N/T.
