# How long can idle-in-transaction or long-running sessions elsewhere in a PostgreSQL cluster hold back an event reader filtered by pg_snapshot_xmin, and which timeouts or monitoring bound that delay in practice?

## Question

An event reader that only returns rows with `transaction_id < pg_snapshot_xmin(pg_current_snapshot())` never skips events committed out of order. But any open transaction elsewhere in the cluster can hold it back. How long can idle-in-transaction or long-running sessions delay it, and which server settings, timeouts and monitoring limit that delay in practice?

## Findings

### Which sessions actually hold back the filter

Practitioner write-ups of this filter, including Oskar Dudycz's outbox article and the Emmett event store's batch reader, say only that "queries may be a bit delayed if our transactions last long". The source code is more precise, and the precise rule matters operationally.

- **Only sessions holding a transaction ID (XID) count.** In `GetSnapshotData` (`procarray.c`), the snapshot's `xmin` starts at `xmax`. The function then lowers it only from the **XIDs** of other processes. It skips any backend with no XID assigned, and it never reads other backends' `xmin` horizons. The docs define `xmin` the same way: "Lowest transaction ID that was still active", counting top-level XIDs only.
- **An XID is assigned at a transaction's first write.** The docs say XIDs come "from a global counter used by all databases within the PostgreSQL cluster" and are assigned "when a transaction first writes to the database". `SELECT FOR UPDATE` also counts as a write, because it "modifies selected rows to mark them locked".
- **The scan covers the whole cluster.** The loop does not filter by database. A long write transaction in an unrelated database on the same instance therefore stalls the reader. So can a job-queue worker that holds a `FOR UPDATE` row lock while it runs a job, a data migration, a bulk load, or a client that wrote something and then went idle in transaction.
- **Prepared transactions count too.** The process array "also include[s] structures representing prepared transactions", and their XIDs are valid entries. An orphaned `PREPARE TRANSACTION` holds the reader back until someone runs `COMMIT PREPARED` or `ROLLBACK PREPARED`.
- **Several things do not hold back the filter, though they still block VACUUM:**
  - read-only transactions, including long `REPEATABLE READ` reports and `pg_dump`-style sessions, because they have a `backend_xmin` but no XID;
  - replication-slot `xmin` and `hot_standby_feedback`, which only feed the global vacuum horizons;
  - backends running lazy VACUUM or logical decoding, which are explicitly skipped (`PROC_IN_VACUUM | PROC_IN_LOGICAL_DECODING`);
  - transactions whose XID was assigned after the event's XID. Those XIDs are higher, so the event is already below `xmin`.

  The usual "idle in transaction blocks vacuum" advice, such as Laurenz Albe's checklist, therefore covers more sessions than actually affect this reader.
- **The reader's own XID counts.** The function takes the reader's own XID into account, so the read should not run inside a transaction that has already written, for example a checkpoint update.
- **Readers on a hot standby are held back too.** On a standby, `xmin` comes from `KnownAssignedXids`, the primary's in-flight XIDs replayed from WAL. A reader there is held back by long transactions on the primary.

### How long the delay can be

An event written with XID *x* becomes readable only when no transaction with an XID at or below *x* is still running. Its extra delay is the remaining lifetime of the longest-lived transaction that already held an XID when the event's own transaction got its XID. This is head-of-line blocking across the whole cluster: every later event, in every stream and category, waits behind that one transaction.

With stock settings this delay has no upper bound:

- `statement_timeout`, `transaction_timeout` and `idle_in_transaction_session_timeout` all default to 0, which means disabled.
- A live client that never commits holds the reader back indefinitely.
- A client that disappears while idle in transaction, for example after a crash or a network partition, is noticed only when TCP keepalive fails. PostgreSQL's `tcp_keepalives_*` settings default to 0, which means "the operating system's default". On Linux that is 2 hours of idle time, then 9 probes 75 seconds apart: about 2 hours 11 minutes in total.
- `client_connection_check_interval` (default 0) helps only "while running queries", not while a session sits idle in a transaction.
- Prepared transactions are not covered by any timeout. The docs warn that "it is unwise to leave transactions in the prepared state for a long time". They recommend `max_prepared_transactions = 0` (a postmaster-level setting) unless an external transaction manager is closing out prepared transactions.

### Which timeouts bound it, and their limits

- **`idle_in_transaction_session_timeout`** ends the session after the given idle time "within an open transaction". It limits each idle gap, not the life of the transaction: a client that sends a statement now and then keeps its XID indefinitely.
- **`statement_timeout`** limits each statement. In extended protocol it runs from Parse, Bind, Execute or Describe until Execute or Sync completes. A long chain of short statements is never caught by it.
- **`transaction_timeout`** (PostgreSQL 17 and later) is the only server setting that limits the transaction as a whole. It ends "any session that spans longer than the specified amount of time in a transaction", for explicit transactions and for single implicit statements. When it is shorter than or equal to the other two timeouts, the longer ones are ignored. Two caveats: "Prepared transactions are not subject to this timeout", and the docs advise against setting it in `postgresql.conf` "because it would affect all sessions". Set it per role or per database instead.
- **These are defaults, not enforced limits.** `statement_timeout`, `transaction_timeout`, `idle_in_transaction_session_timeout` and `idle_session_timeout` are all `PGC_USERSET`, so any session can `SET` them back to 0. Typical practice encourages this: Crunchy Data recommends a 30–60 s `statement_timeout` at database level, raised per session (for example `SET statement_timeout = '30min'`) for migrations and BI work. Those long, writing sessions are exactly the ones that stall the reader.
- **PgBouncer** has client-side equivalents, `idle_transaction_timeout`, `transaction_timeout` and `query_timeout`, all disabled by default.

In practice, the delay is bounded by about the `transaction_timeout` applied to every role that writes anywhere in the cluster. That holds only if prepared transactions are disabled, or watched, and no session overrides the timeout. Without `transaction_timeout`, idle-in-transaction timeouts plus tuned TCP keepalives cover the abandoned-client case. Nothing then limits a transaction that is still doing work.

### Monitoring and remediation

- **Find sessions holding an XID.** Query `pg_stat_activity`, which has one row per server process and a `datname` column, for `backend_xid IS NOT NULL` and sort by `age(backend_xid)` descending. The oldest row is the session holding the reader's `xmin` (unless a prepared transaction is older). Use `backend_xid`, not `backend_xmin`. Albe's vacuum query ranks by both, which would wrongly flag read-only sessions.
- **Check prepared transactions separately.** Query `pg_prepared_xacts` (`transaction`, `gid`, `prepared`, `owner`, `database`), because these transactions have no client session to appear in `pg_stat_activity`. Albe's remedies are `pg_terminate_backend()` for sessions and `ROLLBACK PREPARED` for orphaned prepared transactions.
- **Unprivileged roles see only part of the picture.** In `pgstatfuncs.c`, `backend_xid` and `backend_xmin` are "available to all callers". `state`, query text, `xact_start` and `state_change` are filled only for members of the session's role or holders of `pg_read_all_stats`. A library's own role can therefore detect that some process holds an old XID, but not what it is doing or for how long; operators need `pg_monitor` or `pg_read_all_stats` for that.
- **A suggested library-side metric (my own design inference, not taken from a source):** count the rows that are committed but held back, with `transaction_id >= pg_snapshot_xmin(pg_current_snapshot())`, and report the age of the oldest. That measures the reader's actual lag directly, in time, wherever the blocking session lives.

For a psycopg 3 event store, the practical consequences are:

- the delivery latency it can promise depends on the longest writing transaction anywhere on the instance, not just its own appends;
- it should document setting `transaction_timeout` (or, before PostgreSQL 17, `idle_in_transaction_session_timeout` plus TCP keepalive tuning) for every writing role;
- it should expose a held-back-events or oldest-XID-age signal so operators can see a stall instead of assuming notifications were lost.
