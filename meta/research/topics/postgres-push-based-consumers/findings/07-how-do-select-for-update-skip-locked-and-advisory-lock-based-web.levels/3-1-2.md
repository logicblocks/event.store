# What append throughput and latency does serialising PostgreSQL event-store writes through a single all-stream row lock or per-category advisory lock cost, compared with unserialised sequence appends read through a transaction-id visibility horizon?

## Question

If a PostgreSQL event store forces appends to commit in position order, using one global lock (an all-stream row or table lock) or one lock per category (an advisory lock), what does that cost in append throughput and latency? How does that compare with letting appends draw sequence values concurrently and having consumers read only below a transaction-id visibility horizon (`pg_snapshot_xmin`)?

## Findings

### Why serialisation is used at all

PostgreSQL sequence values are handed out before commit, so a later-starting transaction can commit a higher position first. A consumer that checkpoints the highest position it has seen then skips the lower position when it commits later. Commanded EventStore's issue #3 shows exactly this race. The Python `eventsourcing` library describes the same problem: "insert order and commit order are not the same". One family of fixes makes insert order equal commit order by serialising writers. The other leaves writers alone and limits what readers can see.

### The serialised designs and where their lock sits

- **Single all-stream row lock (Commanded EventStore).** Every append runs one CTE statement. Part of it is `UPDATE streams SET stream_version = stream_version + $2 WHERE stream_id = 0 RETURNING ...`, which increments a gapless counter on the `$all` row. PostgreSQL holds row-level locks until the transaction ends, so all appends across all streams queue on that row. The maintainer says plainly that because `$all` positions must be "unique, monotonically incrementing, and gapless … the linking is blocking, resulting in single writer performance".
- **Table lock (Python `eventsourcing`, psycopg 3).** `PostgresApplicationRecorder` runs `LOCK TABLE … IN EXCLUSIVE MODE` before inserting. Its own comment says this is "to serialize transactions that insert stored events, so that readers don't pass over gaps that are filled in later". The docs say this "effectively serialises writing events". `EXCLUSIVE` still allows `ACCESS SHARE`, so reads continue. It does conflict with `SHARE UPDATE EXCLUSIVE`, the mode taken by `VACUUM`, `ANALYZE` and `CREATE INDEX CONCURRENTLY`, so appends and that maintenance can make each other wait. `POSTGRES_LOCK_TIMEOUT` defaults to 0, which means a writer waits for the lock indefinitely.
- **Per-category advisory lock (Message DB).** `write_message` first calls `acquire_lock`, which runs `pg_advisory_xact_lock(hash_64(category))`. The Eventide docs say: "all writes to streams in a given category are queued and processed in sequence. This ensures that write of a message to a stream does not complete after a consumer has already proceeded past its position." Writes to different categories run in parallel. The guarantee only covers category readers, though: `global_position` "may have gaps", and nothing orders commits across categories. The docs also say transactions "should only be used for writes to the same stream". That avoids holding several category locks in one transaction, which would bring lock-ordering and deadlock risk (that risk is an inference, not stated in the docs).

### What serialisation costs

**The mechanism.** Locks are held until the end of the transaction. The serialising lock is therefore held from the moment it is taken until the commit's WAL flush finishes, plus any client round trips in between. The append rate on one lock can never exceed 1 divided by that hold time, however many writers there are. Each extra writer waiting in the queue adds roughly one hold time to an append's latency. The PostgreSQL docs say "group commit" lets transactions that commit at the same time share one WAL flush, spreading its cost. Writers queued behind one lock never commit at the same time, so each pays a full flush. This is an inference from the docs, not a measured result. The pgbench docs describe the same effect: when concurrent clients outnumber the rows they update, "you'll mostly be measuring update contention".

**Measured evidence (Commanded EventStore, 2018-era, hardware not stated).** Its benchmark spawns N concurrent tasks per op. Each task appends 100 events to its own new stream, and the op waits for all of them to finish.
- Issue #107 reports a single writer at 20,288.68 µs/op (one 100-event append, about 49 appends/s or about 4,900 events/s). With 50 concurrent writers it reports 582,350.50 µs/op (50 appends, 5,000 events: about 86 appends/s or about 8,600 events/s). So 50 times the concurrency gave only about 1.75 times the throughput, which fits near-serial execution. The last of the 50 appends finished about 580 ms after starting, against about 20 ms when running alone. The reporter read the figures as under 2 writes/s, but that misreads what one op contains.
- In issue #139, the maintainer reports how much append time dropped when `$all` building (the global row update plus the `$all` link rows) was turned off: −38.53% for a single writer, −79.53% for 10 writers, −59.88% for 20 and −71.69% for 50. That works out to about 1.6×, 4.9×, 2.5× and 3.5× more throughput. The comparison also removes the extra link inserts, so it is not a pure measure of the lock. The issue is still open, and the current `insert_events` SQL still updates the `stream_id = 0` row.

**Practitioner reports.** Sequin tried a trigger-maintained counter row and found "Write throughput was much lower than we needed, and the lock durations between concurrent writes was very high (seconds)". Moving the counter update "to the very end" of the transaction helped, because it shortens the hold time. So did keeping counters in a separate small table, so that each update did not rewrite heavy rows. Oskar Dudycz (Marten and Emmett) rejected a single-row counter table for the same reason: it makes "all the processing sequential" and the "performance hit was too big to accept".

**Related Marten result (not a lock).** Marten's "Quick" append mode assigns sequence numbers server-side during the INSERT. The older "Rich" mode reserves them in an earlier step. Quick mode cut append time by 40–50% in Marten's load tests and reduced the "event skipping" seen under heavy load. This shows that the longer the gap between drawing a position and committing it, the more out-of-order gaps readers see.

### The unserialised alternative: a transaction-id visibility horizon

Emmett and the `postgresql-event-sourcing` reference implementation do not serialise appends. Each event row stores `pg_current_xact_id()` (an `xid8`) beside a normal sequence position. Emmett's append takes no explicit lock and only does an optimistic per-stream version check. Readers filter with `transaction_id < pg_snapshot_xmin(pg_current_snapshot())`, order by `(transaction_id, position)`, and checkpoint the pair, for example `(e.TRANSACTION_ID, e.ID) > (:lastTx, :lastId)`. Because `xmin` is the "lowest transaction ID that was still active", everything below it is final. A late-committing lower position is therefore held back rather than skipped.

**Write-side cost.** No shared lock is taken, so appends to different streams run in parallel and their commits can share WAL flushes. The extra costs are an 8-byte `xid8` column and the index that supports the `(transaction_id, position)` read order. Every appending transaction writes, so it gets an xid anyway. No published benchmark compares this design with the serialised ones on the same hardware, so the write-throughput advantage is inferred from how the locks work rather than measured.

**Read-side cost (latency).** An event becomes readable only after every transaction with a lower xid has finished. That is normally milliseconds, but the delay is set by the slowest such transaction. Xids come from "a global counter used by all databases within the PostgreSQL cluster" and are assigned "when a transaction first writes". So any long-running writing transaction, even one on unrelated tables, holds back the horizon (this follows from the docs; the practitioner sources describe it within one database or system). Their warnings: a long transaction "will effectively 'pause' all event handlers", and with a two-minute transaction on another table "your cursor/query will be unable to read the last two minutes". Read-only transactions get no xid, so they should not hold it back (an inference from the same docs). Ordering is also by xid assignment, not position. Consumers therefore need a compound checkpoint instead of a single integer.

### Other ways to place the cost

- **Reader-side lock.** `postgresql-event-sourcing` offers an option where the reader briefly takes `LOCK … IN SHARE ROW EXCLUSIVE MODE`. That mode conflicts with the `ROW EXCLUSIVE` held by inserting transactions, so the reader waits for in-flight inserts to finish, then reads up to `pg_sequence_last_value`. Writers stall for each such lock instead of for every other append.
- **Advisory-lock writer registry (Sequin).** Each writer takes a shared advisory lock that marks it as an active writer, plus an exclusive advisory lock whose key encodes the lowest sequence value it may use. Readers find the minimum of those keys in `pg_locks` and read below it. This gives "uncapped, parallel writes" and is not delayed by unrelated long transactions.
- **Gap detection (Marten).** Marten's high-water mark holds at a gap for as long as any transaction that could have reserved it may still be running. It can optionally skip stale gaps after a configured time.

### Bottom line

- **Global row or table lock.** Append throughput tops out at about 1 divided by the lock hold time (lock to commit flush). Append latency grows linearly with the number of concurrent writers, and the one measured case gained less than 2× going from 1 to 50 writers. In return, consumers get one gapless (or at least commit-ordered) integer position, and committed events become visible immediately.
- **Per-category advisory lock.** The same limit applies, but per category, so total throughput grows with the number of categories being written at once. A hot category is still serial, and all-stream readers are not protected.
- **Transaction-id horizon.** Append throughput and latency stay unserialised. The cost moves to consumer visibility latency, which is set by the longest concurrently running writing transaction in the cluster, and to a compound `(xid, position)` checkpoint.

For a push-based psycopg 3 consumer, the horizon design means a notification can arrive before its event falls below `xmin`. The serialised designs make events readable as soon as they commit, at the price of capping append throughput.
