# Why do pull-based log consumers in brokers such as Apache Kafka favour pull over push for throughput and backpressure, and which of those arguments carry over to consumers reading an event table in PostgreSQL?

## Question

Why do log-structured brokers such as Apache Kafka have consumers pull data rather than having the broker push it, in terms of throughput and backpressure? And which of those reasons still hold when the "log" is an event table in PostgreSQL, read by consumers that might be woken by LISTEN and NOTIFY?

## Findings

### What the scholarly record supports, and its limits

The indexed scholarly literature describes Kafka's architecture and sets it against push-style brokers, but its abstracts do not spell out the pull-versus-push rationale. The original Kafka design paper, which states that rationale, is not among the indexed records. The records establish three things:

- **Kafka is a commit log.** It is a publish-subscribe system "with its core architecture as a distributed commit log", built at LinkedIn as a centralised event pipeline (Wang et al., PVLDB).
- **Subscribers read and apply a persistent log.** Kafka "acts as a kind of write-ahead log that records messages to a persistent store and allows subscribers to read and apply these changes", and it serves both offline and online consumption (Thein and Nyunt).
- **Queue brokers carry acknowledgement overhead.** The JMS- and AMQP-based brokers Kafka is contrasted with rely on "centralized brokers, complex routing logic, and tightly coupled acknowledgment semantics", which can become performance bottlenecks (Ghanta).

Dobbelaere and Esmaili compare Kafka with RabbitMQ, the reference push-style broker, both qualitatively and empirically, using a common framework of core pub/sub functions. Outside messaging, gossip-dissemination research reports pull's basic property: messages are transferred only "when recipients request" them, which "enormously" lowers redundant traffic compared with gossip-push (Ahn and Kim).

The Kafka design argument below is the commonly stated one. The records corroborate it in outline but do not quote it. The PostgreSQL carry-over analysis is reasoning from PostgreSQL's documented behaviour, not a published evaluation.

### Why log brokers favour pull

1. **The consumer sets the rate, so backpressure is implicit.** A pulling consumer asks for the next batch only when it has finished the last one. It cannot be flooded, and a slow consumer slows only itself. A push broker has to estimate each consumer's capacity and needs explicit flow control to avoid overrunning slow consumers, for example RabbitMQ's prefetch window of unacknowledged messages. Its per-consumer delivery state grows with the backlog.
2. **Batching is cheap and adapts to lag, which drives throughput.** A pull request names an offset and a maximum size, and the broker returns a contiguous run of the log. A consumer that falls behind automatically receives larger batches, which spreads per-request overhead over more messages exactly when that matters. A push broker must choose between sending each message at once (low latency, poor throughput) and buffering (better throughput, added latency), without knowing whether the consumer is ready.
3. **The broker keeps almost no per-consumer state.** The log is retained whether or not anyone consumes it. Each consumer's progress is one offset per partition, with no per-message acknowledgement or redelivery bookkeeping. That removes the tightly coupled acknowledgement semantics that the Ghanta record identifies as a bottleneck in queue brokers, and it makes many independent consumers cheap.
4. **Replay and mixed-speed consumers come for free.** Each subscriber reads and applies the persistent log from its own offset. A batch job and a real-time service can therefore read the same data at very different speeds, and a consumer can rewind after a bug. A slow consumer never slows producers down.
5. **Pull's weakness, idle spinning, is solved by long-polling, not by push.** A naive pull loop either wastes requests on an empty log or sleeps and adds latency. Kafka's fetch request lets the broker hold the request open until enough data arrives or a timeout expires (the `fetch.min.bytes` and `fetch.max.wait.ms` settings). This keeps pull as the data path while making idle consumers cheap and wake-ups prompt.

### Which arguments carry over to a PostgreSQL event table

**Arguments that carry over fully:**

- **Consumer-controlled rate and backpressure.** A consumer that runs a bounded, ordered range query on the event table (rows after its last position, in position order, with a limit) has exactly Kafka's flow-control property. This is the main strength of the existing polling design and should be kept.
  - The contrast shows when NOTIFY payloads become the data path. PostgreSQL holds undelivered notifications in a single server-wide queue. A listener that falls behind, or sits inside a long transaction, stops that queue from being cleaned up. Once the queue is full, every transaction that issues NOTIFY fails at commit.
  - That is the push-broker failure Kafka was designed to avoid, except that it lands on the writers.
- **Consumer-owned position, with no server-side delivery state.** The event table is the retained log, and each consumer's progress is a row it owns.
  - PostgreSQL can do better than Kafka here. A consumer can update its position in the same transaction as any side effects inside the database. Kafka needs a dedicated transactional protocol to get comparable guarantees, which is the problem its engineers address in the "Consistency and Completeness" work.
  - LISTEN registrations, by contrast, belong to a session and vanish when the connection drops. A design that treats notifications as the source of truth has to rebuild its state on every reconnect. A pull design simply resumes from its stored position.
- **Replay and consumers at different speeds.** New, rebuilding and lagging projections can read the same table from different positions without affecting writers.

**An argument that carries over in form but not in mechanism:**

- **Batch throughput.** Fetching many rows per round trip still spreads network latency, query execution and per-commit cost over the batch. Kafka's mechanical advantages have no PostgreSQL equivalent, though: sequential segment reads, zero-copy transfer from disk to socket, and no per-record visibility checks. Each PostgreSQL batch is an index range scan with MVCC visibility checks and row decoding. Batching should help a great deal, but it will not reach Kafka's absolute rates.

**Arguments that do not carry over, or that need extra machinery:**

- **Offsets that become visible in order.** Kafka assigns an offset when a record is appended, and consumers see only up to the committed high-water mark. So "everything below my offset is final" holds.
  - PostgreSQL allocates an identity or sequence value before commit, and concurrent transactions commit out of order. A reader that moves past the highest visible position can permanently skip a lower-numbered row that commits a moment later.
  - Notification-driven wake-ups make this worse. They arrive just after one commit, which is when concurrent lower-numbered writes are most likely still in flight.
  - Reading by position therefore needs a safe-horizon rule. Options include filtering on transaction-snapshot visibility, serialising position allocation at commit, or staying behind in-flight transactions. Kafka gets this property for free.
- **A cheap long-poll.** PostgreSQL has no query that blocks until rows beyond a given position exist, and an empty poll costs a full query round trip on a dedicated backend process. The nearest equivalent to Kafka's long-poll combines two parts. LISTEN acts as a wake-up hint, and a timeout acts as a fallback. In psycopg 3, that means waiting on the connection's notification generator with a timeout, then running the same range query.
- **Partition-based parallelism.** Kafka consumer groups give ordered parallel consumption by assigning whole partitions to group members. The cost is that ordering holds only within a partition, which is the limitation the Kumar et al. global-ordering record targets.
  - A single PostgreSQL event table has a global order but no built-in partition ownership or rebalancing.
  - Competing consumers must build that themselves, for example by hashing stream identifiers to workers that hold advisory locks or lease rows. The alternative is to fall back to row-claiming queue semantics, which gives up log replay.

### Implication for the design

Kafka's arguments for pull are about the data path: who controls the rate, the batch size and the position. Every one of them favours keeping a pull-based, position-tracked read of the event table. What Kafka has and PostgreSQL lacks is a cheap way to wait, and that is what makes pull low-latency when idle. Push delivery in PostgreSQL is therefore best used to rebuild Kafka's long-poll, not to replace pull:

- NOTIFY acts as a light doorbell. Notifications are coalesced and carry at most a position.
- On wake-up, the consumer drains the table with batched range queries until a batch comes back short. It then waits again, with a fallback timeout.
- On every connect or reconnect, the consumer issues LISTEN before its catch-up query, so a commit that lands between the two cannot be missed.

Hybrid push-pull designs of this kind also appear in pub/sub frameworks for IoT (Lohitha and Pounambal). The case for them in this setting rests on engineering reasoning rather than on comparative studies in the indexed literature.
