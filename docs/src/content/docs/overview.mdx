<p class="es-lede">
The library is a set of building blocks for event sourcing in Python, built on asyncio. Each block
does one job and depends only on the blocks beneath it, so you can start small and add more as you
need them.
</p>

This page carries on with `cart-42`, the shopping cart from the
[introduction to event sourcing](/event.store/event-sourcing/). Each section goes a level deeper
than the one before, so stop whenever you've seen enough. Every package has its own colour, and
it's the same colour in every diagram.

## The map

The library has nine packages in five layers. Each package depends only on packages in the layers
below it, so the higher a package is, the more it does for you. Click a package to see what it's
for, the names you'll use from it, and how it connects to the others.

<PackageMap />

Three things to notice:

- **Most code touches three packages.** `store`, `projection` and `types` cover writing events,
  turning them into state and the values passed between the two. `sources`, `persistence` and
  `query` mostly work behind the scenes.
- **Storage is always pluggable.** The event store and the projection store both hand storage to
  an adapter: in memory for tests, Postgres for production, or
  [your own](/event.store/guides/custom-storage-adapters/).
- **Processing builds on everything else.** It is the one package that pulls the rest together,
  which is why it gets its own [zoom-in](#zoom-in-processing) below.

## The life of an event

Follow one event, a grinder added to `cart-42`, from the moment you describe it to the moment it
changes an answer. The first four steps are always the same. Then pick a branch: work out the state
**on demand** when you need it, or keep it up to date **in the background** as events arrive. The
chips at the top light up the packages each step uses.

<EventJourney />

## The metro map

Here's another way to see how the parts fit together. Each everyday journey through the library is
a line, and each class you meet along the way is a station. Where two lines share a station, the
journeys meet, and that's where the parts of the library connect.

<MetroMap />

Three interchanges hold the library together:

- **`EventStream`** is where writing meets projecting: you publish to a stream, and you project
  from it.
- **`ProjectionStore`** is where on-demand and background projections meet: both save to it.
- **`EventStorageAdapter`** is where tests meet production: swap the in-memory adapter for the
  Postgres one and nothing else changes.

<p class="es-eyebrow">04 · Zoom in</p>

## Zoom in: processing

`processing` has the most moving parts, but they share out three jobs:

- **who reads what**: the broker;
- **reading and remembering**: subscribers, consumers and their checkpoints;
- **keeping it all running**: services.

Here they are, wired together for the `cart-projection` subscriber from the background branch above.

<ProcessingWiring />

:::tip[Three rules of thumb]
- The broker only hands out sources. Subscribers do the reading, and only when they're polled.
- Checkpoints are events too, kept in a state category you choose. Give each subscriber group its
  own.
- Processing is at least once. After a crash, the events since the last checkpoint are processed
  again, so make your processors safe to repeat.
:::
