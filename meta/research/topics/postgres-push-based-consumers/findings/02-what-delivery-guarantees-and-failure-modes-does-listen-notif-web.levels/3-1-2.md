# How do Oban's stager and River's job scheduler elect and fail over the single PostgreSQL-backed leader that periodically re-announces ready work to every consumer?

## Question

How do Oban's stager and River's job scheduler elect and fail over the single PostgreSQL-backed leader that periodically re-announces ready work to every consumer?

## Findings

Both libraries elect their leader the same basic way. Each node keeps trying to write a lease row into a small table that can hold only one row per scope. The node whose row survives is the leader. It keeps the lease by pushing the row's expiry forward more often than the row would expire. When the leader shuts down cleanly, it deletes the row and sends a `NOTIFY` in the same transaction, so the other nodes hold an election at once. When it crashes, the row is simply left to expire. Neither library uses advisory locks or a long-lived session lock: leadership is whatever the most recently committed row says.

The two designs differ in four places:

- how long the lease and renewal intervals are;
- whose clock decides when a lease has expired;
- how an old leader that can no longer reach the database decides to stop;
- how much the leader actually re-announces.

On the last point, the question's premise holds for Oban but only partly for River.

### Oban: `Oban.Peers.Database` and `Oban.Stager`

**Election table and query.** The default peer, `Oban.Peers.Database`, coordinates through the `oban_peers` table. Its columns are `name` (text primary key), `node`, `started_at` and `expires_at`. The V11 migration makes the table `UNLOGGED` unless told otherwise, because the migration module defaults the option with `Map.put_new(:unlogged, true)`.

There is one row per Oban instance name, not per node. The module documentation says "an umbrella application that runs `Oban.A` and `Oban.B` will have two rows in `oban_peers`", so each instance has its own leader.

Each election runs inside one transaction (`Repo.transaction(..., retry: 1, on_exhausted: :log)`) and does two things:

1. It deletes this instance's rows whose `expires_at < DateTime.utc_now()`.
2. It runs an `INSERT … ON CONFLICT (name)` whose conflict action updates `expires_at` only `where p.node == ^node`.

If a row is inserted or updated (`{n, nil}` with n > 0), the node is the leader. If no row is affected (`{0, nil}`), the lease belongs to another live node and this node is a follower. The new `expires_at` is the attempt's start time plus the interval (30 s). If the election transaction fails, the peer marks itself as not the leader.

Oban computes both the expiry it writes and the "now" it compares against with `DateTime.utc_now()` on the application node, not with the database's `now()`. Clock skew between nodes therefore moves the moment a follower can take over.

**Cadence and crash failover.** The peer's defaults are `interval: :timer.seconds(30)` and `leader_boost: 2`. The leader re-runs the election every `interval / leader_boost`, which is 15 s. Followers run it every 30 s. Both timers are jittered downward (`Backoff.jitter(base, mode: :dec)`), so they never fire later than those values.

Oban does not document a worst-case crash failover time. From the defaults it is roughly one lease plus one follower interval, about 60 s. A dead leader's row survives until 30 s after its last renewal, and a follower may then wait up to another 30 s for its next attempt.

**Clean failover.** The peer traps exits. In `terminate/2`, if it is the leader, it runs `delete_self` (matching both name and node) and `Notifier.notify(conf, :leader, %{down: name})` in one transaction. Every peer subscribes to the `leader` channel when it starts. On a `down` message for its own instance name, a peer runs an election immediately.

With the Postgres notifier, the message is a `NOTIFY`. It is therefore delivered only if the row deletion also commits.

**How callers ask about leadership.** `Oban.Peer.leader?/2` is a GenServer call with a 5 s default timeout. It returns the cached flag, or `false` if the call times out. There are two alternatives to the database peer:

- `Oban.Peers.Global` takes a distributed-Erlang global lock.
- `peer: false` swaps in `Oban.Peers.Isolated` with `leader?: false`. The documentation warns that "without leadership, global plugins (Cron, Lifeline, Stager, etc.), will not run on any node."

**What the stager re-announces.** `Oban.Stager` runs on every node, by default every 1 s with a staging limit of 5,000 jobs. On the leader it opens one transaction and does two things:

1. It stages jobs. The query is an `UPDATE` that sets `scheduled`/`retryable` rows with `scheduled_at <= now` to `available`. It joins a `LIMIT` subquery and has no explicit row-lock clause.
2. In `:global` mode it runs `check_available`, which is `SELECT DISTINCT queue … WHERE state = 'available'`, and broadcasts one `insert` notification per queue it finds.

So every second the leader re-announces every queue that still holds available work, whether or not anything new was inserted or staged. This is Oban's recovery path for missed insert notifications, and it matches the "periodic re-announcement" the question describes.

Producers listen on the `insert` and `signal` channels. When an `insert` arrives for its queue, a producer schedules a dispatch after a jittered 5 ms `dispatch_cooldown`. Notifications that arrive while a dispatch is already pending fold into that one dispatch. Each producer also refreshes on its own `refresh_interval`, which the Basic engine sets to 60 s with ±25% jitter, and dispatches after every refresh.

**Fallback when notifications fail.** The stager chooses its mode from `Oban.Sonar`. Each node pings on the `sonar` channel. The ping interval starts at 5 s and doubles up to 60 s while nothing changes, and a node not heard from for 120 s is dropped. The resulting notifier status, and the stager mode it produces, is:

| Status | Meaning | Stager mode |
|---|---|---|
| `:isolated` | hears no pings at all | `:local` |
| `:solitary` | hears only its own pings | `:global` if leader, otherwise `:local` |
| `:clustered` | hears other nodes | `:global` |

In `:local` mode, each node's stager sends `{:notification, :insert, …}` messages directly to its own registered producers every cycle, with no database round trip. In effect, every node polls. The leader also drops to local delivery for a cycle if `Notifier.notify` returns an error or the staging transaction fails.

The Oban documentation summarises this: "Only the leader node stages jobs and notifies queues when the `:notifier`'s pubsub notifications are functional. If pubsub messages can't get through then staging switches to a less efficient 'local' mode in which all nodes poll for jobs to run." From the Sonar defaults, a node can take up to about two minutes to notice that notifications have stopped arriving.

### River: `leadership.Elector`, `QueueMaintainerLeader` and `JobScheduler`

**Election table and queries.** `river_leader` is an `UNLOGGED` table. Its primary key `name` is CHECK-constrained to `'default'`, so the table holds at most one row. The docs say "Leadership is per database and schema."

A follower runs two statements in one transaction:

1. `LeaderDeleteExpired`: `DELETE … WHERE expires_at < now()`.
2. `LeaderAttemptElect`: `INSERT (leader_id, elected_at, expires_at = now() + ttl) ON CONFLICT (name) DO NOTHING RETURNING *`. A returned row means this node is now the leader.

The leader renews with `LeaderAttemptReelect`: `UPDATE … SET expires_at = now() + ttl WHERE elected_at = @elected_at AND expires_at >= now() AND leader_id = @leader_id RETURNING *`. The `elected_at` match ties each renewal to a single leadership term.

The SQL uses the database's `now()` unless an explicit timestamp is passed. The elector passes `e.Time.NowOrNil()`, which by its name is nil outside stubbed test time. Lease expiry is therefore judged against a single clock.

**Cadence and crash failover.** The code constants are:

- `electIntervalDefault = 5s`
- `electIntervalJitterDefault = 1s`
- `electIntervalTTLPaddingDefault = 10s`
- `leaderLocalDeadlineSafetyMargin = 1s`
- `deadlineTimeout = 5s`

The leader TTL is `ElectInterval + 10s`, which is 15 s. The leader renews every 5 s, and followers retry at a random point between 5 and 6 s.

The leader-election documentation says "If the current leader is unable to renew its leadership within a five second TTL, a new leader will automatically be elected." In the current source that five seconds is the renewal interval, and the TTL is 15 s. From the code, worst-case crash failover is about 15 s plus up to 6 s, roughly 21 s.

**How an old leader steps down.** The leader keeps a local trust window: `trustedUntil = attemptStarted + (TTL − 1s safety margin)`. Each renewal attempt times out after whichever is shorter, 5 s or the trust time remaining. On an error, the leader backs off exponentially, capped at the remaining trust time, and retries straight away. When the window runs out, it steps down without waiting for the database ("Current leader stepping down because the reelection deadline elapsed").

The window is measured from a local start time that comes before the database evaluates `now()`. The incumbent's own deadline therefore falls at least 1 s before the database lease expires, as long as the two clocks run at similar rates. The clocks do not need to be synchronised. (This is an inference from the code.)

If a renewal returns no row (`ErrNotFound`), the leader has already lost the lease and skips resigning.

**Clean failover.** Whenever a node leaves the leader state, `attemptResignLoop` runs `LeaderResign` up to three times with backoff. This covers shutdown, forced resignation and an expired deadline. It runs on a `context.WithoutCancel` context so that it finishes during shutdown.

`LeaderResign` is a single statement that does three things:

1. It locks the row matching `elected_at` and `leader_id` with `FOR UPDATE`.
2. It calls `pg_notify('<schema>.river_leadership', {"leader_id": …, "action": "resigned"})`.
3. It deletes the row.

When a follower receives a `resigned` message from another client, it signals a wake-up channel. The channel has a buffer of one, so wake-ups merge. The follower then sleeps a random 0–50 ms and tries to get elected. A `request_resign` message on the same topic forces the current leader to resign.

In poll-only mode there is no notifier, so followers simply retry every 5–6 s.

**Link to maintenance work.** `QueueMaintainerLeader` subscribes to the elector's state through `Listen()`. Each update carries `IsLeader` and a `Term` number. When this client gains leadership, it starts the `QueueMaintainer`, which includes `JobScheduler`, retrying with backoff. If the start keeps failing, it calls `Elector.RequestResign(ctx, term)` so another client can take over. When this client loses leadership, it stops the maintainer. An epoch counter discards start attempts that belong to an earlier term.

**What the scheduler announces.** `JobScheduler` runs only on the leader, every 5 s. Each pass is a transaction:

1. It moves `retryable`/`scheduled` jobs with `scheduled_at <= now + interval` (a 5 s look-ahead) to `available`, in batches, and locks the candidate rows `FOR UPDATE`.
2. It calls `NotifyInsert` only for queues where one of the jobs it just scheduled is due within a 5 ms horizon. Because this happens inside the transaction, the notification is sent at commit.

Jobs promoted early are not run before their time, because the fetch query also requires `scheduled_at <= now()`.

`NotifyInsert` is `Client.maybeNotifyInsertForQueues`. It removes duplicate queue names and rate-limits each queue through `insertNotifyLimiter`, whose wait is `FetchCooldown` (100 ms by default). It then emits `{"queue": name}` payloads on the `river_insert` topic.

Unlike Oban's stager, River's leader does not re-announce queues that already hold available work. River's recovery path sits in each consumer instead. Every producer polls every `FetchPollInterval` (1 s by default, jittered). The source comment describes this as "a back up in case something with listen/notify didn't work, or the fetch limiter was limited so there's still jobs to pick up". An incoming insert notification triggers the same rate-limited fetch.

### Implications for a PostgreSQL-only event store

- **Lease pattern.** One transaction that deletes expired rows and then does a conditional insert or update on a one-row-per-scope table is enough to elect a single announcer. It needs no advisory lock and no session state, so it survives dropped connections and connection poolers.
- **Unlogged lease table.** An `UNLOGGED` table makes lease writes cheap. PostgreSQL documents that an unlogged table is "automatically truncated after a crash or unclean shutdown" and that its contents are "not replicated to standby servers". After a crash or a failover to a standby, the table is therefore empty, which simply forces a fresh election.
- **Clocks and overlap.** Judge lease expiry on the database clock, as River does, rather than on application clocks, as Oban does. Also give the incumbent a local deadline shorter than the lease. These narrow, but do not remove, the window in which two leaders overlap.
- **Idempotent leader work.** Neither library fences leader-only writes with a term token, so work done only by the leader should be safe to run twice. River's scheduling query takes `FOR UPDATE` row locks; Oban's staging `UPDATE` has no explicit lock clause.
- **Re-announce everything, or keep a consumer poll.** A leader that re-announces "everything still pending" on a timer, as Oban does, also recovers consumers that missed a notification. A leader that announces only new work, as River does, needs a poll in each consumer as well. Both libraries keep a path that does not depend on `NOTIFY` at all: Oban's Sonar-driven local mode and River's per-producer poll. They need it because the leader's announcements travel over the same LISTEN/NOTIFY channel that may be failing.
- **Failover gaps.** Deleting the lease and issuing the `NOTIFY` in one transaction at clean shutdown cuts the leadership gap to milliseconds. After a crash, the gap is bounded by the lease length plus the follower retry interval: about 60 s for Oban and 21 s for River with their default settings.
