# Can a LISTEN connection work through PgBouncer or similar connection poolers in transaction or session pooling mode without missing notifications?

## Question

Can a consumer's `LISTEN` connection be routed through PgBouncer or a similar pooler (PgCat, PgDog, Supavisor, RDS Proxy, Pgpool-II, the poolers built into managed PostgreSQL services) in transaction or session pooling mode and still receive every notification?

## Findings

### Short answer

**Transaction or statement pooling: no.** A `LISTEN` issued through a transaction-pooled connection registers whichever backend happened to run it. The client is then detached from that backend, so notifications are dropped or handed to unrelated clients, and the client gets no error.

**Session pooling (or an equivalent "pinned" mode): yes, but only as reliable as a direct connection.** A session-pooled listener gets notifications exactly as it would over a direct connection. The pooler also adds new ways for the connection to drop. After each drop the `LISTEN` registration is gone, and any notification committed during the gap is lost for good. So no pooler path is gap-free by itself. It becomes gap-free only if the consumer re-issues `LISTEN` and then catches up from its last processed position every time it reconnects.

### Why transaction pooling cannot deliver notifications

PostgreSQL ties `LISTEN` to a server session. `LISTEN` "registers the current session as a listener", takes effect at transaction commit, and registrations "are automatically cleared when the session ends". `NOTIFY` only delivers to sessions that are listening at that moment. PostgreSQL never stores notifications for a session that was not listening.

Transaction pooling breaks that assumption. PgBouncer assigns a server connection to a client "only during a transaction", then puts it back in the pool. Its SQL feature map marks `LISTEN` as **Never** supported under transaction pooling, while `NOTIFY` is **Yes**.

PgBouncer's source shows what happens to the notifications. In `handle_server_work()`, a `NotificationResponse` packet goes to whichever client is currently linked to that server connection. If no client is linked, PgBouncer logs the warning `got packet '%c' from server when not linked` and discards the packet. Either way, the notification never reliably reaches the client that asked for it:

- While the listening backend sits idle in the pool, its notifications are thrown away.
- While another client has borrowed it, that client receives notifications it never asked for.

The backend also stays registered as a listener. PgBouncer runs `server_reset_query` (default `DISCARD ALL`, which includes `UNLISTEN *`) only in session-pooling pools, unless `server_reset_query_always` is turned on. As a result, stale listening backends pile up; graphile-worker warns of "too many connections ... in the `LISTEN` state". Turning on `server_reset_query_always` does not help either: it would just run `UNLISTEN *` after every transaction.

The failure is silent. The `LISTEN` statement succeeds and `NOTIFY` commits, but the consumer never wakes up. Oban documents that transaction pooling "disables all of PostgreSQL's `LISTEN` and `NOTIFY` activity", and its Stager falls back to local polling when that happens. A PgBouncer feature request for transaction-mode `LISTEN` support through an internal pub/sub layer (issue #655, opened November 2021) is still open.

Managed poolers take the same position:

| Service | Default mode | What its docs say about `LISTEN` |
|---|---|---|
| Neon (`pool_mode=transaction`) | transaction | `LISTEN`/`NOTIFY` listed as unsupported on pooled connections |
| Google Cloud SQL Managed Connection Pooling | transaction | `LISTEN` listed as unsupported in transaction mode |
| Supabase Supavisor | transaction on port 6543 | "listen and notify" don't survive between transactions in transaction mode; session mode (port 5432) and direct connections support them |
| Azure Flexible Server built-in PgBouncer 1.25.2 | `pgbouncer.pool_mode` = `transaction` | no specific statement; transaction default implies the same limitation |

PgCat describes transaction mode the same way: the server goes back to the pool once the transaction ends. Its README doesn't list `LISTEN` among the unsupported features, but the same mechanism applies.

### Session pooling works, but the pooler adds its own gap sources

In session pooling, PgBouncer assigns a server connection to the client "for the whole duration it stays connected", and `LISTEN` is supported. PgBouncer forwards asynchronous `NotificationResponse` messages to the linked client even when the client is idle. Since 1.7 it has not changed connection state when a `NOTIFY` arrives (changelog: "Don't change connection state when NOTIFY arrives from server"), and the current code keeps the ready and idle-in-transaction flags intact for these async packets.

AWS RDS Proxy reaches the same behaviour by pinning. "Listening on a notification channel" pins the client to one database connection until "the client connection is dropped", so a listener there effectively gets a dedicated session.

While its connection stays up, a session-pooled listener misses nothing. Gaps come from losing the connection, and the pooler adds several ways to lose it:

- **Reset on disconnect.** When a session-mode client disconnects, PgBouncer runs `DISCARD ALL`, which includes `UNLISTEN *`. A reconnecting listener may land on a different backend and has no registration until it issues `LISTEN` again. Anything committed in between is gone, because PostgreSQL does not keep notifications for sessions that weren't listening.
- **Operator actions.**
  - `KILL` drops all client and server connections immediately, and a plain `SHUTDOWN` exits.
  - In session mode, `PAUSE`, `RECONNECT` and `SHUTDOWN WAIT_FOR_SERVERS` all wait for clients to disconnect first, so a permanent listener can hold up maintenance until someone kills it.
  - Rolling restarts with `so_reuseport` use `SHUTDOWN WAIT_FOR_CLIENTS` and expect clients to reconnect to a surviving process.
- **Managed restarts.** Azure restarts its built-in PgBouncer (and the VM) on scaling, high-availability failover or server restart, and "you then need to re-establish the existing connections".
- **Pooler timeouts.**
  - When `client_idle_timeout` is set, PgBouncer closes clients that have been idle that long. A listener blocked waiting for notifications sends nothing, so it looks idle.
  - `idle_transaction_timeout` disconnects a client left idle inside a transaction.
  - A listener should not sit in an open transaction anyway. PostgreSQL holds notifications back until the transaction ends. A long-lived listening transaction also stops queue cleanup, and once the 8 GB notification queue fills, `NOTIFY` transactions fail at commit.
- **Pool capacity.** Each session-mode listener permanently takes one server slot. If a reconnecting listener cannot get a slot, `query_wait_timeout` disconnects it (Azure's default is 120 s).

### Load-balancing poolers must send `LISTEN` to the primary

Hot standbys reject `LISTEN` and `NOTIFY` with an error, so a pooler that routes reads to replicas has to keep the listener on the primary. Pgpool-II bug 116 shows this failure: in streaming-replication load-balancing mode, notifications were unreliable because a query went to a standby, which never sends notifications. It was fixed in 2015.

### Pooler-side multiplexing changes the guarantee, not the need for catch-up

PgDog supports `LISTEN` in transaction mode. It is off by default and enabled with `pub_sub_channel_size`. PgDog registers each channel once with PostgreSQL over a dedicated server connection and fans notifications out to subscribed clients through an in-process broadcast channel.

Its documentation says `NOTIFY` delivery is "at most once": messages may be lost if the dedicated connection breaks, and PgDog doesn't retry them. That makes the feature a useful wake-up signal, but still not a gap-free one.

### Implications for a psycopg 3 event-store consumer

Pooler documentation and job-queue libraries agree on one pattern: keep the listener off the transaction pool, and let everything else use it.

- **Where the listener connects.** Use a session-mode pooler alias, or a direct connection.
- **Where writers connect.** Writers that issue `NOTIFY` or `pg_notify()` can stay on the transaction pool, because `NOTIFY` is supported there.
- **What other projects do.**
  - River puts job inserts and workers on transaction pooling and gives its few coordinators "a raw Postgres pool".
  - Oban recommends session pooling or a separate direct connection.
  - Brandur's notifier pattern keeps one listening connection per process and fans out in-process, so the rest of the application can use transaction pooling.

In psycopg 3, that listener should be:

- dedicated to listening and never borrowed from a general pool;
- in autocommit mode, which psycopg requires for timely notifications;
- read with `Connection.notifies()`, because `add_notify_handler()` callbacks only fire during other connection operations.

Even on a session-mode or direct path, notifications are lost across reconnects. Treat them as hints, not as the delivery mechanism. On every connect or reconnect, issue `LISTEN` first, then read the event log from the last processed position, and keep a fallback poll running.
