### Added

- Added an optional `metadata` field to `NewEvent` and `StoredEvent`, backed by a `metadata JSONB NOT NULL` column in the `events` table. The field accepts an arbitrary JSON-serialisable value and defaults to `None` (no metadata), which is stored as JSON `null`.

### Changed

- The `serialise()` output of both `NewEvent` and `StoredEvent` now includes a `metadata` key. Consumers that persist or strictly validate serialised events (e.g. snapshot stores) should account for the new key.

### Breaking changes

- **`StoredEvent.metadata` is now a required constructor argument.** Code that constructs `StoredEvent(...)` directly (custom adapters, fixtures, tests) must pass `metadata` explicitly (use `None` for no metadata).
- **`NewEvent.metadata` is now a required constructor argument.** Code that constructs `NewEvent(...)` directly (custom adapters, fixtures, tests) must pass `metadata` explicitly (use `None` for no metadata).

- **A schema migration is required for existing deployments.** The `events` table gains a `metadata JSONB NOT NULL` column, and both the read and write paths now depend on it (the read path maps the column directly onto `StoredEvent.metadata`). The migration must therefore be applied **before, or atomically with, deploying the new version** — running the new code against an un-migrated table fails on reads as well as writes.

  Apply the migration in two steps.

  1. Before deploying the new version, add the column with a default:

     ```sql
     SET lock_timeout = '2s';
     ALTER TABLE events ADD COLUMN metadata JSONB NOT NULL DEFAULT 'null'::jsonb;
     ```

  2. Only after every running writer supplies `metadata`, and you no
     longer need to roll back to a version that omits it, drop the
     default:

     ```sql
     SET lock_timeout = '2s';
     ALTER TABLE events ALTER COLUMN metadata DROP DEFAULT;
     ```

  The `DEFAULT 'null'::jsonb` backfills all existing rows during the `ADD COLUMN` step, matching the application's representation of absent metadata (JSON `null`, deserialised as `None`), so historical and newly-written no-metadata rows read back identically. Keep the default while any writer that omits `metadata` is still running: its `INSERT` does not name the column, so without a default it fails the `NOT NULL` constraint. Dropping the default in step 2 brings the column in line with the canonical no-default DDL, so all new rows must supply an explicit value. In PostgreSQL 11+ adding a column with a constant default is a catalogue-only change (no table rewrite); the bounded `lock_timeout` guards against blocking behind a long-running transaction on a busy table.

  **Rolling deploys and rollback.** Releases without `metadata` support, including 0.1.11, read events with `SELECT *` and `RETURNING *`. Once the column exists, those releases fail every read and every save with `TypeError: StoredEvent.__init__() got an unexpected keyword argument 'metadata'`. The retained default protects their inserts, but it does not fix these reads. The explicit-column fix in this release cannot change that retroactively. So:

  - Old and new versions cannot safely run side by side against the migrated table. Plan a coordinated migration and application cutover, or ship a compatibility fix to the old version first.
  - An application-only rollback to such a release does not work while the column exists.
  - Dropping the column (`ALTER TABLE events DROP COLUMN metadata`) lets such a release run again, but permanently discards all stored metadata. Treat it as a last resort, not a routine rollback step.
