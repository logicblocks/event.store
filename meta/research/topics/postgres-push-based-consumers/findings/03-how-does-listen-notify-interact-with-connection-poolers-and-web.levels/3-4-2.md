# Do notifications sent with pg_notify() from a trigger or SQL function bypass PgDog's NOTIFY interception, and are they then delivered at commit through PgDog's dedicated listener connection to transaction-mode clients?

## Question

PgDog, a PostgreSQL pooler, intercepts client `LISTEN` and `NOTIFY` statements in transaction mode. Do notifications raised server-side, by `pg_notify()` in a trigger or SQL function, escape that interception? If they do, does PostgreSQL deliver them at commit to PgDog's dedicated listener connection, and does PgDog then fan them out to its transaction-mode clients?

## Findings

**Short answer: yes to both, with conditions.** PgDog only intercepts a top-level `NOTIFY` statement sent by a client. A `pg_notify()` call, or a `NOTIFY` run inside a trigger, function or `DO` block, executes inside PostgreSQL on whichever pooled server connection carries the transaction. PgDog never sees it. PostgreSQL queues the notification and delivers it at commit to every session listening on that channel in the same database. That includes PgDog's dedicated listener connection, which forwards whatever arrives to every subscribed client. No PgDog document or test covers this path. This answer comes from reading PgDog's source on its `main` branch and from PostgreSQL's documented semantics.

### Why pg_notify() bypasses PgDog's interception

Interception happens at two layers, and a server-side `pg_notify()` gets past both.

1. **Regex pre-filter.** With the default `query_parser = "auto"`, PgDog skips the full SQL parser in simple deployments. These are unsharded clusters where the router is not needed and neither multi-tenancy nor full prepared-statement handling is configured. In that case a `RegexParser` decides whether to parse. Its pattern only matches statements that begin, after any leading comments, with one of `(RE)SET`, `BEGIN`, `COMMIT`, `ROLLBACK`, `LISTEN`, `UNLISTEN`, `NOTIFY` or `DISCARD`. Neither `SELECT pg_notify(...)` nor an `INSERT` whose trigger calls `pg_notify()` matches, so both go straight to a pooled server connection.
2. **Full parser.** When PgDog does parse, it inspects only the first top-level statement. The source says so explicitly: "only the first one is used for routing". Only a `NotifyStmt` node becomes PgDog's internal `Command::Notify`. A `pg_notify()` call parses as a function call inside a `SelectStmt`, so it is routed as an ordinary query. Trigger and function bodies are never visible to PgDog at all.

In PostgreSQL, `pg_notify()` and the `NOTIFY` statement both call the same internal routine, `Async_Notify`. Its source comment reads: "Adds the message to the list of pending notifies. Actual notification happens during transaction commit." The documentation adds that a `NOTIFY` inside a transaction is "not delivered until and unless the transaction is committed". So a trigger's notification gets native PostgreSQL semantics: it is atomic with the data commit and discarded on rollback. Identical channel and payload pairs within one transaction are collapsed into one. None of this depends on PgDog's notify buffer.

### How the notification reaches transaction-mode clients

Pub/sub is off by default. It is enabled by setting `pub_sub_channel_size` in `pgdog.toml`. When a transaction-mode client issues `LISTEN`, PgDog does three things:

- It registers the channel in a per-pool registry, where a pool is one user and database pair.
- It sends a Rust string built from the template `LISTEN "{channel}"` over a standalone connection taken from the shard's primary pool. Several clients on one channel share a single registration.
- It returns a synthetic `LISTEN` reply to the client.

The PostgreSQL docs say that whenever `NOTIFY` is invoked, "either by this session or another one connected to the same database, all the sessions currently listening on that notification channel are notified". So the dedicated connection receives a `NotificationResponse` once the trigger's transaction commits on the pooled backend.

PgDog's listener loop then handles it as follows:

- It treats every message with code `'A'` as a notification and looks the channel up by exact name in the pool's registry.
- It broadcasts the notification on a Tokio broadcast channel.
- Each client's `PubSubClient` merges its subscriptions into one internal queue.
- The client's `Connection::read()` waits on both that queue and server messages at once.
- The client task always polls `read_backend()`, so an idle transaction-mode client that holds no server connection still gets the notification pushed to it.

The listener does not filter by sender PID or by origin. A notification raised by a trigger is indistinguishable from one PgDog forwarded itself. Pub/sub is a transaction-mode feature: in session mode, PgDog passes `LISTEN`, `NOTIFY` and `UNLISTEN` straight to the server.

### Conditions and caveats

- **Pub/sub must be enabled and parsing must not be forced off.** Without `pub_sub_channel_size`, a client's `LISTEN` returns a `PubSubDisabled` error. With `query_parser = "off"`, no statement is ever classified as `LISTEN`. The `LISTEN` would then run on a transaction-pooled backend whose registration does not stay with the client. This is an inference from the dispatch code.
- **Registration race.** PgDog acknowledges `LISTEN` as soon as the request is queued, before PostgreSQL has executed it. The listener's `listen()` returns without waiting for a reply, and the PgDog blog states "Both `LISTEN` and `NOTIFY` commands are acknowledged by PgDog immediately". PostgreSQL's `LISTEN` "takes effect at transaction commit" and receives only events committed after that point. A trigger notification committed between the client's acknowledgement and the real `LISTEN` is therefore never delivered.
- **Exact channel-name match.** PgDog stores the channel name as the parser produced it. Standard PostgreSQL identifier folding turns an unquoted `LISTEN Events` into `events`, whereas `pg_notify()` uses its text argument verbatim. So `pg_notify('Events', ...)` will not reach that listener. This is ordinary PostgreSQL behaviour, preserved by PgDog's exact-match lookup.
- **Database scope.** PostgreSQL treats notifications as database-local, so the trigger must run in the same database as the pool's listener connection.
- **Sharding.** PgDog maps a channel to a shard by hashing the channel name and listens only on that shard's primary. A trigger that fires on a different shard will not be seen. Unsharded deployments are unaffected.
- **At most once.** If PgDog's dedicated connection is down when the trigger's transaction commits, that notification is lost. After reconnecting, PgDog re-issues `LISTEN` for the channels in its registry but replays nothing. A client whose broadcast receiver falls behind loses messages, which PgDog counts as dropped.
- **Timing and PID.** PostgreSQL holds notifications for a listening session that is inside a transaction until the transaction ends. PgDog's read path does not appear to wait for the client's transaction state, so a notification may arrive mid-transaction (inferred from the source). The PID in each notification belongs to whichever pooled backend committed the trigger's transaction. A transaction-mode client cannot meaningfully compare that PID with its own, so filtering out its own notifications by PID does not work.

### Trade-off against sending NOTIFY through PgDog

The two routes differ in atomicity and in commit-time cost.

**Client `NOTIFY` through PgDog.** Inside a transaction, PgDog buffers the `NOTIFY`, drops the buffer if the transaction errors, and after a successful `COMMIT` sends the buffered `NOTIFY`s to the dedicated listener's queue. The listener then executes each one as a separate statement over its own connection. This is not atomic with the data commit: a failure between commit and forwarding loses the notification. The source also builds the forwarded statement by interpolating the payload into `'...'` with no visible escaping. A payload containing a single quote, as JSON payloads often do, may therefore fail to forward. The listener loop ignores error responses, so such a failure would likely be silent. This is inferred from the source as read.

**`pg_notify()` in a trigger.** This keeps PostgreSQL's atomic commit-time delivery, but it brings back the cost PgDog's buffering was designed to avoid. PgDog's docs cite a "known performance problem" with `NOTIFY` inside transactions. PostgreSQL's `PreCommit_Notify` takes a database-wide `AccessExclusiveLock` via `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)` and holds it "till after commit" so that queue entries appear in commit order. Every append transaction whose trigger notifies therefore serialises its commit on that lock.

### Verification status

PgDog's pub/sub documentation does not mention triggers or `pg_notify()`. Its integration tests for `NOTIFY` cover commit delivery and rollback, error and constraint-violation suppression, using only the `NOTIFY` statement. No test exercises `pg_notify()` or a trigger. The conclusions above follow from the routing, listener and fan-out code plus PostgreSQL's documented semantics, but no test has observed them end to end.
