# What flush interval for a debounced notifier that sends one payloadless NOTIFY per batch on a separate autocommit connection best balances consumer wake-up latency against append throughput in a psycopg 3 event store?

## Question

A psycopg 3 event store can wake its consumers by having a notifier send one
payloadless `NOTIFY` per batch of appends, on its own autocommit connection
rather than inside each append transaction. What flush window should that
notifier use to balance consumer wake-up latency against append throughput?

## Findings

### Short answer

No published benchmark measures the best window for this exact design.
PostgreSQL's commit path and the defaults chosen by established
PostgreSQL-backed queues still point to the same choice. The notifier should
fire on both the leading and trailing edges of the window, not use a pure
trailing-edge debounce. The window should be in the **tens of milliseconds**:
about **50 ms** is a reasonable default, configurable from roughly 5 to 10 ms
for latency-sensitive deployments up to 100 to 250 ms for deployments with
many consumers. A fallback poll of about **1 to 2 s** should back it up.

The `NOTIFY` runs on its own autocommit connection, so the window has almost
no effect on append throughput. Two things depend on it:

- how many catch-up reads consumers issue during sustained bursts of appends
- the worst-case extra delay during those bursts

The window adds no delay to the first append after a quiet period.

### Why the window barely affects append throughput in this design

**Only transactions that queued a notification take the global notify lock.**
In `PreCommit_Notify`, PostgreSQL calls
`LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)`.
The source comment reads: "Serialize writers by acquiring a special lock that
we hold till after commit. This ensures that queue entries appear in commit
order." `CommitTransaction` then runs these steps in order:

1. `PreCommit_Notify` takes the lock. Its comment says this step is placed
   "late in the pre-commit sequence to minimize time spent holding the
   notify-insertion lock".
2. `RecordTransactionCommit` runs. This is where a synchronous commit calls
   `XLogFlush`.
3. `ProcArrayEndTransaction` runs.
4. The lock is released.
5. `AtCommit_Notify` signals the listening backends.

So when `NOTIFY` is issued inside an append transaction, the database-wide
lock is held across that append's durable commit. Every concurrent writer
that also notifies then queues behind it. Recall.ai described this failure in
production: database load and waiting sessions spiked while "database CPU,
disk I/O and network traffic all plummeted". An append transaction that
issues no `NOTIFY` never takes this lock, so moving `NOTIFY` to a separate
connection takes it off the append path entirely.

**A transaction that only runs `NOTIFY` is cheap.** `PreCommit_Notify`
assigns the transaction an XID. However, `RecordTransactionCommit` calls
`XLogFlush` only when `wrote_xlog && markXidCommitted && synchronous_commit >
SYNCHRONOUS_COMMIT_OFF`. Otherwise it takes the asynchronous branch
(`XLogSetAsyncXactLSN`). The source comment says asynchronous flushing is
allowed when "the current transaction has not performed any WAL-logged
operation or didn't assign an xid".

From that code, a transaction that only queues a notification has written no
WAL before its commit record, so it should not wait for a WAL flush while
holding the lock. This is an inference from the source and should be
confirmed by measurement. If it holds, each flush costs:

- one XID
- a brief hold of the heavyweight lock
- one write to the notification queue
- one commit record
- one signal to each listening backend

With a 50 ms window, one notifier sends at most 20 such transactions per
second. If P application processes each run their own notifier, the total is
at most P divided by the window, per second. These transactions contend only
with each other and with any other code in the database that issues `NOTIFY`.

**PostgreSQL's development source wakes fewer backends.** It keeps a global
hash table that maps each (database, channel) pair to its listeners. Its
`SignalBackends` advances the queue pointers of backends that are not
listening on the channel directly, instead of waking them. Backends that are
far behind are still signalled. On servers with this change, a flush wakes
only the consumers listening on its channel.

**Several channels per flush should share one transaction.** A notifier may
signal more than one channel per flush, for example one per event category.
Sending them all in one transaction means the lock is taken once per flush,
not once per channel. Oban's Postgres notifier sends many payloads in a single
statement, `SELECT pg_notify($1, payload) FROM
json_array_elements_text($2::json) AS payload`.

PostgreSQL merges duplicate notifications only within one transaction, and
"notifications from different transactions will never get folded into one
notification". Coalescing across appends is therefore the application
notifier's job.

### Where the trade-off actually lies: consumer reads and burst latency

**Read load.** Each flush wakes every listener on the channel, and each woken
consumer reads the events after its checkpoint. During sustained appends,
reads per second are at most the number of consumers divided by the window.
For 20 consumers, the arithmetic gives these upper bounds:

| Window | Maximum reads per second |
|--------|--------------------------|
| 10 ms  | 2,000                    |
| 50 ms  | 400                      |
| 100 ms | 200                      |
| 250 ms | 80                       |

These reads compete with appends for CPU, I/O and shared buffers. This read
load, rather than the cost of the `NOTIFY` itself, is the main way the window
affects append throughput.

**Latency.** The window's effect on latency depends on how the notifier fires:

- **Leading and trailing edges (recommended).** The first append after a quiet
  period triggers a notification immediately, so no delay is added. During
  sustained appends, an event committed inside an open window waits at most
  one window for the trailing notification, and about half a window on
  average.
- **Pure trailing-edge debounce, which waits until appends have been quiet for
  the window.** This adds the full window to every wake-up. Under continuous
  appends it never fires until the burst ends, unless a maximum wait is added.
- **Pure leading-edge throttle.** This drops every signal that arrives inside
  the window. The last events of a burst then wait for the fallback poll.

River's `DebouncedChan` implements the recommended behaviour. Its comment
says: "Multiple invocations to Call during the cooldown period will
deduplicate to a single emission on C on the period's leading edge ... and
then one fire on the trailing edge of each period for as long as Call
continues to be invoked."

### What established libraries chose

| Library and component | Where coalescing happens | How it fires | Default window | Fallback |
|---|---|---|---|---|
| River insert notifications | Insert side, per queue per client; `NOTIFY` is sent inside the insert transaction | Leading edge only; `ShouldTrigger` returns false inside the window | `FetchCooldown`: 100 ms (minimum 1 ms) | `FetchPollInterval`: 1 s |
| River producer | Consumer side, `DebouncedChan` | Leading and trailing edges | `FetchCooldown`: 100 ms | Poll loop at `FetchPollInterval`, with jitter |
| Oban producer | Consumer side; at most one pending dispatch timer | Coalesces into a single timer, with jitter | `dispatch_cooldown`: 5 ms (minimum 1 ms) | Not applicable |
| Oban stager | Leader-only; notifies queues that have available jobs | Periodic | Stager interval: 1 s | Falls back to local-mode messages if the notifier fails |
| PGMQ | Insert trigger, using an unlogged throttle table; payload is `NULL` | Leading edge only | `throttle_interval_ms`: 250 ms when enabled (0 means no throttling) | Consumer polling |
| Graphile Worker | Not applicable | Not applicable | Not applicable | `pollInterval`: 2,000 ms |

Four points stand out:

- **River's window is longer than this design needs.** River's 100 ms
  insert-side window also limits how often `NOTIFY` reaches the insert path,
  because River notifies inside the insert transaction. A separate-connection
  notifier removes that cost, so a shorter window is affordable.
- **Short consumer-side cooldowns are practical.** Oban's 5 ms default shows
  this. Oban documents the throughput trade-off as "average jobs per second
  for a single queue is approximately `(1000 / cooldown) * limit`". The same
  limit applies to an event-store consumer that reads only once per wake-up.
  It does not apply to a consumer that keeps reading until it has caught up.
- **Every library keeps a fallback poll of about 1 to 2 s.** River's poll loop
  is described as "a back up in case something with listen/notify didn't
  work".
- **PGMQ's throttle puts shared state on the append path.** Its trigger runs an
  `UPDATE` on one throttle row per queue inside every inserting transaction.
  By ordinary PostgreSQL row-locking rules, that row stays locked until commit
  (an inference, not stated by PGMQ). A throttle held in application memory
  and flushed over a separate connection avoids any shared state on the
  append path.

### Recommended configuration for a psycopg 3 event store

1. **Notifier connection.** Use a dedicated connection opened with
   `autocommit=True`. On async connections, call `set_autocommit`. Psycopg
   advises keeping notification connections in autocommit "if you wish to
   receive or send notifications in a timely manner."
2. **Notifier logic.** Run the notifier as a single asyncio task, or a thread,
   that holds a pending flag:
   - Set the flag only after an append transaction has committed. Never set it
     inside the append transaction.
   - If no window is open, send immediately and open a window.
   - If a window is open, mark it pending.
   - When the window ends, send once if it is pending and open a new window.
     Otherwise, go idle.

   This copies River's `DebouncedChan`. Even a very short window caps the
   rate at one `NOTIFY` per window per process, however many appends commit
   concurrently. Sending one `NOTIFY` per append (no window at all) would
   instead push every append through one serial connection, one round trip
   at a time.
3. **Window size.**
   - Default to about 50 ms.
   - Lower it to 5 to 10 ms for single-process, latency-sensitive deployments.
   - Raise it to 100 to 250 ms when many consumers or many application
     processes share the database.
4. **Payload.** Send a plain `NOTIFY channel` or `pg_notify(channel, '')`.
   PGMQ passes a `NULL` payload. With no payload, the 8,000-byte limit does
   not apply.
5. **Consumers.**
   - Treat a notification as a sign that new events may exist, not as a count
     of events.
   - Keep reading until caught up.
   - Wait using psycopg's `notifies()` generator with its `timeout` parameter,
     so the same wait also serves as the fallback poll. Set that timeout to
     about 1 to 2 s.
   - If the process crashes between an append's commit and the next flush,
     that wake-up is lost. The fallback poll recovers it.
6. **Measurement.** Run a sweep over windows of 0, 5, 10, 25, 50, 100 and
   250 ms. For each, measure:
   - append transactions per second
   - p50 and p99 delay from commit to handler
   - consumer reads per second

   If the inference about the WAL flush holds, append throughput should stay
   flat across all windows. Choose the smallest window at which consumer read
   load is acceptable.
