# How can a polling or notification-woken consumer of a PostgreSQL event table avoid skipping events whose sequence numbers were allocated earlier but committed later, without serialising all writers on a global lock?

## Question

How can a polling or notification-woken consumer of a PostgreSQL event table avoid skipping events whose sequence numbers were allocated earlier but committed later, without serialising all writers on a global lock?

## Findings

### Why the race exists

PostgreSQL sequences are deliberately non-transactional. The official documentation says that "to avoid blocking concurrent transactions that obtain numbers from the same sequence", a value from `nextval` "is not reclaimed for re-use if the calling transaction later aborts". It also says that sequence state changes "are immediately visible to other transactions". Gaps arise from aborts, crashes and `INSERT ... ON CONFLICT`, so sequences "cannot be used to obtain 'gapless' sequences". A sequence default is evaluated when the row is written, not at commit. Two concurrent appenders can therefore draw 3 and 4 and commit 4 first. A reader that sees 1, 2 and 4 and moves its cursor to `max(seq)` skips 3 for good (Sequin).

Marten's documentation describes the other half of the problem. Most holes fill within milliseconds, but holes left by rolled-back appends or optimistic-concurrency losers never fill. Looking at the hole alone cannot tell the two apart. Advancing to the highest position seen can lose events. Waiting for the sequence to become contiguous can stall forever. Every safe design is a way to compute a **safe frontier**: a point below which no further rows can ever become visible. None of them requires writers to commit in sequence order.

Notifications do not remove the race. PostgreSQL delivers `NOTIFY` events only when the sending transaction commits, and "messages from different transactions are delivered in the order in which the transactions committed". Commit order is exactly what diverges from sequence order. A notification can therefore only tell a consumer when to run its frontier query again. Its payload must never be used as a cursor.

### Approach 1: filter on the transaction-ID visibility horizon

This is an exact technique, and writers need only one extra column. Each event row stores the top-level transaction ID of the transaction that wrote it, in an `xid8` column populated from `pg_current_xact_id()`. Readers then add the predicate `transaction_id < pg_snapshot_xmin(pg_current_snapshot())`. Oskar Dudycz's write-up orders by `transaction_id, position` and keeps a composite checkpoint. The cursor predicate reads "same transaction and later position, or a later transaction" (event-driven.io).

The guarantee comes from PostgreSQL's own definitions. A snapshot's `xmin` is the "lowest transaction ID that was still active. All transaction IDs less than `xmin` are either committed and visible, or rolled back and dead." A transaction is assigned its ID "when a transaction first writes to the database", so lower-numbered IDs started writing before higher-numbered ones. No transaction that starts writing later can obtain an ID below the current `xmin`. The set of rows below the horizon is therefore final, whatever their sequence values.

`xid8` "does not wrap around during the life of an installation". Inside a subtransaction, `pg_current_xact_id()` returns the top-level ID, and snapshots list only top-level IDs, so savepoints do not break the scheme. Writers take no locks, and the extra cost falls on the read query rather than on inserts (event-driven.io).

The caveats are real:

- **The order changes.** Events are ordered by when each transaction first wrote, not by commit time or sequence value: "our ordering guarantee respects when the transaction was started, not when the message was appended" (event-driven.io). PostgreSQL also notes that first-write order can differ from transaction start order.
- **Long transactions hold back the frontier.** Sequin rejected this approach for its access-log use case because "any long-running transaction in your system will set a ceiling" on what can be read. The horizon is the lowest *active* ID, and read-only transactions are not assigned an ID. It follows (an inference, not stated by the sources) that the frontier is held back by any open transaction that has written anything, including writes unrelated to the event table and idle-in-transaction sessions. Long-running read-only transactions do not hold it back. This costs latency, never events.
- **Stream order can invert (an inference from the ordering rule).** Suppose transaction B obtains its ID by writing elsewhere first. It then waits for transaction A, which has a higher ID, to commit version 1 of a stream, and appends version 2. The global feed ordered by transaction ID then places version 2 before version 1. Consumers that require per-stream version order need to handle this.

### Approach 2: hold at the gap until no live transaction could fill it

Marten's async daemon keeps sequence order and changes nothing on the write side. Its high water mark "advances contiguously, so it stops under any hole". Rather than waiting for a timeout, it asks whether "any transaction [is] still running that could have reserved it". While the answer is yes, the mark holds. Once no such transaction remains, "the gap is proven dead and the daemon skips the entire dead span in one step", and records the skip in `mt_high_water_skips`. It ignores its own leadership-lock connections as possible appenders.

An optional cap, `SkipStaleGapsDespiteLiveTransactionsAfter`, guards against leaked sessions that hold a transaction open forever. Past the cap the daemon skips "on a suspicion of deadness, so an append that commits inside the skipped range will never be projected". The manual `AdvanceHighWaterMarkToLatestAsync()` carries the same warning. Without the cap, this approach has the same exposure to long transactions as Approach 1. Dudycz describes high-water-mark gap detection as more expensive than filtering on transaction IDs.

### Approach 3: tolerate gaps for a bounded time

Several JVM event stores accept a bounded loss window in exchange for simplicity:

- **Pekko and Akka Persistence JDBC.** The sequence-retrieval actor retries a missing ordering number, and "the time after which a number in the sequence is assumed missing is equal to maxTries * queryDelay". The defaults are 10 tries at 1 second, so about 10 seconds. An append that commits after that window falls behind a cursor that has already passed it.
- **Axon Framework.** `GapAwareTrackingToken` stores the highest index seen "and additionally stores a set of possible gaps". The consumer can therefore move past a hole immediately and re-query the gaps, delivering late commits out of global order. The JDBC storage engine drops gaps that fall more than `maxGapOffset` behind the index (default 10,000). It also treats a gap as timed out after `gapTimeout` (default 60 seconds), cleaning gaps once a token holds more than `gapCleaningThreshold` (default 250).

Axon's design gives lower latency than holding at a gap. The cost is out-of-order delivery of late events, plus loss of any event that commits after the gap is dropped.

### Approach 4: writers register their in-flight sequence floor

Sequin describes an advisory-lock protocol that is exact and keeps sequence order without making writers queue behind each other. Each appending transaction takes a shared transaction-level advisory lock that marks it as an appender, plus an exclusive one keyed on the sequence's `last_value + 1`. That value is a lower bound on any number it can still draw. Different writers lock different keys, so they do not block one another.

The reader derives a safe ceiling from `pg_locks`, the minimum registered value among live appenders, and reads only `seq` below it. If no appenders are registered, it reads everything. The author calls the design complex. It also depends on every writer following the protocol. A limitation the author points out is that the two-argument advisory-lock functions accept only `int` keys.

### Approach 5: narrow the serialisation rather than remove it

- **Partition the lock.** Message DB's `acquire_lock` takes `pg_advisory_xact_lock` on a 64-bit hash of the stream's *category*. Writers to the same category serialise until commit, while different categories proceed in parallel. As an inference, this protects ordering for readers of a single category but not for a reader of the whole store.
- **Allocate late.** Sequin's optimisation inserts rows first and assigns the sequence value with an `UPDATE` just before commit. A serialising lock is then held only from allocation to commit, not for the whole transaction. This is still global, but much shorter.

### Approach 6: assign the global position after commit

In the transactionally staged job drain pattern, rows are written inside the business transaction. A single separate process then picks them up, because "the enqueuer is unable to see jobs that aren't yet committed". The trade-offs are that "only one enqueuer should be running at any given time", plus some added latency (brandur.org).

Adapted to an event store (an inference, not a documented implementation), writers would insert events with no global position. A single sequencer would then stamp positions on committed, unsequenced rows in its own transaction. Only one transaction ever allocates positions, so positions become visible in order, and consumers can safely use a plain position cursor. The costs are a second write per row, one sequencer cycle of latency, and a singleton process to run. That process can itself be woken by `NOTIFY`.

Logical decoding avoids the race differently. PostgreSQL states that "concurrent transactions are decoded in commit order", so a decoded stream needs no frontier computation.

### Implications for a notification-woken consumer

- Treat each notification as a hint to run the frontier-bounded query again, never as a position to advance to.
- A consumer can be blocked behind the frontier while committed rows already sit beyond it. In that case it cannot count on a later notification to free it. The blocking transaction may not be an appender, as can happen with Approach 1, or may roll back without notifying. As an inference, the consumer needs a re-check timer that runs while the frontier trails the newest committed row, alongside its notification wake-ups.
- For a single-PostgreSQL Python library, Approach 1 is the simplest exact option. It needs one `xid8` column defaulted from `pg_current_xact_id()`, a composite `(transaction_id, position)` checkpoint, and the `pg_snapshot_xmin` predicate. Its costs are a changed ordering contract and frontier lag driven by long transactions. Approaches 2 and 4 keep strict sequence-order delivery at higher read-side or protocol complexity. Approach 3 is the only family that can knowingly lose events.
