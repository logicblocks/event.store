# Does a PostgreSQL backend still registered with LISTEN whose client has silently vanished stop advancing its notification queue position, and can it fill the queue before server-side TCP keepalives terminate the session?

## Question

When a client that issued `LISTEN` disappears without closing its TCP connection (host crash, network partition, a NAT entry dropped), its server backend stays registered as a listener. Does that backend stop advancing its read position in the shared notification queue, and so stop the queue from being truncated? If so, can the queue fill up before the server's TCP keepalives detect the dead peer and end the session?

## Findings

### Short answer

It depends on whether the orphaned backend has notifications to deliver.

- **It has nothing to deliver.** If it is not listening on any channel being notified, it keeps advancing, or is advanced for it, without touching its socket. It does not hold the queue back, and TCP keepalives eventually end the session.
- **It has notifications to deliver.** This is the normal case for an event-store consumer listening on the channel the writer notifies. The backend keeps sending notifications into the dead socket until the server-side buffers fill. Then it blocks with no timeout, in the `ClientWrite` wait event. From that moment its queue position is frozen and it pins the queue tail.

In the blocked state, keepalives are not what ends the session. TCP sends keepalive probes only when the connection has no unacknowledged data, and a blocked backend always has some. What ends the session is the kernel's retransmission timeout: about 15–16 minutes on default Linux settings, or less if PostgreSQL's `tcp_user_timeout` is set.

On default settings with small payloads, one vanished listener cannot realistically fill the default 8 GB queue in that window. With large payloads, high notify rates, longer retransmission limits, or a client that is alive but not reading, it can. If the queue fills, every transaction that issued `NOTIFY` fails at commit and rolls back.

### How queue truncation depends on each listener

All notifications go into one SLRU-backed queue under `pg_notify/`. Each listening backend has its own read position. The tail, which is what can be truncated, is "the minimum of all the per-backend tail pointers" (async.c header comment). So one backend that stops advancing is enough to stop truncation for the whole cluster. Healthy listeners carry on receiving notifications, and new entries are still accepted until the queue is full.

When notifying, `SignalBackends()` decides which listeners to wake:

- **PostgreSQL 18 and earlier:** it signals every listener in the same database that isn't already caught up. It also signals listeners in other databases that are at least `QUEUE_CLEANUP_DELAY` (4) pages behind.
- **PostgreSQL 19:** commit 282b1cd ("Optimize LISTEN/NOTIFY via shared channel map and direct advancement", Joel Jacobson, January 2026) adds a shared hash table mapping channels to listening backends. If a listener "is known not to be interested and is currently stopped at the old queue head, we avoid waking it at all and just directly advance its queue pointer past the notifications we inserted." Backends far behind the head are still signalled so the tail can advance.

Either way, a woken backend with nothing to deliver reads the entries, finds none for its channels, and moves its position forward without writing to the client. So an orphaned listener that is not interested in current traffic does not hold the queue back, even before PostgreSQL 19.

### Why an interested orphan stops advancing

A woken idle backend runs `ProcessIncomingNotify()`. That calls `StartTransactionCommand()`, then `asyncQueueReadAllNotifications()`, then `CommitTransactionCommand()`, and finally `pq_flush()`. Three details of the read loop matter:

1. **The position is written back only once, at the end of the pass.** `asyncQueueProcessPageEntries()` is called in a loop until it reaches the head, advancing a *local* `pos`. Only after the loop does the code take `NotifyQueueLock` and set `QUEUE_BACKEND_POS(MyProcNumber) = pos`.
2. **Sending happens inside the loop, before that write-back.** Each page is copied into a local buffer "to avoid holding the SLRU lock while we transmit them to our frontend". Then, for each matching entry, `NotifyMyFrontEnd()` builds a `NotificationResponse` message (pid, channel, payload) with `pq_beginmessage` and `pq_endmessage`.
3. **Writes can block forever.** Messages go into the backend's 8 KB send buffer (`PQ_SEND_BUFFER_SIZE 8192`), which is flushed to the kernel when full. When the kernel socket buffer is also full, `secure_write()` waits for the socket to become writeable with `WaitEventSetWait(FeBeWaitSet, -1 /* no timeout */, ..., WAIT_EVENT_CLIENT_WRITE)`, then retries. This can loop indefinitely.

So a vanished but interested listener goes through two phases:

- **Silent-loss phase.** At first, writes succeed into the 8 KB buffer and the kernel send buffer (sized from `tcp_wmem`). The backend completes its passes and its position advances normally, but those notifications go into a dead connection and are lost. This lasts for roughly the first few hundred to few thousand messages, depending on payload size and send-buffer size.
- **Pinned phase.** Once the buffers are full, the backend sits in `ClientWrite` partway through a pass. Its shared position stays where that pass began, and the queue tail cannot move past it.

The backend also stays inside the transaction started by `ProcessIncomingNotify()`, holding the snapshot registered by `asyncQueueReadAllNotifications()` (`RegisterSnapshot(GetLatestSnapshot())`, released only at the end). An inference from the code, not stated in the documentation: such a backend would also show a non-null `backend_xmin` in `pg_stat_activity` and hold back VACUUM's cleanup horizon for as long as it is stuck.

Interrupts are handled narrowly while the write is blocked. On a latch wakeup the wait loop calls `ProcessClientWriteInterrupt(true)`, which acts only on a pending termination request. Before dying, it switches output off (`whereToSendOutput = DestNone`) so it does not block again trying to send an error to the client. So `pg_terminate_backend()` does free a stuck listener. Other timers, such as `idle_session_timeout`, are only acted on at a `CHECK_FOR_INTERRUPTS()`, which this loop reaches only when terminating. They would therefore not be expected to break the wait (an inference from the code). `client_connection_check_interval` applies only "while running queries", so it does not cover an idle listener either.

### What actually terminates the session

PostgreSQL turns on `SO_KEEPALIVE` for every accepted TCP connection (pqcomm.c). `tcp_keepalives_idle`, `tcp_keepalives_interval` and `tcp_keepalives_count` all default to 0, which means the operating system defaults. On Linux those are 7,200 s idle, then 9 probes 75 s apart. The tcp(7) man page puts that at about 2 hours 11 minutes before an idle dead connection is dropped.

These keepalive settings only govern the **idle** case: an orphan with nothing to send. It sits in `ClientRead`. When the kernel declares the peer dead, the socket reports an error, the backend's read fails, and the backend exits, unregistering as a listener.

In the **pinned** case there is unacknowledged data in flight, and keepalives do not run. Cloudflare's analysis of Linux TCP puts it directly: "For keepalives to work, the send buffer must be empty". With data in flight, the retransmission timer governs instead. `tcp_retries2` defaults to 15, which the man page describes as "approximately between 13 to 30 minutes, depending on the retransmission timeout". Cloudflare measured a connection with data in flight dying at about 940 s.

PostgreSQL's `tcp_user_timeout` setting ("the amount of time that transmitted data may remain unacknowledged before the TCP connection is forcibly closed") bounds this directly. Per the man page, it also overrides keepalive timing when both are used. It defaults to the OS default (effectively unset) and is unavailable on Windows. When TCP finally gives up, the write fails with "could not send data to client", `ClientConnectionLost` is set, and the backend exits. Since commit 1b46990 (backpatched to 14), the read loop sets `ExitOnAnyError` so that any error while delivering notifications is FATAL. The connection is dropped rather than silently skipping a notification.

On the question's own terms, the session usually ends sooner than idle keepalives would manage. An orphan that is being sent notifications dies through retransmission (about 15 minutes) rather than through keepalives (about 2 hours). But it pins the queue for that whole interval.

### Can it fill the queue in that window?

The queue holds `max_notify_queue_pages` pages (default 1,048,576 × 8 KB, about 8 GB; set at server start). Each entry takes a 16-byte header (length, database OID, xid, sender pid), plus the channel name, plus the payload, plus two terminating NUL bytes, rounded up to an `int` boundary. Entries do not span pages; pages are padded with dummy entries. Within one transaction, duplicate notifications are collapsed, so the queue grows by roughly one entry per notifying commit per distinct channel and payload.

The table below estimates how many entries fill the default queue, and the sustained rate needed to fill it during the roughly 925 s default retransmission window:

| Notification shape | Approx. entry size | Entries to fill 8 GB | Rate needed over ~925 s |
|---|---|---|---|
| No payload, short channel | 24–40 bytes | ~210–360 million | ~230,000–390,000 per second |
| ~100-byte payload | ~128 bytes | ~67 million | ~72,000 per second |
| Near the 8,000-byte payload maximum | one per page | ~1.05 million | ~1,100 per second (about 580 per second over 30 minutes) |

In my judgement, the first two rows are far above what a server sustains in notifying commits, so on default Linux settings with small payloads a single vanished listener will not fill the queue before the kernel kills its connection. The large-payload case is within reach of a busy system. The risk also grows if:

- `tcp_retries2` has been raised;
- the retransmission timeout runs towards the 30-minute end;
- the platform lacks `TCP_USER_TIMEOUT`; or
- the client is still alive but no longer reading, for example a stalled event loop.

The last case is the most dangerous. The peer then advertises a zero window and acknowledges the server's window probes. Per Cloudflare, "As long as the receiver keeps on answering, the sender will keep on sending such probes forever". Keepalives do not run in that state, so the queue could be pinned without limit. Cloudflare also notes that `TCP_USER_TIMEOUT` keeps working there but is "engaged only when the retransmission timer fires". Whether that reliably ends such a connection was not settled by these sources.

### What happens as it fills

- **At 50% full,** `asyncQueueFillWarning()` logs "NOTIFY queue is N% full" at most every 5 seconds. Its detail line is "The server process with PID %d is among those with the oldest transactions". The hint's wording ("until that process ends its current transaction") assumes the backend is in a long transaction, but the PID it names is also the right one for a backend stuck in `ClientWrite`.
- **`pg_notification_queue_usage()`** reports the occupied fraction (0–1) for monitoring.
- **When the queue is full,** `PreCommit_Notify()` raises "too many notifications in the NOTIFY queue" before the commit is recorded in the commit log. The notifying transaction rolls back. For an event store that issues `NOTIFY` in the same transaction as the append, a full queue therefore turns into failed appends, not just missed wake-ups.
- **Older minor releases had a further failure.** A listener that lagged long enough could fail with "could not access status of transaction … Could not open file pg_xact/…" once VACUUM truncated the commit log past xids still in the queue. Commit 8eeb4a0 (November 2025, backpatched to 14) makes VACUUM replace old xids in the queue with frozen or invalid values first. A follow-up commit closed a remaining race.

### Implications for an event-store consumer

- Set `tcp_user_timeout` on the server (and tighter `tcp_keepalives_*`) so that an orphaned listener with data in flight, or one idling, is cut off in seconds to minutes rather than 15 minutes to 2 hours.
- Keep `NOTIFY` payloads empty or tiny, since the durable events table is the source of truth. Small entries stretch the time to fill the queue by orders of magnitude.
- Watch `pg_notification_queue_usage()` and the 50% log warning. Also watch `pg_stat_activity` for listener backends in `ClientWrite` with a long-held `backend_xmin`, and end them with `pg_terminate_backend()`, which works even while the write is blocked.
- Treat a dropped LISTEN connection as possible lost notifications. Notifications can vanish silently into a dead socket before the server notices anything, so a consumer must catch up from its checkpoint after every reconnect.
