# Can ordering a PostgreSQL event log by writing transaction id and then position deliver a single stream's events out of version order, and how should an event store define its global order to prevent that?

## Question

Suppose an event store gives each event a `transaction_id xid8` column filled from `pg_current_xact_id()`, and orders its global feed by `(transaction_id, position)`, where `position` comes from a sequence. Can that feed deliver a single stream's events out of version order? If it can, how should the store define its global order so that every stream's version order is kept?

## Findings

### Short answer

Yes. Ordering by `(transaction_id, position)` puts events in the order in which their transactions were given an xid, which means the order in which they *first wrote*. It is not commit order, and it is not the order in which each event was appended. A stream's version order is set by which append saw the stream's head first. Under READ COMMITTED these two orders can differ. A transaction with a lower xid can append version *n+1* on top of version *n*, which a transaction with a higher xid committed. The feed then delivers *n+1* before *n*.

Both events still arrive. The usual `transaction_id < pg_snapshot_xmin(pg_current_snapshot())` filter stops events being skipped, so only their order is reversed. That still breaks any projection or aggregate consumer that assumes each stream arrives in version order.

The fix is to choose a global order that keeps every stream's version order. Commit order always does. So does a position assigned after the stream's head is checked, as long as reads are fenced by commit visibility. Alternatively, keep `(transaction_id, position)` and run appends at REPEATABLE READ, which turns the bad interleaving into a serialization failure.

### Why xid order and version order diverge

- **xids are assigned at first write, not at commit.** PostgreSQL says non-virtual xids are "assigned sequentially to transactions from a global counter … when a transaction first writes to the database". It adds that "lower-numbered xids started writing before higher-numbered xids", and that this order "might be different from the order in which the transactions started". `pg_current_xact_id()` "will assign a new one if the current transaction does not have one already". So calling it is itself enough to fix the xid early. In PostgreSQL's heap write paths, `heap_insert` and `heap_delete` take the xid (`GetCurrentTransactionId()`) before they check for, or wait on, a concurrent modifier.
- **READ COMMITTED sees commits made after the xid was taken.** Each READ COMMITTED statement sees "data committed before the query began". Two statements in one transaction "can see different data". `VOLATILE` functions, which include PL/pgSQL append functions, "obtain a fresh snapshot at the start of each query they execute". When an `UPDATE` finds its row changed by a concurrent transaction that then commits, it re-runs its `WHERE` clause against the new version of the row and updates that version.

So a transaction can hold an old xid and then build on a stream head committed by a transaction with a newer xid.

### The inverting interleaving

| Step | T1 | T2 |
|---|---|---|
| 1 | Writes anything: an event on stream A, an outbox or business row, or just calls `pg_current_xact_id()`. Gets xid 100. | |
| 2 | | Appends stream S version 5 (xid 101, position 41) and commits. |
| 3 | Reads S's head in a new statement and sees v5. Appends S v6 at position 42. | |
| 4 | Commits. | |

Ordered by `(transaction_id, position)`, the feed reads S v6 at (100, 42) and then S v5 at (101, 41). Ordered by position alone, it reads v5 (41) before v6 (42), which is the correct order for this stream. A reader using the xmin fence holds back T2's v5 while T1 is open, because xmin ≤ 100. Once T1 commits, both events pass the fence and come out as v6 and then v5.

Emmett, a production event store that uses this scheme, shows where the window opens. Its PostgreSQL append function first runs `v_transaction_id := pg_current_xact_id();`. When the caller gives no expected version, it then reads the head in a later statement (`SELECT COALESCE((SELECT stream_position FROM … ), 0) INTO v_expected_stream_position`). It calls `UPDATE … SET stream_position = v_next_stream_position WHERE … AND stream_position = v_expected_stream_position`. The TypeScript wrapper opens a transaction without setting an isolation level. Consumers read `WHERE … transaction_id < pg_snapshot_xmin(pg_current_snapshot()) ORDER BY transaction_id, global_position`, backed by an index on `(transaction_id, global_position)`. For a single append the window is the short gap between taking the xid and reading the head. When the append comes after other writes in the same transaction, the window lasts for the whole transaction.

### Which append paths are exposed

- **Exposed: any transaction that gets its xid before it reads the stream head it builds on.** This covers:
  - appends to several streams in one transaction;
  - appends made after writing outbox or read-model rows in the same transaction;
  - append functions that call `pg_current_xact_id()` before reading the head.

  A column default of `pg_current_xact_id()` does not help, because it returns the xid the transaction already holds.
- **Also exposed: blind "append at end" updates** such as `SET version = version + n` with no expected-version check. Under READ COMMITTED, a writer that blocked behind a concurrent winner re-applies its update to the winner's new row and can succeed. Because the heap paths take the xid before waiting, its xid can be older than the winner's. The window is narrow but real.
- **Safe: a single-stream append whose first write is an exact expected-version check of the head**, with nothing assigning an xid earlier. If the head is read before the xid is assigned, any version it builds on was committed by a transaction with an older xid. A writer that loses the race either fails the re-run `WHERE stream_position = expected` check or hits the unique key on `(stream_id, version)`.

Some writing on this scheme says its guarantee "respects when the transaction was started, not when the message was appended". The PostgreSQL documentation is more precise: xid order is first-write order, which can differ from start order.

### How to define a global order that keeps stream order

The rule to preserve is that the global order must keep every stream's version order. Commit order always meets this for append paths that work out the next version from the committed head. PostgreSQL has no dirty reads, so the writer of *n+1* must either see *n* committed or wait for *n*'s transaction to finish. Each of the designs below meets the rule:

1. **Commit-ordered positions from a serialised counter.** Commanded's Elixir EventStore assigns global positions by updating a single `$all` stream row: `UPDATE … streams SET stream_version = stream_version + $2 WHERE stream_id = 0 RETURNING stream_version - $2`. The row lock is held until commit, so positions are gapless and in commit order, and consumers can safely checkpoint on `position` alone. Sequin describes the same idea with a sequence table, and suggests assigning the number late in the transaction to shorten the lock. The cost is that every append on the database waits on one row lock: "Writes now funnel through updates … which must happen serially."
2. **Position as the order, commit visibility only as a fence.** A sequence default evaluated at `INSERT` time, after the head check, already keeps stream order. The fence must not be a bare `transaction_id < xmin` filter combined with a position checkpoint. That combination can skip a lower position that commits after a higher one has been read. Better fences:
   - **PgQ-style snapshot batches.** PgQ selects events whose transaction is visible in a later tick snapshot but not an earlier one: `NOT txid_visible_in_snapshot(ev_txid, sn1) AND txid_visible_in_snapshot(ev_txid, sn2)`. Inside a batch it orders by event id. Version *n* commits before *n+1*, so it lands in the same batch or an earlier one, and position order inside a batch keeps the stream's order. Consumers checkpoint on ticks.
   - **Marten's high-water mark.** The mark advances in position order and "stops under any hole" while a transaction that could fill the hole is still alive. Its optional stale-gap skip warns that "an append that commits inside the skipped range will never be projected".
   - **Sequin's advisory-lock fence.** Readers find the lowest sequence value still held by an in-flight writer.
3. **Keep `(transaction_id, position)` and run appends at REPEATABLE READ or SERIALIZABLE**, checking the head inside the transaction. A REPEATABLE READ snapshot is taken "as of the start of the first non-transaction-control statement", which is no later than xid assignment. A transaction with a higher xid got it later and committed later still, so the lower-xid transaction cannot see it. If it tries to update that stream's head row it gets `could not serialize access due to concurrent update`. If it inserts the same version it hits the unique key. Either way it must retry, and the retry gets a newer xid, so the inversion cannot commit.

   The costs:
   - retries on contended or multi-stream transactions;
   - the requirement that the expected version is checked against the transaction's own snapshot, not just trusted from the caller;
   - the xmin fence's existing ceiling, which Sequin describes: "if you have a transaction running against another table for two minutes, your cursor/query will be unable to read the last two minutes".
4. **Commit order from logical decoding.** "Concurrent transactions are decoded in commit order", and rolled-back ones "never get decoded". A decoder can therefore stamp a commit-ordered position, at the cost of running decoding infrastructure.

### Implications for a psycopg 3 event store

Ordering by `(transaction_id, position)` is safe from skipping but not from reordering. A library adopting it should do one of two things:

- run append transactions at REPEATABLE READ and treat serialization failures as retryable concurrency conflicts; or
- guarantee that the expected-version head check is the first write in every append transaction, never call `pg_current_xact_id()` before it, and forbid multi-stream or mixed business-and-event transactions.

If commit-ordered or fenced position ordering is preferred, options 1 and 2 avoid the problem by design. Reads of a single stream ordered by version are unaffected either way, since only the global and category feeds can invert. As a defensive check, a consumer that needs per-stream order can verify version continuity and fail loudly on a gap, rather than silently applying events out of order.
