# Does a PgDog transaction-mode client receive any error or signal when PgDog's dedicated pub-sub listener connection drops and reconnects, and how long is the notification gap during a PgDog restart or rolling deploy?

## Question

When PgDog's single dedicated Postgres connection drops, does a PgDog transaction-mode client get any error, notice or other signal? That connection carries LISTEN registrations and notifications for all its clients. And how long are notifications missed when PgDog itself is restarted or rolled during a deploy?

## Findings

### Short answer

**When the dedicated connection drops, the client gets no signal.** It gets no error, notice or other in-band message. Its own connection to PgDog stays open, and PgDog still records its subscriptions. Notifications committed while the dedicated connection is down are simply never delivered. PgDog's documentation calls this at-most-once delivery with no redelivery.

**PgDog shutting down is the opposite case.** On SIGINT or SIGTERM, any client not in a transaction is disconnected immediately with `FATAL 57P01 "PgDog is shutting down"`, and a LISTEN-only client counts as not in a transaction. That is a clear signal.

**PgDog publishes no figure for the restart or deploy gap.** From the code, the gap runs from that disconnect until two things have happened:
- the client has reconnected through a live PgDog instance and re-issued LISTEN;
- that instance's dedicated connection has registered the channel with Postgres.

Nothing in Postgres or PgDog buffers notifications across that window.

**Reconnection after a drop may not be automatic.** The code as published appears not to re-establish a dropped dedicated connection by itself. Instead it seems to wait for the next RELOAD, RECONNECT, replica promotion or PgDog restart. That reading is unverified (see below).

### What PgDog documents

PgDog's pub/sub feature works like this:
- PgDog uses "a dedicated server connection" to register with Postgres on clients' behalf. It registers each channel only once, however many clients listen on it.
- NOTIFY is placed "into an asynchronous queue" and forwarded over that connection. The notification returned by Postgres is then fanned out to all registered clients.
- A NOTIFY inside a transaction is buffered until commit, and dropped on rollback.

The delivery guarantees section says:
- LISTEN and UNLISTEN "are guaranteed to be delivered".
- "A NOTIFY message can be lost if the dedicated connection to Postgres is broken. PgDog will not attempt re-delivery for a message on connection error."
- The model is "at most once", and "Upon reconnection, all subsequent messages will be delivered over the new connection."

The documentation says nothing about telling clients that a loss happened. The feature is enabled by `pub_sub_channel_size`, which sizes the background queue.

### Why the client sees nothing when the dedicated connection drops

The PgDog source (main branch; `listener.rs` last changed 26 August 2026) shows why no signal reaches clients.

- **Connection setup.** The listener task opens its connection with `pool.standalone(ConnectReason::PubSub)`, outside normal pool checkout. On connect it re-sends LISTEN for every channel in an in-memory map of channels to subscribers. It then loops over server messages and queued client requests. Any read or send error ends that run with an error.
- **Error handling only logs.** The error branch logs `pub/sub error: {err} [{addr}]` at error level and sleeps for `connect_attempt_delay`. Nothing is sent towards clients.
- **Subscribers never see a closed channel.** Each channel's `broadcast` sender lives in a shared map keyed by pool, and that map survives the error, so receivers never see a closed channel. Each client's forwarding task handles a lagged receiver by counting a dropped message. It handles a closed channel by exiting quietly. No path turns a listener error into a client message.
- **The only client-visible failure is unrelated.** A client's backend connection waits on both pub/sub messages and server messages. It errors (`ProtocolOutOfSync`) only if its whole per-client notification queue closes. A dedicated-connection drop never causes that, because the senders persist.
- **Operators get only logs and counters.** They have the error log line and the `SHOW LISTENERS` admin command (listeners, messages received, messages dropped), also exported as OpenMetrics. There is no reconnect counter. The "dropped" count covers slow (lagged) receivers, not messages lost during an outage.
- **A successful LISTEN proves nothing.** PgDog sends a synthetic `LISTEN` CommandComplete as soon as it has queued the subscribe request, before Postgres has run LISTEN. If another client already listens on the channel, no Postgres LISTEN is sent at all. `listen()` also succeeds while the dedicated connection is down. NOTIFY sent through PgDog outside a transaction is acknowledged the same way, once queued.

### Reconnection may not happen on its own (code reading, unverified)

The documentation implies that PgDog reconnects automatically. The code reads differently.

- **The loop waits for a start signal every time.** The listener's background loop waits on `comms.start.notified()` (a Tokio `Notify`) at the top of every iteration, before trying to connect. The only call that sends that signal is `launch()`, via `notify_one`.
- **`launch()` runs once per listener.** Each new listener gets exactly one `launch()`, when the shard is launched, and `init_pub_sub` creates a fresh listener each time. That happens at startup, when RELOAD or SIGHUP and RECONNECT rebuild the clusters, and when a replica is promoted to primary.
- **Nothing signals start after a failure.** After a failed run the loop sleeps `connect_attempt_delay` (default 0 ms; PgDog's timer helper treats zero as a real zero-length sleep). It then waits for a start signal that nothing sends. Nothing else calls `launch()`: no timer and no health-check recovery path.

Read literally, a listener whose connection drops mid-life stays dormant until the next RELOAD, RECONNECT, promotion or PgDog restart. Causes include a Postgres restart, `pg_terminate_backend`, a network fault, or a failed first connection at startup. Meanwhile clients stay connected and silently receive nothing.

Two further effects follow from the code (inferences):
- While the listener is dormant, NOTIFYs sent through PgDog sit in the request queue and are never forwarded.
- That queue is bounded by `pub_sub_channel_size`. Once it is full, further LISTEN and NOTIFY calls would wait for space.

None of this has been checked by running PgDog, and the listener file has no reconnect test. It conflicts with the documentation's "Upon reconnection" wording, so it should be tested before anyone relies on it either way.

### PgDog restart or rolling deploy

**Shutdown sequence.** SIGINT and SIGTERM are handled the same way:
1. PgDog stops accepting connections and signals every client.
2. It waits up to `shutdown_timeout` (default 60 s) for clients to finish their transactions.
3. It optionally cancels remaining queries within `shutdown_termination_timeout`.
4. Only then does it shut down the databases, including the pub/sub listeners.

**Idle listeners are cut immediately.** At the top of each loop iteration, each client checks whether it is idle and the pooler is going offline. Idle means no buffered transaction and no checked-out or locked server connection; LISTEN subscriptions are not counted. A LISTEN-only client is therefore disconnected straight away with FATAL 57P01, which a psycopg 3 `notifies()` loop sees as a connection error. Clients mid-transaction stay connected until they finish, and keep receiving notifications meanwhile, because the listeners are shut down last.

**What makes up the gap.** Postgres keeps no backlog for sessions that are not listening, and PgDog keeps none across connections. The gap therefore lasts from the 57P01 until the new instance's dedicated connection has the channel registered with Postgres. Its parts are:
- the client's reconnect delay or backoff, plus routing to a live instance (the terminating instance refuses new connections);
- registration on the new instance:
  - immediate, in memory, if that instance already listens on the channel for other clients;
  - otherwise one LISTEN sent over its dedicated connection;
  - on a freshly started instance, first establishing the dedicated connection (bounded by `connect_timeout`, default 5 s).

**Typical size of the gap (estimate, not published).** With several instances and a client that reconnects promptly, the gap is probably from sub-second to a few seconds. For a single instance restarted in place, it is at least the full PgDog restart time plus the client's reconnect delay.

**RELOAD is different.** The documentation says RELOAD keeps client and server connections. A change made in August 2025 lets the pub/sub listener survive RELOAD and RECONNECT: a new listener is created, re-subscribes every channel in the shared map, and the old one is shut down. Any window around that swap is not documented or measured.

### Implications for a psycopg 3 event-store consumer behind PgDog

- **Treat notifications as a wake-up hint only.** The client gets no signal when the dedicated connection drops, so a periodic catch-up poll from the last processed position must remain the correctness path. The poll interval sets the worst-case latency of a silent outage.
- **Catch up after every disconnect.** After a 57P01 or any other disconnect, reconnect, re-issue LISTEN, then read from the last processed position.
- **Expect a small race the poll must cover.** The LISTEN acknowledgement is synthetic, so the catch-up read can run before Postgres has registered the LISTEN. The fallback poll covers events committed in that window.
- **Detect a silent outage with a heartbeat (design inference).** The consumer can periodically send a NOTIFY on a private channel through PgDog and watch for it to come back. A NOTIFY through PgDog travels over the same dedicated connection, so a missing echo exposes both a dropped listener and a dormant one.
