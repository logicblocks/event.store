# At what write rates and listener counts does issuing NOTIFY on every appending transaction become a bottleneck for a PostgreSQL event store, and how far do constant payloads, sender-side debouncing or the PostgreSQL 19 listener-tracking change reduce that cost?

## Question

If every appending transaction in a PostgreSQL event store issues `NOTIFY`, at what write rate and how many listeners does that become the bottleneck? And how much of the cost goes away with each of three mitigations: a constant (or empty) payload, debouncing on the sender side, and the listener-tracking rework that ships in PostgreSQL 19?

## Findings

### Two different costs

Per-append `NOTIFY` costs the system in two separate ways, and they grow with different things. The first is **commit serialisation**, which grows with the number of *notifying transactions* per second. The second is **listener fan-out**, which grows with the number of *listening backends*. Each mitigation helps with at most one of them, so it matters which one is limiting you.

### Cost 1: the global commit lock (grows with write rate)

At commit, PostgreSQL's `PreCommit_Notify` takes a heavyweight lock. Production reports show it as `AccessExclusiveLock on object 0 of class 1262 of database 0`. The source comment explains why: "Serialize writers by acquiring a special lock that we hold till after commit. This ensures that queue entries appear in commit order". The lock is on a shared object (database 0), so it serialises notifying commits across the whole cluster, not just one database. A documentation proposal on pgsql-hackers described it the same way.

The lock is held until the commit is durable. One patch author put it this way: "each must become durable before the next can proceed". Two consequences follow:

- Notifying transactions run one at a time through the WAL flush.
- They lose the benefit of group commit, where one flush covers many concurrent commits.

So the ceiling on notifying commits is roughly the inverse of how long the lock is held, and that is dominated by commit-flush latency. Transactions that never execute `NOTIFY` are not affected.

The measurements line up with this:

- **pgbench, 100 clients, no listeners** (Arseniy Mukhin, Oct 2025, on master):
  - `INSERT` alone: 30,982 TPS
  - the same `INSERT` plus `NOTIFY`: **818 TPS**, about a 38× collapse
  - a `NOTIFY`-only transaction: 87,751 TPS

  Pure-`NOTIFY` benchmarks therefore look fast. The cost shows up when the notifying transaction also writes data that must be flushed, which is exactly what an event-store append does. 818 TPS works out to about 1.2 ms per serialised commit. That is consistent with one WAL flush per commit, but this is an inference.
- **pgbench, 1,000 clients, one listener** (Joel Jacobson, Jul 2025): 7,679 TPS while preserving commit order (with the lock), against 95,430 TPS with the lock removed in a prototype.
- **DBOS streams.** A trigger fired `NOTIFY` on every stream-chunk write, in the same transaction. On "a large Postgres database" it "could not sustain more than 2.9K stream writes per second". DBOS reports that the limit appeared "without visibly consuming any Postgres resource".
- **Recall.ai production incident.** Tens of thousands of concurrent writers issued `NOTIFY` on update. They saw lock waits above 1,000 ms and hundreds of sessions queued. CPU, I/O and network usage *fell* while load rose, which points to contention on a global mutex rather than resource exhaustion.

**Where the threshold sits.** The limit is a rate of notifying commits, not a fixed number. It is reached when that rate approaches 1 ÷ (commit-flush time):

- hundreds per second on slower durable storage;
- around 800 in the pgbench run above;
- about 3,000 in the DBOS setup.

Queueing delay grows well before full saturation, so latency degrades first under bursts from many concurrent writers.

Anything that lengthens the commit while the lock is held should lower the ceiling further. Synchronous standby acknowledgement is the obvious case. That is an inference from where the lock is released; no source measured it.

### Cost 2: waking listeners (grows with listener count)

Before PostgreSQL 19, PostgreSQL did not track which backend listened on which channel. On every notifying commit, `SignalBackends()` sent a `kill(pid, SIGUSR1)` to every listening backend in the same database. Jacobson's ping-pong benchmark, with two active connections and a growing number of idle listeners on master, shows the effect:

| Extra idle listeners | Throughput (TPS) |
|---|---|
| 0 | 9,126 |
| 10 | 6,233 |
| 100 | 2,020 |
| 1,000 | 238 |

A later round-trip benchmark showed the same trend: 1,351 round-trips per second with 10 idle listeners, falling to 516 with 97.

Jacobson first argued that these signals, not the lock, were the bottleneck. With a pure `NOTIFY`-plus-`LISTEN` workload, removing the commit-order lock gained only about 14%. He later retracted this ("This is much more complex than I initially thought") after the 1,000-writer test showed the lock dominating.

The practical rule:

- **Many writers, few listeners:** the lock is the limit.
- **Many listeners:** the signalling cost dominates, and it scales linearly. Each idle listener costs throughput even at modest write rates.

### Constant or empty payloads

The `NOTIFY` documentation says repeated notifications on the same channel with the same payload *within one transaction* are delivered once. Notifications with distinct payloads are always delivered separately, and notifications from different transactions "will never get folded into one notification". Duplicate checks use a hash table once a transaction has 16 or more pending notifications (`MIN_HASHABLE_NOTIFIES 16`).

For an event store, this means:

- A row-level trigger that sends a constant payload produces one queue entry per *transaction*, not one per *event*. That shrinks queue volume and listener reading work for multi-event appends.
- It does **nothing** for the commit lock. The transaction still notifies, so it still takes the lock.
- For single-event appends, the most common case, a constant payload barely affects the bottleneck.
- It does not reduce signalling cost either, because signals are sent per notifying commit.

### Sender-side debouncing

Debouncing is the most effective lever, because only transactions that actually execute `NOTIFY` take the lock. It caps the rate of notifying commits regardless of the append rate. Two shapes appear in practice.

- **Batching outside the write transaction (DBOS).** Writes stopped issuing `NOTIFY` themselves. Notifications are buffered in memory and "periodically flush[ed]… in a single batch transaction", so the global lock is taken once per flush rather than once per write. Readers also poll occasionally to catch writes whose notification was lost in a crash. Results:
  - 2.9K → **60K writes per second**, about 20×;
  - latency of 15–100 ms;
  - the bottleneck became Postgres CPU saturation instead of lock contention.
- **Per-queue rate limiting (River, a Go job queue).** On insert, River's client checks a per-queue limiter. It emits a `{"queue": …}` notification only if that queue has not been notified within `FetchCooldown`. The limiter's comment says it calls the notify function "no more than once per waitDuration". Defaults:
  - `FetchCooldown` is 100 ms (minimum 1 ms), so each client process sends at most about 10 notifications per second per queue;
  - a `FetchPollInterval` of 1 s acts as a fallback poll.

  The limiter lives inside each process, so the total notify rate is roughly processes × queues ÷ cooldown.

What debouncing costs:

- Wake-up latency grows by up to the debounce window.
- A limiter that fires only on the first write in a window can stay silent for the last append in a burst. Correctness then depends on a trailing notification or a fallback poll. Both systems above keep a poll for exactly this reason.
- Because the notification only acts as a wake-up hint over a log the consumer reads by position, merging several notifications into one is otherwise harmless.

Recall.ai went further and removed `NOTIFY` entirely, moving the logic into the application.

### The PostgreSQL 19 listener-tracking change

Tom Lane committed Joel Jacobson's patch "Optimize LISTEN/NOTIFY via shared channel map and direct advancement" on 2026-01-15 (`282b1cde9`). The PostgreSQL 19 release notes describe it as "Improve NOTIFY to only wake up backends that are listening to specified notifications". It does two things:

1. A shared hash table records which backends listen on each channel, identified by database and channel name. Only interested listeners are signalled.
2. A listener that is not interested and is parked at the old queue head is moved past the new entries directly, without being woken.

The commit message claims "integer multiples" of `NOTIFY` throughput and lower latency "when there are many listeners but only a few are interested in any specific message". An early single-listener prototype held about 8,937 TPS with 1,000 idle listeners, against 238 TPS on master.

Its limits for an event store:

- **One shared channel gets nothing.** The commit message states: "There is no improvement for the simplest case where every listener reads every message". A single global channel that every consumer listens on is exactly that case.
- **Per-category or per-stream channels do benefit**, when each consumer listens on only a subset.
- **The commit lock is untouched.** DBOS notes the patch "does not remove the global lock or fix the bottleneck we observed". The write-rate ceiling from cost 1 is the same in PostgreSQL 19.

### Proposals not in PostgreSQL 19

Two other approaches were tried on pgsql-hackers. Neither appears in the PostgreSQL 19 release notes.

- **Writing notifications through WAL** (Rishu Bagga, Sept 2025, following a design sketched by Tom Lane). Notification data goes into WAL outside the lock, and the lock is held only to add a small fixed-size queue entry.
  - Benchmarks: `INSERT` plus `NOTIFY` rose from 818 to about 33,800 TPS, but `NOTIFY`-only fell from 87,751 to about 34–36K TPS.
  - Reviewers raised MVCC-visibility and WAL-retention concerns.
  - Its review status was last checked through the November 2025 thread; it may have moved since.
- **An out-of-order delivery setting** (Jacobson). Benchmarks showed +125% for `NOTIFY`-only and +14% for `LISTEN` plus `NOTIFY`.

### Summary for an event store

- **When per-append `NOTIFY` is fine:** low hundreds of appending transactions per second with a handful of listeners.
- **When it becomes the limit:** when appending commits approach the inverse of commit-flush latency (hundreds to low thousands per second), or earlier under bursts from many concurrent writers.
- **Listener count:** on PostgreSQL before 19, every extra listener in the database adds per-commit signalling cost. At 100 listeners, notify throughput drops roughly 4.5×; at 1,000, about 38×.
- **Mitigations, from most to least effective:**
  1. Sender-side debouncing or batching, which caps notifying commits regardless of append rate and needs a fallback poll.
  2. PostgreSQL 19 tracking, which only helps many listeners on distinct channels.
  3. Constant payloads, which only help multi-event transactions and do nothing for the lock.

Keeping the number of listening connections small helps on every version. One approach is a single listening connection per process that hands notifications to in-process consumers. This is a design inference, not something measured here.
