# Which Python clients can consume pgoutput logical replication asynchronously alongside a psycopg 3 application today, and how mature and maintained are they for production use?

## Question

Which Python PostgreSQL clients can consume the built-in `pgoutput` logical
replication stream asynchronously, in a process that otherwise uses psycopg 3,
and how mature and well maintained is each one for production use as of
October 2026?

## Findings

### Summary

As of October 2026 no Python library offers a mature, maintained,
asyncio-native `pgoutput` consumer. The only mature implementation of the
replication protocol in Python is psycopg2's replication cursor. It works
with non-blocking connections and can be driven from an asyncio event loop,
but it does not decode `pgoutput` messages. psycopg 3, asyncpg and psqlpy have
no replication API. The async and decoder projects built on top of them are
either unmerged or prototypes. A team that needs this today has three
realistic options:

1. Wrap psycopg2's replication cursor in an asyncio adapter and write its own
   `pgoutput` decoder.
2. Drive the replication stream through psycopg 3's low-level libpq bindings,
   which is a do-it-yourself approach with no supported API.
3. Skip the streaming protocol and poll the slot over SQL with psycopg 3's
   async connection. This is fully supported, but it is polling rather than
   push.

### psycopg2: mature protocol support, async-capable, no pgoutput decoder

psycopg2 added replication protocol support in 2.7, extended it with
`ReplicationCursor`, `start_replication()` and `consume_stream()` in 2.8, and
added interval-based automatic keepalives in 2.8.3. It provides:

- **Connection factory.** Opening a connection with the
  `LogicalReplicationConnection` factory creates a replication connection.
- **`start_replication()`.** This takes a slot name, a `slot_type`, an
  `options` dictionary passed to the output plugin, a `decode` flag and a
  `status_interval` of at least one second.
- **Two ways to consume.**
  - `consume_stream()` handles incoming messages and keepalive replies for
    you, but "can only be used with synchronous connection".
  - For asynchronous connections, the documentation says to call
    `read_message()` in a loop. That call tries "to read the next message
    from the server without blocking" and returns `None` when nothing is
    buffered.
- **Socket access.** The cursor exposes `fileno()`, so a program can wait on
  the socket alongside other sockets.
- **Feedback.** `send_feedback()` reports the flushed LSN, with `force` and
  `reply` flags. The cursor also tracks `feedback_timestamp` and
  `io_timestamp`.

The documentation's own non-blocking example loops over `read_message()`,
calls `send_feedback(flush_lsn=msg.data_start)` after handling each message,
and uses `select()` with a timeout taken from `status_interval` and
`feedback_timestamp`. In asyncio, the same pattern maps onto registering the
cursor's file descriptor as a reader on the event loop. That mapping is an
inference: the documentation shows only `select()`.

For `pgoutput`, which is a binary plugin, the plugin options are
`proto_version` and `publication_names`. Messages must not be text-decoded.
dlt's production `pg_replication` source does exactly this: it imports
`LogicalReplicationConnection`, `ReplicationCursor` and `StopReplication`
from `psycopg2.extras`, calls `start_replication(..., decode=False)`, and
parses `pgoutput` bytes with its own vendored `decoders` module.

On maintenance, the psycopg2 README states that the package "is still widely
used and actively maintained, but it is not expected to receive new
features". It also says that new projects "should probably start from 3".
Release 2.9.13 was uploaded on 9 September 2026 and supports Python 3.10 to
3.15, so it remains a dependable foundation. However, any replication
improvements will not come from psycopg2.

Using it alongside psycopg 3 means a second driver dependency, with its own
type adaptation, used only for the replication connection. psycopg2 decodes
nothing inside `pgoutput` payloads, so the application decodes column values
itself.

### aiopg: replication support exists only as a long-unmerged pull request

aiopg is the asyncio wrapper around psycopg2. Its open issue 287 (2017)
reports that passing `LogicalReplicationConnection` as `connection_factory`
fails.

Pull request 880, opened in August 2021, adds logical and physical streaming
replication. It passes the psycopg2 replication factories through aiopg's
`connect()` and adds an asynchronous `message_stream()` generator. Its author
says it was "extensively battle-tested in a production environment", but
that claim is the author's own and has not been independently checked. The
pull request is still open and unmerged, with a "dirty" merge state, and was
last updated in June 2026.

aiopg's last release on PyPI is 1.4.0, from 26 October 2022. It is not a
viable dependency for this feature, although pull request 880 is a useful
reference design for an async wrapper around psycopg2.

### psycopg 3: START_REPLICATION runs, but there is no consumption API

psycopg 3 has no replication API:

- **Issue 71 ("Replication support").** This was opened in August 2021 and
  is still open. In June 2023 the maintainer wrote that replication "is not
  implemented in psycopg 3. It needs complete redesign and implementation …
  it is a major work."
- **Pull request 1219 (merged 24 November 2025).** This change, titled
  "Don't fail on commands returning COPY_BOTH results", shipped in psycopg
  3.3. It means that `START_REPLICATION SLOT … LOGICAL 0/0 (proto_version
  '1', publication_names '…')` can be executed on a connection opened with
  `replication="database"` and `autocommit=True` without raising "COPY
  cannot be used with this method". The maintainer said at the time: "No
  further replication support is planned for release 3.3." The change is not
  listed in the 3.3 release notes.
- **What is left to the application.** After `START_REPLICATION`, the
  COPY-both stream has to be driven through the low-level `psycopg.pq`
  `PGconn` object. Its protocol defines `socket`, `consume_input()`,
  `is_busy()`, a `nonblocking` property, `flush()`,
  `get_copy_data(async_)`, `put_copy_data()` and `put_copy_end()`. The
  `psycopg.pq` reference page still says "TODO finish documentation".
- **Community bridge proof of concept.** Posted on issue 71 in October 2025,
  it takes direct control of the socket once COPY_BOTH is established. It
  later added reconnection with exponential backoff, LSN tracking across
  reconnects and keepalive handling. Its author reports "9 concurrent
  replication consumers" in production, which is again unverified. The
  maintainer ran it successfully on PostgreSQL 17, but it "didn't work with
  Postgres 15".
- **Pull request 1311 (May 2026).** A contributor proposed a fuller
  replication connection: a `pgoutput` decoder with logical row factories,
  a `test_decoding` decoder and partial C acceleration. The maintainer
  closed it the same day without merging. He said he already had "in
  progress some work to add replication support to Psycopg 3" with a
  different, "more advanced and much simpler to use" design, "disclosed in
  the upcoming weeks".
- **No announcement since.** On 27 July 2026 a user asked whether that had
  happened. psycopg.org's articles through August 2026 contain no
  replication announcement. The latest release is 3.3.6, uploaded on 18
  September 2026, and its release notes do not mention replication.

In practice, first-party asynchronous `pgoutput` support in psycopg 3 is
being worked on but has not been released or specified. Building on
`psycopg.pq` today means owning the protocol framing, keepalives and
feedback, and possibly reworking that code when the official API arrives.

### asyncpg and psqlpy: no replication protocol

asyncpg issue 91, "Add support for logical replication protocol", has been
open since March 2017 and has had no comments since August 2022. In it the
maintainer suggested running the replication commands as SQL. He also
suggested polling `pg_logical_slot_get_changes()` from an asyncio task, and
said only that they "may potentially look into implementing support for the
replication protocol".

psqlpy, a Rust-based async driver for Python, does not mention replication
in its README. A search of its issue tracker for "replication" returns no
results.

### pgoutput decoders: prototypes and vendored code

`pgoutput` is a binary format. Before the first change to a table, the
server sends a Relation message describing that table, and clients must cache
it before they can decode Insert, Update or Delete messages. The protocol
versions depend on the server:

| `proto_version` | Minimum server | What it adds |
|---|---|---|
| 1 | Any | Base version |
| 2 | 14 | Streaming of large in-progress transactions |
| 3 | 15 | Two-phase commit |
| 4 | 16 | Parallel streaming |

Other options are `binary`, `messages`, `streaming`, `two_phase` and
`origin`.

The Python decoders available today are:

- **pypgoutput** (PyPI 0.0.3, February 2022; last push April 2024). It
  depends on psycopg2 and Pydantic, was developed against PostgreSQL 12, and
  its README warns: "this is a prototype and not production tested".
- **dlt's vendored `decoders` module.** It is maintained as part of dlt's
  verified sources, but it is not a standalone library. dlt's consumer is a
  batch extractor rather than a live tail: it stops the stream with
  `StopReplication` and advances the slot with `pg_replication_slot_advance()`
  instead of `send_feedback()`.
- **Other Python `pgoutput` repositories on GitHub.** These are demos or
  personal projects with zero to about twenty stars.

For an event store that only needs Inserts into one append-only table, the
decoding needed is small: Begin, Relation, Insert and Commit, plus Type
messages for non-built-in types. Writing it in-house is feasible.

### Fully supported psycopg 3 alternative: polling pgoutput over SQL

`pgoutput` can be read over an ordinary connection through
`pg_logical_slot_get_binary_changes()` and
`pg_logical_slot_peek_binary_changes()`, which return `bytea`. PostgreSQL's
own subscription test suite calls
`pg_logical_slot_peek_binary_changes('tap_sub', NULL, NULL, 'proto_version',
'1', 'publication_names', 'tap_pub', 'messages', 'true')`. That works
unchanged from a psycopg 3 `AsyncConnection`.

How the slot behaves over SQL:

- **Consuming versus peeking.** `get` consumes changes from the slot's last
  consumed point. `peek` leaves them in place, and is paired with
  `pg_replication_slot_advance()` for at-least-once handling.
- **Advance is not durable straight away.** An advanced position is written
  "at the next checkpoint", so after a crash "the slot may return to an
  earlier position", which causes redelivery.
- **Temporary slots.** A slot created with `temporary` set to true belongs
  to the session and is "released upon any error".
- **Batch size.** The `upto_nchanges` argument is checked only after each
  committed transaction is decoded, so a call can return more rows than
  asked for.

This is polling, not push. It removes the second driver but keeps a polling
interval, so it gives up the latency benefit that motivates streaming
replication. The streaming commands themselves (`CREATE_REPLICATION_SLOT`,
`START_REPLICATION`) are "only available over replication connections".

### Production-readiness ranking

Ordered by how ready each option is for production today:

1. **psycopg2 replication cursor plus an in-house decoder.** Mature and
   maintained for bug fixes. It is async-capable through `read_message()` and
   the file descriptor, but it means a second driver.
2. **SQL polling through psycopg 3.** Fully supported, but not push.
3. **psycopg 3 low-level libpq bridge.** It works on recent servers and
   avoids a second driver, but it is undocumented, unsupported and likely to
   be replaced by the maintainer's forthcoming API.
4. **aiopg pull request 880, pypgoutput, asyncpg and psqlpy.** Unmerged,
   prototype, or no support at all.

Keeping the replication consumer behind a narrow adapter would let the first
or third option be swapped for psycopg 3's official API once it is released.
