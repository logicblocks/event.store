# How much does the PostgreSQL 19 change to NOTIFY listener signalling improve append throughput when many concurrent appending transactions each notify, and how much commit serialization remains from the database-wide lock?

## Question

How much does the PostgreSQL 19 change to NOTIFY listener signalling improve
append throughput when many concurrent appending transactions each notify? And
how much commit serialization still comes from the lock that NOTIFY takes at
commit?

## Findings

**Short answer.** PostgreSQL 19 changes who gets woken after a NOTIFY. It does
not change the lock that NOTIFY-ing transactions hold while they commit. The
gains are large, often 10x to 40x, when many listening backends exist and only
a few care about each message. When every listener reads every message, the
commit message reports no improvement. For an event store whose appending
transactions write rows and also NOTIFY, the main cost is the commit-time
lock, and it stays. That lock is cluster-wide, not database-wide. It is held
across the commit record's WAL flush, and also across the synchronous-replication
wait when one applies. So appends that each notify still commit one at a time.
On master before the change, 100 clients running INSERT plus NOTIFY reached
about 818 TPS, against about 31,000 TPS for INSERT alone. Nothing merged into
PostgreSQL 19 removes that gap.

### What PostgreSQL 19 changed

Commit 282b1cd, "Optimize LISTEN/NOTIFY via shared channel map and direct
advancement", was written by Joel Jacobson and committed by Tom Lane on
2026-01-15. The PostgreSQL 19 release notes list it as "Improve NOTIFY to only
wake up backends that are listening to specified notifications … Previously
most backends were woken by NOTIFY." The commit makes three changes:

- **Per-channel listener map.** A shared dynamic hash table maps (database OID,
  channel name) to listening processes. A notifier signals only the listeners
  on the channels it notified. Before, the only filter was whether a listener
  was in another database.
- **Direct advancement.** A listener that does not care about the new entries
  and is parked at the old queue head is not woken. The notifier simply moves
  that listener's queue pointer past the entries it just wrote.
- **Signal coalescing.** Each listener's queue slot has a `wakeupPending`
  flag. A listener that has already been signalled but has not yet read the
  queue is skipped ("already signaled, no need to repeat").

Compare `SignalBackends()` in PostgreSQL 18. On every NOTIFY-ing commit it
scans all listeners while holding `NotifyQueueLock`, and signals every
same-database listener that is not fully caught up. It has no channel filter
and no coalescing.

A later fix, 0f24332 (2026-05-27, "Fix NOTIFY wakeups for pre-commit LISTEN
entries"), closed a window in the new code. Direct advancement could make a
listener whose LISTEN had not yet committed miss messages. PostgreSQL 19
deployments should therefore run a build that includes this fix.

### Measured gains, and where they apply

- **Many uninterested listeners.** Jacobson's early ping-pong benchmark
  measured master at 9,126, 6,233, 2,020 and 238 TPS with 0, 10, 100 and 1,000
  extra listeners on other channels. The patched build stayed flat at
  9,152–8,937 TPS. With no extra listeners there was no difference.
- **Many concurrent notifiers, one listener per channel.** Tom Lane tested the
  committed version (v35) on an Intel Xeon W-2245 running RHEL 8. The test
  used 1,000 channels, each with one notifier connection and one listener
  connection, with senders rate-limited. Pre-patch HEAD moved 1,565
  messages/s, and 99.3% of them arrived more than 100 ms late (average 253 ms).
  v35 moved 19,966 messages/s, and about 80% arrived within 0.1 ms. Unthrottled,
  v35 reached about 95,000 messages/s on 100 channels. On 1,000 channels it
  reached about 36,000/s, with an average latency of about 28 ms. Lane said
  pre-patch HEAD was "not in the same league". Profiling showed that
  notify-specific code was only 10–15% of runtime. Lane took this as a reason
  to "minimiz[e] process wakeups rather than trying to optimize anything more
  in the notify processing itself."
- **Every listener interested in every message.** The commit message says
  "There is no improvement for the simplest case where every listener reads
  every message." An earlier variant in the same patch series used an atomic
  state machine to suppress redundant signals. It was tested with one listener
  and pure NOTIFY transactions on a MacBook Pro M3 Max. Master collapsed from
  177,351 TPS at 4 clients to 35,000–41,000 TPS at 16–128 clients. The variant
  held 121,000–165,000 TPS. That design was not committed. The committed code
  has a simpler `wakeupPending` flag, and no published measurement of it for
  this one-channel, many-notifier shape was found.

All of these benchmarks use transactions that only NOTIFY. Such a transaction
writes no WAL except its commit record, so it commits asynchronously. The
measurements therefore exclude the cost that dominates real appends.

### The serialization that remains

`PreCommit_Notify()` in current master still calls
`LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)`. The
comment there reads: "Serialize writers by acquiring a special lock that we
hold till after commit. This ensures that queue entries appear in commit order
…". The lock is on "database 0", and the file header says "all writers
serialize on a cluster-wide heavyweight lock". As a result, NOTIFY-ing commits
in different databases of the same cluster also queue behind each other. The
new direct-advancement logic depends on this lock: "The heavyweight lock above
provides this guarantee, since it serializes all writers."

The order of steps in `CommitTransaction()` sets how long the lock is held:

1. `PreCommit_Notify()` takes the lock and writes the queue entries.
2. `RecordTransactionCommit()` runs. For a transaction that wrote WAL under
   synchronous commit, this calls `XLogFlush()` and then `SyncRepWaitForLSN()`.
   The source notes that at this stage the transaction "continue[s] to hold
   locks".
3. `ProcArrayEndTransaction()` runs.
4. `ResourceOwnerRelease(RESOURCE_RELEASE_LOCKS)` releases the lock.
5. Only then does `AtCommit_Notify()` call `SignalBackends()`.

So all of PostgreSQL 19's signalling work runs after the lock is released. It
does not shorten the serialized section. The following points are inference
from the code, not separately measured. A smaller wakeup storm can still help
indirectly: fewer woken listeners compete for `NotifyQueueLock`, which the next
lock holder needs to append its entries. But the WAL flush under the lock
remains. Notifying transactions that write data cannot share a group commit
with each other, so each one pays its own flush, plus a standby round trip
under synchronous replication.

Measurements show how large this is:

- **Arseniy Mukhin, 2025-10-17.** Master, `pgbench -c 100 -j 10 -T 100`:
  INSERT only gave 30,982 TPS; INSERT plus NOTIFY gave 818 TPS (about 38x
  lower); NOTIFY only gave 87,751 TPS. NOTIFY-only is fast because it skips
  the flush. These scripts had no listeners at all, so PostgreSQL 19's
  signalling change has nothing to remove in this case.
- **Rishu Bagga, other hardware, same 100-client INSERT plus NOTIFY.** Master
  gave about 29,000–31,000 TPS. The large gap from Mukhin's 818 TPS fits a
  serialized section whose length is set by WAL flush latency (inference).
  Bagga notes the cost "becomes especially expensive in environments where
  compute and storage are separated."
- **Jacobson's own conclusion** was that the bottleneck "depends on the
  workload, which is either the kill() syscalls *or* the heavyweight lock."
  PostgreSQL 19 addresses only the first.

### Status of relief for the lock

Tom Lane proposed (2025-07-18) carrying NOTIFY payloads through WAL. Under that
design the global lock is needed only to write a small fixed-size queue entry
in commit order, "which is much shorter than what happens now". Rishu Bagga's
"Write Notifications Through WAL" patch implements this. In Mukhin's benchmark
it raised INSERT plus NOTIFY from 818 to about 33,800 TPS (v6 and v7), close
to the INSERT-only baseline. The cost was NOTIFY-only throughput, which fell
from about 87,800 to about 34,000–36,000 TPS. The thread was still under
review at its last message (v9, 2025-11-25). The PostgreSQL 19 release notes
contain no such item, and current master still takes the heavyweight lock.

An earlier proposal for a GUC to skip the lock entirely (out-of-order
notifications) roughly doubled NOTIFY-only TPS. With LISTEN plus NOTIFY it
gave only about 14% (73,000 to 83,000 TPS), and it was not adopted.

Recall.ai's widely cited post blamed this lock for its outage. A May 2026
update to that post says commit 282b1cd "has eliminated the bottleneck in the
postgres core". The source code contradicts this: the lock and its hold window
are unchanged.

### Implications for a notifying event store

The following points are inference from the code and measurements above.

- Appends that write events and NOTIFY in the same transaction, under
  synchronous commit, will serialize their commits across the whole cluster
  on PostgreSQL 19 just as on 18. Throughput is roughly capped at one commit
  per WAL-flush latency.
- PostgreSQL 19 helps the consumer side when there are many listening
  connections that are mostly uninterested, such as fine-grained per-stream or
  per-category channels. It does little for a few consumers sharing one
  channel.
- The measured NOTIFY-only numbers suggest a mitigation: notify in a separate,
  data-free transaction after the append commits. That transaction commits
  without a flush, so it holds the lock only briefly. The cost is that the
  notification is no longer atomic with the append, and a crash between the
  two steps loses the wake-up.
