# How far does the snapshot xmin horizon lag behind the newest committed event under realistic workloads with long-running, idle-in-transaction or unrelated writing sessions, and which server-side timeouts can safely bound that lag?

## Question

An event store can stamp each event with `pg_current_xact_id()` and have consumers
read only events whose transaction ID is below
`pg_snapshot_xmin(pg_current_snapshot())`. This stops a consumer skipping events
whose position was allocated earlier but committed later. How far behind the
newest committed event does that horizon fall when the cluster has long-running
transactions, sessions left idle in a transaction, or unrelated writing
sessions? Which server-side timeouts can bound the lag without causing other
harm?

## Findings

### What the horizon is, and what holds it back

PostgreSQL defines a snapshot's `xmin` as the "lowest transaction ID that was
still active. All transaction IDs less than `xmin` are either committed and
visible, or rolled back and dead". This guarantee is what makes the
`transaction_id < pg_snapshot_xmin(pg_current_snapshot())` filter safe. The
eugene-khyst `postgresql-event-sourcing` reference implementation, Oskar
Dudycz's outbox-ordering article and Sequin's write-up on out-of-order sequence
commits all use it. It works together with a `(transaction_id, id) > (last_txid, last_id)`
cursor ordered by transaction ID and then position.

The PostgreSQL source shows exactly which sessions hold the horizon back.
`GetSnapshotData` loops over every proc in the ProcArray. It skips any entry
that has no transaction ID assigned, its own transaction, and backends flagged
`PROC_IN_LOGICAL_DECODING` or `PROC_IN_VACUUM`. It takes the minimum of all
remaining running XIDs as `xmin`. Five consequences follow for an event-store
consumer:

1. **Only sessions that hold an XID count.** A transaction gets a real XID only
   "when a transaction first writes to the database". Until then it has only a
   virtual ID. Read-only work therefore never holds back `pg_snapshot_xmin`.
   That covers long `REPEATABLE READ` reports, `pg_dump`, and a psycopg
   connection left idle in transaction after a `SELECT`. Such sessions do
   still hold back the vacuum horizon (`backend_xmin`), which is a separate
   quantity. `pg_current_xact_id()` itself forces an XID to be assigned, so
   writers that stamp events get one at that point.
2. **Row locks count as writes.** The PostgreSQL docs state that `SELECT FOR UPDATE`
   "modifies selected rows to mark them locked, and so will result in disk
   writes", so it takes an XID. A consumer that locks its checkpoint or lease
   row (for example with `FOR UPDATE SKIP LOCKED`) and keeps that transaction
   open while its handler runs holds back the horizon for every other
   subscription. Its own snapshot excludes its own XID, so it does not see
   the stall itself.
3. **The horizon is cluster-wide, not per-database.** XIDs "are assigned
   sequentially to transactions from a global counter used by all databases
   within the PostgreSQL cluster". The snapshot loop does not filter by
   database. A long writer in an unrelated database on the same cluster stalls
   the event store's consumers just as a writer in the event store's own
   database would. The eugene-khyst README describes the effect as "a
   long-running transaction in the same database". The source shows the scope
   is wider than that.
4. **Prepared transactions hold it back indefinitely.** A prepared (two-phase)
   transaction keeps a dummy PGPROC entry, "what keeps the XID considered
   running". Its XID stays in every snapshot until `COMMIT PREPARED` or
   `ROLLBACK PREPARED`, even after the preparing session has gone.
5. **Some activity is excluded.** Lazy `VACUUM` (autovacuum included) and
   logical-decoding walsenders are explicitly skipped. Replication slots and
   standby feedback affect vacuum horizons (`xmin`/`catalog_xmin`), not the set
   of running XIDs, so they do not delay this horizon.

### How far it lags

No published measurements of `pg_snapshot_xmin` lag under production workloads
were found. The lag follows directly from the mechanism. Suppose an event is
committed at time *c* by a transaction with XID *X*. It becomes readable once
every transaction with an XID below *X* that was still running at *c* has
ended. Its delivery delay is therefore the remaining lifetime of the
longest-lived *older* XID-holding transaction anywhere in the cluster. While
that transaction runs, the horizon is fixed at its XID and every event from a
later-starting writer waits behind it. The eugene-khyst README describes the
effect as a long-running transaction that "will effectively 'pause' all event
handlers". Sequin's analysis puts it concretely: "if you have a transaction
running against another table for two minutes, your cursor/query will be unable
to read the last two minutes" of the event table. Sequin rejected the approach
for that reason. Ordering follows the order in which transactions first wrote.
That is not the order they started, as one practitioner article says, because
XIDs are assigned at the first write.

| Workload | Holds an XID? | Resulting lag |
| --- | --- | --- |
| Short OLTP write transactions (event appends, ordinary updates) | Yes, briefly | Roughly the duration of the longest overlapping write transaction, typically milliseconds |
| Event writer that inserts, then awaits an external call before commit | Yes | The full duration of the external call |
| Session that wrote, then sits `idle in transaction` (an application bug, or awaiting user or network input) | Yes | Unbounded until commit, rollback or termination |
| Batch jobs, backfills or migrations run as one transaction in **any** database on the cluster | Yes | The full duration of the job |
| Consumer holding a `FOR UPDATE` lease row across handler execution | Yes | The handler's batch duration, imposed on all other subscriptions |
| Forgotten prepared transaction | Yes | Unbounded, and immune to session timeouts |
| Read-only reports, `pg_dump`, idle read-only transactions | No | None (vacuum is still held back) |
| Autovacuum (lazy), logical decoding, replication slots | Excluded | None |

The live lag can be observed directly. `pg_stat_activity.backend_xid` is the
"top-level transaction identifier of this backend, if any". `xact_start` gives
the transaction start, which is an upper bound because the XID may have been
assigned later. `state` distinguishes `idle in transaction`. `pg_prepared_xacts`
lists prepared transactions. A query like the following identifies the
transaction currently holding back consumers:

```sql
SELECT pid, datname, usename, state, xact_start, backend_xid
FROM pg_stat_activity
WHERE backend_xid IS NOT NULL
ORDER BY age(backend_xid) DESC
LIMIT 1;
```

### Which server-side timeouts bound it

All five client timeouts default to `0` (disabled), are in milliseconds, and are
`PGC_USERSET`. Any session can therefore override them, and they act as
defaults rather than enforcement.

| Setting | Behaviour (per PostgreSQL docs) | Does it bound horizon lag? |
| --- | --- | --- |
| `statement_timeout` | Aborts any single statement exceeding the limit | No: a transaction made of many short statements, or one idling between them, is unaffected |
| `idle_in_transaction_session_timeout` | Terminates a session idle *within an open transaction* longer than the limit | Partly: it removes the abandoned-transaction case, but not a busy long transaction |
| `transaction_timeout` (PostgreSQL 17+) | "Terminate any session that spans longer than the specified amount of time in a transaction", explicit or implicit | Yes, for sessions it applies to: lag is at most the limit plus termination latency |
| `lock_timeout` | Aborts a statement waiting too long for one lock | Only indirectly, by stopping writers stuck behind locks while holding an XID |
| `idle_session_timeout` | Terminates sessions idle *outside* a transaction | No: such sessions hold no XID |
| `max_prepared_transactions = 0` | Disables `PREPARE TRANSACTION` (the docs' recommendation without an external transaction manager) | Yes, removes the prepared-transaction case, which `transaction_timeout` explicitly does not cover |

`transaction_timeout` is the only setting that caps total transaction duration
on the server, and it exists only from PostgreSQL 17. If it is set at or below
`idle_in_transaction_session_timeout` or `statement_timeout`, the longer one is
ignored. On earlier versions, idle-in-transaction and statement timeouts
together still allow a transaction to run indefinitely. Lag can then be bounded
only by an external watchdog that terminates sessions whose `backend_xid` is
older than a threshold.

Applying the timeouts safely has five constraints:

- **Scope them by role or database, not cluster-wide.** The docs say setting
  `statement_timeout`, `transaction_timeout` and `lock_timeout` in
  `postgresql.conf` "is not recommended because it would affect all sessions".
  Since only XID-holding transactions matter here, a broad timeout would kill
  harmless read-only work such as `pg_dump` and reports for no gain. Aim the
  limits at application writer and consumer roles.
- **They cannot be enforced against a determined client.** As `PGC_USERSET`
  settings, a migration or batch session can set them to `0`. Because the
  horizon is cluster-wide, every role on every database in the cluster has to
  be covered for a bound to hold. Shared or multi-tenant clusters make this
  hard.
- **Termination aborts work.** `transaction_timeout` and
  `idle_in_transaction_session_timeout` terminate the session rather than just
  cancelling a statement. Legitimate long migrations must therefore be split
  into batches or run under a role without the limit, which accepts stalled
  consumers for their duration. The docs warn that poolers and middleware may
  react poorly to unexpected connection closure. psycopg notes that PgBouncer
  already discards connections left in a transaction.
- **Prepared transactions sit outside every session timeout.** Disable them,
  or monitor `pg_prepared_xacts`.
- **The event store's own code is part of the workload.** Consumers should
  read in autocommit mode or very short transactions. They should not hold a
  write lock or uncommitted projection write across handler execution.
  Writers should take their XID late, by inserting events immediately before
  commit, and should never await external I/O while holding it. psycopg
  starts a transaction implicitly on the first statement, and its docs warn
  that sessions otherwise "remain *idle in transaction*".

A setting such as `transaction_timeout` of tens of seconds on application roles,
`idle_in_transaction_session_timeout` of a few seconds, and
`max_prepared_transactions = 0` bounds worst-case consumer latency to that
transaction limit for application traffic. Within that limit, consumers see the
usual millisecond-scale lag. The bound holds only if every XID-holding session
in the cluster, including administrative ones, is subject to the limits. The
event store should still measure horizon age, `now()` minus the oldest
`backend_xid` holder's `xact_start`, and alert on it, rather than assume the
limits hold.
