# Will a listener connection that only receives notifications and never sends queries be closed as idle by RDS Proxy IdleClientTimeout, PgBouncer client_idle_timeout or Supavisor, and what heartbeat interval keeps it alive without defeating proxy idle management?

## Question

A dedicated `LISTEN` connection sends one `LISTEN` statement and then only receives `NotificationResponse` messages. Will the three common proxies (Amazon RDS Proxy, PgBouncer and Supavisor) treat it as idle and close it? If so, how often should a heartbeat run to keep it open, and how can that be done without undermining the proxies' management of idle connections?

## Findings

### Short answer

Every one of these idle timers counts only requests sent by the client. Traffic from the server to the client, including notifications, does not count. The proxies differ in whether the timer applies to a session-mode listener at all:

| Proxy | Will it close a notification-only listener? | Default |
| --- | --- | --- |
| RDS Proxy `IdleClientTimeout` | **Yes**, even if notifications keep arriving | 1,800 s (30 min) |
| PgBouncer `client_idle_timeout`, session mode | **No**. A client linked to a server is skipped | 0 (disabled) |
| Supavisor `client_idle_timeout`, session mode | **Yes, if enabled**. Notifications do not reset the timer | 0 (disabled) |

PostgreSQL's own `idle_session_timeout` is a fourth timer of the same kind. It is off by default.

A cheap round-trip query such as `SELECT 1`, sent on an autocommit connection, resets every one of these timers. It should run at no more than about half of the shortest client-request idle timeout on the path. If a layer-4 load balancer or NAT device sits in the path, the interval must also stay below that device's idle timeout (350 s by default on AWS Network Load Balancers). One to five minutes works for most deployments. AWS's own example pings once a minute against the 30-minute default.

Idle management keeps working if the heartbeat runs only on the dedicated listener connection, never on pooled query connections, and runs from the same loop that consumes notifications. Then a hung or dead listener stops sending heartbeats, and the proxy reclaims its connection.

On RDS Proxy, no heartbeat stops the non-configurable 24-hour maximum lifetime of a client connection. A listener must therefore always be able to reconnect, re-issue `LISTEN` and catch up.

### RDS Proxy: notification-only listeners are idle and will be closed

AWS defines client idleness in terms of requests from the application. "A client connection is considered *idle* when the application doesn't submit a new request within the specified time after the previous request completed." The default is 1,800 seconds (30 minutes). The configuration guide gives the range as 1 minute to 8 hours. The setting covers the client-to-proxy leg only.

Under this definition, a listener that only receives notifications is idle however many notifications arrive. The proxy will close it once `IdleClientTimeout` passes after its `LISTEN` completed. The guide also says what does reset the timer: "the client connection must be truly idle without sending any queries (even simple health checks such as `SELECT 1;`)" for the timeout to be enforced. AWS's own example is a heartbeat: "if you configure `IdleClientTimeout` to 30 minutes (default) and ping the database every minute, the connection never exceeds the idle timeout, but it doesn't remain open indefinitely. RDS Proxy closes the connection after 24 hours even if it doesn't qualify as idle." The 24-hour maximum lifetime of a client connection "is not configurable."

`LISTEN` is listed as a pinning condition for PostgreSQL: "Listening on a notification channel." A pinned connection keeps its backend database connection until the client session ends. AWS also states that pinned connections "are not available for reuse by other clients, and therefore don't count as idle for the purposes of enforcing `MaxIdleConnectionsPercent`."

This bears directly on the "without defeating idle management" part of the question. On a listener, a heartbeat costs the proxy nothing it could otherwise reclaim. The `LISTEN` has already taken the backend out of the multiplexing pool, and the heartbeat only stops `IdleClientTimeout` from closing a session that is still wanted.

AWS's guidance on liveness checks says the same. In general they should be disabled, because a no-op `SELECT 1` "prevents the proxy from enforcing idle client timeouts and managing the connection pool size". AWS names two exceptions: when "you deliberately want to prevent certain connections from timing out in the proxy layer", and when you want to "proactively detect when a connection is dropped by the proxy". Its examples of the second are a pinned backend closed by a database restart and a client connection that exceeds the 24-hour lifetime. Its recommendation is to "only perform them for the specific connections that you want to keep from timing out". For an event-store library, that means heartbeats on the listener connection and no keep-alive queries on the pooled query connections.

AWS also advises aligning timeouts so that "client timeout < proxy timeout < database timeout". In practice, the library should make the heartbeat interval configurable and set it well below the deployed `IdleClientTimeout`.

### PgBouncer: client_idle_timeout does not apply to a session-mode listener

The documentation says that `client_idle_timeout` closes "Client connections idling longer than this many seconds". It is disabled by default (0) and flagged as potentially dangerous: "This should be larger than the client-side connection lifetime settings, and only used for network problems."

PgBouncer's source shows when the timeout fires. The janitor (`pool_client_maint` in `src/janitor.c`) walks the active client list and runs `if (client->link) continue;` before comparing `now - client->request_time` against the timeout. That timeout is either the global value or a per-user override. Clients that currently hold a server connection are therefore never closed by `client_idle_timeout`.

In session mode the documentation says the "Server is released back to pool after client disconnects". The source (`src/server.c`) confirms that release on `ReadyForQuery` happens only when the pool mode is not `POOL_SESSION`. A session-mode client that has issued `LISTEN` stays linked to its server for life, so `client_idle_timeout` never applies to it, whatever its value.

`server_idle_timeout` (default 600 s) does not apply either. It is enforced on the used, tested and idle server lists, not on servers linked to an active client. `server_lifetime` explicitly covers only "an unused (not currently linked to any client connection) server connection".

PgBouncer forwards an asynchronous `NotificationResponse` without changing the server's ready or idle-in-transaction state, so notifications reach an idle session-mode client normally. LISTEN does not work in transaction mode in the first place, so the timeout question only arises in session mode.

PgBouncer therefore needs no heartbeat to keep a listener open. What PgBouncer does not do is detect a dead peer quickly. Its `tcp_keepalive` is on by default but uses OS defaults, which the documentation gives as `tcp_keepidle=7200, tcp_keepintvl=75, tcp_keepcnt=9` on Linux. A heartbeat on the listener remains useful as a liveness probe of the full path, client to PgBouncer to PostgreSQL. It also keeps middlebox state warm.

### Supavisor: closes the listener only if client_idle_timeout is enabled

Supavisor's tenant schema defines `client_idle_timeout` (integer, default `0`), described as "the maximum duration of an idle client connection". It also defines `client_heartbeat_interval` (integer, default `60`). Supabase's release note says the heartbeat "helps us detect client connections from behind a load balancer which are dead but did not close the TCP connection correctly" and "defaults to one minute".

The following comes from reading the Supavisor source on its main branch. In the client handler, the idle timeout is a gen_statem `state_timeout` (`:idle_terminate`). It is armed each time the handler enters its `:idle` state, which happens when the database handler reports `ReadyForQuery` after a client query. A query arriving from the client moves the handler from `:idle` to `:busy` and back, which re-arms the timer.

In session mode the database handler stays checked out and in its `:busy` state across queries. It writes backend bytes, including asynchronous notifications, straight to the client socket. It tells the client handler only when a batch completes with `ReadyForQuery`, and a lone `NotificationResponse` has no `ReadyForQuery`.

The inference is that notifications reach a session-mode listener but do not re-arm the idle timer. So when `client_idle_timeout` is non-zero, a notification-only listener is closed once that time passes after its last query, and a client query such as `SELECT 1` resets it. With the default of `0`, Supavisor does not close idle clients at all.

The unit of `client_idle_timeout` is not stated in the tenant documentation. The value is passed to the client handler without visible conversion, so operators should check it against their deployed version.

Supavisor's own heartbeat runs in the opposite direction. It is a proxy-to-client send of a precompiled `application_name` protocol message, repeated at the heartbeat interval. Its job is to find dead clients. It does not keep the client counted as active.

### PostgreSQL and network middleboxes

PostgreSQL's `idle_session_timeout` (PostgreSQL 14 and later, default 0) terminates "any session that has been idle (that is, waiting for a client query), but not within an open transaction". A listener spends nearly all its time waiting for a client query, so a value set on the server, or on the listener's role, is another client-request timer the heartbeat must beat. The documentation itself warns against enforcing it on pooled or middleware connections.

The heartbeat must also run on an autocommit connection, outside any transaction. A heartbeat left inside an open transaction would leave the session idle in transaction. That is exactly the state targeted by `idle_in_transaction_session_timeout` in PostgreSQL and by `idle_transaction_timeout` and `transaction_timeout` in PgBouncer.

Below the proxies, layer-4 devices time out on any traffic at all. An AWS Network Load Balancer closes a TCP flow when "no data is sent through the connection by either the client or target" for its idle timeout. That timeout defaults to 350 seconds, is adjustable from 60 to 6,000 seconds for TCP listeners, and is fixed at 350 seconds for TLS listeners.

libpq's `keepalives_idle`, `keepalives_interval`, `keepalives_count` and `tcp_user_timeout` tune TCP-level keepalive and dead-peer detection on the client-to-proxy hop. When left at zero they use the system default. TCP keepalive probes end at the proxy's TCP stack and are not requests, so they never reset RDS Proxy's, PgBouncer's or Supavisor's client idle timers. Only a protocol-level query does that.

### Choosing the interval

Take the smallest client-request idle timer that applies to the listener:

- RDS Proxy `IdleClientTimeout`;
- Supavisor `client_idle_timeout`, if it is non-zero;
- PostgreSQL `idle_session_timeout`, if it is set for the listener's role.

PgBouncer session mode adds no timer. Set the heartbeat to at most about half that value, so that one late or failed heartbeat does not cause a disconnect. If the path crosses an NLB, a NAT gateway or a similar device, also keep the interval below that device's idle timeout (around 300 s for a 350 s device), or tune TCP keepalives below it.

The heartbeat also sets the worst-case delay before a silent half-open listener is noticed. Without it, a listener cannot tell "no events" from "dead connection". This argues for the shorter end of the range, roughly 30 seconds to 5 minutes, especially if catch-up polling is infrequent.

Each heartbeat is a single round trip on a connection that is already dedicated or pinned. The costs are protocol noise, plus one held backend per listener process for as long as the process runs. The backend is held anyway, because the listener needs it.

### Implementing it with psycopg 3

From psycopg 3.2, `Connection.notifies()` accepts `timeout` and `stop_after`. The source computes the timeout once as a total deadline, `deadline = monotonic() + timeout`, and does not reset it after each notification. A loop of `notifies(timeout=interval)` therefore returns at least once per interval even while notifications keep arriving. This matters because, as shown above, incoming notifications do not keep an RDS Proxy or Supavisor listener alive.

The generator holds the connection lock while it runs. The heartbeat query has to run after the generator ends and before it is re-entered.

Since psycopg 3.2.4, notifications that arrive while the generator is not running are "captured and yielded by the generator once it is started". Since 3.2.10, "if a handler is registered then notifications are not captured when the generator is not running". So a listener that relies on `notifies()` must not also register `add_notify_handler()` callbacks. Using both together raises a runtime warning from 3.2.10, and the documentation says to "use only one of the two methods".

The deadline check runs after notifications have been yielded. If the code consuming the generator blocks, the next heartbeat is delayed. Keep per-notification work short, or hand it off to a queue, so that the heartbeat keeps its schedule. The same property is what lets idle management work: a stuck consumer stops sending heartbeats, and the proxy's timeout then reclaims the connection.
