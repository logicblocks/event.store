# What decoding cost and wake-up latency does reading a logical slot through pg_logical_slot_peek_changes and pg_replication_slot_advance on an ordinary psycopg 3 connection incur compared with streaming the slot over a replication connection?

## Question

A Python event store using psycopg 3 can read a logical replication slot in two ways. It can call the SQL functions `pg_logical_slot_peek_changes` (to read) and `pg_replication_slot_advance` (to acknowledge) on an ordinary connection. Or it can stream the slot over a replication connection (`START_REPLICATION SLOT ... LOGICAL`). What does each route cost in decoding work, and how quickly does each wake the consumer?

## Findings

### Short answer

The SQL-function route is stateless, which makes it much more expensive per wake-up. Every call builds a new decoding context, flushes the backend's catalog caches, and re-reads WAL from the slot's `restart_lsn`. That point can sit well behind the last confirmed position. A peek-then-advance cycle reads that WAL twice: once with full decoding for the peek, then again in fast-forward mode for the advance. The cost of a call therefore grows with the amount of cluster-wide WAL since `restart_lsn`, not with the number of new events. The functions also never block waiting for new WAL. A consumer has to poll or be woken by `LISTEN` and `NOTIFY`, so its wake-up latency is the signal latency plus a round trip plus that re-decode.

A streaming walsender works differently. It keeps one decoding context for the whole session and decodes each WAL record once. It sleeps on a latch that WAL flush sets through a condition-variable broadcast, so it pushes a transaction as soon as the transaction's commit record is flushed.

psycopg 3 cannot use the streaming route: its replication-protocol support issue has been open since 2021. The consulted primary sources publish no millisecond benchmarks for either route. The bounds below come from the server's code and documentation.

### What one SQL-function call does

The PostgreSQL source shows the shared implementation behind the get, peek and binary variants, `pg_logical_slot_get_changes_guts` in `logicalfuncs.c`. Each call does the following:

- **Takes the slot without waiting.** It calls `ReplicationSlotAcquire(name, true, true)`, and `nowait = true` means "an error is raised if ... the slot is currently in use" (`replication slot "..." is active for PID ...`). Only one session can read a slot at a time. A second consumer process, or a call that overlaps a walsender on the same slot, fails instead of queueing.
- **Builds a fresh decoding context.** It calls `CreateDecodingContext(InvalidXLogRecPtr, ...)`, which loads the output plugin and runs its startup callback. It calls `InvalidateSystemCaches()` before decoding (commented "invalidate non-timetravel entries") and again after freeing the context. The backend's catalog caches are cold at the start of every call and are rebuilt under historic snapshots.
- **Reads WAL from `restart_lsn`, not from the confirmed position.** The source says: "Decoding of WAL must start at restart_lsn so that the entirety of xacts that committed after the slot's confirmed_flush can be accumulated into reorder buffers." Transactions that committed before `confirmed_flush` are left out of the output, but their WAL is still read and their changes are still queued, then discarded. WAL is shared by the whole cluster, so the reader also scans records for other databases and filters them out.
- **Stops at the flush pointer and does not wait.** It sets `end_of_wal = GetFlushRecPtr(NULL)` (the replay pointer on a standby), clamped by `upto_lsn`, and loops `while (ctx->reader->EndRecPtr < end_of_wal)`. When it reaches the end of flushed WAL it returns. It only blocks for failover slots, which wait for `synchronized_standby_slots` confirmation.
- **Builds the whole result before returning any of it.** It uses `InitMaterializedSRF`, which writes every row into a tuplestore before psycopg sees the first row. `upto_nchanges` is checked "only ... after adding the rows produced when decoding each new transaction commit", so a single large transaction comes back in full. With wal2json format version 1, which emits one JSON object per transaction unless `write-in-chunks` is set, that means one very large row.
- **Only get confirms.** The code runs `LogicalConfirmReceivedLocation(ctx->reader->EndRecPtr)` only when `confirm` is true. Peek skips it, and the documentation says peeked changes "will be returned again on future calls". A loop that only peeks re-reads and re-decodes everything since the last advance on every call. Paging through a backlog with `upto_nchanges` and peek alone costs quadratic work.

### What `pg_replication_slot_advance` adds

`pg_replication_slot_advance` clamps the target to the flush pointer ("We can't move slot past what's been flushed/replayed"). For a logical slot it calls `LogicalSlotAdvanceAndCheckSnapState`, which explains that it "need[s] to digest WAL to advance restart_lsn allowing to recycle WAL and removal of old catalog tuples". It starts "reading at the slot's restart_lsn" and decodes up to the target in **fast-forward mode**. In `decode.c`, fast-forward skips `DecodeInsert`, `DecodeUpdate`, `DecodeDelete` and transactional logical messages, and `DecodeTXNNeedSkip` returns true for every transaction. No output-plugin work runs.

Advance is therefore much cheaper per record than a decoding call, but it still reads the same WAL range and runs the snapshot builder. Each peek-then-advance cycle reads the span from `restart_lsn` to the target twice: once with full decoding and plugin output, then once in fast-forward. Like get, advance's new position is "written out at the next checkpoint". After a crash the slot can fall back and redeliver.

### Why `restart_lsn` keeps the re-read window wide

Confirming a position moves `confirmed_flush` straight away, but `restart_lsn` moves only in steps. `snapbuild.c` says the slot is told where it can restart "only ... every time we see a running xacts record". The new restart point is the first LSN of the oldest in-progress transaction, or the last serialized snapshot if none is running.

Those `xl_running_xacts` records come from the background writer every `LOG_SNAPSHOT_INTERVAL_MS` (15000 ms) when "interesting records have been inserted", and also from checkpoints. Under steady load, every SQL call therefore re-reads at least roughly the WAL since the last running-xacts record that the slot confirmed past. Any long-running transaction anywhere in the cluster pins the window further back, because "large or long-running transactions prevent the database from increasing the restart LSN".

`pg_log_standby_snapshot()` writes such a record on demand. The documentation describes it as a way to avoid "having to wait for bgwriter or checkpointer to log one", aimed at logical decoding on standbys. Whether calling it after each batch actually narrows the window for a primary-side SQL consumer was not established.

### Streaming over a replication connection

- **One decoding context per session.** In the walsender, `StartLogicalReplication` calls `CreateDecodingContext` once and keeps it for the whole `WalSndLoop`. The reorder buffer, snapshot builder and caches survive between waits, so each WAL record is read and decoded once. It is re-read only after a reconnect.
- **Resumes from the confirmed position.** `START_REPLICATION SLOT ... LOGICAL` starts at "WAL location XXX/XXX or the slot's confirmed_flush_lsn ... whichever is greater". Internally the walsender still begins at `restart_lsn`, but it pays that cost once per connection, not once per wake-up.
- **Push wake-up on WAL flush.** A logical walsender that has caught up waits in `WalSndWaitForWal` ("Wait till WAL < loc is flushed to disk so it can be safely sent to client"). Since PostgreSQL 16 the commit "Optimize walsender wake up logic using condition variables" has walsenders register on shared condition variables (`wal_flush_cv` and `wal_replay_cv`). Processes that flush WAL call `WalSndWakeup()`, which runs `ConditionVariableBroadcast()` and so `SetLatch()`. On a primary that happens "when flushing WAL". The consumer has no polling interval and makes no request round trip. A transaction is sent once its commit record is flushed and decoded.
- **Acknowledgement is separate from delivery.** The client reports progress with Standby status update messages, and the server sends keepalives that can ask for a reply. psycopg2 exposes this through `start_replication(status_interval=...)` (at least 1 s) and `send_feedback(flush_lsn=...)`. The feedback interval controls how often the slot's position moves, not how fast data arrives. psycopg2 warns that failing to "constantly consume and report success" retains WAL until the disk fills.
- **Synchronous replication is only possible here.** "Synchronous replication is only supported on replication slots used over the streaming replication interface. The function interface ... do[es] not support synchronous replication."

psycopg 3 has no replication-protocol support. Issue #71, "Add support for streaming replication as in psycopg2", has been open since 29 August 2021. A psycopg 3 consumer that wants streaming must use psycopg2's `LogicalReplicationConnection`, run `pg_recvlogical` as a subprocess, or use another client library. `pg_recvlogical` "has no equivalent to the logical decoding SQL interface's peek and get modes" and "sends replay confirmations for data lazily". Using the SQL functions on a normal connection is the only route psycopg 3 supports natively.

### Wake-up latency compared

| | SQL functions on psycopg 3 | Streaming walsender |
|---|---|---|
| Trigger | Client poll, or a `LISTEN` and `NOTIFY` wake-up followed by a call | Server pushes when WAL flush sets the walsender's latch |
| Added latency | Half the poll interval on average (or the notification delivery time), plus a query round trip, plus decoding everything since `restart_lsn`, plus materialising the batch | Decoding only the new records, plus network send |
| Cost of one wake-up | Grows with WAL since `restart_lsn`, read twice if peek then advance | Grows with new WAL only |
| Steady-state reads | The same WAL is re-read on every call until `restart_lsn` moves | Each record is read once |

Both routes see only **flushed** WAL. With `synchronous_commit = off`, a commit can be reported to clients up to "three times wal_writer_delay" (`wal_writer_delay` defaults to 200 ms) before its WAL is flushed. Under asynchronous commit, a consumer woken by `NOTIFY` that calls the SQL function at once may therefore find nothing and need to retry. That is an inference from the flush-pointer bound and is not documented. A walsender, by contrast, is simply woken when the WAL writer flushes.

### Production precedent and practical guidance

Supabase's walrus, the engine behind Realtime's Postgres Changes, consumes a wal2json slot by calling `pg_logical_slot_get_changes('realtime', null, null, ...)`. That is the consuming get variant, not peek-then-advance. It shows that polling through the SQL interface is used in production, at the cost of the get variant's at-most-once acknowledgement inside the call. No source consulted publishes measured latencies for that route.

For a psycopg 3 event store, the code supports these conclusions:

1. Peek-then-advance gives at-least-once delivery, but confirm promptly and in large batches so that `restart_lsn` can move. Never loop on peek alone.
2. Run exactly one reading session per slot, because concurrent calls fail with "active for PID".
3. Prefer row-sized plugin output (wal2json format version 2, or `write-in-chunks`) so that the materialised result does not hold whole transactions as single rows.
4. Expect the per-wake-up re-decode to dominate at high commit rates. Coalescing wake-ups, or moving to a streaming client, is the remedy when it does.
