# What breaks for existing consumers, stored checkpoints and replays when an event store switches from ordering by global sequence number alone to ordering by transaction ID and then sequence number?

## Question

An event store's consumers read by global sequence number alone. If it switches to ordering by transaction ID and then sequence number, what breaks for those consumers, for their stored checkpoints and for replays, and how have existing PostgreSQL event stores and message libraries handled the change?

## Findings

### The change replaces a single-integer position with a pair

All three implementations that document this design follow the same pattern: eugene-khyst's postgresql-event-sourcing reference implementation, Oskar Dudycz's outbox article, which he applied in Emmett, and Watermill's PostgreSQL Pub/Sub. Each event row stores `pg_current_xact_id()` in an `xid8` column. Readers only see rows whose transaction ID is below `pg_snapshot_xmin(pg_current_snapshot())`. Rows are ordered by `transaction_id, sequence`, and the reader resumes with a row comparison such as `(transaction_id, id) > (:last_xid, :last_id)`.

The motivation is the gap problem. Sequence values become visible before commit, and a transaction that commits late can carry a lower number. A reader that advances its checkpoint past that number loses the event.

The new order differs from both of the orders consumers may have relied on:

- **It is not sequence order.** An event can have a higher sequence number and a lower transaction ID than another event.
- **It is not commit order either.** PostgreSQL assigns a transaction ID "when a transaction first writes to the database", and "the order in which transactions perform their first database write might be different from the order in which the transactions started".

Dudycz puts the consequence directly: "our ordering guarantee respects when the transaction was started, not when the message was appended… in some edge cases, it may create problems if forgotten."

So everything that treated the position as one monotonically increasing integer is affected.

### Stored checkpoints: a bigint can no longer express the position

Each implementation had to widen its checkpoint:

- **eugene-khyst** stores both `LAST_TRANSACTION_ID` (`xid8`) and `LAST_EVENT_ID`.
- **Watermill** has an offsets table holding `offset_acked` and `last_processed_transaction_id xid8 NOT NULL`. Its messages table's primary key became `("transaction_id", "offset")`.
- **Emmett** is the clearest record of migrating an existing deployment. PR #336, merged May 2026 for milestone 0.43.0, says the author had "somehow didn't include (or probably removed somehow) the full transaction id handling", and that "in high contention, this could cause some messages to be lost in processors". The PR made PostgreSQL checkpoints "a compound checkpoint built from the transaction id and global position". It was flagged as breaking: "Made global position be string… they're not always bigint, but they will be always monotonic alphanumeric." New checkpoints are written as the transaction ID zero-padded to 20 digits, then `:`, then the global position, so they compare correctly as strings.

**How Emmett converts old checkpoints.** The 0.43.0 schema migration converts each stored plain-position checkpoint by joining it to the event at that position:

```sql
UPDATE emt_processors p
SET last_processed_checkpoint = lpad(m.transaction_id::text, 20, '0') || ':' || p.last_processed_checkpoint
FROM emt_messages m
WHERE m.global_position = p.last_processed_checkpoint::bigint
  AND p.last_processed_checkpoint NOT LIKE '%:%';
```

Two edge cases are left unhandled:

- If no event exists at the stored position (for example, it was archived or deleted), the row is silently left in the old format.
- When new code reads an old-format checkpoint, it looks up `transaction_id` for that `global_position` with a query that throws if the row is missing. The only special case is position zero.

**The overlap window (my inference, not documented by any of these projects).** Mapping an old checkpoint `p` to `(xid_of(p), p)` is only exact when no event straddles it. It follows from PostgreSQL's transaction-ID semantics:

- An event with a higher sequence number than `p` but a lower transaction ID sorts before the new checkpoint. Its consumer has not processed it, and it will be skipped forever.
- An event with a lower sequence number than `p` but a higher transaction ID sorts after the new checkpoint. It is delivered a second time.

Emmett is less exposed than a store that reads strictly by sequence. Its 0.42.x reader already filtered by `transaction_id < pg_snapshot_xmin(...)` and ordered by `transaction_id, global_position`, even though its cursor was `global_position >= after + 1`. That mismatch was itself the source of the loss PR #336 fixed: the batch was ordered by the pair, but the cursor advanced on the integer alone.

A store whose consumers read strictly by sequence is fully exposed to the window. Two ways to avoid it, both my inference:

- **Convert at a quiescent point.** Do it when no append transactions are in flight and every consumer is caught up.
- **Backfill all existing events with one constant transaction ID**, such as `'0'::xid8`. History then keeps its old sequence order, `(0, p)` is exactly equivalent to the old checkpoint `p`, and every new event sorts after all history. PostgreSQL's documentation supports this: adding a column with a non-volatile `DEFAULT` is metadata-only with no table rewrite, and a later `SET DEFAULT` (here, to `pg_current_xact_id()`) "will only apply in subsequent INSERT or UPDATE commands".

**Events already lost stay lost.** Events a sequence-only reader already skipped past cannot be recovered by converting checkpoints. The new scheme only prevents future loss, and only a replay from before the gap will deliver them.

### Running old and new consumer code together

A rolling or blue/green deploy means old and new consumer code write the same checkpoint rows. Emmett handled this in both directions:

- **Old code reads new checkpoints.** A 0.42.4 maintenance release (PR #381, August 2026) taught 0.42.x to read the 0.43.x checkpoint format "for blue/green migration when both 0.42.x and 0.43.x nodes are up".
- **The database function accepts both formats.** Its `store_processor_checkpoint` function does a format-aware compare-and-set. It uses `split_part(..., ':', 2)` to compare a new-format expected checkpoint with an old-format stored one, and the reverse. A TODO reads "Remove once all deployments have run the 0.43.0 migration."

Emmett's migration tests cover four cases:

- new-then-old and old-then-new blue/green sequences;
- a legacy consumer round-tripping a migrated checkpoint;
- a legacy reader returning a new-format value unchanged;
- the removed legacy `storeSubscriptionCheckpoint` function now failing with "does not exist" (SQLSTATE 42883).

The lesson: once the checkpoint format changes, optimistic checkpoint updates written by one version will not match values written by the other unless they normalise both formats.

### Consumer-facing APIs and derived calculations

Code outside the store that treats the position as an integer breaks or quietly misbehaves. Emmett changed the position's type from bigint to string, a breaking change for user code. Examples of what is affected (my inference from the tuple semantics):

- consumer lag computed as `head_sequence - checkpoint`;
- read-your-writes waits of the form "until the checkpoint is at or past my event's position";
- "read from" and "read up to" bounds, which Emmett now expresses as row comparisons on `(transaction_id, global_position)`;
- any API or HTTP feed that exposes a single numeric position to clients.

Indexes and query plans change too:

- Emmett's migration creates `idx_messages_transaction_id_global_position` and drops the single-column `global_position` index.
- Watermill's PostgreSQL adapter puts `transaction_id` first in the primary key "because we are using it alone in the WHERE clause". Its comments describe using a subquery to stop the planner mis-estimating, contrasting a plan that scanned 241,157 rows with one that scanned 112.

### Replays

Once a row's transaction ID is below every live snapshot's xmin, the `(transaction_id, sequence)` order is a stable total order, so replays from now on are deterministic. Historical replays, though, may not match what live consumers originally saw (my inference):

- **Real transaction IDs in history.** If existing events carry real transaction IDs, as Emmett's always did, a projection rebuilt from zero processes cross-stream events in a different order from the sequence order a sequence-only consumer used live. Order-sensitive projections can then rebuild to a different state.
- **Out-of-order events within one stream.** This is possible when an append transaction wrote something else (an outbox row or a read-model update) before appending. Its transaction ID can then be older than that of a concurrent transaction that appended the stream's previous event. Handlers that assume stream versions arrive in order, or that check expected versions, would need to tolerate this.
- **Constant backfill keeps history as it was.** History replays exactly as before, and the new ordering applies only to new events.

Replays bounded by "up to position N" need a tuple bound, because a single sequence number no longer marks a prefix of the new order.

### New stall and portability failure modes

Switching also adds behaviours that sequence-only consumers never had.

**Long transactions now block delivery.** The `pg_snapshot_xmin` filter means any long-running write transaction holds back every consumer. Watermill's documentation warns that "very long-running transactions may result in delayed message delivery". It describes an hour-long transaction blocking delivery until it commits, and recommends its Queue schema adapter, "which does not depend on the transaction ID", for such workloads. PostgreSQL assigns transaction IDs "from a global counter used by all databases within the PostgreSQL cluster", so transactions in other databases on the same cluster are involved too.

**Restores and cluster moves break stored transaction IDs.** `xid8` "does not wrap around during the life of an installation", and the epoch "is not actually stored anywhere in the database" except in the control-file field `pg_resetwal` sets. Stored transaction IDs are therefore tied to one cluster's counter. Two projects acknowledge this:

- Watermill's documentation says that when migrating data between databases "you may need to set `last_processed_transaction_id` in your offsets table".
- Emmett's PR #336 defers "helpers to handle cases properly after restoring PostgreSQL from a snapshot or pg_dump backup".

The consequence (my inference): after restoring into a cluster whose counter is behind the stored values, two things go wrong.

- Restored rows with transaction IDs above the new cluster's xmin are hidden by the visibility filter.
- New appends get lower transaction IDs than consumers' checkpoints, so resumed consumers never see them.

**Version and API requirements.** `xid8` and the `pg_*` snapshot functions need PostgreSQL 13 or later. The older `txid_*` bigint functions are deprecated and "may be removed from a future release".

### Status of the reference implementations

As of October 2026, Emmett's compound checkpoint is merged on main for milestone 0.43.0. The latest tag is 0.42.4 (12 August 2026), which carries only the forward-compatibility reader. Watermill's transaction-ID ordering dates from watermill-sql v2.0.0 (PR #23, July 2023), which its author said required "changing the public API, so a version bump is required". `xid8` support was added in v4.0.0. Watermill's release notes do not publish migration steps for existing message or offsets tables.
