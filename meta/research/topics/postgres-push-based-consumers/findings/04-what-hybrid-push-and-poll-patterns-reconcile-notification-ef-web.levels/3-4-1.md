# How should one listener connection per process fan notifications out to many in-process subscriptions, with per-subscription filtering by category and back-pressure, as Commanded's PubSub and GenStage pipeline does?

## Question

How should a process hold one PostgreSQL `LISTEN` connection and fan the notifications it receives out to many in-process subscriptions, so that each subscription sees only its own categories and a slow subscription is held back without stalling the others? The model to follow is the pipeline Commanded uses through its PostgreSQL store, `commanded/eventstore`. What does that pipeline do, and how does it carry over to a psycopg 3 library?

## Findings

### In short

Commanded's PostgreSQL event store splits the work into three parts, and the split carries over directly to psycopg 3:

1. **A listener that never blocks.** One dedicated connection per process runs `LISTEN` on a single channel. Every notification is drained off that connection straight away, whatever the consumers below are doing.
2. **A dispatcher that reads once and never waits.** It reads the notified events from the store once and routes them by key to the subscriptions registered for that key. It never waits on any subscriber.
3. **Back-pressure inside each subscription.** Each subscription has a bounded buffer. When the buffer overflows, the subscription stops taking pushed events and catches up from the durable log instead.

The push path is therefore lossy by design: an event that is dropped, skipped or missed is re-read from storage. The rest of this note describes how the store does this and what a psycopg 3 version should keep.

A naming point first. Commanded's own `Commanded.PubSub` (with a local adapter and a Phoenix adapter) is a general application message bus. The fan-out of database notifications lives in the EventStore library, which Commanded uses as its PostgreSQL adapter.

### The EventStore pipeline, stage by stage

**1. Trigger and payload.**
- A row-level trigger, `AFTER INSERT OR UPDATE ON streams FOR EACH ROW`, calls `pg_notify` on the channel `<schema>.events`.
- The payload is `stream_uuid,stream_id,first_version,last_version`.
- Each append updates both the target stream's row and the `$all` row (stream id 0). So every append sends two notifications on the same channel: one for the stream and one for `$all`. Topic routing therefore needs no extra work.
- The payload is parsed by splitting from the right. This lets stream identifiers safely contain commas.

**2. Listener (a GenStage producer).**
- It calls `Postgrex.Notifications.listen` once on the single channel.
- Each `{:notification, …}` message is parsed and appended to an Erlang `:queue` kept in the producer's state. This happens whatever the downstream demand is.
- Queued items are handed on only when demand exists.
- The effect is that the database connection is always drained. A slow stage below causes notifications to pile up in the listener's memory, which is unbounded; it never causes them to back up into PostgreSQL.

**3. Publisher (a GenStage consumer).**
- It subscribes to the listener with `max_demand: 1`, so it handles one notification at a time.
- For each notification it reads exactly that version range with `Storage.read_stream_forward`, using a pooled connection rather than the listener connection.
- It deserialises the events once, then calls `PubSub.broadcast(event_store, stream_uuid, {:events, events})`.
- Read errors are logged and the batch is dropped. It is not retried.

**4. PubSub fan-out (an Elixir `Registry`).**
- `EventStore.PubSub` is a node-local `Registry` with `keys: :duplicate`, split into one partition per scheduler.
- Subscribing registers the calling process under a topic key, and can store a per-subscriber `selector` and `mapper` with it.
- On broadcast, `Registry.dispatch` runs inside the publisher. For each registered process it filters the batch with that subscriber's selector, maps it, and sends it as a plain message.
- Per the Registry docs, dispatch "happens in the process that calls dispatch/3", and an entry is removed automatically when its process dies.
- Filtering therefore happens at two levels:
  - by topic key: only subscribers to that stream, or to `$all`, are visited;
  - by per-subscriber predicate: applied before the message is sent.
- Sending a message never blocks, so a slow subscriber cannot slow the publisher or its siblings.

**5. Subscription state machine (where back-pressure actually lives).**
- Each subscription is a process that subscribes to its stream's topic and passes `{:events, events}` messages to a state machine. Its states are: initial, request catch-up, catching up, subscribed, max capacity, disconnected and unsubscribed.
- **Only the subscribed state accepts pushed events,** and only if the first event number equals `last_received + 1`:
  - earlier events are ignored as duplicates;
  - later events mean there is a gap, and the subscription moves to request catch-up;
  - expected events are queued and sent on.
- **In every other state a pushed batch only advances `last_received`.**
- **Two settings bound the queues:**
  - `max_size` (default 1,000) caps the queue. Hitting it moves the subscription to max capacity, where later notifications are noted but not queued.
  - `buffer_size` (default 1) caps how many unacknowledged events each subscriber may hold at once.
- **Catch-up reads from storage** from `last_sent + 1`, in batches of `max_size`. It goes back to subscribed only when a read returns nothing *and* `last_sent == last_received`. Otherwise a notification arrived during the read, and it loops again.
- **Selector-rejected events are acknowledged automatically,** so they never hold back the checkpoint.
- **`partition_by` routes each key to one subscriber,** keeping per-key ordering when several subscribers share a subscription.
- The guide puts it like this: the subscription "will buffer events until the subscriber is ready to receive, or an overflow occurs. At which point it will move into a catch-up mode and query events and replay them from storage", and "A subscriber will not receive further published events until it has confirmed receipt of all received events."

**6. Supervision and connections.**
- The notifications connection, listener and publisher are supervised together with `one_for_all`, so if any one fails all three restart.
- The Postgrex notifications connection starts with `backoff_min: 0`.
- Since v1.2.0, several event-store instances can share one notifications connection (`shared_connection_pool`).
- Postgrex warns that while it is reconnecting, notifications "are not queued and cannot be recovered".
- The current listener holds no code that triggers a catch-up when it reconnects. As far as that code shows, a lost notification is recovered only when a later one on the same topic reveals the gap.
- Notifications and advisory locks need session-mode connections. The docs call out PgBouncer in transaction mode as incompatible.

**7. How the design evolved.**
- LISTEN/NOTIFY was introduced in v0.14.0.
- By v0.17.0 the notifications supervisor was registered under a cluster-wide `{:global, …}` name, giving one listener per cluster. It was a three-stage pipeline: listener → reader (a producer-consumer using `GenStage.BroadcastDispatcher`) → stream broadcaster.
- The current Cluster guide says instead that "A listener database connection process is started on each node". The reader and broadcaster were merged into a single publisher that sends to a node-local Registry.
- The move away from `BroadcastDispatcher` matters for back-pressure. That dispatcher guarantees events go to all consumers "without exceeding the demand of any given consumer", which means the slowest consumer sets the pace for everyone. It suits a fixed internal stage. It does not suit an open-ended set of user subscriptions.

### Other designs that confirm the pattern

- **Rails Action Cable PostgreSQL adapter:**
  - It lazily creates one `Listener` per process, under a mutex, on its own dedicated connection.
  - A subscriber map issues `LISTEN` when a channel gets its first subscriber and `UNLISTEN` when its last subscriber leaves.
  - The listener thread loops on `wait_for_notify(1)`. The one-second timeout lets it work through a command queue (listen, unlisten, shutdown) between waits.
  - Callbacks run on an executor, so a slow subscriber cannot block the thread that reads from the socket.
  - Channel names longer than 63 bytes are hashed with SHA-1, because PostgreSQL silently truncates longer identifiers. This matters if per-category channels are used.
- **Oban's notifier:** there is one notifier per Oban instance. Registered listeners live "in a registry that lives outside of the notifier process", so "Registration is durable across notifier restarts". Payloads are decoded once, before being relayed.

### Carrying this over to psycopg 3

The design below is a synthesis from the sources above, not something any one source prescribes.

- **One dedicated listener connection per process.**
  - Keep it in autocommit mode. psycopg says to do this "if you wish to receive or send notifications in a timely manner".
  - Run `LISTEN` on one global channel. Alternatively, run `LISTEN` per category with reference counting, as Action Cable does.
  - Loop on `notifies(timeout=…)`; the `timeout` and `stop_after` parameters were added in psycopg 3.2. The timeout lets one task also handle subscribe and unsubscribe commands, heartbeats and shutdown, as Action Cable's one-second wait does.
  - Use only one of `notifies()` and `add_notify_handler()`. The psycopg docs warn against using both.
- **The listener task only parses and hands off. It never awaits subscriber work.**
  - Have the writer put the category and position range in the payload. The dispatcher can then route without a query, like EventStore's stream id and version range.
  - Rather than keeping EventStore's unbounded queue, merge pending notifications into "highest notified position per category". That bounds memory no matter how fast notifications arrive.
- **A registry that lives outside the listener.**
  - Use a map from category to a set of subscriptions, plus a set of all-categories subscribers. This mirrors the duplicate-key Registry and its `$all` topic.
  - Keeping it outside the listener means a reconnect does not drop registrations (Oban's approach).
  - Apply a per-subscription predicate when finer filtering is needed (EventStore's `selector`).
- **Delivery: pick one of two models.**
  - **(A) Read once, push events.** This is EventStore's model. The dispatcher reads the notified range once, using a pooled connection rather than the listener, and offers it to each matching subscription's bounded `asyncio.Queue` with `put_nowait`. On `QueueFull`, the subscription is flagged as overflowed instead of the dispatcher waiting. Using `await put()` would bring back the slowest-consumer pacing that `BroadcastDispatcher` imposes.
  - **(B) Wake-up only.** The dispatcher just sets a per-subscription flag or `asyncio.Event`. Each subscription reads from its own checkpoint. This model merges repeated notifications into one wake-up by itself and is simpler. The cost is one query per subscription per wake-up instead of one shared read.
- **Each subscription keeps EventStore's state rules.**
  - Track `last_received` and `last_sent`.
  - Ignore positions it has already seen, and treat a jump as a reason to catch up.
  - When the queue overflows, stop queueing pushed events and catch up from storage.
  - Leave catch-up only when a read comes back empty and no newer notification arrived during it.
  - Auto-acknowledge events the subscription filters out.
  - Note that EventStore's "expected next number" check works because its `$all` positions are handed out under a single row update during the append. A store whose global positions can have gaps needs a different gap test.
- **After any reconnect, tell every subscription to catch up.** Postgrex documents that notifications sent during the gap are lost, and EventStore's listener has no code to trigger recovery itself.
- **Watch thread boundaries.** `asyncio.Queue` is documented as not thread-safe. If a synchronous psycopg listener runs on its own thread, the hand-off to an event loop must go through a thread-safe path.
- **Keep the listener connection idle and out of transactions.** PostgreSQL holds back notifications from a session that is inside a transaction until it ends. A session that sits in a transaction for a long time also blocks the server's notification queue from being cleaned up.
