# How should a consumer adapt its batch size and fast-path threshold to observed handler throughput so that immediate re-query does not outrun downstream processing or hold long-running read transactions?

## Question

A consumer that re-queries immediately whenever its last fetch came back full drains a backlog quickly. How should it size each fetch, and decide when a fetch counts as "full enough" to skip the wait, so that this fast path tracks what its handlers can actually absorb? And how should it avoid keeping a PostgreSQL read transaction or cursor open while slow handlers work?

## Findings

### The fast path measures backlog, not capacity

"Re-query immediately on a full batch" is a signal about the database: more rows are probably waiting. It says nothing about whether the handlers can take more work. Mature consumers keep two controls apart:

- **How much may be outstanding:** a demand or in-flight bound.
- **How often the database may be asked:** a fast-path rule plus a rate floor.

If the reader is decoupled from the handlers and has no demand bound, the fast path lets the reader outrun them. Events pile up in memory and the checkpoint falls behind what has been read. If the reader is coupled to the handlers through an open cursor or transaction, slow handlers keep that transaction open instead.

Production systems handle the first risk with demand-driven fetching:

- **Reactive Streams** makes this a specification rule. The number of elements delivered "MUST be less than or equal to the total number of elements requested", so that all buffer sizes are bounded and controlled by the subscriber.
- **Oban** computes `demand = meta.limit - map_size(running)` and fetches nothing when running jobs already reach the limit.
- **River** sizes parallelism per queue with `MaxWorkers`. It caps the fetch rate with `FetchCooldown`: "Jobs will only be fetched *at most* this often… Throughput is limited by this value" (default 100 ms). LISTEN/NOTIFY normally triggers fetches, with `FetchPollInterval` (default 1 s) as a fallback.
- **Kafka** recommends that when processing time varies unpredictably, processing moves to another thread and the consumer calls `pause()` to stop fetching until earlier records finish.
- **Python's `asyncio.Queue(maxsize=n)`** gives the same bound natively: `await put()` blocks once the queue holds `maxsize` items, until a `get()` removes one.

So the fast-path rule should be: re-query immediately only when the last fetch was full **and** there is free downstream capacity. Each fetch should request `n = min(batch_limit, free_capacity)` rather than a fixed maximum. Under sustained backlog the consumer then settles at handler throughput by construction. Notifications that arrive while there is no free capacity only need to set a "more work exists" flag. They should not trigger a query.

### Choosing the fast-path threshold

Two Postgres-backed implementations publish explicit bands:

- **Akka Persistence R2DBC** (event-sourcing queries over Postgres), with `refresh-interval = 3s`. The next query is "emitted immediately" when the previous one returned at least 90% of `buffer-size` (default 1000). Between 10% and 90% it waits half the refresh interval. At 10% or below, or with no rows, it waits the full interval. `buffer-size` is defined as the "in-memory buffer holding events when reading from database", so the threshold is relative to what the consumer is prepared to hold, not to an arbitrary page size.
- **Graphile Worker's `localQueue.refetchDelay`**. This option exists because at high scale "each time a new job comes in, each pool may request it, multiplying up the load".
  - When a fetch returns `threshold` jobs or fewer (default 0), the pool waits, on average, `durationMs` before asking again. While it waits, it mostly ignores new-job notifications.
  - It abandons the delay once it has been notified of `maxAbortThreshold` jobs (default `5 × localQueue.size`).
  - The documented cost model is about `(1000/durationMs) × INSTANCE_COUNT` fetch queries per second while work trickles in. Raising `durationMs` lowers database load and raises latency.

Taken together, a sound policy:

- Compare the returned row count with the **requested** `n`, not with the configured maximum. Once `n` shrinks to match free capacity, a page that fills `n` still signals backlog.
- Use a high band for immediate re-query, around 90% or more of `n`.
- Use a low band, roughly 0 to 10%, that triggers a randomised delay during which notifications are coalesced.
- Abort that delay once accumulated notifications show the work is real.
- Keep a hard cooldown floor between queries, as River does, so the query rate stays bounded even under constant notification.

### Adapting the batch size to observed throughput

Sizing rests on Little's law. The Netflix concurrency-limits library states it as "Limit = Average RPS * Average Latency". For a batch consumer this gives:

`batch_limit ≈ observed_handler_rate × target_batch_duration`

The target duration is the longest you are willing to let one batch's handling run. Several things depend on that time:

- how often the checkpoint advances
- how quickly the consumer reacts to shutdown or rebalancing
- how long any write transaction opened by the handler lasts

Kafka's history shows why an explicit bound matters:

- Before KIP-41, `poll()` could return an unbounded number of records, which made processing time per poll unpredictable.
- `max.poll.records` was added so users could "predict the maximum that must be handled within each poll interval".
- KIP-62 then set defaults of 500 records and a 5-minute `max.poll.interval.ms`. A consumer that exceeds that interval leaves its group.

AWS Lambda's event source mappings advise testing batch sizes "so that the polling frequency of each event source is tuned to how quickly your function is able to complete its task". They note that larger batches spread per-invoke overhead over more records. A batch closes on whichever comes first: record count, batching window, or a 6 MB payload limit. Akka Projections likewise groups by count or time (`group-after-envelopes = 20`, `group-after-duration = 500 ms`), and saves offsets after 100 envelopes or 500 ms. Bounding a batch by bytes as well as rows stops large payloads from inflating memory and fetch time.

None of these sources describes a *self-tuning* batch size for a database-polling consumer. Akka, Graphile Worker, River, Oban and Solid Queue all use static batch sizes and adapt only through demand gating. Solid Queue, for example, defaults to 3 worker threads, a 0.1 s polling interval and dispatcher batches of 500. The closest published controllers adapt concurrency limits instead, and their control laws carry over to batch size directly:

- **AIMD (Netflix `AIMDLimit`).** On a drop or timeout (default 5 s), multiply the limit by 0.9. Add 1 only when in-flight work is at least half the current limit, within a default range of 20 to 200. That growth condition matters: it prevents the limit creeping up while it is not the bottleneck.
- **Gradient (Envoy, Netflix Gradient2).**
  - `limit_new = gradient × limit_old + headroom`, where `gradient = (minRTT + buffer) / sampleRTT`.
  - Headroom is fixed at √limit.
  - Every so often the limit is pinned to its minimum to re-measure baseline latency.
- **Vegas.** Estimates queueing as `L × (1 − minRTT/sampleRTT)` and moves the limit by ±1 around small thresholds.

Mapped to an event consumer, with per-batch handling time standing in for RTT:

- Keep an exponentially weighted moving average of handler throughput.
- After a *full* batch that finished under target, grow the limit additively, or set it towards `rate × target`.
- After a batch that ran over target, or a handler error or timeout, cut it multiplicatively.
- Clamp the limit between a floor and a ceiling.

This mapping is an inference from the sources above, not a pattern those sources document for event stores. For a strictly ordered per-subscription consumer, batch size is the main lever. Where events can be handled in parallel, for example per stream, a concurrency limit is a separate lever with its own controller.

### Never let handler pace set the length of a read transaction

The fetch and the handling should run in separate transactions. Read each batch with a keyset predicate (`position > last_seen ORDER BY position LIMIT n`) in autocommit mode or a short explicit transaction, then load the rows into client memory and end the transaction before any handler runs. PostgreSQL warns that rows skipped by `OFFSET` "still have to be computed inside the server", so keyset paging keeps fetch cost flat as a subscription advances.

This matters because psycopg 3 starts a transaction even for a plain `SELECT` when not in autocommit mode. A long-running program then sits *idle in transaction*: "locks are held by the session, tables bloat". PostgreSQL's documentation adds that "an open transaction prevents vacuuming away recently-dead tuples that may be visible only to this transaction".

Streaming constructs that look like a way to get large batches cheaply tie the database to handler speed:

- **Server-side cursors.** A cursor without `WITH HOLD` lives only inside its transaction. One declared `WITH HOLD` is materialised into temporary storage when the transaction commits. psycopg notes that server cursors use server memory and resources until they are closed. Its default `itersize` is 100.
- **`Cursor.stream()`.** It leaves the connection ACTIVE until the iterator has been fully consumed. Interleaving handler work with iteration therefore keeps the statement running for as long as the handlers take.

The batch ceiling should therefore come from client memory and the batch-duration target, not from cursor mechanics.

Server-side timeouts are backstops, not a control mechanism. Set them per role or session for consumer connections. PostgreSQL advises against setting them globally in `postgresql.conf`, because they would affect every session.

- `statement_timeout` bounds the fetch query.
- `idle_in_transaction_session_timeout` terminates sessions that stay idle inside a transaction.
- `transaction_timeout`, added in PostgreSQL 17, bounds the whole transaction.

If handlers write projections to the same database, the batch size also sets how long those write transactions last. Marten's async daemon caps concurrent event-page loads and projection batch writes at 4 per database by default for this reason.

### Summary policy

1. Track free capacity using an in-flight count or a bounded queue. Fetch `n = min(limit, free)` rows, and only when `free > 0`.
2. Treat roughly 90% or more of `n` as a fast-path hit and re-query as soon as capacity frees, never faster than a cooldown floor.
3. Treat 10% or less as a slack signal: use a randomised delay that coalesces notifications and aborts after enough of them.
4. Adapt `limit` towards `observed_rate × target_batch_duration` using AIMD-style growth on full, fast batches and multiplicative cuts on slow or failed ones, within fixed bounds and with a byte cap.
5. Fetch in short autocommit reads with keyset paging. Hold no cursor or transaction across handling, and keep the timeouts above as backstops.
