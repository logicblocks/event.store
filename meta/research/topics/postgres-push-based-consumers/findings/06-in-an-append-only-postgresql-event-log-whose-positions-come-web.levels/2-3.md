# How does consuming an append-only PostgreSQL event table through logical decoding compare with LISTEN and NOTIFY plus watermark queries for commit-ordered, gap-free delivery to Python consumers, and what client support exists for it?

## Question

An append-only event table gets its positions from a `BIGSERIAL` sequence, so concurrent transactions can commit out of position order. How does tailing that table through PostgreSQL logical decoding (a replication slot plus an output plugin) compare with LISTEN and NOTIFY plus a transaction-id or snapshot watermark query? The comparison covers commit ordering, gap-freedom, latency, durability and operating cost. Which Python clients, especially psycopg 3, can consume a logical replication stream?

## Findings

### Summary

Logical decoding delivers commit-ordered, gap-free events by construction. The server decodes each committed transaction as a single unit, in commit order. It never emits aborted transactions, and a crash-safe replication slot records how far the consumer has confirmed. The consumer therefore never sees the "late commit of an earlier position" problem, and it needs no watermark query.

That guarantee has costs:

- **Stream order is commit order, not position order.** A consumer can see position 11 before position 10.
- **Delivery is at-least-once.** Duplicates can arrive after a crash.
- **A slot cannot replay history** from before its confirmed position.
- **Operations are heavier.** The server needs `wal_level = logical`, consumers need replication privileges, and each slot allows only one receiver. Slots retain WAL and catalog rows and can be invalidated, and surviving failover takes extra configuration.
- **Python support is thin.** psycopg2 is the only mainstream Python driver with a full streaming-replication API. psycopg 3 and asyncpg have none, apart from a small psycopg 3 change that stops `START_REPLICATION` from raising an error.

LISTEN and NOTIFY with an xid8 watermark has different trade-offs. It runs on ordinary connections with no server reconfiguration. Its delivery latency, however, is bounded by the oldest open transaction in the cluster.

### What logical decoding guarantees

The PostgreSQL output-plugin documentation is explicit about ordering: "Concurrent transactions are decoded in commit order, and only changes belonging to a specific transaction are decoded between the `begin` and `commit` callbacks." It also says that "Transactions that were rolled back explicitly or implicitly never get decoded."

The `pgoutput` wire protocol makes the same point: "The logical replication protocol sends individual transactions one by one. This means that all messages between a pair of Begin and Commit messages belong to the same transaction." Each Begin message carries the transaction's final (commit) LSN, its commit timestamp and its xid.

Large transactions are decoded incrementally and may spill to disk. However, "all the decoded changes have to be transmitted when the transaction finally commits (or more precisely, when the commit is decoded from the transaction log)." An output plugin can optionally stream in-progress transactions. `pgoutput` does this when `streaming` is set to `on` or `parallel`; the default is `off`. Even then, "the changes are still applied in commit order." Streamed blocks can still end in a Stream Abort, though. An event-store consumer that must only ever see committed events should leave streaming off.

Two consequences follow for an event table keyed by a `BIGSERIAL` position:

- **No skipped events, and no watermark.** Every committed row reaches the slot consumer exactly once in normal operation, in the order its transaction committed. The consumer needs no `pg_snapshot_xmin` comparison, gap timeout or serialised append.
- **Not delayed by other open transactions.** Each transaction is sent when its own commit record is decoded. A long-running or idle-in-transaction session elsewhere therefore does not hold back delivery of other committed events. This is an inference from the commit-time transmission rule above. In contrast, the xid8 watermark filter `transaction_id < pg_snapshot_xmin(pg_current_snapshot())` hides everything newer than the oldest running transaction. Dudycz notes that with that approach "our queries may be a bit delayed if our transactions last long."
- **Position order differs from stream order.** Positions are allocated when the row is inserted, but the stream is in commit order. The consumer must therefore checkpoint by commit LSN, or by xid and LSN, rather than by "highest position seen." Any API that promises strictly increasing positions to subscribers must either reorder events or redefine its ordering contract as commit order.

### Durability, duplicates and replay

A slot "will emit each change just once in normal operation". After a crash, however, "the slot might return to an earlier LSN, which will then cause recent changes to be sent again." Clients "are responsible for avoiding ill effects from handling the same message more than once." The documentation suggests that clients record the last LSN they processed and skip repeats.

The client acknowledges progress with a Standby status update. In psycopg2's terms, the `flush_lsn` is the "LSN position up to which the client has processed the data reliably."

`START_REPLICATION SLOT ... LOGICAL` begins at the requested LSN or the slot's `confirmed_flush_lsn`, "whichever is greater." The view documentation adds that "Data corresponding to the transactions committed before this LSN is not available anymore." A slot is therefore only a live-tail cursor. A new subscriber, a replay from position zero, or recovery after slot loss must read the event table itself.

PostgreSQL provides a gap-free handoff point for this. When a slot is created over the replication protocol, "a snapshot is exported, which will show exactly the state of the database after which all changes will be included in the change stream." A client can read the table under `SET TRANSACTION SNAPSHOT` and then stream the slot, "without losing any changes." `CREATE_REPLICATION_SLOT` accepts `SNAPSHOT 'export'`, `'use'` or `'nothing'`.

### Comparison with LISTEN and NOTIFY plus watermark queries

| Concern | Logical decoding slot | LISTEN and NOTIFY plus watermark query |
|---|---|---|
| Ordering source | Server decodes transactions in commit order | NOTIFY: "messages from different transactions are delivered in the order in which the transactions committed". The table query must still sort by xid and position under a snapshot watermark. |
| Skipping late commits | Impossible by construction | Prevented only by the watermark, for example `transaction_id < pg_snapshot_xmin(pg_current_snapshot())` ordered by `(transaction_id, position)` |
| Latency under long transactions | Unaffected for other transactions (inference) | Held back to the oldest running transaction's xmin |
| Durable cursor | Server-side slot (`confirmed_flush_lsn`), crash-safe, at-least-once | Session-scoped: notifications carry no durable position, and the consumer stores its own checkpoint |
| Replay from history | Not possible from the slot; must read the table | Native: the same query serves catch-up and live tail |
| Many consumers | "Only one receiver may consume changes from a slot at any given time"; usually one slot per consumer | Any number of listeners per channel |
| Server prerequisites | `wal_level = logical` (restart), replication privilege, slot and WAL-sender capacity | None beyond ordinary connections |
| Failure modes | WAL and catalog retention, slot invalidation, failover gaps | 8 GB notification queue ("transactions calling `NOTIFY` will fail at commit" when full); cleanup blocked by a listener in a long transaction |
| Payload | Full row images (or `pg_logical_emit_message` content) | At most about 8000 bytes, so usually a wake-up only |

A hybrid design is also possible. An append transaction can call `pg_logical_emit_message(transactional => true, ...)`. That message "should be part of the current transaction" and is decoded in commit order with the transaction's rows. `pgoutput` forwards such messages when its `messages` option is enabled. This gives a NOTIFY-like signal that is durable and commit-ordered. It is only reachable through a slot, however.

### Operating cost and constraints

- **WAL level.** In PostgreSQL 18, `wal_level` "can only be set at server start", and logical decoding needs `logical`. The PostgreSQL 19 documentation (19 Beta 4, 24 September 2026) adds automatic behaviour: with `wal_level = replica`, the server "automatically increases the effective WAL level to `logical` when creating the first logical replication slot." It reports the result through `effective_wal_level`.
- **Managed services.** On Amazon RDS this requires the static `rds.logical_replication` parameter, a reboot and the `rds_replication` role. AWS warns that an unread slot can "quickly fill up your DB instance's storage."
- **Capacity.** `max_replication_slots` and `max_wal_senders` both default to 10 and can only be set at server start. The replication commands `CREATE_REPLICATION_SLOT` and `START_REPLICATION` "are only available over a replication connection; they cannot be used via SQL."
- **Retention.** Slots "will prevent removal of required resources even when there is no connection using them": neither WAL nor needed catalog rows can be vacuumed. "In extreme cases this could cause the database to shut down to prevent transaction ID wraparound."
  - `max_slot_wal_keep_size` (default `-1`, unlimited) caps retained WAL by invalidating the slot. PostgreSQL 18 adds `idle_replication_slot_timeout` (default `0`, off).
  - `pg_replication_slots` exposes `wal_status` (`reserved`, `extended`, `unreserved` or `lost`), `safe_wal_size`, `inactive_since` and `invalidation_reason` (`wal_removed`, `rows_removed`, `wal_level_insufficient` or `idle_timeout`).
  - An invalidated slot cannot resume. The consumer must fall back to reading the table and create a new slot.
- **Failover.** A slot survives promotion only if it was created with `failover = true` and the standby runs `sync_replication_slots`. The standby also needs a physical slot and `hot_standby_feedback`. `synchronized_standby_slots` is recommended so that logical consumers never get ahead of the standby.
- **Output plugins.** `pgoutput` and `test_decoding` ship with PostgreSQL. `pgoutput` uses a binary protocol and requires a publication; protocol versions 2 to 4 add streaming, two-phase commit and parallel apply. `wal2json` is a third-party plugin that emits JSON per transaction (format 1) or per tuple (format 2).
  - PostgreSQL 18.6 (13 August 2026, CVE-2026-6471) and the matching minor releases of 14 to 17 restrict output plugins to a new `output_plugin_libraries` allowlist. By default it contains only `pgoutput` and `test_decoding`, so `wal2json` users must add it explicitly.
  - On upgrades from version 17 or later, `pg_upgrade --check` now fails if the new cluster's allowlist omits a plugin used by an existing slot.
- **Connection poolers.** PgBouncer 1.23.0 (3 July 2024) added "support for replication connections through PgBouncer." Its configuration reference does not document pool-mode constraints for them.

### Python client support

- **psycopg2: full support.**
  - `LogicalReplicationConnection` and `ReplicationCursor` provide `create_replication_slot`, `start_replication(slot_name, decode, start_lsn, options, status_interval)` and `send_feedback(write_lsn, flush_lsn, apply_lsn, ...)`.
  - Messages can be consumed with the blocking `consume_stream`, or with `read_message` for loops based on `select` or `poll`.
  - Each `ReplicationMessage` exposes `payload`, `data_start`, `wal_end` and `send_time`.
  - Decoding is left to the application. `wal2json` and `test_decoding` produce text, while `pgoutput` produces binary that needs a parser.
  - The documentation warns that failing to consume and acknowledge "can eventually lead to 'disk full' condition on the server."
  - psycopg2 (latest 2.9.13) is "actively maintained, but it is not expected to receive new features", and its maintainers point new projects to psycopg 3. A psycopg 3 library would therefore need psycopg2 as an extra dependency just for the slot connection.
- **psycopg 3: no replication API.**
  - The tracking issue (#71, opened August 2021) is still open. In 2023 the maintainer wrote: "Replication support is not implemented in psycopg 3. It needs complete redesign and implementation."
  - PR #1219, merged 24 November 2025 and aimed at 3.3, only stops `conn.execute("START_REPLICATION ...")` on a `replication="database"` connection from failing; the cursor now ends in `COPY_BOTH` status. The maintainer stated that "No further replication support is planned for release 3.3", and the psycopg 3 release notes up to 3.3.6 do not mention it.
  - Community proof-of-concepts exist: a 2025 "bridge" that switches to raw socket I/O with a hand-written `pgoutput` parser, and a May 2026 draft PR (#1311). In May 2026 the maintainer said he was working on a different design. As of October 2026 there is no supported psycopg 3 streaming API.
- **asyncpg: none.** The issue requesting replication-protocol support (#91) has been open since 2017.
- **pypgoutput: prototype only.** It parses `pgoutput` messages on top of psycopg2's replication connection, and it states that it "is a prototype and not production tested."
- **The SQL interface works on psycopg 3 today.** `pg_logical_slot_peek_changes`, `pg_logical_slot_get_changes` and `pg_replication_slot_advance` run on an ordinary connection.
  - They return whole transactions. `upto_lsn` "will include only those transactions which commit prior to the specified LSN", and the `upto_nchanges` limit is only checked after each decoded commit.
  - `get_changes` consumes changes as it returns them. Peeking, processing durably and then advancing the slot gives at-least-once semantics.
  - This is a pull interface, so it still needs a wake-up such as NOTIFY or a timer. It does, however, replace the watermark logic with server-side commit ordering.

### Assessment for a psycopg 3 event store

Logical decoding is the stronger correctness primitive for a live tail. It is commit-ordered and gap-free, and it is not delayed by unrelated long transactions. Several things limit it as the primary delivery path:

- It cannot replay history.
- Its slots are invalidated under retention limits.
- It needs one slot per independent receiver.
- It requires server-level configuration and privileges that many deployments lack.
- Its psycopg 3 support is effectively absent.

The event table must stay the source of truth for catch-up and recovery in any case. A plausible design therefore treats logical decoding as an optional accelerator: a single dispatcher tails one slot, checkpoints by commit LSN and fans events out in-process. It runs either on psycopg2 or on the SQL slot functions under psycopg 3. LISTEN and NOTIFY plus the xid8 watermark remains the zero-configuration default. This recommendation is an inference from the sources, not a documented pattern.
