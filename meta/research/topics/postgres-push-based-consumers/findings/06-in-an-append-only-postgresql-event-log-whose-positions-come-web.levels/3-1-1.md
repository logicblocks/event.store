# How do asynchronous-standby failover and point-in-time recovery, which can reissue transaction ids and positions past the recovery point, affect event-store consumer checkpoints held outside the database, and how can consumers detect such a rewind?

## Question

When a PostgreSQL event store fails over to an asynchronous standby, or is restored to an earlier point in time, the database's history is cut back. Transaction ids (xids), `BIGSERIAL` positions and WAL positions (LSNs) after the cut can then be handed out again to different data. What does that do to consumer checkpoints held outside the database, and how can a consumer detect that the history it has already consumed was rewound?

## Findings

### How the history gets cut back

**Asynchronous failover loses committed transactions.** The PostgreSQL documentation says plainly that streaming replication "is asynchronous by default. If the primary server crashes then some transactions that were committed may not have been replicated to the standby server, causing data loss. The amount of data loss is proportional to the replication delay at the time of failover." Patroni gives the operational bound. In asynchronous mode "the cluster is allowed to lose some committed transactions to ensure availability", and the loss is "worst case bounded by `maximum_lag_on_failover` bytes of transaction log plus the amount that is written in the last `ttl` seconds." A consumer reading from the primary can therefore process events that the promoted standby never received. pg_rewind then makes the loss permanent on the old primary: it "examines the timeline histories of the source and target clusters to determine the point where they diverged" and overwrites the blocks the old primary changed after that point.

**Synchronous replication narrows the gap but does not close it.** With `synchronous_commit` at `on` or `remote_apply` and a synchronous standby, "the only possibility that data can be lost is if both the primary and the standby suffer crashes at the same time." Patroni's `synchronous_mode` will not promote a standby "unless it is certain that the standby contains all transactions that may have returned a successful commit status to client." That guarantee covers acknowledged commits only. If a backend's wait for the standby is cancelled, PostgreSQL warns that "the transaction has already committed locally, but might not have been replicated to the standby". Patroni notes that such changes "become visible for other backends… and may be lost in case of standby promotion." So a push-woken consumer can still see an event that later disappears, even on a synchronous cluster.

**Point-in-time recovery creates a branch.** "Whenever an archive recovery completes, a new timeline is created to identify the series of WAL records generated after that recovery." PostgreSQL writes a timeline history file "that shows which timeline it branched off from and when." The documentation calls the abandoned WAL a different "history of the database universe". Everything a consumer read from that abandoned history no longer exists in the restored database.

### What gets reissued

- **Positions from a sequence.** Sequences pre-log values: `SEQ_LOG_VALS` is 32, and "in the event of crash we can lose (skip over) as many values as we pre-logged." When `nextval` writes that WAL record, it acquires an xid "so this transaction's commit will trigger a WAL flush and wait for syncrep". So the sequence state the standby holds is whatever pre-log record reached it. If the record covering the lost values replicated, the new primary resumes beyond them, leaving a gap. If that record was in the lost WAL tail, the new primary hands out the same position numbers again, for different events. (This gap-or-reuse outcome is inferred from the source comments, not stated in the documentation.) The sequence documentation warns that to use a value "for persistent outside-the-database purposes, make sure that the `nextval` call has been committed before doing so". Under asynchronous replication, a commit on the old primary is not enough.
- **Transaction ids.** During recovery, `nextXid` is only advanced past xids found in the replayed WAL. `AdvanceNextFullTransactionIdPastXid` "must only be called during recovery or from two-phase start-up code". The xids of lost transactions are therefore assigned again to new transactions. The 64-bit `xid8` epoch carries on from the replayed history, so stored `xid8` values stay comparable but can alias different transactions.
- **LSNs.** The new timeline's WAL starts at the switch point, so LSNs past that point are reused for different records. Only the timeline ID tells the two apart. The timeline ID is part of every WAL file name.
- **System identifier.** This does not change on failover or point-in-time recovery. The replication protocol describes it as "the unique system identifier identifying the cluster", useful "to check that the base backup used to initialize the standby came from the same cluster". A changed identifier means the consumer is talking to a different cluster, not that history was rewound.

### Effect on external checkpoints

A checkpoint held outside the database can end up ahead of the database's new history. There are three consequences:

1. **Phantom events.** Projections or side effects built from events that no longer exist.
2. **Skipped events.** New events that reuse positions at or below the checkpoint are never delivered.
3. **Wrong watermarks.** A stored snapshot-xmin or `xid8` watermark from the lost history makes new transactions with reused xids look already consumed.

Kafka hit the same problem with unclean leader election. KIP-320 explains that new data can be written "so that the consumer's fetch offset becomes valid again. In this case, the consumer will just miss whatever data had been written between the truncation point and its fetch offset." Checkpoints kept in the same PostgreSQL database, and updated in the same transaction as the projection, rewind together with the log and stay consistent. Only state outside that database diverges.

Notifications do not help. `LISTEN` and `NOTIFY` are rejected on a hot standby, so notifications are not replicated. After promotion, a listener must reconnect to the new primary and resume by querying from its checkpoint, which is exactly the moment a rewind check belongs.

### Detecting a rewind

A layered check works best. Each layer below is a design inference from the mechanisms above, apart from the quoted PostgreSQL and Kafka behaviour.

1. **Cheap bounds check (necessary, not sufficient).** On reconnect, compare the checkpoint position with the table's maximum position. For `xid8` watermarks, call `pg_xact_status(stored_xid8)`: PostgreSQL raises "transaction ID … is in the future" for any xid not yet assigned. A checkpoint beyond the current end proves a rewind. The check stops working once new appends pass the old values, so it cannot be the only defence.
2. **Identity check (robust).** Store the last consumed event's unique id, or a hash of the last few ids, alongside the position. On resume, confirm that the row at that position still carries the same id. This still catches the rewind after positions have been reused, and costs one indexed lookup.
3. **Timeline epoch, the PostgreSQL version of Kafka's leader epoch.** KIP-320 stores "the leader epoch" with committed offsets and validates it against the new leader, raising `LogTruncationException` "to reset state if needed or revert changes to downstream systems". The PostgreSQL version works like this:
   - **Store the timeline with the checkpoint.** On a primary, `pg_split_walfile_name(pg_walfile_name(pg_current_wal_lsn()))` returns the current timeline ID. `pg_walfile_name` composes the name from `GetWALInsertionTimeLine()` and errors during recovery; `pg_split_walfile_name` needs PostgreSQL 16 or later. The `IDENTIFY_SYSTEM` replication command also returns the timeline. `pg_control_checkpoint().timeline_id` comes from the last checkpoint and may lag just after a promotion.
   - **Store an LSN upper bound with the checkpoint.** Record `pg_current_wal_insert_lsn()` after each read returns. It is an upper bound on the commit LSN of everything that read could see.
   - **Compare against the switch point when the timeline changes.** Fetch the history file with the `TIMELINE_HISTORY` replication command, or read it from the archive. If the stored bound is at or before the switch point, the checkpoint lies in shared history and is safe; a lossless switchover also bumps the timeline. If it is past the switch point, fall back to the identity check.

   Also store the system identifier from `pg_control_system()`, to catch the consumer being pointed at a different cluster.

### Preventing it

- **Synchronous commit.** Synchronous replication with `synchronous_standby_names` (`FIRST` or `ANY` quorum), or Patroni `synchronous_mode` and `synchronous_mode_strict`, prevents losing acknowledged appends. It cannot stop a cancelled sync wait from exposing an unreplicated event.
- **Gate delivery on standby confirmation.** PostgreSQL already does this for logical failover slots. With `synchronized_standby_slots`, logical walsenders "send decoded changes to plugins only after the specified replication slots confirm receiving WAL", and the documentation states that "the standby server must be ahead of the subscriber". An event store could do the same for push consumers: release a batch only once a standby's `flush_lsn` in `pg_stat_replication` has passed the batch's LSN bound. The cost is extra wake-up latency roughly equal to the replication lag.
- **Recover by re-reading.** Debezium's answer to failover is to re-snapshot. Its `always` snapshot mode "ensures that the connector does not miss any changes that were made after the new primary had been promoted". An event store that detects a rewind should either stop with an explicit error, as `LogTruncationException` does, or reset the consumer to its last verified position and rebuild the affected projections.
