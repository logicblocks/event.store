# How can an event-store consumer pair a temporary logical replication slot for the live tail with ordinary table reads for catch-up, so that slot loss, invalidation or failover causes neither missed events nor more redelivery than idempotent handling can absorb?

## Question

How can an event-store consumer use a temporary logical replication slot for the live tail and ordinary table reads for catch-up, so that losing the slot (through disconnection, invalidation or failover) neither drops events nor causes more redelivery than idempotent handlers can absorb?

## Findings

### Summary

Treat the events table as the only source of truth and the temporary slot as a low-latency transport you can throw away. Two rules make the pairing safe:

1. **Store the checkpoint in table terms.** The durable checkpoint must be something a plain table read can resume from. A slot LSN does not qualify, because it disappears with the session that owns a temporary slot.
2. **Join every slot attachment to the table through the slot's exported snapshot.** When PostgreSQL creates a slot over the replication protocol, it can export a snapshot that marks exactly where the slot's change stream begins. Reading the gap through that snapshot leaves no hole and no overlap.

With both rules in place, every way of losing the slot has the same recovery: reconnect, create a fresh temporary slot, read the delta between the durable checkpoint and the new slot's snapshot, then stream. The snapshot handoff prevents missed events. How stale the durable checkpoint is allowed to get sets the limit on redelivery.

The attachment protocol and checkpoint scheme below are put together from documented PostgreSQL behaviour. PostgreSQL does not publish them as a recipe. Where a step depends on inference rather than a documented guarantee, the text says so.

### What PostgreSQL guarantees

- **Temporary slots are tied to the session.** They "are not saved to disk and are automatically dropped on error or when the session has finished". The SQL function form describes the slot as "only meant for use by the current session" and "released upon any error".
- **Slot creation exports a snapshot that matches the stream boundary.** `CREATE_REPLICATION_SLOT` returns a `consistent_point` LSN and a `snapshot_name`. The exported snapshot "will show exactly the state of the database after which all changes will be included in the change stream". The documentation describes reading the database through it with `SET TRANSACTION SNAPSHOT` and then applying the slot's contents "without losing any changes". There are two ways to use it:
  - `SNAPSHOT 'export'` cannot run inside a transaction. The exported snapshot stays valid until the next command on the replication connection, or until that connection closes. Importing it requires a `REPEATABLE READ` or `SERIALIZABLE` transaction, and `SET TRANSACTION SNAPSHOT` must come before the transaction's first query.
  - `SNAPSHOT 'use'` applies the snapshot to the current transaction on the replication connection itself. `CREATE_REPLICATION_SLOT` must be the first command in that transaction.

  The SQL function `pg_create_logical_replication_slot` returns only `(slot_name, lsn)` and no snapshot. An exact handoff therefore needs the replication protocol.
- **The stream has no gaps while connected, and it arrives in commit order.** "Concurrent transactions are decoded in commit order", and rolled-back transactions "never get decoded". Within one connected session, the live tail has none of the gap problems pollers face. The trade-off is that the stream follows commit order, not the order of pre-allocated sequence positions.
- **Delivery is at least once.** A slot's position "is persisted only at checkpoint, so in the case of a crash the slot might return to an earlier LSN", and clients "are responsible for avoiding ill effects from handling the same message more than once". `START_REPLICATION` resumes from whichever is greater: the requested LSN or the slot's `confirmed_flush_lsn`.
- **Streaming of in-progress transactions is opt-in.** If it is enabled, large transactions can be streamed before they commit, and some of them may later abort. A consumer that leaves it off only ever receives committed transactions, still in commit order.
- **The stream carries transaction identity.** Every pgoutput `Begin` message carries the transaction's final LSN, commit timestamp and 32-bit xid. Every `Commit` message carries the commit LSN and the end LSN.

### Ways the slot is lost, and how to detect each

1. **The session ends.** A network error, consumer crash, restart or server-side error drops the temporary slot. Abrupt disconnects "might leave an orphaned connection slot behind until a timeout is reached", and `wal_sender_timeout` defaults to 60 seconds. Practical consequences:
   - Give each attachment a unique slot name, so that reattaching does not collide with a slot an orphaned walsender still holds.
   - Leave headroom in `max_wal_senders` and `max_replication_slots`. Both default to 10.
2. **WAL retention is exceeded.** When `max_slot_wal_keep_size` is set, a slot whose `restart_lsn` falls too far behind moves through `wal_status` `unreserved` to `lost`, with `invalidation_reason = wal_removed`.
   - If the slot is in use, the server signals the owning process to terminate ("terminating process %d to release replication slot"). For a temporary slot, that ends the session and drops the slot, so the consumer sees a connection error and takes the normal resync path.
   - A consumer can watch `safe_wal_size` and detach on its own terms before this happens.
   - Acknowledging handled commit LSNs in standby status updates lets the server recycle WAL while the session is alive.
3. **The slot sits idle.** `idle_replication_slot_timeout` (PostgreSQL 18) invalidates slots that have not been used by a replication connection for longer than the setting, with reason `idle_timeout`. It does not apply to synced standby slots.
4. **Standby-specific invalidation.** `rows_removed` and `wal_level_insufficient` apply only to logical slots on a standby, so they matter only if the consumer decodes from a standby.
5. **Failover.** A temporary slot can never follow a failover:
   - The server rejects creating one with failover enabled ("cannot enable failover for a temporary replication slot").
   - The documented failover-readiness check requires `synced AND NOT temporary AND invalidation_reason IS NULL`.

   After every promotion, the consumer must create a new temporary slot on the new primary and resync from its table-based checkpoint. `synchronized_standby_slots`, which stops logical walsenders from sending changes before a physical standby has received them, only applies to failover slots. The server skips the wait when the acquired slot "is not a logical failover slot". So a temporary-slot consumer with an asynchronous standby can handle events that the new primary never received.

   There is a further hazard, inferred rather than documented. The new primary continues the replicated xid space and can reissue xids that the lost history had used. A checkpoint built on xid snapshots could then wrongly treat new transactions as already handled. On reconnect, the consumer should compare its stored snapshot's `xmax` with the new primary's current snapshot, and treat a checkpoint that is "ahead of" the server as a sign of lost history rather than resuming from it.

### Checkpoints: why "max position" fails, and what to store instead

The live tail arrives in commit order, but event positions are allocated before commit. A transaction holding a lower position can therefore commit after one holding a higher position. Two problems follow:

- **Resuming from the highest position skips events.** If the consumer stores the highest position it has handled and later resumes the table read with `position > p`, it skips every lower-positioned event that committed late. Pollers face the same gap hazard.
- **Deduplicating by position discards events.** Dropping stream events with `position <= last handled` would throw away exactly those late commits.

A safe checkpoint describes *which transactions* have been handled, not which positions:

- Record the writing transaction on every event row as `transaction_id xid8 DEFAULT pg_current_xact_id()`. Practitioners already use this column to make pollers gap-safe.
- Store the checkpoint as a `pg_snapshot` `S`, meaning "every transaction visible in `S` has been fully handled".
- Resume with `transaction_id >= pg_snapshot_xmin(S) AND NOT pg_visible_in_snapshot(transaction_id, S)`. An index on `transaction_id` turns this into a range scan bounded below by `S`'s `xmin`.

`pg_visible_in_snapshot` answers whether a transaction "was completed before the snapshot was taken", using the snapshot's `xmin`, `xmax` and in-progress list.

### Attaching a slot without a gap or overlap

1. **Bulk catch-up without a slot.** Use the ordinary, gap-safe polling read until the consumer is close to the head. Doing the bulk read before creating the slot avoids two costs: a temporary slot retaining WAL during a long read, and an imported `REPEATABLE READ` snapshot pinning the cluster's xmin horizon for that whole time.
2. **Create the slot.** Open a replication connection and issue `CREATE_REPLICATION_SLOT <unique-name> TEMPORARY LOGICAL pgoutput`, with either:
   - `SNAPSHOT 'export'`, then import the snapshot into a `REPEATABLE READ` transaction on an ordinary connection; or
   - `SNAPSHOT 'use'`, inside a transaction on the replication connection.

   Slot creation does not return until it reaches a consistent state. The snapshot builder only becomes `CONSISTENT` "once all those previously running transactions have committed or aborted", so a long-running or idle-in-transaction session stalls attachment. Bound the wait with a timeout and keep polling meanwhile.
3. **Read the delta in the snapshot.** Read events whose transaction is not visible in the stored checkpoint, and capture `S0 = pg_current_snapshot()`. In the PostgreSQL source this function reads the backend's *active* snapshot (`GetActiveSnapshot()`), which under `REPEATABLE READ` should be the imported slot snapshot. Hand the delta to the handlers.
4. **Start streaming.** Close the snapshot transaction and issue `START_REPLICATION SLOT ... LOGICAL <consistent_point>` with a publication limited to the events table. In `'export'` mode, the import must happen before the replication connection runs its next command.
5. **Advance the checkpoint.** Once the delta has been handled, the durable checkpoint becomes `S0`. The stream contains exactly the transactions that commit after `S0`, so this boundary adds no duplicates and no gaps.

### Moving the checkpoint forward during streaming

Streamed transactions are identified by LSN and xid, but the checkpoint has to be a table-readable snapshot. Converting "handled through commit LSN L" into such a snapshot takes a watermark, a technique similar to DBLog's use of low and high watermarks to interleave table reads with log events without locking:

- **Watermark message (inferred).** Periodically run `SELECT pg_logical_emit_message(false, 'ckpt', pg_current_snapshot()::text)` on an ordinary connection. A non-transactional message is "written immediately and decoded as soon as the logical decoder reads the record". Every transaction visible in the captured snapshot committed before the statement started, so its commit record should come before the message in WAL. When the message arrives and everything before it has been handled, persist the embedded snapshot as the checkpoint. This needs pgoutput's messages option. The ordering argument is inferred and still needs confirming.
- **LSN fence.** Take `S_t = pg_current_snapshot()`, then `L_t = pg_current_wal_insert_lsn()`. The insert location is "the 'logical' end of the write-ahead log at any instant", so every commit visible in `S_t` lies before `L_t`. Persist `S_t` once the consumer has handled a commit whose LSN is at or beyond `L_t`. On a quiet system no such commit may come along for a while; in that case the existing checkpoint simply stays in place.

Either way, the redelivery a slot loss can cause is limited to transactions handled since the last persisted checkpoint. With a checkpoint every N transactions or T seconds, the bound is roughly N, or T times throughput. Handlers can deduplicate exactly within that window by event id or by `(transaction_id, position)`. Anchoring the checkpoint only at attachment time, and never advancing it, would make redelivery grow with session length, which is not acceptable for long-lived consumers.

### Temporary versus persistent failover slots

- **Persistent failover slots (PostgreSQL 17+)** can keep their position across a promotion. They require all of the following: `failover = true`, `sync_replication_slots` and `hot_standby_feedback` on the standby, `primary_slot_name`, and ideally `synchronized_standby_slots` on the primary. The cost is that persistent slots "prevent removal of required resources even when there is no connection using them": both WAL and catalog rows. In extreme cases this risks a wraparound shutdown.
- **Temporary slots** never leave orphaned retention behind. The price is a table delta on every reattachment, which the snapshot handoff makes exact.

The same pattern shows up elsewhere. Debezium's `when_needed` mode re-snapshots when "a previously recorded offset specifies a log position that is not available on the server", and its incremental snapshots run "in parallel with streamed data capture" using watermark windows. One practitioner push-based outbox design uses a persistent slot with status-update acknowledgements, and its author explicitly leaves fault tolerance and failover unresolved.

### Capacity

Each slot ties up a walsender and decodes the WAL stream independently, and the defaults allow 10 slots and 10 walsenders. A temporary slot per subscription will not scale to hundreds of subscriptions. One slot per consumer process, fanned out to subscriptions inside the process, keeps the slot count small.
