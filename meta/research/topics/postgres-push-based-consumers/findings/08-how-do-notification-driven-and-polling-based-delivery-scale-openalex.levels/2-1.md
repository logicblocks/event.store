# How does PostgreSQL serialise committing transactions that issue NOTIFY, and what commit throughput and notification latency have engineering benchmarks measured as notifying writers, listening sessions and channels increase?

## Question

How does PostgreSQL serialise the commits of transactions that issue NOTIFY,
and what commit throughput and notification latency have engineering
benchmarks measured as the number of notifying writers, listening sessions and
channels grows?

## Findings

The scholarly literature indexed by OpenAlex does not answer either part of
this question. No indexed work explains how PostgreSQL orders or serialises
the commits of transactions that run NOTIFY. No indexed work reports
benchmarks of commit throughput or notification latency as notifying writers,
listening sessions or channels are added. Catalogue queries aimed at
PostgreSQL LISTEN and NOTIFY performance return no records. Queries aimed at
PostgreSQL as a message queue or broker, with latency and throughput
measurements, return none either. The gap is a property of the peer-reviewed
record, not of the topic. NOTIFY's commit-path behaviour and its measured cost
are documented outside academic venues: in PostgreSQL's own documentation,
its source code and mailing-list discussions, and in practitioner write-ups.

The nearest scholarly work is a research programme by Luis Vargas, Jean Bacon
and Ken Moody at Cambridge. It joins active databases to publish/subscribe
middleware, using PostgreSQL and the Hermes event-based middleware as its test
setting. Their workshop paper, "Integrating databases with publish/subscribe",
describes an architecture in which each database manager defines and
advertises change events. Clients subscribe to those events, rather than
registering continuous queries against the database. An advertised event can
span several physical relations and corresponds to a virtual relation of a
security view. Clients subscribe to the events they want and can narrow their
subscriptions further. A later paper, "Event-Driven Database Information
Sharing", published in Lecture Notes in Computer Science, continues the same
programme. Its catalogue record has no abstract, so the record alone cannot
show whether it measures the cost that event detection adds to the database
commit path.

This work is relevant to the question's design context but not to its
measurements. It shows that a PostgreSQL database can push its own change
events to subscribers through an external broker. That moves the fan-out to
many subscribers out of the database session and into middleware. Nothing in
the available records describes PostgreSQL's built-in NOTIFY queue, how
notifying transactions are ordered at commit, or how commit rate or delivery
delay changes as writers, listeners or channels increase.

Two things follow for an event-sourcing library built on psycopg 3 that would
replace fixed-interval polling with notification-driven delivery. First,
claims about NOTIFY's commit-time serialisation and its throughput ceiling
must rest on PostgreSQL's primary project sources and engineering benchmarks
outside the scholarly literature. Second, those claims are best confirmed by
benchmarks run against the library's own write and listen workload. The
scholarly record offers only an architectural alternative: database-advertised
change events with fan-out in a broker. It gives no quantitative evidence
about the cost of NOTIFY itself.
