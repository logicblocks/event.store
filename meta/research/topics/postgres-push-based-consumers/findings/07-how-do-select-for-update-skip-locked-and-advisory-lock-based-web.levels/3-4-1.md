# How should a PostgreSQL event-store consumer fence its checkpoint or completion write with a lease token or epoch so that a handler whose lease has expired cannot overwrite progress committed by the consumer that took over?

## Question

A consumer claims a partition, stream or job with a time-limited lease and then
runs a handler. If the handler stalls (GC pause, slow I/O, network partition)
past the lease's expiry, another consumer can take over and commit newer
progress. How should the checkpoint or completion write be guarded with a lease
token or epoch so that the stale handler's late write is rejected rather than
regressing the new owner's progress, and how is that guard made race-free in
PostgreSQL?

## Findings

### The rule: the store must check the token in the write itself

Martin Kleppmann's analysis of distributed locking sets out the failure: a
client holding a lease pauses, the lease expires, a second client acquires it
and writes, and then the first client resumes and writes stale data. Expiry
alone cannot prevent this, because the pause can happen anywhere, including
between a client's "do I still hold the lease?" check and its write. The fix is
a **fencing token**: "a number that increases (e.g. incremented by the lock
service) every time a client acquires the lock". The storage then rejects a
write carrying an older token. Kleppmann stresses that this "requires the
storage server to take an active role in checking tokens". A client checking
its own lease does not give this guarantee.

Mature consumer-group systems all follow this pattern for progress commits:

- **Kafka.** Under the KIP-848 rebalance protocol, OffsetCommit carries the
  member ID and member epoch. The coordinator verifies them and returns
  `STALE_MEMBER_EPOCH` or `UNKNOWN_MEMBER_ID`. KIP-447 adds member ID,
  group instance ID and generation to transactional offset commits, for the
  exact zombie case where a client "gets out of sync and becomes a zombie due
  to session timeout" after a long GC. If a field does not match, "the client
  will be fenced immediately". The Java client surfaces this as
  `CommitFailedException`, which it raises when "a group rebalance completes
  before the commit could be successfully applied".
- **Kinesis Client Library (KCL).** Each lease row stores the shard's
  `checkpoint` together with `leaseOwner` and `leaseCounter`. The counter
  increases when ownership moves to another worker. The code bumps it on take
  and renew, and every take, renew and update is a DynamoDB conditional write
  expecting the counter value the worker last saw. Checkpointing calls
  `updateLease` with a per-acquisition concurrency token. If the token or the
  conditional write does not match, the checkpointer throws `ShutdownException`
  ("Can't update checkpoint - instance doesn't hold the lease for this shard").
- **Marten (PostgreSQL).** The async daemon uses PostgreSQL advisory locks to
  run each projection shard on one node. It still writes progress as a
  compare-and-set:
  `update mt_event_progression set last_seq_id = ? ... where name = ? and last_seq_id = ?`.
  When zero rows are affected, it throws `ProgressionProgressOutOfOrderException`
  instead of silently overwriting.

There is also a counter-example of a silent fence. In SQS, an old receipt handle
behaves as a fence that fails without telling you: "If you use an old
`ReceiptHandle`, the request will succeed, but the message might not be
deleted." A PostgreSQL design should not copy this. The fenced write must
report that the lease was lost, as KCL and Kafka do.

### Recommended PostgreSQL shape: lease and checkpoint in one row, fenced by an epoch

Store the lease and the progress for one partition (or one consumer and stream
pair) in a single row. The fence and the progress write then become one
single-row compare-and-set, as in KCL's lease item:

```sql
CREATE TABLE consumer_partitions (
  consumer_group   text        NOT NULL,
  partition        int         NOT NULL,
  owner_id         text,
  epoch            bigint      NOT NULL DEFAULT 0,
  lease_expires_at timestamptz,
  position         bigint      NOT NULL DEFAULT 0,
  PRIMARY KEY (consumer_group, partition)
);
```

**Claim.** The claim increments the epoch and returns the checkpoint in the
same statement:

```sql
UPDATE consumer_partitions
   SET owner_id = %(me)s,
       epoch = epoch + 1,
       lease_expires_at = clock_timestamp() + %(ttl)s
 WHERE consumer_group = %(group)s AND partition = %(partition)s
   AND (owner_id IS NULL OR lease_expires_at < clock_timestamp())
RETURNING epoch, position;
```

**Renew.** Renewal is guarded by the epoch. Zero rows means the lease was lost,
so the consumer stops and cancels its in-flight handler:

```sql
UPDATE consumer_partitions
   SET lease_expires_at = clock_timestamp() + %(ttl)s
 WHERE consumer_group = %(group)s AND partition = %(partition)s
   AND epoch = %(epoch)s;
```

**Checkpoint or completion.** The write is guarded by the epoch and,
optionally, by the expected previous position (Marten's guard):

```sql
UPDATE consumer_partitions
   SET position = %(new_position)s
 WHERE consumer_group = %(group)s AND partition = %(partition)s
   AND epoch = %(epoch)s
   AND position = %(expected_previous_position)s;
```

In psycopg 3, check `cursor.rowcount` (or that `RETURNING` produced a row).
Raise a lease-lost error if it is zero, and raise it inside the
`conn.transaction()` block so the whole unit of work rolls back.

- **Epoch: bigint, never reset.** Use a monotonically increasing `bigint`
  rather than a random UUID. Equality on either works for a single-row
  compare-and-set. Monotonicity matters once the token is passed to other
  stores that only remember the highest token seen, which is Kleppmann's model.
  Never delete and re-insert the lease row in a way that resets the epoch.
- **Epoch guard vs position guard.** The epoch guard enforces ownership. The
  expected-previous-position guard enforces ordering and catches concurrent
  writers even inside one owner, for example overlapping batches. Using both
  matches the KCL and Marten designs.

### Why the guarded UPDATE is race-free in PostgreSQL

The guard must sit in the same statement as the write, or behind a row lock
held until commit. A separate `SELECT epoch` followed by an `UPDATE` is a
check-then-act race.

Under READ COMMITTED, an `UPDATE` that finds its target row already updated by
a concurrent transaction waits for that transaction to finish. If it committed,
the UPDATE "will attempt to apply its operation to the updated version of the
row", and "the `WHERE` clause is re-evaluated to see if the updated version of
the row still matches". That gives both orderings the right outcome:

- **Claimant commits first.** The stale owner's checkpoint `UPDATE` re-checks
  `epoch = 33` against the new row (epoch 34), matches zero rows, and the
  stale transaction rolls back.
- **Stale owner's checkpoint locks the row first.** The claimant's `UPDATE`
  waits. When the stale owner commits, the claimant re-evaluates its expiry
  predicate against the new row version. Its `RETURNING position` then yields
  the progress the stale owner just committed, so nothing is lost or replayed
  from an older checkpoint.

Under REPEATABLE READ or SERIALIZABLE, the same conflict raises "could not
serialize access due to concurrent update". The consumer should treat this as
lease lost (or retry the claim), not as a fatal error.

### Fencing handler side effects written in the same transaction

When the handler's projection or read-model writes go to the same database,
put them in the same transaction as the fenced checkpoint. Two placements work:

- **Fence at the end.** Run the epoch-guarded checkpoint `UPDATE` as the last
  statement. If a takeover happened mid-handler, it matches zero rows, the
  application raises, and every side effect rolls back. If no takeover
  happened, the `UPDATE` row-locks the lease row, so a claimant blocks until
  commit and then sees the committed position. The row lock is held only
  briefly, but work done after losing the lease is wasted, and two owners'
  handler transactions can briefly overlap on the same projection rows.
- **Fence at the start.** Begin the transaction with an epoch-guarded locking
  read, `SELECT 1 FROM consumer_partitions WHERE ... AND epoch = %(epoch)s
  FOR SHARE` (or `FOR NO KEY UPDATE`), and abort if it returns no row. The
  lock mode matters:
  - `FOR SHARE` blocks other transactions' `UPDATE`, so the claimant cannot
    take over mid-handler.
  - `FOR KEY SHARE` must not be used. It conflicts only with `FOR UPDATE`, so
    an ordinary non-key `UPDATE` by the claimant would not be blocked.

  The cost is that the lease's time bound is replaced by the lifetime of the
  transaction. The owner's own renewal from another connection, and any
  takeover, both block until the transaction ends. Bound that lifetime with
  server-side timeouts such as `idle_in_transaction_session_timeout` or
  `statement_timeout`, and with prompt detection of dead connections.

### Time and clocks

- **Expiry runs on the database clock.** Base claims and expiry on the
  database clock, not client clocks.
- **Use `clock_timestamp()`, not `now()`.** `now()` and
  `transaction_timestamp()` return the start time of the current transaction
  and "do not change during the transaction". In a long handler transaction, a
  predicate like `lease_expires_at > now()` compares against a stale instant.
  Use `clock_timestamp()`, or `statement_timestamp()` for per-statement
  precision.
- **Safety comes from the epoch, not from expiry.** Expiry only decides when a
  takeover may happen. Adding `AND lease_expires_at > clock_timestamp()` to the
  checkpoint predicate is optional self-fencing: it also rejects an owner
  whose lease lapsed with no claimant, which is safe but costs a re-claim.
- **Local deadlines are only a heuristic.** Owners should stop work a margin
  before expiry. A pause can still land between the local check and the write,
  so this does not replace the server-side fence.

### Advisory-lock ownership still needs an epoch

If ownership is a session-level advisory lock, a checkpoint written on the
same session is implicitly fenced: if the session ends, the lock is released
and that connection can no longer commit. The fence disappears in two cases:

- **Different connection.** The checkpoint goes through a different (pooled)
  connection.
- **Session reset.** The session is reset while the client still believes it
  owns the lock. `DISCARD ALL`, a common pool-reset command, runs
  `SELECT pg_advisory_unlock_all()`. Session advisory locks also "do not
  honor transaction semantics", so a lock taken in a rolled-back transaction
  is still held, and an unlock takes effect even if its transaction fails.

The robust pattern is to increment the epoch row when the advisory lock is
acquired, and fence the checkpoint on the epoch as above. This is what Marten
does by pairing advisory-lock leadership with a compare-and-set progression
row.

### Limits: completion writes and external side effects

- **Job deletion vs checkpoints.** Job-queue completion is a weaker case than a
  checkpoint. Graphile Worker's completion statement for jobs without a named
  queue deletes by job ID alone, with no `locked_by` check. Deleting a finished
  job is terminal and roughly idempotent, but an unfenced checkpoint write is a
  mutable high-water mark that can move progress backwards. For per-message
  completion rows, guard on the attempt or claim token returned at claim time
  (`WHERE id = $1 AND claim_token = $2`). This is the database analogue of
  SQS's newest-receipt-handle rule, but with an error on mismatch.
- **External side effects.** Fencing protects only the stores that check the
  token. For effects outside PostgreSQL, such as HTTP calls or other databases,
  pass the epoch downstream where the target can check it. Otherwise make
  handlers idempotent, because the processing guarantee is at-least-once. The
  Cosmos DB change feed processor, for example, states this explicitly.
- **Lease timings.** Cosmos DB's defaults (60 s expiration, 13 s renewal,
  expiration never below the renewal interval) are a reasonable reference
  ratio. With these, a crashed owner's partitions move after roughly expiry
  plus one renewal interval.
