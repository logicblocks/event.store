# Is it safe to cancel an asyncio task blocked in a psycopg 3 AsyncConnection notifies() wait so that LISTEN or UNLISTEN can be issued immediately, or does cancellation leave the connection unusable?

## Question

A psycopg 3 `AsyncConnection` that is iterating `notifies()` cannot run other statements. If the task blocked in that wait is cancelled so that `LISTEN` or `UNLISTEN` can be sent, is the connection left in a usable state? Or does cancellation corrupt it, hang, or lose notifications?

## Findings

### Short answer

In psycopg 3.2 and later, it is safe to cancel a task that is blocked awaiting the next notification inside `AsyncConnection.notifies()`. The connection stays idle and usable, the connection lock is released, no cancel request goes to the server, and a following `await conn.execute("LISTEN ...")` runs straight away. This holds under three conditions:

- The generator must actually be finalised.
- Cancellation should land while the task is awaiting inside the generator, not while it is processing a notification in its own loop body.
- The application must tolerate losing the rest of a notification batch that was already read when the generator closed.

The 3.1 series is different. There, cancellation sends a pointless server cancel request. It then blocks until the next notification arrives and discards it, so the 3.1 series is unfit for this pattern.

The psycopg maintainer recommends a cooperative alternative to cancellation: a control channel, or a `timeout`, used to leave the loop.

These conclusions come mainly from reading psycopg's source code at the released tags and at `master`. The documentation does not describe what cancelling a `notifies()` wait does to the connection.

### Why LISTEN cannot be issued while notifies() is iterating

Since psycopg 3.2 (PR #760), `AsyncConnection.notifies()` runs its whole receive loop inside `async with self.lock` and yields each `Notify` while still holding the lock. Any `execute()` on the same connection needs the same `asyncio.Lock`:

- From another task, `execute()` waits until the generator ends.
- From the task that is iterating, it deadlocks.

The maintainer confirmed in 2026 that holding the lock across yields "is intended to preclude all operations" (issue #1310). The reasoning in PR #760 was that the earlier code let an `execute()` sneak in while notifications were being consumed, which gave a false impression that mixing commands with listening was safe. The PR states: "If someone wants to mix commands with listening on the same connection, they should do it collaboratively with an adequately short notifies() timeout." In 3.1 the lock was taken around each wait rather than across yields. Because the wait itself had no end, `execute()` still hung in practice (issue #340, 2022).

You cannot close the generator from another task. Calling `aclose()` while the generator is suspended in an `await` raises `RuntimeError: aclose(): asynchronous generator is already running` (issue #340). An outside party therefore has only two ways to end an in-progress wait: cancel the iterating task, or cause a notification to arrive.

### What cancellation does to the connection (psycopg 3.2 and later)

Following a `CancelledError` through the current source:

1. **`waiting.wait_async`** awaits a future that is resolved either by an `add_reader` callback on the socket or by an interval timer (100 ms by default). The `CancelledError` is raised at `await fut`. The `finally` blocks cancel the timer and remove the reader. The low-level generator `generators.notifies(pgconn)` is paused at `yield WAIT_R`, before `pgconn.consume_input()` runs. So nothing has been read from the socket and no protocol message is half-processed. libpq keeps any notification it has not yet absorbed. `PQnotifies` "does not actually read data from the server; it just returns messages previously absorbed by another libpq function", so data still in the socket is picked up by the next operation.
2. **`AsyncConnection.wait`** catches `_INTERRUPTED`, which is `(asyncio.CancelledError, KeyboardInterrupt, SystemExit)`. It sends a server cancel and waits again only if `pgconn.transaction_status == ACTIVE`. A connection waiting for notifications is not running a query, so its status is IDLE, or INTRANS if a transaction was left open. Notifications are only delivered after a transaction ends, so a listener normally runs in autocommit or closes the transaction after `LISTEN` (issue #1038). In either state, `wait` re-raises immediately: no CancelRequest, and no second wait. For the same reason, the hang fixed in 3.3.6 does not apply to an idle `notifies()` wait. That hang was a second wait with no limit on an unresponsive server (#1371); the fix needs libpq 17. It does still apply to the `LISTEN` that follows if the server has stopped responding.
3. **`AsyncConnection.notifies`** lets the exception propagate. Its `finally: self._notifies_backlog = d` restores the per-connection backlog, and leaving `async with self.lock` releases the lock. The async generator then finishes.

The result is an IDLE connection with a free lock and an intact socket, ready for `LISTEN` or `UNLISTEN`. The documentation's general statement on cancellation does not contradict this, because it covers running queries: psycopg "will ask the PostgreSQL postmaster to cancel the operation when it encounters the standard Python `CancelledError`", and "Cancelling the Python Task does not guarantee that the operation will not complete". `asyncio.timeout()` and `asyncio.wait_for()` around `anext(gen)` cancel internally, so the same analysis applies to them.

### Caveats that make cancellation unsafe in practice

**Where the cancellation lands.** asyncio raises `CancelledError` "at the next opportunity", meaning at whatever the task is awaiting at that moment. If the task is inside its own `async for` body, for example awaiting a handler for the previous notification, the error is raised there. The generator then stays paused at its `yield`, still holding the connection lock. A `break` behaves the same way. The Python language reference warns that when an async generator exits early through `break`, task cancellation or an exception, its cleanup may run "in an unexpected context ... when the async-generator garbage collection hook is called". It says the caller "must explicitly close the async generator by calling `aclose()`". Under PEP 525, asyncio only schedules `aclose()` when the generator is garbage-collected. If the generator object is still referenced, for instance held in a variable, a later `execute()` in the same task waits on a lock that is never released.

`contextlib.aclosing()` (Python 3.10+) fixes this. It guarantees that "the generator's async exit code is executed in the same context as its iterations" however the block is left. Iterating `async with aclosing(conn.notifies()) as gen:` makes the lock release deterministic, so `LISTEN` can safely follow either a cancellation or a `break`.

**Losing part of a batch.** `notifies()` absorbs everything available in one `consume_input()` into a local list, then yields the items one at a time. The documentation of `stop_after` reflects this batching: "You might actually receive more than this number if more than one notifications arrives in the same packet". If the generator is closed in the middle of a batch, the rest of the batch is dropped. Those items have already been removed from libpq's queue and are not put back in the backlog. Items being drained *from* the backlog are restored by the `finally`, but items freshly read from the socket are not. This is inferred from the source code, not documented.

**Notifications that arrive while the generator is closed.** These include notifications delivered during the `LISTEN` round trip:

- **3.2.0 to 3.2.3:** lost if no handler was registered (#962).
- **Since 3.2.4 (#975):** appended to `_notifies_backlog` and yielded first by the next `notifies()` call, as long as no `add_notify_handler()` handlers are registered.
- **Since 3.2.10 (#1092):** if handlers are registered, these notifications go to the handlers instead, and using handlers together with the generator raises a `RuntimeWarning` and is deprecated.

One effect of the backlog is that notifications received before an `UNLISTEN` are still yielded afterwards (#1128), which the maintainer considers correct. Consumers should therefore ignore notifications for channels they no longer track.

### The 3.1 series is not safe for this pattern

In 3.1.18 and in the final 3.1.20 release, `AsyncConnection.wait` catches `CancelledError` unconditionally. It calls `_try_cancel`, which sends a CancelRequest over a new connection; the protocol says a cancel "will have no effect" when no query is running. It then waits again on the same `notifies` generator. The 3.1 `wait_async` treats its `timeout` argument only as a polling interval and keeps looping, so this second wait has no deadline. The cancellation does not finish until data arrives on the socket, normally the next notification. The batch read during that second wait is thrown away before `CancelledError` is re-raised. On a quiet channel, cancellation is delayed indefinitely and costs a wake-up. The ACTIVE-status guard that fixes this first appears in 3.2.0.

### Cooperative alternatives

- **Control channel (the maintainer's recommendation).** Also `LISTEN` on an extra channel such as `relisten`. When subscriptions change, send a `NOTIFY` on it from another connection. The loop receives it, breaks out, runs `LISTEN` or `UNLISTEN`, and re-enters `notifies()`. The maintainer notes that this "way you don't have to timeout every 0.1s, you can timeout as long as you want, because you will be waken up by a notification anyways" (#1310). In #340 they suggested the same approach with a `listen_change` channel and `stop_after=1`. Notifications that are already pending are processed immediately when the socket becomes readable, and there is "no polling, if not to enforce the timeout".
- **`timeout` or `stop_after`.** Since 3.2, the generator ends itself through an internal `_WaitTimeout` or by counting notifications, and the lock is released by normal generator completion rather than by cancellation. A user-posted workaround loops over `notifies(stop_after=1)`, calling `aclose()` after each notification (#340).
- **Not a substitute: `add_notify_handler()`.** It only receives notifications when they arrive alongside the result of another operation, so it cannot listen actively (#1310).
- **Dedicated connection.** The maintainer recommends opening listening connections separately rather than taking them from a pool (#1038).

### Implication for an event-store consumer

In an event store, a notification is only a hint to re-read the event table. The losses cancellation can cause on 3.2+ are therefore acceptable, provided the consumer runs a catch-up read after each `LISTEN` completes. Those losses are the rest of a partly yielded batch and, before 3.2.4, notifications delivered during the `LISTEN` round trip. The real hazards are holding the lock because the generator was never closed, and running 3.1.x. The control-channel or `timeout` patterns avoid both without relying on cancellation.
