# Does psycopg 3 buffer PostgreSQL notifications that arrive while the connection is executing a query or is outside its notifies generator, so that a listen-first consumer cannot lose a wake-up inside the client library?

## Question

When a consumer issues `LISTEN` before reading the event log, does psycopg 3
keep a notification that reaches the connection while it is running a query,
or while no `notifies()` generator is active, so that the consumer still sees
the wake-up later? Or can the client library drop it, reopening the
lost-wakeup window that listen-first ordering is meant to close?

## Findings

**The scholarly record does not answer this question.** None of the works
OpenAlex indexes looks at how psycopg 3 handles notifications. None looks at
libpq's notification queue either, or at the client-side window in which a
notification could arrive and then be lost. The indexed literature that
mentions PostgreSQL `LISTEN` and `NOTIFY` uses them as a tool inside
applications. It does not study driver behaviour. So no peer-reviewed or
preprint source can confirm or rule out the guarantee the question asks
about.

**The answer depends on three layers, and each must be checked separately.**
A listen-first consumer is safe from in-library loss only if all three of the
following hold:

1. **Server.** PostgreSQL keeps a notification for a session that is busy
   or inside a transaction, and sends it once the session can receive it.
2. **libpq.** psycopg 3 is built on libpq. libpq must hold a
   notification message that arrives while it is reading a query result, and
   keep it until the application asks for it, rather than throwing it away.
3. **psycopg 3.** The library must pass such a held message on later,
   either through the `notifies()` generator or through a registered notify
   handler. It must not drain and discard it while running an ordinary
   query, or while no consumer of notifications is active.

The question is really about the third layer. Even so, a full answer has to
cover all three, because a guarantee at the top layer is worthless if a
lower layer drops the message first. Behaviour at the third layer may also
differ between psycopg 3 releases. Any check should therefore name the exact
version it was run against.

**Conservative position for consumer design.** With no evidence either way,
a consumer should not treat in-library buffering as a correctness guarantee.
The following follows from the design, not from any source. The approaches
that stay safe whatever psycopg does are:

- Re-read the log every time a wait ends, whether a notification woke it or
  a timeout did. A missed notification then only delays work and never loses
  it.
- Keep a safety-net poll whose interval caps how stale the consumer can get
  if a wake-up is silently lost.

Under this design, client-library buffering only affects latency, not
correctness.

**How to settle the question empirically.** A small test can confirm the
behaviour for a pinned psycopg 3 version:

1. A listening connection runs a long query, such as a `pg_sleep` call, or
   sits idle with no `notifies()` generator open.
2. During that time, a second connection commits a `NOTIFY` on the same
   channel.
3. The listening connection then opens `notifies()` with a short timeout,
   and the test checks whether the notification arrives.

Repeat the test with and without a registered notify handler, and with a
query that is still running when the notification commits. Together these
cover the cases the question names.
