# How can a Python consumer stream a logical replication slot and safely confirm flushed positions when psycopg 3 lacks replication protocol support, comparing psycopg2's replication connection, a pg_recvlogical subprocess and a sidecar process?

## Question

A psycopg 3 application cannot natively speak PostgreSQL's streaming replication protocol. How can a Python consumer still stream changes from a logical replication slot and confirm flushed positions safely, so that the slot advances only past work the consumer has really handled? The three routes compared are psycopg2's `LogicalReplicationConnection`, a `pg_recvlogical` child process, and a separate sidecar process.

## Findings

### The psycopg 3 gap, as of late 2026

Psycopg 3 still has no replication API. Issue #71, "Add support for streaming replication as in psycopg2", was opened by maintainer Daniele Varrazzo in August 2021 and is still open. In 2023 he wrote: "Replication support is not implemented in psycopg 3. It needs complete redesign and implementation." The only change so far is PR #1219, merged on 2025-11-24 and shipped in psycopg 3.3. It stops `conn.execute("START_REPLICATION ...")` on a `replication="database"` connection from failing with "COPY cannot be used with this method", and returns a cursor in `COPY_BOTH` state. The maintainer was explicit that "from there on the connection will be broken for further usage" and that "No further replication support is planned for release 3.3."

In May 2026 a community proof-of-concept PR (#1311) proposed a full replication module with pgoutput and test_decoding decoders. It was closed the same day without merging. The maintainer said "there is some ongoing work that goes in a direction different for this design" and that more information would follow. The psycopg 3 release notes, up to 3.3.6, mention no replication feature. Another commenter on the issue described a "bridge" approach: psycopg 3 sends `START_REPLICATION`, then raw socket I/O takes over to read the wire protocol and send feedback. That approach is outside anything psycopg supports. The low-level `psycopg.pq.PGconn` does expose `get_copy_data(async_)`, `put_copy_data(buffer)` and `flush()`, so a hand-written protocol loop on top of psycopg 3.3 is possible but unsupported.

### What "safely confirming a flushed position" means on any route

All three routes share the same server-side rules, and these rules set what a safe confirmation looks like:

- **Confirming flush moves the slot.** The client sends a standby status update carrying write, flush and apply LSNs. For a logical slot, the flush value becomes `confirmed_flush`, and the server only ever moves it forward (`if (lsn > ...confirmed_flush) ... = lsn`). psycopg2 describes `flush_lsn` as the position "up to which the client has processed the data reliably (the server is allowed to discard all and every data that predates this LSN)".
- **A confirmation cannot be undone.** `START_REPLICATION SLOT ... LOGICAL` starts at the requested LSN or at the slot's `confirmed_flush_lsn`, "whichever is greater". A consumer that confirmed too early cannot rewind the slot to replay. The docs suggest checking `confirmed_flush_lsn` against expectations before starting. `pg_replication_slot_advance` is also forward-only.
- **Commit-granular confirmation is safe.** The server tags each emitted message with a position. For BEGIN it is the transaction's first LSN, for a change it is the change's LSN, and for COMMIT it is `txn->end_lsn` ("points to the end of the record"). On restart, the decoder skips a transaction only when the start of its commit record lies before the slot's start point (`SnapBuildXactNeedsSkip(..., buf->origptr)`). So confirming a COMMIT message's position retires the whole transaction. Confirming a mid-transaction change's position is lower than the commit record, so the whole transaction is resent. The pg_recvlogical docs say the same: a partially output transaction "will not be consumed and will be replayed again when the slot is next read from."
- **Delivery is at-least-once in all cases.** A `confirmed_flush` change only marks the slot dirty, and it is written to disk at the next checkpoint. The docs warn that "in the case of a crash the slot might return to an earlier LSN", and that clients "are responsible for avoiding ill effects from handling the same message more than once", for example by recording the last LSN seen. Whichever route is used, the consumer must deduplicate by LSN or by event position.
- **The client must keep confirming, even when the database is idle.** By default `max_slot_wal_keep_size` is -1, so a slot may retain unlimited WAL. `idle_replication_slot_timeout` defaults to 0 (disabled). `wal_sender_timeout` defaults to 60 s and ends connections that stop replying. Keepalive messages carry a "reply requested" byte that the client must answer "to avoid a timeout disconnect". When the slot's database has no changes, the client must still advance its confirmed position to the server's WAL end taken from keepalives, or WAL builds up. Debezium recommends a periodic `heartbeat.action.query` on low-traffic databases for this reason.
- **Only one consumer per slot.** "Only one receiver may consume changes from a slot at any given time". A single process must own the stream and fan events out to everything else.

### Option 1: psycopg2 `LogicalReplicationConnection` (consumer-driven acknowledgement)

psycopg2 has supported the replication protocol since 2.7. Releases continue: 2.9.11 added Python 3.14 support and 2.9.13 added Python 3.15. The API:

- `start_replication(slot_name, ..., decode, status_interval)`. `status_interval` defaults to 10 s and must be at least 1 s. Leave `decode` unset for binary plugins such as pgoutput.
- `consume_stream(consume)` for synchronous connections ("can only be used with synchronous connection").
- A non-blocking `read_message()` plus `select` for asynchronous connections.
- `send_feedback(write_lsn, flush_lsn, apply_lsn, reply, force)`.

`send_feedback` without `reply` or `force` "will just update internal structures". The library then sends the stored position automatically at each `status_interval` and answers keepalives that request a reply. The C code (`pqpath.c`) solves the idle-database problem safely: it moves `flush_lsn` to the server's `wal_end` only when `explicitly_flushed_lsn >= last_msg_data_start`, meaning the client has already confirmed every message it received. Positions the consumer has not acknowledged are never confirmed for it.

The documented pattern is to process the message, then call `msg.cursor.send_feedback(flush_lsn=msg.data_start)`. For an event store this becomes:

1. Apply the event and commit its effects plus the consumer's checkpoint on the ordinary psycopg 3 connection.
2. Only then record that position with `send_feedback`.
3. Let `status_interval` batch the confirmations, or use `force=True` to push one at once.

Done this way, a crash replays at most the unconfirmed tail, which is at-least-once and handled by LSN-based deduplication. Of the three routes, this is the only one that offers consumer-driven acknowledgement without custom protocol code.

The costs:

- A second database driver in the dependency tree.
- A dedicated replication-mode connection.
- No native asyncio support. The async mode is `select`-based, so an asyncio application needs to watch the cursor's file descriptor or run the loop in a thread. That is an inference from the select-based API, not a documented recipe.
- Payload parsing is the consumer's job. pgoutput is binary. pypgoutput is the visible Python parser built on psycopg2, and its README warns that it is "a prototype and not production tested". Text plugins such as wal2json avoid a binary parser.

### Option 2: a `pg_recvlogical` subprocess (the slot is confirmed when data is written to the output)

`pg_recvlogical --start --slot ... -f -` streams decoded changes to stdout until it receives SIGINT or SIGTERM. Before exiting it flushes and sends final feedback, and it exits with status 0. If the server disconnects it reconnects in a loop unless `--no-loop` is given. Other options: `-o` passes options to the output plugin, `-I` sets a start position, and `-E` stops at an end LSN. The source shows exactly when it confirms:

- After each message it raises `output_written_lsn` to that message's LSN and writes the payload followed by a newline. Keepalives also raise `output_written_lsn` to the server's WAL end, so idle slots advance on their own.
- The flush position it reports is `output_fsync_lsn`. `OutputFsync()` sets this to `output_written_lsn` every fsync interval (default 10 s, `-F`) and before answering keepalives that request a reply. It also saves that position as the start point for reconnects.
- `OutputFsync()` calls `fsync()` only when the output is a regular file (`output_isfile = S_ISREG(...) && !isatty(outfd)`). For a pipe or stdout it skips the `fsync()` but still advances the reported flush position. Status updates go out every 10 s by default (`-s`) through `sendFeedback()`, which does not fsync first. With `-F 0` progress is still reported, "data could be lost in the event of a crash".

So when pg_recvlogical is piped into a Python consumer, the slot is confirmed once bytes have been written into the pipe, not once Python has processed them. There is no channel for the consumer to send acknowledgements back. Because the server will not rewind past `confirmed_flush_lsn`, a consumer crash loses the events that were in the pipe buffer or in flight but already confirmed. For the stream itself, that window is at-most-once.

Two ways to make it safe:

- **Durable spool.** Write to a regular file. Each confirmation then follows a real `fsync`. Python reads the file and keeps its own offset, and SIGHUP makes pg_recvlogical reopen the file for rotation.
- **Wake-up signal only.** Treat the stream purely as a signal to read, and catch up from the durable events table using the consumer's own checkpoint. Lost stream messages then cost latency, not data.

Framing is a newline after each message. That suits text plugins that emit one record per line, such as wal2json `format-version` 2 ("a JSON object per tuple", with `include-lsn` adding `nextlsn`). A binary pgoutput stream framed only by newlines cannot be split reliably; that is an inference from the framing. Operationally, this route needs PostgreSQL client binaries wherever the consumer runs, plus process supervision.

### Option 3: a sidecar process (the slot is confirmed at the sidecar's own storage)

Off-the-shelf change-data-capture (CDC) sidecars move the point of acknowledgement to their own storage:

- **Debezium Server** runs without Kafka. It can deliver to sinks including an HTTP client, Redis Streams, NATS JetStream and JDBC, and it stores offsets in a file, in a database over JDBC, or in Redis. The HTTP sink retries 5 times by default. Its PostgreSQL connector supports pgoutput and decoderbufs, and its documentation says it confirms the slot LSN only after its own offsets are committed. Debezium's FAQ promises exactly-once "when all systems are running nominally" and "at least once" after faults.
- **Sequin** is a standalone Docker container. Its sinks include webhooks and a "Sequin Stream" HTTP pull API, and it claims "exactly-once processing of database changes using idempotency keys".
- **pgstream** is a CLI and library with webhook, Kafka and PostgreSQL targets.

In each case the slot advances when the sidecar's sink or offset store accepts an event. Safety for the Python consumer then depends on that sink's acknowledgement rules, such as a webhook's 2xx response or a Redis consumer group. For a library meant to depend only on PostgreSQL, a broker sink adds infrastructure. A PostgreSQL sink just copies changes into another table, which brings back the polling or NOTIFY problem a slot was supposed to remove.

A custom sidecar is the other version of this option. It is a small separate process, for example a psycopg2 loop, that keeps the psycopg2 dependency out of the main application, passes events to workers over inter-process communication (IPC), and calls `send_feedback` only after workers acknowledge. This is Option 1 with process isolation, and the cost is that the acknowledgement channel has to be designed explicitly.

### Comparison for an event-store consumer

| Route | Who decides the slot advances | Crash window for the stream | Idle-database WAL advance | Added dependencies |
|---|---|---|---|---|
| psycopg2 replication connection | The consumer, through `send_feedback` after processing | Replays the unconfirmed tail (at-least-once) | Automatic once all received messages are confirmed | psycopg2, a replication-mode connection, select-based async |
| pg_recvlogical piped to stdout | pg_recvlogical, when it writes to the pipe (~10 s cadence) | Loses data already in the pipe (at-most-once), unless the events table is the recovery source | Automatic from keepalive WAL end | PostgreSQL client binaries, process supervision, text plugin |
| pg_recvlogical writing to a file | pg_recvlogical, after `fsync` of the file | Durable spool; the consumer tracks its own file offset | Automatic | As above, plus file rotation |
| Off-the-shelf sidecar | The sidecar, after its offset store or sink commits | At-least-once into the sink | Needs a heartbeat on low-traffic databases (Debezium) | A JVM or container service, often a broker |

Two designs follow, depending on what the slot is used for:

- **The decoded stream is the delivery channel** (events are taken from slot payloads). Only consumer-driven acknowledgement is safe. That means psycopg2, or a custom protocol loop on psycopg 3.3's `PGconn` copy functions, confirming the COMMIT message's LSN after the consumer's work and checkpoint have committed, and deduplicating by LSN because of checkpoint-lag replays.
- **The append-only events table stays the system of record, and the slot only pushes wake-ups.** Early confirmation by pg_recvlogical or a sidecar is acceptable. Confirming promptly is even preferable, because it limits WAL retention. Recovery then comes from catch-up reads by event position, not from slot replay.

In both designs, run one owner process per slot, set `max_slot_wal_keep_size`, and monitor slot lag.
