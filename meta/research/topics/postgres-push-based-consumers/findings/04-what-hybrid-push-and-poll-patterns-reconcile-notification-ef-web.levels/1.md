# What hybrid push-and-poll patterns reconcile notification efficiency with polling durability — notify as a wake-up hint over a durable log, safety-net polling, adaptive and backoff polling, long-polling, and coalescing or debouncing of notification bursts — and how are missed notifications detected and recovered from?

## Question

Which hybrid designs let a PostgreSQL-backed consumer get the low latency of LISTEN/NOTIFY while keeping the durability of polling? The designs in scope are: notification as a wake-up hint over a durable log, safety-net polling, adaptive and backoff polling, long-polling, and coalescing or debouncing of notification bursts. The question also asks how a consumer detects missed notifications and recovers from them.

## Findings

### The consensus shape: durable log is truth, NOTIFY is a lossy hint

Every mature PostgreSQL-backed consumer surveyed here uses the same hybrid. The table is the source of truth. NOTIFY is only a hint that says "look now". Each consumer keeps its own durable checkpoint and always re-reads from it, and a periodic poll stays in place as a safety net. This follows directly from PostgreSQL's notification semantics:

- **Undelivered notifications are not stored.** A session receives only "events committed after an instant during the [LISTEN] transaction's commit step". LISTEN itself takes effect only at commit. Anything sent before then is never delivered to that session.
- **Notifications sent during a disconnect are lost.** The Postgrex driver documentation says plainly that notifications occurring while the listener is disconnected "are not queued and cannot be recovered".
- **Connection poolers can silently disable LISTEN.** PgBouncer lists LISTEN as "Never" supported in transaction and statement pooling modes. Graphile Worker warns this can produce missed events, and Oban says it disables all LISTEN/NOTIFY activity.
- **Delivery waits on the listener's transactions.** A listening session inside a transaction gets nothing until that transaction ends. Notifications also queue in a fixed-size server queue (8 GB in a standard installation). If that queue fills, transactions calling NOTIFY fail at commit, so a stalled listener can eventually break writers.
- **Idle-session limits may kill the listener.** PostgreSQL defines `idle_session_timeout` as terminating sessions "waiting for a client query" outside a transaction. A connection parked waiting for notifications fits that description, so the setting is a likely cause of silent listener death. This is an inference from the definition, not a documented interaction.

PostgreSQL's own documentation frames NOTIFY this way. A notification on a table-named channel "essentially means, 'I changed this table, take a look at it to see what's new'". The docs recommend firing it from a statement trigger so that writers cannot forget it.

### Pattern 1 — Notify as a wake-up hint over a durable log

**Startup and reconnect order.** The LISTEN docs prescribe one sequence, and it is the core of every implementation:

1. Execute and commit LISTEN.
2. In a new transaction, inspect the database state.
3. Rely on notifications for later changes.

The first few notifications may refer to changes already seen, which "is usually harmless". Postgrex gives the same three steps (subscribe, read current state, handle notifications) as its recommended way to recover after a reconnect.

**An event-store implementation.** The Elixir EventStore library (used by Commanded) applies this to a log:

- A trigger on the `streams` table issues one NOTIFY per batch of appended events. The payload carries the stream uuid, stream id and the first and last stream versions, for example `stream-12345,1,1,5`.
- A single listener per node receives these, reads the event data from storage and broadcasts it to local subscriptions.
- Persistent subscriptions store the last acknowledged position and guarantee at-least-once delivery of every persisted event.
- Advisory locks ensure each named subscription runs only once across a cluster.

**Job queues.** Graphile Worker, River, Oban, GoodJob, Que, Procrastinate and PgQueuer all work the same way: a notification tells an idle worker to run its normal fetch query against the table. Notifications never carry the work itself. Procrastinate's API reference says the worker "polls the database regardless of this setting" (`listen_notify`). Que's locker always runs both a `Listener` and per-queue `Poller`s.

**Single listener connection.** Brandur Leach's "notifier pattern", from the River author, keeps one LISTEN connection per process. That connection serves any number of topics and passes notifications to in-process subscribers. This saves scarce PostgreSQL connections compared with one listener per consumer.

### Pattern 2 — Safety-net polling

The safety-net poll does three jobs:

1. It puts an upper bound on how late any missed notification can make a consumer.
2. It finds work that no notification will ever announce.
3. It acts as a degraded mode when notifications are unavailable.

The poll intervals libraries choose show that, once notifications exist, polling is treated as a backstop rather than the main path:

| Library | Poll interval and guidance |
|---|---|
| River | `FetchPollInterval` defaults to 1 s and "provides a fallback". New jobs are normally picked up "~immediately after insert via LISTEN/NOTIFY". |
| Procrastinate | `fetch_job_polling_interval` defaults to 5 s. When LISTEN/NOTIFY is on, it "acts as a fallback mechanism and can reasonably be set to a higher value". |
| Graphile Worker | Defaults to a 2 s poll and says 30–60 s "is probably fine". |
| Oban | Polls every second. Insert notifications exist only so queues need not wait "up to 1s for the next polling interval". |

Graphile Worker also polls for future-dated and retried jobs, because "there's nothing to generate an event when the time 'ticks over'". GoodJob's README describes polling as a fallback for disrupted notifications. It also calls an overflowing scheduled-job cache "another reason to poll".

Several libraries make the fallback an explicit degraded mode:

- **River** has `PollOnly`, which issues no LISTEN at all. It enters that mode automatically when the database driver cannot listen.
- **Oban** switches its job staging from "global mode" to "local mode" when notifications fail. In global mode only the leader queries and fans out over pub/sub. In local mode every queue polls on its own. This keeps work moving at the cost of many more queries.

### Pattern 3 — Waiting on the hint with a timeout (long-polling on the listen socket)

The simplest way to combine push and poll is to replace the poll loop's sleep with a bounded wait on the notification socket. The consumer reads from its checkpoint until it has caught up. It then blocks until either a notification arrives or the safety-net interval expires, and either way it reads again. A notification shortens the wait; the timeout gives durability.

**psycopg 3 support.** Client libraries expose this wait directly:

- `Connection.notifies(*, timeout=None, stop_after=None)` gained its `timeout` and `stop_after` parameters in psycopg 3.2. `stop_after` may yield more than asked if several notifications share one packet.
- psycopg recommends autocommit on the listening connection so notifications arrive promptly.
- Since 3.2.4, notifications received while the `notifies()` iterator is not running are no longer lost. The changelog warns this can produce duplicates when notifications were used to bridge the gap between LISTEN and starting the iterator.
- Since 3.2.10, mixing notify handlers and the generator on one connection is deprecated.

**Other clients.** Npgsql offers `Wait` and `WaitAsync` with a timeout and recommends TCP keepalives. Que's locker checks every 50 ms for notifications or an expired timer, with a default poll interval of 5 s.

**Long-polling elsewhere.** Other messaging systems use the same idea at the protocol level, which supports holding the wait on the server or the socket rather than sleeping:

- **Amazon SQS** long polling (`WaitTimeSeconds` up to 20 s) answers as soon as a message is available, which "reduce[s] the number of empty responses".
- **Kafka** fetches block for up to `fetch.max.wait.ms` (default 500 ms) until `fetch.min.bytes` have accumulated. This both long-polls and batches.
- **EventStoreDB/KurrentDB** has an `ES-LongPoll` header that makes a read at the head of a stream wait for new data.
- **PGMQ's `read_with_poll`** runs the loop inside PostgreSQL. It re-checks every `poll_interval_ms` (default 100) for up to `max_poll_seconds` (default 5) and returns as soon as messages arrive. That is still polling, now inside the database, and it holds a connection for the whole wait.

### Pattern 4 — Adaptive and backoff polling

When polling is the only signal, systems scale its frequency to recent results. Azure Functions' queue trigger uses a "random exponential back-off algorithm":

- After a message is found, it waits 100 ms and checks again.
- After an empty check, it waits about 200 ms.
- The wait keeps growing up to `maxPollingInterval` (default one minute).

The opposite case, a backlog, is handled by fetching again at once. River (v0.14.0) became "more aggressive about fetching when it just fetched a full batch of jobs, or when it skipped its previous triggered fetch because it was already full". River v0.24.0 lets each queue set its own `FetchCooldown` and `FetchPollInterval`, so high-priority queues can be checked more often.

How this combines with notifications (synthesis): backoff should apply only to the safety-net timer. Any notification should reset the wait to an immediate read, and a full batch should trigger another read straight away. The backoff ceiling then becomes the worst-case latency for a missed hint, so it must stay within the consumer's latency budget.

### Pattern 5 — Coalescing and debouncing bursts

Bursts are absorbed at three points.

**In PostgreSQL itself.**

- Identical channel and payload pairs signalled within one transaction may be delivered as one notification.
- Notifications from different transactions are never merged, and distinct payloads are always delivered separately.
- Order is preserved within a transaction and across transactions in commit order.
- Since a 2019 commit (PostgreSQL 13), de-duplication uses a hash table once a (sub)transaction has more than 16 distinct events. Before that it was a linear scan that degraded to O(N²).
- An earlier patch to let senders skip de-duplication entirely was returned with feedback and never merged.

The practical consequence is that a statement-level trigger, or a constant payload, gives one notification per committing transaction. Per-row payloads multiply the notification count.

**At the sender.**

- **River** v0.5.0 moved insert notifications out of database triggers into the client. They are now "piggy-backed onto the insert query", with a client-side debouncer so they are not emitted more often than is useful.
- **Oban** likewise moved insert notifications into application code. Its scaling guide suggests disabling them when sub-second dispatch is unnecessary.
- **PGMQ** (1.8.0+) offers `enable_notify_insert` with a throttle interval, according to the PgFlow library's documentation.

One reason to throttle at the source is commit-time cost. Recall.ai reported that a transaction which issued NOTIFY takes a database-wide lock during commit, which serialised commits under many concurrent writers and caused outages. PostgreSQL contributor Joel Jacobson argued on pgsql-hackers that the deeper problem is every NOTIFY waking every listening backend. A January 2026 commit to master (the PostgreSQL 19 cycle) adds a shared map of which processes listen on which channels, so uninterested listeners are no longer woken. It reports throughput gains of integer multiples when many listeners exist but few are interested in each message.

**At the receiver.**

- **River's `FetchCooldown`** (default 100 ms) is the minimum gap between fetches: "Jobs will only be fetched *at most* this often".
- **Graphile Worker** drops a notification if no worker is idle, "knowing that when one of the workers finishes they'll ask for the next job anyway".
- **The notifier pattern** delivers to each subscriber through a buffered channel with a non-blocking send, discarding the notification when the buffer is full.

Dropping is safe only because the next read always starts from the durable checkpoint. Any number of notifications that arrive between two reads collapse into one "something changed" flag.

### Detecting and recovering from missed notifications

These systems recover from missed notifications by design rather than by detecting each loss. Every read starts from a persisted checkpoint and is idempotent, so a lost hint costs at most one safety-net interval. Duplicate or stale hints cost one empty read. On every connect and reconnect the consumer runs the LISTEN-commit-then-catch-up sequence, so changes committed while it was deaf are picked up by the first read. On top of that baseline, the sources describe three kinds of explicit detection.

**1. Gap detection from positions in the payload.** The Elixir EventStore subscription state machine compares the first event number in each notification with `last_received + 1`:

- Earlier numbers are ignored as already seen.
- The expected number is enqueued.
- A later number means "Missed event(s), request catch-up". The subscription then reads the stream forward from `last_sent + 1` until it has caught up, and returns to the subscribed state.

A buffer overflow from a slow subscriber also forces this catch-up mode.

**2. Checking that the listener is alive.** A dead listener looks exactly like a quiet system. Oban addresses this with a `sonar` channel of periodic checks, which classifies its notifier as `unknown`, `isolated` (receiving nothing), `solitary` (receiving only its own messages) or `clustered`. An isolated notifier pushes Oban into local polling.

The same idea can be built from PostgreSQL primitives. A consumer can NOTIFY a heartbeat channel and expect it back; notification messages carry the sender's server PID, so self-sent messages can be recognised. Transport-level failures can be caught with libpq's `keepalives*` and `tcp_user_timeout` parameters.

**3. Watching server-side health.** `pg_notification_queue_usage()` reports how full the notification queue is. PostgreSQL logs warnings at half full, naming the session that is blocking cleanup, which is typically a listener stuck in a long transaction. This is one reason to keep the listening connection in autocommit and separate from the processing connection.

**The durable-log caveat.** A hint arriving after commit does not by itself make a read of "position > checkpoint" safe. A row whose position was reserved by a transaction that commits later can be skipped. Marten's async daemon handles this with a high-water mark that "stops under any hole in the event sequence". It asks whether any running transaction could still fill the hole, and skips stale gaps only after a threshold. Its documentation and issue tracker show this remains a subtle source of skipped events under concurrent appends. Any notify-plus-poll design therefore has to sit on top of a gap-safe read.

### Synthesis for a psycopg 3 consumer

Taken together, the sources point to one composite design:

- **Listener.** A single autocommit listener connection per process, using LISTEN-then-catch-up on every (re)connect.
- **Main loop.** Read from the checkpoint until a batch comes back short. Then block in `notifies(timeout=safety_interval)`. On any wake-up or timeout, drain what is pending and re-read once.
- **Fetch limits.** A minimum gap between fetches, so bursts collapse into one read.
- **Safety net.** A backoff ceiling on the safety-net interval, kept within the latency budget.
- **Health.** A heartbeat to detect a deaf listener and fall back to poll-only mode.
- **Payloads.** Optionally, positions in the payload so that gaps trigger an immediate catch-up.
- **Correctness.** Gap-safe read semantics underneath, because notifications are only an optimisation for latency.
