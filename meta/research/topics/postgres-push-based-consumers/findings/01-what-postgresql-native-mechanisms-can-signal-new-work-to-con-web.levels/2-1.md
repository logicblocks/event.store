# How can a consumer woken by NOTIFY avoid skipping events whose transactions commit out of sequence-number order, given that notifications arrive in commit order but positions are assigned at insert time?

## Question

An event log's position comes from a sequence, so each event gets its number when the row is inserted. `NOTIFY` messages arrive in the order transactions commit. A consumer that wakes on a notification and reads "everything after my last position" can therefore move past a position whose transaction has not committed yet, and never come back for it. What can the consumer, or the write path, do so that no event is ever skipped?

## Findings

### Why the obvious approach skips events

Three documented behaviours combine to cause the problem.

- **Positions are handed out at insert time and are not tied to commit.** A value taken by `nextval` is never given back if the transaction aborts, so aborts, crashes and even `INSERT ... ON CONFLICT` leave gaps. PostgreSQL says outright that sequences "cannot be used to obtain 'gapless' sequences". Concurrent sessions always get distinct values. With a sequence `CACHE` setting above one, the values may not even be handed out in order across sessions; with a cache of one they are handed out in order. In every case, transactions can commit in any order relative to when they took their numbers.
- **`NOTIFY` follows commit order.** Notifications are delivered "until and unless the transaction is committed", so never for a rolled-back transaction. Notifications from different transactions arrive "in the order in which the transactions committed". Internally, `async.c` makes notifying writers take a lock that is held until after commit, so "queue entries appear in commit order". Listeners stop reading when they reach an entry from a transaction that has not committed.
- **Gaps cannot be read as signals.** A hole in the positions might be a transaction that is still running and will fill it, or a rollback that never will. Marten's documentation notes that most holes fill within milliseconds but some "never fill", for example after a rolled-back save or an optimistic-concurrency conflict. Precision Nutrition found about 0.6% of its ids missing in normal operation.

So suppose transaction A takes position 4 and transaction B takes position 5, and B commits first. The consumer wakes on B's notification, runs `WHERE position > 3`, gets 5 and saves 5 as its checkpoint. When A commits, its notification wakes the consumer again, which runs `WHERE position > 5` and never sees event 4. Precision Nutrition (ids 187–188 became visible after 189), Cloudscale (an audit-log API cursor), Oskar Dudycz (outbox polling) and Axon users (`BIGSERIAL` global index) all describe this exact failure.

The general conclusion is that **a notification can only be a wake-up hint**. A position carried in the payload is not a safe checkpoint, and neither is the highest position the consumer has seen. Correctness has to come from the read query (it must define a safe frontier), or from the write path (it must hand out positions in commit order). Five families of solution appear in the sources.

### 1. Read only behind the transaction horizon (`xid8` plus `pg_snapshot_xmin`)

Each event records the ID of the transaction that wrote it. The consumer reads only events from transactions that are guaranteed to have finished. Dudycz and Sequin both describe this approach:

```sql
ALTER TABLE events ADD COLUMN transaction_id xid8 NOT NULL DEFAULT pg_current_xact_id();

SELECT position, ...
FROM events
WHERE ((transaction_id = :last_tx AND position > :last_pos) OR transaction_id > :last_tx)
  AND transaction_id < pg_snapshot_xmin(pg_current_snapshot())
ORDER BY transaction_id, position
LIMIT 100;
```

**Why it is safe.** PostgreSQL defines a snapshot's `xmin` as the lowest transaction ID still active. Every ID below it is "either committed and visible, or rolled back and dead". No row with a transaction ID below the frontier can appear later, so a consumer moving through `(transaction_id, position)` order up to the frontier never passes over a row that turns up afterwards.

- `pg_current_xact_id()` returns the top-level transaction ID even inside a subtransaction.
- Snapshots list only top-level IDs, and `pg_visible_in_snapshot` gives wrong answers for subtransaction IDs.
- So store the function's value. Do not rely on the system `xmin` column, which uses the 32-bit `xid` type that wraps around. `xid8` "does not wrap around during the life of an installation".

**Costs.**

- **Any long-running write transaction holds the frontier back.** Sequin points out that the frontier is set by the oldest active transaction across the whole system, so a two-minute transaction elsewhere hides two minutes of recent data. Dudycz's guidance is simply to keep transactions short.
- **The order changes meaning.** Events come out in transaction-ID order, which roughly follows when a transaction first wrote, not when it appended or committed. Dudycz warns this "may create problems if forgotten".
- **A possible per-stream reordering (an inference, not taken from a source).** Suppose transaction T2 first writes something else, which gives it a lower ID than T1. T1 then appends version 5 of a stream and commits, and T2 appends version 6. Ordering by `(transaction_id, position)` puts version 6 before version 5.

**How it fits with `NOTIFY` (an inference from the documented semantics).** When B's notification arrives while A is still running, B's events are behind the frontier and the read returns nothing new. If A commits, A's own notification wakes the consumer again. But if A rolls back, or the blocking transaction is unrelated and never notifies, nothing arrives when the frontier moves, because notifications are only sent on commit. A consumer using this method therefore needs a timed re-check whenever it knows committed work is waiting behind the frontier.

### 2. Read the difference between two snapshots (PgQ)

Skype's PgQ queue avoids the frontier stall. Its checkpoint is the previous snapshot rather than a position. Each batch takes the events whose writing transaction became visible between the previous snapshot `sn1` and the current one `sn2`:

```sql
WHERE ev_txid >= xmin1 AND ev_txid <= xmax2
  AND NOT txid_visible_in_snapshot(ev_txid, sn1)
  AND txid_visible_in_snapshot(ev_txid, sn2)
```

PgQ stores each tick's snapshot in a table (`tick_snapshot`). Its source acknowledges that long transactions, by keeping `xmin1` low, force wide scans. It deals with this by range-scanning only `[xmax1..xmax2]` and finding transactions in `[xmin1..xmax1]` that committed between the snapshots through an exact `IN (...)` list. Modern equivalents of the deprecated `txid_*` functions are `pg_current_snapshot`, `pg_visible_in_snapshot` and related functions.

The following points are inferences from the documented semantics, not claims made by PgQ:

- **It matches `NOTIFY` closely.** A committed transaction's events can be read straight away, whatever older transaction is still running. A transaction that was in flight lands in the first batch after it commits, which is exactly when its notification arrives. Rollbacks add nothing and need no wake-up. So the consumer needs no timer for held-back work, only the general fallback for lost notifications.
- **Order is commit order between batches and position order within a batch.** This keeps per-stream order: a later append to the same stream can only be written after the earlier append has committed, so it falls in the same batch or a later one, with a higher position.
- **It is more complex.**
  - The checkpoint is a snapshot value.
  - A batch has no natural `LIMIT`, so paging through a large batch needs an inner cursor, such as `(sn1, sn2, last position)`.
  - The rows and the snapshot must be read under the same snapshot, for example in one `REPEATABLE READ` transaction.

### 3. Keep reading in position order and handle gaps explicitly

- **Marten's high-water mark** advances one position at a time without jumping, so it "stops under any hole". The daemon asks "is any transaction still running that could have reserved it?" Once no such transaction remains, it skips the dead span in one step and records the skip in `mt_high_water_skips`. The setting `SkipStaleGapsDespiteLiveTransactionsAfter` defaults to null, which "never knowingly skips past a live appender". This keeps order and is safe by default, but processing stalls behind slow appenders. The documentation does not say which PostgreSQL mechanism the liveness check uses.
- **Axon's gap-aware tracking tokens** keep reading upwards from the last known position but record the gaps they meet and look for them again in later batches. The JDBC engine's defaults are `gapTimeout` 60 000 ms, `maxGapOffset` 10 000 (how far below the highest known position a gap is still tracked) and `gapCleaningThreshold` 250. This never stalls, but there are trade-offs. An event that fills a gap is delivered after events with higher positions. An event whose transaction takes longer than the timeout to commit, or that falls further back than the maximum offset, is silently dropped. An Axon maintainer calls the approach costly and points users to Axon Server instead.
- **Sequin's advisory-lock ceiling.** Each writer takes transaction-scoped advisory locks keyed on the position it expects. The reader takes the lowest locked position from `pg_locks` as a ceiling and reads `seq < ceiling`. Writes stay concurrent. However, the lock key is computed from the sequence's `last_value` before the insert actually draws its number, so the two are not paired atomically (an inference). That should be checked under concurrent writers before anyone relies on it.

With any gap-handling scheme, gaps left by rollbacks never trigger a notification, so the consumer needs a timed re-check of open gaps.

### 4. Hand out positions in commit order on the write path

If no writer can draw a position until the previous writer has finished, position order matches commit order. Then `position > checkpoint` is safe, and a notification for position *n* means every lower position is final. Gaps from aborts remain but do no harm.

- **Commanded EventStore** (Elixir) assigns global positions with `UPDATE streams SET stream_version = stream_version + $2 WHERE stream_id = 0 RETURNING ...`. Every append locks the `$all` stream row until it commits, which makes positions gapless and in commit order.
- **Counter tables** work the same way but serialise whole transactions. Dudycz calls this the "nuke option". In one forum benchmark, throughput fell from 1,600 to 120 requests per second (anecdotal).
- **Assigning positions at commit time** shrinks the serialised section. Cloudscale uses a deferred constraint trigger that runs `LOCK TABLE ... IN EXCLUSIVE MODE` and then `UPDATE ... SET sequence_id = nextval(...)`. Transactions run in parallel until commit and hold the lock only briefly. Sequin's variant also assigns `seq` at the end of the transaction.

Because `async.c` already serialises commits of notifying transactions under a lock held until after commit, an append path that issues `NOTIFY` on every commit is already serial at commit time. A commit-time position lock would therefore add the work done while holding it rather than a whole new point of serialisation. This is an untested inference. With this design, any position carried in a notification payload has to be sent from the deferred trigger, after the position is assigned.

### 5. Read a stream that is already in commit order (logical decoding)

A logical replication slot replays changes "in the order they were made on the origin server". The documentation also says "Concurrent transactions are decoded in commit order". Delivery is at least once: after a crash a slot can rewind, so consumers must be idempotent. This replaces `NOTIFY` plus table reads with the replication protocol. It removes the ordering problem, but the infrastructure is heavier. One team considered ordering by commit timestamps and rejected it because of indexing limits at tens of millions of rows and wraparound concerns (Precision Nutrition).

### Putting it together for a NOTIFY-driven consumer

| Approach | Consumer checkpoint | Held back by | Timer re-check needed for held work | Write-side cost |
|---|---|---|---|---|
| Transaction horizon | `(xid, position)` | any long write transaction, system-wide | yes | none |
| Snapshot difference | previous snapshot (plus an inner cursor) | nothing | no | none |
| Marten-style gaps | position | appenders still running | yes | none |
| Axon-style gaps | position plus gap set | nothing (can drop events) | yes | none |
| Commit-ordered positions | position | nothing | no | serialised commit section |

For a psycopg 3 event store moving off fixed-interval polling, the sources point to these rules:

- Treat each notification as a hint and combine several into one wake-up.
- Never take the checkpoint from the payload.
- After waking, repeat the frontier query until it returns nothing.
- Keep a fallback poll for lost notifications.

If appends can be serialised at commit, the commit-ordered option (Commanded's precedent, Cloudscale's deferred trigger) keeps the simplest consumer: one integer checkpoint and position order. If appends must stay concurrent, the snapshot difference fits `NOTIFY` wake-ups best (an inference). The transaction-horizon method is simpler but needs a timer for held-back work and can be stalled by unrelated long transactions. Gap tracking with timeouts trades correctness for liveness and should be avoided wherever a skipped event is unacceptable.
