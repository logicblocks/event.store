# How do stored xid8 transaction-id watermarks in a PostgreSQL event log behave after pg_upgrade, a pg_dump restore, or a logical-replication migration to a new cluster, and how can an event store keep consumer ordering correct across such moves?

## Question

An event store can stamp each appended row with `pg_current_xact_id()` (an `xid8`). Consumers then order by `(transaction_id, position)` and only read rows whose transaction is below `pg_snapshot_xmin(pg_current_snapshot())`, and they often persist the last transaction id they processed as part of their checkpoint. What happens to those stored `xid8` values, and to the comparisons built on them, when the database is moved by `pg_upgrade`, by `pg_dump` and restore, or by logical replication to a new cluster? How can the store keep consumer ordering correct across each kind of move?

## Findings

### The guarantee an xid8 makes, and its scope

PostgreSQL assigns real transaction ids "sequentially to transactions from a global counter used by all databases within the PostgreSQL cluster", when a transaction first writes. The 32-bit `xid` wraps every 4 billion transactions, and "a 32-bit epoch is incremented during each wraparound". `xid8` packs the two together: the epoch in the upper 32 bits and the `xid` in the lower 32 (`FullTransactionIdFromEpochAndXid` in `transam.h`). The documentation promises only that `xid8` "does not wrap around during the life of an installation". So monotonicity holds only within one counter lineage. The value stored in an event row is ordinary column data that any copy carries along unchanged. Whether it stays meaningful depends entirely on whether the destination continues the source's counter.

The source code makes the same point. The header of `xid8funcs.c`, whose 64-bit txids are credited to Marko Kreen of Skype Technologies (the Skytools and PgQ authors), notes that "xid8s frequently persist beyond the global xmin horizon, or may even be shipped to other machines". The `pg_resetwal` documentation names this hazard too. The epoch "is not actually stored anywhere in the database except in the field that is set by pg_resetwal", and "you might need to adjust this value to ensure that replication systems such as Slony-I and Skytools work correctly". Those are the earlier queue and replication systems that, like an xid-watermarked event store, persisted 64-bit txids.

### pg_upgrade: counter continuity is preserved

`pg_upgrade` copies the old cluster's counter into the new one. Its `copy_xact_xlog_xid` routine runs `pg_resetwal -f -x <old next xid>` and then `pg_resetwal -f -e <old epoch>` against the new data directory, under the comment "set the next transaction id and epoch of the new cluster". It also sets the frozen-xid and multixact limits. The same two calls appear in the 9.3 branch (then `pg_resetxlog` in `contrib`), the 9.6 and 10 branches, and current master, so this is long-standing behaviour. User data files are transferred with their relfilenodes kept, so stored `xid8` columns and sequence state arrive byte-identical.

The result is that every stored `transaction_id` stays below every xid the upgraded cluster will assign. Persisted `(transaction_id, position)` checkpoints remain valid, and the `transaction_id < pg_snapshot_xmin(pg_current_snapshot())` predicate goes on working with no remediation. Two caveats apply:

- Logical replication slots migrate only when the old cluster is 17.0 or later. Subscription state (the `pg_subscription_rel` table state and the replication origin) also migrates, so a store that additionally uses logical decoding must plan for that.
- `pg_upgrade` cannot help when the migration path is not `pg_upgrade` itself.

### pg_dump and restore: positions survive, the xid space does not

`pg_dump` includes sequence data by default (`--sequence-data` "is the default behavior"), and data-only dumps include "sequence values". So a `BIGSERIAL` position counter resumes correctly after restore. Nothing in `pg_dump` carries the cluster's transaction counter. The restore target keeps its own counter: for a freshly initialised cluster that is the low end of epoch 0 (the first normal xid is 3), and for a long-lived cluster it is whatever that cluster has reached. The restored `transaction_id` values are inserted verbatim. Three outcomes follow, depending on where the target's counter sits.

1. **Target counter below every stored value (the usual case for a new cluster).** Every new append gets an `xid8` smaller than all migrated history.
   - Ordering by `(transaction_id, position)` now sorts new events before old ones.
   - A consumer using the widely published checkpoint query, which keeps `last_processed_transaction_id` and `last_processed_position` and reads `transaction_id > last_processed_transaction_id` (event-driven.io), will skip every new event. That lasts until the target's counter passes the old maximum, which is billions of transactions away if the source had passed epoch 0.
   - The safe-read predicate `transaction_id < pg_snapshot_xmin(...)` is false for every migrated row. A consumer that had not drained before the move stalls on them indefinitely.
   - `pg_visible_in_snapshot` treats any value at or above the snapshot's `xmax` as invisible.
   - `pg_xact_status` on such a value raises `ERROR: transaction ID … is in the future` (`TransactionIdInRecentPast` in `xid8funcs.c`).
2. **Target counter between the minimum and maximum stored values.** New appends interleave with history. Some old rows read as committed and others as in the future, which is the worst case because nothing fails loudly.
3. **Target counter above every stored value (restoring into a busier, older cluster).** Comparisons happen to preserve old-before-new order, so ordering survives by luck. However, each stored value now aliases an unrelated transaction of the target. Any `pg_xact_status` or `pg_visible_in_snapshot` call about a stored id answers for the wrong transaction.

### Logical-replication migration: same problem, plus a pre-cutover trap

Logical replication matches columns by name. A subscriber column receives its own default only when the publication does not supply it, so a published `transaction_id` arrives as the publisher's value. The apply worker applies changes "in correct transactional order" (publisher commit order), but it does so in subscriber transactions that draw xids from the subscriber's own counter. After switchover the subscriber therefore faces exactly the three cases above.

Logical replication also does not carry the position counter. "Sequence data is not replicated": the subscriber's sequence "will still show the start value". For switchover, sequences "must be manually updated to latest values" (PostgreSQL 18 documentation). The PostgreSQL 19 development documentation adds `CREATE PUBLICATION … FOR ALL SEQUENCES` with an on-demand `ALTER SUBSCRIPTION … REFRESH SEQUENCES`, but sequences are still not replicated incrementally. They must be refreshed at cutover, after appends stop.

A trap specific to logical replication: consumers must not run the xmin-predicate read against a live subscriber. The predicate compares publisher-stamped ids with the subscriber's snapshot, but row visibility on the subscriber is set by apply commits. The following sequence is inferred from the documented semantics:

1. Publisher transactions T1 (xid 100) and T2 (xid 101) overlap, and T2 commits first.
2. On the publisher, xmin stays at or below 100 until T1 commits, so 101 is withheld.
3. On a subscriber whose counter is higher, T2's row is applied first and passes `101 < xmin`. The consumer advances past (101, p).
4. T1's row then arrives with `transaction_id` 100 and is skipped permanently.

Two related tools do not avoid the problem:

- `pg_createsubscriber`, which builds a logical replica from a physical standby, changes the system identifier with `pg_resetwal`. It requires the same major version on both sides. The replica starts from the standby's counter but then assigns xids independently.
- Upgrading a logical-replication cluster with `pg_upgrade` (all members 17.0 or later) keeps the topology, but it does not change the analysis for data that crosses a logical link.

A further option inferred from the documentation is to have the subscriber re-stamp rows. Column lists may omit `transaction_id` (insert-only publications may even omit replica-identity columns), so the subscriber's `DEFAULT pg_current_xact_id()` fills it with the apply transaction's id. This puts history into the target's xid space. However, the initial table sync is a single COPY-like transaction, so all pre-existing rows get one xid and their order collapses to position order. Existing consumer checkpoints therefore cannot be carried across this way.

### Keeping ordering correct across moves

**Detect a foreign xid space.** On a cluster that produced its own data, every committed `transaction_id` must be below the current snapshot's `xmax` ("all transaction IDs greater than or equal to xmax had not yet completed"). A startup or periodic check such as `SELECT max(transaction_id) >= pg_snapshot_xmax(pg_current_snapshot()) FROM events` (cheap with an index on the column) flags cases 1 and 2 and the subscriber trap. When it fires, the store should refuse to append or deliver until remediation runs. Case 3 cannot be detected this way, but it is also the case where ordering survives.

**Option A: fence the counter (self-hosted targets).**

1. Before the target accepts appends, stop it cleanly.
2. Run `pg_resetwal -e E`, where `E` is greater than the highest stored epoch: `floor(max(transaction_id)::text::numeric / 4294967296) + 1`.

Every subsequent `xid8` then exceeds all migrated values. Stored rows, persisted checkpoints and the xmin predicate all stay valid with no data rewrite. This is the remedy the `pg_resetwal` documentation describes for Skytools and Slony-I. Constraints:

- The server must not be running.
- Only "the user who installed the server" can run it, because it needs read and write access to the data directory. Hosted services that hide the data directory will not allow it.
- Outside that documented epoch use, the tool is a "last resort", and the epoch should only ever be raised.
- An alternative is to consume xids until the counter passes the old maximum. That is practical only when the gap is small, not when it spans an epoch.

**Option B: add an era column (works anywhere).**

- Keep a `current_era` row in a metadata table and stamp each event with `(era, transaction_id, position)`.
- Order and checkpoint on that triple.
- Use the safe predicate `era < current_era OR transaction_id < pg_snapshot_xmin(pg_current_snapshot())`. Rows from an earlier era are all committed by construction.
- Increment `current_era` as the last step of every logical move.

Existing checkpoints remain valid because old-era rows keep their relative order. The costs are a wider ordering key and index, plus discipline to bump the era, which the detection check above can enforce. This design follows from the primary facts here rather than from a documented product.

**Option C: normalise at cutover.** Rewrite migrated rows' `transaction_id` to a value below the target's counter. This collapses their order to position order, so it is safe only if every consumer has fully drained and is re-pointed at the head. It also costs a full-table update of an append-only log.

**Option D: do not persist xids.** Checkpoint on positions only and use xids, if at all, only transiently inside one cluster. Marten's high-water mark is the reference design: it "advances contiguously, so it stops under any hole in the event sequence" and asks "is any transaction still running that could have reserved it?" before skipping. Progress rows are stored in the database. Position-only checkpoints survive any move that carries the sequence:

- `pg_upgrade` carries it.
- `pg_dump` carries it by default.
- Logical replication needs a manual `setval` above `max(position)`, or `REFRESH SEQUENCES` on PostgreSQL 19 or later, before appends resume.

The trade-off is gap handling with timeouts instead of an exact commit-order watermark.

**Cutover procedure for any logical move.**

1. Stop appends on the source.
2. Let the dump finish, or let replication drain.
3. Move the sequence to at least `max(position) + 1`.
4. Apply Option A or bump the era (Option B).
5. Run the detection check.
6. Open appends and consumers on the target.

No xmin-based consumer should ever read from a subscriber that is still being fed. `pg_upgrade` needs none of these steps for xid continuity.
