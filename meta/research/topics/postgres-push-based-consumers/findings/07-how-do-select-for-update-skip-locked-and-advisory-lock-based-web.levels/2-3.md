# How do PostgreSQL-backed consumer groups assign and rebalance stream partitions among members, using hash-modulo membership, lease rows or advisory locks, when consumers join, leave or crash?

## Question

When several processes share the work of one logical subscription over a PostgreSQL event store, how do they decide which member owns which streams or partitions? How does that ownership move when a member joins, leaves cleanly or crashes? The three mechanisms in scope are hash-modulo membership, lease rows and advisory locks.

## Findings

PostgreSQL-backed systems use five designs. They differ in three ways: the unit of assignment (a stream, a projection, a hash segment or a whole subscription), who decides ownership (static configuration, first come first served, or an elected leader) and what releases ownership (a restart, the end of a database session, or an expired lease). In every design, per-key ordering holds only because a key has at most one owner at a time. Each handoff is a point where that rule can break.

### 1. Static hash-modulo membership (Message DB and Eventide)

Message DB builds consumer groups into its category read. If a caller passes both `consumer_group_member` and `consumer_group_size` to `get_category_messages`, the function adds the predicate `MOD(@hash_64(cardinal_id(stream_name)), $6) = $5`. It hashes the stream's cardinal ID to a 64-bit integer and keeps only the streams whose hash, modulo the group size, equals the caller's member number. It raises an error unless both values are given, the size is at least 1 and the member number is in the range 0 to size minus 1. The cardinal ID drops compound suffixes (the cardinal ID of `someStream-123+abc` is `123`), so related compound streams always go to the same member. Consumer groups work only for category reads; passing them to a single-stream read is an error.

Eventide promises that "any given stream is processed by a single consumer, and that the consumer processing the stream is always the same consumer." Each member must use its own consumer identifier, because positions are written to `{category}+position-{identifier}` streams. If two consumers share an identifier, they overwrite each other's position records and "skip messages."

Membership is pure configuration. `group_size` and `group_member` are set at startup, and neither Message DB nor Eventide documents any protocol for joining, leaving or failover. Three consequences follow from the design itself rather than from the documentation:

- **Crash:** if a member crashes, its share of streams stops until a process with that member number is restarted. No other member takes it over.
- **Resize:** changing `group_size` moves most streams to a different member. Each member's single category position only says how far it got through its old share, so a resize needs a coordinated stop. After that, the operator either accepts reprocessing (with idempotent handlers) or resets positions.
- **Cost:** the model needs no locks or coordination table, because the read query computes the assignment. Keeping exactly one process running per member number is left to an outside supervisor.

### 2. One advisory lock per unit of work

Several libraries give each named unit a PostgreSQL advisory lock. A unit can be a projection, a subscription or a set of subscriptions. Whichever process gets the lock does the work.

- **Marten (HotCold mode)** runs "a built in leader election function individually for each projection on each tenant database," which ensures that "each projection is running on exactly one running process." By default the lock is session-scoped (`pg_try_advisory_lock`). Setting `UseAdvisoryLockTransaction` switches to transaction-scoped locks (`pg_try_advisory_xact_lock`), which Marten calls "the better fit behind PgBouncer in transaction pooling mode." Marten also watches the lock (`UseMonitoredAdvisoryLock`, on by default) "so that it notices when the connection holding the lock is lost — a database restart or a fail-over." On graceful shutdown the locks are released before `Projections.StopAndDrainTimeout` runs out.
- **The Elixir EventStore** (the event store behind Commanded) allows "only one instance of a named subscription to a stream" to connect, across a whole cluster. It enforces this with session-level advisory locks keyed by two 32-bit values: the first is derived from the `oid` of the `subscriptions` table and the second identifies the subscription. If the connection dies, every lock owner gets a `lock_released` message, and "it is up to the lock owner to attempt to reacquire the lost lock." Inside the one instance that holds the lock, `concurrency_limit` lets several subscriber processes attach. Events go to them round-robin, unless a `partition_by` function sends all events with the same key to the same subscriber "to guarantee processing order."
- **Row locks instead of advisory locks** give the same claiming pattern. A reference implementation by Eugene Khyst locks the row of the subscription it is working on (`SELECT FOR UPDATE`) and uses `SKIP LOCKED` so other instances move on to "the 'next' subscription." Watermill's PostgreSQL adapter keeps one offsets row per consumer group and reads it with `SELECT ... FOR UPDATE`. A second member of the same group therefore waits on that row while the first member's transaction is open. pg_eventstore locks all subscriptions started by one manager as a single `SubscriptionsSet` and offers `force_lock: true` to take over a set that is already locked.

PostgreSQL's rules decide how these locks behave in failure. A session-level advisory lock "is held until explicitly released or the session ends." It also survives a rollback of the transaction that took it. A transaction-level lock is released when its transaction ends. Both kinds share a pool of shared memory sized by `max_locks_per_transaction` and `max_connections`. This has three consequences:

- **A crash only frees the lock once the server sees the session end.** With the default `client_connection_check_interval` of 0, the server notices a lost connection "only at the next interaction with the socket." Reliable detection "within a known timeframe" may require tuning `tcp_keepalives_idle`, `tcp_keepalives_interval`, `tcp_keepalives_count` or `tcp_user_timeout`.
- **Advisory locks detect a dead connection, not a stuck process.** A process that hangs while its connection stays open keeps its locks forever. In the other direction, network equipment that drops idle sessions causes false failovers: Wolverine's troubleshooting guide lists "Lost advisory-lock connection" as a trigger for leadership failover.
- **A session lock needs a long-lived connection of its own.** That is why Marten offers transaction-scoped locks for PgBouncer transaction pooling.

First come, first served is not load balancing. Marten's own documentation warns that its built-in distribution "is somewhat limited, and it's still likely that all projections will end up running on the first process to start up." A node that joins later gets no work, because a lock holder never gives up a lock on its own. Work only moves when the holder crashes or shuts down.

### 3. Lease rows renewed by heartbeat

A lease row is an ordinary table row that records who owns a unit and until when. The owner renews it regularly. Anyone may claim a row whose lease has run out.

- **Axon's token store** (JPA or JDBC, often on PostgreSQL) keeps one row per processor and segment. The row holds the progress token, the owner node and a timestamp. A processor must claim a segment before it processes events. If the owner fails to update its claim within `claimTimeout` (10 seconds by default), other threads or nodes may "steal" it. Free segments are retried every `tokenClaimInterval` (5000 ms by default). Axon warns that because of stealing, "an event may be handled twice (or more)," and strongly recommends idempotent handlers.
- **prooph's PDO projector** takes its lease with `UPDATE ... SET locked_until = ?, status = ? WHERE name = ? AND (locked_until IS NULL OR locked_until < ?)`. If the update does not change exactly one row, it fails with "Another projection process is already running." It extends `locked_until` as it makes progress.
- **PgQ's cooperative consumer** lets one logical consumer read a queue in parallel through named subconsumers. `pgq_coop.next_batch` locks the master consumer's subscription row `FOR UPDATE`. If a subconsumer "has active batch, but has been inactive more than i_dead_interval, the batch is taken over." The function copies the dead subconsumer's `sub_batch`, `sub_last_tick` and `sub_next_tick` to the new owner, then unregisters the dead one. Batches are not tied to keys, so this design gives up per-stream ordering in exchange for throughput.
- **Solid Queue** (Rails, job queue) shows a design choice that matters on takeover. Processes send a heartbeat every 60 seconds by default and count as dead after 5 minutes. When a dead process is pruned, its claimed jobs are marked failed rather than released, because the job itself may have killed the process.

Compared with advisory locks, leases detect a stuck process (it stops renewing) and work through any connection pooler, since they are ordinary rows written in short transactions. The costs are that takeover waits for the lease to expire, and that an owner which is slow but still alive may keep processing after its lease has been stolen. Both owners can then handle the same events. Axon's warning about duplicate handling describes exactly this case.

### 4. Hash segments separate from the number of members

Axon separates the hash space from the member count. A `SequencingPolicy` gives each event a sequence identifier; the default, `SequentialPerAggregatePolicy`, keeps each aggregate's events in order. The identifier is hashed and matched against segments with `mask == 0 || (mask & value) == segmentId`. Splitting a segment makes a new mask, `(mask << 1) + 1`, and produces two segments. Merging reverses this, finding the partner segment with `segmentId ^ firstBit`. Each segment has its own token.

When membership changes, whole segments move with their tokens, and no keys are rehashed. The new owner continues each aggregate from where the segment's token left off. This avoids the resize problem of static hash-modulo membership.

The segment count caps parallelism. A Tracking Event Processor uses one thread per segment and starts with 1 segment. A Pooled Streaming Event Processor starts with 16 segments, but `maxClaimedSegments` defaults to `Short.MAX`, so one instance can claim every segment. Spreading segments across nodes needs either `releaseSegment(segmentId, duration, unit)`, which lets go of a segment for a while so another node can claim it, or automatic balancing through Axon Server. Axon advises that "changing the number of segments requires care." To merge, the processor must own both segments being merged.

### 5. A leader assigns the work

Wolverine replaces Marten's lock grabbing with explicit assignment by a leader. It keeps running nodes in `wolverine_nodes` and agent placements in `wolverine_node_assignments`. With PostgreSQL storage, the leader is chosen with an advisory lock. The leader makes sure that "every single known asynchronous event projection and every event subscription is running on exactly one running node" and sends start and stop commands through control queues.

- **Join:** when nodes join, the leader rebalances "to purposely spread the running load across your entire cluster." The optional `AssignmentSettlePeriod` (off by default) makes the leader wait for the node set to settle during rolling deploys, up to `MaxAssignmentSettleTime`, or until `AssignmentSettleNodeCount` nodes are present.
- **Leave:** when a node leaves, its work is reassigned straight away.
- **Health checks:** node health is checked every `HealthCheckPollingTime`, and assignments are re-checked every `CheckAssignmentPeriod`.
- **Multiple databases:** with several databases, the agents for each database stay together on one node to keep the connection count down.

Leader election itself is often done with lease rows plus a notification that speeds up handover.

- **River** keeps a `river_leader` row (`leader_id`, `elected_at`, `expires_at`). The leader re-elects itself every 5 seconds, and the lease lasts for that interval plus 10 seconds of padding. Followers delete expired leader rows and then try to insert their own. On shutdown, a leader resigns with "a delete with NOTIFY." Followers then "try to win the next election after a very short random interval (to prevent all clients from bidding at once)."
- **Oban's database peer** writes to an `oban_peers` row whose `expires_at` is `started_at` plus the election interval (30 seconds by default). The upsert only extends a lease the node already holds, and expired rows are deleted before each election. A leader that shuts down deletes its row and broadcasts a leader-down notification, so the others re-elect at once instead of waiting for the lease to run out.

### Join, leave and crash compared

| Design | Member joins | Member leaves cleanly | Member crashes |
| --- | --- | --- | --- |
| Static hash-modulo (Message DB) | Every member must be restarted with a new `group_size`, and streams are remapped | Its share stops until it restarts | Same as leaving cleanly |
| Advisory lock per unit (Marten HotCold, Elixir EventStore) | No rebalancing; the new member gets only free units | Releases its locks; others take them on their next attempt | Locks free up when the server ends the session; how fast depends on keepalive settings |
| Lease row per unit (Axon tokens, prooph, PgQ coop) | Claims unclaimed units; balancing needs an explicit release | Releases its claims | Taken over after the claim timeout or dead interval; duplicate handling is possible |
| Hash segments (Axon) | Same as lease rows; segments move whole with their tokens | Same as lease rows | Same as lease rows |
| Leader assignment (Wolverine) | Leader rebalances, with an optional settle period | Work is reassigned at once | Health check notices; work is reassigned |

### What this means for a psycopg 3 consumer-group design (synthesis)

The following points combine the sources above. No single source prescribes them.

- **Separate the hash space from membership.** Hash stream IDs into a fixed number of virtual partitions, much larger than the expected number of members. Keep one checkpoint per group and partition, so a membership change moves partitions together with their checkpoints. This is Axon's segment model, and it avoids the resize problem of static hash-modulo membership.
- **Pick the ownership primitive deliberately.**
  - A session advisory lock keyed by group and partition, held on a dedicated connection, gives exclusive ownership and releases automatically on disconnect. That connection could be the same session that runs `LISTEN`. The costs are keepalive tuning, no protection against stuck handlers, and no support for transaction-mode poolers.
  - Lease rows (owner, `expires_at`) renewed by heartbeat work through poolers and detect stuck processes. The costs are idempotent handlers, and checkpoint writes that only succeed if the writer still owns the lease.
- **Add a real balancing step.** First-come claiming leaves all the work on the first process, as Marten's documented limitation shows. Either every member follows a fair-share rule (count live members from heartbeat rows, claim at most the partition count divided by members, rounded up, and release any extra), or an elected leader writes the assignments, as Wolverine does.
- **Use NOTIFY for fast handover on graceful leave or resignation,** as River and Oban do, and keep lock or lease expiry as the path for crashes. A missed notification then costs only latency, never correctness.
