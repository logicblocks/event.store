<p class="es-lede">
logicblocks.event.store is a set of building blocks for event sourcing in Python, built on asyncio.
You publish events to streams, fold them into state with projectors and, when you need to, keep that
state up to date in the background as events arrive.
</p>

This page assumes you know the ideas behind event sourcing. If you don't, start with the
[introduction to event sourcing](/event.store/event-sourcing/). The examples here use the same
shopping cart, `cart-42`.

## What you'll work with

Most of your code uses four parts of the library. Each one is built from one or two packages under
`logicblocks.event`, and each package has its own colour on this page.

<Capabilities />

The other packages work underneath. You'll import from `persistence` to connect to PostgreSQL. To
[write your own storage adapter](/event.store/guides/custom-storage-adapters/), you subclass
`EventStorageAdapter` from `store` or `ProjectionStorageAdapter` from `projection`, with helpers from
`sources` and `persistence`.

## The life of an event

Follow one event, a grinder added to `cart-42`, through the library. The first four steps are
always the same. Then pick a branch: work out the state **on demand** when you need it, or keep it
up to date **in the background** as events arrive. The chips at the top light up the packages each
step uses.

## Ideas behind the design

A few ideas explain most of the library's behaviour. Once they click, the rest of the API is
predictable.

<CardGrid>
	<Card title="Streams are addresses" icon="list-format">
		`store.stream(...)`, `store.category(...)` and `store.log()` don't touch storage, and nothing
		needs creating first. A stream exists once it has events.
		[Streams, categories and the log](/event.store/guides/streams-categories-and-logs/)
	</Card>
	<Card title="Everything reads the same way" icon="open-book">
		A stream, a category and the whole log are all event sources, read with `async for`,
		`read()` or `latest()`. So a projector or a subscriber works on any of them.
		[Reading events](/event.store/guides/streams-categories-and-logs/#reading-events)
	</Card>
	<Card title="Writes are conditional, not locked" icon="code-branch">
		Read, decide, then publish on condition that the stream hasn't moved. If it has, `publish`
		raises and writes nothing, so you read and decide again.
		[Concurrency and write conditions](/event.store/guides/concurrency/)
	</Card>
	<Card title="Storage is an adapter" icon="database">
		The event store, the projection store and the broker each hand storage to an adapter. Use the
		in-memory adapters in tests and the PostgreSQL ones in production. Your code stays the same,
		though [a few projection queries](/event.store/guides/projection-store/#in-memory-and-postgres-differences)
		behave differently in memory.
		[Using PostgreSQL](/event.store/guides/postgres/)
	</Card>
	<Card title="The broker allocates, subscribers read" icon="random">
		A broker only decides which subscriber reads which source. Subscribers read when they're
		polled. A distributed broker aims for one live subscriber per source per group across all your
		processes, though two can overlap briefly while a source moves.
		[Choose a broker type](/event.store/guides/event-processing/#choose-a-broker-type)
	</Card>
	<Card title="Processing is at least once" icon="approve-check-circle">
		Checkpoints are events too. After a crash, a subscriber carries on from its last saved
		checkpoint, so it may process some events again. Make processors safe to repeat.
		[Track and resume progress](/event.store/guides/event-processing/#track-and-resume-progress)
	</Card>
</CardGrid>
