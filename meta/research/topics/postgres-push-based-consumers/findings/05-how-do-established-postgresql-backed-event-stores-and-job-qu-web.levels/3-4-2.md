# Can an event store take its per-category ordering lock just before commit, for example from a deferred constraint trigger, so that the serialised part of each append transaction is as short as possible without losing commit-order guarantees?

## Question

Can a PostgreSQL event store take its per-category ordering lock at the end of the append transaction, for example from a `DEFERRABLE INITIALLY DEFERRED` constraint trigger? The aim is to keep the serialised part of each append as short as possible while readers still see a category's positions become visible in position order.

## Findings

### Short answer

Yes, with one hard condition and one hard limit.

- **Condition:** the ordering value (the global or category position) must be drawn *after* the lock is taken, inside the deferred trigger. It cannot come from a sequence default evaluated at `INSERT` time.
- **Limit:** the lock is still held through the commit itself: the commit record's WAL flush, any synchronous-replication wait, and the point where the transaction becomes visible. So a late lock removes only the work that sits between the append and `COMMIT`. It cannot shrink the serialised section below the cost of one commit.

PostgreSQL's own `NOTIFY` queue uses the same pattern: it takes an ordering lock as late as possible in the pre-commit sequence and holds it until after commit.

### Where deferred constraint triggers run in the commit sequence

The documentation defines constraint triggers this way:

- They must be `AFTER ROW` triggers on plain tables, specified `FOR EACH ROW` only.
- `INITIALLY DEFERRED` makes them fire "at the end of the containing transaction".
- `SET CONSTRAINTS ... IMMEDIATE` makes pending firings happen "retroactively" during that command.

PostgreSQL's `CommitTransaction()` (in `src/backend/access/transam/xact.c`) fixes where this happens:

1. A loop calls `AfterTriggerFireDeferred()` ("Fire all currently pending deferred triggers"). It then closes open portals and loops back in case they queued more deferred triggers.
2. Next come the pre-commit callbacks, `AfterTriggerEndXact`, `PreCommit_on_commit_actions()`, and then `PreCommit_Notify()`.
3. `HOLD_INTERRUPTS()` follows, then `RecordTransactionCommit()`. This calls `XLogFlush` when the commit is synchronous, or `XLogSetAsyncXactLSN` when `synchronous_commit` is off.
4. The synchronous-replication wait follows. Its comment notes that "at this stage we have marked clog, but still show as running in the procarray and continue to hold locks."
5. `ProcArrayEndTransaction()` follows. Its comment says this "must be done _before_ releasing locks we hold and _after_ RecordTransactionCommit".
6. Last, `ResourceOwnerRelease(... RESOURCE_RELEASE_LOCKS ...)` runs. The stated aim is to "release locks at the point where any backend waiting for us will see our transaction as being fully cleaned up."

Transaction-level advisory locks (`pg_advisory_xact_lock`) are "held until the current transaction ends; there is no provision for manual release." A session that already holds an advisory lock gets it again at once on later requests.

So a `pg_advisory_xact_lock(category_hash)` call inside a deferred constraint trigger is acquired at the start of commit processing. It is held until after the commit record is durable (under synchronous commit), after any synchronous standby has acknowledged, and after the transaction is visible to new snapshots.

### Why the ordering guarantee survives (when positions are drawn under the lock)

This argument follows from the source ordering above:

- Transaction T1 takes category lock L in its deferred trigger, draws positions, and commits.
- L is released only after T1 has left the proc array, so any snapshot taken after the release sees T1.
- Transaction T2 in the same category can draw a higher position only after it acquires L.
- Any snapshot that sees T2 was therefore taken after T2 left the proc array, which was after T1 did, so it also sees T1.

A category reader therefore never sees a higher position committed while a lower position in the same category is still in flight. If a lower position never appears, the transaction that drew it aborted after drawing it, for example because a later deferred check or the commit failed. That gap is permanent, never filled later, so a reader can skip it safely.

Asynchronous commit does not break the visibility ordering, because proc-array exit still comes before lock release. The documentation also says that after a crash "transactions are replayed in commit order", so a later commit cannot survive while an earlier one is lost. A consumer could still have acted on events that a crash then erases.

The precedent inside PostgreSQL is the notification queue:

- `PreCommit_Notify` takes a database-wide heavyweight lock with the comment "Serialize writers by acquiring a special lock that we hold till after commit. This ensures that queue entries appear in commit order".
- `xact.c` places that call "late in the pre-commit sequence to minimize time spent holding the notify-insertion lock."

That is the same design the question proposes, used by the server itself.

### The hard condition: positions must be drawn under the lock

Message DB, the usual model for per-category locking, does not draw positions under its lock:

- `write_message` calls `acquire_lock` first, which runs `pg_advisory_xact_lock` on a hash of the category. It then reads the stream version and inserts.
- `global_position` is a `bigserial` column, so its value comes from a sequence default at `INSERT` time, while the lock is already held.

That is correct for Message DB because the lock comes before the insert. If only the lock were moved to a deferred trigger, two transactions would draw positions in insert order but take the lock in commit order. That reopens exactly the out-of-order window the lock exists to close.

A deferred-lock design must therefore assign positions inside the trigger, for example with `UPDATE events SET global_position = nextval(...)` for the transaction's rows. Sequin's write-up recommends this late assignment ("make sure you don't touch `my_seq` until the last possible moment in your transaction", inserting first and updating `seq` just before `COMMIT`). It reports that assigning per-insert sequence values from a counter table in a `BEFORE INSERT` trigger gave lock durations "very high (seconds)" and write throughput "much lower than we needed."

This has consequences of its own:

- **Write amplification.** Readers need an index on the position column, so updating it cannot be a HOT update. HOT requires that "the update does not modify any columns referenced by the table's indexes". Every event is therefore written as two heap tuples, gets new entries in every index, and leaves a dead tuple for vacuum.
- **Nullable column.** The position column must be nullable at insert time. Other sessions never see the `NULL` because the update happens before commit, but `NOT NULL` cannot be declared.
- **Per-row firing.** Constraint triggers are row-level only, so an N-event append queues N firings. A practical shape (an inference, not taken from a published store) is to have the first firing take the lock and number every row the transaction inserted, and later firings do nothing. Repeated lock requests by the holder succeed immediately.
- **Order within a transaction.** This should come from an explicit column set at insert time, not from trigger-firing order. The documentation defines firing order only as alphabetical by trigger name for triggers on the same event.
- **Avoiding the per-row rewrite.** Writing one commit-order row per transaction and ordering events by (commit number, ordinal within transaction) would avoid it. This is a design inference; none of the stores examined does it.

### What stays serialised, and where the gain actually is

Even with the lock taken in a deferred trigger, the section holding the category lock still includes:

- the trigger's own work (numbering every event in the batch);
- any deferred triggers and on-commit actions that run after it;
- `PreCommit_Notify`, including waiting for its database-wide lock, if the append also issues `NOTIFY`;
- inserting the commit record and, under synchronous commit, flushing WAL;
- any synchronous-replication wait;
- the proc-array exit.

Group commit lets "other server processes ... add their commit records to the WAL buffers so that all of them will be flushed by the leader's eventual sync operation". Two commits in the same category can never share a flush, though, because the second cannot draw positions or write its commit record until the first has flushed and released the lock. This is an inference from the commit ordering above. Group commit still helps across categories, but per-category throughput is capped at roughly one commit per (WAL flush latency + synchronous-standby round trip + lock hand-off + trigger work), wherever the lock is taken.

The only thing a deferred trigger removes from the serialised section is work between the append and `COMMIT`:

- extra client round trips;
- other statements in the unit of work, such as projection updates or outbox writes;
- application logic;
- the expected-version read.

For a single-statement, auto-committed append, the gain is close to nil. Existing stores already put the lock near the end in that case:

- The Python `eventsourcing` library takes `LOCK TABLE ... IN EXCLUSIVE MODE` (with `SET LOCAL lock_timeout`) immediately before inserting stored events. Its stated aim is that "the insert order [is] the same as the commit order" so "readers don't pass over gaps that are filled in later".
- Commanded's EventStore draws `$all` positions with `UPDATE streams SET stream_version = stream_version + $2 WHERE stream_id = 0` inside the insert statement. That row lock serialises every append from that statement until commit.

The gain is real for multi-statement transactions, where the lock would otherwise be held across every later statement and network round trip. Practitioners report the cost of holding such a lock for the whole transaction:

- Laurenz Albe warns that a counter-table sequence "will serialize all transactions that use that 'sequence'" and advises keeping those transactions short.
- Oskar Dudycz rejected that approach for outbox messaging because "the performance hit was...too big to accept", preferring transaction-ID (`xid8`) filtering.

### Hazards specific to the deferred-trigger placement

- **The trigger may silently not fire.** Ordinarily enabled triggers fire only when `session_replication_role` is `origin` or `local`. Logical replication apply sets it to `replica`, so the trigger must be `ENABLE ALWAYS` if rows can arrive that way. The enable status of a deferred trigger "is checked when the event occurs, not when the trigger function is actually executed." A row inserted with the trigger disabled commits with a `NULL` position and is invisible to position-based readers forever.
- **Early firing.** `SET CONSTRAINTS ALL IMMEDIATE` anywhere in the transaction fires pending deferred triggers retroactively. That takes the lock early: still correct, but the lock is held longer.
- **`COMMIT` becomes a lock wait.** It can now block and fail through `lock_timeout` (which covers explicit and implicitly acquired locks), `statement_timeout` or deadlock detection. Clients must treat a failed commit as a failed append and retry. Deadlocks become possible if a deferred trigger that runs after the lock-taking one, such as a deferrable foreign-key or uniqueness check, waits on a row lock held by a transaction that is itself queued for the category lock.
- **Optimistic concurrency loses its lock.** Message DB checks the expected stream version under the category lock. Without that, a non-deferrable unique index on (stream, position) must enforce it: "the would-be inserter must wait to see if that transaction commits" and then gets a uniqueness violation. Keeping that constraint non-deferrable puts the wait at insert time, outside the serialised section.
- **Session-level locks are not a substitute.** prooph's PDO event store offers an optional Postgres write-lock strategy. It takes a session-level `pg_advisory_lock(hashtext(...))` named after the stream table before the insert and calls `pg_advisory_unlock` after the insert returns, with transactions managed by the caller. Reading the code (not a documented claim), the order holds only when the insert auto-commits. Releasing a session lock before an outer transaction's `COMMIT` reopens the out-of-order window.
- **Ordering across categories is unchanged.** A per-category lock orders positions only within a category. Readers of the global sequence across categories still need gap detection or transaction-ID filtering, as with Message DB.

### Status of the evidence

Message DB, Commanded EventStore, Python `eventsourcing` and prooph's PDO event store all take their ordering lock at append time. None takes it from a deferred trigger. The deferred-trigger design rests on documented PostgreSQL behaviour and the commit-sequence code, together with the server's own use of the pattern for `NOTIFY`, rather than on a published production event store.
