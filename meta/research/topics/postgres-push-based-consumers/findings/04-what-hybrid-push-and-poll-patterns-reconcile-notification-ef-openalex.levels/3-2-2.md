# What append-throughput cost does serialising PostgreSQL event appends so that position order equals commit order impose, compared with snapshot-xmin gating that tolerates concurrent appenders?

## Question

If a PostgreSQL event store assigns positions from a sequence before commit, how much append throughput does it lose by making appends run one at a time, so that position order matches commit order? How does that compare with letting appenders run concurrently and having consumers gate their reads on the snapshot's xmin?

## Findings

### The two designs being compared

When positions are drawn from a sequence before commit, they can become visible out of order. A transaction holding position 101 may commit before the one holding 100, and a consumer that moves its cursor to 101 will never see 100. There are two common ways to prevent this.

- **Serialised appends.** Every append takes one exclusive lock before drawing its position and keeps it until the transaction ends. In PostgreSQL this is typically a transaction-scoped advisory lock or a table lock. The next appender cannot draw a position until the previous one has committed. Position order therefore equals commit order, and a consumer can safely read "everything after my last position".
- **Snapshot-xmin gating.** Appenders run concurrently, and each row records the ID of the transaction that wrote it. A consumer only reads past rows whose writing transaction is older than its snapshot's xmin, which is the oldest transaction still running when the snapshot was taken. Every transaction below xmin has finished, so no earlier event can still appear behind the consumer.

### Serialising turns lock hold time into a hard throughput ceiling

Serialised appends form a queue with a single server. The most they can commit, in append transactions per second, is one divided by how long the lock is held. Adding more appenders does not raise this ceiling. It only lengthens the queue, and append latency rises steeply as the arrival rate approaches the ceiling. This is basic single-server queueing, not a result from the sources below.

The literature shows why the hold time is long when a lock is held until commit:

- **Commit logging can outlast the work itself.** Graefe et al. observe that in databases with a large buffer pool "a transaction may run in less time than it takes to log the transaction's commit record on stable storage". Early lock release lets a transaction drop its locks as soon as its commit record is in the in-memory log buffer. They report that this "cuts overall lock duration to a fraction and reduces lock contention accordingly" (Controlled lock violation).
- **Locks held during the log flush limit scaling.** Johnson et al.'s Aether paper identifies four logging-related barriers to database scalability, and transactions holding locks while they wait for the log flush is one of them. A follow-up journal paper extends the analysis to multicore and multisocket hardware.
- **Early lock release has been evaluated directly.** Athanassoulis et al. test it as a way to raise OLTP concurrency.

A serialised PostgreSQL append is exactly this lock-held-across-flush case. PostgreSQL releases a transaction-scoped lock only when the transaction ends: after the commit record is flushed and, if synchronous replication is configured, after a standby acknowledges it. This describes PostgreSQL's commit sequence; the scholarly sources do not cover it and it should be checked against the server version in use. The serial section is therefore roughly:

> hold time ≈ statement work after the lock is taken + client round trips while it is held + commit WAL flush (+ synchronous standby round trip, if configured)

There is a second cost. Group commit normally lets concurrent committers share one WAL flush. A serialised appender never commits alongside another appender, so every append pays for its own flush. In the concurrent design, that flush cost is shared across the group.

Some illustrative figures (arithmetic, not measurements):

- A 1 ms hold time caps serialised appends at about 1,000 append transactions per second.
- A 5 ms hold time, as with networked storage or a synchronous standby, caps them at about 200 per second.

These caps hold whatever the number of clients or cores. Putting several events in one append transaction raises events per second, but not transactions per second.

### Xmin gating keeps concurrency and moves the cost to read-side latency

Under xmin gating, appenders share no lock that lasts until commit. What they still share are short critical sections: drawing the next sequence value, inserting at the rightmost leaf of the position index, and inserting into the WAL. None of these is held across the commit flush, and concurrent commits can share flushes through group commit. Throughput therefore grows with the number of appenders until the WAL or the hardware saturates, which is a much higher limit than the serialised ceiling. The extra work on the append side is storing one transaction ID per row. On the read side, taking a snapshot to read its xmin costs the same as taking any snapshot.

The multicore database literature favours avoiding a central ordering point over paying for one:

- **Silo** "avoids all centralized contention points, including that of centralized transaction ID assignment", yet still provides serializability and correct logging and recovery (Speedy transactions in multicore in-memory databases). It recovers a durable order afterwards, at coarse granularity, instead of forcing every commit through one ordered point. Xmin gating follows the same idea: commits are not forced into position order, and the consumer works out a safe-to-read boundary from snapshot state afterwards.
- **Eleda** shows that the database's own central log buffer is already a multicore bottleneck that needs dedicated engineering (Scalable database logging for multicores). Serialising appends adds a second, coarser serial section on top of it, covering the whole transaction and its flush rather than just the copy of the log record.

Gating is not free, but its costs fall outside append throughput:

- **Delivery latency.** An event cannot be delivered until every transaction older than it has finished, so one slow append holds up all later events, even ones already committed.
- **Unrelated sessions can stall delivery.** Snapshot xmin covers every running transaction, not just appenders, so long-running or idle-in-transaction sessions elsewhere also hold consumers back.
- **More complex consumers.** The consumer's cursor and query must take transaction IDs into account, not just positions.

With serialisation, by contrast, an event can be delivered as soon as it commits.

### SERIALIZABLE isolation is not a substitute

PostgreSQL's SERIALIZABLE level uses Serializable Snapshot Isolation (SSI). Ports and Grittner describe it as the first SSI implementation in a production database release, and the first in a database that had no earlier lock-based serializable level (Serializable snapshot isolation in PostgreSQL). SSI guarantees results equivalent to *some* serial order without blocking, but that order need not be commit order, and drawing a sequence value is non-transactional. So raising the isolation level does not make position order equal commit order. It adds conflict tracking and serialization-failure retries while leaving the visibility gap open. This conclusion follows from how SSI is designed; the paper does not discuss event positions.

### Reducing the cost of the serialised design

If position order must equal commit order, the only options are to shorten the hold time or spread it over more events:

- **Take the lock as late as possible.** Send the lock, the insert and the commit in one round trip, for example through pipelining or a single server-side function.
- **Append several events per lock acquisition.**
- **Use asynchronous commit for append transactions.** PostgreSQL then makes the commit visible and releases its locks before the WAL flush. This is in effect early lock release, and commit order is kept. The trade-off is that a crash can lose recently acknowledged appends that consumers may already have read.

Serialising per stream instead of globally reduces contention, but it only orders positions within each stream. A consumer reading the global log is still exposed to out-of-order visibility.

### Answer

Serialising appends caps throughput at about one append transaction per lock hold time, however many appenders there are. In PostgreSQL that hold time includes the commit WAL flush and any synchronous standby round trip, and serialisation also prevents group commit. Storage flush latency therefore sets the ceiling: on the order of hundreds to low thousands of append transactions per second for one database.

Xmin gating removes that ceiling, and throughput grows with concurrent appenders up to the WAL and hardware limits. In exchange, an event is delivered only once the oldest in-flight transaction finishes, which makes delivery latency depend on activity anywhere in the cluster.

The sources establish the general penalty of holding locks through the commit flush and of central ordering points. None of them benchmarks PostgreSQL event appends, so the actual throughput ratio for a given deployment has to be measured.
