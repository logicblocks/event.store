# Is PgDog's transaction-mode LISTEN and NOTIFY support, with its at-most-once delivery and buffered forwarding, reliable enough in production to replace a dedicated session-mode listener connection?

## Question

PgDog, a Rust connection pooler for PostgreSQL, intercepts `LISTEN`, `NOTIFY` and `UNLISTEN` in transaction mode and handles them through its own dedicated server connection. Is that reliable enough to replace the usual pattern of one long-lived session-mode connection per listening process? The consumer in question is an event-sourcing library built on psycopg 3 that wants to stop polling on a fixed interval.

## Findings

**Short answer.** It can stand in for a dedicated session listener only if notifications are treated as wake-up hints and a bounded catch-up poll is kept. PgDog's own authors say the same: "If you're building systems that require 100% message delivery guarantees, consider storing messages in a Postgres table and using a secondary polling mechanism." For an event store that already reads from its own log by position, that is acceptable. It is not a drop-in replacement where the consumer counts on notifications to learn about every commit, or on a dropped connection to tell it when to catch up.

**How the feature works.** Pub/sub is off by default. Setting `pub_sub_channel_size` (the docs use 4096 as the example) in `pgdog.toml` turns it on and sets the size of the background queue. Three things happen once it is enabled:

- **LISTEN.** PgDog registers the channel with Postgres once per pool over a single standalone connection, however many clients listen on that channel.
- **Fan-out.** Each incoming `NotificationResponse` goes out to subscribed clients through a Tokio `broadcast` channel. Postgres therefore sends each message once per PgDog instance rather than once per client.
- **NOTIFY.** Statements go onto an `mpsc` queue with the same capacity. The listener task then sends each one to Postgres as a plain `NOTIFY "channel", 'payload'` query, outside any transaction.

A `NOTIFY` issued inside a client transaction is kept in a per-client buffer. The buffer is cleared on rollback or error and flushed only after the transaction ends. PgDog says this preserves transactional semantics while avoiding PostgreSQL's commit-time contention for in-transaction notifications. The registry is keyed by database, user and shard, so each pool has its own channels. After an error, the listener waits `connect_attempt_delay` and reconnects. It then re-issues `LISTEN` for its pool's channels and keeps its identity across a primary promotion.

**Where messages can be lost, and why it matters more than with a direct connection.** The docs promise LISTEN and UNLISTEN delivery with eventual consistency, but NOTIFY only "at most once". The source and design notes show four ways a notification can go missing:

1. **Silent gaps when the backend connection breaks.** If PgDog's dedicated connection to Postgres drops, in-flight notifications are not re-sent. Nothing Postgres emits while the listener is reconnecting reaches anyone. The backoff and re-LISTEN happen inside PgDog, and the client's own connection stays open. The source shows no step that tells subscribed clients about the gap. This is the main difference from a direct session listener. A direct listener also loses notifications while it is disconnected, but the client sees the connection fail and knows to catch up. Behind PgDog the gap is probably invisible to the client.
2. **Slow consumers are dropped.** The per-client forwarding task reads from a broadcast channel whose capacity is `pub_sub_channel_size`. A subscriber that falls behind gets `RecvError::Lagged`. PgDog only increments a "dropped" counter, exposed through `SHOW LISTENERS` and OpenMetrics, and carries on. The client is not told.
3. **LISTEN is acknowledged before it takes effect.** PgDog replies to `LISTEN` and `NOTIFY` at once without waiting for Postgres. The blog notes "a short delay between when the first command is acknowledged and messages start to arrive" for the first subscriber to a channel. This breaks the usual "LISTEN, then run the catch-up query" pattern. A commit that lands in that window can be missed even though LISTEN has already succeeded. A race in first-time registration was also fixed only in June 2026 (PR #1079).
4. **NOTIFY is no longer tied to the commit.** A buffered NOTIFY lives in PgDog's memory until COMMIT. It then waits in an in-process queue for the listener connection, and nothing waits for Postgres to execute it. If PgDog crashes, restarts or is redeployed between the commit and the forward, the notification is lost while the data stays committed.

Some smaller semantic differences follow from the design. These are inferred from the source, not documented:

- The notifying PID that clients see is PgDog's listener backend, not the sender.
- Buffered notifications are sent one by one outside a transaction, so Postgres's merging of duplicate notifications within a transaction does not apply.
- The listener builds the forwarded statement by string interpolation. I could not tell from the code read whether payloads are re-escaped earlier in the path, so payloads containing quotes should be tested.

PgDog's interception is described only for the `NOTIFY` statement, which is parsed specifically since PR #1078. Notifications raised with `pg_notify()` from triggers or functions would therefore probably run on the client's pooled server connection and keep Postgres's commit-time delivery. I did not confirm this.

**Maturity record.** The feature shipped in August 2025 (PR #301). Its tracking issue carried the "bleeding edge" label under the "Road to v1" milestone. PgDog is still on 0.1.x, with v0.1.60 released in September 2026. Its README says "most features are stable, while some are experimental", without saying which category pub/sub is in. Correctness fixes have kept arriving:

- **April 2026 (PR #925):** the pub/sub listener had to be re-initialised after failover.
- **March 2026 (PR #800):** session-mode pools wrongly rejected LISTEN and NOTIFY with "pub/sub disabled".
- **June 2026 (PR #1079):** fixed the first-registration race described above.
- **July 2026 (PR #1285, v0.1.52):** channels were global rather than per database. With several databases, listeners got another database's notifications and missed their own.
- **September 2026 (v0.1.57):** `DISCARD` now clears a client's notification channels.
- **September 2026 (issue #1512, fixed in v0.1.59):** a protocol violation in which `LISTEN` sent through the extended protocol in a pipeline returned `ReadyForQuery` before `Sync`. It was reproduced with psycopg 3, which failed with `unexpected result status from query: PIPELINE_SYNC`.

Issue #1462 is still open. `client_idle_timeout`, which is off by default, can only be set globally and closes any client that sends nothing, so it disconnects silent LISTEN clients. One reporter cited about 8,400 disconnect errors a day in production. PR #1467, which adds per-user and per-database overrides, has not been merged.

**What this means in practice.** Using PgDog's transaction-mode pub/sub in front of the event store makes sense under these conditions:

- Run v0.1.59 or later. That covers the psycopg 3 pipeline fix and the per-pool channel scoping.
- Leave `client_idle_timeout` off for listener clients, or have them send periodic traffic.
- Size `pub_sub_channel_size` for bursts and alert on the dropped counter.
- Most importantly, keep a catch-up read from the consumer's last-processed log position, triggered by each notification and also run on a bounded timer. That timer caps how stale a silently missed event can get.

Under those conditions PgDog's design brings real benefits: one Postgres registration per channel per instance, cheap fan-out to thousands of clients, and no per-process session connection. If missed signals must instead be detectable, a session-mode connection still gives stronger guarantees. That can be direct to Postgres or through a PgDog session-mode pool, which since PR #800 passes LISTEN and NOTIFY straight to the backend. Either way the delivery is at commit time, comes from the real backend, and a broken connection is visible to the client. Even then, a catch-up read is needed after every reconnect.
